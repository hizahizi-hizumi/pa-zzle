# 自己説明的なコード

- 実装が何をしているか、どうしているかは、コメントではなく、名前・型・データ構造・関数やモジュールの分割・制御フロー・設定構造などコード自身で表現する。
- 何をしているか、どうしているかを説明するコメントが必要に見えたら、コメントを足す前に、命名改善、条件や中間値の名前付け、処理抽出、定数化、責務分割、制御フローの単純化で自己説明的にできないか検討する。
- コードを逐語的に言い換えるコメント、処理手順をナレーションするコメント、構造を見出しコメントだけで補う実装は書かない。
- コメントは、コードだけでは合理的に表現できない次の情報に限る。
  - なぜその実装・制約・例外処理が必要なのかという理由
  - 外部システムや仕様に由来する非局所的な制約・特異挙動
  - コードだけでは表現しきれない不変条件や前提。ただし型・契約・構造で表現できるなら先にそちらへ移す
  - 意図的に選んだ非自明なトレードオフ、回避策、互換性上の理由
  - 本当に複雑な処理を読むために必要な高レベルの「何をしているか」。個々の手順は説明しない
- 一見すると単純化・削除できそうなコードを意図的に残す場合は、将来の変更で壊されないために必要な理由だけをコメントに残す。
- 運用手順、変更履歴、過去の実装との比較を実装コメントに残さない。現在も有効な制約だけを現在形で記述する。
- コメントは短く局所的に保つ。説明が長くなる場合は、まずコード側の責務や構造が大きすぎないか見直す。
- 公開APIのドキュメント文字列やAPI文書は実装コメントと分けて扱い、利用者に必要な目的・契約・使用上の制約は記述してよい。ただしシグネチャ、型、実装手順を重複して説明しない。
