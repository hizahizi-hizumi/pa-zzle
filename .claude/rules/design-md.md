# DESIGN.md 作成ルール

`DESIGN.md` を書く・変える際の、書く範囲・構成・用語・トークンの扱いのルール。

## 1. 書く範囲

- アプリ全体で共有するデザインシステムだけを書く。決まりは「どの意味・状態・場面のときに、どう見せ、どう反応させ、どう聞かせるか」の単位で書く
  - 画面の判断が、根拠のないままアプリ全体の決まりとして読まれないようにする
- 次は書かない
  - 特定の画面・ゲーム・コンポーネント実装を名指しした決まり。共通部品は種類（操作ボタン・選択肢・ゲームピクトグラムなど）で呼ぶ
  - 何を表示するか・しないかの選択
  - `APP.md`・`GAME.md` と重なる内容（アプリとゲームの分担、揃えること自体を目的にしない、など）
- 一つの画面の要求を一般化して決まりにしない。複数の画面・ゲームで同じ意味を持つと確かめたものだけを足す

## 2. 構成

- 正式フォーマット（Google Labs DESIGN.md Format）の8節に、次の日本語見出しの `##` 節で、この順に従う。番号は付けない。決まりが無い節は省く
  1. 概要: 人格、与えたい印象、表現の強さ。個別の決まりが無いときの判断の拠り所
  2. 色: 色の体系と、各トークンの役割・使い分け
  3. タイポグラフィ: 書体の使い分けと、文字階層の各段の役割
  4. レイアウト: 余白・密度・画面幅への対応
  5. 奥行き: 面・影・レイヤーによる前後関係の示し方
  6. 形: 角丸・境界による形の言語
  7. コンポーネント: 共通部品の種類ごとの指針
  8. すべきこと・避けること: どの節にも収まらない短い歯止め
- 8節に収まらないアプリ全体の決まり（操作と状態、動き、音など）は独自の `##` 節にし、「コンポーネント」と「すべきこと・避けること」の間に置く
- `#` 見出しは表題だけに使う
- 1項目だけの `###` 節を作らない
- 一つの決まりは一か所にだけ書く。複数の節に関わる決まりは、最も近い節に置き、他の節で言い直さない

## 3. 用語

- 表現の強さの段階は、平常・操作・解く場面・達成と呼ぶ。場面の呼び方（選ぶ・解く・結果）と食い違わないようにする

## 4. 値とトークン

- 正確な値（色値・数値・フォント名など）は書かない。値の正本 `frontend/styles/globals.css` の `@theme` への参照を、表題の直後、最初の `##` 節より前に1か所だけ置く
- YAML front matter やトークンのコードブロックは置かない
  - 値を `@theme` と二重に持たないため
- トークン名を書く・変える前に `@theme` を読み、そこにあるトークンだけを書く
- トークン名は `@theme` の名前から先頭の `--` を除いて書く。色のトークンは `--color-` を除いた名前で書く（`--color-primary` は `primary`、`--radius-sm` は `radius-sm`）
- トークンは、名前と、そのトークンを使う意味・状態を言葉で定義した文で書く
- DESIGN.md でトークンの定義を足す・変える・消すときは、同じ変更で `@theme` も揃える。意味と使い分けを決めないまま、トークンや段階の定義を足さない
