# 画面文書作成ルール

`docs/プロダクト/画面/` の画面文書を新規作成・編集する際の、書く範囲・構成・記法のルール。

## 1. 書く範囲

- 仕様に書かれていない場面でその画面を足す・変える・レビューするとき、作業者がプロダクトオーナーと同じ方向に判断できるようにすることだけを書く
- その画面について、コードから読めない今の意図（Why / Why not）だけを書く。画面の仕様と、コードから読める What / How（配置、構成、大きさ、動きの手順、表示項目の並びなど）は書かない
- 何を表示するか・しないかは、遊ぶ人が知る価値があるかの判断と、その理由を書く
- 次は書かない
  - 要求・要件・仕様と、`APP.md`・`GAME.md`・`DESIGN.md` で言えていること
  - 複数の画面で同じ意味を持つ見せ方の決まり。それは `DESIGN.md` が持つ
  - 別の画面の決まり。決まりは、その画面の文書にだけ書く
- 1文ごとに「この文が無ければ、作業者はこの画面でどんな判断を誤るか」に答えられるものだけを残す
- 意図のある決まりが一つも無い画面には、文書を作らない

## 2. 構成

- 1つの画面を1つの文書にし、ファイル名を `SCR-nnn.md` にする。番号に意味を持たせない
- YAML フロントマターには `id: SCR-nnn` だけを置き、`upstream` は持たない
- `#` 見出しは表題だけに使い、表題は画面名にする
- 表題の後に次の `##` 節をこの順に置く。見出しは次の語をそのまま使い、番号は付けない。該当する決まりが無い節は省く
  1. 目的: 遊ぶ人がその画面で何を得るか
  2. 優先すること: その画面で何を強く見せ、何を退かせるかと、その理由
  3. やらないこと: 一般には良さそうに見えるが、その画面ではやらないことと、その理由。他の節で言えているものは書かない

## 3. 記法

- 決まりは箇条書きの1項目に1つ書く
- 要求・要件・仕様の決まりに触れるときは、言い直さずに ID で指す
- 別の画面に触れるときは、その画面の文書の表題で呼ぶ
