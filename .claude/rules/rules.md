# ルールの書き方

## 文言

- 短いほどよい
- 叶えたい正の姿を書く

  ```
  OK:
  - ボタンは `@/components/ui/button` の `Button` を使う
  NG:
  - 独自のボタンコンポーネントを作らない
  ```

- 意図が伝わる最小の文言で書く
- 文言だけで伝わらないときは例を添える
  - 例は項目の下のコードブロックに書く
  - 項目どおりの書き方はルールに書くときの形のまま `OK:` の下に示す
  - `OK:` の例だけでは境目が伝わらないときは項目に反する書き方を `NG:` の下に示す
  - 複数行にわたる例を並べるときは例ごとに `OK:` か `NG:` を付ける
- 1項目に1つの決まりを書く
- 大事な決まりもほかと同じ書式と語調で書く

  ```
  OK:
  - トークンの名前を変えたら同じ変更で `DESIGN.md` も直す
  NG:
  - トークンの名前を変えたら**同じ変更で** `DESIGN.md` も直す
  - トークンの名前を変えたら必ず同じ変更で `DESIGN.md` も直すこと
  - IMPORTANT: トークンの名前を変えたら同じ変更で `DESIGN.md` も直す
  ```

## 内容

- 決まりと手順だけを書く

  ```
  OK:
  - 色は `frontend/styles/globals.css` の `@theme` のトークンで指定する
  NG:
  - 色は `frontend/styles/globals.css` の `@theme` のトークンで指定する
    - 色を一か所で変えられるようにするため
  ```

- コードと一般知識から分からないことだけを書く

  ```
  OK:
  - `_private` で export したものはテストからだけ参照する
  NG:
  - テストから参照する内部の要素は `_private` にまとめて export する
  - 関数名は処理の内容が分かる名前にする
  ```

- 守れたかを確かめられる形で書く
- コードと一般知識のほかは、そのルールと本文に書いたパスの文書だけで守れるように書く
- ほかのルールの決まりやデザイントークンの値のようにルールの外で定まるものは置き場所のパスと読むタイミングだけを書く

## ファイル

- 1ファイルで1つの関心だけを扱う
- 同じ対象への1つの決まりは1つのルールファイルにだけ書く
- フロントマターには `paths` だけを書く
- `paths` を書くときはそのルールを守る必要があるファイルに過不足なく一致させる
