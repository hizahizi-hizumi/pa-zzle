# 文書ルール

pa-zzle の文書に何を書き、どう保つかのルール。いつ読むかは `AGENTS.md` を正とする。

## 1. 文書の存在目的

- 文書は、コードからは読めない次のものを、人とエージェントが失わないためにある
  - 何を目指し、何を保証するか。実装が正しいかを判定する基準にする
  - 今の決まりと、その意図。決まりを知らずに戻さず、決まりの無い場面でも同じ方向に判断できるようにする
  - どう作業するか。手順・手引きで、コードや設定からは読めない進め方をそろえる
  - どう意思決定してきたか。意思決定の記録（ADR）で、将来の意思決定に一貫性を持たせる

## 2. どの文書に何を書くか

| 文書 | 書くもの |
|---|---|
| `docs/プロダクト/要求/` | 利用者が実現したい状態 |
| `docs/プロダクト/要件/` | 製品として保証する能力・性質 |
| `docs/プロダクト/仕様/` | 要件を満たすための今の決まり。アプリ・ゲーム共通の取り決めと、パズルごとのルール・評価・難易度の定義 |
| `docs/プロダクト/画面/` | 画面ごとの目的と、その画面で優先すること・やらないことの意図。画面の配置・構成は書かない |
| `APP.md` | アプリ全体の体験で大事にすること。アプリとゲームの分担 |
| `GAME.md` | 1つのゲームを遊ぶ体験で、全ゲームに共通して大事にすること |
| `DESIGN.md` | アプリ全体のデザインシステム。見た目・操作への反応・動き・音の使い分け |
| `docs/パズル/` の難易度文書 | 難易度の意味と、作るときの手引き |
| `docs/adr/` | 将来の意思決定に一貫性を持たせるための、プロジェクト全体の意思決定の記録。何を、どんな前提で、何と比べて決め、なぜそうし、何が起きるか |

- 各ディレクトリの書き方は、それぞれの README を正とする。`docs/` 配下の文書を書く・変える前に、そのディレクトリと上位ディレクトリの `README.md` を読む
- 次は資料であり、正本ではない。必要なときに読み、正本として維持しない
  - `docs/パズル/導入調査/` と `docs/パズル/` のパズル固有の検討資料: パズル候補の調査・検証と、導入時の検討の記録
  - `docs/棚上げ/`: パズル候補の台帳
  - `docs/立ち上げ/`・`docs/メモ/`: 立ち上げ期の経緯と開発上の参考資料

## 3. 食い違ったときに従う順

- 文書・コード・資料が食い違ったときは、次の順に強い
  1. 要求・要件、リポジトリ直下の文書（`AGENTS.md`・`CLAUDE.md`・`APP.md`・`GAME.md`・`DESIGN.md`）、`.claude/rules/`
  2. コードとテスト
  3. 1 以外の正本の文書（仕様、難易度文書、各ディレクトリの README など）
  4. 資料
- 1 は実装が正しいかを判定する基準と、プロダクトの判断・作業の決まりである。コードが 1 と食い違っていたら、コードを直す。1 の決まりそのものを変えるときは、同じ変更で 1 を直す
- 3 より 2 が強いのは、正しさを確かめる仕組み（型・テスト・静的検査・実際の動作）がコードの方に揃っているから。3 がコードと食い違っていたら、3 が古いものとして、コードに合わせて直す
- 1 の決まりは、できるものはテスト・静的検査に載せて守らせる
- ADR は意思決定の記録で、この順には含めない。今の文書・コードと食い違ったときの ADR の扱いは `docs/adr/README.md` に従う

## 4. 書き方

ADR を除く正本に適用する。ADR は `docs/adr/README.md` と adr-create スキルに従う。

### 何を書くか

- コードから読めない今の決まりと、その意図を書く
  - 意図は Why（何のために、なぜそうするか）と Why not（なぜそうしないか、何を退けたか）
  - 決まりの意図は、その決まりと同じ文書に書く。別の文書へ分けない
- コードから読める What / How（配置、構成、値、振る舞いの詳細）は書かない。コードとテストに置く
- 決まりは、次の両方を満たすものだけを書く
  - 当たり前ではない判断であること。UI/UX の基本、一般的なエッジケースの扱い、どのゲームでも自然にそうなることは書かない
  - 知らずに変えると意図が壊れること。コードを読めば分かり、変わっても困らないことは書かない
- 今の決まりを言い切りで書く。決まるまでの経緯、将来の予定、まだ決めていないことは書かない
- 同じことを二つの文書に書かない。上位の文書で言えていることを言い直さない
- 文書を変えたら、他の文書との重複や食い違いを作っていないか確かめる

### リポジトリ直下の文書と画面の文書

`APP.md`・`GAME.md`・`DESIGN.md` と、`docs/プロダクト/画面/` の画面の文書には、「何を書くか」に加えて次を適用する。

- `CLAUDE.md` と同じように書く
  - 短く、守れているかを確かめられるほど具体的に書く
  - 見出しと箇条書きで構造化する。太字・斜体・引用・IMPORTANT などの強調表現は使わない
  - 行数の上限は設けない
- 意図は、決まりの無い場面へ判断を広げるのに要るところにだけ添える。すべての決まりに意図を求めない
  - 短ければ決まりと同じ項目に続け、長くなるときだけ直下の子項目に書く
  - 子項目には、親の決まりの意図だけを書く
- 意図には、プロダクトオーナーが示したもの（過去の版、PR 本文、ADR、要求などの一次資料にあるもの）だけを書く
  - 作業者が考えた理由を、プロダクトオーナーの理由として書かない
  - 根拠の無い決まりは、意図を添えずに決まりだけを書く
- 場面・人・対象の呼び方をそろえる
  - 場面は「選ぶ」（遊ぶものを選んで始めるまでと、過去のプレイを振り返る間）・「解く」（プレイ中）・「結果」と呼び、並べるときはこの順にする
  - 人は、`APP.md`・`DESIGN.md` では「遊ぶ人」、`GAME.md` では「プレイヤー」と呼ぶ
  - 全ゲームに共通する表示は「共通UI」と呼ぶ
  - 「パズル」はルール・題材・問題の種類を、「ゲーム」は一つのパズルを遊べる形にしたものを指す
- `DESIGN.md` は Google Labs の DESIGN.md Format に従い、本文で値の意図と使い方を伝える
