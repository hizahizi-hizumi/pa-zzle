# 文書ルール

pa-zzle の文書に何を書き、どう保つかのルール。いつ読むかは `AGENTS.md` を正とする。

## 1. 文書の存在目的

文書は、コードからは読めない次の3つを、人とエージェントが失わないためにある。

- 何を目指し、何を保証するか。実装が正しいかを判定する基準になる
- 何を決めたか。知らずに戻されないようにする
- なぜそう決めたか。蒸し返されないようにする

これに役立たない文書は置かない。

## 2. どの文書に何を書くか

| 文書 | 書くもの |
|---|---|
| `docs/プロダクト/要求/` | 利用者が実現したい状態 |
| `docs/プロダクト/要件/` | 製品として保証する能力・性質 |
| `docs/プロダクト/仕様/` | 要件を満たすための今の決まり。アプリ・ゲーム共通の取り決めと、パズルごとのルール・評価・難易度の定義 |
| `APP.md` | アプリ全体の体験で大事にすること。アプリとゲームの分担 |
| `GAME.md` | 個々のゲームの体験で大事にすること |
| `DESIGN.md` | アプリ全体のデザインシステム。見た目・操作への反応・動き・音の使い分け |
| `docs/パズル/` の難易度文書 | 難易度の意味と、作るときの手引き |
| `docs/adr/` | 将来の意思決定に一貫性を持たせるための意思決定の記録。何を、どんな前提で、何と比べて決め、なぜそうし、何が起きるか |
| `AGENTS.md`・`.claude/rules/` | エージェントが作業するたびに守る決まり |

- 各ディレクトリの書き方は、それぞれの README を正とする。`docs/` 配下の文書を書く・変える前に、そのディレクトリと上位ディレクトリの `README.md` を読む

## 3. 書く基準

- この節は `docs/`・`APP.md`・`GAME.md`・`DESIGN.md` の正本に適用する。ADR は意思決定の記録として `docs/adr/README.md` に従う
- 書くのは、今の決まりと、コードから読めないその Why（何のために、なぜそうするか）・Why not（なぜそうしないか、何を退けたか）
- コードから読める What / How（配置、構成、値、手順、振る舞いの詳細）は書かない。コードとテストを正とする
- 決まりの Why / Why not は、その決まりと同じ文書に書く。別の文書へ分けない
- 正本に書くのは、次の両方を満たすことだけ
  - 当たり前ではない判断であること。UI/UX の基本、一般的なエッジケースの扱い、どのゲームでも自然にそうなることは書かない
  - 知らずに変えると意図が壊れること。コードを読めば分かり、変わっても困らないことは書かない
- 今の決まりを言い切りで書く。決まるまでの経緯は書かない
- 同じことを二つの文書に書かない。上位の文書で言えていることを言い直さない
- 将来の予定や、まだ決めていないことは書かない
- 今の実装に合わせるためだけに、要求・要件を書き換えない

## 4. 文書を変えるとき

- 文書を変えたら、他の文書との重複や食い違いを作っていないか確かめる

## 5. 資料

- 次は資料であり、正本ではない
  - `docs/パズル/導入調査/` と `docs/パズル/` のパズル固有の検討資料: パズル候補の調査・検証と、導入時の検討の記録
  - `docs/棚上げ/`: パズル候補の台帳
  - `docs/立ち上げ/`・`docs/メモ/`: 立ち上げ期の経緯と開発上の参考資料
- 資料は必要なときに読み、正本と食い違うときは正本を正とする
- 資料は正本として維持しない
