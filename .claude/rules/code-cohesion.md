# コードの責務と統廃合

- ファイルは、同じ変更理由を持つ規則・状態・処理をひとまとまりで所有する。
- 型・関数も、実装方法ではなく意味と責務で分ける。
- 包括的な名前が必要になるときは、責務が混在していないか見直す。
- 独立した変更理由や不変条件を持つ処理は、それぞれの責務を所有できる単位へ分ける。
- 切り出し先は、自身で所有する規則・状態・契約を持つものにする。独立した契約を持たない中継は所有者へ統合する。
- 共通化するのは、処理の形だけでなく、意味・不変条件・変更理由を共有するときにする。
- 統廃合の前後で、理解・変更に必要な追跡範囲と、増える引数・依存・状態の重複を比較し、複雑性の小さい構造を選ぶ。
- ファイルを追加・変更するときは、直接の利用元・依存先・同種の実装・関連テストを確認し、分割・統合・共通化・維持を判断する。

## 適用除外

- 上流の配布単位を維持する `frontend/src/components/ui/**` は、その管理方針に従う。
