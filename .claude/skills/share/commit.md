# コミットの境界とメッセージ

## 境界

- 1コミットを、1文で説明できる1つの論理的変更にする
- 無関係な変更を混ぜない
- 機械的変更（整形・リネーム・移動）と意味変更を分ける
- 純粋なリファクタと挙動変更を分ける
- 依存更新・CI・開発環境変更と機能変更を分ける
- ディレクトリ境界ではなく、変更理由と、独立して revert できる単位で分ける
- 可能な範囲で各コミットを、変更範囲に対応する `AGENTS.md` の検証コマンドが通る状態にする
- 分けると中間コミットが壊れるときは同じコミットに置く

次は同じコミットに置く:

- 1つの機能変更と、その変更を成立させる最小の回帰テスト
- schema / API / 型などの契約変更と、その新契約へ必須で追従する利用側
- 設定変更と、その設定を前提にしないと成立しない実装変更

次は分ける:

- 大規模なファイル移動と、その後の内容変更
- 純粋な用語置換と、意味論の変更
- 開発ツール導入と、利用者向け機能変更
- 独立して revert したい変更

## 履歴

- レビューで「何を」「なぜ」変えたかを追えるようにする
- 1コミットを単独で revert しても意図が分かるようにする
- 移動だけのコミットでは、可能な限り内容を編集しない
- コミットをきれいに見せるためだけの意味変更を混ぜない
- `main` に `WIP`・`とりあえず`・`あとで直す` のような中間履歴を残さない
- 履歴の書き換えと push は `AGENTS.md` の「Git運用」に従う

## メッセージ

コミットメッセージと PR タイトルは次の形式にする。scope が要らなければ省く。`git log --oneline` の直近の件名が別の形式に揃っているときはそれに合わせる。

```text
<label>(<scope>): <日本語の短い件名>
```

| label | 用途 |
|---|---|
| `feat` | 利用者・開発者に新しい価値を追加 |
| `fix` | 不具合・回帰修正 |
| `refactor` | 挙動不変の内部改善 |
| `perf` | 性能・コスト改善 |
| `test` | テスト・検証基盤 |
| `docs` | ドキュメントのみ |
| `style` | 意味を変えない整形 |
| `chore` | CI・依存・運用・周辺設定 |
| `dev` | 開発体験向上 |
| `revert` | 既存変更の取り消し |

scope には `frontend`・`backend`・`api`・`docs`・`ci`・`skills` などの変更範囲を書く。

```text
OK:
feat(frontend): パズル選択画面を追加
fix(backend): 無効な難易度を拒否
docs: PoCの検証観点を明確化
```
