# brush-up-puzzle

`/brush-up-puzzle <game>`

`<game>`（`$ARGUMENTS`）は `frontend/src/games/` のディレクトリ名にする。

## 大原則

1つでも破っていれば、作業は終わっていない。

- P1. 今の画面を出発点にして磨かない。発散・選択・深掘り・収束の順を飛ばさない。
  - 磨く手法は、目指す姿を変えない。目指す姿が今のままなら、磨いても今の姿の仕上げにしかならない。
- P2. 方向は、このパズルの気持ちよい瞬間を強めるかで出す。変わっていること・ほかと違うことを目当てにしない。
  - 誰でも思いつく素直な方向を、素直だからという理由で外さない。
- P3. 方向の良し悪しは PO が決める。自分でもサブエージェントでも、良し悪しで方向を選ばず、点数も付けない。
  - 自分が落とすのは、同じ方向の重なりと、P4 に反する方向だけにする。
- P4. 変えるのは見た目と手応え（盤面の姿、動き、音、操作への反応、地）だけにする。ルール・問題・難易度・操作の意味は変えず、機能や操作の種類も足さない。盤面の姿を写している所（ピクトグラム、遊び方の図など）は、選ばれた後に新しい姿へ合わせる。
- P5. 方向は、遊べる試作で見せる。選ばれる前の試作は、その方向の姿で盤面が描き直されていて、1問を最後まで遊べて、気持ちよい瞬間がその方向の形で動く所までにする。物差しと見比べて直すくり返し、遊ばせて確かめること、通らない操作や速い操作の作り込み、テスト、文書、`review-changes`、`.claude/rules/` に沿った書き方、ダークモード・PC 幅・動きを減らす設定への対応は、選ばれた1つにだけかける。
  - 選ばれなければ捨てるものを、選ばれる前に仕上げない。
- P6. 試作は、今の画面の部品に仕掛けを足すのではなく、その方向の姿として盤面を描き直す。目指す描き込みの水準は、PO が仕上がりを認めた画面に置く。
- P7. PO に聞くのは、方向の選択、深掘りの選択、PO にしか決められないことだけにする。それ以外では止まらない。見せるときは、触れる URL を必ず付ける。
- P8. 過去の閉じた PR とブランチを、手がかりとして探さない。

## 補助ファイル

- `references/direction-brief.md`: 方向を出すサブエージェントへ渡す文面のひな形。手順 5 で読む
- `references/prototype-brief.md`: 遊べる試作を作るサブエージェントへ渡す文面のひな形。手順 8・11 で読む
- `${CLAUDE_PROJECT_DIR}/.claude/skills/share/playtest-driver.mjs`: 実画面を操作して撮る。手順 3・8・9・11・13・14 で使い、手順 17 で止める。使い方は冒頭のコメントを読む

## 手順

PO の返事を受けて別のセッションで続けるときは、作業ブランチに切り替え、`frontend/src/games/<game>/ui/prototypes/` があればその中の `brief.md` と通すスクリプトを作業用のディレクトリへ写して読み、手順 3 のとおり開発サーバーと playtest-driver を起動してから、返事を求めた手順の続きから進める。

サブエージェントを起動する手順では、起動したものが全部返るまで待ってから次へ進む。

### 準備

1. `GAME.md`・`APP.md`・`DESIGN.md`・`docs/開発/画面レビュー手順.md` と、`docs/プロダクト/仕様/パズル/` から対象パズルの仕様を読む
2. 今のブランチが `main` なら作業ブランチを作る。リポジトリの外に作業用のディレクトリ `/tmp/brush-up-puzzle/<game>/` を作り、撮った画像・絵・道具はすべてこの下に置く
3. 今の画面を通す
   - `frontend/node_modules` が無ければ `bun install --cwd frontend` を実行する
   - 開発サーバーを `bun run --cwd frontend dev -- --port <ポート> --strictPort` で、`run_in_background` と最長の `timeout` を付けて起動する
   - playtest-driver を `iphone` で、出力先を作業用のディレクトリの下にして起動する
   - 通す問題を1つ決め、始めから完成までの解き方（操作の列）を `frontend/src/games/<game>/` の解探索か問題集の情報から求める。解き方には、通らない操作（誤り）を1回と、このパズルだけの操作（メモなど）を1回ずつ入れる
   - 解き方を playtest-driver で順に打つスクリプトを作業用のディレクトリに作る。打つ場所は、要素の読み上げ名（`aria-label`）やボタンの名前から `rect` で求め、座標を書き込まない
   - スクリプトで1問を通し、返った画像を Read で見る。始まり・操作の途中・完成の瞬間の画像を控える
   - PO が仕上がりを認めたパズルの画面を2つ、同じ端末で撮って控える。どれが当たるかは、会話と、このリポジトリでマージされた見た目の作り直しのコミットから決める
4. 作業用のディレクトリに `brief.md` を作り、次を書く
   - 変えないもの: P4 に当たる、このパズルのルール・操作の意味
   - 気持ちよい瞬間: このパズルを遊んでいて気持ちよい瞬間を3〜5個。操作と盤面の変化の言葉で書く（例: 注いだ色が先の色とつながる瞬間、1本が1色で満ちる瞬間）
   - 場面: 遊ぶ人がこのパズルで出会う場面。眺める・選ぶ・動かす（置く）・通らない（誤る）・一部が済む・完成するから、このパズルにあるものを挙げ、このパズルだけの場面を足して、5〜8個にする
   - 残すもの: PO が今の画面で良いと言った所。会話と、このパズルの名前で探した Issue から拾う。見つからなければ空のままにする
   - 一緒に変えるもの: 盤面の姿を写している所。ピクトグラム、色と動きのあるピクトグラム、遊び方の図、チュートリアル、結果画面、ゲームのホームの地から、このパズルにあるものを挙げる
   - 通す問題: 手順 3 の1問、その問題を指定するクエリを付けた入口パス、解き方、通すスクリプトのパス
   - 見比べる盤面: 通す問題の途中の1つの盤面（操作を1つ選んだ所で、済んだものと済んでいないものが両方ある）を、解き方の何手目かで書く。一覧の画像の「操作の途中」に使う
   - 最も厳しい盤面: 画面に出るものが最も多く、最も小さくなる問題と、その入口パス。盤の大きさが変わらないパズルでは、遊ぶ人が書き込むものが最も多くなる問題にする
   - 物差し: 手順 3 で控えた、PO が仕上がりを認めた画面の画像のパス

### 発散

5. 方向を出す。`references/direction-brief.md` を読み、文脈を引き継がないサブエージェントを4つ同時に起動して、方向を8個ずつ出させる。2つには題材ありの文面、2つには題材抜きの文面を、`<…>` を埋めて渡す。手順 9 から戻ってきた2周目では、前の周に出た方向の一覧と、PO の返事も渡す
6. 返った方向をまとめる
   - 盤面を何として描くかが同じ方向を1つにまとめ、いくつのサブエージェントが出したかを数える。場面ごとの返し方は、その方向を出した中で最も番号の若いサブエージェントのものを採り、混ぜない
   - P4 か `GAME.md` の「判断の優先順位」に反する方向を外し、理由を控える
   - 残りを、出したサブエージェントの数が多い順に並べ、上から10前後を試作にする。同じ数の中では、自分の好みで順を付けず、サブエージェントの番号と返答の中の番号の順にする
   - 試作にする方向ごとに英小文字の短い `<id>` を付け、出た方向の全部・外した方向と理由・試作にする方向を `brief.md` に書く
7. 切り替え口を作る
   - 盤面の姿と手応えを描く部品と、プレイ画面の地を描く部品を、`frontend/src/games/<game>/ui/prototypes/<id>/` の試作に差し替えられる入口にする
   - プレイ画面の隅に、今の画面と全部の試作から選ぶ `select` を、ほかの要素の配置を変えない位置に重ねて置く。選んだ試作が、同じ問題の盤面のまま切り替わり、次の問題や結果画面へ移っても保たれるように作る。URL の `look` クエリは最初に開く試作を決めるためだけに読み、無いときは今の画面を描くようにする
   - 切り替え口を、選ばれた試作だけをそのときに読み込む（動的 import）作りにする。ほかの試作の書き換えで、開いている画面が読み直されないようにするため
   - 試作が自分の音を鳴らすときに今の効果音と重ならないよう、試作ごとに今の効果音を止められるようにする
   - `<id>` ごとに、今の画面をそのまま描く仮の部品を `prototypes/<id>/` に置いて切り替え口に登録し、`bun run --cwd frontend build` が通ることを確かめる
8. 試作を作らせて確かめる
   - `references/prototype-brief.md` を読み、方向1つにつきサブエージェントを1つ、同時に起動する。ひな形の `<…>` を埋めた文面だけを渡し、会話の経緯・自分の見立て・ほかの方向は渡さない。driver のポートと出力先は、試作ごとに、開発サーバーとも互いにも重ならない値にする
   - 返った試作を1つずつ、通すスクリプトで最後まで通す。この段では、遊ばせて確かめるサブエージェントを起動しない。作り込みは、選ばれた1つにだけ手順 11 でかける
   - 次に当たる試作は、当たった所を画像と一緒に、作った同じサブエージェントへ続きとして送り、1回だけ直させる。直らなければ落として理由を控える
     - `bun run --cwd frontend build` が、その試作のファイルのエラーで通らない
     - 1問を最後まで遊べない
     - ルール上の区別（どれが動かせる物か、何が済んだか、通らなかったこと）が画面から読めない
     - 今の画面の部品（今の描き方）に、何かを足しただけになっている
     - 配置が崩れている、文字が読めない

### 選択

9. PO に試作を見せて、方向を選んでもらう
   - 試作と今の画面について、通す問題の始まり・`brief.md` の「見比べる盤面」・完成の瞬間を撮り、行を試作、列を場面にした一覧の画像にまとめる。縦に長くなるときは数枚に分け、どの枚も1行目を今の画面にする
   - 手順 12 と同じやり方で、一時コミットと push をして、Branch Preview URL を得る
   - 一覧の画像、Branch Preview URL と通す問題の入口パスをつないだ URL を1つ、試作ごとの一文、落とした試作と理由を、1つの返信で渡す
   - 作り込む方向を1つ選ぶか、組み合わせるか、全部違うかを聞く。`brief.md` の「残すもの」が空なら、今の画面で残したい所も聞く。返事を待つ
   - 全部違うと返ったら、試作を少しずつ直さない。番号で答えられること（いちばんましな試作、いちばん遠い試作、試作の一部で良かった所）だけを聞く。ましな試作も良かった所も無いときは、PO が良いと思う実物や作例の画像を1枚もらうか、こちらで集めた12枚ほどから近いものを指してもらう。そのうえで手順 5 に戻り、前の周の方向の一覧と PO の返事を渡して、方向を出し直させる
   - 発散は2周までにする。2周目も全部違うなら、3周目を作らず、2周ぶんの返事から分かったことと分からなかったことを伝えて止まる

### 深掘り

10. 選ばれた方向の試作を1つだけ残す。切り替え口から、選ばれなかった試作を消す。組み合わせを指定されたら、選ばれた試作に、指定された所だけをほかの試作から移す
11. 残した1つを作り込む。別の試作を新しく作らない
    - 作り込みは、その試作を作った同じサブエージェントに続きとして送って行わせる。同じサブエージェントに送れないときだけ、新しく1つ起動して、試作のディレクトリと `references/prototype-brief.md` の文面を渡す
    - 物差しの画面と並べて撮り、描き込みが足りない所を直すことを、足りない所を挙げられなくなるまでくり返させる
    - `puzzle-playtester` を1つ起動し、開発サーバーの URL と、通す問題の入口パスに `look=<id>` を足したパスを渡して、初めて遊ぶ人の目線でのつまずき・分かりにくさ・崩れを返させ、直させる
    - 通らない操作、通す問題で出会えない場面、演出の間の速い操作、「最も厳しい盤面」を通し、崩れる所を直させる
12. PO に作り込んだ試作を見せる
    - 最初の push のときだけ、一時コミットの前のコミットを `brief.md` に控える。手順 16 で一時コミットをほどくときに使う
    - `brief.md` と通すスクリプトを `frontend/src/games/<game>/ui/prototypes/` に写す。写した `brief.md` が作業用のディレクトリのファイルを指していれば、その中身を `brief.md` に書き入れる
    - 試作・切り替え口・写した2つを、後で消す一時コミットとして `commit` スキルでコミットし、push する。PR が無ければ `pr` スキルで作り、本文に、試作を並べた見本であり、このままマージしないことを書く
    - チェック `Workers Builds: pa-zzle` が成功するのを待ち、Branch Preview URL と通す問題の入口パスをつないだ URL を1つ渡す
    - これで仕上げてよいか、直してほしい所があるかを聞く。返事を待つ
    - 直してほしい所が返ったら、同じ試作を直して、もう一度見せる。PO が「何パターンか見たい」と言った所だけ、同じ試作の中でその1か所の値を変えた見本を `select` で切り替えられるようにして見せる。値の見本のために、別の試作を作らない

### 収束

13. 仕上げてよいと返った試作から、本番の画面を作る
    - 選ばれた方向を、このパズルの面白さがどこにあるかの一文に言い直し、`brief.md` に書く。以降の判断はこの一文に照らす
    - 盤面の要素ごとに、ルール上の働き（止める、通す、動かせる、済んだ、など）を書き出し、姿をその働きから決め直す。働きからも方向からも説明できない飾りを外す
    - 試作のコードを写さず、`.claude/rules/` の決まりに沿って、本番の部品として書き直す。ダークモード、PC 幅、動きを減らす設定にも対応させる
    - 決めきれない値は、ほかを固定して1つの軸だけを振った見本を実画面で並べ、自分で決める。PO にしか決められないときだけ、見本を切り替え口に登録して一時コミットとして push し、Branch Preview URL と一緒に聞く
    - 動きは、playtest-driver の `frames`・`trace` で途中を撮り、位置の飛びやがたつきを数値で確かめる。直すときは原因を突き止めてから直す
    - `brief.md` の「一緒に変えるもの」を新しい姿に合わせる
    - 試作のディレクトリと切り替え口を消す
14. 「残すもの」が残っていること、「最も厳しい盤面」と動きを減らす設定で成り立つことを、撮って確かめる
15. `./scripts/verify.sh` を実行し、`review-changes` スキルを起動して、確かめた指摘を直す。直した後に `./scripts/verify.sh` をもう一度通す
16. 一時コミットを消してコミットを作り直す。`git reset --soft <brief.md に控えたコミット>` で一時コミットをほどき、試作と切り替え口が差分に残っていないことを確かめてから、`commit` スキルで未コミットの差分からコミットを作り、`git push --force-with-lease` で push する。PR の題と本文を、仕上がった変更の説明と、確かめたこと・確かめていないことに書き換える。チェック `Workers Builds: pa-zzle` が成功するのを待つ
17. 開発サーバーを TaskStop で止める。自分で起動した playtest-driver が残っていれば `quit` で止める
18. PO に次を伝える
    - 仕上がった画面の画像と Branch Preview URL
    - `brief.md` の一文と、要素ごとの働きと姿の対応
    - 確かめていないこと（実機、音など）
    - この手順のとおりに進まなかった所と、その原因
