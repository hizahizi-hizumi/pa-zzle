# 姿の探索方法

`/design-game-pictogram-showcase` の材料抽出、発散、候補整理に使う。目的は案数を稼ぐことではなく、目的 A（遊びが分かる）と目的 B（解けた気持ちよさが見える）を満たしうる異なる方向を、安い段階で広く確保することにある。

## 1. 材料を抽出する

発散の前に、ゲームから材料を短く列挙する。次の 2 つは必須とし、欠けたまま発散へ進まない。

```yaml
central_action:   # A の材料。プレイヤーが何を見て、何を考え、何をするか
  - 一番上の色が同じ瓶を探す（考える）
  - 瓶を選び、別の瓶へ注ぐ（する）
solved_moment:    # B の材料。何が揃い、どう終わるか
  - 1 本の瓶が単色で満ちる
  - 全瓶が単色で揃い、盤面が静まる
```

加えて次を拾う。

- 動かせる対象と、その所属関係（容器と中身、盤とマス、駒と通路など）
- 題材の物理（重力、流動、衝突、整列、反転など）
- プレイ画面のゲーム固有色（範囲は `references/contract.md` の 3 節）と、その色が担う役割（識別、状態、完了）と定義元のパス。ライト/ダークで値が変わるかと、両テーマの実際の値（下の「色の定義元の調べ方」）。ゲーム固有色が無ければ無いことを書く。静止状態は白黒版そのものになり、A と B は動きだけで伝えることになる
- プレイ画面の演出（選択・移動・完了で何がどう動くか、どれだけ動くか）。演出が少ないゲームもある
- 白黒版が何をどの構図で、どの状態（解く前・解いている途中・解けた後、静止か動きの途中か）で描いているか（途中なら 3 節「白黒版が途中の姿を描くゲーム」）。どこをゲーム固有色にすると同じパズルのまま姿が立つか
- 白黒版にある字形（数字・記号）と、その書き方（1 字ずつのパスか、複数の字が 1 本のパスにまとまっているか）
- ゲーム中には実際に起きないが、ゲームの意味から無理なく連想できる誇張

`central_action` は操作の名前ではなく、考える部分とする部分の両方を書く。考える部分が動きで見えないと、A は「何をするか」止まりになる。

### 色の定義元の調べ方

`frontend/src/games/<game>/ui/` 配下で、盤・駒・状態の要素がどう塗られているかを Grep し、定義元ごとに値を引く。アプリのトークンで塗られた要素は、ゲーム固有色として写すかを `references/contract.md` の 3 節の基準で見分ける。

| 定義元 | 値の引き方 |
|---|---|
| TS / CSS の定数（色の表、CSS 変数） | 定義ファイルを読む。テーマで分岐していれば両方 |
| Tailwind のパレット色のクラス（`bg-blue-600`、`dark:text-red-400` 等） | `frontend/node_modules/tailwindcss/theme.css` の `--color-<名前>`（`oklch()`） |
| アプリのトークンのクラス（`bg-background`、`border-border`、`text-muted-foreground` 等） | `frontend/styles/globals.css` の `:root`（ライト）と `.dark`（ダーク） |

SVG での書き方は `references/contract.md` の 3 節。

`scripts/resolve_color.py` に、クラス名・名前・`oklch()` を並べて渡すと、どの定義元かと値（hex、トークンなら両テーマと `var()` で書けるか）を出す。`oklch()` を hex へ変換して sRGB の色域外を丸めた場合は印が付くので、`notes` に書く。

```sh
python3 .claude/skills/design-game-pictogram-showcase/scripts/resolve_color.py bg-blue-600 'dark:bg-blue-400' 'bg-red-500/50' border-border
```

## 2. アイデアカードを作る

初回発散ではコードを書かない。1 案につき次だけを短く記録する。

```yaml
id: pour-settle-01
name: 注いで揃う
idea: 片方の瓶が傾き、上の色がもう片方へ移り、受け側が単色で満ちて止まる
aim_play: 「同じ色の上へ注ぐ」判断と操作を 1 回で見せる
aim_payoff: 受け側が単色で満ちた瞬間に動きが止まる
static_pose: 揃った後の姿（2 本の瓶、片方が単色で満ちている）。各周の終わりの止まりでもあり、0% は注ぐ前の姿
playback: cut
references:
  - 中心の操作: 注ぐ
  - 解けた瞬間: 1 本が単色で満ちる
```

- `aim_play` は遊んでいる瞬間の動きで見せる。規則を矢印や記号で説明する図解寄りの案は、遊びたくなる姿にならず除外されやすい。
- `aim_play` / `aim_payoff` は評価点ではなく、後で束ね、セルフレビューで「宣言どおり読めるか」を確かめるための仮説である。
- `static_pose` は一覧の選択中に見せる静止状態であり、どの再生形式でも周の終わりの姿になる。動きと切り離して考えない。
  - 静止状態は、白黒版と同じ形で、違うのは色だけの姿にする（`references/contract.md` の 2 節）。選んだ瞬間に一覧もヒーローも白黒版からこの姿へ色だけが変わるので、形・配置・盤の中身が違うと跳んで見える。
  - 動きは、白黒版と同じ絵で終わるように組む。見せ場の後の姿で終われるよう、白黒版の絵のどこが「動いた後」に見えるかから逆算する。白黒版が途中の姿を描いていて、その姿で止まると「止まっているのに途中」の絵になる場合の組み方は 3 節「白黒版が途中の姿を描くゲーム」。
- `playback` は仮置きでよい。形式の定義は `references/contract.md` の 2 節、選び方は 3 節。

## 3. 再生形式を選ぶ

形式の定義は `references/contract.md` の 2 節、組み立て方と周期の目安は `references/motion.md` の 1〜2 節。

`cut` を基本とする。解く前から見せ場まで動いて見せ場の後の姿で止まる流れをそのまま繰り返せ、構図も周期も膨らまない。1 回だけ再生して止まる形式は使わない。選んだ瞬間しか動かず、見逃すと A/B が伝わらない。D は止まりで満たす。

- `cut`: 周の境界で開始の姿へ戻る切り替えは「場面の頭出し」として読まれる。静止状態を見せ場の後の姿にできるなら、この形式にする。
- `rest-cut`: 白黒版が解いている途中の盤を描き、白黒版を直さずに解けた瞬間まで見せたいときに使う（下の「白黒版が途中の姿を描くゲーム」）。周の頭と終わりにも静止状態の区間があるぶん、見せ場の後の止まりは `cut` より短くなりやすい。
- `seam`: 継ぎ目が意味として自然に成立する場合だけ検討する。白黒版が動きの途中を描くとき、その瞬間を継ぎ目にする `seam` はその典型である（下の「白黒版が途中の姿を描くゲーム」）。不可逆な操作のゲーム（注ぐ、消す、置く等）は元に戻らないため、継ぎ目に「次の問題が来る」「役割が交代する」などの物語が要り、構図が変わり周期も伸びやすい。
- フェードや巻き戻しなど、開始の姿や静止状態へ戻る途中経過を見せる戻し方は試作しない。

形式ごとの人間の受け取り方は `references/review.md` の 6 節「これまでの人間レビューの傾向」の「再生の形」。

ヒーローには枠がないため、画面端から対象が出入りする動きは描画域の端で切れて見え、D を損なう。`seam` の継ぎ目を作るために出入りを使わない。

### 可逆な操作のゲーム

操作を戻せるゲーム（動かした駒を動かし戻せる、反転を反転し直せる等）では、`seam` が物語なしで作れそうに見える。戻し方を 2 つに分けて考える。

- 逆の手で戻す（やった手を逆順にたどる）: 巻き戻し再生に見え、「戻りが不自然」と受け取られやすい。採らない。
- 合法手で一巡して戻る（別の手順を進めた結果として元の配置に戻る）: 前へ進む動きのまま始めの姿へ着くため、自然な継ぎ目になりうる。ただし手数が増え周期が伸びやすい。試作する前に、合法手で一巡する最小手数を数え、その手数で周期の目安（`references/motion.md` の 2 節）に収まるかと比べてから試作するか決める。

`seam` で継ぎ目（= 静止状態）を解けた姿にすると、周の最初の動きが完成を崩すことになり、「解けた姿を崩す」場面が最初に見える。A/B の順（操作 → 解けた瞬間）と逆になるため、`cut`（解く前から始めて解けた姿で止まる）と比べてから採る。

### 白黒版が途中の姿を描くゲーム

白黒版が解いている途中や動いている途中の姿を描いていると、その姿を `cut` の止まりに置いたとき「止まっているのに途中」の絵になる。どちらの途中かで、候補の組み方を分ける。どちらでも、見せ場の後に止める `cut` には白黒版の修正案（`base_revision`）を添え、今の白黒版に寄せる案と並べる。修正案で失うもの（`references/review.md` の 1 節「白黒版の修正案」で `notes` に書く、今の白黒版と比べた結果）と、今の白黒版に寄せる案の弱点を比べて、どちらに寄せるかは人間が選ぶ。白黒版を直す理由が周の組み方の都合だけのときは、今の白黒版に寄せる案が選ばれやすい（`references/review.md` の 6 節の傾向）。

解いている途中の盤（数字が埋まりかけた盤、引きかけの道など）:

- 白黒版のその盤から始めて解けて止まる `cut` を、必ず候補に入れる。静止状態は解けた盤になるので、解けた盤に描き直した修正案を添える。`cut` なら一覧の選択中と動きを減らす設定でも解けた盤を見せられ、見せ場の後の止まりを長く取れる。修正案を並べることで、白黒版としての良し悪しも人間が比べて選べる。
- 今の白黒版に寄せる案として、`rest-cut` を必ず候補に入れる（見せ場が成り立たないときは、次の項目の今の白黒版で止まる `cut`）。白黒版の盤を静止状態にしたまま、修正案の `cut` と同じ動きで解けた瞬間まで見せられる。弱点は、一覧の選択中と動きを減らす設定では途中の盤を見せ、解けた盤は見えないことと、解けた盤の止まりが修正案の `cut` より短くなりやすいこと。修正案の `cut` と並べるときは、動きを揃えて周の組み方だけを変え、`notes` にこの弱点を書く。
- `rest-cut` で見せ場が成り立たないとき（解けるまでの動き、解けた盤の止まり、周の終わりの静止状態を合わせると周期が目安に収まらないなど）に限り、白黒版の盤を止まりにする `cut`（それより前の盤から始めて、白黒版の盤まで進めて止まる）を今の白黒版に寄せる案にする。この案は解けた瞬間（B）を見せられない。
- 静止した途中の盤には継ぎ目にする瞬間が無く、元へ戻す流れも要るので、`seam` にはしない。

動きの途中の姿（スライドパズルの半マスずれた駒など）:

- その瞬間を継ぎ目にした `seam` を、今の白黒版に寄せる案として候補に入れる。`cut` の止まりに置くと、動いている途中で固まった絵に見える。アプリは周の終わり（= 継ぎ目）から再生し始めるので、選んだ直後に途中の動きがそのまま続き、見せ場へ入る。
- `seam` と並べて、修正案で見せ場の後に止める `cut` も必ず入れる。
- 継ぎ目へ戻る流れは、合法手で一巡して作る（上の「可逆な操作のゲーム」）。合法手で一巡できない、一巡する最小手数が周期の目安に収まらないときは、自然に戻せないものとして `seam` を入れず、修正案で見せ場の後に止める `cut` と、今の白黒版に寄せる `cut` で比べる。

## 4. 一回の長い発散へ依存しない

同じ prompt で案数だけ増やすと、後半が言い換えになる。複数回を独立させ、毎回違う刺激を与える。1 エージェント内で発散するなら回ごとに刺激と視点（A 側 / B 側、操作する人 / 盤面）を変え、サブエージェントを使える環境なら回ごとに別のサブエージェントへ発散させる。

A 側の刺激:

- 中心の操作を 1 回だけ、はっきり見せる
- 「考える」部分（探す、見比べる、迷う、手がかりを読む）を間で見せる
- 操作の結果として盤面がどう変わるかを主役にする
- 動きを極端に少なくして操作の核だけ残す
- このゲームのルールにしか無い操作や制約（何が動けて何が動けないか、何が何を決めるか）を見せる
- 1 手ではなく、数手の手順（順番に意味がある並び）を見せる

B 側の刺激:

- 揃った瞬間に動きが止まる「静まり」を見せ場にする
- 最後の一手など終端の間を主役にする
- 一つの完了から連鎖させる
- 状態の変化（未確定 → 確定、ばらばら → 整列、隠れている → 見える）が盤面全体へ広がる構成にする
- 達成の構造（どこが揃えば解けたか: 行・列・全体・対応関係）が見える構成にする
- プレイ画面で完了・正解が色で示されるゲームなら、完了したものの色が初めて全部見える構成にする

プレイ画面の演出（選択・移動・完了の動き）が少ないゲームでは、演出を写すのではなく、ルール固有の操作・状態の変化・手順・達成の構造から刺激を選ぶ。色の変化を前提にした刺激は、ゲーム固有色のあるゲームでだけ使う。

これはカテゴリごとのノルマではない。同じ局所解から離れるための刺激として使う。

D（落ち着き）は発散段階で案を縛らない。ただし、常時大きく動き続ける、強く点滅する、画面外へ飛び出す・画面端から出入りするなど、明らかに D を侵す案は試作対象にしない。

## 5. 初回の量は探索空間に合わせる

操作が 1 種類で盤が小さい単純な題材なら、30〜60 枚程度のアイデアカードを作り、重複を整理してから 10〜20 程度を試作する運用が一つの目安になる。数値は固定条件ではない。

- 十分に異なる方向が揃えば増やさない
- 同系統しか出なければ、案数ではなく刺激を変える
- 実装コストが高い題材では、カードを増やして試作数を減らす

## 6. 微差と別方向を分ける

次の差だけでは、通常は同じ案として扱う。

- 速度、移動距離、回転角度、イージング、開始時刻
- 同じ色の別配色

同じ「注ぐ」動作でも、次は別方向として残しうる。

- 普通に注いで揃う: A を操作そのもので見せる
- 迷ってから注ぐ: A の「考える」部分を見せる
- 最後の一滴で揃う: B の終端の間を見せる

動作の形ではなく、`aim_play` × `aim_payoff` の組み合わせが異なるかを見る。

## 7. 束ねて代表を選ぶ

- 似た `aim_play` と `aim_payoff` を持つカードを同系統にまとめ、各系統から代表を残す
- 説明しにくいが他と明らかに異なる案を、無理に既存系統へ入れない
- モデルが「成功しそう」と感じる案だけで寄せない。系統の多様性を優先する
- 代表を並べ、`aim_payoff` と終わりの姿が同じ代表が半数を超えるなら、別の見せ場の系統の代表を加えるか入れ替える
- `aim_play` の「考える」部分だけが違い、ヒーローで見える流れ（何が欠け、何が置かれ、盤がどう変わるか）が同じ案は 1 系統にまとめ、違いは選ばれた後の分岐（9 節）で試す
- 白黒版が途中の姿を描くゲームでは、3 節「白黒版が途中の姿を描くゲーム」で必ず入れる案を代表から外さない
- 系統ごと落とすのは、契約・遊びの誤伝達・D の侵害など規則上の理由があるときに限る。構図上見えにくいなどの予測は、開始の姿と見せ場の 2 フレームを試作して確かめてから決める
- C（選んだ手応え）を束ねや選定の基準にしない。C は A/B の結果として確かめる

初回試作の目的は勝者予測ではなく、人間が方向を比較できることにある。

## 8. 試作では核心以外を削る

試作は `aim_play` と `aim_payoff` が伝わる最小実装にする。

- 静止状態を先に、白黒版（または修正案）の図形を写して描く
- 色は試作の段階でもプレイ画面のゲーム固有色から置き換えない（書き方は `references/contract.md` の 3 節）
- 字形の扱いは `references/contract.md` の 5 節。白黒版で複数の字が 1 本のパスにまとまっている場合は、サブパス（`M` で始まる区切り）ごとに座標を見て字ごとに分け、1 字 1 要素にする（字ごとに色や動きを付けられる）。`<text>` は横を `text-anchor="middle"` で中心に合わせ、縦は `y` をマスの中心から字の大きさの約 0.35 倍下げて合わせる（`dominant-baseline` は描画環境で効き方が揃わない）。一覧サイズで読めるか確かめる
- 例えば「最後の一手」が核なら、そこまでの手を細かく作り込むより、最後の一手の前の間と、その手で盤面が変わる瞬間を優先する
- 回転・拡縮の中心は `transform-origin` で明示する。`transform-box` の選び方は `references/motion.md` の 8 節
- 緩急は `references/motion.md` の 3 節、構図の調整は 4 節に従う

完成品質の細部に時間を使うのは、人間が方向を選んだ後にする。

## 9. 選択後は探索範囲を狭める

方向が選ばれたら、選択理由（残す A と B）を変えずに 4〜8 案程度へ分岐するのが目安になる。

変える候補:

- 見せ場までの間、軌道、反応順、誇張の強さ、終わり方
- 静止状態にする瞬間（`base_revision` で白黒版を直す案に限る）、再生形式（`cut` / `rest-cut` / `seam`）、止まりと開始の間の長さ
- 色の置き方（ゲーム固有色をどの要素に持たせるか、量）
- 他候補から部分採用する表現

各案で変えるのは、上から選んだ差分だけにする。登録済みの `pictogram-showcase.svg`、または人間が `candidate` / `explore` とした案に寄せるときは、構図だけでなく、流れ（何を読んで次へ進むか）・拍・見せ場の値（何がどれだけ動き、何色になるか）まで寄せる。構図だけをまねて流れや見せ場が別物になった案は、選ばれた方向を掘ったことにならない。見せ場を弱める変更（量を減らす、間を詰める、色を抑える）は、推測だけを根拠にせず、人間の指摘か観察の結果があるときにだけ行う。

さらに方向が定まったら 1〜3 案へ絞って仕上げる。

## 10. 再発散する条件

次の場合は、選択済み方向の微調整を続けず広い発散へ戻る。

- A または B の核自体が弱いと人間が判断した
- C が生まれず、A/B の作り方を直しても改善しない
- D を侵さないと A/B が成立しない
- 白黒版と別物にしないと成立しない。白黒版の方を直す案（`base_revision`）を添えて人間に判断を求めてもよい
- 候補間の差がタイミングや量の微差だけになった

再発散は失敗ではない。探索空間へ戻るための通常の操作として扱う。
