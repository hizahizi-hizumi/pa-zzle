# 姿の探索方法

`/design-game-pictogram-showcase` の材料抽出、発散、候補整理に使う。目的は案数を稼ぐことではなく、目的 A（遊びが分かる）と目的 B（解けた気持ちよさが見える）を満たしうる異なる方向を、安い段階で広く確保することにある。

## 1. 材料を抽出する

発散の前に、ゲームから材料を短く列挙する。次の 2 つは必須とし、欠けたまま発散へ進まない。

```yaml
central_action:   # A の材料。プレイヤーが何を見て、何を考え、何をするか
  - 一番上の色が同じ瓶を探す（考える）
  - 瓶を選び、別の瓶へ注ぐ（する）
solved_moment:    # B の材料。何が揃い、どう終わるか
  - 1 本の瓶が単色で満ちる
  - 全瓶が単色で揃い、盤面が静まる
```

加えて次を拾う。

- 動かせる対象と、その所属関係（容器と中身、盤とマス、駒と通路など）
- 題材の物理（重力、流動、衝突、整列、反転など）
- プレイ画面で使う色と、その色が担う役割（識別、状態、完了）と定義元のパス。ライト/ダークで値が変わるかと、両テーマの実際の値（下の「色の定義元の調べ方」）
- プレイ画面の演出（選択・移動・完了で何がどう動くか、どれだけ動くか）。演出が少ないゲームもある
- 白黒版が何をどの構図で、どの状態（解く前・解いている途中・解けた後、静止か動きの途中か）で描いているか。どこを色にすると同じパズルのまま姿が立つか
- 白黒版にある字形（数字・記号）と、その書き方（1 字ずつのパスか、複数の字が 1 本のパスにまとまっているか）
- ゲーム中には実際に起きないが、ゲームの意味から無理なく連想できる誇張

`central_action` は操作の名前ではなく、考える部分とする部分の両方を書く。考える部分が動きで見えないと、A は「何をするか」止まりになる。

### 色の定義元の調べ方

`frontend/src/games/<game>/ui/` 配下で、盤・駒・状態の要素がどう塗られているかを Grep し、定義元ごとに値を引く。

| 定義元 | 値の引き方 | SVG での書き方 |
|---|---|---|
| TS / CSS の定数（色の表、CSS 変数） | 定義ファイルを読む。テーマで分岐していれば両方 | 実値。テーマで変わるなら `.dark` 条件で切り替える |
| Tailwind のパレット色のクラス（`bg-blue-600`、`dark:text-red-400` 等） | `frontend/node_modules/tailwindcss/theme.css` の `--color-<名前>`（`oklch()`） | hex / `rgb()` へ変換した実値。`dark:` 付きのクラスがあれば `.dark` で切り替える |
| アプリのトークンのクラス（`bg-background`、`border-border`、`text-muted-foreground` 等） | `frontend/styles/globals.css` の `:root`（ライト）と `.dark`（ダーク） | `var(--background)` などで参照する（`SKILL.md` の「色」） |

`scripts/resolve_color.py` に、クラス名・名前・`oklch()` を並べて渡すと、どの定義元かと値（hex、トークンなら両テーマと `var()` で書けるか）を出す。`oklch()` を hex へ変換して sRGB の色域外を丸めた場合は印が付くので、`notes` に書く。

```sh
python3 .claude/skills/design-game-pictogram-showcase/scripts/resolve_color.py bg-blue-600 'dark:bg-blue-400' 'bg-red-500/50' border-border
```

### 有彩色の無いゲーム

プレイ画面がアプリのトークン（無彩色）だけで描かれるゲームでは、色付き静止画は白黒版に近くなってよい。色で差を作るためにプレイ画面に無い色を足さない。A と B は動きで伝え、静止状態は「プレイ画面と同じ面・枠の塗り分け」と「解けた状態」で白黒版との違いを持たせる。

## 2. アイデアカードを作る

初回発散ではコードを書かない。1 案につき次だけを短く記録する。

```yaml
id: pour-settle-01
name: 注いで揃う
idea: 片方の瓶が傾き、上の色がもう片方へ移り、受け側が単色で満ちて止まる
aim_play: 「同じ色の上へ注ぐ」判断と操作を 1 回で見せる
aim_payoff: 受け側が単色で満ちた瞬間に動きが止まる
static_pose: 揃った後の姿（2 本の瓶、片方が単色で満ちている）。各周の終わりの止まりでもあり、0% は注ぐ前の姿
playback: cut
references:
  - 中心の操作: 注ぐ
  - 解けた瞬間: 1 本が単色で満ちる
```

- `aim_play` は遊んでいる瞬間の動きで見せる。規則を矢印や記号で説明する図解寄りの案は、遊びたくなる姿にならず除外されやすい。
- `aim_play` / `aim_payoff` は評価点ではなく、後で束ね、セルフレビューで「宣言どおり読めるか」を確かめるための仮説である。
- `static_pose` は一覧選択中の色付き静止画であり、切り替えループの止まり、継ぎ目ループの継ぎ目でもある。動きと切り離して考えない。
  - 静止状態は、白黒版と同じ構成要素・枠組み・視点を保ちながら、ゲームで実際に起こりうる状態にする。典型的には見せ場の後の解けた・揃った状態で、盤の中身は白黒版と違ってよい。
  - 白黒版が解いている途中や動いている途中の姿を描いている場合、その姿をそのまま静止状態にすると「止まっているのに途中」の絵になる。その姿は開始の姿（0%）の候補として使い、静止状態は見せ場の後の状態にする。
  - 中身を変えた静止状態が白黒版と同じパズルに見えるかは、一覧サイズの比較列（白黒版と他ゲームと並べた列）で確かめる。
  - `cut`（切り替えループ）: 開始の姿から見せ場まで動いた後、見せ場の姿（= 静止状態）で止まり、周の境界で開始の姿へ瞬時に切り替えて繰り返す。「解けた後の姿」を静止状態にすれば、見せ場で終わってそのまま止まれる。始点は静止状態と異なってよい（例: 解く前の姿から始める）。
  - `seam`（継ぎ目ループ）: 0% = 100% の継ぎ目を静止状態にする。「解く前の姿」を静止状態にするなら、解けた状態から元へ戻す流れが要る。「解けた後の姿」を静止状態にするなら、一度崩してから再び揃える流れになる。
- `playback` は仮置きでよい（選び方は 3 節）。

## 3. 再生形式を選ぶ

`cut` を基本とする。「解く前 → 見せ場 → 解けた姿で止まる」流れをそのまま繰り返せ、構図も周期も膨らまない。1 回だけ再生して止まる形式は使わない。選んだ瞬間しか動かず、見逃すと A/B が伝わらない。D は `cut` の止まりで満たす。

- `cut`: 見せ場の姿で止まった後、開始の姿へ瞬時に切り替えて繰り返す。切り替えは「場面の頭出し」として読まれ、フェードや巻き戻しで戻すより自然に受け取られた。
- `seam`: 継ぎ目が意味として自然に成立する場合だけ検討する。不可逆な操作のゲーム（注ぐ、消す、置く等）は元に戻らないため、継ぎ目に「次の問題が来る」「役割が交代する」などの物語が要り、構図が変わり周期も伸びやすい。これまでの試作では「次の問題」系は除外され、「交代」は対象の大きさを揃える点だけが採用された。
- フェードで開始の姿へ戻すループは、ループ自体は受け入れられても戻りが不自然と受け取られた。途中経過を見せる戻し方は試作しない。

ヒーローには枠がないため、画面端から対象が出入りする動きは描画域の端で切れて見え、D を損なう。`seam` の継ぎ目を作るために出入りを使わない。

### 可逆な操作のゲーム

操作を戻せるゲーム（動かした駒を動かし戻せる、反転を反転し直せる等）では、`seam` が物語なしで作れそうに見える。戻し方を 2 つに分けて考える。

- 逆の手で戻す（やった手を逆順にたどる）: 巻き戻し再生に見え、「戻りが不自然」と受け取られやすい。採らない。
- 合法手で一巡して戻る（別の手順を進めた結果として元の配置に戻る）: 前へ進む動きのまま始めの姿へ着くため、自然な継ぎ目になりうる。ただし手数が増え周期が伸びやすい。試作する前に、合法手で一巡する最小手数を数え、その手数で周期の目安（`references/motion.md` の 2 節）に収まるかと比べてから試作するか決める。

`seam` で継ぎ目（= 静止状態）を解けた姿にすると、周の最初の動きが完成を崩すことになり、「解けた姿を崩す」場面が最初に見える。A/B の順（操作 → 解けた瞬間）と逆になるため、`cut`（解く前から始めて解けた姿で止まる）と比べてから採る。

組み立て方と周期の目安は `references/motion.md`。

## 4. 一回の長い発散へ依存しない

同じ prompt で案数だけ増やすと、後半が言い換えになる。複数回を独立させ、毎回違う刺激を与える。1 エージェント内で発散するなら回ごとに刺激と視点（A 側 / B 側、操作する人 / 盤面）を変え、サブエージェントを使える環境なら回ごとに別のサブエージェントへ発散させる。

A 側の刺激:

- 中心の操作を 1 回だけ、はっきり見せる
- 「考える」部分（探す、見比べる、迷う、手がかりを読む）を間で見せる
- 操作の結果として盤面がどう変わるかを主役にする
- 動きを極端に少なくして操作の核だけ残す
- このゲームのルールにしか無い操作や制約（何が動けて何が動けないか、何が何を決めるか）を見せる
- 1 手ではなく、数手の手順（順番に意味がある並び）を見せる

B 側の刺激:

- 揃った瞬間に動きが止まる「静まり」を見せ場にする
- 最後の一手など終端の間を主役にする
- 一つの完了から連鎖させる
- 状態の変化（未確定 → 確定、ばらばら → 整列、隠れている → 見える）が盤面全体へ広がる構成にする
- 達成の構造（どこが揃えば解けたか: 行・列・全体・対応関係）が見える構成にする
- プレイ画面で完了・正解が色で示されるゲームなら、完了したものの色が初めて全部見える構成にする

プレイ画面の演出（選択・移動・完了の動き）が少ないゲームでは、演出を写すのではなく、ルール固有の操作・状態の変化・手順・達成の構造から刺激を選ぶ。有彩色を前提にした刺激は、プレイ画面に有彩色があるゲームでだけ使う。

これはカテゴリごとのノルマではない。同じ局所解から離れるための刺激として使う。

D（落ち着き）は発散段階で案を縛らない。ただし、常時大きく動き続ける、強く点滅する、画面外へ飛び出す・画面端から出入りするなど、明らかに D を侵す案は試作対象にしない。

## 5. 初回の量は探索空間に合わせる

操作が 1 種類で盤が小さい単純な題材なら、30〜60 枚程度のアイデアカードを作り、重複を整理してから 10〜20 程度を試作する運用が一つの目安になる。数値は固定条件ではない。

- 十分に異なる方向が揃えば増やさない
- 同系統しか出なければ、案数ではなく刺激を変える
- 実装コストが高い題材では、カードを増やして試作数を減らす

## 6. 微差と別方向を分ける

次の差だけでは、通常は同じ案として扱う。

- 速度、移動距離、回転角度、イージング、開始時刻
- 同じ色の別配色

同じ「注ぐ」動作でも、次は別方向として残しうる。

- 普通に注いで揃う: A を操作そのもので見せる
- 迷ってから注ぐ: A の「考える」部分を見せる
- 最後の一滴で揃う: B の終端の間を見せる

動作の形ではなく、`aim_play` × `aim_payoff` の組み合わせが異なるかを見る。

## 7. 束ねて代表を選ぶ

- 似た `aim_play` と `aim_payoff` を持つカードを同系統にまとめ、各系統から代表を残す
- 説明しにくいが他と明らかに異なる案を、無理に既存系統へ入れない
- モデルが「成功しそう」と感じる案だけで寄せない
- C（選んだ手応え）を束ねや選定の基準にしない。C は A/B の結果として確かめる

初回試作の目的は勝者予測ではなく、人間が方向を比較できることにある。

## 8. 試作では核心以外を削る

試作は `aim_play` と `aim_payoff` が伝わる最小実装にする。

- 静止状態を先に描き、白黒版と並べて同じパズルだと分かることを確かめる
- 色はプレイ画面の定義元から写す（1 節の表）。試作の段階でも別の色に置き換えない。テーマで変わる実値は、ダーク側の値を祖先 `.dark` 条件のルールで切り替える。アプリのトークンは `var()` で参照すればテーマに追従する
- 輪郭など前景の線は `var(--game-pictogram-strong)`、補助は `var(--game-pictogram-soft)` にする
- プレイ画面の値のままでは実表示サイズで見えない線・面（淡い枠線など）は、見えることを優先して近い役割の色で代え、理由を `notes` に書く
- 数字・記号は白黒版の字形を流用する。複数の字が 1 本のパスにまとまっている場合は、サブパス（`M` で始まる区切り）ごとに座標を見て字ごとに分け、1 字 1 要素にする（字ごとに色や動きを付けられる）。白黒版に無い字形は `<text>` で書き、`font-family` に `system-ui, sans-serif` などシステムの sans-serif 系を明示する。横は `text-anchor="middle"` で中心を合わせ、縦は `y` をマスの中心から字の大きさの約 0.35 倍下げて合わせる（`dominant-baseline` は描画環境で効き方が揃わない）。一覧サイズで読めるか確かめる
- 例えば「最後の一手」が核なら、そこまでの手を細かく作り込むより、最後の一手の前の間と、その手で盤面が変わる瞬間を優先する
- 回転・拡縮は `transform-box: fill-box` と `transform-origin` を明示する
- 緩急は keyframe 内の `animation-timing-function` で付け、イージングを線形 keyframe へサンプリングしない（`references/motion.md`）
- 構図の調整は `references/motion.md` の「構図を変えてよい範囲」に収める

完成品質の細部に時間を使うのは、人間が方向を選んだ後にする。

## 9. 選択後は探索範囲を狭める

方向が選ばれたら、選択理由（残す A と B）を変えずに 4〜8 案程度へ分岐するのが目安になる。

変える候補:

- 見せ場までの間、軌道、反応順、誇張の強さ、終わり方
- 静止状態にする瞬間、再生形式（`cut` / `seam`）、止まりと開始の間の長さ
- 色の置き方（どの要素に色を持たせるか、量）
- 他候補から部分採用する表現

さらに方向が定まったら 1〜3 案へ絞って仕上げる。

## 10. 再発散する条件

次の場合は、選択済み方向の微調整を続けず広い発散へ戻る。

- A または B の核自体が弱いと人間が判断した
- C が生まれず、A/B の作り方を直しても改善しない
- D を侵さないと A/B が成立しない
- 白黒版と別物にしないと成立しない
- 候補間の差がタイミングや量の微差だけになった

再発散は失敗ではない。探索空間へ戻るための通常の操作として扱う。
