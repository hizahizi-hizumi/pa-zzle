# PR粒度・レビュー容易性・構成ルール

## コア原則

- 1 PR = 1つの目的。1文で要約できないなら分割を検討する。
- 無関係な変更を「ついで」で混ぜない。
- 機械的変更と意味変更は原則分ける。
- 純粋なリファクタと挙動変更は原則分ける。
- 依存更新・CI・開発環境変更と学習者向け機能変更は原則分ける。
- 小さく保つが、分割そのものを目的にしない。
- 可能な範囲で各PRを単体でマージ可能な状態にする。

## AmuQueryでのPR境界

ディレクトリではなく、成立する学習・実行・採点単位で切る。

同じPRに置くべき典型:

- 1つの問題を成立させる problem / fixture / answer path / manifest / oracle / 採点基準
- 1つのLU変更で同時に整合させる必要がある 学習設計 / material / practice / TST
- runtime変更と、その回帰を閉じるテスト・契約更新
- learner-facing変更と、それに必須のCLI/Web表示修正

別PRに分ける典型:

- 大規模な移動・整形と意味変更
- 独立したリファクタと機能追加
- 開発基盤変更と学習者向け変更
- 独立してrevertしたい変更

AmuQueryのVertical Sliceを、フォルダが違うという理由だけで分断しない。

## PR本文

タイトルは短く具体的にする。

本文には以下を含める。

- **What**: 何を変えたか
- **Why**: なぜ変えるか
- **Validation**: 何を確認したか。`uv run --frozen python -m dev.tools.validate`、実runtime確認、手動確認など
- **Impact / Risk**: 必要な場合のみ

特に次を明示する価値が高い。

- learner-facing表示・回答契約への影響
- grading / oracle / 採点基準への影響
- execution environmentへの影響
- 公開境界への影響
- breaking changeや移行の有無

実施していない確認を実施済みと書かない。

## レビュー品質

- 差分が大きい場合は、分割できない理由と推奨レビュー順序を書く。
- 対応するテスト・fixture・仕様更新を欠いた未完成状態をmainへ入れない。
- `uv run --frozen python -m dev.tools.validate` は最低条件であり、実runtime成立を単独で証明しないというリポジトリ方針をPR本文でも誤認しない。

## 禁止事項

- 無関係な変更の混在。
- 大規模整形と意味変更の混在。
- レビュー不能な巨大PRを理由なく作ること。
- PRを小さく見せるために、成立に必要な契約・テスト・fixtureを別PRへ追い出すこと。
