# PR の粒度と本文

## 粒度

- 1PR を、1文で要約できる1つの目的にする。1文で要約できなければ分割を検討する
- 無関係な変更を「ついで」で混ぜない
- 機械的変更（大規模な移動・整形）と意味変更は原則分ける
- 純粋なリファクタと挙動変更は原則分ける
- 依存更新・CI・開発環境変更と利用者向け機能変更は原則分ける
- 小さく保つが、分割そのものを目的にしない
- 可能な範囲で各 PR を単体でマージできる状態にする
- ディレクトリではなく、独立して利用・検証・revert できる変更目的で切る
- 関連する垂直スライスを、フォルダが違うという理由だけで分断しない
- 1つの機能変更と、それを成立させるテスト・契約・表示変更は同じ PR に置く
- API / schema / 型の変更と、その新契約へ必須で追従する利用側は同じ PR に置く
- バグ修正と、その再発を防ぐ回帰テストは同じ PR に置く
- PR を小さく見せるために、成立に必要な契約・テストを別 PR へ追い出さない
- 対応するテスト・仕様更新を欠いた未完成の状態を `main` へ入れない

## PR 本文

- タイトルは「何が変わるか」が1行で分かるように、短く具体的にする
- 本文には次を書く
  - What: 何を変えたか
  - Why: 背景と、なぜ変えるか
  - Validation: 何を確かめたか。変更範囲に対応する `AGENTS.md` の検証コマンドや手動確認を書く
  - Impact / Risk: 当てはまるときだけ書く
- Impact / Risk では、次に当てはまるものを明示する
  - 利用者向け挙動への影響
  - API / データ契約への影響
  - 実行環境・CI・運用への影響
  - breaking change や移行の有無
- 実施していない確認は未実施と書く
- 静的検査だけで、実行時に動くことを確かめた扱いにしない
- 差分が大きいときは、分割できない理由と推奨するレビュー順序を書く
