# PR粒度・レビュー容易性・構成ルール

## コア原則

- 1 PR = 1つの目的。1文で要約できないなら分割を検討する。
- 無関係な変更を「ついで」で混ぜない。
- 機械的変更と意味変更は原則分ける。
- 純粋なリファクタと挙動変更は原則分ける。
- 依存更新・CI・開発環境変更と利用者向け機能変更は原則分ける。
- 小さく保つが、分割そのものを目的にしない。
- 可能な範囲で各PRを単体でマージ可能な状態にする。

## PR境界

ディレクトリではなく、独立して利用・検証・revertできる変更目的で切る。

同じPRに置くべき典型:

- 1つの機能変更と、その変更を成立させるテスト・契約・表示変更
- API / schema / 型の変更と、その新契約へ必須で追従する利用側
- バグ修正と、その再発を防ぐ回帰テスト

別PRに分ける典型:

- 大規模な移動・整形と意味変更
- 独立したリファクタと機能追加
- 開発基盤変更と利用者向け変更
- 独立してrevertしたい変更

関連する垂直スライスを、フォルダが違うという理由だけで分断しない。

## PR本文

タイトルは短く具体的にする。

本文には以下を含める。

- **What**: 何を変えたか
- **Why**: なぜ変えるか
- **Validation**: 何を確認したか。変更範囲に対応する `AGENTS.md` のコマンドや手動確認を記載する
- **Impact / Risk**: 必要な場合のみ

特に次を明示する価値が高い。

- 利用者向け挙動への影響
- API / データ契約への影響
- 実行環境・CI・運用への影響
- breaking changeや移行の有無

実施していない確認を実施済みと書かない。

## レビュー品質

- 差分が大きい場合は、分割できない理由と推奨レビュー順序を書く。
- 対応するテスト・仕様更新を欠いた未完成状態をmainへ入れない。
- 静的検査だけで実行時の成立を保証した扱いにしない。

## Git運用

- PRはオープンで作成し、ドラフトにしない。
- PRのマージ方式はmerge commitとし、squash merge / rebase mergeは使わない。
- 作業中に`main`を取り込まない。
- 作業完了時に`main`とコンフリクトしている場合だけ、最新`main`をmerge commitで取り込む。

## 禁止事項

- 無関係な変更の混在。
- 大規模整形と意味変更の混在。
- レビュー不能な巨大PRを理由なく作ること。
- PRを小さく見せるために、成立に必要な契約・テストを別PRへ追い出すこと。
