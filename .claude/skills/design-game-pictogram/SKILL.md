# design-game-pictogram

ゲーム一覧で対象ゲームを素早く識別でき、そのゲーム自身の姿を保ち、既存ピクトグラム群と並べても成立する高品質なピクトグラムを制作する Skill。

## 起動

`/design-game-pictogram`

対象ゲーム、表示サイズ、色数などの制約を引数または会話 context から受け取る。

## 目的と成果物

第一の成果物は、実際に採用できる完成ピクトグラムである。

大量生成、候補比較、評価軸、比較シート、機械検査、判断記録は、完成品質を上げるための手段として使う。工程の再現や記録量を完成条件にしない。

通常は次を成果物とする。

- 採用する SVG ピクトグラム
- 必要な場合だけ、最終判断に関係する候補と短い判断理由
- `scripts/check_svg.py` の最終検査結果

探索途中の大量候補、比較シート、試作 SVG は原則として一時ファイルに置き、対象 Issue や依頼で保存が必要な場合だけリポジトリへ残す。

## 依頼別の入口

依頼内容に応じて開始位置を変える。

- **新規制作**: Step 1 から開始し、着眼点の探索から完成 SVG まで進める。
- **既存 SVG の改善**: 既存 SVG と利用条件を読み、Step 7 で問題を診断してから Step 8 以降で再探索・仕上げを行う。
- **レビュー / 検証のみ**: 対象 SVG を変更せず、Step 7 の実サイズ比較と Step 10 の機械検査を行い、`references/method.md` の評価軸に沿って findings を返す。変更は依頼された場合だけ行う。

## 参照する正本

制作開始時に次を確認する。

- `DESIGN.md` — ゲームを表す視覚表現と一覧での視覚的優先順位
- `references/method.md` — 探索とふるい分けで使う評価方法
- `examples/README.md` — レビュー済み完成見本と品質観点

評価軸の外部根拠が必要な場合だけ `references/research.md` を参照する。PoC の途中経緯が必要な場合だけ `docs/立ち上げ/ゲーム選択ピクトグラムPoC.md` を参照する。

## 動作原則

- 安い表現で広く探索し、有望な案だけ高コストな表現へ進める。
- 生成前に候補を厳密なスキーマへ押し込まず、生成後の選別と改善に構造化を使う。
- 初期探索では微差の完成度より着眼点の幅を優先する。
- ふるい分けでは明確な欠点を先に落とし、残った候補を相対比較する。数値採点で機械的に順位を決めない。
- 類似案は同じ方向としてまとめる。ただし小さな差が見た目を大きく変えそうなら別候補として残す。
- 早い段階で一方向へ収束させず、異なる有望方向を複数残す。
- 候補数そのものを達成条件にしない。新しい方向が出なくなったこと、または十分な品質の候補が得られたことを次段階へ進む判断に使う。

## 動作フロー

### 1. 制作条件を確認する

最初に、品質判断に必要な条件だけを確認する。

- 対象ゲームと、プレイヤーが実際に見る・触る主要な対象や構造
- ピクトグラムが使われる場所と代表表示サイズ、最小表示サイズ
- SVG の `viewBox`
- 使用可能な色、色数、透過の可否
- 線幅、塗り、文字使用など既存制約
- 比較対象となる既存ピクトグラム群

未指定の制約を勝手にブランド規則として追加しない。現在の実装と依頼内容から必要な制作条件だけを置く。

### 2. 着眼点を大量生成する

SVG を作る前に、「何を描くか」の候補を一文程度で大量生成する。

初期探索は数十案規模になってもよい。少数の案を丁寧に説明することより、異なる着眼点を広く出すことを優先する。

候補生成では、必要に応じて次を発想材料として使う。

- ゲーム中に見る対象
- 盤面や対象同士の構造
- 数字、水、向き、空きなどの状態・記号
- 移動、積層、流入などの関係・動作
- プレイヤーがそのゲームらしいと感じる典型的な状態

これらを全候補へ埋める必要はない。候補ごとの「対象 / 構造 / 状態 / 仮説」の記録を必須にしない。

### 3. 着眼点を粗くふるい分ける

`references/method.md` の「着眼点の選別」を使い、ゲーム固有性が弱い、説明依存が強い、小さな一枚絵へ落とし込みにくいなど、SVG にする価値が低い案を早い段階で落とす。

類似案は方向ごとにまとめ、代表案を残す。有望な方向が複数ある場合は、現時点の完成度だけで一本化しない。

### 4. 有望方向を具体的な構図へ展開する

残した各方向から複数の構図案を生成し、「どう描くか」の探索へ進む。

この段階では SVG を書かず、次が判断できる程度まで具体化する。

- 主役となる対象
- 補助要素
- 要素数
- 配置と余白
- 具体性の程度
- 何を省略するか
- 線中心か面中心かなどの大まかな表現

一つの方向から微差だけを増やさず、主役、配置、情報量、具体度などを振った派生を作る。

### 5. SVG 化する案をふるい分ける

具体的な構図案から、`references/method.md` の「構図案の選別」を使って、実際に描いて比較する価値があるものを残す。

弱い案を落とした後も、着眼点の異なる候補を複数残す。評価軸ごとの点数合計で上位だけを残す方法は使わない。

### 6. SVG の試作を生成する

絞った案だけを SVG 化する。ここでは最終的な光学補正まで仕上げず、構図と主要要素が実物として成立するか確認できる精度を優先する。

試作 SVG は原則として一時領域に置く。

生成後、比較を妨げる構文エラーや明らかな制約違反を先に除くため、必要に応じて機械検査を実行する。

```sh
python3 .claude/skills/design-game-pictogram/scripts/check_svg.py path/to/candidate.svg
```

### 7. 実サイズで SVG を比較する

候補 SVG と既存ピクトグラムを同じ表示条件で並べる。

```sh
python3 .claude/skills/design-game-pictogram/scripts/make_review_sheet.py \
  --output /tmp/pictogram-review.html \
  --size 112 \
  candidate-a.svg candidate-b.svg candidate-c.svg existing.svg
```

代表サイズに加えて、実際に使う最小サイズでも確認する。

`references/method.md` の「SVG 試作の選別」を使い、構成要素の知覚可能性、実表示サイズ、光学的重量、弁別性、一覧内での見え方を比較する。

ゲーム名を隠した表示は診断に使えるが、ゲーム名を完全に当てられること自体を絶対条件にはしない。

### 8. 良案を起点にもう一度探索する

有望な SVG が見つかったら、そのまま微調整だけで終わらせず、良かった要素の周辺をもう一度探索する。

ここで初めて「なぜ良かったか」を分析し、次世代の候補生成へ使う。

派生例:

- 主役をさらに強くする
- 不要な補助要素を削る
- 余白や占有率を大きく変える
- 配置を反転・再構成する
- 他候補の良い部分を組み合わせる
- より大胆に単純化または具体化する

原因と直し方が明確な問題は局所修正してよい。直し方が複数ある場合や、さらに上振れを狙える場合は複数派生を生成して再比較する。

生成時に一変数だけ変える実験へ限定しない。比較目的が失われない範囲で、複数要素をまとめて変えてよい。

### 9. 最終候補を仕上げる

最終候補が絞れたら、探索より造形品質へ重点を移す。

- 線幅
- 要素間隔
- 外形の占有率
- 余白
- 黒量・密度
- 視覚階層
- 光学的な中心
- 最小サイズでの可読性

必要な要素が弱い場合、要素数を増やす前に大きさ、位置、線幅、余白を調整する。

既存ピクトグラム群と同条件で再比較し、重大な問題がなく微調整だけになったら採用候補とする。

### 10. 最終 SVG を検査する

採用する SVG に対して機械検査を実行する。

```sh
python3 .claude/skills/design-game-pictogram/scripts/check_svg.py path/to/pictogram.svg
```

色数などの条件がある場合は明示する。

```sh
python3 .claude/skills/design-game-pictogram/scripts/check_svg.py \
  path/to/pictogram.svg \
  --max-colors 2 \
  --forbid-gradients \
  --forbid-filters \
  --forbid-external-images
```

機械検査は構文、色数、外部依存などの制約を確認する。意味の分かりやすさ、魅力、光学的重量を自動判定したものとは扱わない。

## 完成条件

`references/method.md` の収束条件を満たし、採用 SVG が最終機械検査を通ることを完了条件とする。

特に、盤面の縮小コピーでも汎用アイコンでもなく、そのゲーム自身の姿を一覧向けに縮約できていることを確認する。

候補数、反復回数、判断記録の網羅性、工程の再現そのものを完成条件にしない。

## 制約

- `DESIGN.md` をこの Skill の成果物として変更しない
- ゲーム本体コンポーネントの縮小・再利用を目的にしない
- ゲーム固有図形の無理な共通コンポーネント化をしない
- 生成案を構造化すること自体を目的にしない
- 大量生成した候補を保存すること自体を目的にしない
- 機械検査で視覚評価を代替したと主張しない
- SVG 内に実装履歴や PoC 経緯をコメントとして残さない
