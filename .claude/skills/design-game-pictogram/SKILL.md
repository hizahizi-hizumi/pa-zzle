# design-game-pictogram

対象ゲーム・表示サイズ・色数などの制約は、引数か会話から受け取る。

## 依頼別の入口

- 新規制作: 手順 1 から始め、手順 11 まで進める
- 既存 SVG の改善: 既存 SVG と利用条件を読み、手順 7 で問題を診断してから、手順 8 以降で探索し直して仕上げる
- レビュー・検証だけ: 対象の SVG を変えず、手順 7 の実サイズ比較と手順 10 の機械検査を行い、`${CLAUDE_SKILL_DIR}/references/method.md` の「評価軸」に沿った指摘を返す。変更は頼まれたときだけ行う
- `/add-puzzle` からの起動: 新規制作と同じ手順で進め、手順 8 で人間の方向選択を待たない
  - 磨いた候補を間引かずに並べ、比較表示に推奨する候補と理由を添える
  - 推奨候補を仮採用として手順 9・10 で仕上げ、比較表示・各候補の SVG・仮採用の SVG を起動側へ返す
  - 代替案の SVG は `docs/パズル/導入調査/<パズル名>/ピクトグラム検討/` に置く
  - 方向の選択は `/add-puzzle` の最終レビューで人間が行う。別の方向や組み合わせが選ばれたら手順 9 から仕上げ直す

## 手順

1. 次を読む
   - `DESIGN.md` の「コンポーネント」の「ゲームを表す表現」と「ゲームピクトグラム」
   - `${CLAUDE_SKILL_DIR}/references/method.md`。手順 2〜10 はその「探索の原則」に沿って進める
   - `${CLAUDE_SKILL_DIR}/examples/README.md` と、そこに挙げた完成見本の SVG（`${CLAUDE_SKILL_DIR}/examples/nanpure.svg` ほか）
   - 評価軸の外部の根拠が要るときだけ `${CLAUDE_SKILL_DIR}/references/research.md`、PoC の途中の経緯が要るときだけ `docs/立ち上げ/ゲーム選択ピクトグラムPoC.md`
2. 対象ゲーム・実表示サイズ・比べる既存ピクトグラム群を確かめる。指定されていないブランドの決まりを足さない
3. 新しい SVG は `${CLAUDE_SKILL_DIR}/assets/pictogram.svg` を写して始め、次の共通描画契約に従う。ゲーム固有の形・線端・線の結合・塗り分けは対象ゲームに合わせて決める
   - `viewBox` は `0 0 120 120`
   - 線幅は `4` と `2` だけ
   - 描画色は `var(--game-pictogram-strong)` と `var(--game-pictogram-soft)` の2色だけ
4. SVG を作る前に、何を描くかの着眼点を一文ずつ、数十案の規模で出す。説明の丁寧さより着眼点の幅を優先する
5. method.md の「着眼点の選別」で弱い案と重複する案を落とす。一方向だけを勝者として残さず、異なる有望な方向を残す
6. 残した各方向から、主役・補助要素・配置・余白・具体性・省くものを振った構図案を複数出し、method.md の「構図案の選別」で SVG にして磨く方向を複数残す
7. 方向ごとに SVG を作り、各方向を独立に磨く
   - 一方向の中で試作を複数作り、その方向を最もよく表す代表案を残す。内部の試作は人間に見せない
   - method.md の「人間提示前の品質条件」を代表サイズと最小サイズで確かめる
   - 一候補だけを丁寧に仕上げて、ほかをラフなまま並べない
   - 機械検査は `python3 ${CLAUDE_SKILL_DIR}/scripts/check_svg.py <SVG のパス>` で行う
8. 磨いた候補を同じ条件で並べ、代表サイズと最小サイズの両方を人間に見せる
   - 比較表示は `python3 ${CLAUDE_SKILL_DIR}/scripts/make_review_sheet.py --output /tmp/pictogram-review.html --size 112 <候補の SVG>... <既存の SVG>...` で作る
   - 各候補に識別子と一行の方向説明を付ける。順位を付けて一案へ誘導しない
   - 採用する方向、組み合わせたい部分（「A の構図 + C の要素」のような部分選択）、探索し直すかを人間に確かめ、選択を待つ。人間が選択を明示的に任せたときだけ待たずに進む。`/add-puzzle` からの起動では「依頼別の入口」に従う
9. 選ばれた方向か要素の組み合わせを元に、線幅・要素の間隔・余白・黒の量・視覚の階層・光学中心・最小サイズでの読みやすさを詰める。部分を組み合わせるときは、その意図を一案にまとめて実サイズの比較をやり直す
10. 採用する SVG に `check_svg.py` を実行する。機械検査の結果を、意味の分かりやすさ・魅力・光学的重量の判定として扱わない
11. そのゲームに `pictogram-showcase.svg` があり、`pictogram.svg` の図形を変えたときは、`DESIGN.md` の「ゲームピクトグラム」に沿って showcase の静止状態にも同じ図形を写し、`design-game-pictogram-showcase` スキルを起動して、その動作フロー 4（自己チェックとレビュー）からやり直す

## 完了の条件

- 新規制作・改善: 人間の方向選択を経て method.md の「収束条件」の「最終完成」を満たし、採用した SVG が `check_svg.py` を通り、手順 11 が要るときはそれを終えたときに完了とする。方向の候補を見せた時点は途中であり、人間が選択を明示的に任せていなければ完了にしない
- `/add-puzzle` からの起動: 仮採用の SVG が最後の機械検査を通り、推奨と理由を添えた比較表示を返したときに完了とする
- レビュー・検証だけ: 対象を変えずに評価と機械検査の結果を返したときに完了とする

## 守ること

- 探索中の大量の候補・内部比較・試作の SVG は一時ファイルに置く。方向選択の前の候補を完成見本やプロダクションの成果物として扱わない
- `DESIGN.md` を変えない
- ゲーム本体のコンポーネントを縮めて再利用することを目的にしない
- ゲーム固有の図形を無理に共通コンポーネントにしない
- 生成した案を構造化することと、大量の候補を保存することを目的にしない
- 機械検査で見た目の評価に代えたと言わない
- SVG に実装の履歴や PoC の経緯をコメントで残さない
