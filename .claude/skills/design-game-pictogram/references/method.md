# ゲーム選択用ピクトグラム設計方法

この文書は `/design-game-pictogram` で使う評価方法を定義する。特定ゲームの正解形状は定義しない。

## 1. 目的

ゲーム選択用ピクトグラムの目的は、ゲーム一覧で対象ゲームを素早く識別できることにある。

実ゲーム盤面を忠実に縮小すること、一般的なUI操作アイコンへ還元すること、ブランド装飾を追加することは目的ではない。

また、一発で完成形を生成することも目的ではない。再現可能にすべきものは、**複数候補を発散して比較し、良い部分を選択・合成し、評価軸に基づいて完成度を上げていく収束過程**である。

## 2. 設計モデル

### 2.1 視覚語彙

対象ゲームから次の4種類を列挙する。

- **対象**: ゲーム内で見る物体
- **構造**: 対象同士の空間関係や盤面構造
- **状態・記号**: 数字、液体、向き、空きなど識別に必要な状態
- **関係・動作**: 移動、積層、流入など、静止画でも重要な関係

列挙した全てを描かない。意味的距離を縮めるのに寄与するものだけを残す。

### 2.2 最小構成

最小構成は「要素数が最少」ではなく、次の両方を満たす最小の視覚情報である。

1. 対象ゲームへの意味的距離が十分近い
2. 他ゲームのピクトグラムと区別できる

役割の異なる特徴を組み合わせると、同種の細部を増やすより少ない情報量で識別できる場合がある。

例:

- ウォーターソート: 容器という**対象** + 水という**状態**
- ナンプレ: 格子という**構造** + 数字という**記号**

この組み合わせは現時点のPoC観察であり、固定テンプレートではない。

### 2.3 発散と収束

候補を1案ずつ順番に直し続けるだけでは、最初の偶然に強く依存する。初稿では、意図的に異なる仮説を持つ候補群を作る。

候補を増やすときは無作為に量産せず、次のどれを変えた案か説明できるようにする。

- 採用する視覚語彙の組み合わせ
- 対象・構造・状態のどれを主役にするか
- 外形の占有率と余白
- 線中心か面中心か
- 状態情報をどこまで具体化するか
- 要素同士の位置関係

候補数は固定しない。探索初期では4〜8案程度を目安にし、互いにほぼ同じ案を大量生成しない。

候補群からの収束方法は3種類ある。

1. **全体採用**: 1案が明確に良ければ、その案を基準に磨く
2. **部分採用**: 「Aの外形」「Bの余白」「Cの記号配置」のように良い部分を選ぶ
3. **合成案**: 部分採用した要素を新しい1案へ再構成し、独立した候補として再評価する

合成は単純な平均ではない。採用した各部分がどの評価軸を改善するためかを記録する。

## 3. 評価軸

### 意味的距離

ピクトグラムの見た目と、表したいゲーム概念との隔たり。

確認:

- ゲーム名を隠したとき、対象ゲームまたは十分近いゲーム類型を想起できるか
- 汎用的な「水」「格子」「車」だけで止まっていないか
- 追加した細部がゲーム識別に寄与しているか

### 構成要素の知覚可能性

描いた各要素が、意図した物体または形として認識できるか。

確認:

- 数字が格子線に埋もれていないか
- 容器と水が別要素として読めるか
- 小サイズで隙間や境界が潰れていないか

### 視覚複雑性

認識のために処理しなければならない線、面、記号、状態の量。

確認:

- 問題状態の再現にしか使わない情報を持っていないか
- 同じ意味の情報を過剰に繰り返していないか
- 色や濃淡を増やす前に余白と配置で分離できないか

### 具体性

現実の対象またはゲーム中に見る対象との形状的な近さ。

抽象化自体を目的にしない。具体性を下げて意味的距離が悪化するなら戻す。

### 弁別性

一覧中の他ゲームと見分けられるか。

単体表示ではなく、必ず既存ピクトグラム群と同じサイズで比較する。

### 光学的重量

見た目としての強さ。面積、線幅、黒量、密度、余白、形状によって決まる。

数値上同じサイズ・線幅でも揃うとは限らない。

確認:

- 一つだけ大きく・濃く見えないか
- 識別に必要な副要素が主構造に負けていないか
- 幾何学的中央より見た目として偏っていないか

## 4. 候補比較

候補群は同一表示条件で並べる。評価は「どれが好きか」だけで終わらせない。

比較時は、各候補について次を短く記録する。

- 残す価値がある部分
- 捨てるべき部分
- 他案より優れている評価軸
- 他案より弱い評価軸

「Aが良い」だけでなく、「Aの外形は良いが、数字配置はBが良い」のような部分比較を許容する。

人間から「こことここがいい」というフィードバックが出た場合、それをそのまま合成せず、どの評価軸を改善しているかへ翻訳してから新案を作る。

## 5. 反復手順

各反復で次を1セットとして記録する。

1. **観察**: 実サイズで何が問題に見えるか
2. **仮説**: どの評価軸の問題か
3. **変更**: 何を変えるか
4. **機械検査**: SVG制約に違反していないか
5. **比較**: 同じ表示条件で改善したか

反復には2種類ある。

- **局所修正**: 位置、線幅、余白、占有率など、原因が明確な問題を1案のまま直す
- **分岐探索**: どの直し方が良いか不明な場合、2〜4案へ枝分かれさせて比較する

一度の局所修正で複数の独立要因を大きく変えない。変更理由が追えなくなるため。

一方、分岐探索では違いを意図的に大きくし、比較可能な仮説を作る。

## 6. 収束条件

「候補をたくさん作った」こと自体を完了条件にしない。次を満たすまで反復する。

- 対象ゲームへの意味的距離が十分近い
- 必要な構成要素が実サイズで知覚できる
- 既存ゲーム群と弁別できる
- 一覧内で光学的重量が突出しない
- 与えられた色数・線・SVG制約を満たす
- 直近の反復で、重大な問題ではなく微調整だけが残っている

最終判断が人間の視覚評価を含むことは許容する。ただし、そこまで到達する工程と判断理由は記録可能でなければならない。

## 7. 機械化する範囲

スクリプトで判定してよいもの:

- SVGとして解析可能か
- `viewBox` の有無
- 色指定の種類数
- gradient / filter / 外部画像等の使用
- `<text>` 使用の有無
- 比較用HTMLの同一サイズ配置

人間または視覚モデルで確認するもの:

- 意味的距離
- 構成要素を正しく知覚できるか
- 光学的重量
- 一覧全体の静けさ
- 他ゲームとの弁別性
- 候補間の部分比較と合成判断

機械検査のPASSをデザイン品質のPASSと同一視しない。

## 8. 再現性

再現性とは同じSVGが出ることではない。

次を同じ入力条件から繰り返せることを指す。

- 視覚語彙の列挙
- 意図的に差のある候補群の生成
- 候補間の比較と、部分採用・合成理由の記録
- SVG制約の機械検査
- 実表示サイズでの比較
- 評価軸に基づく修正理由
- 許容できる品質範囲までの収束

異なる実装者・AIでも、同じ工程と評価軸を使い、許容できる品質範囲へ収束できることを目標とする。
