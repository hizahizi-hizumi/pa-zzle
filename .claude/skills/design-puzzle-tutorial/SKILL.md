# design-puzzle-tutorial

`/design-puzzle-tutorial <game>`

パズルを知らないプレイヤーが、本物の小さな盤面を1枚解きながらルールとゲームでの操作を身につけ、そのゲームを遊びたくなるチュートリアルを作る・改める・見直す。

- `<game>`（`$ARGUMENTS`）: 対象のゲームの、`frontend/src/games/` のディレクトリ名
- 本物の盤面: 本番と同じルールと盤面部品で作った盤面。マスを確定させていくパズルでは完成形が1つに決まり、手を重ねて状態を進めるパズルでは完成に届く。大きさは本番と違ってよい
- ゲームの実装規則: `.claude/rules/game-*.md`（`game-md.md` を除く）

## 決まりの重さ

- 必ず守る: 「大原則」と「動作フロー」。大原則を1つでも破っているか、動作フローを飛ばしていれば、作業は終わっていない。
- 迷ったらこうする: 「基本の形」。パズルに合わなければ、大原則を守る範囲で変えてよい。ただし、`AGENTS.md` が読むよう求める文書と、動作フローで読む文書で決まっている所は変えない。
- 書いていないこと: 見た目・言い回し・演出・ステップの数などのうち、それらの文書で決まっていないものは、作った本人が大原則に照らして決める。案を並べて PO に選ばせない。

## 大原則

- P1. 本物の盤面を1枚、プレイヤー自身の手で解いて完成させる。
- P2. 何をするパズルかとゴールを、操作より先に見せる。
- P3. ルールは1つずつ伝えてすぐ盤面で使わせ、伝えていないルールが要る手を求めない。
- P4. 言葉は、盤面と操作で伝わらないことだけにする。
- P5. 手の正誤への盤面の反応は、伝えたことと食い違わない。
- P6. 375px 幅でも、動きを減らす設定でも、伝えることが欠けたり崩れたりしない。
- P7. チュートリアルだけの助けや例外を、本番にもあるように言わない。

## 基本の形

- 入口: ゲームの名前、何をするパズルかの一文、ゴールの盤面、始まりの盤面を見せる。ゴールは、これから解く1枚の完成形にする。読む速さに合わせて「次へ」で進める。
- 手を引く: 最初に操作を教え、次のステップからはルールを1つ伝えては、そのルールで決まる手を打たせる。
  - 打つ所に印を付け、印の所の操作だけを受け付ける。印の無い所への操作は盤面を変えず、印へ目を向けさせる。正しい手には盤面の合図で応える。
  - 教える操作は、この盤面を解き切るのに要るものまでにする。取り消し方や長押しなど、解くのに要らない操作は、遊び方の説明と本番に任せる。
- 手を離す: 盤面の手を決めるルールをすべて伝えたら、一言で残りを任せ、自分で解かせる。盤面の反応は本番と同じにし、ほかに一言を出すのは、ルールに合わない手を打ったときと、止まって手がかりを出すときだけにする。手がかりは、次に打てる所に印を付けて示す。
- 本番との境: 本番に何を出すかは `GAME.md` の「目指すゲーム」と「判断の優先順位」に従い、チュートリアルの印・合図・一言・手がかりを本番へ持ち込まない。
- 完成: 本番と同じクリア演出を見せ、本番へつなぐ。見せ方とつなぎ方は、ゲームの実装規則の「チュートリアル」節に従う。

## 動作フロー

始め方:

- 新しく作る: 1から進める。
- 既存のチュートリアルを改める: 1を行い、今の盤面が2-3の条件を満たすかを確かめる。満たさなければ2から作り直す。満たせば、今の盤面で2-2の表を作り、2-3の条件のうちテストに無いものを足してから2-4を行い、3へ進む。どちらの場合も、`frontend/src/games/<game>/tutorial/` を最後に変えた PR の本文の表から、`【PO】`（PO が決めた言い回しの印）の付いた一言を新しい表へ引き継ぐ。
- 改めずに見直した結果だけを求められた: 6の「作る側」と「遊ぶ側」だけを行い、結果を報告する。PR は開かない。

1. パズルを知る: `docs/プロダクト/仕様/パズル/` の該当パズルの仕様、`frontend/src/games/<game>/ui/<Game>HowToPlayDialog.tsx`、`frontend/src/games/<game>/puzzle/` を読み、ルールを書き出す。開発サーバーでレベル1と2を1問ずつ解き、ゲームでの操作を確かめる。
2. 盤面とステップを決める:
   1. 2-3の条件を満たす小さめの盤面を、`puzzle/` のルールを使う一時的なスクリプトで総当たりして探し、1枚選ぶ。
   2. 盤面とステップの表を `assets/step-table.md` の形で作る。
   3. 選んだ盤面について、次の条件を `frontend/src/games/<game>/tutorial/` のテストに残す。
      - 手を引く間: 操作を教える手はゴールの盤面と一致し、ルールを伝えた後の各手は、それまでに伝えたルールで決まる。手を引く間のどの盤面も（1手が複数の操作から成るときはその途中も）、まだ伝えていないルールに反しない。1で書き出したルールのそれぞれが、1つ以上の手を決める。
      - 手を離した後: マスを確定させていくパズルでは、伝えたルールを当てはめるだけで残りが解き切れる。手を重ねて状態を進めるパズルでは、どう進めても手詰まりにならない。そういう盤面が作れないパズルでは、手詰まりから戻る操作（待ったや盤面を戻すなど）を、解くのに要る操作として手を引く間に教える。
   4. `commit-pr` スキルを起動してテストをコミットし、PR を開く。PR 本文に2-2の表を載せる。
3. 実装する: ゲームの実装規則の「チュートリアル」節と「依存方向」節を読み、そこに書かれた置き場所・共通の進行・画面・部品・つなぎ先で作る。入口でゴールの盤面から始まりの盤面へ替えるとき、盤面の動きで場面を見せないゲームでは `frontend/src/components/TutorialCrossFadeIntroScene.tsx` を使う。
4. 言葉を整える: `references/review-requests.md` の「編集者役」の依頼で、新しいサブエージェントに PR 本文の表の文字を見直させる。挙がった所を、出る場面・改行位置と合わせて画面で直し、PR 本文の表も同じに揃える。
5. 自分で通す: `AGENTS.md` の全品質検証を通す。`docs/開発/画面レビュー手順.md` に従い、通常の設定・375px 幅・動きを減らす設定のそれぞれで入口から完成まで自分で操作し、スクリーンショットで確かめる。
6. 見直す: `references/review-requests.md` の「作る側」と「遊ぶ側」の依頼で、新しいサブエージェント2つに並行して見直させる。
   - 大原則の違反と不具合は直す。同じ原因の所がほかにないか探し、まとめて直す。
   - 遊ぶ側が迷った・止まったと書いた所は、どの大原則に反しているか原因を探して直す。言葉に引っかかった所は、同じ種類の言葉が他にも残っているとみて、4でまとめて直す。
   - それ以外は、直す価値があるものだけ直す。
7. PO に見せる: 確認を頼むときに、自分で決めたことと、直さなかった指摘を、判断を求めずに短く添える。

進め直し:

- 6で直したら、5までを進め直す。言葉を変えたときは4から、それ以外は5から始める。大原則の違反か不具合を直したときだけ、そのあともう一度6を行う。
- 6は最初を含めて2回までにする。2回目で出た大原則の違反と不具合は直して自分で確かめ、7へ進む。

PO から指摘を受けたとき:

- 大原則に反している指摘は、反している大原則を特定し、6と同じように直して進め直す。6の回数は0に戻す。
- どの大原則にも当たらない指摘は、そのチュートリアルだけを直し、6と同じように進め直す。このスキルには足さない。PO が言い回しを決めたときは、表のその一言に `assets/step-table.md` の書き方で印を付ける。
- 大原則を見直したほうがよいと考えたときは、`AGENTS.md` の進め方に従って、大原則を直す案と直さない案を PO に出す。
