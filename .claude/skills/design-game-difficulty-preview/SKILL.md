# design-game-difficulty-preview

`/design-game-difficulty-preview <ゲーム ID> [新規 | 見直し | 追従 | レビュー] [指摘]`

難易度選択に出す、各レベルの挑戦の差を比べるためのゲーム固有の小さな図（難易度プレビュー）を作る、見直す、難易度の変更に追従させる。プレビューはパズル追加の人間レビューで最も作り直しが多い領域で、失敗はいつも同じ型（実問題を縮小する、軸でない違いで差を作る、描き込みすぎ・答えを描く、既存の意図を読まずに置き換える）に落ちる。この Skill は、それを人間に見せる前に落とし、候補を実寸で既存ゲームと並べて判断できるようにするためにある。

## 守ること

1. **決まりは正本にある。** 難易度選択で何を見せ、何を見せないかは下の「参照する正本と読む時」の文書を正とし、この Skill に写さない。この Skill が持つのは作り方の手順・検査・比較画像の型・実例だけ。正本と食い違ったら正本に従い、食い違いを報告する。
2. **実際の問題ではなく、挑戦を描く。** 図は手で作り、そのゲームの挑戦の差を描く。問題集の盤面や代表問題を縮小しない。
3. **差は挑戦の軸の量だけで作る。** レベル間で変える量は、問題集で測って差がある軸の量に限る。それ以外は全レベルで同じにする。
4. **安く広く探してから作る。** 案は一文とレベルごとの記法で広げ、実装は絞った案だけにする。
5. **判断は実寸の画像で行う。** 本物の選択肢の枠に入れ、スマホ幅で、既存ゲームと並べて見る。コードや記法だけで良し悪しを決めない。
6. **既存の図は意図を読んでから変える。** 見直しでは、今の図が描いている挑戦と、人間が決めたことを先に書き出す。
7. **方向は人間が決める。** AI は弱い案を落とし、候補の完成度をそろえ、推奨を示すところまで。`/add-puzzle` から起動されたときだけ、推奨を仮採用して進める。
8. **確かめていないことを確認済みと書かない。** AI の目や確認者の読み方は人間の判断の代わりにならない。

## 依頼別の入口

| 入口 | 起動のされ方 | 進め方 |
|---|---|---|
| 新規 | 人間から、新しいゲームの難易度選択を作るとき | 流れ 1〜8。流れ 6 で人間の選択を待つ |
| 新規（`/add-puzzle` から） | 実装役が difficulty-select の項目で起動する | 流れ 1〜8。流れ 6 で待たずに推奨を仮採用し、別案は画像と一文で報告する（「出力」）。サブエージェントを起動しない（入れ子にできない）。読まれ方の確かめは報告に「頼むこと」として書く |
| 見直し | 人間の指摘や、既存ゲームのプレビューを良くしたいとき | 流れ 0 で意図を読み、`references/checks.md` を今の図に当てて何が悪いかを書いてから、流れ 1 に戻って変わる所だけやり直す。人間が決めた形を覆す案は、今の形と並べて人間に選ばせる |
| 追従 | 難易度の組み合わせ定義・問題集・盤面サイズの割り当てが変わったとき（`/design-game-difficulty` の波及を含む） | 下の「割り当てが変わったときの追従」 |
| レビュー | 図を変えずに確かめてほしいとき | 流れ 0 と流れ 8 だけ。対象を変更せず、検査の結果と比較画像を返す |

## 参照する正本と読む時

着手時に読む。読む前に方針を決めない。節番号は版で変わるので見出しで探す。

- `DESIGN.md`:
  - 「画面ごとの優先順位」の「難易度選択」: 何を比べさせ、何を見せないか、枠をゲーム間でそろえること。流れ 1 の前に読み、流れ 4・8 で読み返す。
  - 「余白と密度」（難易度を選ぶ画面）、「ゲームを表す視覚表現」、「色」の「ゲーム固有色」、「レスポンシブ設計」、「避ける表現」: 流れ 3〜5 と流れ 8 で読む。
- `frontend/styles/globals.css` の `@theme`: 色・余白の値。図の色と余白を決めるとき（流れ 5・7）。
- `GAME.md`（盤面で分からせる、内部のデータ構造をそのまま描かない）と `APP.md`（見せる情報）: 流れ 1・2 で読む。
- `docs/プロダクト/要件/NFR-007.md`・`NFR-008.md`（難易度の差は挑戦の差から生じ、規模だけで作らない）と `docs/パズル/難易度提供.md` の「共通レベルとゲーム固有の体験説明を分ける」: 流れ 1 で読む。
- `docs/プロダクト/仕様/ゲーム/SPEC-004.md`（推奨・初期選択を作らない）・`SPEC-005.md`（5段階）: 流れ 3 の前に読む。
- そのゲームの SPEC（`docs/プロダクト/仕様/パズル/SPEC-nnn.md`）の難易度の節、`frontend/src/games/<game>/difficulty.ts` の組み合わせ定義、導入調査（`docs/パズル/導入調査/<パズル名>/`）の難易度の資料: 流れ 1 で読む。
- `frontend/src/components/DifficultyOption.tsx`: 見本の枠（幅と行の高さ）。寸法は写さず、流れ 3・5 で毎回読む。
- `.claude/rules/game-structure.md`、`.claude/rules/typescript.md`（`_private`）、`.claude/rules/vitest.md`: 流れ 7 で読む。
- 決まりを変えたくなったときは `docs/adr/index.csv` で理由を確かめる。

## 補助ファイル

- `references/examples.md`: 既存プレビューの表（何を挑戦の差として描き、何を描かないか）、収束した共通の構造、覆された経緯。流れ 0・1・3 の前に読む。
- `references/checks.md`: 失敗の型と検査の手順。流れ 4・5・8 と、見直し・レビューで全行を当てる。
- `references/review-sheet.md`: 一時的な比較の画面、撮り方、比較画像の型、添える文。流れ 5・6・8 で使う。

## 流れ

### 0. 今の図の意図を読む（見直し・追従・レビュー）

今の `<Game>DifficultyPreview.tsx` の定数の上のコメント、テストの各項目、`git log --format='%h %ad %s%n%b' -- <ファイル>` のコミット本文、導入調査の「難易度プレビュー」の記録を読み、次の「意図のメモ」を書く。

- 描いている挑戦（利用者向けの一言）と、それを表す量
- レベル間の関係（入れ子・単調・レベルごとの局面など）と、テストが固定しているもの
- 描かないと決めているもの
- 人間が決めたこと（導入調査の「人間の判断」や最終レビューの指摘から）

意図のメモは以後の検査（`references/checks.md` の「意図を読まずに置き換える」）の基準になる。

### 1. 挑戦の表を作る

そのゲームの難易度の組み合わせ定義のつまみごとに1行を書く。

| つまみ | 利用者向けの一言 | レベル1〜5の値（問題集の中央値と範囲） | 隣接レベルで差があるか | 図で表せるか |
|---|---|---|---|---|

- 値は問題集で測る。`/design-game-difficulty` から渡された「プレビューが写す量」があればそれを使い、無ければそのゲームの分析コードと問題集から測る（一度だけ測る一時スクリプトは使ってよいが、繰り返し使う量はテストでの照合に移す）。
- 「図で表せるか」は、見本の枠の中で、プレイ画面と同じ姿の要素の数・長さ・幅・密度などとして読めるかで判断する。
- 差があり、図で表せ、盤面を見て分かるつまみを1〜2個選び、「描く軸」とする。規模（盤面の大きさ）は、それが難易度のつまみのときだけ候補にする。
- 描く軸に選ばなかった量は、全レベルで同じにすると決める。

### 2. 描かない物のリストを作る

案を作る前に、このゲームで描かない物を具体的に書き出す。`references/examples.md` の「描かないもの」の列を手がかりにする。

- 答え（決まるマスの中身、正解の配置、解いた後の姿）
- 挑戦に関わらない数字・記号・格子・ヒントの欄
- 説明文、レベルの帯とラベル以外の文字
- 生成の情報・内部の特徴量
- 描く軸を表すのに要らない色（盤面の地のほかに2色程度まで）

### 3. 案を広げる

一案を「一文（何を見せ、上のレベルで何が増える・減るか）」と「レベル1〜5の配置の記法（既存プレビューの定数と同じく文字の格子や表で書く）」で表す。10案前後を目安に、次の軸を振って方向の幅を出す。同じ発想の微差を数えない。

- 切り出し方: 数行の帯、盤面の隅、局面に関わる行だけ、全体
- 量の見せ方: 要素の数、線の長さ・折れる回数、密度、幅、レベルごとの局面
- レベル間の関係: 足していく入れ子、減らしていく入れ子、レベルごとに違う局面
- 描き方: 本番の描画部品をそのまま使う、本番の部品に線などを1つ重ねる

記法の段階で、見本の枠に収めたときのマスの大きさを計算して添える。

### 4. 絞る

`references/checks.md` の全行を記法と一文に当て、当たる案を落とす。特に、マスの大きさが既存のプレビューより明らかに小さい案、軸でない量がレベル間で変わる案、答えを描く案を落とす。異なる方向の2〜4案を残し、一案だけにしない。

### 5. 候補を作り、実寸で並べる

- 残した案ごとに、本番の描画部品と定数で図を実装する。粗い案と仕上げた案を同じ比較に混ぜないよう、どの候補も「枠に収まる」「マスの大きさが全レベルで同じ」「描かない物のリストを守る」までそろえる。
- `references/review-sheet.md` の型で、一時的な比較の画面に候補と既存ゲーム2つ以上を並べて撮る。
- 撮った画像に `references/checks.md` を当て、当たった候補は直すか落とす。
- 読まれ方を確かめる（`references/checks.md` の「読まれ方の確かめ」）。サブエージェントを起動できない立場では行わず、報告の「頼むこと」に入れる。

### 6. 方向を決める

- 単独で起動されたとき: 比較画像と、候補ごとの添える文（`references/review-sheet.md`）を示し、推奨と理由を添えて、人間に方向を選んでもらう。候補の部分の組み合わせも受ける。人間が明示的に任せた場合を除き、選択を待つ。
- `/add-puzzle` から起動されたとき: 待たない。推奨案を仮採用して流れ 7 に進む。別案は画像と添える文を報告に入れ、配置の記法と一文を導入調査の実装前提調査（仮決定一覧の難易度プレビューの行の「比べた案」）に残し、選ばれたら作り直せるようにする。

### 7. 仕上げる

- 採らなかった候補のコードと、一時的な比較の画面を消す。
- 図の定数の上に、実際の問題ではないこと、描く挑戦と量の出所、レベル間の関係、描かないものをコメントで書く（`references/examples.md` の各ファイルに倣う）。次に見直す人が意図を読む手がかりになる。
- テストで次を固定する。定数は `_private` で公開する。
  - 描く軸の量が、難易度の組み合わせ定義の範囲に入るか、問題集の値（中央値など）と一致する。定義から直接読めるものは読む。
  - レベル間の関係（入れ子なら包含、単調なら隣接レベルで下がらない）と、描く軸以外の量が全レベルで同じであること。
  - 図がルール上成り立つこと（可解、解法器で示したマスがちょうど決まる、など）が問えるゲームでは、それ。
  - 描かない物（数字・文字が無い、`aria-hidden`）。
- 決めた理由と比べた案は、導入調査の文書に残す（`docs/README.md` の資料の扱いに従う）。全ゲームに効く判断で理由が要るものは、起動側か人間に ADR を提案する。

### 8. 最終検査

- `references/checks.md` の全行を仕上げた図に当てる。
- `bun run --cwd frontend check`、`typecheck`、`test`（プレビューのテストを含む）を通す。
- `references/review-sheet.md` の型で、推奨案（仕上げた図）を既存ゲームと並べて撮り直し、`browser-errors.log` にエラーが無いことを確かめる。

## 割り当てが変わったときの追従

1. 流れ 0 の意図のメモを書き、プレビューのテストを流す。定義や問題集と照合しているテストが落ちれば、そこが追う量。
2. 変わったのが量だけ（範囲や中央値）なら、定数を新しい値に合わせ、流れ 7・8 を行う。照合するテストが無く手で決めていた量は、このときテストを足す。
3. つまみが増えた・減った・意味が変わったなら、見直しとして流れ 1 からやり直す。
4. 新しい割り当てが図で表せない（最上位の盤面が枠に収まらないなど）ときは、図を潰して押し込まない。プレビューの都合で割り当てを変えた前例（スライドパズル）はあるが、割り当ては難易度の側で決めるので、理由と案を起動側か人間に返す。
5. 何を追い、何を変えなかったかを報告に書く。

## 出力

| 入口 | 出すもの |
|---|---|
| 新規 | `frontend/src/games/<game>/ui/<Game>DifficultyPreview.tsx` とテスト、難易度選択の View への組み込み、比較画像、挑戦の表と描かない物のリスト、決めたことの記録 |
| 新規（`/add-puzzle` から） | 上と同じもの。比較画像には仮採用した推奨案と別案を並べる。起動側への報告: 推奨案と理由、別案ごとの添える文と画像のパス、挑戦の表の要点、検査の結果（型ごとに当たり・直したこと・残したこと）、頼むこと（読まれ方の確かめ・iOS 実機で見てほしい点）、確かめていないこと |
| 見直し | 意図のメモ、今の図の検査の結果、候補と今の図を並べた比較画像。人間が選んだら、上の新規と同じもの |
| 追従 | 定数とテストの差分、撮り直した画像、追ったもの・変えなかったものの一覧 |
| レビュー | 意図のメモ、検査の結果、比較画像（変更なし） |

## 制約

- `DESIGN.md`・`APP.md`・`GAME.md`・仕様・難易度文書をこの Skill の中で書き換えない。直すべきと分かったら、理由を添えて報告に「人間に残す」として書く。
- 問題集を読む処理・問題を選ぶ処理をプレビューの実装に置かない（テストで照合するのはよい）。
- 共通部品 `DifficultyOption` の枠を、1ゲームの都合で変えない。
- 撮影のためのスクリプトを作らない。撮影は `playtest-driver.mjs` か、その場の Playwright で行う。
- 一時的な比較の画面と採らなかった候補をコミットしない。
- 難易度の組み合わせ定義と問題集はこの Skill の中で変えない（`/design-game-difficulty` が持つ）。
