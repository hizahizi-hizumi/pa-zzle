# design-game-difficulty-preview

`/design-game-difficulty-preview <ゲーム ID> [新規 | 見直し | 追従 | レビュー] [指摘]`

難易度選択に出す、各レベルの挑戦の差を比べるためのゲーム固有の小さな図（難易度プレビュー）を作る、見直す、難易度の変更に追従させる。プレビューはパズル追加の人間レビューで最も作り直しが多い領域で、失敗はいつも同じ型（実問題を縮小する、軸でない違いで差を作る、描き込みすぎ・答えを描く、既存の意図を読まずに置き換える）に落ちる。この Skill は、それを人間に見せる前に落とし、候補を実寸で既存ゲームと並べて判断できるようにするためにある。

## 守ること

1. **決まりは正本にある。** 難易度選択で何を比べさせ、何を見せないか、入れ子にするかは下の「参照する正本と読む時」の文書を正とし、この Skill に写さない。この Skill が持つのは作り方の手順・検査・比較画像の型・実例だけ。正本と食い違ったら正本に従い、食い違いを報告する。
2. **実際の問題ではなく、挑戦を描く。** 図はレベルごとの定数で手で作る。問題集の盤面や代表問題を縮小せず、問題集を読む処理・問題を選ぶ処理をプレビューの実装に置かない（問題集の値はテストで照合するだけにする）。この Skill の中でこの点に触れる所は、すべてここを指す。
3. **差は DESIGN.md「難易度選択」に従って作る。** この Skill では、図でレベルごとに変える量を、問題集で測ってレベル間に差がある挑戦の量に結び付ける（流れ 1）。
4. **安く広く探してから作る。** 案は一文とレベルごとの記法で広げ、実装は絞った案だけにする。
5. **判断は実寸の画像で行う。** 本物の選択肢の枠に入れ、スマホ幅で、既存ゲームと並べて見る（`references/review-sheet.md`）。コードや記法だけで良し悪しを決めない。
6. **既存の図は意図を読んでから変える。** 見直しでは、今の図が描いている挑戦と、人間が決めたことを先に書き出す（流れ 0）。
7. **方向は人間が決める。** AI は弱い案を落とし、候補の完成度をそろえ、推奨を示すところまで。`/add-puzzle` から起動されたときだけ、推奨を仮採用して進める。
8. **確かめていないことを確認済みと書かない。** AI の目や確認者の読み方は人間の判断の代わりにならない。

## 依頼別の入口

| 入口 | 起動のされ方 | 進め方 |
|---|---|---|
| 新規 | 人間から、新しいゲームの難易度選択を作るとき | 流れ 1〜8。流れ 6 で人間の選択を待つ |
| 新規（`/add-puzzle` から） | 実装役が difficulty-select の項目で起動し、作業ディレクトリと報告ファイルのパスを渡す | 流れ 1〜8。前提（盤面の大きさの扱いなど）は brief の合意節の写しに従う。流れ 6 で待たずに推奨を仮採用する。サブエージェントを起動しない（入れ子にできない）。報告は「出力」の報告ファイルに書く |
| 見直し | 人間の指摘や、既存ゲームのプレビューを良くしたいとき | 流れ 0 で意図を読み、`references/pitfalls.md` を今の図に当てて何が悪いかを書いてから、流れ 1 に戻って変わる所だけやり直す。人間が決めた形を覆す案は、今の形と並べて人間に選ばせる |
| 追従 | 難易度の再設計・再校正の後に、`/design-game-difficulty` が `/design-game-difficulty-preview <game> 追従` で起動する（人間から頼まれてもよい） | 下の「割り当てが変わったときの追従」 |
| レビュー | 図を変えずに確かめてほしいとき | 流れ 0 と流れ 8 だけ。対象を変更せず、検査の結果と比較画像を返す |

## 参照する正本と読む時

着手時に読む。読む前に方針を決めない。節番号は版で変わるので見出しで探す。

- `DESIGN.md`:
  - 「画面ごとの優先順位」の「難易度選択」: 何を比べさせ、何を見せないか、レベル間の構成、枠をゲーム間でそろえること。流れ 1 の前に読み、流れ 2・4・8 で読み返す。
  - 「余白と密度」（難易度を選ぶ画面）、「ゲームを表す視覚表現」、「色」の「ゲーム固有色」、「レスポンシブ設計」、「避ける表現」: 流れ 3〜5 と流れ 8 で読む。
- `frontend/styles/globals.css` の `@theme`: 色・余白の値。図の色と余白を決めるとき（流れ 5・7）。
- `GAME.md`（盤面で分からせる、内部のデータ構造をそのまま描かない）と `APP.md`（見せる情報）: 流れ 1・2 で読む。
- 流れ 1 で読む要件と難易度文書:
  - `docs/プロダクト/要件/NFR-007.md`: 高い難易度ほどそのパズル固有の挑戦が強く、隣接する難易度の間で順序が逆転しない。
  - `docs/プロダクト/要件/NFR-008.md`: 難易度の差は挑戦の差から生じ、作業量・規模・視認の負担だけで作らない。
  - `docs/パズル/難易度提供.md` の「共通レベルとゲーム固有の体験説明を分ける」。
- `docs/プロダクト/仕様/ゲーム/SPEC-004.md`（推奨・初期選択を作らない）・`SPEC-005.md`（5段階）: 流れ 3 の前に読む。
- そのゲームの SPEC（`docs/プロダクト/仕様/パズル/SPEC-nnn.md`）の難易度の節、`frontend/src/games/<game>/difficulty.ts` の組み合わせ定義、難易度の資料（`docs/パズル/導入調査/<パズル名>/<パズル名>難易度.md`）の「下流に渡す量」の節: 流れ 1 で読む。`/add-puzzle` からは brief の合意節の写しも読む。
- `frontend/src/components/DifficultyOption.tsx`: 見本の枠（幅と行の高さ）。寸法は写さず、流れ 3・5 で毎回読む。
- `.claude/rules/game-structure.md`、`.claude/rules/typescript.md`（`_private`）、`.claude/rules/vitest.md`: 流れ 7 で読む。
- 決まりを変えたくなったときは `docs/adr/index.csv` で理由を確かめる。

## 補助ファイル

- `references/examples.md`: 既存プレビューの表（何を挑戦の差として描き、何を描かないか）、作り直しを経て残った形、覆された経緯。流れ 0・1・3 の前に読む。
- `references/pitfalls.md`: 失敗の型の表。流れ 4・5・8 と、見直し・レビューで全行を当てる。
- `references/checks.md`: 失敗の型を確かめる手順（量の書き出し、描かない物、意図のメモ、入れ子、色の数、スマホ幅、読まれ方）。
- `references/review-sheet.md`: 一時的な比較の画面、撮り方、比較画像の型、添える文。流れ 5・6・8 で使う。

## 一時的な変更の置き場所と後始末

案の比較と一度だけの計測のために、次の2つだけを一時的に作ってよい。

- 比較の画面: `frontend/src/views/<Game>DifficultyView.tsx` の書き換えと、候補ごとの一時的なプレビューのコンポーネント（中身は `references/review-sheet.md` の「一時的な比較の画面」）。
- 一時スクリプト: worktree の `frontend/scripts/tmp-<目的>.ts`。問題集の量を一度だけ測るときに使い、繰り返し使う量はテストでの照合に移す。

後始末: 流れ 7 の最初と、作業を途中でやめるときに、これらをすべて消す。コミットしない。消したら `git -C <worktree> status` で一時的なファイルと書き換えが残っていないことを確かめる。撮影のためのスクリプトは作らない。

## 流れ

### 0. 今の図の意図を読む（見直し・追従・レビュー）

今の `<Game>DifficultyPreview.tsx` の定数の上のコメント（無いものもある）、テストの各項目、`git -C <root> log --format='%h %ad %s%n%b' -- <ファイル>` のコミット本文、導入調査の「難易度プレビュー」の記録を読み、次の「意図のメモ」を書く。

- 描いている挑戦（利用者向けの一言）と、それを表す量
- レベル間の関係（入れ子・単調・レベルごとの局面など）と、テストが固定しているもの
- 描かないと決めているもの
- 人間が決めたこと（導入調査の「人間の判断」や最終レビューの指摘から）

意図のメモは以後の検査（`references/pitfalls.md` の「既存プレビューの意図を読まずに置き換える」）の基準になる。

### 1. 挑戦の表を作る

難易度の資料の「下流に渡す量」の節を読み、つまみごとに1行を書く。

| つまみ | 利用者向けの一言 | レベル1〜5の値（10/50/90 パーセンタイルと最小〜最大） | 隣接レベルで差があるか | 図で表せるか |
|---|---|---|---|---|

- 値は「下流に渡す量」の節から写し、出したコードの場所を添える。節が無い（既存ゲームなど）ときは、そのゲームの分析コードと問題集から同じ形で測る（一時スクリプトは「一時的な変更の置き場所と後始末」）。
- 「図で表せるか」は、見本の枠の中で、プレイ画面と同じ姿の要素の数・長さ・幅・密度などとして読めるかで判断する。
- 差があり、図で表せ、盤面を見て分かるつまみを1〜2個選び、「描く軸」とする。規模（盤面の大きさ）は、それが難易度のつまみのときだけ候補にする。
- 描く軸に選ばなかった量は、全レベルで同じにすると決める。

### 2. 描かない物のリストを作る

案を作る前に、このゲームで描かない物を具体的に書き出す。`references/examples.md` の「描かないもの」の列を手がかりにする。

- 答え（決まるマスの中身、正解の配置、解いた後の姿）
- 挑戦に関わらない数字・記号・格子・ヒントの欄
- 説明文、レベルの帯とラベル以外の文字
- DESIGN.md「難易度選択」が表示しないとしているもの
- 描く軸を表すのに要らない色（`references/checks.md` の「色の数」）

### 3. 案を広げる

一案を「一文（何を見せ、上のレベルで何が増える・減るか）」と「レベル1〜5の配置の記法（既存プレビューの定数と同じく文字の格子や表で書く）」で表す。10案前後を目安に、次の軸を振って方向の幅を出す。同じ発想の微差を数えない。

- 切り出し方: 数行の帯、盤面の隅、局面に関わる行だけ、全体
- 量の見せ方: 要素の数、線の長さ・折れる回数、密度、幅、レベルごとの局面
- レベル間の関係: 足していく入れ子、減らしていく入れ子、レベルごとに違う局面（DESIGN.md「難易度選択」が求める構成の範囲で振る）
- 描き方: 本番の描画部品をそのまま使う、本番の部品に線などを1つ重ねる

記法の段階で、見本の枠に収めたときのマスの大きさを計算して添える。

### 4. 絞る

`references/pitfalls.md` の全行を記法と一文に当て、当たる案を落とす。特に、マスの大きさが既存のプレビューより明らかに小さい案、軸でない量がレベル間で変わる案、答えを描く案を落とす。異なる方向の2〜4案を残し、一案だけにしない。

### 5. 候補を作り、実寸で並べる

- 残した案ごとに、本番の描画部品と定数で図を実装する。粗い案と仕上げた案を同じ比較に混ぜないよう、どの候補も「枠に収まる」「マスの大きさが全レベルで同じ」「描かない物のリストを守る」までそろえる。
- `references/review-sheet.md` の型で撮る。
- 撮った画像に `references/pitfalls.md` を当て、当たった候補は直すか落とす。
- 読まれ方を確かめる（誰がどう行うかは `references/checks.md` の「読まれ方の確かめ」）。

### 6. 方向を決める

- 単独で起動されたとき: 比較画像と、候補ごとの添える文（`references/review-sheet.md`）を示し、推奨と理由を添えて、人間に方向を選んでもらう。候補の部分の組み合わせも受ける。人間が明示的に任せた場合を除き、選択を待つ。
- `/add-puzzle` から起動されたとき: 待たない。推奨案を仮採用して流れ 7 に進む。別案は配置の記法・添える文・画像を報告ファイルに入れるだけにする（実装前提調査の仮決定一覧にはメインが書く）。

### 7. 仕上げる

- 「一時的な変更の置き場所と後始末」に従って、採らなかった候補と一時的な変更を消す。
- 図の定数の上に、守ること 2 の図であること、描く挑戦と量の出所、レベル間の関係、描かないものをコメントで書く（`references/examples.md` の各ファイルに倣う）。次に見直す人が意図を読む手がかりになる。
- テストで次を固定する。定数は `_private` で公開する。
  - 描く軸の量が、難易度の組み合わせ定義の範囲に入るか、問題集の値（「下流に渡す量」の中央値など）と一致する。定義から直接読めるものは読む。
  - レベル間の関係（入れ子なら包含、単調なら隣接レベルで下がらない）と、描く軸以外の量が全レベルで同じであること。
  - 図がルール上成り立つこと（可解、解法器で示したマスがちょうど決まる、など）が問えるゲームでは、それ。
  - 描かない物のリストにある物（ヒントの数字・文字など）が図に無いことと、`aria-hidden`。
- 決めた理由と比べた案を残す。単独の起動では導入調査の文書に書く（`docs/README.md` の資料の扱いに従う）。`/add-puzzle` からは報告ファイルに書き、文書へはメインが書く。全ゲームに効く判断で理由が要るものは、起動側か人間に ADR を提案する。

### 8. 最終検査

- `references/pitfalls.md` の全行を仕上げた図に当てる。
- `bun run --cwd frontend check`、`typecheck`、`test`（プレビューのテストを含む）を通す。
- `references/review-sheet.md` の型で、推奨案（仕上げた図）を撮り直し、`browser-errors.log` にエラーが無いことを確かめる。
- 一時的な変更が残っていないことを `git -C <worktree> status` で確かめる。

## 割り当てが変わったときの追従

`/design-game-difficulty` が再設計・再校正の後に起動する前提で書く。入力は、更新された難易度の資料の「下流に渡す量」の節と、変わったつまみ・境界の説明。

1. 流れ 0 の意図のメモを書き、プレビューのテストを流す。定義や問題集と照合しているテストが落ちれば、そこが追う量。
2. 変わったのが量だけ（範囲やパーセンタイル）なら、定数を新しい値に合わせ、流れ 7・8 を行う。照合するテストが無く手で決めていた量は、このときテストを足す。
3. つまみが増えた・減った・意味が変わったなら、見直しとして流れ 1 からやり直す。
4. 新しい割り当てが図で表せない（最上位の盤面が枠に収まらないなど）ときは、図を潰して押し込まない。プレビューの都合で割り当てを変えた前例（スライドパズル）はあるが、割り当ては難易度の側で決めるので、理由と案を起動側に返す。
5. 何を追い、何を変えなかったかを報告に書く。

## 制約

- `DESIGN.md`・`APP.md`・`GAME.md`・仕様・難易度文書をこの Skill の中で書き換えない。直すべきと分かったら、理由を添えて報告に「人間に残す」として書く。
- 共通部品 `DifficultyOption` の枠を、1ゲームの都合で変えない。
- 難易度の組み合わせ定義と問題集はこの Skill の中で変えない（`/design-game-difficulty` が持つ）。
