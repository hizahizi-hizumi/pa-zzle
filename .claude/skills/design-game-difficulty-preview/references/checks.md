# 検査の手順

`pitfalls.md` の各行を確かめる手順。どの行がどの手順を使うかは `pitfalls.md` の「検査」の列。

## 量の書き出し（軸でない違い・逆転）

1. 図の定数を読み、レベルごとに「描かれている量」を表にする（要素の数、列数・行数、線の長さや折れる回数、色ごとの要素の数、空き・未開示の数など）。
2. 各量について、隣接レベルで変わるか、変わるならどの挑戦の軸に対応するかを書く。
3. 対応する軸の値を、挑戦の表（`SKILL.md` 流れ 1）のレベルごとの値と並べる。
4. 軸に対応しない量が変わっていれば、全レベルで同じにする。軸に対応する量は、テストで定義・問題集と照合する。

## 描かない物の突き合わせ（描き込みすぎ・答え）

1. 流れ 2 のリストの各項目を、図の DOM と画像で探す（数字・文字は `textContent`、色は使っているクラス）。
2. 決まるマスについて、その中身（塗り・数字・タイル）が描かれていないかを見る。
3. 図の中と選択肢に、説明の文字が無いことを確かめる（盤面の数字など、描く軸としてゲームの姿のまま描くものは除く）。

## 色の数（経験則）

正本の決まりではなく、レビューで覆った経験からの目安。盤面の地と格子の色を除き、図の色は2色程度までにする。

根拠: リフレクションの最初の図（光路をレベルの数だけ、ピース4種、外周ヒントの数字・記号）は人間のレビューで「賑やかすぎる」と覆り、光路とピースの2色で決着した（`examples.md` の「覆された経緯」）。超えるときは、超える色が描く軸を表すのに要る理由を報告に書く。

## 意図のメモとの突き合わせ（意図を読まずに置き換える）

1. `SKILL.md` 流れ 0 の意図のメモの各行（描いている挑戦、レベル間の関係、描かないもの、人間が決めたこと）について、新しい図でどうなったかを書く。
2. テストが固定していた関係は、残すか、覆す理由を報告と記録に書く。
3. 「捨てた」行があれば、理由と、捨てない別案の画像を報告に入れる。

## 入れ子

入れ子にするかどうかは DESIGN.md「難易度選択」に従う。

1. DESIGN.md「難易度選択」を読み、レベル間の構成（上位が下位を含むかなど）を求めているかを確かめる。
2. 求めていれば、図が入れ子か（上のレベルが下のレベルの要素を同じ位置に含むか）を定数で確かめ、テストで包含を固定する。
3. 求めているのに入れ子にできない（難易度の定義が積み上がらないなど）ときは、正本との食い違いとして理由を添えて報告に書く。自分で入れ子をやめると決めない。

## スマホ幅での見え方

1. 記法の段階（流れ 3・4）では、スマホの枠に収めたときのマスの大きさを計算し、既存のプレビューのマスの大きさ（各ファイルのクラスと変数）と比べる。
2. 候補と仕上げた図は `review-sheet.md` の型で撮る。行の高さと見本の幅は幅によらず同じなので、マスの大きさは iphone の画像で決まる。
3. 拡大の画像で、マス・数字・線が潰れていないか、枠からはみ出していないかを見る。
4. 既存ゲームと並べた画像で、見本の大きさ・重さ（線の太さと面積の濃さ）が突出していないかを見る。
5. ブラウザエラーが無いことを `browser-errors.log` で確かめる。

## 読まれ方の確かめ（模式図が別の物に読まれる）

文脈を持たない確認者に、ゲーム名とプレイ画面の画像1枚、レベルの順を伏せて並べ替えた5つの図だけを渡し、次を答えさせる。正解や意図は渡さない。

- それぞれの図は何に見えるか（盤面の一部、進み具合、ヒント、答えなど）。
- 難しいと思う順に並べるとどうなるか。理由は図のどこか。
- 図とプレイ画面の盤面は同じゲームに見えるか。

順が合わない、または盤面以外の物に読まれたら、流れ 3 に戻って描き方を変える。

誰が行うか:

- `/add-puzzle` から: 作り込みで、メインが使い捨てのサブエージェントに頼む（`/add-puzzle` の SKILL.md の「実行役」）。この Skill では行わず、レベルごとの見本の画像と、どれがどのレベルかを報告ファイルに書く。名前の付け直しと並べ替えはメインが行う。
- ほかの入口: 起動した会話のメインが、経緯を渡さないサブエージェントに頼む。
