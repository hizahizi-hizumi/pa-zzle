# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に連絡するのは、着手時の認識合わせ・作り切った後の最終レビュー・合意したパズルが成り立たないと分かったときの3つだけ。途中経過は送らない（人間は見ない）。
2. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる（他ブランチ・PR で同じパズルが進んでいないかも確かめる）。
3. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、資料に書く。合意したパズルが成り立たないと分かったときは、理由と代案（推奨つき）を示す。
4. 人間には、作り切って、遊ぶ側の目線で確かめ、判断しやすくしたものだけを見せる。
5. 人間のマージが本決定。マージ後の変更は新しい改善。
6. 確かめていないことを確認済みと書かない。サブエージェントの報告だけで「見た」と書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`）。返事を待つのはここだけ。
2. 調査: 開始時に導入調査 Issue を作り、合意を記録する。実装前提調査の冒頭に識別表（パズル名 / ゲーム ID / ブランチ接頭辞 / 候補 ID / SPEC 番号）を置き、`list-used-ids.sh` で空き番号を確かめて予約し、最下段（調査の段）のブランチで push する。問題供給・難易度・スマホ操作・導入判断が合意の範囲で成り立つかを観点ごとに並行で確かめ、仮決定と段の並びを決める。識別表・調査時の仮決定・台帳の行はこの段で書く。
3. 実装: 段ごとに実装役を起動して確かめ、段の PR を前段の上に積む。段で決めたことは PR 本文に残し、仮決定一覧と台帳の行へは最上段（SPEC の段）でまとめる。
4. 品質の作り込み: 機械検査（各段の `verify.sh`、`capture-screens.mjs` の browser-check、`naive-play-core.ts` の素朴なプレイヤーの表、問題集の `--verify`、`list-used-ids.sh`）・試遊・AI レビュー・`references/pitfalls.md` の自己点検を、直すべき指摘が無くなるまで回す。直しは原因の段に入れて上を積み直す。
5. 最終レビュー（`references/final-review.md`）。指摘を反映したら 4 からやり直す。指摘のうち他のパズルにも当てはまるものは、守る決まりとして正本（`GAME.md`・`DESIGN.md` 等）か `references/pitfalls.md` への追記を最上段（SPEC の段）に入れ、マージで人間に決めてもらう。AI レビューが拾えるのは書かれた決まりの範囲だけなので、これが次のパズルで同じ指摘を出させない唯一の仕組みになる。

試遊役を除く全サブエージェントに合意と人間の判断を渡す。レビュー役と試遊役には経緯を渡さない。状態は Issue・PR 本文・導入調査の文書に置き、再開時はそこから進み具合を判定する。

## 起動前に用意するもの

メインが作業ディレクトリに置き、パスで渡す。

| もの | 中身 | いつ作るか | 渡す相手 |
|---|---|---|---|
| brief | 識別表、合意（導入調査 Issue の合意節を写したもの）、最終レビューでの人間の判断、作業ディレクトリ、作業の決まり | 調査の段の後。人間の判断は反映のたびに足す | 実装役 |
| 段カード | 段の範囲・完成条件・（直しの起動では）直す指摘・その段に効く失敗パターン | 実装役の起動ごと | 実装役 |
| 範囲ファイル | 段カードから「直す指摘」を除いたもの（経緯を渡さないため） | レビューの起動ごと | レビュー役3種 |
| 合意ファイル | brief の合意と人間の判断の部分だけ | brief を作る・変えるたび | レビュー役3種・自己点検役 |
| レビュー版の worktree | レビューする版。ブランチを checkout せずに作る | レビューの起動ごと | レビュー役3種（リポジトリのルート）・自己点検役 |
| 差分と変更ファイル一覧 | 比較基準のコミット範囲の差分本文と変更ファイル | レビューの起動ごと | コードレビュー役 |
| 画面と browser-check.txt | `capture-screens.mjs` の出力と、比較用の既存ゲームの画面 | UI のある段のレビューと作り込み | 体験レビュー役・自己点検役（画面） |
| 使用中の番号の一覧 | `list-used-ids.sh` の出力 | 文書レビューの直前（`git fetch --all --prune` の後） | 文書レビュー役 |

試遊役には合意を渡さず、Agent の8つの入力だけを渡す。段ごとの試遊では「まだ作っていない画面・機能」を、品質の作り込みでは比較用の既存ゲームを渡す。

## 実行役

- 段の実装・直し: `puzzle-stage-implementer`
- 試遊（遊べる段で軽く、作り込みで必ず）: `puzzle-playtester`
- AI レビュー（段ごと・作り込み）: `puzzle-code-reviewer`・`puzzle-experience-reviewer`・`puzzle-document-reviewer`
- 失敗パターン集の自己点検（自己点検役）: 経緯を渡さない汎用サブエージェント（Opus）に、`references/pitfalls.md` とレビュー版の worktree・画面・素朴なプレイヤーの表・合意ファイルを渡して全行を当てさせる
- ピクトグラム: `/design-game-pictogram`。理由を残す判断: `/adr-create`
- この Skill の `scripts/`: `list-used-ids.sh`（調査開始時の番号予約と SPEC 直前の衝突確認）、`restack.sh`（直した後の積み直し、知らせる前に main と衝突していたときの rebase。積み直す前に原因の段を push しない。既定の `--old-base` が push 済みの原因の段のため）、`capture-screens.mjs`（撮影とブラウザエラー確認）、`playtest-driver.mjs`（試遊役が使う）、`naive-play-core.ts`（素朴なプレイヤーで各レベルを解かせる検査。「簡単すぎる」を止める向きにだけ使う。使い方は冒頭。ゲームごとのアダプタは `examples/naive-play-*.ts` を手本に書く）

## 環境

- サブエージェントは入れ子で起動できない。実装 → レビュー → 直しはメインが回す。
- GraphQL を使う `gh pr`（`/pr` Skill も）は失敗する。GitHub MCP か `gh api` の REST を使う。
