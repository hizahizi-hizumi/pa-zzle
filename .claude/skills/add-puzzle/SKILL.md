# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせと「成り立たない」の2つ。
2. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
3. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる。
4. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
5. 人間には、作り切って、遊ぶ側の目線で確かめ、判断しやすくしたものだけを見せる。
6. 人間のマージが本決定。マージ後の変更は新しい改善。
7. 確かめていないことを確認済みと書かない。サブエージェントの報告だけで「見た」と書かない。

## 流れ

段の種類の名前（research・rules・playable・difficulty・spec など）は `references/pitfalls.md` の冒頭で定める。

1. 認識合わせ（`references/alignment.md`）。後で要る許可もここで得る。
2. 調査の段:
   - 導入調査 Issue を作り、合意と許可を記録する。
   - `list-used-ids.sh` で空き番号を確かめ、実装前提調査の冒頭の識別表（パズル名 / ゲーム ID / ブランチ接頭辞 / 候補 ID / SPEC 番号）で予約して、調査の段のブランチを push する。
   - 問題供給・難易度・スマホ操作・導入判断が合意の範囲で成り立つかを観点ごとの調査役で並行に確かめ、仮決定と段の並びを決める。調査時の仮決定と台帳の行の初版はこの段で書き、文書レビューを通して PR を作る。
3. 実装: 段ごとに実装役を起動し、レビュー・試遊・自己点検（実行役の節で決める段だけ）で確かめてから、段のブランチを push して PR を前段の上に積む。SPEC の段で、各段の「AI が決めたこと」を仮決定一覧と台帳の行へまとめる。
4. 品質の作り込み:
   - 機械検査（各段の `verify.sh` と CI、`capture-screens.mjs`、素朴なプレイヤーの表、問題集の `--verify`）を通し、試遊・自己点検・AI レビューを回す。
   - 直しは原因の段に入れて上を積み直す。2巡目からは前回からの差分と、直した点に関わる試遊・自己点検だけを当てる。
   - 止め時: 機械検査と CI が通り、全段を push してプレビュー URL が出ている。AI レビューに Critical・Major が無く、Minor は直したか最終レビュー資料の「確かめていないこと・未決」に載せてある。試遊と自己点検の所見は直してあり、直さずに最終レビュー資料へ回したのは好み・面白さ・難易度の体感・時間とスコアの水準のものだけ。各段の PR 本文が最新。
5. 最終レビュー（`references/final-review.md`）。指摘を反映したら 4 からやり直す。

## 記録

- 合意・許可・人間の判断（「成り立たない」への返事と最終レビューの判断）は、導入調査 Issue の合意節に追記する。最終レビュー資料の URL と、人間の指摘の原文も同じ Issue に残す。
- 段で決めたことは段の PR 本文の「AI が決めたこと」に書く。
- 再開時は、導入調査 Issue・段の PR 本文・導入調査の文書から進み具合を判定する。作業ディレクトリのファイルは、そこから作り直せるものだけにする。

## サブエージェントに渡すもの

レビュー役・試遊役・自己点検役には経緯を渡さない。メインが作業ディレクトリに置き、パスで渡す。

| もの | 中身 | いつ作るか | 渡す相手 |
|---|---|---|---|
| 識別表 | パズル名・ゲーム ID・ブランチ接頭辞・候補 ID・SPEC 番号 | 調査の段 | 調査役・レビュー役3種（ゲーム ID とパズル名）・自己点検役。実装役には brief で渡す |
| brief | 識別表、合意節の写し、作業ディレクトリ、作業の決まり | 調査の段の後。合意節が変わるたび | 実装役 |
| 段カード | 段の番号と topic、前段のブランチ、範囲と完成条件、開発サーバーのポート、その段に効く失敗パターン。直しの起動では直す指摘、SPEC の段では各段の PR 本文の「AI が決めたこと」 | 実装役の起動ごと | 実装役 |
| 範囲ファイル | 段の番号と topic、範囲と完成条件。作り込みでは全段ぶん | レビュー・自己点検の起動ごと | レビュー役3種・自己点検役 |
| 合意ファイル | 合意節の写し（合意と人間の判断） | 認識合わせの後。合意節が変わるたび | 調査役・レビュー役3種・自己点検役 |
| 調査の段の worktree と書いてよいパス | 導入調査ディレクトリと `scripts/research/` の観点ごとのファイル | 調査役の起動ごと | 調査役 |
| レビュー版の worktree | レビューする版。ブランチを checkout せずに作る | レビューの起動ごと | レビュー役3種・自己点検役 |
| 差分と変更ファイル一覧 | 比較基準のコミット範囲の差分と変更ファイル。大きいときは責務ごとに分け、レビュー役も分ける | コードレビューの起動ごと | コードレビュー役 |
| 画面 | `capture-screens.mjs` の出力（browser-check.txt を含む）。操作が要る画面（結果・クリア直後など）は `playtest-driver.mjs` で撮り、同じ命名にそろえる。比較用の既存ゲームの同じ画面（作り込みでは必須） | UI のある段と作り込み | 体験レビュー役。作り込みでは自己点検役にも |
| 文書の場所と使用中の番号 | SPEC のパス、導入調査ディレクトリ、台帳の行と `PUZZLE-nnn.md` のパス、`list-used-ids.sh` の出力 | 文書のある段と作り込み | 文書レビュー役 |
| 素朴なプレイヤーの表 | アダプタ（`.claude/skills/add-puzzle/examples/naive-play-<ゲーム>.ts`。difficulty の段の範囲に含め、実装役が書く）を、メインが worktree のゲームのディレクトリに向けて流した出力 | difficulty の段と、問題集を作り直すたび | 自己点検役 |
| 失敗パターン集 | この Skill の `references/pitfalls.md` の絶対パス（worktree の版は古いか無いことがある） | 起動ごと | 調査役・実装役・体験レビュー役・自己点検役 |

worktree のパスと手本の参照は、実装役の起動のプロンプトで段カードと一緒に渡す。試遊役には Agent が定める入力だけを渡す。アプリの URL は、メインが開発サーバーを起動して渡す。段ごとの試遊では「まだ作っていない画面・機能」を、作り込みでは比較用の既存ゲームを渡す。

## 実行役

- 調査役: 汎用サブエージェント（Opus）を観点ごとに1つ
- 段の実装と直し: `puzzle-stage-implementer`。pictogram の段では、この中で `/design-game-pictogram` を起動する
- 試遊: `puzzle-playtester`。playable 以降で UI か遊びが変わる段では iphone で、作り込みでは iphone と pc で。difficulty 以降の段では、遊ぶレベルを1〜5の各1問とする
- AI レビュー: `puzzle-code-reviewer`（段ごと・作り込み）、`puzzle-experience-reviewer`（UI のある段・作り込み）、`puzzle-document-reviewer`（文書のある段・作り込み）
- 自己点検役: 汎用サブエージェント（Opus）。当てた行ごとに「当たる（どこで）／当たらない（根拠）／確かめられない（なぜ）」を返させる
- 失敗パターン集の当て方: 調査役は「進め方」より前の節で「いつ」に research を含む行、自己点検役は difficulty の段では「いつ」に difficulty を含む行、作り込みでは「進め方」より前の節の全行。「進め方」の節は、メインが各行をその「いつ」で当てる
- 理由を残す判断: `/adr-create`
- この Skill の `scripts/`（使い方と使い時は各スクリプトの冒頭）: `list-used-ids.sh`、`restack.sh`、`capture-screens.mjs`、`playtest-driver.mjs`、`naive-play-core.ts`（アダプタは `examples/naive-play-*.ts` が手本）

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューのどれにも当てはめる。

- 結論から書く。最初の1〜2行で、何ができたかと、何をしてほしいか。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。`/tmp` のパスや、説明の無い内部用語を使わない。
- 案を記号だけで呼ばず、中身で説明する。難易度の案は、判定に使うつまみと利用者向けの一言で示す。
- 推奨を既定にする。推奨の理由は、このパズルで何が良くなるかを具体的に書き、不利な点も並べる。

## 参照する正本

- ゲームとUIの決まり: `GAME.md`、`APP.md`、`DESIGN.md`、`.claude/rules/game-structure.md`
- 文書の置き場所と書き方: `docs/README.md`
- 導入調査: `docs/パズル/導入調査/<パズル名>/`（実装前提調査・難易度の資料・ピクトグラム検討）
- 難易度の決まり: `docs/パズル/README.md` から辿る難易度文書
- 候補台帳: `docs/棚上げ/パズル候補.csv` と `docs/棚上げ/パズル候補/PUZZLE-nnn.md`
- 仕様: `docs/プロダクト/仕様/パズル/SPEC-nnn.md`

## 環境

- サブエージェントは入れ子で起動できない。実装 → レビュー → 直しはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う（GraphQL を使う `gh` は失敗する）。
