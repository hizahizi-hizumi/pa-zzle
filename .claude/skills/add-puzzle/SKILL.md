# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせ（push できる環境の用意を含む）と「成り立たない」の2つ。
2. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
3. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる。
4. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
5. 書く役は1つに通し、見る役は使い捨てにする。実装は1本の作業ブランチで1つの実装役が続けて行い、確かめは経緯を渡さない役に毎回新しく頼む。
6. PR は人間に渡す単位で、作る・確かめる単位ではない。作り切ってから、完成した木を依存の層で PR に切り出す。
7. 人間のマージが本決定。マージ後の変更は新しい改善。確かめていないことを確認済みと書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`）。合意と許可を得たら、作業ブランチを作る。
   - 接頭辞は `git ls-remote origin '<接頭辞>/*'` が空のものを選ぶ（既存のブランチを force-push で消さないため）。
   - 作業ブランチと worktree は main から作る（`git worktree add <作業ディレクトリ>/work -b <接頭辞>/work origin/main`）。
   - 既存の実装を引き継ぐと合意したときは、ゲーム固有のパス（`frontend/src/games/<game>/`・`game-catalog/<game>/`・`pages/puzzles/<game>/` と View・導入調査）だけを既存の最上層の版で取り込んでコミットし（`git -C <worktree> checkout <既存の最上層> -- <パス>`）、識別表の番号も既存のものを使う。共通のファイル（カタログの並び・`biome.json`・`router.ts`・`package.json` など）は main の版のまま、実装役に作業カードで足させる。作る順番のどの項目が済んでいるかは調査で確かめる。
   - 作業ブランチと、層のブランチと同じ形の名前（`<接頭辞>/00-check`）を push し（後者は消す）、push できることを実際に確かめる。できなければ、push できるようにしてほしいことを頼んで待つ（認識合わせの続き）。
2. 調査（`references/research.md`）:
   - 導入調査 Issue を `導入調査: <パズル名>` の題で作り、合意と許可を記録する。Issue 番号は識別表に書く。
   - SPEC 番号・候補 ID が origin のどのブランチでも対象パズル以外に使われていないことを `git ls-tree` と `git grep` で確かめ、実装前提調査の識別表で予約する（台帳に対象パズルの行があれば、その ID を使う）。ADR は spec の作業カードを出すときに同じ確かめで番号を選ぶ。
   - 観点ごとの調査役を並行に起動する（作業ブランチの worktree で、観点カードの書いてよいパスだけに書かせる）。結果をメインが実装前提調査（仮決定一覧・作る順番とその済み・未済・PR の切り方）と台帳の行へまとめてコミットし、文書レビューを通して直しを新しいコミットで足し、push する。
3. 実装: 実装役を1つ起動し、作る順番の未済の項目ごとに作業カードを渡して、同じ実装役に続けて頼む（SendMessage）。報告を受けるたびに、作業ディレクトリの `implementer-log.md` に済んだ項目・決めたこと・未処理の所見・作り方の Skill の報告のパス・実装役の ID を追記する。山場ごとに作業ブランチを push し、確かめを回して、所見を振り分ける。
   - 山場1（rules・playable ができたとき。遊べる最小の縦断）: 試遊（iphone で、実装役が報告した入口の問題）とコードレビュー。ルールの核と操作が成り立つかを見る。
   - 山場2（difficulty・problem-pool ができたとき）: 自己点検（`/design-game-difficulty` が頼む解法器の独立した確かめを含む）と試遊（iphone で、`/design-game-difficulty` の報告の「試遊に渡す問題」。無ければレベル1〜5の各1問）。レベル差と最上位の手応えを見る。
   - ここで覆ると上を全部作り直すので、この2つだけは作り切る前に確かめる。ほかの項目は作り込みでまとめて確かめる。
4. 品質の作り込み（巡を回す）:
   - 確かめる版を決め、作り方の Skill の検査の結果（`difficulty-checks.md`）と順を伏せたプレビュー画像を、その版で実装役に作り直させる（両 Skill の「`/add-puzzle` の確かめの準備」の入口）。
   - 機械検査（`verify.sh`、問題集の `--verify`、難易度の計測）を通したうえで、試遊・自己点検・AI レビュー3種と読まれ方の確かめを全体に当てる。
   - 所見を振り分け、「直す」は直しの作業カード（直す所見と、その所見が属する作る順番の項目）にして、同じ実装役に新しいコミットとして直させる。巡ごとに「記録」の巡の記録を残す。
   - 2巡目からは、前回のレビュー版からの差分をレビューし、直した所に関わる試遊を回し、自己点検役には直しの作業カードの項目の「いつ」と「全項目」だけを渡す（解法器を直したら頼まれた確かめも渡す）。
   - 止め時（すべてを満たしたら 5 へ進む）: 機械検査が通り、作業ブランチのプレビュー URL が出ている。直しを入れた後の版に当てた巡で「直す」が0件。自己点検の「確かめられない」の行はメインが測ってから振り分けた。
5. PR への切り出し（`references/research.md` の「PR の切り方」）:
   - 最下層のブランチ `<接頭辞>/01-<層の topic>` を `git merge-base origin/main <接頭辞>/work` から作り、上の層を前の層の上に作る。各層のファイルを作業ブランチの版で取り込んでコミットする。
   - 各層を detach した worktree に展開し、`bun install --frozen-lockfile`（frontend と tools/semantic-lint）の後に `verify.sh` を通す。
   - `git diff --stat <最上層> <接頭辞>/work` が空であることを確かめる（空でなければ、どの層にも入らなかったファイルを実装前提調査の「PR の切り方」に足して切り直す）。
   - 全部を push して PR を積み、PR 本文は「記録」の型で書く。CI（Quality Gate）は PR で走るので、落ちたら作業ブランチで直して 4 の機械検査を通し、切り出し直す。
6. 最終レビュー（`references/final-review.md`）。指摘は作業ブランチで直して 4 の止め時を満たし、5 で切り出し直して force-push する。
   - PR が main とコンフリクトしたときだけ、メインが作業ブランチを最新の main へ rebase し（衝突はメインが解く）、波及の直しを実装役に新しいコミットとして頼み、4 の機械検査を通してから 5 で切り出し直す。
   - 下の層の PR が先にマージされたら、作業ブランチを最新の main へ rebase してから、残りの層だけを `origin/main` の上に、層の番号を保ったまま切り出し直し、上の PR の base を付け替える。マージ済みの層のパスを後で直した分は、新しい PR として切る。

## 所見の振り分け

試遊・自己点検・AI レビュー・機械検査の所見と、実装役の報告にある作り方の Skill の「人間に残す候補」・別案を、役を問わずすべて1つに振る。作り方の Skill の「頼むこと」と「試遊に渡す問題」は所見ではないので振り分けず、自己点検役・試遊役・後の作業カードへ渡す。プレビューの Skill の「iOS 実機で見てほしい点」「撮っていないもの」は最終レビュー資料の同じ名前の節と「確かめていないこと・未決」へ置く。

- 直す: 成果物を変えるもの。変えるなら必ずここに振る。
- AI が決める: 欠陥ではなく、合意した意図の範囲の設計判断への異論だった所見。今の作りを理由つきで採り、巡の記録の「AI が決めたこと」に書く。
- 人間に残す: 面白さ・好み、計測で裏付けられない難易度の体感・時間とスコアの水準、合意か正本の制約のために直せないもの（どの制約かを添える）。置き場所は `references/final-review.md` の「作り方」。

重さ: Critical・Major は「直す」か「人間に残す」のどちらかで、「AI が決める」には振らない。Minor は直さなければ「確かめていないこと・未決」へ置く。重さの無い所見は、自己点検の「当たる」を Major、レビュー役の「規約で確定できる論点」を「直す」として扱う。同じ所見が直した後も2巡続けて出たら、直し方を変えるか、直せない理由を添えて「人間に残す」へ移す。

## 記録

- 導入調査 Issue の合意節: 合意・許可・人間の判断（「成り立たない」への返事と最終レビューの判断）、最終レビュー資料の URL、人間の指摘の原文。
- 導入調査 Issue の巡の記録: 山場と作り込みの巡ごとにコメントを1つ。対象の版のコミット、起動した確かめ、所見と振り分け、直したコミット、AI が決めたこと（合意した意図の範囲で前提の細部を変えたときもここに書き、最終レビュー資料では「認識合わせからの変更点」に載せる）。止め時と2巡の判定はここから行う。
- 実装前提調査: 識別表・仮決定一覧・作る順番・PR の切り方。作り方の Skill の別案と、山場の間の項目で実装役が決めたことは、メインが仮決定一覧に書く。作り込みの後に「実装で確定した差分」を足す。
- 切り出した PR の本文: その層の範囲、その層に関わる「AI が決めたこと」、確かめたこと（巡の記録への参照）、残した所見、マージの順。
- 再開時は、識別表の接頭辞と Issue（題 `導入調査: <パズル名>`）・作業ブランチ・実装前提調査から進み具合を判定する。`git worktree prune` の後に `origin/<接頭辞>/work` から worktree を作り直し、brief を Issue の合意節から作り直して、新しい実装役に引き継ぎファイルとともに渡す。作業ディレクトリのファイルは消えている前提で、作り方の Skill の報告の要点（試遊に渡す問題・頼むこと・伏せた画像の正解の順）は巡の記録に写しておき、`difficulty-checks.md` と伏せた画像は実装役に作り直させる。`implementer-log.md` は巡の記録と作業ブランチの履歴から作り直す。

## 実行役

- 調査: `puzzle-researcher` を観点ごとに1つ。
- 実装と直し: `puzzle-implementer` を1つに通す。作業カードの項目に作り方の Skill があれば、実装役がその中で起動する（difficulty・problem-pool は `/design-game-difficulty`、difficulty-select は `/design-game-difficulty-preview`、pictogram は `/design-game-pictogram`、spec の ADR は `/adr-create <タイトル>`）。作り方の Skill の報告は作業ディレクトリのファイルに書かれ、実装役の報告にパスが載る。新しい実装役に代えるのは、SendMessage が失敗したときか、報告が前に決めたことを落とし始めたときだけで、引き継ぎファイルを渡す。
- 試遊: `puzzle-playtester`。山場1は iphone、山場2は iphone で上の「試遊に渡す問題」、作り込みは iphone でレベル1〜5の各1問と pc で最も低いレベルの1問。
- AI レビュー: `puzzle-code-reviewer`（山場1・作り込み）、`puzzle-experience-reviewer`（作り込み）、`puzzle-document-reviewer`（調査・作り込み）。
- 自己点検: `puzzle-pitfall-checker`（山場2・作り込み）。「確かめられない」の行はメインが測る。
- 失敗パターン集の配り方: 行は「いつ」で配る。作る順番の項目か「全項目」の行は、その項目の作業カードへ（research の行は調査役へ）。工程（認識合わせ・実装・作り込み・反映・最終レビュー）の行は、メインがその工程で当てる。自己点検役に渡す「いつ」は、山場2では difficulty と problem-pool と「全項目」、作り込みの1巡目では作る順番の項目すべてと「全項目」。作り方の Skill の集は、その冒頭に書かれた扱いに従う。
- 読まれ方の確かめ: 汎用サブエージェント（Opus）を使い捨てで1つ。ゲーム名・プレイ画面の画像1枚・順を伏せたプレビュー画像の組だけを渡し、リポジトリは読ませない。画像の名前の付け直しと並べ替えはメインが行い、正解の順はメインだけが持つ。順が合わない・盤面以外の物に読まれたら Major の所見として振り分ける。
- 確かめの役（試遊・自己点検・レビュー3種・読まれ方）は入力が互いに独立しているので、同時に起動してよい。
- この Skill のスクリプトは `scripts/playtest-driver.mjs`（試遊と撮影のための常駐ブラウザ。使い方は冒頭）だけ。

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューのどれにも当てはめる。

- 結論から書く。最初の1〜2行で、何ができたかと、何をしてほしいか。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。`/tmp` のパスや、説明の無い内部用語を使わない。
- 案を記号だけで呼ばず、中身で説明する。難易度の案は、判定に使うつまみと利用者向けの一言で示す。
- 推奨を既定にする。推奨の理由は、このパズルで何が良くなるかを具体的に書き、不利な点も並べる。

## 環境

- サブエージェントは入れ子で起動できない。確かめの役の起動と所見の振り分けはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う（GraphQL を使う `gh` は失敗する）。
- この環境からプレビュー URL は開けない。描画は手元の開発サーバーで確かめ、そう書く。
- アプリは今ダーク表示に切り替えないので、ダークは確かめる範囲から外す。
