# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせと「成り立たない」の2つ。
2. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
3. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる。
4. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
5. 人間には、作り切って、遊ぶ側の目線で確かめ、判断しやすくしたものだけを見せる。
6. 人間のマージが本決定。マージ後の変更は新しい改善。
7. 確かめていないことを確認済みと書かない。

## 流れ

段の種類の名前（research・rules・playable・difficulty・spec など）は `references/pitfalls.md` の冒頭で定める。

1. 認識合わせ（`references/alignment.md`）。失敗パターン集の「いつ」が認識合わせの行も、メインがここで当てる。
2. research の段:
   - 導入調査 Issue を作り、合意と許可を記録する。
   - `list-used-ids.sh` で空き番号を確かめ、実装前提調査の冒頭に識別表を置いて予約し（形は `list-used-ids.sh` の冒頭）、research の段のブランチを push する。
   - 問題供給・難易度・スマホ操作・導入判断が合意の範囲で成り立つかを観点ごとの調査役で並行に確かめ、仮決定と段の並びを決める。段は段の種類から組み、片方を直すともう片方を必ず作り直す種類（difficulty と problem-pool など）は分けない。調査時の仮決定と台帳の行の初版はこの段で書き、文書レビューを通して PR を作る。
3. 実装: 段ごとに実装役を起動し、実行役の節でその段に要る確かめ（レビュー・試遊・自己点検）を回して、所見を振り分ける（4 と同じ）。段の PR 本文を型（「記録」）どおりに埋めてから段のブランチを push し、PR を前段の上に積む。spec の段で、各段の「AI が決めたこと」を実装前提調査の仮決定一覧と「実装で確定した差分」、台帳の行へまとめる。
4. 品質の作り込み:
   - 機械検査（各段の `verify.sh` と CI、`capture-screens.mjs` の browser-check、問題集の `--verify`）を通し、素朴なプレイヤーの表を今の問題集で測り直したうえで、試遊・自己点検・AI レビューを回す。
   - 所見の振り分け（役を問わず、すべての所見を1つに振る）:
     - 直す: AI が直せるもの。直しは原因の段に入れ、波及の連鎖（`references/final-review.md` の「指摘の反映」）を上から通して積み直す。
     - AI が決める: 合意した意図の範囲で決められるもの。段の PR 本文の「AI が決めたこと」に書く。
     - 人間に残す: 面白さ・好み、計測で裏付けられない難易度の体感・時間とスコアの水準、合意か正本の制約のために直せないもの（どの制約かを添える）。最終レビュー資料の節へ置く（`references/final-review.md` の「作り方」）。
     - Critical・Major は「直す」か「人間に残す」のどちらか。Minor は直さなければ資料の「確かめていないこと・未決」へ置く。
     - 同じ所見が、直した後も2巡続けて出たら、直し方を変えるか、直せない理由を添えて「人間に残す」へ移す。
   - 2巡目からは前回からの差分と、直した点に関わる試遊・自己点検だけを当てる。
   - 止め時（すべてを満たしたら最終レビューへ進む）:
     - 機械検査と CI が通り、全段を push してプレビュー URL が出ている。main とコンフリクトしていれば `restack.sh --onto origin/main` で載せ直してある。
     - 直前の巡の所見がすべて振り分け済みで、「直す」に残りが無い。自己点検の「確かめられない」の行は、メインが測ってから振り分けた。
     - 各段の PR 本文が型どおり最新。
5. 最終レビュー（`references/final-review.md`）。指摘を反映したら 4 からやり直す。

## 記録

- 合意・許可・人間の判断（「成り立たない」への返事と最終レビューの判断）は、導入調査 Issue の合意節に追記する。最終レビュー資料の URL と、人間の指摘の原文も同じ Issue に残す。
- 段の PR 本文の型（ほかのファイルが「PR 本文」と言うときはこの欄を指す）:
  - 範囲と完成条件
  - AI が決めたこと: 段で決めたこと。合意した意図の範囲で前提の細部を変えたときもここに書き、最終レビュー資料では「認識合わせからの変更点」に載せる
  - 確かめたこと: 機械検査と、実行役の節でその段に要るレビュー・試遊・自己点検の結果（件数と要点）、計測の詳細
  - 残した所見: 振り分けで残した Minor と「人間に残す」所見
  - 積み直し前の旧コミット ID（`restack.sh` の出力）
- 「確かめたこと」に、その段に要る確かめが欠けていれば push しない。
- 再開時は、導入調査 Issue・段の PR 本文・導入調査の文書から進み具合を判定する。作業ディレクトリのファイルは、そこから作り直せるものだけにする。

## 実行役

この Skill の `scripts/`（使い方と使い時は各スクリプトの冒頭）: `list-used-ids.sh`、`restack.sh`、`capture-screens.mjs`、`playtest-driver.mjs`、`naive-play-core.ts`（素朴なプレイヤーのアダプタの土台）。

- 調査役: 汎用サブエージェント（Opus）を観点ごとに1つ
- 段の実装と直し: `puzzle-stage-implementer`。pictogram の段では、この中で `/design-game-pictogram` を起動する
- 試遊: `puzzle-playtester`。research・rules・pictogram・spec だけの段を除く各段では iphone で、作り込みでは iphone と pc で。遊ぶレベルは、difficulty より前の段では段にある問題、difficulty 以降の段と作り込みでは1〜5の各1問
- AI レビュー: `puzzle-code-reviewer`（rules 以降の各段・作り込み）、`puzzle-experience-reviewer`（UI が変わる段・作り込み）、`puzzle-document-reviewer`（文書を変える段・作り込み）
- 自己点検: `puzzle-pitfall-checker`。difficulty の段と作り込みの各巡で起動する。「確かめられない」の行はメインが測る（画面は `capture-screens.mjs`・`playtest-driver.mjs`、難易度の量は worktree の分析コードと素朴なプレイヤー）
- 失敗パターン集の当て方: 行は節ではなく「いつ」で配る。段の種類か「全段」の行は、その段の段カードへ入れる（research の行は調査役へ）。工程（認識合わせ・実装・作り込み・反映・最終レビュー）の行は、メインがその工程で当てる。自己点検役に渡す「いつ」は、difficulty の段では difficulty と problem-pool、作り込みでは段の種類すべてと「全段」。体験レビュー役には絶対パスだけを渡し、当てる節は Agent が定める
- 理由を残す判断: spec の段の実装役が、段カードにある判断ごとに `/adr-create <タイトル>`（タイトルを渡して確認を待たせない）を worktree で起動する

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューのどれにも当てはめる。

- 結論から書く。最初の1〜2行で、何ができたかと、何をしてほしいか。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。`/tmp` のパスや、説明の無い内部用語を使わない。
- 案を記号だけで呼ばず、中身で説明する。難易度の案は、判定に使うつまみと利用者向けの一言で示す。
- 推奨を既定にする。推奨の理由は、このパズルで何が良くなるかを具体的に書き、不利な点も並べる。

## 参照する正本

- ゲームとUIの決まり: `GAME.md`、`APP.md`、`DESIGN.md`、`.claude/rules/game-structure.md`
- 文書の置き場所と書き方: `docs/README.md`
- 導入調査: `docs/パズル/導入調査/<パズル名>/`（実装前提調査・難易度の資料・ピクトグラム検討）
- 難易度の決まり: `docs/パズル/README.md` から辿る難易度文書
- 候補台帳: `docs/棚上げ/パズル候補.csv` と `docs/棚上げ/パズル候補/PUZZLE-nnn.md`
- 仕様: `docs/プロダクト/仕様/パズル/SPEC-nnn.md`

## 環境

- サブエージェントは入れ子で起動できない。実装 → レビュー → 直しはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う（GraphQL を使う `gh` は失敗する）。
