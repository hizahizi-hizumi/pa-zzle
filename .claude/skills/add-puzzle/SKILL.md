# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせと「成り立たない」の2つ。
2. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる。
3. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、段の PR 本文の「AI が決めたこと」に書く。合意したパズルが成り立たないと分かったときは、理由と代案（推奨つき）を知らせて返事を待つ。
4. 人間には、作り切って、遊ぶ側の目線で確かめ、判断しやすくしたものだけを見せる。
5. 人間のマージが本決定。マージ後の変更は新しい改善。
6. 確かめていないことを確認済みと書かない。サブエージェントの報告だけで「見た」と書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`）。スタックのブランチの push・段の PR・導入調査 Issue の許可もここで得る。
2. 調査の段:
   - 導入調査 Issue を作り、合意を記録する。
   - `list-used-ids.sh` で空き番号を確かめ、実装前提調査の冒頭の識別表（パズル名 / ゲーム ID / ブランチ接頭辞 / 候補 ID / SPEC 番号）で予約して、調査の段のブランチを push する。
   - 問題供給・難易度・スマホ操作・導入判断が合意の範囲で成り立つかを、観点ごとの調査役（合意を渡す）で並行に確かめ、仮決定と段の並びを決める。識別表・調査時の仮決定・台帳の行の初版はこの段で書く。
3. 実装: 段ごとに実装役を起動し、レビューと試遊で確かめ、段のブランチを push して PR を前段の上に積む。段で決めたことは PR 本文の「AI が決めたこと」に残し、SPEC の段で仮決定一覧と台帳の行へまとめる。
4. 品質の作り込み: 機械検査（各段の `verify.sh` と CI、`capture-screens.mjs`、素朴なプレイヤーの表、問題集の `--verify`）を通したうえで、試遊・自己点検・AI レビューを回す。遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。直しは原因の段に入れて上を積み直す。2巡目からは前回からの差分と、直した点に関わる試遊・自己点検だけを当てる。
   止め時: 機械検査と CI が通り、AI レビューに Critical・Major が無く、自己点検と試遊の所見がすべて直したか最終レビュー資料に載せたもので、各段の PR 本文が最新であること。知らせる前に、失敗パターン集の「進め方」の節をメインが当てる。
5. 最終レビュー（`references/final-review.md`）。指摘を反映したら 4 からやり直す。

## 再開

状態は導入調査 Issue・段の PR 本文・導入調査の文書に置き、再開時はそこから進み具合を判定する。

## サブエージェントに渡すもの

試遊役を除く全サブエージェントに、合意と人間の判断を渡す。レビュー役と試遊役には経緯を渡さない。メインが作業ディレクトリに置き、パスで渡す。

| もの | 中身 | いつ作るか | 渡す相手 |
|---|---|---|---|
| brief | 識別表、合意（導入調査 Issue の合意節）、最終レビューでの人間の判断、作業の決まり | 調査の段の後。人間の判断は反映のたびに足す | 実装役 |
| 段カード | 段の番号と名前、worktree のパス、範囲と完成条件、手本、開発サーバーのポート、その段に効く失敗パターン。直しの起動では直す指摘、SPEC の段では各段の PR 本文の「AI が決めたこと」 | 実装役の起動ごと | 実装役 |
| 範囲ファイル | 段カードから直す指摘を除いたもの。作り込みでは全段の範囲と完成条件 | レビューの起動ごと | レビュー役3種 |
| 合意ファイル | brief の合意と人間の判断の部分だけ | brief を作る・変えるたび | レビュー役3種・自己点検役 |
| レビュー版の worktree | レビューする版。ブランチを checkout せずに作る | レビューの起動ごと | レビュー役3種・自己点検役 |
| 差分と変更ファイル一覧 | 比較基準のコミット範囲の差分と変更ファイル。大きいときは責務ごとに分け、レビュー役も分ける | コードレビューの起動ごと | コードレビュー役 |
| 画面 | `capture-screens.mjs` の出力（browser-check.txt を含む）と、比較用の既存ゲームの同じ画面 | UI のある段と作り込み | 体験レビュー役・自己点検役 |
| 文書の場所と使用中の番号 | SPEC のパス・導入調査ディレクトリ・台帳の行と、`list-used-ids.sh` の出力 | 文書のある段と作り込み | 文書レビュー役 |
| 素朴なプレイヤーの表 | `naive-play-core.ts` とアダプタの出力 | 難易度の段と作り込み | 自己点検役 |
| 失敗パターン集 | この Skill の `references/pitfalls.md` の絶対パス（レビュー版の worktree には無いことがある） | 起動ごと | 体験レビュー役・自己点検役 |

試遊役には Agent が定める入力だけを渡す。段ごとの試遊では「まだ作っていない画面・機能」を、作り込みでは比較用の既存ゲームを渡す。

## 実行役

- 段の実装と直し: `puzzle-stage-implementer`
- 試遊: `puzzle-playtester`。遊べる段ごとに iphone で（難易度のある段では各レベル1問ずつ）、作り込みでは iphone と pc で
- AI レビュー: `puzzle-code-reviewer`（段ごと・作り込み）、`puzzle-experience-reviewer`（UI のある段・作り込み）、`puzzle-document-reviewer`（文書のある段・作り込み）
- 自己点検役: 経緯を渡さない汎用サブエージェント（Opus）。失敗パターン集の「面白さ・問題の質」「難易度」「プレイUI・プレビュー・見た目」「スコア・結果」の節を全行当て、「当たる（どこで）／当たらない（根拠）／確かめられない（なぜ）」を返させる
- ピクトグラム: `/design-game-pictogram`
- 理由を残す判断: `/adr-create`
- この Skill の `scripts/`（使い方は各スクリプトの冒頭）: `list-used-ids.sh`（調査開始時の番号の予約と、文書レビューの直前）、`restack.sh`（直した段の上の積み直しと、main と衝突したときの rebase）、`capture-screens.mjs`（撮影とブラウザエラーの確認）、`playtest-driver.mjs`（試遊役が使う）、`naive-play-core.ts`（素朴なプレイヤーの検査。「簡単すぎる」を止める向きにだけ使う。アダプタは `examples/naive-play-*.ts` が手本）

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューのどれにも当てはめる。

- 結論から書く。最初の1〜2行で、何ができたかと、何をしてほしいか。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。`/tmp` のパスや、説明の無い内部用語を使わない。
- 案を記号だけで呼ばず、中身で説明する。難易度の案は、判定に使うつまみと利用者向けの一言で示す。
- 推奨を既定にする。推奨の理由は、このパズルで何が良くなるかを具体的に書き、不利な点も並べる。

## 環境

- サブエージェントは入れ子で起動できない。実装 → レビュー → 直しはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う（GraphQL を使う `gh` は失敗する）。
