# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせと「成り立たない」の2つ。
2. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
3. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる。
4. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
5. 書く役は1つに通し、見る役は使い捨てにする。実装は1本の作業ブランチで1つの実装役が続けて行い、確かめは経緯を渡さない役に毎回新しく頼む。
6. PR は人間に渡す単位で、作る・確かめる単位ではない。作り切ってから、完成した木を依存の層で PR に切り出す。
7. 人間のマージが本決定。マージ後の変更は新しい改善。確かめていないことを確認済みと書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`）。合意と許可を得たら、作業ブランチ `<接頭辞>/work` を main から作って push し、push できることを実際に確かめる。できなければ、push できるようにしてほしいことを頼んで待つ。
2. 調査（`references/research.md`）:
   - 導入調査 Issue を作り、合意と許可を記録する。
   - SPEC 番号・候補 ID が origin のどのブランチでも使われていないことを `git ls-tree` と `git grep` で確かめ、実装前提調査の識別表で予約する。
   - 観点ごとの調査役を並行に起動し、結果をメインが実装前提調査（仮決定一覧・作る順番・PR の切り方）と台帳の行の初版へまとめる。文書レビューを通してコミットし、push する。
3. 実装: 実装役を1つ起動し、作る順番の項目ごとに作業カードを渡して、同じ実装役に続けて頼む（SendMessage）。山場ごとに作業ブランチを push し、確かめを回して、所見を振り分ける。
   - 山場1（rules・playable ができたとき。遊べる最小の縦断）: 試遊（iphone）とコードレビュー。ルールの核と操作が成り立つかを見る。
   - 山場2（difficulty・problem-pool ができたとき）: 自己点検と試遊（レベル1〜5の各1問）。レベル差と最上位の手応えを見る。
   - ここで覆ると上を全部作り直すので、この2つだけは作り切る前に確かめる。ほかの項目は作り込みでまとめて確かめる。
4. 品質の作り込み（巡を回す）:
   - 機械検査（`verify.sh` と CI、問題集の `--verify`、難易度の計測）を通したうえで、試遊（iphone と pc）・自己点検・AI レビュー3種を全体に当てる。
   - 所見を振り分け、「直す」は同じ実装役に新しいコミットとして直させる。巡ごとに「記録」の巡の記録を残す。
   - 2巡目からは、前回からの差分をレビューし、直した所に関わる試遊を回し、自己点検役には直した項目の「いつ」と「全項目」だけを渡す。
   - 止め時（すべてを満たしたら 5 へ進む）: 機械検査と CI が通り、作業ブランチのプレビュー URL が出ている。直しを入れた後の版に当てた巡で「直す」が0件。自己点検の「確かめられない」の行はメインが測ってから振り分けた。
5. PR への切り出し（`references/research.md` の「PR の切り方」）: 完成した作業ブランチから、下の層から順に層ごとのブランチ `<接頭辞>/<NN>-<層>` を前の層の上に作り、その層のファイルを作業ブランチの版で取り込んでコミットする。各層で `verify.sh` を通し、最上層と作業ブランチの差分が空であることを確かめて、全部を push し PR を積む。PR 本文は「記録」の型で書く。
6. 最終レビュー（`references/final-review.md`）。指摘は作業ブランチで直して 4 の止め時を満たし、5 で切り出し直して force-push する。

## 所見の振り分け

試遊・自己点検・AI レビュー・機械検査の所見を、役を問わずすべて1つに振る。

- 直す: 成果物を変えるもの。変えるなら必ずここに振る。
- AI が決める: 成果物を変えずに、今の作りを採る判断。理由を巡の記録の「AI が決めたこと」に書く。
- 人間に残す: 面白さ・好み、計測で裏付けられない難易度の体感・時間とスコアの水準、合意か正本の制約のために直せないもの（どの制約かを添える）。最終レビュー資料の「見てほしい点」（3点まで）か、あふれたものを「確かめていないこと・未決」に置く。

重さ: Critical・Major は「直す」か「人間に残す」のどちらか。Minor は直さなければ「確かめていないこと・未決」へ置く。重さの無い所見は、自己点検の「当たる」を Major、レビュー役の「規約で確定できる論点」を「直す」として扱う。同じ所見が直した後も2巡続けて出たら、直し方を変えるか、直せない理由を添えて「人間に残す」へ移す。

## 記録

- 導入調査 Issue の合意節: 合意・許可・人間の判断（「成り立たない」への返事と最終レビューの判断）、最終レビュー資料の URL、人間の指摘の原文。
- 導入調査 Issue の巡の記録: 山場と作り込みの巡ごとにコメントを1つ。対象の版のコミット、起動した確かめ、所見と振り分け、直したコミット、AI が決めたこと（合意した意図の範囲で前提の細部を変えたときもここに書き、最終レビュー資料では「認識合わせからの変更点」に載せる）。止め時と2巡の判定はここから行う。
- 実装前提調査: 識別表・仮決定一覧・作る順番・PR の切り方。作り込みの後に「実装で確定した差分」を足す。
- 切り出した PR の本文: その層の範囲、その層に関わる「AI が決めたこと」、確かめたこと（巡の記録への参照）、残した所見、マージの順。
- 再開時は、Issue・作業ブランチ・実装前提調査から進み具合を判定する。作業ディレクトリのファイルは、そこから作り直せるものだけにする。

## サブエージェントに渡すもの

レビュー役・試遊役・自己点検役には経緯を渡さない。ファイルにできるものは、メインが作業ディレクトリ（`/tmp/<接頭辞>/`）に置いてパスで渡す。

| もの | 中身 | 渡す相手 |
|---|---|---|
| 識別表 | パズル名・ゲーム ID・ブランチ接頭辞・候補 ID・SPEC 番号 | 調査役・実装役（brief）・レビュー役3種と自己点検役（ゲーム ID とパズル名） |
| brief | 識別表、合意節の写し、作業ディレクトリ、worktree のパス、手本にする直近のパズル | 実装役（起動時と、合意節が変わったとき） |
| 作業カード | 作る順番の項目と範囲・完成条件（`references/research.md` の「作る順番」）、開発サーバーのポート、その項目に効く失敗パターン。直しでは直す所見。spec では ADR にする判断と使う番号 | 実装役（項目と直しごと） |
| 観点カード | 観点と問い（`references/research.md` の「調査役の分担」）、書いてよいパス | 調査役 |
| 範囲ファイル | 確かめる範囲と完成条件（作り込みでは全体） | レビュー役3種・自己点検役 |
| 合意ファイル | 合意節の写し（合意と人間の判断） | 調査役・レビュー役3種・自己点検役 |
| レビュー版の worktree | 確かめる版。作業ブランチを checkout せずに作る | レビュー役3種・自己点検役 |
| 差分と変更ファイル一覧 | 山場1と作り込みの1巡目は main から、2巡目からは前回のレビュー版から | コードレビュー役（差分と一覧）・文書レビュー役（一覧） |
| 画面 | 対象の画面と比較用の既存ゲームの同じ画面（メインが `playtest-driver.mjs` の goto と shot で撮り、画面名・端末つきの一覧にする）と browser-errors.log | 体験レビュー役・自己点検役 |
| 文書の場所と使用中の番号 | SPEC・導入調査・台帳のパス、origin の全ブランチで使われている SPEC・候補 ID・ADR の番号の一覧 | 文書レビュー役 |
| 難易度の計測 | `/design-game-difficulty` の検査の結果（レベルごとの分布・素朴な解き方の結果） | 自己点検役 |
| 試遊の入力 | アプリの URL（メインが起動した開発サーバー）、入口パス（一覧に載る前は、実装役が報告したレベルごとのプレイ画面のパス）、端末、遊ぶレベル、出力先、driver のポート（端末ごとに重ならないもの）、まだ作っていない画面・機能、比較用の既存ゲーム（作り込み） | 試遊役 |
| 失敗パターン集 | この Skill の `references/pitfalls.md` の絶対パス。自己点検役には、当てる「いつ」の一覧と、作り方の Skill の集（`/design-game-difficulty` と `/design-game-difficulty-preview` の `references/pitfalls.md`）の絶対パスも | 調査役・実装役・体験レビュー役・自己点検役 |

## 実行役

- 調査: `puzzle-researcher` を観点ごとに1つ。
- 実装と直し: `puzzle-implementer` を1つに通す。作業カードの項目に作り方の Skill があれば、実装役がその中で起動する（difficulty・problem-pool は `/design-game-difficulty`、difficulty-select は `/design-game-difficulty-preview`、pictogram は `/design-game-pictogram`、spec の ADR は `/adr-create <タイトル>`）。新しい実装役に代えるのは文脈の上限が近いときだけで、引き継ぎは「記録」と作業カードで行う。
- 試遊: `puzzle-playtester`。山場1は iphone、山場2は iphone でレベル1〜5の各1問、作り込みは iphone と pc でレベル1〜5の各1問。
- AI レビュー: `puzzle-code-reviewer`（山場1・作り込み）、`puzzle-experience-reviewer`（作り込み）、`puzzle-document-reviewer`（調査・作り込み）。
- 自己点検: `puzzle-pitfall-checker`（山場2・作り込み）。「確かめられない」の行はメインが測る。
- 失敗パターン集の配り方: 行は「いつ」で配る。作る順番の項目か「全項目」の行は、その項目の作業カードへ（research の行は調査役へ）。工程（認識合わせ・実装・作り込み・反映・最終レビュー）の行は、メインがその工程で当てる。自己点検役に渡す「いつ」は、山場2では difficulty と problem-pool、作り込みの1巡目では作る順番の項目すべてと「全項目」。体験レビュー役には絶対パスだけを渡す。
- 確かめの役（試遊・自己点検・レビュー3種）は入力が互いに独立しているので、同時に起動してよい。
- この Skill のスクリプトは `scripts/playtest-driver.mjs`（試遊と撮影のための常駐ブラウザ。使い方は冒頭）だけ。

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューのどれにも当てはめる。

- 結論から書く。最初の1〜2行で、何ができたかと、何をしてほしいか。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。`/tmp` のパスや、説明の無い内部用語を使わない。
- 案を記号だけで呼ばず、中身で説明する。難易度の案は、判定に使うつまみと利用者向けの一言で示す。
- 推奨を既定にする。推奨の理由は、このパズルで何が良くなるかを具体的に書き、不利な点も並べる。

## 参照する正本

- ゲームとUIの決まり: `GAME.md`、`APP.md`、`DESIGN.md`、`.claude/rules/game-structure.md`（依存方向は PR の切り方の根拠）
- 文書の置き場所と書き方: `docs/README.md`
- 導入調査: `docs/パズル/導入調査/<パズル名>/`
- 難易度の決まり: `docs/パズル/README.md` から辿る難易度文書
- 候補台帳: `docs/棚上げ/パズル候補.csv` と `docs/棚上げ/パズル候補/PUZZLE-nnn.md`
- 仕様: `docs/プロダクト/仕様/パズル/SPEC-nnn.md`

## 環境

- サブエージェントは入れ子で起動できない。確かめの役の起動と所見の振り分けはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う（GraphQL を使う `gh` は失敗する）。
- この環境からプレビュー URL は開けない。描画は手元の開発サーバーで確かめ、そう書く。
- 並行で重い処理を流すと、変更と無関係な既存テストが時間切れで落ちることがある。そのファイルだけを流し直して確かめてから進める。
