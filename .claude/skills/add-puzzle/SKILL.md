# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 判断はすべて、そのパズルならではの面白さを強めるかで決める（`GAME.md`）。難易度・点数・操作・見た目はそのための手段で、手段の量（指標・採用率・所要時間）だけを理由に要素や作りを削らない。
2. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせ（push できる環境の用意を含む）と「成り立たない」の2つ。
3. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
4. 認識合わせは、指示が伝わったかの確認。AI が思い描いているパズルを、触れる見本と図で見せる。方針を決めてもらう場にしない。
5. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
6. 書く役は1つに通し、見る役は使い捨てにする。実装は1本の作業ブランチで1つの実装役が続けて行い、確かめは経緯を渡さない役に毎回新しく頼む。
7. PR は人間に渡す単位で、作る・確かめる単位ではない。作り切ってから、完成した木を依存の層で PR に切り出す。
8. 人間のマージが本決定。マージ後の変更は新しい改善。確かめていないことを確認済みと書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`）。合意と許可を得たら、作業ブランチを作り、push できることを確かめる（`references/research.md` の「作業ブランチ」）。push できなければ、できるようにしてほしいことを頼んで待つ。
2. 調査（`references/research.md`）。導入調査 Issue に合意と許可を記録し、識別表で番号を予約し、観点ごとの調査役の結果を実装前提調査にまとめ、文書レビューを通して push する。難易度は、ここで案を広げて比べてから1つに決める。
3. 実装。実装役を1つ起動し、作る順番の項目ごとに作業カードを渡して、同じ実装役に続けて頼む（SendMessage）。山場1と山場2で「確かめ」の表の確かめを回し、所見を振り分ける。ここで覆ると上を全部作り直すので、この2つだけは作り切る前に確かめる。
4. 品質の作り込み。全部そろった版を決めて実装役に確かめの準備をさせ、「確かめ」の表の作り込みの確かめを当て、所見を振り分けて直しの作業カードを渡し、記録を残す。直しは機械検査で確かめる。止め時は次のすべて。
   - 「直す」に振った所見をすべて直し、機械検査が通っている。
   - 自己点検の「確かめられない」の行は、メインが測ってから振り分けた。
5. PR への切り出し（`references/research.md` の「PR の切り方」）。完成した作業ブランチを層ごとに切り出し、漏れと main との衝突を確かめて push し、PR を積む。
6. 最終レビュー（`references/final-review.md`）。指摘は作業ブランチで直し、「確かめ」の表の最終レビューの反映の確かめと機械検査を通して、5 で切り出し直す。

## 確かめ

確かめの役には経緯を渡さず、互いに独立なので同時に起動してよい。機械検査は `verify.sh`（CI の制限時間内に収まること）と問題集の `--verify`。難易度の判定を変えたときは、難易度の計測（難易度の Skill の `references/checks.md` のうち機械で測るもの）も流す。

| 時点 | 試遊 | 自己点検 | コード | 体験 | 文書 |
|---|---|---|---|---|---|
| 調査の後 | — | — | — | — | ○ |
| 山場1（rules・playable） | iphone で入口の1問 | — | ○ | — | — |
| 山場2（difficulty・problem-pool） | iphone で難易度の Skill の「試遊に渡す問題」 | ○（頼まれた解法器の確かめを含む） | — | — | — |

## 所見の振り分け

試遊・自己点検・AI レビュー・機械検査の所見と、作り方の Skill の報告の「人間に残す候補」・別案を、役を問わずすべて1つに振る。

- 直す: 成果物を変えるもの。変えるなら必ずここに振る。
- AI が決める: 欠陥ではなく、合意した意図の範囲の設計判断への異論だった所見。今の作りを理由つきで採り、確かめの記録に書く。
- 人間に残す: 面白さ・好み、計測で裏付けられない難易度の体感・時間とスコアの水準、合意か正本の制約のために直せないもの（どの制約かを添える）。最終レビュー資料へ置く。

Critical・Major は「直す」か「人間に残す」のどちらかで、Minor は直さなければ最終レビュー資料の「まだ確かめていないこと」へ置く。レビュー役の「規約で確定できる論点」は「直す」。

難易度の判定（つまみと境目）は山場2で決め切る。その後に変えるのは、機械で確かめられる違反（隣のレベルの逆転、状態の混同、解法器の誤り、数え方の変種でレベルが変わる率の超過など）があるときだけ。AI の試遊の体感や「重なりそう」という見込みだけの所見は、計測で同じずれが出なければ「人間に残す」。

## 作り方の Skill との受け渡し

実装役は、作業カードの項目に作り方の Skill があれば中で起動する（項目との対応は `references/research.md` の「作る順番」）。Skill は報告を作業ディレクトリの `<Skill 名>-report.md` に書き、メインが読む。報告の「頼むこと」と「試遊に渡す問題」は所見ではないので振り分けず、「確かめ」の表の役か作業カードに渡し、要点を確かめの記録に写す。

## 記録

- 導入調査 Issue の合意節: 識別表の写し、認識合わせのページの URL と人間の返事、許可、人間の判断、最終レビュー資料の URL、人間の指摘の原文。
- 導入調査 Issue の確かめの記録: 調査の後・山場・作り込み・最終レビューの反映ごとにコメントを1つ。対象の版のコミット、起動した確かめ、所見と振り分け、直したコミット、AI が決めたこと、作り方の Skill の報告の要点。止め時の判定はここから行う。
- 実装前提調査: 識別表・仮決定一覧・作る順番・PR の切り方。別案と実装役が決めたことはメインが仮決定一覧に書き、止め時を満たした後に「実装で確定した差分」を足す。
- 切り出した PR の本文: その層の範囲、その層に関わる「AI が決めたこと」、確かめたこと（確かめの記録への参照）、残した所見、マージの順。

## 再開

作業ディレクトリのファイルは消えている前提で進む。

1. 識別表の接頭辞と導入調査 Issue（題 `導入調査: <パズル名>`）を探し、確かめの記録・作業ブランチ・実装前提調査から進み具合を判定する。
2. `git worktree prune` の後に、`git worktree add <作業ディレクトリ>/work -B <接頭辞>/work origin/<接頭辞>/work` で worktree を作り直す。
3. brief を合意節から、引き継ぎファイルを確かめの記録と作業ブランチの履歴から作り直し、新しい実装役に渡す。
4. 作業ディレクトリにしか無かった確かめの入力は、次の確かめの準備で作り直す。

## 実行役

- 調査: `puzzle-researcher` を観点ごとに1つ。
- 実装と直し: `puzzle-implementer` を1つに通す。代えるのは SendMessage が失敗したときか、報告が前に決めたことを落とし始めたときだけで、引き継ぎファイルを渡す。
- 試遊: `puzzle-playtester`。
- 自己点検: `puzzle-pitfall-checker`。
- AI レビュー: `puzzle-code-reviewer`・`puzzle-experience-reviewer`・`puzzle-document-reviewer`。
- ページの読み手: 汎用サブエージェント（Opus）を使い捨てで1つ。認識合わせのページか最終レビュー資料だけを渡す（`references/alignment.md` の「見せるページ」、`references/final-review.md` の「資料」）。
- 失敗パターン集の配り方（ここが正本）:
  - この Skill の `references/pitfalls.md` は行の「いつ」で配る。作る順番の項目か「全項目」の行はその項目の作業カードへ（research の行は調査役へ）、工程の行はメインがその工程で当てる。
  - `/design-game-difficulty` の集は全行を difficulty・problem-pool の行として扱う。
  - 自己点検役に渡す「いつ」は、山場2では difficulty・problem-pool と「全項目」、作り込みでは difficulty・problem-pool を除く全項目（山場2の後に難易度の判定を変えたときは含める）。
  - 体験レビュー役には、この Skill の集の「プレイUI・見た目」の節を渡す。
- スクリプトは `scripts/playtest-driver.mjs`（試遊と撮影のための常駐ブラウザ。使い方は冒頭）だけ。

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューは、経緯を知らない人間がスマホで空き時間に見るものとして作る。読ませる文書ではなく、見て動ける画面にする。見本は `assets/alignment-sample.html` と `assets/final-review-sample.html`。

- 構成は人間のやることの順に並べる（最終レビューなら、遊ぶ → 答える → マージ）。AI の作業の区分（確かめの記録・所見・振り分け・調査の観点）では並べない。最初に、何をすればよいかと、どれだけかかるかを見せる。
- 答えてほしいことは問いの形で書き、選択肢を並べて見比べられるようにする。おすすめに印を付け、それぞれの良い点・悪い点と、変えたときの手戻りを1行で添える。返事がなければおすすめで進むと書く。
- 答えなくてよい参考（AI が決めたこと、変えたこと、確かめていないことなど）は、件数を見せて畳む。
- 日本語は、人が口で言う短い言い回しにする。1文に1つのこと。名詞を連ねた造語や、AI の作業用語（推奨・仮決定・所見・合意など）を使わない。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。ページの見た目は Vercel の Geist に寄せ、`assets/page.css` の中身を `<style>` に入れて使う。

## 参照する正本

- ゲームとUIの決まり: `GAME.md`、`APP.md`、`DESIGN.md`、`.claude/rules/game-structure.md`（依存方向は PR の切り方の根拠）
- 文書の置き場所と書き方: `docs/README.md`
- 導入調査: `docs/パズル/導入調査/<パズル名>/`
- 難易度の決まり: `docs/パズル/README.md` から辿る難易度文書

## 環境

- サブエージェントは入れ子で起動できない。確かめの役の起動と所見の振り分けはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う。
- この環境からプレビュー URL は開けない。描画は手元の開発サーバーで確かめ、そう書く。
- アプリは今ダーク表示に切り替えないので、ダークは確かめる範囲から外す。
