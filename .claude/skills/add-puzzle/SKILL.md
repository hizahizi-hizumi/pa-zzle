# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 判断はすべて、そのパズルならではの面白さを強めるかで決める（`GAME.md`「目指すゲーム」）。難易度・点数・操作・見た目・音はそのための手段で、手段の量（指標・採用率・所要時間）だけを理由に要素や作りを削らない。
2. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせ（push できる環境の用意を含む）と「成り立たない」の2つ。
3. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
4. 認識合わせは、指示が伝わったかの確認。AI が思い描いているパズルを、触れる見本と図で見せる。方針を決めてもらう場にしない。
5. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
   - 合意に無いルールの要素（床・駒・手がかりの種類など）を足すのも、そのパズルならではの面白さを強め、核（何を考えるゲームか）を変えないなら、この範囲に入る。足したら作り切り、最終レビューの最初の問いで、要素なしの場合と比べて聞く。
   - 核を変えないと成り立たないなら「成り立たない」で知らせる。
6. 書く役は1つに通し、見る役は使い捨てにする。実装は1本の作業ブランチで1つの実装役が続けて行い、確かめは経緯を渡さない役に毎回新しく頼む。
7. PR は人間に渡す単位で、作る・確かめる単位ではない。作り切ってから、完成した木を依存の層で PR に切り出す。
8. 人間のマージが本決定。マージ後の変更は新しい改善。確かめていないことを確認済みと書かない。

## 流れ

1. `references/alignment.md` を読み、認識合わせをする。合意と許可を得たら、`references/branches.md` の「作業ブランチ」を読んで作業ブランチを作り、push できることを確かめる。push できなければ、できるようにしてほしいことを頼んで待つ。
2. `references/research.md` を読み、調査する。導入調査 Issue に合意と許可を記録し、識別表で番号を予約し、観点ごとの調査役の結果を実装前提調査にまとめ、文書レビューを通して push する。難易度は、ここで案を広げて比べてから1つに決める。
3. 実装する。実装役を1つ起動し、作る順番の項目ごとに作業カードを渡して、同じ実装役に続けて頼む（SendMessage）。山場1と山場2で「確かめ」の表の確かめを回し、所見を振り分ける。ここで覆ると上を全部作り直すので、この2つだけは作り切る前に確かめる。後の項目の作業中に前の項目を直すときは、今の項目を区切りのよい所までコミットさせてから直しの作業カードを渡し、終わったら元の項目の続きの作業カードを渡す。
4. 品質を作り込む。全部そろった版を決め、「確かめ」の確かめの準備をしてから、表の作り込みの確かめを当てる。所見を振り分けて直しの作業カードを渡し、記録を残す。直しは機械検査で確かめる。止め時は次のすべて。
   - 「直す」に振った所見をすべて直し、機械検査が通っている。
   - 自己点検の「確かめられない」の行は、メインが測ってから振り分けた。この環境で測れないもの（iOS Safari の挙動など）は「人間に残す」に振った。
5. `references/branches.md` の「PR の切り方」を読み、PR に切り出す。完成した作業ブランチを層ごとに切り出し、漏れと main との衝突を確かめて push し、PR を積む。
6. `references/final-review.md` を読み、最終レビューをして指摘を反映する。

## 確かめ

- 確かめの役には経緯を渡さず、同時に起動する。前の確かめで振り分けた所見は「既知の所見」として渡し、同じ所見を振り分け直さない。
- 試遊用の開発サーバーは、メインが確かめる版の worktree で起動し、その時点の確かめが終わったら止める。
- 機械検査: `scripts/verify.sh` を流して `.github/workflows/quality-gate.yml` の `timeout-minutes` に収まることを確かめ、問題集の `--verify` を流す。
- 確かめの準備: 作り込みの版を決めたときと、山場2の後に難易度の判定を変えたときに、実装役に確かめの準備の作業カードを渡す。実装役に `/design-game-difficulty` を入口「`/add-puzzle` の確かめの準備」で起動させて難易度の計測を流させ、できた `difficulty-checks.md` を読む。

## 所見の振り分け

試遊・自己点検・AI レビュー・機械検査の所見と、作り方の Skill の報告の「人間に残す候補」・別案を、役を問わずすべて1つに振る。

- 直す: 成果物を変えるもの。変えるなら必ずここに振る。
- AI が決める: 欠陥ではなく、合意した意図の範囲の設計判断への異論だった所見。今の作りを理由つきで採り、確かめの記録に書く。
- 人間に残す: 面白さ・好み、計測で裏付けられない難易度の体感・時間とスコアの水準、合意か正本の制約のために直せないもの（どの制約かを添える）。最終レビュー資料へ置く。

Critical・Major は「直す」か「人間に残す」のどちらかで、Minor は「直す」か「AI が決める」（直さない理由を書く）のどちらか。レビュー役の「規約で確定できる論点」は「直す」。

難易度の判定（つまみと境目。特徴の定義を含む）は山場2で決め切る。その後に変えるのは、`/design-game-difficulty` が書いた `difficulty-checks.md` で検査が「当たる」になったときと、最終レビューで人間が難易度を指摘したときだけ。それ以外の難易度の所見（AI の試遊の体感など）は「人間に残す」。難易度の範囲の所見を直しの作業カードに載せるときは、判定を変えてよいかをこの決まりで決めて書く。判定を変えたら、山場2の中でも、変えた版に独立した確かめ（`/design-game-difficulty` の報告が頼む A4。F1 で見つかった変更なら F1 も）と自己点検を当て直す。

## 作り方の Skill との受け渡し

作業カードを作る前に `references/build-order.md` を読み、その項目の作り方の Skill を作業カードに書く。実装役はそれを中で起動する。Skill は報告を作業ディレクトリの `<Skill 名>-report.md` に書き、メインが読む。報告の「頼むこと」と「試遊に渡す問題」は所見ではないので振り分けず、「確かめ」の表の役か作業カードに渡し、要点を確かめの記録に写す。

`/add-puzzle` 向けの入口が無い Skill（`/design-game-pictogram-showcase`・`/adr-create`）では、実装役は人間に聞く段とサブエージェントを起動する段で止まり、報告の「メインに頼むこと」に書いて返す。実装役の報告の「メインに頼むこと」のうち、起動してほしい役（`showcase-pictogram-reviewer` など）はメインが起動し、結果を続きの作業カードで渡す。人間に聞く・選んでもらう段は、メインが合意した意図の範囲で推奨を選んで続きの作業カードに書き、最終レビューの「答える」に回す。

## 記録

- 導入調査 Issue の合意節: 識別表の写し、認識合わせのページの URL と人間の返事、許可、人間の判断、最終レビュー資料の URL、人間の指摘の原文。
- 導入調査 Issue の確かめの記録: 調査の後・山場・作り込み・最終レビューの反映ごとにコメントを1つ。対象の版のコミット、起動した確かめ、所見と振り分け、直したコミット、AI が決めたこと、作り方の Skill の報告の要点。止め時の判定はここから行う。
- 実装前提調査: `references/research.md` の「実装前提調査の節」。別案と実装役が決めたことはメインが仮決定一覧に書く。
- 切り出した PR の本文: その層の範囲、その層に関わる「AI が決めたこと」、確かめたこと（確かめの記録への参照）、残した所見、マージの順。

### 作業カード

どの作業カードにも、作る順番の項目と範囲・完成条件、その項目の作り方の Skill（あれば）、worktree、開発サーバーと driver のポート、その項目に効く失敗パターン、出発点（引き継ぐときの既存のブランチとパス）を書く。カードの種類ごとに次を足す。

- difficulty・problem-pool の項目と、難易度の範囲の直し: 合意に無いルールの要素を足してよい条件と、足したときの扱い（原則 5）。
- 直し: 直す所見とその項目。難易度の範囲の直しでは、難易度の判定を変えてよいか（「所見の振り分け」）。
- main への追従: `references/resume.md` の「main への追従の作業カード」の中身。
- spec: 仕様に移す決まりとその意図（仮決定一覧と確かめの記録の「AI が決めたこと」から）、難易度の資料の SPEC の難易度の節の案、ゲームをまたぐ判断があればそれ。
- 確かめの準備: 確かめる版。

## 実行役

- 調査: `puzzle-researcher` を観点ごとに1つ。
- 実装と直し: `puzzle-implementer` を1つに通す。代えるのは SendMessage が失敗したときか、報告が前に決めたことを落とし始めたときだけで、引き継ぎファイルを渡す。
- 試遊: `puzzle-playtester`。
- 自己点検: `puzzle-pitfall-checker`。
- AI レビュー: `puzzle-code-reviewer`・`puzzle-experience-reviewer`・`puzzle-document-reviewer`。
- ピクトグラムのレビュー: `showcase-pictogram-reviewer`（実装役の報告が頼んだとき）。
- 独立した確かめ（`/design-game-difficulty` の検査 F1・A4）: 汎用サブエージェント（Opus）を、確かめごとに使い捨てで新しく1つ。渡すのは、`/design-game-difficulty` の報告（調査では難易度の観点の結果）の「頼むこと」にある物だけ。
- ページの読み手: 汎用サブエージェント（Opus）を、ページごとに使い捨てで新しく1つ。経緯を渡さず、認識合わせのページか最終レビュー資料だけを渡す。返させる中身は `references/alignment.md` の「見せるページ」と `references/final-review.md` の「資料」に従う。
- 試遊と撮影には `${CLAUDE_SKILL_DIR}/scripts/playtest-driver.mjs`（常駐ブラウザ）を使い、起動する前に冒頭の使い方を読む。この Skill のスクリプトはこれだけ。

## 失敗パターン集の配り方

- この Skill の `references/pitfalls.md` は行の「いつ」で配る。作る順番の項目か「全項目」の行はその項目の作業カードへ（research の行は調査役へ）。認識合わせの行はメインが認識合わせで当てる。作り込みの行は下の範囲で確かめの役に渡す。
- 難易度と問題の質の集 `${CLAUDE_PROJECT_DIR}/.claude/skills/share/difficulty-pitfalls.md` は、全行を difficulty・problem-pool の行として扱う。
- 実装役には、起動時に集ごとの絶対パスを渡す。
- 確かめの役には、集ごとに絶対パスと当てる範囲（「いつ」の一覧か、全行か）を入力で渡す。役は渡された範囲の行だけを当てる。
  - 自己点検役: 山場2では、この Skill の集の「全項目」の行と、難易度と問題の質の集の全行。作り込みでは、この Skill の集の全行（山場2の後に難易度の判定を変えたときは、難易度と問題の質の集の全行も）。
  - 体験レビュー役: この Skill の集の play-ui・sound・作り込みの行。

## 人間への知らせ方

認識合わせのページ・「成り立たない」の知らせ・最終レビュー資料を作る前に、`${CLAUDE_PROJECT_DIR}/.claude/skills/share/human-notice.md` を読んで従い、そこで使う `${CLAUDE_PROJECT_DIR}/.claude/skills/share/page.css` を使う。認識合わせのページは `assets/alignment-sample.html` を、最終レビュー資料は `assets/final-review-sample.html` を複製して作る（page.css の入れ方は human-notice.md に従い、雛形の page.css の `<link>` はそれで置き換える）。

## 参照する正本

観点カード・作業カードを作る前と、所見を振り分ける前に、関わるものを読む。

- ゲームとUIの決まり: `GAME.md`、`APP.md`、`DESIGN.md`、画面の文書 `docs/プロダクト/画面/`、`.claude/rules/game-*.md`（「依存方向」は PR の切り方の根拠）
- 文書の置き場所と書き方: `.claude/rules/documents.md`。導入調査・台帳・仕様を書く前に読む
- 導入調査: `docs/パズル/導入調査/<パズル名>/`
- 難易度の決まり: `docs/パズル/README.md` から辿る難易度文書
- 候補台帳: `docs/棚上げ/パズル候補.csv` と `docs/棚上げ/パズル候補/PUZZLE-<番号>.md`
- 仕様: `docs/プロダクト/仕様/パズル/SPEC-<番号>.md`
