# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間とやり取りするのは、着手時の認識合わせと、作り切った後の最終レビューだけ。途中経過は送らない（人間は見ない）。
2. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる（他ブランチ・PR で同じパズルが進んでいないかも確かめる）。
3. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、資料に書く。止まるのは合意したパズルが成り立たないと分かったときだけで、理由と代案（推奨つき）を示す。
4. 人間には、作り切って、遊ぶ側の目線で確かめ、判断しやすくしたものだけを見せる。
5. 人間のマージが本決定。マージ後の変更は新しい改善。
6. 確かめていないことを確認済みと書かない。サブエージェントの報告だけで「見た」と書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`）。返事を待つのはここだけ。
2. 調査: 問題供給・難易度・スマホ操作・導入判断が合意の範囲で成り立つかを観点ごとに並行で確かめ、仮決定と段の並びを決める。
3. 実装: 段ごとに実装役を起動して確かめ、段の PR を前段の上に積む。
4. 品質の作り込み: 機械検査・試遊・AI レビュー・`references/pitfalls.md` の自己点検を、直すべき指摘が無くなるまで回す。直しは原因の段に入れて上を積み直す。
5. 最終レビュー（`references/final-review.md`）。指摘を反映したら 4 からやり直す。指摘のうち他のパズルにも当てはまるものは、守る決まりとして正本（`GAME.md`・`DESIGN.md` 等）か `references/pitfalls.md` への追記を同じスタックに入れ、マージで人間に決めてもらう。AI レビューが拾えるのは書かれた決まりの範囲だけなので、これが次のパズルで同じ指摘を出させない唯一の仕組みになる。

全サブエージェントに合意と人間の判断を渡す。レビュー役と試遊役には経緯を渡さない。状態は Issue・PR 本文・導入調査の文書に置き、再開時はそこから進み具合を判定する。

## 実行役

- 段の実装・直し: `puzzle-stage-implementer`
- 試遊（遊べる段で軽く、作り込みで必ず）: `puzzle-playtester`
- AI レビュー（段ごと・作り込み）: `puzzle-code-reviewer`・`puzzle-experience-reviewer`・`puzzle-document-reviewer`
- ピクトグラム: `/design-game-pictogram`。理由を残す判断: `/adr-create`
- この Skill の `scripts/`: `list-used-ids.sh`（調査開始時の番号予約と SPEC 直前の衝突確認）、`restack.sh`（直した後の積み直し、知らせる前に main と衝突していたときの rebase）、`capture-screens.mjs`（撮影とブラウザエラー確認）、`playtest-driver.mjs`（試遊役が使う）、`naive-play-core.ts`（素朴なプレイヤーで各レベルを解かせる検査。ゲームごとのアダプタは `examples/naive-play-*.ts` を手本に書く。最上位を補助ありの素朴なプレイヤーがほぼ必ず・最短に近い手数で解くなら「簡単すぎる」候補。素朴なプレイヤーが苦労しても熟練者に難しいとは限らないので、止める向きにだけ使う）

## 環境

- サブエージェントは入れ子で起動できない。実装 → レビュー → 直しはメインが回す。
- GraphQL を使う `gh pr`（`/pr` Skill も）は失敗する。GitHub MCP か `gh api` の REST を使う。
