# add-puzzle

`/add-puzzle <パズル名> [最終レビューの指摘]`

新しいパズルを main へのマージまで運ぶ。限られているのは人間の時間で、AI の作り直しは安い。

## 原則

1. 人間に知らせるのは、着手時の認識合わせ、合意したパズルが成り立たないと分かったとき（理由と、推奨つきの代案を添える）、作り切った後の最終レビューの3つだけ。返事を待つのは認識合わせ（push できる環境の用意を含む）と「成り立たない」の2つ。
2. 遊びの欠陥（抜け道・レベル差・近道・計測の誤り）を見つけるのは試遊と自己点検で、AI レビューは作法と契約の逸脱を見る。
3. 認識合わせは時間より確かさ。覆ると大きな作り直しになる前提をはっきりさせる。
4. 途中で止まらない。迷ったら合意した意図の範囲で決めて進み、決めたことを残す（「記録」）。
5. 書く役は1つに通し、見る役は使い捨てにする。実装は1本の作業ブランチで1つの実装役が続けて行い、確かめは経緯を渡さない役に毎回新しく頼む。
6. PR は人間に渡す単位で、作る・確かめる単位ではない。作り切ってから、完成した木を依存の層で PR に切り出す。
7. 人間のマージが本決定。マージ後の変更は新しい改善。確かめていないことを確認済みと書かない。

## 流れ

1. 認識合わせ（`references/alignment.md`、文面の見本は `assets/alignment-sample.md`）。合意と許可を得たら、作業ブランチを作り、push できることを確かめる（`references/research.md` の「作業ブランチ」）。push できなければ、できるようにしてほしいことを頼んで待つ。
2. 調査（`references/research.md`）。導入調査 Issue に合意と許可を記録し、識別表で番号を予約し、観点ごとの調査役の結果を実装前提調査にまとめ、文書レビューを通して push する。
3. 実装。実装役を1つ起動し、作る順番の項目ごとに作業カードを渡して、同じ実装役に続けて頼む（SendMessage）。山場1と山場2で「確かめ」の表の確かめを回し、所見を振り分ける。ここで覆ると上を全部作り直すので、この2つだけは作り切る前に確かめる。
4. 品質の作り込み。巡ごとに、確かめる版を決めて実装役に確かめの準備をさせ、「確かめ」の表の確かめを当て、所見を振り分けて直しの作業カードを渡し、巡の記録を残す。止め時は次のすべて。
   - 機械検査が通り、作業ブランチのプレビュー URL が出ている。
   - 直しを入れた後の版に当てた巡で、「直す」が0件。
   - 自己点検の「確かめられない」の行は、メインが測ってから振り分けた。
5. PR への切り出し（`references/research.md` の「PR の切り方」）。完成した作業ブランチを層ごとに切り出し、各層で `verify.sh` を通し、漏れと main との衝突を確かめて push し、PR を積む。
6. 最終レビュー（`references/final-review.md`、資料の見本は `assets/final-review-sample.md`）。指摘は作業ブランチで直して 4 の止め時を満たし、5 で切り出し直す。

## 所見の振り分け

試遊・自己点検・AI レビュー・機械検査の所見と、作り方の Skill の報告の「人間に残す候補」・別案を、役を問わずすべて1つに振る。

- 直す: 成果物を変えるもの。変えるなら必ずここに振る。
- AI が決める: 欠陥ではなく、合意した意図の範囲の設計判断への異論だった所見。今の作りを理由つきで採り、巡の記録に書く。
- 人間に残す: 面白さ・好み、計測で裏付けられない難易度の体感・時間とスコアの水準、合意か正本の制約のために直せないもの（どの制約かを添える）。最終レビュー資料へ置く。

Critical・Major は「直す」か「人間に残す」のどちらかで、Minor は直さなければ資料の「未確認」へ置く。レビュー役の「規約で確定できる論点」は「直す」。同じ所見が直した後も2巡続けて出たら、直し方を変えるか、直せない理由を添えて「人間に残す」へ移す。

## 作り方の Skill との受け渡し

実装役は、作業カードの項目に作り方の Skill があれば中で起動する（項目との対応は `references/research.md` の「作る順番」）。Skill は報告を作業ディレクトリの `<Skill 名>-report.md` に書き、メインが読む。報告の「頼むこと」と「試遊に渡す問題」は所見ではないので振り分けず、「確かめ」の表の役か作業カードに渡し、要点を巡の記録に写す。

## 記録

- 導入調査 Issue の合意節: 識別表の写し、合意・許可・人間の判断、最終レビュー資料の URL、人間の指摘の原文。
- 導入調査 Issue の巡の記録: 山場と作り込みの巡ごとにコメントを1つ。対象の版のコミット、起動した確かめ、所見と振り分け、直したコミット、AI が決めたこと、作り方の Skill の報告の要点。止め時と2巡の判定はここから行う。
- 実装前提調査: 識別表・仮決定一覧・作る順番・PR の切り方。別案と実装役が決めたことはメインが仮決定一覧に書き、止め時を満たした後に「実装で確定した差分」を足す。
- 切り出した PR の本文: その層の範囲、その層に関わる「AI が決めたこと」、確かめたこと（巡の記録への参照）、残した所見、マージの順。

## 再開

作業ディレクトリのファイルは消えている前提で進む。

1. 識別表の接頭辞と導入調査 Issue（題 `導入調査: <パズル名>`）を探し、巡の記録・作業ブランチ・実装前提調査から進み具合を判定する。
2. `git worktree prune` の後に、`git worktree add <作業ディレクトリ>/work -B <接頭辞>/work origin/<接頭辞>/work` で worktree を作り直す。
3. brief を合意節から、引き継ぎファイルを巡の記録と作業ブランチの履歴から作り直し、新しい実装役に渡す。
4. 作業ディレクトリにしか無かった確かめの入力は、次の巡の確かめの準備で作り直す。

## 実行役

- 調査: `puzzle-researcher` を観点ごとに1つ。
- 実装と直し: `puzzle-implementer` を1つに通す。代えるのは SendMessage が失敗したときか、報告が前に決めたことを落とし始めたときだけで、引き継ぎファイルを渡す。
- 試遊: `puzzle-playtester`。
- 自己点検: `puzzle-pitfall-checker`。
- AI レビュー: `puzzle-code-reviewer`・`puzzle-experience-reviewer`・`puzzle-document-reviewer`。
- 読まれ方: 汎用サブエージェント（Opus）を使い捨てで1つ。手順は `/design-game-difficulty-preview` の `references/checks.md` の「読まれ方の確かめ」。メインが見本の名前を付け直して順を伏せ、正解の順はメインだけが持つ。当たれば Major の所見にする。
- 資料の読み手: 汎用サブエージェント（Opus）を使い捨てで1つ。最終レビュー資料だけを渡す（`references/final-review.md` の「仕上げ」）。
- 失敗パターン集の配り方（ここが正本）:
  - この Skill の `references/pitfalls.md` は行の「いつ」で配る。作る順番の項目か「全項目」の行はその項目の作業カードへ（research の行は調査役へ）、工程の行はメインがその工程で当てる。
  - `/design-game-difficulty` の集は全行を difficulty・problem-pool の行、`/design-game-difficulty-preview` の集は全行を difficulty-select の行として扱う。
  - 自己点検役に渡す「いつ」は、山場2では difficulty・problem-pool と「全項目」、作り込みの1巡目では全項目すべて、2巡目からは直しの作業カードの項目と「全項目」。
  - 体験レビュー役には、この Skill の集の「プレイUI・プレビュー・見た目」の節と、プレビューの集を渡す。
- スクリプトは `scripts/playtest-driver.mjs`（試遊と撮影のための常駐ブラウザ。使い方は冒頭）だけ。

## 人間への知らせ方

認識合わせ・「成り立たない」・最終レビューのどれにも当てはめる。

- 結論から書く。最初の1〜2行で、何ができたかと、何をしてほしいか。
- 文ではなく短い句で書く。1項目1〜2行。表はスマホで潰れない3列までにする。前置きと注記を書かない。
- 人間が開ける形（Artifact、プレビュー URL、画像）だけを渡す。`/tmp` のパスや、説明の無い内部用語を使わない。
- 案を記号だけで呼ばず、中身で説明する。難易度の案は、判定に使うつまみと利用者向けの一言で示す。
- 推奨を既定にする。推奨の理由は、このパズルで何が良くなるかを具体的に書き、不利な点も並べる。

## 参照する正本

- ゲームとUIの決まり: `GAME.md`、`APP.md`、`DESIGN.md`、`.claude/rules/game-structure.md`（依存方向は PR の切り方の根拠）
- 文書の置き場所と書き方: `docs/README.md`
- 導入調査: `docs/パズル/導入調査/<パズル名>/`

## 環境

- サブエージェントは入れ子で起動できない。確かめの役の起動と所見の振り分けはメインが回す。
- GitHub の操作は GitHub MCP か `gh api` の REST で行う。
- この環境からプレビュー URL は開けない。描画は手元の開発サーバーで確かめ、そう書く。
- アプリは今ダーク表示に切り替えないので、ダークは確かめる範囲から外す。
