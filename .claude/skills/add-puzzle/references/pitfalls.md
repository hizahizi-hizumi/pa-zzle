# 失敗パターン集

過去のパズル追加で、人間に指摘されてから直したもの。各行は「兆候 → 予防（いつ・何で確かめるか）」。段の実装担当にはその段に効く領域を渡す。品質の作り込みでは、経緯を渡さないサブエージェントに全行を当てさせ、「当たらない（根拠）／当たる（どこで）／確かめられない（なぜ）」を付けさせる。

「いつ」は前例のスタックの段の名前で書く: rules・playable・play-ui・difficulty・problem-pool・pictogram・difficulty-select・score・result-records・spec。

## 面白さ・問題の質

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 核の取り違え | 人間と AI が違うパズルを想像している。ルールの核が最終レビューで覆る | 認識合わせ: ルール・挑戦の1文・近縁との違いを示し、必要なら遊べる紹介 HTML |
| 前提を無承認で決める | 推測の要否・一意解・盤面幅・近縁との統合を AI が決めて進む | 認識合わせ: 覆ると大きな作り直しになる前提として想定を示して聞く |
| 試作の条件を完成仕様と取り違える | 固定サイズ・固定数など、比べていない値が SPEC や実装に入る | 調査: 試作の条件は比較実験の条件と書く。採用には変種の比較を要する |
| 核の天井が低い | 最上位でも数秒で解ける。盤面全体を見渡せる | 調査・作り込み: 単純なプレイヤーで最上位の解ける割合と所要の代理を測る。天井を受け入れるなら資料に書く |
| 罰で難しくする | 穴・即死・50/50 の推測で失敗率を上げている | 調査: 追加要素を「先読みを要求するか、罰を増やすか」で分ける |
| 生成器の偏り | 生成条件がレベルごとに1つの値に張り付く。一意化の操作で易しい盤ばかりになる | difficulty・problem-pool: レベルごとに生成条件の分布を出す。候補領域を巡回して採る |
| 自明・重複・単調の混入 | 回転反転の重複、角始点の蛇行、同じ形の繰り返し | problem-pool・作り込み: 正規化キーと解手順の指紋で重複0、自明の下限、単調さの代理 |
| 推論の種類の偏り | 上位の推論が1つの手筋や「仮置きの回数」だけ | difficulty: レベルごとの推論の種類の出現表。偏りが残るなら資料に書く |
| 解き順・視点への依存 | 手筋の適用順や同点の扱いで帯が動く。UI の進め方だと深い読みが要る | difficulty: 順序と視点を変えた感度を測る |
| 同値解で難易度が再現しない | 解の道筋ごとに帯が2段以上揺れる | 認識合わせ・調査: 一意解を採るか、道筋に依存しない指標を先に作る |
| 判定の誤りが下流に波及する | 「この一致、間違えてない？」。偽の一致・偽の違反 | rules・play-ui: 性質テスト（正解配置で全一致、ランダムな途中盤面を完全な判定器と突き合わせる）。直したら問題集・基準時間まで通す |
| 根拠が1つ・推測を事実として言う | 推奨の理由が「一般的だから」だけ | 全段: 事実（計測）・外部知見・推測を書き分け、利点を具体的に複数書く |

## 難易度

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 最上位が試行錯誤で押し切られる | 一致・違反・正誤の即時表示がある。解法器のレベルは高いのに手数・時間の代理が短い。「レベル5でも簡単すぎる」 | difficulty・作り込み: 合意した補助表示のもとで単純なプレイヤー（1手ずつの試し置き等）を当て、上位は押し切れない問題に限る |
| 1つのつまみだけ | 組み合わせ定義の列が1つ。レベルの説明が「〜が多い」の言い換えだけ。特徴どうしの相関が高い | difficulty: 2〜3系統のつまみを出し、系統間の相関を測る。利用者向けの一言を各レベルで言えるか |
| 規模の扱いを誤る | 「規模は難易度ではない」を理由に全レベル同じ盤面にする／逆にレベル＝盤面サイズになる | 認識合わせで規模をつまみに使うかを聞く。difficulty: 同じ規模にそろえた隣接レベルの分かれ方と、規模とレベルの相関を両方出す |
| 盤面の逆転 | 上位ほど盤面が小さい。同じレベルで広い盤面ほど早く解ける | difficulty・difficulty-select: 密度をそろえ、逆転なしをテストで固定する |
| 帯の中のばらつき | 「これほんまに同じ難易度？」。最上位に上限が無い | difficulty: 帯内の分布と最弱の問題を出す。入口の広さ（初手で確定できる箇所数）を特徴に入れる |
| 解法器が緩い・深すぎる | 上位が多すぎ／少なすぎ。手で追うと浅く解ける | difficulty: 別のサブエージェントが代表問題で検証する。既知の解を落とさないテスト |
| 状態の混同 | 評価不能を5へ、軽すぎを1へ押し込む | difficulty: 評価の状態を分けて返す |
| 分位点で閾値を決める | 閾値が三分位・五分位・平均。「境界を変えたら合った」 | difficulty: 組み合わせ定義（データ）で決める。原因を挑戦の定義から探す |
| 人間の判断の巻き戻し | 再校正で、人間が入れると決めたつまみを外す | 全段: 合意内容と人間の判断を実装担当とレビュー役に渡す。外すなら資料の「見てほしい点」に置く |
| 版の波及漏れ | 問題集を作り直したのに基準時間・プレビュー・SPEC が古い | 反映: 波及の連鎖（`references/final-review.md`）を上から通す |
| 1人の記録への過適合 | 校正の根拠が1人・1レベル・慣れた再プレイ | score・反映: 件数と人数と限界を書き、全レベルを同じ根拠で動かさない |

## プレイUI・プレビュー・見た目

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 説明文で知らせる | プレイ中に「〜してください」「n本あります」。遊び方を自動で開く | play-ui・作り込み: プレイ画面の説明文を数える。形・色・動きで知らせる |
| 知らせが難易度を壊す | 一致表示・個数表示を足した | play-ui: 足した情報を単純なプレイヤーに与えて測り直す |
| 共通部品から外れる | 待ったが無い・位置が違う。ヘッダー・結果・プレビュー幅が1ゲームだけ違う | play-ui・作り込み: 共通部品を使い、既存ゲームと並べたスクショで比べる。外すなら理由を書く |
| がたつき・ちらつき | 操作のたびに盤面や計数が揺れる。色のフェード。9→10 で桁がずれる | play-ui・作り込み: 操作の前後と毎フレームの位置、レイアウトシフト、色の中間値を測る。状態で切り替わる見た目に transition を付けない |
| 座標系が2つ | 線や印が中心からずれる、外枠をまたぐ | play-ui: 幾何を1モジュールにまとめ、印とマス中心の差を測る |
| 重なり順を合成に任せる | 線が罫線・外枠の下に回る（iOS だけのこともある） | play-ui・作り込み: 重なりを明示し、交差点の画素と最前面の要素で測る |
| はみ出し | 字や印が地の外へ出る。拡大時だけはみ出す | play-ui・作り込み: 要素と字面の外接矩形を地と比べる。高 DPR・ズームでも測る |
| 窮屈・重ねすぎ | 角丸・枠・影・札・破線が1つの要素に重なる。「窮屈」「角丸多すぎ」 | play-ui: 1つの要素に重ねる表現は1つまで。`@theme` に無い値を数える |
| 色の意味の不一致 | 同じ意味に別の色、別の意味に同じ色。ダークで格子が消える | play-ui: 色の対応表（意味 → ライト / ダーク）を1か所から取り、輝度比を測る |
| iOS のタップ | 「隣を押しても同じマスの判定」 | play-ui: ダブルタップを踏まえた扱いを最初から入れ、隣のマスを素早く押す操作を模擬する。実機は資料の「iOS で見てほしい点」へ |
| スクロールとの競合 | 盤面のドラッグでページが動く、端で戻る | play-ui: 盤面だけスクロールを止め、盤面上のドラッグでページが動かないことを測る |
| 一つの視野に収まらない | スマホで盤面と操作の間をスクロールで往復する | play-ui・作り込み: スマホ縦画面（最小幅を含む）で、盤面と全操作が画面内に収まるか測る |
| プレビューに実問題を描く | 代表問題の縮小。マスが潰れる。上位のレベルが同じに見える | difficulty-select: 挑戦を抽象化して描く。実問題を選ぶ処理をプレビューに置かない |
| 軸でない違いでプレビューの差を作る | レベル間で差の無い量を描き分けている | difficulty-select: 写す量を問題集で測り、レベル間で差がある量だけ使う |
| プレビューの描き込みすぎ・答えを描く | 4色以上、数字・格子・記号。決まるマスを埋めて描く | difficulty-select: 2色程度まで。描かない物のリストを先に作る。既存ゲームのプレビューの意図を読み、並べた画像で比べる |
| 仮の表示が残る | 「クリア」の文字、仮の完了パネル | playable・play-ui: 置かない。結果画面ができるまでは盤面のまま |
| 通る＝完成と取り違える | 「最後まで操作できた」だけで済ませる | 遊べる段・作り込み: プレイヤー目線の試遊と体験のレビュー、既存ゲームと並べた比較を通す |

## スコア・結果

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 取れる値から観点を作る | 事実の表に「評価に使わない理由」が無い。入力回数や違反回数が観点に入る | score: 良いプレイの1文 → 事実の表（使う / 記録だけ / 使わない＋理由）の順に書く |
| 遊び方の中心の操作を罰する | 確かめる UI があるのに置き直しや試行を減点する。「置き直しのペナルティってどうなんや？」 | 認識合わせで良いプレイの定義を前提として聞く。score: 中心の操作は時間にだけ表れる形にする |
| 攻略法を称える | 速さだけにしたら総当たり・試し置きが最高評価を取る | score・作り込み: 単純なプレイヤーで評価の段階の割合を出す |
| 二重減点 | 待ったで戻した手を手数と時間の両方で数える | score: 事実の依存関係を表にし、時間に入るものを別に減点しない |
| 基準時間をレベルから決める | レベルごとの定数。難易度を作り直すと根拠が消える | score: 問題の作業量から求め、レベル間で同じ腕前の点が平らかを測る |
| 解法器の回数をそのまま時間にする | 1つの項が基準の過半を占める。熟練者が全部最高評価 | score: 項の割合と、操作だけの下限を検算する |
| 結果を診断値の一覧にする | 主要成績が4つ以上。内部の特徴量が主表示に出る | result-records: 主要成績は2〜3個。ほかは内訳へ（`DESIGN.md`） |
| 結果と記録で別の指標 | 結果は実時間、記録は基準との差 | score・result-records: 比較値は1か所で計算し、両方の画面で使う |
| 評価値を保存して動けなくなる | 記録に点数を持つ。旧規則で再計算する分岐 | score: 事実と作業量だけ保存し、事実の意味を変えたら記録の版を上げる |
| 文書とコードの数値のずれ | 採点基準の文・SPEC・成績評価文書・テストの数値が違う | score・spec: 代表例の値をテストと文書で照合する。係数は SPEC に書かない |
| 自己ベストの抜け道 | 盤面を戻せば減点の事実が消える | score: 点に入る事実が、どの操作で消えるかを確かめる |
| 難易度を変えたのに採点を見直さない | 規模をつまみにしたのに基準時間の項が一定 | 反映: 波及の連鎖で score まで通す |

## 進め方

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 指摘の読み違え | 「枠線」を外枠と読んで直し、自分の計測で「直った」とした | 反映: AI の読み方を資料に書き、指摘と同じ画面・条件の前後の画像を出す。自分の解釈を裏付けるだけの計測にしない |
| 遊ぶ側の目線が抜ける | 計測とコードのレビューは通るのに、初見で何をすればよいか分からない、手応えが無い、理不尽 | 遊べる段で軽く、作り込みで必ず、経緯を渡さない試遊役に遊ばせる。好みや面白さの所見は直さずに資料へ |
| 見ずに「確認済み」 | サブエージェントの報告やテスト結果だけで報告する | 全段: 撮った画面を一覧にして自分で見る。見ていないものは見ていないと書く |
| Chromium だけで済ませる | iOS でだけ出る不具合をマージ後に人間が見つける | 作り込み: タッチの模擬・高 DPR・ズームを測る。WebKit が無いので、未検証の点を資料に並べる |
| 人間レビュー前に止まる | レビュー・問題集の検証・PR 本文の更新を残したまま知らせる、または止まる | 作り込み: 知らせる前に、直すべき指摘・検証・CI・PR 本文が残っていないことを確かめる |
| 最上段に直しを積む | 直しが上の段にたまり、原因の段が古いまま。最上段で作った直しが古い段に当たらない | 反映: 原因の段で直し、上の段を積み直す |
| 全段が同じ文書を書き換える | 実装前提調査の表が段ごとに変わり、積み直しで衝突する | 実装: 段で決めたことは PR 本文に書き、文書へは spec の段でまとめる |
| worktree が段を握ったまま | 積み直しで一部の段だけ動かない | 実装: 段の PR を作ったら worktree を消す。レビュー用のツリーはブランチを checkout せずに作る |
| 番号の衝突 | 並行スタックや main と同じ SPEC 番号・候補 ID を使う | 調査の開始時に番号を予約して push し、SPEC の直前に衝突を調べ直す |
| 進行中の同じパズルを見落とす | 別ブランチでほぼ完成した同じパズルがあるのに、作り始める | 認識合わせ: 全リモートブランチとオープンの PR・Issue を調べ、引き継ぐか作り直すかを前提として聞く |
| 積み直しの一部だけ直す | 検証に落ちた段だけを直して push し、上の段に直しが載らない | 反映: 積み直しを戻し、原因の段で直してから積み直しをやり直す |
| main に取り残される | 衝突は無いのに共通契約が変わっている。滞留中に共通化が入る | 作り込み: main との使い捨てのマージで verify し、追従するかを AI が決めて資料に書く |
| 生成が途中で止まる | バックグラウンド実行の上限（2時間）で打ち切られ、未完了の問題集をコミットする | problem-pool: 再開できる生成にし、件数と全問の再検証で完了を確かめてからコミットする。候補の比較は小さな仮の問題集で行う |
| 候補ブランチの放置 | 積み直した後も古い別案の URL が資料に残る | 最終レビュー: 別案のブランチはレビュー回ごとに使い捨て、決まったら消す |
| 資料が重くて着手されない | 見てほしい点が回ごとに増え、本文が長い | 最終レビュー: 15〜20分に収め、途中でやめてよい地点を置き、AI が決めたことは費用順の上位3件だけ本文に置く |
| 経緯をコードに残す | 「〜の段でカタログへ載せる」などの予定や経緯のコメント | 全段: `.claude/rules/self-documenting-code.md`。手本のコメントを写さない |
| 正本への勝手な確定 | サブエージェントが選定基準や仮の値を正本に書く | 全段: 書いてよいパスを渡す。SPEC は spec の段で今の決定だけを書く |
