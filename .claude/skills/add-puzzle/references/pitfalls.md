# 失敗パターン集

過去のパズル追加で、人間に指摘されてから直したもの。各行は「兆候 → 予防（いつ・何で確かめるか）」。誰がいつ当てるかは SKILL.md。

「いつ」は作る順番の項目か工程の名前で書く。項目は同じディレクトリの `research.md` の「作る順番」。工程: 認識合わせ・実装・作り込み・反映（最終レビューの指摘の反映）・最終レビュー。全項目に効くものは「全項目」。

難易度と問題の質の失敗は `/design-game-difficulty`、難易度プレビューの失敗は `/design-game-difficulty-preview` の `references/pitfalls.md` にあり、その Skill が自分の流れの中で当てる。

## 面白さ・問題の質

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 核の取り違え | 人間と AI が違うパズルを想像している。ルールの核が最終レビューで覆る | 認識合わせ: ルール・挑戦の1文・近縁との違いを示し、必要なら遊べる紹介 HTML |
| 前提を無承認で決める | 推測の要否・一意解・盤面幅・近縁との統合を AI が決めて進む | 認識合わせ: 覆ると大きな作り直しになる前提として想定を示して聞く |
| 試作の条件を完成仕様と取り違える | 固定サイズ・固定数など、比べていない値が SPEC や実装に入る | research: 試作の条件は比較実験の条件と書く。採用には変種の比較を要する |
| 判定の誤りが下流に波及する | 「この一致、間違えてない？」。偽の一致・偽の違反 | rules・play-ui: 性質テスト（正解配置で全一致、ランダムな途中盤面を完全な判定器と突き合わせる）。直したら問題集・基準時間まで通す |
| 根拠が1つ・推測を事実として言う | 推奨の理由が「一般的だから」だけ | 全項目: 事実（計測）・外部知見・推測を書き分け、利点を具体的に複数書く |

## プレイUI・プレビュー・見た目

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 説明文で知らせる | プレイ中に「〜してください」「n本あります」。遊び方を自動で開く | play-ui・作り込み: プレイ画面の説明文を数える。形・色・動きで知らせる |
| 知らせが難易度を壊す | 一致表示・個数表示を足した | play-ui: 足した情報を素朴な解き方に与えて測り直す（`/design-game-difficulty` の検査） |
| 共通部品から外れる | 待ったが無い・位置が違う。ヘッダー・結果・プレビュー幅が1ゲームだけ違う | play-ui・作り込み: 共通部品を使い、既存ゲームと並べたスクショで比べる。外すなら理由を書く |
| がたつき・ちらつき | 操作のたびに盤面や計数が揺れる。色のフェード。9→10 で桁がずれる | play-ui・作り込み: 操作の前後と毎フレームの位置、レイアウトシフト、色の中間値を測る。状態で切り替わる見た目に transition を付けない |
| 座標系が2つ | 線や印が中心からずれる、外枠をまたぐ | play-ui: 幾何を1モジュールにまとめ、印とマス中心の差を測る |
| 重なり順を合成に任せる | 線が罫線・外枠の下に回る（iOS だけのこともある） | play-ui・作り込み: 重なりを明示し、交差点の画素と最前面の要素で測る |
| はみ出し | 字や印が地の外へ出る。拡大時だけはみ出す | play-ui・作り込み: 要素と字面の外接矩形を地と比べる。高 DPR・ズームでも測る |
| 窮屈・重ねすぎ | 角丸・枠・影・札・破線が1つの要素に重なる。「窮屈」「角丸多すぎ」 | play-ui: 1つの要素に重ねる表現は1つまで。`@theme` に無い値を数える |
| 色の意味の不一致 | 同じ意味に別の色、別の意味に同じ色。ダークで格子が消える | play-ui: 色の対応表（意味 → ライト / ダーク）を1か所から取り、輝度比を測る |
| iOS のタップ | 「隣を押しても同じマスの判定」 | play-ui: ダブルタップを踏まえた扱いを最初から入れ、隣のマスを素早く押す操作を模擬する。実機は資料の「iOS 実機で見てほしい点」へ |
| スクロールとの競合 | 盤面のドラッグでページが動く、端で戻る | play-ui: 盤面だけスクロールを止め、盤面上のドラッグでページが動かないことを測る |
| 一つの視野に収まらない | スマホで盤面と操作の間をスクロールで往復する | play-ui・作り込み: スマホ縦画面（最小幅を含む）で、盤面と全操作が画面内に収まるか測る |
| プレビューに実問題を描く | 代表問題の縮小。マスが潰れる。上位のレベルが同じに見える | difficulty-select: 挑戦を抽象化して描く。実問題を選ぶ処理をプレビューに置かない |
| 軸でない違いでプレビューの差を作る | レベル間で差の無い量を描き分けている | difficulty-select: 写す量を問題集で測り、レベル間で差がある量だけ使う |
| プレビューの描き込みすぎ・答えを描く | 4色以上、数字・格子・記号。決まるマスを埋めて描く | difficulty-select: 2色程度まで。描かない物のリストを先に作る。既存ゲームのプレビューの意図を読み、並べた画像で比べる |
| 仮の表示が残る | 「クリア」の文字、仮の完了パネル | playable・play-ui: 置かない。結果画面ができるまでは盤面のまま |

## スコア・結果

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 取れる値から観点を作る | 事実の表に「評価に使わない理由」が無い。入力回数や違反回数が観点に入る | score: 良いプレイの1文 → 事実の表（使う / 記録だけ / 使わない＋理由）の順に書く |
| 遊び方の中心の操作を罰する | 確かめる UI があるのに置き直しや試行を減点する。「置き直しのペナルティってどうなんや？」 | 認識合わせ・score: 認識合わせで良いプレイの定義を前提として聞く。score の段で中心の操作は時間にだけ表れる形にする |
| 攻略法を称える | 速さだけにしたら総当たり・試し置きが最高評価を取る | score・作り込み: 素朴な解き方で評価の段階の割合を出す |
| 二重減点 | 待ったで戻した手を手数と時間の両方で数える | score: 事実の依存関係を表にし、時間に入るものを別に減点しない |
| 基準時間をレベルから決める | レベルごとの定数。難易度を作り直すと根拠が消える | score: 問題の作業量から求め、レベル間で同じ腕前の点が平らかを測る |
| 解法器の回数をそのまま時間にする | 1つの項が基準の過半を占める。熟練者が全部最高評価 | score: 項の割合と、操作だけの下限を検算する |
| 結果を診断値の一覧にする | 主要成績が4つ以上。内部の特徴量が主表示に出る | result-records: 主要成績は2〜3個。ほかは内訳へ（`DESIGN.md`） |
| 結果と記録で別の指標 | 結果は実時間、記録は基準との差 | score・result-records: 比較値は1か所で計算し、両方の画面で使う |
| 評価値を保存して動けなくなる | 記録に点数を持つ。旧規則で再計算する分岐 | score: 事実と作業量だけ保存し、事実の意味を変えたら記録の版を上げる |
| 文書とコードの数値のずれ | 採点基準の文・SPEC・成績評価文書・テストの数値が違う | score・spec: 代表例の値をテストと文書で照合する。係数は SPEC に書かない |
| 自己ベストの抜け道 | 盤面を戻せば減点の事実が消える | score: 点に入る事実が、どの操作で消えるかを確かめる |
| 難易度を変えたのに採点を見直さない | 規模をつまみにしたのに基準時間の項が一定 | 作り込み・反映: 「版の波及漏れ」と同じく score まで通す |

## 進め方

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| Chromium だけで済ませる | iOS でだけ出る不具合をマージ後に人間が見つける | 作り込み: タッチの模擬・高 DPR・ズームを測る。WebKit が無いので、未検証の点を資料に並べる |
| main に取り残される | 衝突は無いのに共通契約が変わっている。滞留中に共通化が入る | 作り込み: 共通契約のずれは最終レビュー資料に書く |
