# 失敗パターン集

パズル追加で繰り返さないための兆候と予防。多くは、過去のパズル追加で人間に指摘されてから直したもの。各行は「兆候 → 予防（いつ・何で確かめるか）」。誰がいつ当てるかは SKILL.md。

「いつ」は作る順番の項目か工程の名前で書く。項目は同じディレクトリの `build-order.md`。工程: 認識合わせ・実装・作り込み・反映（最終レビューの指摘の反映）・最終レビュー。全項目に効くものは「全項目」。

難易度と問題の質の失敗は、`/design-game-difficulty` の `references/pitfalls.md` にある。配り方は SKILL.md の「実行役」。

## 面白さ・問題の質

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 核の取り違え | 人間と AI が違うパズルを想像している。ルールの核が最終レビューで覆る | 認識合わせ: 文で説明せず、触れる見本と図で見せる（`alignment.md` の「見せるページ」） |
| 前提を見せずに決める | 推測の要否・一意解・盤面幅・近縁との統合を、人間に見えないまま AI が決めて進む | 認識合わせ: `alignment.md` の「見本に映すもの」を全部当て、見本に映すか、こちらで決めて進めることに書く |
| 試作の条件を完成仕様と取り違える | 固定サイズ・固定数など、比べていない値が SPEC や実装に入る | research: 試作の条件は比較実験の条件と書く。採用には変種の比較を要する |
| 判定の誤りが下流に波及する | 「この一致、間違えてない？」。偽の一致・偽の違反 | rules・play-ui: 性質テスト（正解配置で全一致、ランダムな途中盤面を完全な判定器と突き合わせる）。直したら問題集・基準時間まで通す |
| 根拠が1つ・推測を事実として言う | 推奨の理由が「一般的だから」だけ | 全項目: 事実（計測）・外部知見・推測を書き分け、利点を具体的に複数書く |

## プレイUI・見た目

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 説明文で知らせる | プレイ中に「〜してください」「n本あります」。遊び方を自動で開く | play-ui・作り込み: プレイ画面の説明文を数える。形・色・動きで知らせる |
| そろえる所と当てはめる所の取り違え | アプリが持つもの（ヘッダー・結果・ゲームのホーム・待ったの強さ）が1ゲームだけ違う。逆に、前のゲームの盤面・操作・姿・音をそのまま当てはめている | playable・play-ui・sound・作り込み: アプリが持つもの（`APP.md`「アプリとゲームの分担」）は共通部品を使い、既存ゲームと並べたスクショで比べる。ゲームが持つものは題材から作り（`GAME.md`「やらないこと」）、手本と並べて同じに見えないかを見る。実装役に渡す手本の使い方もこの行に従う |
| がたつき・ちらつき | 操作のたびに盤面や計数が揺れる。色のフェード。9→10 で桁がずれる | play-ui・作り込み: 操作の前後と毎フレームの位置、レイアウトシフト、色の中間値を測る。状態で切り替わる見た目に transition を付けない |
| 座標系が2つ | 線や印が中心からずれる、外枠をまたぐ | play-ui: 幾何を1モジュールにまとめ、印とマス中心の差を測る |
| 重なり順を合成に任せる | 線が罫線・外枠の下に回る（iOS だけのこともある） | play-ui・作り込み: 重なりを明示し、交差点の画素と最前面の要素で測る |
| はみ出し | 字や印が地の外へ出る。拡大時だけはみ出す | play-ui・作り込み: 要素と字面の外接矩形を地と比べる。高 DPR・ズームでも測る |
| 窮屈・重ねすぎ | 角丸・枠・影・札・破線が1つの要素に重なる。「窮屈」「角丸多すぎ」 | play-ui: 1つの要素に重ねる表現は1つまで。`@theme` に無い値を数える |
| 色の意味の不一致 | 同じ意味に別の色、別の意味に同じ色 | play-ui: 色の対応表（意味 → 色）を1か所から取り、輝度比を測る |
| iOS のタップ | 「隣を押しても同じマスの判定」 | play-ui: ダブルタップを踏まえた扱いを最初から入れ、隣のマスを素早く押す操作を模擬する。実機は最終レビュー資料の「遊ぶ」へ |
| スクロールとの競合 | 盤面のドラッグでページが動く、端で戻る | play-ui: 盤面だけスクロールを止め、盤面上のドラッグでページが動かないことを測る |
| 一つの視野に収まらない | スマホで盤面と操作の間をスクロールで往復する | play-ui・作り込み: スマホ縦画面（最小幅を含む）で、盤面と全操作が画面内に収まるか測る |
| 仮の表示が残る | 「クリア」の文字、仮の完了パネル | playable・play-ui: 置かない。最初の版は中身ごと作る（`build-order.md`） |

## スコア・結果

| パターン | 兆候 | 予防（いつ・何で） |
|---|---|---|
| 取れる値から観点を作る | 事実の表に「評価に使わない理由」が無い。入力回数や違反回数が観点に入る | score: 良いプレイの1文 → 事実の表（使う / 記録だけ / 使わない＋理由）の順に書く |
| 遊び方の中心の操作を罰する | 確かめる UI があるのに置き直しや試行を減点する。「置き直しのペナルティってどうなんや？」 | 認識合わせ・score: 認識合わせのページで良いプレイの定義を見せる。score で中心の操作は時間にだけ表れる形にする |
| 攻略法を称える | 速さだけにしたら総当たり・試し置きが最高評価を取る | score・作り込み: 素朴な解き方で評価の段階の割合を出す |
| 二重減点 | 待ったで戻した手を手数と時間の両方で数える | score: 事実の依存関係を表にし、時間に入るものを別に減点しない |
| 基準時間をレベルから決める | レベルごとの定数。難易度を作り直すと根拠が消える | score: 問題の作業量から求め、レベル間で同じ腕前の点が平らかを測る |
| 解法器の回数をそのまま時間にする | 1つの項が基準の過半を占める。熟練者が全部最高評価 | score: 項の割合と、操作だけの下限を検算する |
| 結果を診断値の一覧にする | 主要成績が4つ以上。内部の特徴量が主表示に出る | result-records: 主要成績は2〜3個。ほかは内訳へ（`docs/プロダクト/画面/SCR-004.md`） |
| 結果と記録で別の指標 | 結果は実時間、記録は基準との差 | score・result-records: 比較値は1か所で計算し、両方の画面で使う |
| 評価値を保存して動けなくなる | 記録に点数を持つ。旧規則で再計算する分岐 | score: 事実と作業量だけ保存し、事実の意味を変えたら記録の版を上げる |
| 文書とコードの数値のずれ | 採点基準の文・SPEC・成績評価文書・テストの数値が違う | score・spec: 代表例の値をテストと文書で照合する。係数は SPEC に書かない |
| 自己ベストの抜け道 | 盤面を戻すかリセットすれば減点の事実が消える | score: 点に入る事実が、どの操作で消えるかを確かめる。作り込みの試遊で、リセット・盤面を戻すをわざと試す（試遊役の観点） |
| 遊び直しで点が意味を失う | 図鑑から同じ問題を遊び直すと、覚えた解をなぞるだけで最高評価になる。逆に、2回目の上達が点に出ない | score: 1回目と、覚えた解をなぞる2回目の点を計算で出し、どう扱うかを仮決定一覧に書く。作り込みの試遊の遊び直しと、最終レビューの遊び直しのカードで確かめる |
