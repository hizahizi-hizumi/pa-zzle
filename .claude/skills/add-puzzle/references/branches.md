# ブランチと PR

作業ブランチの作り方と、作り切った作業ブランチを PR に切り出す手順。

## 作業ブランチ

1. 接頭辞は、`git ls-remote origin '<接頭辞>/*'` が空のものを選ぶ（既存のブランチを force-push で消さないため）。
2. main から作業ブランチと worktree を作る: `git worktree add <作業ディレクトリ>/work -b <接頭辞>/work origin/main`。
3. 作業ブランチを push して、push できることを実際に確かめる。

既存の実装を引き継ぐと合意したときも、作業ブランチは main から作り、既存の実装は取り込まない。作業カードの「出発点」に既存のブランチとパスを書き、実装役と作り方の Skill に読ませる。

確かめのためだけのブランチは作らない。ブランチの削除を人間に頼まない。要らなくなったブランチは AI が消し、この環境で消せなければ黙って残す。

## PR の切り方

作り込みを終えた作業ブランチの木を、依存の層で切る。各ファイルは、import する先がすべてその層以下にそろう最も下の層に入れる。こうすると下から順に各層が単体でビルドとテストを通る。

- ゲームの中は `.claude/rules/game-*.md` の「依存方向」でほぼ下の表どおりになる。外れるもの（上の層の `score.ts` を import する問題集の生成スクリプト、共通のファイルなど）も上の決まりで層が決まる。
- import されないファイルは、下の表で名前を挙げた層に入れる。
- 小さいパズルでは隣の層をまとめてよい。決めた切り方は実装前提調査に書く。

| 層（ブランチ名の topic） | 入るもの |
|---|---|
| 調査（research） | `docs/パズル/導入調査/<パズル名>/`（実装前提調査は「実装で確定した差分」を含む最終版）、`scripts/research/<ゲーム ID>_*` |
| ルールと問題（rules-problem） | ルール・問題・難易度・問題集と、その生成スクリプト |
| プレイと画面（play-ui） | プレイ・画面・採点・記録と、効果音を書き出したスクリプト `scripts/assets/<ゲーム ID>_sounds.ts` |
| 掲載（catalog） | カタログ・ルート・View と、一覧のテスト |
| 文書（docs） | 仕様・台帳の行と候補ファイル・各 README の一覧、ゲームをまたぐ判断の ADR（あるときだけ）、最終レビューで足した正本と失敗パターン集への追記 |

カタログの網羅テスト（`frontend/src/game-catalog/game-catalog.test.ts`）は `src/games/` の全ゲームが一覧にあることを確かめる。掲載より下の層では、このゲームを外す一時的な除外をそのテストに置き、掲載の層で消す。置く前に `git log --all -S gamesNotInCatalogYet` を流して前例を読み、同じ形で置く。作業ブランチには置かない。

切り出しの手順:

1. 最下層のブランチ `<接頭辞>/01-<topic>` を `git merge-base origin/main <接頭辞>/work` から作り、上の層を前の層の上に作る。各層は層ごとの worktree（`git worktree add <作業ディレクトリ>/layer-<NN> -b <ブランチ> <下の層>`）で作る。
2. 各層に、ゲーム固有のパスは作業ブランチの版で取り込み（`git checkout <接頭辞>/work -- <存在するパス>`）、共通のファイルは作業ブランチでの差分だけを当てて（`git diff <merge-base> <接頭辞>/work -- <パス> | git apply -3`）、main に並行で入った変更を消さないようにしてコミットする。
3. `git diff --stat <最上層> <接頭辞>/work` が空であることを確かめる。空でなければ、どの層にも入らなかったファイルを実装前提調査の「PR の切り方」に足して切り直す。
4. 積んだ PR では上の層と main の衝突が GitHub に出ないので、`git merge-tree --write-tree origin/main <最上層>` で衝突しないことを確かめる。衝突したら `references/final-review.md` の「コンフリクトと部分マージ」に従う。
5. 全部を push して PR を積み、PR 本文は SKILL.md の「記録」の型で書く。層ごとの確かめは PR の CI（Quality Gate）に任せ、CI の完了は待たない。落ちたと分かったら作業ブランチで直して切り出し直す。
6. 最終レビュー資料に載せるプレビュー URL（`references/final-review.md` の「資料」の「出す前に」）だけは、出るまで待つ。待つ前に起きる手段（PR の購読か、数分後に戻る予約）を用意してから作業を終える。
