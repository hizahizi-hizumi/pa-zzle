# 人間レビューフェーズ（human-review）

AIレビューを終えたスタックを人間に試遊・判断してもらい、指摘を反映し、H2（最終レビューと正式採用）とマージまでつなぐ。人間レビューは全段の実装後にまとめて行い、複数回になる前提で進める。

## 1. レビュー資料を作る

`assets/review-sheet.md` の型で Artifact を作る（作業はサブエージェントに任せてよいが、公開前にメインが全体を見る）。資料はリポジトリに置かない。詰将棋では `詰将棋最終レビュー.md` を導入調査に置いたが、回ごとに書き換わる資料を資料ディレクトリに残さないため、この Skill では Artifact だけにする。

- **触る URL**: 最上段 PR の Cloudflare の bot コメントにある Branch Preview URL（SKILL.md の「GitHub の操作」で取る）。最上段のブランチがスタック全体を反映する。問題を指定して開く URL は `<Preview URL>/puzzles/<game>/play/<レベル>?problem=<問題ID>`。
- **領域ごとの節**: ピクトグラム / 難易度プレビュー / ゲーム体験（見た目を含む）/ 難易度の体感 / スコアの納得感。各節に「AI が決めたこと」「判断してほしいこと」「根拠（文書の節）」「画像（ライト・ダーク、390・1280）」「記入欄（選択肢と所感）」を置く。人間に聞くのはこの5領域と H2 の確認項目だけにする。
- **伏せ問題**: 各レベルの代表問題と境界問題を合わせて10問程度、A・B・C… の記号で並べ、遊ぶ順番を決める。
  - 問題 ID の URL はパスにレベルの数字が入り、結果画面にもレベルが出る。伏せられるのは記号の並びだけなので、「URL バーと結果画面のレベルの表示を見ずに、体感レベルを書いてからスコアを見る」よう依頼し、この限界を資料に書く。
  - 検証情報のダイアログ（内部診断が有効なビルドで出る）にもレベルが出るので、遊び終えるまで開かないよう書く。
  - 問題 ID で開いたプレイも記録に残るので、自己ベストに入れたくなければプライベートウィンドウで遊ぶよう書く。
  - レベルとの対応表は折りたたみ（`<details>`）にし、遊び終えてから開くよう書く。
- **H2 の確認項目**: 表示名の確定、商標確認（J-PlatPat は人間が確かめる）が済んだか、main の共通契約の変化に追従するか（AIレビューの記録から）、正式採用するか。
- **AI が自分で見つけた懸念**: 直さずに残した見た目の好み、確かめられなかったこと（iOS Safari 実機、意味 lint など）。
- **PR 一覧とマージ順**: 調査 PR → 段01 → … → 最上段。
- 案を記号だけで呼ばない。各案に中身の説明を付ける（`references/reporting.md`）。
- Artifact へのコメントは通知されないので、指摘は会話で送ってもらうよう資料の冒頭に書く。
- 資料は回ごとに同じ URL で更新する。前回までの指摘と対応を冒頭に要約する。

資料ができたら、`references/reporting.md` に従って URL と見てほしい順番を短く知らせる。

## 2. 指摘を受けたとき

人間の指摘は短い口語で、1回に複数件届く。スクショ、検証情報 JSON、記録 JSON が添えられることがある。

1. **解釈を確かめる**: どの画面・どの要素の話かが曖昧なときだけ、一言で確かめる。明らかなときは確かめずに進める。スクショを受け取れていないときは、推測で答えずにそう伝える。
2. **記録する**: 最上段 PR 本文に「## 人間レビュー対応（N回目）」節を足し、日付、指摘の原文の引用、要旨、原因を持つ責務、修正内容とコミット、見てほしい点（追加）、Validation を書く。
3. **原因を持つ責務へ戻す**: 下の表で原因の段を決め、その段の元のコミットへ畳み込む（手順は `references/ai-review.md` の「修正と各段への畳み込み」）。
4. **影響範囲の AI レビューをやり直す**: 経緯を渡さない新しいレビュー Agent で、変えた範囲を見直す。人間決定の一覧には今回の判断を足して渡す。メインが画面を撮り直して自分で見る。
5. **次の回の資料にする**: 資料を同じ URL で更新し、対応の要約と追加で見てほしい点を知らせる。

### 原因の責務と直し方

段は標準スタックの topic で示す。段01のスタック表で対応する段に読み替える。

| 指摘の種類 | 戻す段 | 直し方 |
|---|---|---|
| 難易度の体感のずれ（簡単すぎる、帯の中の差が大きい、サイズの逆転） | difficulty・problem-pool（連動して difficulty-select・score・spec） | 挑戦の定義から見直す。試行ソルバーや特徴量を足し、組み合わせ定義（データ）を作り直し、問題集の版を上げて再生成し、基準時間・プレビュー・SPEC も連動して直す。人間のプレイ記録 JSON があれば、問題集から復元して特徴量と所要時間の相関を測り、限界（何人・何件か）を添える |
| 問題の正当性・ルール判定の誤り | rules（連動して difficulty・problem-pool） | 判定を直し、問題集を再生成する。過去の記録が再プレイできなくなるかを確かめて書く |
| 状態の知らせ・正誤の分かりにくさ | play-ui（連動して spec） | 盤面の形・色・動きで知らせる案を2〜3並べて選んでもらう。SPEC の状態の知らせ・補助の節を人間判断に合わせて書き換える。難易度判定の前提（例: 一致表示が無いこと）が崩れないか確かめる |
| 補助操作・操作体系（待った、置き直し、タップ判定） | playable・play-ui（連動して score・spec） | 既存ゲームの同じ操作にそろえる。session・記録の形が変わるなら記録の版を上げる。遊び方と SPEC も直す |
| 見た目（ダサい、窮屈、がたつき、はみ出し、重なり順、角丸・枠・影） | 該当する UI の段 | 原因を計測で特定する（boundingBox、画素、座標）。必要なら複数案を同じ条件で並べて選んでもらう。直した後に数値で確かめる |
| 難易度プレビュー | difficulty-select | 既存ゲームのプレビューの意図を読み直し、入れ子・単調性のテストを付けて描き直す（`references/implementation.md` の「仮の決まり」） |
| ピクトグラム | pictogram | `/design-game-pictogram` で直す。検討記録に指摘と選んだ案を追記し、代替案を同じ品質で残す |
| スコア・基準時間 | score | 成績評価文書に比較案とシミュレーションを書く。記録は読み出し時に計算し直す |
| 名称 | 全段（`display-name.ts` 起点） | 表示名を1か所で変え、文書の名称を直す |
| 「楽しくない」など体験全体の否定 | research から | 原因を分析して方向を2〜3案示し、人間に選んでもらってから作り直す。部分修正で済ませない |

- 人間が選んだ案・確定した値を、確定時に勝手に調整しない。
- 方向の指示（「色をもっと使っていい」など）には、案を2〜4並べて選んでもらう。具体的な指示には、そのまま従う。
- 規約・正本の誤りが指摘の原因なら、その正本の直しを同じ変更に含める（例: 誤った不採用理由を書き換える）。
- 特定の指摘の再発防止だけを理由にテストを足さない（`AGENTS.md`「検証」）。振る舞いの契約として要るテストは足す。

## 3. 決まったことの反映

同じ変更の中で反映する（`AGENTS.md`）。

- 振る舞い → コードとテスト。
- 守る決まり → SPEC など該当する正本。SPEC は今の決定として言い切る。
- 理由を失うと戻される判断 → ADR（`/adr-create`）。パズル固有の判断で ADR が要ることはまれなので、要否を判断してから作る。
- 仮決定一覧: 覆った仮決定は「人間判断（日付、N回目のレビュー）で取り下げ」、認められた仮決定は「人間判断（日付）で確定」と追記し、新しい決定を「人間判断」として足す。調査時点の本文は当時の記録として残し、書き換えずに追記する。
- 実装前提調査の「実装で確定した差分」表を更新する。

## 4. H2 最終レビューと正式採用（人間関門）

5領域の判断と H2 の確認項目がそろったら、正式採用するかを人間に確かめる。

- 人間が「正式採用」と判断したら:
  - 調査 PR 本文と最上段 PR 本文に「## 人間決定（H2, YYYY-MM-DD）」節を書く（表示名、商標確認の結果、main への追従の判断、正式採用）。
  - 台帳の `導入判断` を `正式採用` にし、4ゲートの状態を最終の状態に合わせ、`PUZZLE-NNN.md` に SPEC へのリンクを足す。
  - 仮決定一覧の残りの行に、人間判断で確定・取り下げを追記する。
  - これらを最上段（SPEC の段）に入れる。
- 人間が正式採用を判断せずにマージだけを指示したら、台帳は `条件付き保留` のままにし、残る判断を最上段 PR 本文に書く。AI が台帳を `正式採用` に上げない。

## 5. マージ

- マージは人間が、下の段（調査 PR）から順に merge commit で行う。AI はマージしない。
- 人間がマージすると言ったら（H2 の後）:
  1. `git merge-tree --write-tree origin/main <最上段>` で main とのコンフリクトを確かめる。
  2. コンフリクトしていなければ何もしない（`main` を取り込まない）。
  3. コンフリクトしていれば、rebase してよいかを人間に確かめてから、最新 `origin/main` へ全段をまとめて rebase（`--update-refs`。手順1・2の全段のローカルブランチ作成と tag での退避は `references/ai-review.md` と同じ）して解消し、最上段の先端で verify し、`git push --atomic --force-with-lease` で push する。merge commit で追従しない。この rebase は1回だけにする。
  4. 各 PR 本文の Validation に「最新 main（SHA）へ rebase（日付）」を追記し、各段の CI を一度確かめて知らせる。
- H2 で main の共通契約に追従すると決めた場合は、範囲と作業量を示して人間に選んでもらう（マージ前に追従する段を足すか、マージ後に追従 PR を作るか）。
- 導入調査 Issue のクローズは人間の指示で行う（PR は `Refs` で参照し、自動では閉じない）。
- マージ後に見つかった指摘は、スタックを開き直さず、最新 `main` から新しいブランチと PR で直す。
- 全段がマージされたら、ローカルの退避の tag（`backup/<game>-*`）を消す。
