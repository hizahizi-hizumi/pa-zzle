# 最終レビュー

作り切ったものを人間に渡し、指摘を反映する。

## 資料

人間がこのページだけで、遊んで確かめ、問いに答え、マージするか直しを頼むかを決められるようにする。所要は遊ぶ時間を含めて15〜20分。

SKILL.md の「人間への知らせ方」に従い、`assets/final-review-sample.html` を複製して中身を置き換えて Artifact にし、回ごとに同じ URL で更新する。画像は Artifact の files で一緒に出す。Artifact が使えないときは、同じ中身を導入調査 Issue のコメントに画像つきで書く。記入欄は作らず、指摘は会話かページへのコメントで受ける。

並びと中身の出どころ:

1. 頭: パズル名、遊び方の1行、盤面の小さな画像。返し方の1行（指摘はこの会話に一言とスクショで。答えがない問いはおすすめで進める。マージしたら、それで決まる）。やること3つ（遊ぶ・答える・マージ）と、それぞれの量（遊ぶはカードの枚数と目安の時間の合計、答えるは問いの数、マージは PR の数）。
2. 前回の指摘（2回目から）: 指摘の原文、AI の読み方、直す前と後の画像（指摘の画面を、指摘と同じ条件で撮る）。前回までの直しが戻っていないか。
3. 遊ぶ: 3〜5枚のカード。各カードに、レベル、問い（そこで確かめてほしいこと）、目安の時間、遊ぶ URL。
   - 1枚目は一覧から開いて遊び方を読まずに始める。
   - 1枚は、遊んだ問題をゲームのホームの図鑑から選んで遊び直すカードにする（`references/pitfalls.md` の「遊び直しで点が意味を失う」を人間が確かめる）。そのカードには、どのカードで遊んだ問題を、図鑑のどのレベルの何番で選ぶかを書く。
   - 問題は作り込みで試遊役が遊んだものから選ぶ。
   - 問いには、「人間に残す」とした所見、試遊役の「人間に確かめてほしい点」、遊んで決める判断、iOS 実機の点と音（この環境は Chromium しか無く、AI は音を聞けないので、人間にしか確かめられないもの。試遊役と作り方の Skill の報告にある点を含む）を、それが起きるカードに割り当てる。
   - 時間は試遊役の実時間と基準時間から見積もる。
   - 2回目からは直した所だけ。
4. 答える: 3問まで。好みと、遊んで決めるもの（図鑑で絞り込む問題の特徴の切り口など）。おすすめ（今の作り）と別案を並べる（下の「別案の出し方」）。ルールの要素を足したとき（SKILL.md の原則 5）は、それを最初の問いにし、要素なしの案の最上位の重さを数値で並べる。見た目の違いは、それぞれの選択肢に画像を置く。
5. マージ: PR を下の層から順に、中身と PR へのリンク。CI の状態は、確かめたときだけ書く。
6. 畳む参考（件数つき）:
   - AI が遊んだ結果: 試遊役のレベルごとの時間と一言、見つけて直したもの。人間の初見の感想を消さないよう、遊ぶより後に置いて畳む。
   - 最初の約束から変えたこと: 確かめの記録の「AI が決めたこと」のうち、合意の細部を変えたもの。
   - AI が決めたこと: 確かめの記録の「AI が決めたこと」と仮決定一覧。変えると手戻りが大きい順に、手戻りの範囲つきで。
   - まだ確かめていないこと: 実施できなかった検査（`difficulty-checks.md` の「測れない」の行と、実装役の報告の「確かめていないこと」）、main との共通契約のずれ、人が遊ばないと分からないこと（基準時間・面白さ）、人間にしか確かめられないこと（商標など）、並行作業の形跡、答えるからあふれた「人間に残す」所見。
7. 末尾: 難易度の調整に使うので、遊んだレベルごとに、ゲームのホームの「成績」でコピーできる JSON を貼ってほしいこと。受け取ったのがマージの前なら、記録のパスを直しの作業カードに書き、実装役に `/design-game-difficulty` を入口「`/add-puzzle` の直しから」で起動させる（記録の扱いは同じ Skill の `references/recalibration.md` に従わせる）。マージの後なら新しい改善として、入口「再校正」で起動する。

出す前に:

- 遊べる URL は Workers Builds の check run にある版ごとのプレビュー URL にする（測ったものと遊ぶものを一致させるため）。最上層の PR の先頭のコミットの check run（`gh api repos/<owner>/<repo>/commits/<sha>/check-runs`）のうち Workers Builds のものの `output.summary` にある Preview URL を使う。この環境からは開けないので、同じパスが手元の開発サーバーで開けることを確かめる。
- 画像は判断に使うものだけを、同じ条件（端末・テーマ・状態）で撮る。ピクトグラムはゲーム一覧の実表示サイズで既存と並べる。
- SKILL.md の「実行役」のページの読み手に見せ、次を返させて直す: 最初の画面で何をすればよいか言えるか、分からなかった語。

## 別案の出し方

- 既定は AI の推奨案で、作ったものには推奨案を入れておく。別案は、人間の好みで決まるか前提が連鎖するもので、AI が自信を持てないものだけ。1回に出す軸は少なく（目安2軸）、難易度に影響する軸は1つまで。
- 難易度への影響は、プレイ条件を引数に取る分析で同じコードのまま測り、表の要点を載せる。
- 遊んで決める別案（補助表示・待った・盤面の上限・ルールの変種など）だけ、推奨案から1軸だけ変えた使い捨てのブランチを作る（PR なし。プレビュー URL はブランチだけで出る）。
  1. メインが作業ブランチから別案のブランチ `<接頭辞>/alt-<軸>` と worktree を作る。
  2. 同じ実装役に、その worktree を書いた作業カードで作らせる。問題集は小さな仮のものにする。
  3. 決まったら、採用案を作業ブランチの worktree で新しいコミットとして作り直させ、別案のブランチと worktree を消す。
- ピクトグラムの案は、ブランチにせず画像で並べる。

## 指摘の反映

人間の指摘は短い口語で、1回に複数届く。

- 指摘ごとに、どの画面のどの要素の話かを決める。曖昧なら AI の読み方を決めてその読み方で直し、資料の「前回の指摘」に読み方を書く（聞き返して待たない）。スクショを受け取れていなければ、推測で直さずにそう書く。
- 具体的な指示にはそのまま従う。人間が選んだ案や値を、取り込むときに勝手に調整しない。
- 計測は指摘の画面そのものを測り、自分の読み方を裏付けるだけにしない（撮り方は「資料」の 2）。
- 作業ブランチで直し、波及先を同じ回で一気に通す。難易度に触れる指摘は、直しの作業カードで実装役に `/design-game-difficulty` を入口「`/add-puzzle` の直しから」で起動させ、報告の「頼むこと」に回った段を作業カードにして最後まで通す。
- 指摘のうち他のパズルにも当てはまるものは、守る決まりとして正本（置き場所は `.claude/rules/documents.md` を読んで決める）か `references/pitfalls.md` への追記を作業ブランチ（文書の層）に入れ、マージで人間に決めてもらう。このパズルだけの決まりは、その意図と一緒に仕様に書く。
- 反映の後は、SKILL.md の「確かめ」の表の最終レビューの反映の行の役を1回起動し、機械検査を流してから、`references/branches.md` の「PR の切り方」で切り出し直す。

## コンフリクトと部分マージ

作業ブランチを rebase するかは、AGENTS.md の「Git運用」を読んで決める。

- コンフリクトしたとき: メインが作業ブランチを最新の main へ rebase して衝突を解き、波及の直しを実装役に新しいコミットとして頼み（main で契約が変わっていれば、`references/resume.md` の「main への追従の作業カード」）、機械検査を通してから PR を切り出し直す。次に確かめるときの差分の基準は、`git range-diff` で前回のレビュー版に当たる rebase 後のコミットにする。
- 下の層だけがマージされた後に指摘が出たとき: マージ済みの層は main の一部とし、上の PR の base を main に付け替える。残りの層は、マージ済みの最上層のブランチの先端の上に同じ手順で切り直す（main を取り込まない）。直しがマージ済みの層のパスに及ぶなら、その分を新しい層 `<接頭辞>/<元の番号>b-<topic>` として残りの層の下に積む。
