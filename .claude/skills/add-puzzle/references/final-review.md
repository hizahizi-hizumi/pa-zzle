# 最終レビュー

作り切ったものを人間に渡し、指摘を反映する。

## 資料の目的と読み手

- 目的: 人間がこの資料だけで、遊んで確かめ、見てほしい点を選び、マージするか直しを頼むかを決められること。マージが本決定。
- 読み手: 経緯を覚えていない。スマホで、自分の都合のよいときに読み、15〜20分で終える。リンクを開いて遊ぶ。
- 載せないもの: 経緯、作業の量（巡の数・所見の件数）、計測の詳細、内部用語、`/tmp` のパス。これらは導入調査 Issue の巡の記録に置く。
- 書き方の共通の決まりは SKILL.md の「人間への知らせ方」。

## 型

`assets/final-review-template.md` の見出しと順で書き、`<...>` を埋める。

- 資料は Artifact（HTML）にし、回ごとに同じ URL で更新する。HTML にしても見出しと順は保つ。Artifact が使えないときは、同じ中身を導入調査 Issue のコメントに画像つきで書く。
- 中身が無い節は消さずに「無し」と書く（書き漏れと区別するため）。「前回の指摘への対応」だけは2回目から置く。
- 記入欄を作らない。指摘は会話かページへのコメントで受け、AI が構造化する。

## 節ごとの書き方

| 節 | 読み手がそこで決めること | 書くこと |
|---|---|---|
| 冒頭 | 何をすればよいか、どれだけかかるか | してほしいこと、所要時間、途中でやめてよい地点（「何を作ったか」の終わり）。挨拶と経過は書かない |
| 何を作ったか | 核（ルール・挑戦・難易度の軸）が想像どおりか。違えば以降は見ない | ルールとクリア条件、何を考えるのが面白いか、レベルで何が変わるか（利用者向けの一言）。遊べる URL と、レベルごとの代表問題を開く URL を少数 |
| 前回の指摘への対応 | 自分の指摘がどう読まれ、どう直ったか | 指摘の原文 → AI の読み方 → 今どうなったか（指摘と同じ条件の前後の画像）。前回までに直したものが戻っていないか |
| 見てほしい点 | AI が決められない好みと、遊んで決めるもの | 3点まで。各点に、論点を中身で一言、試す操作と開く URL、推奨と理由（良くなること・不利な点）、別案（下の「別案の出し方」）。「何も言わなければ推奨のまま」と書く |
| 認識合わせからの変更点 | 合意した前提の変え方を認めるか | 巡の記録の「AI が決めたこと」のうち、合意した前提の細部を変えたもの。合意・変えたこと・理由 |
| AI の試遊の要約 | 自分で遊ぶ前のつまずきと手応えの見当 | 最初に分からなかったこと、操作のつまずき、レベルごとの手応え、つまらなかった点・理不尽だった点、既存ゲームとの比較。直したものと「人間に残す」とした所見を分ける。人間の体感の代わりではないと書く |
| AI が決めたこと | 黙っていれば通る判断のうち、覆したいもの | 覆すと作り直しが大きい順。上位3件を本文に（決めたこと・理由・作り直す範囲）、残りは折りたたむ。「何も言わなければこのまま」と書く |
| iOS 実機で見てほしい点 | 実機で数十秒ずつ確かめるもの | この環境は Chromium しか無く確かめられないもの（ダブルタップ、描画順、拡大時のはみ出し、スクロールとの競合など）。試遊役と作り方の Skill の報告にある同じ名前の点を含む。点ごとに開く URL と操作 |
| 確かめていないこと・未決 | マージで何を引き受けるか | 実施できなかった検査（作り方の Skill の報告の「撮っていないもの」を含む）、直していない AI レビューの Minor、main との共通契約のずれ、素朴な解き方では分からないこと（人間の速さ、見渡しの負荷、面白さ）、人間にしか確かめられないこと（表示名の商標など）、見つけた並行作業の形跡、見てほしい点からあふれた「人間に残す」所見 |
| PR とマージの順 | マージの操作 | 下の層から、PR へのリンク・中身を一言・CI の結果 |
| 指摘の返し方 | 指摘の出し方 | 一言とスクショでよいこと。普通に遊んだ記録の JSON を貼ってもらえれば校正に使うこと |

## 仕上げ

- 遊べる URL は Workers Builds の check run にある版ごとのプレビュー URL にする（測ったものと遊ぶものを一致させるため）。この環境からは開けないので、同じパスが手元の開発サーバーで開けることを確かめる。
- 画像は判断に使うものだけを、同じ条件（端末・テーマ・状態）で並べる。難易度プレビューは既存ゲームの難易度選択と並べ、ピクトグラムはゲーム一覧の実表示サイズで既存と並べる。
- 数値は判断に要る1〜2個だけにする。
- 出す前に、経緯を渡さない汎用サブエージェント（Opus）に資料だけを読ませ、冒頭だけで何をすればよいか言えるか、分からなかった語、核を「何を作ったか」だけで判断できるかを返させて直す。

## 別案の出し方

- 既定は AI の推奨案で、作ったものには推奨案を入れておく。別案は、人間の好みで決まるか前提が連鎖するもので、AI が自信を持てないものだけ。1回に出す軸は少なく（目安2軸）、難易度に影響する軸は1つまで。
- 難易度への影響は、プレイ条件を引数に取る分析で同じコードのまま測り、表の要点を載せる。
- 遊んで決める別案（補助表示・待った・盤面の上限・ルールの変種など）だけ、推奨案から1軸だけ変えた使い捨てのブランチを作る（PR なし。プレビュー URL はブランチだけで出る）。
  1. メインが作業ブランチから別案のブランチ `<接頭辞>/alt-<軸>` と worktree を作る。
  2. 同じ実装役に、その worktree を書いた作業カードで作らせる。問題集は小さな仮のものにする。
  3. 決まったら、採用案を作業ブランチの worktree で新しいコミットとして作り直させ、別案のブランチと worktree を消す。
- ピクトグラムや難易度プレビューの案は、ブランチにせず画像で並べる。

## 指摘の反映

人間の指摘は短い口語で、1回に複数届く。

- 指摘ごとに、どの画面のどの要素の話かを決める。曖昧なら AI の読み方を決めてその読み方で直し、資料の「前回の指摘への対応」に読み方を書く（聞き返して待たない）。スクショを受け取れていなければ、推測で直さずにそう書く。
- 具体的な指示にはそのまま従う。人間が選んだ案や値を、取り込むときに勝手に調整しない。
- 作業ブランチで直し、波及先を同じ回で一気に通す。波及の連鎖は `/design-game-difficulty` の `references/ripple.md`。
- 反映の後の確かめは、SKILL.md の「確かめ」の作り込みの2巡目と同じ。
- 指摘の画面を、指摘と同じ条件で直す前と後に撮る。計測は指摘の画面そのものを測り、自分の読み方を裏付けるだけにしない。
- 指摘のうち他のパズルにも当てはまるものは、守る決まりとして正本（`GAME.md`・`DESIGN.md` 等）か `pitfalls.md` への追記を作業ブランチ（文書の層）に入れ、マージで人間に決めてもらう。

## コンフリクトと部分マージ

作業ブランチは、AGENTS.md の Git 運用のとおり、PR が main とコンフリクトしたときだけ rebase する。

- コンフリクトしたとき: メインが作業ブランチを最新の main へ rebase して衝突を解き、波及の直しを実装役に新しいコミットとして頼み、機械検査を通してから PR を切り出し直す。次の巡の差分の基準は、`git range-diff` で前回のレビュー版に当たる rebase 後のコミットにする。
- 下の層だけがマージされた後に指摘が出たとき: マージ済みの層は main の一部とし、上の PR の base を main に付け替える。残りの層は、マージ済みの最上層のブランチの先端の上に同じ手順で切り直す（main を取り込まない）。直しがマージ済みの層のパスに及ぶなら、その分を新しい層 `<接頭辞>/<元の番号>b-<topic>` として残りの層の下に積む。
