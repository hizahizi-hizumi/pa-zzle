# 最終レビュー

作り切ったものを人間に渡し、指摘を反映する。

## 資料

人間がこのページだけで、遊んで確かめ、問いに答え、マージするか直しを頼むかを決められるようにする。所要は遊ぶ時間を含めて15〜20分。作り方は SKILL.md の「人間への知らせ方」と `assets/final-review-sample.html`。

見本の HTML を複製して中身を置き換え、`assets/page.css` の中身を `<style>` に入れて Artifact にし、回ごとに同じ URL で更新する。画像は Artifact の files で一緒に出す。Artifact が使えないときは、同じ中身を導入調査 Issue のコメントに画像つきで書く。記入欄は作らず、指摘は会話かページへのコメントで受ける。

並びと中身の出どころ:

1. 頭: パズル名、遊び方の1行、盤面の小さな画像。やること3つ（遊ぶ・答える・マージ）と、それぞれの量。
2. 前回の指摘（2回目から）: 指摘の原文、AI の読み方、直す前と後の画像（指摘と同じ条件で撮る）。前回までの直しが戻っていないか。
3. 遊ぶ: 3〜4枚のカード。各カードに、レベル、問い（そこで確かめてほしいこと）、目安の時間、遊ぶ URL。1枚目は一覧から開いて遊び方を読まずに始める。問題は作り込みで試遊役が遊んだものから選ぶ。問いには、「人間に残す」とした所見、試遊役の「人間に確かめてほしい点」、遊んで決める判断、iOS 実機の点（この環境は Chromium しか無いので確かめられないもの。試遊役と作り方の Skill の報告にある点を含む）を、それが起きるカードに割り当てる。時間は試遊役の実時間と基準時間から見積もる。2回目からは直した所だけ。
4. 答える: 3問まで。好みと、遊んで決めるもの。おすすめ（今の作り）と別案を並べる（下の「別案の出し方」）。見た目の違いは、それぞれの選択肢に画像を置く。
5. マージ: PR を下の層から順に、中身と PR へのリンク。
6. 畳む参考（件数つき）:
   - AI が遊んだ結果: 試遊役のレベルごとの時間と一言、見つけて直したもの。人間の初見の感想を消さないよう、遊ぶより後に置いて畳む。
   - 最初の約束から変えたこと: 確かめの記録の「AI が決めたこと」のうち、合意の細部を変えたもの。
   - AI が決めたこと: 確かめの記録の「AI が決めたこと」と仮決定一覧。変えると手戻りが大きい順に、手戻りの範囲つきで。
   - まだ確かめていないこと: 実施できなかった検査（作り方の Skill の報告の「撮っていないもの」を含む）、直していない Minor、main との共通契約のずれ、人が遊ばないと分からないこと（基準時間・面白さ）、人間にしか確かめられないこと（商標など）、並行作業の形跡、答えるからあふれた「人間に残す」所見。
7. 末尾: 指摘は一言とスクショでよいこと。記録画面のコピーで取れる JSON を貼れば難易度の調整に使うこと。

出す前に:

- 遊べる URL は Workers Builds の check run にある版ごとのプレビュー URL にする（測ったものと遊ぶものを一致させるため）。この環境からは開けないので、同じパスが手元の開発サーバーで開けることを確かめる。
- 画像は判断に使うものだけを、同じ条件（端末・テーマ・状態）で撮る。難易度プレビューは既存ゲームの難易度選択と並べ、ピクトグラムはゲーム一覧の実表示サイズで既存と並べる。
- 経緯を渡さない汎用サブエージェント（Opus）にページだけを見せ、最初の画面で何をすればよいか言えるか、分からなかった語はどれかを返させて直す。

## 別案の出し方

- 既定は AI の推奨案で、作ったものには推奨案を入れておく。別案は、人間の好みで決まるか前提が連鎖するもので、AI が自信を持てないものだけ。1回に出す軸は少なく（目安2軸）、難易度に影響する軸は1つまで。
- 難易度への影響は、プレイ条件を引数に取る分析で同じコードのまま測り、表の要点を載せる。
- 遊んで決める別案（補助表示・待った・盤面の上限・ルールの変種など）だけ、推奨案から1軸だけ変えた使い捨てのブランチを作る（PR なし。プレビュー URL はブランチだけで出る）。
  1. メインが作業ブランチから別案のブランチ `<接頭辞>/alt-<軸>` と worktree を作る。
  2. 同じ実装役に、その worktree を書いた作業カードで作らせる。問題集は小さな仮のものにする。
  3. 決まったら、採用案を作業ブランチの worktree で新しいコミットとして作り直させ、別案のブランチと worktree を消す。
- ピクトグラムや難易度プレビューの案は、ブランチにせず画像で並べる。

## 指摘の反映

人間の指摘は短い口語で、1回に複数届く。

- 指摘ごとに、どの画面のどの要素の話かを決める。曖昧なら AI の読み方を決めてその読み方で直し、資料の「前回の指摘」に読み方を書く（聞き返して待たない）。スクショを受け取れていなければ、推測で直さずにそう書く。
- 具体的な指示にはそのまま従う。人間が選んだ案や値を、取り込むときに勝手に調整しない。
- 作業ブランチで直し、波及先を同じ回で一気に通す。波及の連鎖は `/design-game-difficulty` の `references/ripple.md`。
- 反映の後の確かめは SKILL.md の流れ 6（直した所を見る確かめ役を1回と、機械検査）。
- 指摘の画面を、指摘と同じ条件で直す前と後に撮る。計測は指摘の画面そのものを測り、自分の読み方を裏付けるだけにしない。
- 指摘のうち他のパズルにも当てはまるものは、守る決まりとして正本（`GAME.md`・`DESIGN.md` 等）か `pitfalls.md` への追記を作業ブランチ（文書の層）に入れ、マージで人間に決めてもらう。

## コンフリクトと部分マージ

作業ブランチは、AGENTS.md の Git 運用のとおり、PR が main とコンフリクトしたときだけ rebase する。

- コンフリクトしたとき: メインが作業ブランチを最新の main へ rebase して衝突を解き、波及の直しを実装役に新しいコミットとして頼み、機械検査を通してから PR を切り出し直す。次に確かめるときの差分の基準は、`git range-diff` で前回のレビュー版に当たる rebase 後のコミットにする。
- 下の層だけがマージされた後に指摘が出たとき: マージ済みの層は main の一部とし、上の PR の base を main に付け替える。残りの層は、マージ済みの最上層のブランチの先端の上に同じ手順で切り直す（main を取り込まない）。直しがマージ済みの層のパスに及ぶなら、その分を新しい層 `<接頭辞>/<元の番号>b-<topic>` として残りの層の下に積む。
