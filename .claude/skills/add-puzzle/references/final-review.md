# 最終レビュー

作り切ったスタックを人間に1回だけ知らせ、指摘を反映し、人間のマージにつなぐ。人間は自分の都合で見て、経緯を覚えていない前提で読む。資料だけで判断が完結するようにする。

## 1. 資料を作る

`assets/review-sheet.md` の型で Artifact を作る（作業はサブエージェントに任せてよいが、公開前にメインが全体を見る）。リポジトリには置かない。回ごとに同じ URL で更新する。

### 中身（この順に置く）

| 節 | 書くこと |
|---|---|
| 所要時間と途中でやめてよい地点 | 全体の目安（15〜20分に収める）と、「ここまで見て違和感があれば以降は見なくてよい」地点。核（ルール・挑戦・難易度の軸）を最初に置く |
| 何を作ったか | ルールと挑戦の核を3行。iPhone で遊べる URL |
| 認識合わせからの変更点と理由 | 合意した前提から変えたもの。無ければ「無し」 |
| 見てほしい点 | 少なく（目安3点まで）。AI が自信を持てない好み・遊んで決めるもの（試遊で出た好みや面白さの所見を含む）だけ。各点に、試す操作と開く URL |
| AI の試遊レポートの要約 | 遊ぶ側の目線での所見（最初に分からなかったこと、操作のつまずき、レベルごとの手応え、つまらなかった点・理不尽だった点、クリア時の気持ち、既存ゲームとの比較）。直したものと、直さずに残した好みや面白さの所見を分け、根拠の画像を添える。AI の試遊であり人間の体感の代わりではないと書く |
| AI が決めたことと理由 | 覆すと費用が大きい順。上位3件を本文に、残りは折りたたむ。「何も言わなければこのまま」と明記する |
| 前回からの差分と回帰の確認 | 2回目以降。前回の指摘 → AI の読み方 → 今どうなったか（前後の画像） |
| iOS 実機で見てほしい未検証の点 | Chromium で確かめられなかったこと（ダブルタップ、描画順、ピンチ拡大時のはみ出し、スクロールとの競合など） |
| 確かめていないこと・未決 | 意味 lint の未実施、単純なプレイヤーで分からないこと、`TODO(人間判断)` と従った既定、並行作業の形跡、表示名の商標確認（J-PlatPat は人間が行う） |
| PR 一覧とマージの順 | 調査 PR → 段01 → … → 最上段。下から merge commit |

### 作り方の決まり

- **URL**: 版ごとの `Preview URL`（測ったものと遊ぶものを一致させる）を主に、ブランチの `Preview Alias URL` を「最新」として添える（取り方は SKILL.md の「GitHub の操作」）。AI はプレビューを開けないので、描画は手元のビルドで確かめ、そう書く。問題を指定して開く URL は `<URL>/puzzles/<game>/play/<レベル>?problem=<問題ID>`。
- **遊ぶ問題**: レベルごとの代表問題を少数（目安5問）並べる。レベルを伏せる遊び比べは必須にしない（問題の URL のパスと結果画面にレベルが出る）。普通に遊んだ記録の JSON を貼ってもらえれば AI が読んで校正に使う、と添える。
- **画像**: 判断に使う画像だけを、同じ条件（390 / 1280、ライト / ダーク）で並べる。難易度プレビューは直近の既存ゲーム2つの難易度選択と並べ、ピクトグラムはゲーム一覧の実表示サイズで既存と並べる。
- **数値**: 判断に要る1〜2個だけ。測定値の羅列・計測条件・AI レビューの件数は PR 本文に置く。
- **入力の形**: 記入欄を埋めてもらう形にしない。会話での一言・スクショを正式な入力とし、AI が構造化する。Artifact へのコメントは通知されないので、指摘は会話で送ってもらうよう冒頭に書く。
- 案を記号だけで呼ばない。各案を中身で説明する（`references/reporting.md`）。

資料ができたら、最上段 PR 本文に「## 最終レビュー（N回目）」節（日付、資料の URL、知らせたこと）を置き、`references/reporting.md` に従って1回だけ知らせる。

## 2. 選択肢の扱い

- 既定は AI の推奨案で、スタックには推奨案を入れておく。別案を用意するのは、人間の好みで決まるもの・前提が連鎖するもので、AI が自信を持てないものだけ。
- 1回のレビューで別案を出す軸は少なくする（目安2軸まで）。難易度に影響する軸は1つまで。
- **難易度への影響**は、プレイ条件を引数に取る分析で同じコードのまま測る（ブランチを分けない）。固定 seed の同じ候補集合に対し、条件ごとの分布表と単純なプレイヤーの表を出し、資料に要点だけ貼る。
- **遊んで決める別案**（補助表示・状態の知らせ・待った・盤面上限・ルールの変種）だけ、最上段から使い捨ての候補ブランチを作る。
  - 名前は `claude/<prefix>-x-<軸>-<案>`（短く。プレビュー URL のホスト名に収める）。PR は作らない。推奨案から1軸だけ変える。組み合わせは作らない。
  - 問題集は全部を作り直さず、既存の候補集合から条件に合う問題を各レベル数十問選んだ小さな仮の問題集を入れる。
  - PR の無いブランチには CI が走らないので、push の前に手元で `./scripts/verify.sh` を通す。
  - push すると Workers Builds がビルドする。版ごとの URL を資料に載せる。記録（localStorage）はブランチの URL ごとに分かれることを資料に書く。
  - 最上段 PR 本文の「候補」表（軸 / 案 / ブランチ / URL / 測定値 / 結論）に記録する。
- **ピクトグラム・難易度プレビューの案**は、ブランチにせず画像で並べる。
- 決まったら、採用案を原因の段に組み込み直し（下の「3. 指摘の反映」）、候補ブランチを `git push origin --delete <ブランチ>` で消して「候補」表に結論を書く。候補ブランチは積み直しに付いてこないので、レビュー回ごとに使い捨てる。

## 3. 指摘の反映

人間の指摘は短い口語で、1回に複数件届く。スクショや記録の JSON が添えられることがある。

1. **読む**: 指摘ごとに、どの画面・どの要素の話かを決める。曖昧な指摘は、AI がどう読んだかを書き、その読み方で直す（聞き返して待たない）。読み方は資料の「前回からの差分」に必ず出す。スクショを受け取れていないときは、推測で直さずにそう書く。
2. **記録する**: 最上段 PR 本文の「## 最終レビュー（N回目）」節に、指摘の原文の引用、AI の読み方、原因の段、直し、見てほしい点（追加）を書く。この節は次の作り込みでレビュー Agent に渡す「最終レビューでの人間の判断」の元になる。
3. **原因の段と波及を決める**: 下の原因表で原因の段を決め、波及表に沿って影響する段をすべて洗い出す。
4. **直して積み直す**: `references/ai-review.md` の「9. 直しと積み直し」。波及先は一気に通す（ルールを直したなら、難易度・問題集・基準時間・プレビュー・SPEC まで同じ回で直す）。
5. **前後の画像を撮る**: 指摘の画面を、指摘と同じ条件（幅・テーマ・状態）で直す前と後に撮る。計測で確かめるときは、自分の読み方を裏付けるだけにならないよう、指摘の画面そのものを測る。
6. **作り込みをやり直す**: `references/ai-review.md` の全体の作り込み → 資料を更新 → 1回だけ知らせる。

### 原因表

| 指摘の種類 | 原因の段 | 直し方 |
|---|---|---|
| 難易度の体感のずれ（簡単すぎる、帯の中の差が大きい、サイズの逆転） | difficulty | 挑戦の定義から見直す。単純なプレイヤーや特徴量を足し、組み合わせ定義（データ）を作り直す。記録の JSON があれば、問題集から復元して特徴量と所要時間の相関を測り、件数と人数を添える |
| 問題の正当性・ルール判定の誤り | rules | 判定を直し、性質テストを足す。過去の記録が再プレイできなくなるかを確かめて書く |
| 状態の知らせ・正誤の分かりにくさ | play-ui | 盤面の形・色・動きで知らせる。難易度の前提（例: 一致表示が無いこと）が崩れないか、単純なプレイヤーで測り直す |
| 補助操作・操作体系（待った、置き直し、タップ判定） | playable・play-ui | 既存ゲームの同じ操作にそろえる。session・記録の形が変わるなら記録の版を上げる |
| 見た目（ダサい、窮屈、がたつき、はみ出し、重なり順、角丸・枠・影） | 該当する UI の段 | 原因を計測で特定し（boundingBox、画素、座標）、直した後に数値で確かめる。方向の指示（「色をもっと使っていい」など）は、案を画像で並べ、推奨を既定にする |
| 難易度プレビュー | difficulty-select | 既存ゲームのプレビューの意図を読み直し、入れ子・単調性のテストを付けて描き直す |
| ピクトグラム | pictogram | `/design-game-pictogram` で直す。検討記録に選んだ案を追記し、代替案を同じ品質で残す |
| スコア・基準時間 | score | 成績評価文書に比較案とシミュレーションを書く。記録は読み出し時に計算し直す。人間の記録1件だけで全レベルを動かさない |
| 名称 | `display-name.ts` を持つ段 | 表示名を1か所で変え、文書の名称を直す |
| 「楽しくない」など体験全体の否定 | research から | 原因を分析し、合意した意図の範囲で方向を決めて作り直す。意図から外れるなら「成り立たない」として知らせる |

- 人間が選んだ案・確定した値を、確定時に勝手に調整しない。具体的な指示にはそのまま従う。
- 規約・正本の誤りが指摘の原因なら、その正本の直しを同じ変更に含める。
- 特定の指摘の再発防止だけを理由にテストを足さない（`AGENTS.md`「検証」）。振る舞いの契約として要るテストは足す。

### 波及表

直した段から、表の矢印の先をすべて確かめ、必要なら同じ回で直す。

| 変えたもの | 確かめて直す先 |
|---|---|
| ルール・補助・表示（状態の知らせ） | 難易度分析と単純なプレイヤー → 問題集 → 基準時間 → プレビュー → SPEC → 記録の互換 |
| 難易度分析・組み合わせ定義 | 問題集 → 基準時間 → プレビュー → SPEC |
| 問題集 | 基準時間 → プレビュー（問題集の量を写していれば）→ SPEC |
| プレビュー | 難易度の割り当て（プレビューで約束した差が、組み合わせ定義と合うか） |
| 補助表示 | 単純なプレイヤー → 難易度 → 採点（試し置きが得をしないか） |
| session・記録の形 | 記録の版 → 再プレイ → 結果画面 |

- 問題集の段より後で問題集の入力（ルール・生成器・分析）を変えたら、問題集の段で再生成と `--verify` を行う。
- 候補の比較には小さな仮の問題集を使い、全部の再生成は採用案だけにする。生成は再開できる形で回し、件数と `--verify` で完了を確かめてからコミットする。

## 4. 決まったことの反映

同じ変更の中で反映する（`AGENTS.md`）。

- 振る舞い → コードとテスト。
- 守る決まり → SPEC など該当する正本。今の決定として言い切る。
- 理由を失うと戻される判断 → ADR（`/adr-create`）。パズル固有の判断で要ることはまれなので、要否を判断してから作る。
- 実装前提調査の仮決定一覧: 覆った行に「人間の判断（日付、N回目）で取り下げ」、新しい決定を追記する。調査時点の本文は書き換えない。「実装で確定した差分」表を更新する。

## 5. マージと台帳

- 人間のマージが本決定で、別の採用手続きは持たない。マージ後の直しは新しい改善として、最新 `main` から新しいブランチと PR で行う（スタックを開き直さない）。
- 台帳は資料で、マージに付随して更新する。SPEC の段で、台帳の4ゲートを最終の状態にし、導入判断を `正式採用` にし、`PUZZLE-NNN.md` に SPEC へのリンクを足す。マージされなければ main には入らない。
- マージは人間が、調査 PR から順に merge commit で行う。AI はマージしない。
- 人間がマージすると言ったら、`git merge-tree --write-tree origin/main <最上段>` で `main` とのコンフリクトを確かめる。
  - コンフリクトしていなければ何もしない（`main` を取り込まない）。
  - コンフリクトしていれば、最新 `origin/main` へ全段をまとめて1回だけ rebase する（`git rebase --update-refs origin/main` を最上段で実行し、段ごとに衝突を解き、各段の先端で verify し、`git push --atomic --force-with-lease` で push）。許可は認識合わせで得たものを使う。各 PR 本文の Validation に「最新 main（SHA）へ rebase（日付）」と旧コミット ID を書き、CI を一度確かめて知らせる。merge commit で追従しない。
- 導入調査 Issue のクローズは人間の指示で行う（PR は `Refs` で参照し、自動では閉じない）。
- 全段がマージされたら、残っている候補ブランチを消す。
