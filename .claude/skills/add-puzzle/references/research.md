# research の段

認識合わせの合意をもとに、実装の前提を確かめて仮に決め、段の並びを決める。ここで書いたものを、以後の段・再開・レビューが読む。

## 作るもの

| もの | 置き場所 | 中身 |
|---|---|---|
| 導入調査 Issue | GitHub の Issue | 合意節: 合意した前提、得た許可、人間の判断（「成り立たない」への返事・最終レビューの判断）、最終レビュー資料の URL、人間の指摘の原文 |
| 実装前提調査 | `docs/パズル/導入調査/<パズル名>/<パズル名>実装前提調査.md` | 下の「実装前提調査の節」 |
| 調査コード | `scripts/research/<ゲーム ID>_<観点>.py` | seed を固定し、標準ライブラリだけで測る |
| 難易度の資料 | `docs/パズル/README.md` から辿る難易度文書の決まりに従う | 採用ゲートの根拠 |
| 台帳の行の初版 | `docs/棚上げ/パズル候補.csv` と `パズル候補/PUZZLE-nnn.md` | 導入判断と各成立性 |

## 実装前提調査の節

上から順に置く。書き方は `docs/README.md` に従う。

1. 識別表: タイトルの直後に `| 項目 | 値 |` の2列で、パズル名・ゲーム ID・ブランチ接頭辞・候補 ID・SPEC 番号を1行ずつ（`list-used-ids.sh` が予約として読む）。段のブランチは `<接頭辞>/<NN>-<topic>`
2. 根拠の書き分け: 事実・計測（どのスクリプトで）・推測・AI判断（仮決定）
3. 認識合わせの合意
4. 成立性: 問題供給・難易度・スマホ操作・導入判断の観点ごと
5. 仮決定一覧: 決めたこと、理由、比べた案、覆したときに作り直す範囲。spec の段で、この下に「実装で確定した差分」（調査時の計画と違った点）を足す
6. 段の並び: 段の番号・topic・含む段の種類・範囲と完成条件
7. 確かめていないこと

## 調査役の分担

- 観点（問題供給・難易度・スマホ操作・導入判断）ごとに1つ起動する。
- 調査役が書くのは、自分の観点の調査コードと、作業ディレクトリの `<観点>.md` だけ。メインがそれを実装前提調査へまとめてコミットする。

## 段の種類

この並びで積む。段の並びは種類から組み、いくつかを1段にまとめてよい。片方を直すともう片方を必ず作り直す種類（difficulty と problem-pool など）は分けない。失敗パターン集の「いつ」はこの名前で書き、「A〜B」はこの並びの範囲を指す。手本は直近のパズルの同じ種類の段。

| 種類 | 作るもの |
|---|---|
| research | この文書の「作るもの」 |
| rules | ルール・判定・状態とそのテスト（画面なし） |
| playable | 1問を最後まで遊べるプレイ画面（盤面・操作・クリア判定）。入口とプレイ画面のパスだけのカタログエントリと、網羅テスト（`game-catalog.test.ts`）から未掲載のゲームを外す一覧（前例: `git log --all -S gamesNotInCatalogYet`） |
| play-ui | 補助操作（待った・盤面を戻すなど）、状態の知らせ、遊び方、クリア演出 |
| difficulty | 解法器・難易度の判定・生成器と、素朴なプレイヤーのアダプタ（`examples/naive-play-<略称>.ts`） |
| problem-pool | 問題集と生成スクリプト（`--verify` で全問を再検証できる） |
| pictogram | ゲーム一覧のピクトグラム（`/design-game-pictogram`） |
| difficulty-select | 難易度選択の画面と難易度プレビュー |
| score | スコア（評価規則と基準時間） |
| result-records | 結果画面・記録・記録からの遊び直し |
| catalog | 一覧への掲載と並び。網羅テストの除外を外す |
| spec | SPEC、ADR（段カードの番号で）、台帳の行（導入判断を正式採用にする。マージが決定）、実装前提調査の仮決定一覧と「実装で確定した差分」 |
