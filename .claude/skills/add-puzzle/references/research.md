# 調査フェーズ（research）

候補の確認から H1（本実装へ進むか）までの手順。成果物は、紹介 Artifact、導入調査 Issue、`docs/パズル/導入調査/<パズル名>/` の文書群、`scripts/research/` の実験コード、台帳の更新、調査 PR（`claude/<prefix>-00-feasibility`）、段01 PR（`claude/<prefix>-01-research`）。

## 全体の流れ

| 手順 | 担当 | 成果物 | 止まるか |
|---|---|---|---|
| 1 候補の確認 | メイン（検索はサブエージェント可） | 既存候補・近縁候補の一覧、必要なら台帳への1行（調査 PR に入れる） | いいえ |
| 2 イメージ合わせ | サブエージェント → メインが確認 | 遊べる紹介 Artifact | いいえ（H0 と一緒に見せる） |
| 3 H0 ルールの核の合意 | 人間 | 合意したルールの核 | **はい** |
| 4 導入成立性調査 | サブエージェント 2〜4 本並行 → メインが統合 | Issue、4ゲートの文書、実験コード | いいえ |
| 5 実装前提調査（段01） | サブエージェント → メインが統合 | 識別表、仮決定一覧、根拠の区分、スタック表 | いいえ |
| 6 調査 PR・段01 PR | メイン | 2本の PR と Preview URL | いいえ |
| 7 H1 本実装へ進むか | 人間 | 判定と進め方の合意 | **はい** |
| 8 H1 の記録 | メイン | 調査 PR 本文の人間決定節、仮決定一覧の更新 | いいえ |

## 1. 候補の確認

1. `docs/棚上げ/パズル候補.csv`、`docs/パズル/導入調査/`（全体調査 `全体/パズル調査.md` を含む）、`frontend/src/games/` を grep し、同じパズル・名前違い・近縁候補を探す。ルールの言い換え（「ぶつかるまで進む」「一筆書き」など）でも探す。
2. 見つかった候補は ID・名前・現在のゲート状態・既存 Issue / PR を短い表で示す。近縁候補（例: ハミルトン路に対する Hidato・経路接続）は「ブロッカーか」「別ゲームとして成り立つか」を一言添える。統合するかの判断は H1 で人間に聞く。
3. 台帳に無ければ1行追加する（ゲート列は `未確認`、導入判断は `未判断`）。候補 ID は `git fetch --all --prune` の後に `.claude/skills/add-puzzle/scripts/list-used-ids.sh` を実行し、「全ブランチを通した次の番号」を使う（採番の決まりは `references/implementation.md` の「採番」）。この行は調査 PR に入れる。
4. 古い調査文書を読むときは、壊れた参照（`docs/開発/*`、`SCR-00N`、`FR-004`、旧ディレクトリ名など）を正本扱いしない。TODO(人間判断): 資料内の壊れた参照を直すか。既定: 資料は維持しないものなので直さずに読み飛ばす。

## 2. イメージ合わせ（紹介 Artifact）

人間と AI が同じパズルを想像しているかを、調査に入る前に確かめる。

- 遊べる紹介 HTML を Artifact として作る。リポジトリには入れない（`scripts/research/` にも置かない）。
- 入れるもの: ルールの3コマ程度の図、遊べる小さなデモ（スマホ幅で操作できる）、近縁パズルとの違い、名前の候補、H0 で決めたいこと。
- メインが Playwright で開き、描画・操作・ブラウザエラー 0 を確かめてから見せる。確かめられなかった点はそう書く。

## 3. H0 ルールの核の合意（人間関門）

ここだけは仮決定で進めない。紹介 Artifact と一緒に、次を1画面で示して合意を取る。

- 基本ルール（盤面・操作単位・移動や配置の規則）
- クリア条件と、ミスとして扱うもの
- 解の扱い（一意解を要求するか、同値解を許すか）と、推測を要する問題を出すか
- 想定する盤面の大きさの幅
- 面白さの仮説（何を推論し、何を先読みするパズルか）
- 調査で比較して決めること（例: 床の種類、手がかりの種類）と、人間がいま決めること

人間の回答は「人間決定（H0）」として、導入調査 Issue の本文（`assets/research-issue.md` の「人間決定（H0, YYYY-MM-DD）:」の行）、以後のすべてのサブエージェント指示、調査文書の冒頭に書く。調査 PR を作ったら、その本文に「## 人間決定（H0, YYYY-MM-DD）」節として写す。

## 4. 導入成立性調査

### Issue

H0 の直後に、`assets/research-issue.md` を使って導入調査 Issue を起票する（最新の型は #514）。Issue の題はテンプレートのコメントにある形にし、本文は題を繰り返さずに「参考:」の行から始める。候補 ID、近縁候補と Issue 番号、参照製品、人間決定（H0）を差し込む。Issue は必ず立てる（`docs/棚上げ/README.md`「具体的な作業は Issue で扱う」）。

### 4ゲートと確認すること

| ゲート | 確認すること | 通過条件 |
|---|---|---|
| 1 問題供給 | 採用ルールと比べて採らない変種、生成方式、一意性または可解性の機械検証、seed 再現、性能（生成と検証の時間、事前生成で回避できるか）、多様性・同型除外、自明な問題の抑制 | 継続的に妥当な問題を供給する方法があり、生成・検証・性能・多様性に致命的な問題がない |
| 2 難易度運用 | まず人間の挑戦を言語化する（何を推論し、何を先読みするか）→ 人間向け解法器の特徴量（探索ノード数や計算時間は使わない）→ 帯1〜5を作り分けられるか、帯ごとの供給率と時間、生成条件で分布が動くか、評価不能の数 | 最終的な区分・閾値は未確定でも、狙った帯を作り分け、後続で校正できる現実的な方法がある |
| 3 スマホプレイ | 操作方式の比較、320/360/375/390px でのマス幅、ページスクロールとの競合、誤操作からの復帰、色に頼らない識別、代替入力（WCAG 2.5.7）、盤面上限 | 現実的な盤面サイズで正確に操作できる方式が少なくとも1つ成立する。上限があれば明示する |
| 4 導入判断 | 市場実績（一次表示を確かめたかを明記）、名称・権利（一般名を使う、避ける名称、表示名の仮名の候補。J-PlatPat の確認は人間が H2 までに行う）、実装量と保守、既存の `games/<game>/` 構成への載り方、近縁候補との差異表、保留の解消条件 | 結論を `実装候補` / `条件付き保留` / `見送り` から選び、保留なら不足している未知を具体的に書く |

難易度は `docs/パズル/難易度開発手順.md` の採用ゲートに従う。特に次を守る。

- 生成条件をそのまま難易度とみなさない。人間の解法過程で観測する。
- 挑戦と無関係な作業量・問題規模で段階を作らない。盤面サイズ・要素の量・推論の種類など複数の要因の組み合わせで考え、ユーザー向けの短い説明で言える形にする。
- 最難の帯が簡単すぎないか、帯の中のばらつきが大きすぎないかも見る。
- 上のレベルほど盤面を小さくしない（`references/implementation.md` の「仮の決まり」）。

### サブエージェントの分け方

観点別に 2〜4 本を並行で起動する。代表的な分け方は次のとおり。

| 担当 | 内容 | 成果物 |
|---|---|---|
| 供給・難易度 | ルール変種の比較、生成器と一意性検証、人間向け解法器、帯1〜5の分布 | `<パズル名>供給実験.md`・`<パズル名>難易度PoC.md`（または `<パズル名>供給・難易度実験.md`）、`scripts/research/<game_snake>_*.py` |
| スマホ操作 | 操作試作（`/tmp/<game>-work/` に置く）、Playwright でマス幅・タッチ・pageerror 0 | `<パズル名>スマホ操作PoC.md` |
| 名称・権利・市場 | 一般名、避ける名称、表示名の仮名の候補、市場実績、近縁候補との差異 | `<パズル名>名称・権利調査.md` |
| 実装前提の草稿 | 段01の草稿。他の担当の結果に依存する箇所は `【統合時に記入】` で空ける | `<パズル名>実装前提調査.md` の草稿 |

`<game_snake>` はゲーム ID のハイフンをアンダースコアにしたもの（例: `hamiltonian_path`）。

指示に必ず入れること。

- 人間決定（H0 の結果）
- 書式の手本: 直近パズルの同じ文書（main 上なら `docs/パズル/導入調査/リフレクション/`、ブランチ上なら `git show origin/claude/tsume-shogi-01-research:<path>`）
- 実験コードの決まり: 標準ライブラリだけ、argparse のサブコマンド、seed 固定、`selfcheck` サブコマンド、`scripts/research/<game_snake>_<topic>.py`
- 試作 HTML・一時ルートは PR に入れない。`/tmp/<game>-work/` に置く
- コミットしない。担当外の文書を触らない
- 根拠の区分（下記）を付ける

サブエージェント同士で結論が食い違ったら（例: 一意解に仕切りが必要なのに操作試作は壁なしを推奨）、メインが食い違いを解消する追加確認を指示してから統合する。完成したものから順にメインがコミットし、未完成の草稿はコミットしない。

### 導入成立性調査の文書の型

要約文書 `<パズル名>導入成立性調査.md`（または `<パズル名>調査.md`）に次を置く。

- 冒頭: 調査日、Issue 番号、人間決定（H0）、詳細文書への索引
- 状態表: ゲート / 判定 / 根拠の要約（詳細文書へのリンク）
- 基礎仕様候補: 採用案と、比べて採らなかった変種の表
- ゲート1〜4（上の表の観点）
- この調査で確定しないこと、参考文献・事例

## 5. 実装前提調査（段01の中身）

`<パズル名>実装前提調査.md` は、4ゲートだけでは本実装の後に決め直す項目が多いことへの対策で、本実装の論点を実装前に整理する。手本は `docs/パズル/導入調査/リフレクション/リフレクション実装前提調査.md`（main 上）と、`origin/claude/tsume-shogi-01-research` の同名文書。

### 根拠の区分

見出し語で根拠を書き分ける: **事実（リポジトリ）** / **事実（計測）** / **外部知見** / **導出** / **推測** / **人間決定** / **AI判断（仮決定）**。推測は「試遊で確かめる必要がある」と書く。

### 章立て

0. **識別表**（冒頭に必ず置く）: パズル名 / ゲーム ID / ブランチ接頭辞 / 候補 ID / SPEC 番号（SPEC の段で採番するまで「未採番」）
1. 目的、根拠の区分、本実装の進め方（AI判断）
2. 現時点の導入判断（観点 × 状態 × 根拠 × 残り。観点に体験価値と名称・権利を含める）
3. 現在の pa-zzle から導かれる条件（ゲーム共通仕様・`game-structure.md`・既存ゲームの de facto 標準）
4. 守る遊びの核と `GAME.md` の原則への対応
5. 近縁候補との関係、採用ルールと除外する変種、問題成立条件
6. 問題 identity と供給方式（事前生成の問題集を基本にする）
7. 視覚表現、操作、誤りの扱いと状態の知らせ（SPEC-017）、補助操作とやり直し（SPEC-007）、クリア
8. 難易度: 挑戦の定義、基準とするプレイ条件、5段階の組み合わせモデル、評価不能と提供範囲外、各レベルの供給見込み
9. スマートフォン、プレイ評価（良いプレイの定義・評価に使う事実・配点は仮置き）、記録・再プレイ・診断、表示名（仮名）
10. **仮決定一覧**: 論点 / 仮決定 / 理由 / 比べた案 / 最終レビューで判断してほしい点。人間判断が出た行は「人間判断（日付）で取り下げ」「人間判断（日付）で確定」を追記する
11. **本実装スタック**: 段 / branch `claude/<prefix>-NN-<topic>` / 範囲 / 完成条件（`references/implementation.md` の標準スタックから足し引きする）。この表が段ごとのレビューに渡す「段の範囲と完成条件」の正になる
12. **実装へ進むための残件**: 必須（全段実装後の最終レビューで行う）/ 公開前 / 今回は扱わない

SPEC 番号は段01で予約しない。仮であることと最終レビューで判断してほしい点は、この仮決定一覧だけに置く（SPEC には書かない）。

### 差し戻しに強い作り（本実装の進め方に書く）

- 難易度の組み合わせ定義はデータで持ち、分類コードへ埋め込まない。
- 表示の切り替えが論点になるもの（補助表示の有無など）は1か所で切り替えられる作りにする。
- 配点・基準時間は仮置きと明記し、記録には生のプレイ事実だけを保存して評価は読み出し時に計算する。
- 利用者に見える名称は `display-name.ts` の1か所から参照する。
- ピクトグラムは採用案だけでなく代替案と検討記録を残す。

## 6. 調査 PR・段01 PR

H1 の前に2本の PR を出し、人間が開ける資料をそろえる。作成・本文の更新は SKILL.md の「GitHub の操作」に従う。

- 台帳: 導入成立性調査の最後のコミットで `パズル候補.csv` の行（手順1で足した行を含む）の4ゲートの状態を更新し、`パズル候補/PUZZLE-NNN.md` を索引として作る（調査内容は複製しない）。状態値は `docs/棚上げ/README.md` の例（`未確認` / `確認中` / `通過`）を使い、条件付きの場合はその条件を索引に書く。段01では台帳の段階を変えない。
- 調査 PR: `claude/<prefix>-00-feasibility`、base は `main`。導入成立性調査の文書・実験コード・台帳を入れる。本文に「## 人間決定（H0, YYYY-MM-DD）」節と `Refs #<Issue番号>` を書く。
- 段01 PR: `claude/<prefix>-01-research`、base は調査 PR のブランチ。以後のスタックの最下段になる。本文に `Refs #<Issue番号>` と Stack 表を書く。
- PR 本文の型は `references/implementation.md` の「PR 本文」に従う。
- 両 PR の CI `quality-gate` が success であることを一度確かめる。

## 7. H1 本実装へ進むか（人間関門）

- 開ける資料: 調査 PR と段01 PR の URL、導入成立性調査と実装前提調査の GitHub 上の URL（`https://github.com/<owner>/<repo>/blob/claude/<prefix>-01-research/docs/パズル/導入調査/<パズル名>/<文書名>.md`）、紹介 Artifact の URL

## 8. H1 の記録

- 調査 PR 本文に「## 人間決定（H1, YYYY-MM-DD）」節を追記する。人間の回答の要旨、導入判断の結論、進む・進まない、統合の判断、段構成、表示名の仮名、force-push の許可の範囲を書く。
