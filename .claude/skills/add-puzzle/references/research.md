# 調査

認識合わせの合意をもとに、実装の前提を確かめて仮に決め、実装前提調査に書く。ここで書いたものを、以後の実装・再開・レビューが読む。作業ブランチは `branches.md`、作る順番は `build-order.md`。

## 作るもの

| もの | 置き場所 | 中身 |
|---|---|---|
| 導入調査 Issue | GitHub の Issue（題 `導入調査: <パズル名>`） | 合意節と、確かめごとの記録（SKILL.md の「記録」） |
| 実装前提調査 | `docs/パズル/導入調査/<パズル名>/<パズル名>実装前提調査.md` | 下の「実装前提調査の節」 |
| 調査コード | `scripts/research/<ゲーム ID>_<観点>.py` | seed を固定し、標準ライブラリだけで測る |
| 移植の期待値 | `scripts/research/<ゲーム ID>_<観点>.expected.json` | 採った案の、seed ごとの結果（解の数、探索の打ち切りに関わる量、採否と、採否の規則で除いた問題）。使い方は `/design-game-difficulty` の検査 F2 |
| 難易度の資料 | `docs/パズル/README.md` から辿る難易度文書の決まりに従う | 採用ゲートの根拠。難易度の観点の調査役が下書きする |
| 台帳の行 | `docs/棚上げ/パズル候補.csv` と `パズル候補/PUZZLE-nnn.md` | 導入判断と各成立性。対象パズルの行がすでにあれば、その行を更新する |

## 実装前提調査の節

上から順に置く。実装前提調査は資料で、書き方は `.claude/rules/documents.md` と `docs/パズル/README.md` に従う。決まりとその意図の正本は、マージで仕様（SPEC）に移したもの。

1. 識別表: タイトルの直後に `| 項目 | 値 |` の2列で、パズル名・ゲーム ID・ブランチ接頭辞・候補 ID・SPEC 番号・導入調査 Issue 番号を1行ずつ（ほかのファイルが「識別表」と言うときはこの項目を指す）。SPEC 番号と候補 ID は、origin のどのブランチでも対象パズル以外に使われていないことを `git ls-tree` と `git grep` で確かめて予約する（台帳に対象パズルの行があれば、その ID を使う）
2. 根拠の書き分け: 事実・計測（どのスクリプトで）・推測・AI判断（仮決定）
3. 認識合わせの合意
4. 成立性: 観点ごと
5. 仮決定一覧: 決めたこと、理由、比べた案、覆したときに作り直す範囲。作り込みの後に、この下へ「実装で確定した差分」（調査時の計画と違った点）を足す
6. 作る順番: `build-order.md` の表から、このパズルで使う項目と、その範囲・完成条件
7. PR の切り方: `branches.md` の「PR の切り方」から、このパズルの層と各層に入るパス
8. 確かめていないこと

## 調査役の分担

観点ごとに `puzzle-researcher` を1つ起動し、観点カードで観点と問いを渡す。問題供給と図鑑と問題の特徴は、難易度の観点が決めた案の分類で測るので、難易度の観点の後に起動する。難易度の観点の結果にある反例探しの頼み（SKILL.md の「確かめ」の表の「調査の後」）を先に回し、反例が出たら難易度の調査役に案を直させてから起動する。ほかの観点は難易度と同時に起動する。調査役が書くのは、自分の観点の調査コード・移植の期待値と、作業ディレクトリの `<観点>.md`（難易度の観点では難易度の資料の下書きも）だけで、メインがそれを実装前提調査へまとめてコミットする。

| 観点 | 問い |
|---|---|
| 問題供給 | 問題集の件数と並び。どちらも遊ぶ人に見える結果になる（`/design-game-difficulty` の守ること 8）ので、供給の都合ではなく、レベルごとにどれだけ集められると「もう1問」になるかで件数を決める。その件数を、想定の盤面の大きさごとの一意解の割合と生成時間でそろえられるか。問題集の大きさ |
| 難易度 | 挑戦の定義。難しさの源を全部当ててつまみの案を広げ、案ごとに上限・隣のレベルの分かれ方・素朴な解き方で押し切れる割合・数え方でレベルが変わる割合・収率を小さな生成で測って比べ、1つに決める。各レベルを利用者向けの一言で言えるか。調査役は `/design-game-difficulty` を入口「`/add-puzzle` の調査」で起動して進める |
| 図鑑と問題の特徴 | 始めたときの盤面で分かる特徴（SPEC-026「問題の特徴」）のうち、遊ぶ人が次の1問を選ぶ切り口になるもの。案ごとに3つを測って決める: レベルの中で値が分かれるか（1つのレベルの値の種類と、各値の問題の数）、ほかの案の特徴と重ならないか（特徴どうしの順位相関）、難易度の写しにならないか（難易度の観点で決めた読みの量との順位相関。ADR-0004 の背景）。決めた特徴の値の書き方と、数をまとめる幅 |
| 音 | どの操作の瞬間に何を返すか（`DESIGN.md`「音」に当てる）と、題材のどの素材から作るか。既存ゲームの効果音の本数と合計の大きさを測り、このゲームの目安を決める（大きさが効く理由は ADR-0011 と `frontend/src/frontend.tsx`: タイトルで全部の効果音を読み込んでから入る） |
| スマホ操作 | スマホ縦画面の最小幅でのマスの大きさ（既存ゲームと比べる）、盤面と全操作が一画面に収まる盤面の上限、操作とスクロールの競合 |
| 導入判断 | 近い既存ゲーム・候補との違い、表示名（商標を避けた一般名）、台帳の各成立性の値 |
