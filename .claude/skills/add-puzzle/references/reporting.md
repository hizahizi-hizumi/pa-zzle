# 人間への報告・提示

人間へ報告・質問・提案を書く前に毎回読む。人間はスマホで読み、スマホで触って確かめる前提で書く。

## いつ知らせるか

- 関門（H0・H1・H2）に来たとき。H1 は調査 PR と段01 PR を出してから知らせる。
- 人間レビューに出せる状態（`references/ai-review.md` の「人間へ渡す条件」を満たした状態）になったとき。
- 人間の指摘への対応が終わり、資料を更新したとき。
- 進められない障害（権限、環境、正本どうしの矛盾）に当たったとき。

それ以外では止まって知らせない。残作業（AIレビュー、`--verify`、PR 本文の更新など）を抱えたまま「レビューをお待ちしています」と書いて止まらない。止まる前に、そのフェーズの完了条件を満たしているかを確かめる。

## 書き方

- 結論から書く。最初の1〜2行で「何ができたか」「人間に何をしてほしいか」を言う。
- 触る URL（Preview URL、問題 ID 付きの URL、Artifact）と画像を添える。URL は人間が調整しなくてよいように、見てほしいパターンすべてを並べる。
- scratchpad や `/tmp` のパスを渡さない。人間が開ける形（Artifact、Preview URL、画像）にする。
- 分からない内部用語（「両方のブランチ」「段10と段11」など）を説明なしに使わない。どの PR・どの画面かを具体的に書く。
- 推測と実測を分ける。「計測した」「画面で見た」「コードから推測した」「確かめていない」を書き分ける。
- 自分で画面を見てから報告する。サブエージェントの報告やテスト結果だけで「確認済み」と書かない。スクショを受け取れないときは、推測で答えずにそう書く。
- 確かめられなかったこと（iOS Safari 実機、意味 lint 未実施など）を明記する。

## 案を示すとき

- 案を記号（案A、案c）だけで呼ばない。各案を中身で説明する。難易度なら「判定に使うつまみ」と「ユーザー向けヘルプに出す一言の説明」で示す。
- 推奨には具体的な利点を書く。「一般的だから」だけで推奨しない。不利な点も並べる。
- 見た目の案は、同じ条件（同じ幅・テーマ・状態）で並べた画像で示す。
- 人間が選んだ案・確定した案を、確定時に勝手に変えない。見せたものから余計な修正をしない。

## 聞くこと・聞かないこと

- 人間に聞くのは、関門（H0・H1・H2）と人間レビュー領域（ピクトグラム / 難易度プレビュー / ゲーム体験（見た目を含む）/ 難易度の体感 / スコアの納得感）だけ。
- それ以外は、規約（`AGENTS.md`・`APP.md`・`GAME.md`・`DESIGN.md`・ゲーム共通仕様）と既存ゲームの前例で判断して進め、仮決定一覧に残す。念押しの確認を重ねない。
- ゲームの性格を変える設計上の重要判断（推測を要する問題を出すか、一意解を要求するか）は H0 に、近縁ゲームと統合するかは H1 に含めて聞く。人間を通していない判断を前提にしない。
- 規約に無い前提（例: main への追従方法）を自分で置かない。`AGENTS.md` と SKILL.md の制約に従う。
- `TODO(人間判断)` は作業中に聞かない。既定どおり進め、フェーズを終えたときの報告で「未決と従った既定」として挙げる。

## してはいけないこと

- PR 監視、定期確認、スケジュール実行を提案・設定しない。
- 人間の指示より Stop hook などの自動の催促を優先しない（指示の無い push、未完成の作業のコミットをしない）。
- 謝罪や経緯の説明で報告を長くしない。誤りがあったら、何が誤りで、どう直したかを短く書く。

## 報告の型

関門・レビュー依頼の報告は次の順にする。

1. 結論（1〜2行）
2. 見てほしいもの（URL・画像・資料）と順番
3. 判断してほしいこと（各項目に、AI の推奨とその具体的な利点・不利な点）
4. AI が決めて進めたこと（仮決定の要約。詳細は資料へのリンク）
5. 確かめていないこと・残っていること・未決の `TODO(人間判断)` と従った既定
