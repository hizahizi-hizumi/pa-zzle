# 人間への連絡

人間へ書く前に毎回読む。人間はスマホで読み、スマホで触って確かめる前提で書く。

## いつ知らせるか

知らせるのは次の3つだけ。

| 場面 | 返事 |
|---|---|
| 認識合わせ（`references/alignment.md`） | 待つ。返事を待つのはここだけ |
| 最終レビューの資料ができたとき、指摘を反映して資料を更新したとき（`references/final-review.md`） | 待たない。人間の都合で見てもらう |
| 調査で「合意したパズルが成り立たない」と分かったとき（`references/research.md`） | 待つ（方向を決めてもらう） |

- 途中で連絡しない。進み具合の報告、返事を待たない途中の見本、念押しの確認を送らない。人間はそれを見ない。
- 未完成のものを判断させない。残作業（品質の作り込み、`--verify`、PR 本文の更新など）を抱えたまま知らせない。知らせる前に、その場面の条件（`references/ai-review.md` の「人間に見せる条件」、`references/final-review.md` の「0. main との衝突を確かめる」、各段の CI）を満たしたかを確かめる。
- 迷ったら AI が決めて進め、最終レビュー資料に書く。前提を変える必要が出ても、合意した意図の範囲なら同じ。
- 権限や環境の障害は、回避して進める（MCP が無ければ `gh api` など）。回避できず作業そのものを続けられないときだけ、「成り立たない」と同じ形（理由と、人間にしてほしいこと）で知らせる。
- `TODO(人間判断)` は作業中に聞かない。最終レビュー資料で「未決と従った既定」として挙げる。

## 書き方

- 結論から書く。最初の1〜2行で「何ができたか」「人間に何をしてほしいか」を言う。
- 触る URL（版ごとの Preview URL、問題 ID 付きの URL、Artifact）を添える。URL は人間が手で直さなくてよい形にする。
- scratchpad や `/tmp` のパスを渡さない。人間が開ける形（Artifact、Preview URL、画像）にする。
- 内部用語（「段10と段11」「両方のブランチ」など）を説明なしに使わない。どの PR・どの画面かを具体的に書く。
- 計測・目視・推測を書き分ける。「計測した」「画面で見た」「コードから推測した」「確かめていない」。
- 自分で画面を見てから書く。サブエージェントの報告やテスト結果だけで「確認済み」と書かない。
- 確かめられなかったこと（iOS Safari 実機、意味 lint など）を明記する。
- 謝罪や経緯の説明で長くしない。誤りがあったら、何が誤りでどう直したかを短く書く。

## 案を示すとき

- 案を記号（案A、案c）だけで呼ばない。中身で説明する。難易度なら「判定に使うつまみ」と「利用者向けの一言の説明」で示す。
- 推奨を既定にし、何も言わなければ推奨で進めると書く。推奨には、このパズルで何が良くなるかを具体的に書く。「一般的だから」だけで推奨しない。不利な点も並べる。
- 見た目の案は、同じ条件（同じ幅・テーマ・状態）で並べた画像で示す。
- 人間が選んだ案・確定した案を、確定時に勝手に変えない。

## 型

### 最終レビューを知らせる

1. 結論（1〜2行）: 何ができたか、資料の URL、所要時間の目安
2. 見てほしい点（少なく）と、途中でやめてよい地点
3. 2回目以降は、前回の指摘への対応の要約（詳細は資料）

### 成り立たないと知らせる

1. 結論（1行）: 合意したどの前提のもとで、何が成り立たないか
2. 根拠: 何を試し、何を測ったか（計測と推測を分ける）
3. 代案 2〜3: 合意した意図に近い順に、それぞれ何を変え、何が成り立ち、何を失うか。推奨を既定にする
4. 返事をもらったら、合意節を更新して調査を続ける

## してはいけないこと

- PR 監視、定期確認、スケジュール実行を提案・設定しない。
- 人間の指示より Stop hook などの自動の催促を優先しない（指示の無い push、未完成の作業のコミットをしない）。
