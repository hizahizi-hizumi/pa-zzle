# 認識合わせ

指示を受けてから着手するまでの手順。人間と AI が同じパズルを想像しているかを確かめ、覆ると大きな作り直しになる前提だけを決めてもらい、着手時の許可をまとめて得る。人間の返事を待つのはこの場面だけ。

返す文面は `assets/alignment.md` の型で作る。

## 品質の基準

- **時間より中身の確かさを優先する。** 指示から10分ほどは人間が画面の前にいることが多いが、これは「すぐ見てもらえる可能性が高い」目安で、締め切りではない。確かめが必要な前提は確かめてから出す。
- **速くしたいときは、確かめを削らずに聞く点を絞る。** 聞くのは「覆ると大きな作り直しになる前提」だけ。それ以外は AI が決め、「AI が決めて進めること」に並べるか、最終レビュー資料に書く。
- **確かめていないことは推測と明記する。** 前提ごとに「確かめた（何で）」か「推測」かを書く。
- **AI の想定を言い切って示す。** 「どうしますか」と白紙で聞かず、想定・理由・覆ったときに作り直す範囲を添えて、異論があるときだけ答えればよい形にする。
- 案を記号だけで呼ばない。推奨の理由を「一般的だから」で済ませない（`references/reporting.md`）。

## 1. 候補と近いパズルを調べる

1. `docs/棚上げ/パズル候補.csv`、`docs/パズル/導入調査/`（`全体/パズル調査.md` を含む）、`frontend/src/games/` を grep し、同じパズル・名前違い・近縁を探す。ルールの言い換え（「ぶつかるまで進む」「一筆書き」など）でも探す。
2. 見つかったものは ID・名前・ゲートの状態・既存の Issue / PR を短く控える。近縁は「別ゲームとして成り立つか」を一言添える。統合するか別ゲームにするかは、覆ると大きな作り直しになる前提として聞く。
3. 古い調査文書の壊れた参照（`docs/開発/*`、`SCR-00N`、`FR-004`、旧ディレクトリ名など）は正本扱いせず、読み飛ばす。

## 2. 中身を作る

| 項目 | 書くこと |
|---|---|
| ルールとクリア条件 | 盤面・操作単位・移動や配置の規則、クリア条件、ミスとして扱うもの |
| 想定盤面 | 大きさの幅、要素の量、スマホ縦画面での1マスの幅の見込み |
| 何を考えるのが面白いか | 挑戦の1文（何を推論し、何を先読みするか）。作業量や罰で難しくするものではないこと |
| 近い既存パズル・候補との違い | 1で見つけたものとの違い |
| 覆ると大きな作り直しになる前提 | 下の表から、このパズルで効くものを選ぶ。AI の想定・根拠（確かめた / 推測）・覆ったときに作り直す範囲 |
| AI が決めて進めること | 聞かないが、知っておいてほしい決めごと（数行） |
| 確かめたこと・確かめていないこと | 何を何で確かめたか |
| 着手時の許可 | 下の「着手時の許可の聞き方」 |

### 覆ると大きな作り直しになる前提の候補

人間が AI の想定を覆してきた論点を種にする。全部は聞かない。このパズルで覆り得て、覆ると複数の段（難易度・問題集・スコア・プレビュー）をやり直すものだけを選ぶ。目安は3〜6点。

| 前提 | 覆ったときに作り直す範囲 |
|---|---|
| 盤面の大きさを難易度のつまみに使うか、上位ほど広い盤面を許すか | 生成器・難易度・問題集・プレビュー・基準時間 |
| 最上位のレベルをどこまで難しくするか（誰向けか） | 難易度・問題集 |
| 補助・状態の知らせ（一致・違反・正誤の表示）をどこまで出すか | 解法器と単純なプレイヤー・難易度・問題集・スコア |
| 推測を要する問題を出すか | 生成器・解法器・難易度 |
| 一意解を要求するか、同値解を許すか | 生成器・検証・難易度の再現性 |
| 待った・置き直しの有無と、良いプレイの定義（何を減点するか） | session・記録の形・スコア |
| ルールの変種（床の種類・手がかりの種類など）のどれを採るか | ほぼ全段 |
| 近縁ゲームと統合するか、別ゲームにするか | スタック全体 |
| 盤面の上限（スマホで操作できる最大） | 生成器・難易度・問題集 |

## 3. 確かめが必要な前提を確かめる

覆ると作り直しになり、しかも机上で答えが出ないものは、出す前に小さく確かめる。観点ごとに Opus サブエージェントを並行で起動してよい（成果物は `/tmp/<game>-work/alignment/`、リポジトリに入れない、コミットしない）。導入成立性調査の代わりではないので、問いに答える最小限にとどめる。

| 前提 | 確かめ方 |
|---|---|
| 一意解の問題を作れるか | 標準ライブラリの Python で生成器と一意性検証を書き、想定盤面の最小・最大で数十問作れるか、1問あたりの時間を測る |
| スマホで操作できる盤面か | 320 / 390px で想定最大盤面の1マスの幅を計算する（44px 前後を目安に既存ゲームの最小と比べる）。必要なら操作試作の HTML を Playwright で開き、マスを正確に押せるかを測る |
| 挑戦が成り立つか（最上位が自明にならないか） | 素朴な解き方（貪欲・1手ずつの試し置き）で、生成した難しめの問題が解けてしまう割合を測る |
| 補助表示で試行錯誤に落ちないか | 認識合わせでは確かめきれないことが多い。推測と書き、調査と品質の作り込みで単純なプレイヤーを使って測ると添える |
| 名称・市場 | 一般名と、避ける名称の当たりを付ける（確定は調査で行う） |

確かめた結果、合意する前から成り立たないと分かったら、その理由と代案を中身に書く。

## 4. 紹介 HTML（必要なとき）

ルールを文で伝えにくいときは、軽く遊べる紹介 HTML を Artifact として作る。

- 入れるもの: ルールの3コマ程度の図、スマホ幅で操作できる小さなデモ、近縁パズルとの違い。
- メインが Playwright で開き、描画・操作・ブラウザエラー 0 を確かめてから見せる。確かめられなかった点はそう書く。
- リポジトリには入れない。

## 着手時の許可の聞き方

文面の末尾に、次をまとめて「既定で許可をもらう」形で並べる。返事に異論が無ければ許可を得たとみなす。

- このパズルのスタックのブランチ（`claude/<prefix>-*`）への `git push --force-with-lease`（直しを原因の段に入れて上の段を積み直すため）
- 候補ブランチ（`claude/<prefix>-x-<軸>-<案>`、PR なし）の作成と削除（最終レビューで遊んで決める別案のため）
- 段の組み替え（段の分割・統合・並べ替え）

## 返事を受けたら

- 合意したら、導入調査 Issue の「## 認識合わせの合意（YYYY-MM-DD）」節に記録して調査へ進む（`references/research.md` の手順1）。中身は、合意したルール・挑戦・前提（人間が変えた点はその内容）と許可の範囲。経緯ではなく決まったこととして書く。以後のすべてのサブエージェント指示に、この節を「認識合わせの合意内容」として渡す。
- 返事が一部の前提だけに触れていれば、ほかは提示した想定で合意とみなす。
- 返事の意味が二通りに読めて、どちらかで作り直す範囲が大きく変わるときだけ、その点を一言で聞き直す。
- 返事が来るまで調査に入らない。
- 合意後に前提を変える必要が出たら、合意した意図の範囲で AI が決めて進め、最終レビュー資料の「認識合わせからの変更点と理由」に書く。意図の範囲に収まらないときは「成り立たない」として知らせる（`references/research.md`）。
