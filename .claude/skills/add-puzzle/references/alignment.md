# 認識合わせ

人間と AI が同じパズルを想像しているかを確かめ、覆ると大きな作り直しになる前提だけを決めてもらい、後で要る許可もここでまとめて得る。

## 確かさの基準

- 確かめが要る前提は確かめてから出す。速くしたいときは確かめを削らず、聞く点を絞る。
- 前提ごとに「確かめた（何で）」か「推測」かを書く。
- 覆ると作り直しになり、机上で答えが出ないものは、出す前に小さく確かめる。例: 想定盤面の最小と最大で一意解の問題を作れるか小さな生成器で測る、スマホ縦画面の最小幅でのマスの大きさを計算して既存ゲームと比べる、素朴な解き方（貪欲・1手ずつの試し置き）で難しめの問題が解けてしまう割合を測る。

## 先に調べるもの

- main の作業ツリーだけでなく、全リモートブランチ・オープンの PR と Issue。名前違いやルールの言い換え（「ぶつかるまで進む」「一筆書き」など）でも探し、候補台帳・導入調査・既存ゲームも見る。
- このセッションから origin へスタックのブランチを push できるか（`git push --dry-run` で、識別表のブランチの形の名前を試す）。できなければ、プレビュー URL で確かめられないので、覆ると作り直しになる前提として示す。
- 同じパズルが進行中なら、引き継ぐか作り直すかを前提として聞く。近縁があれば、統合するか別ゲームにするかを聞く。

## 示すもの

- ルールとクリア条件（クリアの型、ミスとして扱うもの）
- 想定盤面の大きさと、スマホでの1マスの大きさの見込み
- 何を考えるのが面白いか（何を推論し、何を先読みするか）。作業量や罰で難しくするものではないこと
- 近い既存パズル・候補との違い
- 覆ると大きな作り直しになる前提。「どうしますか」と白紙で聞かず、想定を言い切って異論があるときだけ答えればよい形にする
- AI が決めて進めること（返事不要）、確かめたこと・確かめていないこと
- 後で要る許可: このパズルのスタックのブランチの push と force-push（段ごとのプレビュー URL で確かめ、直しを原因の段に入れて積み直すため）、段の PR と導入調査 Issue の作成、遊んで比べる別案の使い捨てブランチの作成と削除、段の組み替え

文面は、返事が要る「覆ると大きな作り直しになる前提」（各点を想定1行・根拠1〜2行・作り直す範囲1行）と許可を先頭に置き、画面1〜2枚で読める長さにする。ルール・面白さ・近縁・確かめたことは、その後に短く添える。試算の詳細は書かず、結論と数値だけにする。

ルールを文で伝えにくいときは、スマホで軽く遊べる紹介 HTML を Artifact で添える（描画・操作・ブラウザエラーを確かめてから出す）。

## 聞くべき前提の候補

人間が AI の想定を覆してきた論点。このパズルで覆り得て、覆ると複数の段（難易度・問題集・スコア・プレビュー）をやり直すものだけを選ぶ。目安は3〜6点。AI が論点と思っていない前提は選択肢にならないので、一度この表を全部当ててから絞る。

| 前提 | 覆ったときに作り直す範囲 |
|---|---|
| 既存の実装（別ブランチ・オープンの PR）を引き継ぐか作り直すか | スタック全体 |
| 近縁ゲームと統合するか、別ゲームにするか | スタック全体 |
| ルールの変種（床や手がかりの種類など）のどれを採るか | ほぼ全段 |
| クリア条件の型（到達・最短手数・全回収など） | ルール判定・生成器・難易度・スコア |
| 表示名とゲーム ID（商標を避けた一般名。ID はディレクトリ名・ブランチ名になる） | スタック全体の名前の付け替え |
| 盤面の大きさを難易度のつまみに使うか、上位ほど広い盤面を許すか、スマホで操作できる上限はどこか | 生成器・難易度・問題集・プレビュー・基準時間 |
| 最上位をどこまで難しくするか（誰向けか） | 難易度・問題集 |
| 補助・状態の知らせ（一致・違反・正誤の表示）をどこまで出すか | 解法器と素朴なプレイヤー・難易度・問題集・スコア |
| 推測を要する問題を出すか | 生成器・解法器・難易度 |
| 一意解を要求するか、同値解を許すか | 生成器・検証・難易度の再現性 |
| 待った・置き直しの有無と、良いプレイの定義（何を減点するか） | 記録の形・スコア |

## 返事の扱い

- 返事が一部の前提だけに触れていれば、ほかは示した想定で合意とみなす。
- 返事が二通りに読めて、どちらかで作り直す範囲が大きく変わるときだけ、その点を一言で聞き直す。
- 許可は、返事で明示されたものだけを得たとする。許可に触れていない返事には、許可だけを一言で聞き直して待つ。
