# 認識合わせ

人間と AI が同じパズルを想像しているかを確かめ、覆ると大きな作り直しになる前提だけを決めてもらい、後で要る許可もここでまとめて得る。

## 確かさの基準

- 確かめが要る前提は確かめてから出す。速くしたいときは確かめを削らず、聞く点を絞る。
- 前提ごとに「確かめた（何で）」か「推測」かを書く。
- 覆ると作り直しになり、机上で答えが出ないものは、出す前に小さく確かめる。例: 想定盤面の最小と最大で一意解の問題を作れるか小さな生成器で測る、スマホ縦画面の最小幅でのマスの大きさを計算して既存ゲームと比べる、素朴な解き方（貪欲・1手ずつの試し置き）で難しめの問題が解けてしまう割合を測る。

## 先に調べるもの

- main の作業ツリーだけでなく、全リモートブランチ・オープンの PR と Issue。名前違いやルールの言い換え（「ぶつかるまで進む」「一筆書き」など）でも探し、候補台帳・導入調査・既存ゲームも見る。
- 同じパズルや近縁が見つかったら、下の「聞くべき前提の候補」の該当行を当てる。

## 文面の目的と読み手

- 目的: 人間が、AI の想像しているパズルと自分の想像が同じかを確かめ、違う前提だけを直し、許可を出せること。覆ると大きな作り直しになる前提をここで固め、以後は聞かずに進めるため。
- 読み手: 調べた中身を知らない。会話の中で、画面1〜2枚で読む。
- 載せないもの: 試算の詳細（結論と数値だけにする）、「どうしますか」という白紙の問い、内部用語。
- 書き方の共通の決まりは SKILL.md の「人間への知らせ方」。

## 見本

`assets/alignment-sample.md`（ノノグラムで書いた見本）の見出しと順で書き、中身はすべてそのパズルのものに置き換える。各節に何を書くかは下の「節ごとの書き方」が正で、見本の言い回しや分量はその例にすぎない。

- 返事が要る2節（前提と許可）を先頭に置く。
- ルールを文で伝えにくいときは、スマホで軽く遊べる紹介 HTML を Artifact で作り、「どんなパズルか」にリンクを置く（描画・操作・ブラウザエラーを確かめてから出す）。

## 節ごとの書き方

| 節 | 読み手がそこで決めること | 書くこと |
|---|---|---|
| 冒頭 | 何を返せばよいか | 返してほしいこと（違う前提の番号と一言、許可の OK）、触れなかった前提は想定どおりに進めること、所要時間 |
| 違ったら作り直しが大きい前提 | 想定どおりでよいか | 下の「聞くべき前提の候補」から選んだもの。各点を、想定を言い切った見出し、想定1行、根拠1〜2行（「確かめた（何で）」か「推測」か）、違ったら作り直す範囲1行で書く |
| 許可 | 何をしてよいか | このパズルのブランチ（作業ブランチ・層ごとの PR のブランチ・別案や確認用の使い捨てのブランチ）の作成・push・force-push・削除、導入調査 Issue と層ごとの PR の作成と更新（base の付け替えを含む）、作り直すときに置き換える既存の PR を閉じること（無ければ「無し」） |
| どんなパズルか | 想像が合っているか | ルールとクリア条件（クリアの型、ミスとして扱うもの）、何を考えるのが面白いか（何を推論し、何を先読みするか。作業量や罰で難しくするものではないこと）。想定盤面の大きさとスマホでの1マスの大きさは、前提に出していなければここに書く |
| 近い既存ゲーム | 別のゲームにする意味があるか | 近い既存ゲーム・候補ごとに、違いを一言 |
| AI が決めて進めること | 返事は要らない。気になれば言う | 前提ほど作り直しが大きくない判断 |
| 確かめたこと・確かめていないこと | どこまで信じてよいか | 確かめたことは、結論・数値・何で確かめたか。確かめていないこと |

## 聞くべき前提の候補

人間が AI の想定を覆してきた論点。このパズルで覆り得て、覆ると複数の項目（難易度・問題集・スコア・プレビュー）をやり直すものだけを選ぶ。目安は3〜6点。AI が論点と思っていない前提は選択肢にならないので、一度この表を全部当ててから絞る。

| 前提 | 覆ったときに作り直す範囲 |
|---|---|
| 既存の実装（別ブランチ・オープンの PR）を引き継ぐか作り直すか | 作業ブランチ全体 |
| 近縁ゲームと統合するか、別ゲームにするか | 作業ブランチ全体 |
| ルールの変種（床や手がかりの種類など）のどれを採るか | ほぼ全部 |
| クリア条件の型（到達・最短手数・全回収など） | ルール判定・生成器・難易度・スコア |
| 表示名とゲーム ID（商標を避けた一般名。ID はディレクトリ名・ブランチ名になる） | 作業ブランチ全体の名前の付け替え |
| 盤面の大きさを難易度のつまみに使うか、上位ほど広い盤面を許すか、スマホで操作できる上限はどこか | 生成器・難易度・問題集・プレビュー・基準時間 |
| 最上位をどこまで難しくするか（誰向けか） | 難易度・問題集 |
| 補助・状態の知らせ（一致・違反・正誤の表示）をどこまで出すか | 解法器と素朴な解き方・難易度・問題集・スコア |
| 推測を要する問題を出すか | 生成器・解法器・難易度 |
| 一意解を要求するか、同値解を許すか | 生成器・検証・難易度の再現性 |
| 待った・置き直しの有無と、良いプレイの定義（何を減点するか） | 記録の形・スコア |

## 返事の扱い

- 返事が一部の前提だけに触れていれば、ほかは示した想定で合意とみなす。
- 返事が二通りに読めて、どちらかで作り直す範囲が大きく変わるときだけ、その点を一言で聞き直す。
- 許可は、返事で明示されたものだけを得たとする。許可に触れていない返事には、許可だけを一言で聞き直して待つ。
- 許可の一部が断られたら、断られたものの代わりの進め方（例: PR を開かずに作業ブランチの URL で最終レビューする）を推奨つきで示して待つ。
