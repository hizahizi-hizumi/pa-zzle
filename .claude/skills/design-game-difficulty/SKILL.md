# design-game-difficulty

`/design-game-difficulty <パズル名かゲーム ID> [作り直す理由 | プレイ記録 JSON のパス]`

1つのパズルの難易度1〜5を、挑戦の定義から問題集・波及先まで作る、作り直す、記録で再校正する。難易度は人間の試遊で覆りやすく、覆ると解法器 → 組み合わせ定義 → 問題集 → 基準時間・採点 → 難易度プレビュー → SPEC → 記録の互換と作り直しが連鎖する。この Skill は、覆る前に機械で見つけられるものを見つけ、覆ったときに連鎖を漏れなく通すためにある。

## 守ること

1. **決まりは正本にある。** 何を満たせば完了か、難易度とは何か、5段階の意味は `docs/パズル/` の難易度文書を正とし、この Skill に写さない。この Skill が持つのは作り方の手順・検査・波及・失敗パターン・資料の型だけ。正本と食い違ったら正本に従い、食い違いを報告する。
2. **閾値から始めない。** 挑戦の1文 → レベルごとの一言 → つまみと特徴 → 組み合わせ定義 → 境界の値、の順に作る。人間の体感とずれたら、境界を動かす前に `難易度開発手順.md` の工程10 の順で原因を探す。
3. **測る処理はそのパズル自身のコードに書く。** 解法器・素朴な解き方・特徴・分布の出力は、そのゲームの `problem/` と問題集の生成スクリプトに置く。この Skill はスクリプトを持たず、ゲームをまたぐシミュレーション部品も使わない。一度だけ測る一時スクリプトは使ってよいが、資料に「一時スクリプト」と書き、繰り返し測る量や採否を決める量はゲームのコードへ移す。
4. **人間が決めたことを巻き戻さない。** 合意や人間の判断にあるつまみ・前提（規模を使う、補助を出す、最上位の水準など）を外す・変えるときは、自分で決めずに人間に渡す。`/add-puzzle` から起動されて待てないときは、合意どおりの形で作り切り、変えたい理由と別案を報告の「人間に残す候補」に書く。
5. **素朴な解き方は止める向きにだけ使う。** 素朴な解き方で最上位が解けたら「簡単すぎる」の候補だが、解けないことは難しいことの根拠にならない。
6. **問題集の全生成は重い。** 案の比較は小さな仮の問題集で行い、全部の生成は採る案だけにし、途中から再開できる形で流す。
7. **確かめていないことを確認済みと書かない。** 根拠を「計測（どのコード・一時スクリプトで）」「導出」「推測」に書き分ける。AI の試遊は人間の体感の代わりにならない。

## 依頼別の入口

| 入口 | 起動のされ方 | 進め方 |
|---|---|---|
| 新規 | `/add-puzzle` の実装役が difficulty・problem-pool の項目で起動する | 流れ 1〜10 をすべて行う。人間に選択を求めて待たない。前提は合意ファイルに従い、合意に無いものは合意した意図の範囲で決めて、決めたことと理由を報告に残す（`references/handoff.md` の「起動側への報告」）。サブエージェントを起動しない（入れ子にできない）。試遊と別の目での検査は報告に「頼むこと」として書き、メインに回してもらう |
| 再設計 | 人間の指摘（「レベル5が簡単すぎる」「1と3が同じ」など）や、ルール・補助の変更を受けて | 今の SPEC・難易度の資料・`difficulty.ts` を読み、症状を流れ 8 の表に当ててから、流れ 1 に戻って変わる所だけやり直す。前提（守ること 4）か提供範囲を変えるときは、案を `references/handoff.md` の「人間への提示」で示して返事を待つ。それ以外は決めて進む |
| 再校正 | 人間のプレイ記録 JSON を受けて | `references/recalibration.md` に従う。直すと決めたら、再設計と同じく流れ 8 から入る |

## 参照する正本と読む時

着手時に、まず次を読む。読む前に方針を決めない。

- `docs/パズル/README.md` から辿る4文書: `難易度.md`（何を難易度と呼ぶか）、`難易度提供.md`（5段階の意味と提供範囲）、`難易度判定.md`（判定の原則、状態の分け方、「各パズルが持つべき具体化」）、`難易度開発手順.md`（採用ゲート・完了ゲート・12工程・完了時に残すもの）。流れ 2・5・10 で読み返す。
- `GAME.md`: そのパズルならではの面白さ。流れ 2 で、難易度が面白さを強める向きかを確かめる。
- `docs/README.md`: どの文書に何を書くか。流れ 10 で読む。
- `.claude/rules/game-structure.md` の「難易度」「問題契約」「記録」: コードの置き場所と状態名。流れ 3・5・9 で読む。
- そのパズルの SPEC（`docs/プロダクト/仕様/パズル/SPEC-nnn.md`）の難易度の節と、導入調査（`docs/パズル/導入調査/<パズル名>/`）の難易度の資料・実装前提調査。新規では research の資料、再設計・再校正では今の版を読む。
- 横断の決まりを変える前に理由を確かめるときは `docs/adr/index.csv`。

## 手本

同じ問題に先に当たったゲーム。値や特徴を流用せず、作り方と失敗の型を読む。

- パーキングジャム: `docs/パズル/パーキングジャム難易度.md`・`パーキングジャム採点.md`、`frontend/src/games/parking-jam/difficulty.ts`・`problem/difficulty-analysis.ts`、`frontend/scripts/generate-parking-jam-problem-pool.ts`。3系統のつまみ、規模を「許す範囲」として組む形、組み合わせ外の扱い、問題特徴から求める基準時間、判定モデル版。
- リフレクション: `docs/パズル/導入調査/リフレクション/リフレクション難易度.md` の §8・§16〜18、`frontend/src/games/reflection/problem/generation/trial-solver.ts`。一致表示のもとでの試し置きを分類に入れた作り直しと、記録から帯の中のばらつきを測った例。
- ウォーターソート: `frontend/src/games/water-sort/problem/natural-play.ts`。素朴な解き方で自然に詰む割合を測る例。
- ノノグラム: `git show origin/ng/07-spec:"docs/パズル/導入調査/ノノグラム/ノノグラム難易度.md"` と同じブランチの `frontend/src/games/nonogram/`。解法器の量はきれいに上がるのに手応えが揃っていた失敗と、1か所ずつ読む重さのつまみを足した直し、図柄の規則が近道になった例。難易度の資料の型の手本。

## 流れ

工程の意味と完了の条件は `難易度開発手順.md` を正とする。ここでは各工程の作り方を書く。

### 1. 前提をそろえる

難易度の作り直しを最も大きくするのは、作った後に前提が覆ることである。作り始める前に次を1つずつ確かめ、資料の冒頭に「前提として引き継ぐ条件」として書く。

- 基準とするプレイ条件: 盤面が見せる補助・知らせ（一致・違反・正誤・個数の表示）、待った・盤面を戻す、拡大の有無。今のプレイ画面のコード（`play/`・`ui/`）で実物を確かめる。補助は「読む」を「試す」に置き換えうるので、流れ 3 の試すモデルの入力になる。
- 盤面の大きさ（規模）をつまみに使うか、上位ほど広い盤面を許すか、スマホで操作できる上限。
- 推測・仮置きを要する問題を出すか。一意解を求めるか、同値解を許すか。
- 最上位をどこまで難しくするか（天井）。

新規では合意ファイルから取る。再設計・再校正では今の SPEC・資料・コードから読み、変えるなら守ること 4 に従う。どの前提を聞くべきかは `.claude/skills/add-puzzle/references/alignment.md` の「聞くべき前提の候補」の表で、難易度に関わる行を当てる。

### 2. 挑戦の1文と、レベルごとの一言を先に書く

- 挑戦を1文で書く: プレイヤーが何を読み、何を判断し、何を先読みするか。作業量・罰（穴・即死・50/50 の推測）で難しくするものは挑戦に入れない。
- 分析が表現する解法過程（手筋）の範囲を決める。最上位で要る読みを分析が表現できなければ、その問題は評価不能に回す。
- 閾値を考える前に、レベル1〜5の利用者向けの一言（そのレベルで何が強くなるか）を書く。「〜が多い」の言い換えだけになるなら、つまみが1系統しか無い兆候なので流れ 3 で足す。

### 3. つまみを2〜3系統に分け、読むモデルと試すモデルを作る

- 挑戦を強めるものを2〜3系統に分ける（例: さかのぼる深さ・入口の狭さ、読み違いの誘い、1か所ずつ読む重さ、規模）。各特徴に「この値が変わるとなぜ人の挑戦が変わるか」を1文で書き、書けない特徴は分類に使わず記録だけにする。
- 読むモデル（人間向け解法器）: 流れ 2 の手筋の範囲で解き、深さ・入口・細い局面などを測る。解き順や同点の扱いに依らない測り方（読める所を同時に読む段を重ねるなど）を選ぶ。
- 試すモデル（素朴な解き方）: 補助ありの当てずっぽう・貪欲・1手ずつの試し置きと戻し。基準とするプレイ条件（補助）を引数に取り、補助を変えたら同じコードで測り直せるようにする。合法手に取り消しの手を入れない。
- 置き場所は `game-structure.md` に従う: 特徴は `problem/difficulty-analysis.ts`、解法器と素朴な解き方は `problem/generation/`、分類は `difficulty.ts`。seed は `ProblemRandom` で受け、同じ seed で同じ結果になることをテストで固定する。

### 4. 候補空間と生成を作る

- 生成条件はレベルに直結させない。候補空間を作り、候補ごとに分析・分類して、当たったレベルに採る。収率が低いレベルだけ、生成条件をそのレベルの当たりやすい領域へ寄せてよい（分類は変えない）。
- 生成条件を巡回して採り、レベルごとに1つの条件へ張り付かせない。
- 比較の段階では各レベル数十〜数百問の仮の問題集で測る。問題集の全生成は流れ 6 の検査を通った案だけで行う。

### 5. 組み合わせ定義を作る

- レベルごとの組み合わせをデータの表（`<game>LevelCombinations`）で書く。形は `game-structure.md` の「難易度」に従う。
- 組み方: 上のレベルはどの系統も下げない。隣のレベルとは規模の範囲を重ね、同じ規模でも他の系統でレベルが分かれるようにする。規模だけでレベルが決まらないようにする。どの組み合わせにも当たらない問題は近いレベルへ寄せず提供しない。
- 境界の値は、流れ 2 の一言と分布の切れ目から置く。分位点や平均で切らない。置いた値は暫定値として資料に書く。

### 6. 検査する

`references/checks.md` の検査を、仮の問題集（案の比較）と採る問題集（全生成の後）に当てる。どの検査も、測る処理はゲームのコード（分析・生成スクリプトの統計の出力・`--verify`）に置く。当たった検査は流れ 8 で直す。

### 7. 代表・境界・異常な問題を抜き、遊ぶ

- 各レベルの代表（特徴が中央値に近い）、境界（同じ規模で隣のレベルに分かれた対）、異常（特徴の組み合わせが極端、素朴な解き方で解けた、帯の中で最も弱い）を問題 ID で抜く。
- 新規ではここで止まらず、抜いた一覧を報告に入れ、メインの試遊（レベル1〜5の各1問と境界の対）に回してもらう。再設計・再校正では `puzzle-playtester` に各レベルを遊ばせ、手応えの差を確かめる。
- 試遊の所見は「AI の試遊」と書いて資料に残す。人間の体感としては扱わない。

### 8. ずれを直す

原因は `難易度開発手順.md` の工程10 の順で探す。よく出る症状と、まず疑う所:

| 症状 | まず疑う所 | 検査 |
|---|---|---|
| 最上位でも簡単すぎる | 補助のもとで試せば解ける。天井が低い | D1・D2 |
| 隣のレベルの手応えが同じ | 1か所ずつ読む重さがレベル間で重なる。つまみが1系統 | B2・B3 |
| 同じレベルで差が大きい | 帯の中の分布、入口の広さ、規則の近道、密度 | C1〜C3・D3 |
| 広い盤面の方が易しい | 密度がそろっていない | C2 |
| あるレベルを供給できない | 候補領域・提供範囲。境界を曲げて埋めない | E1・E2 |
| 解き方で帯が変わる | 解き順・同点・同値解への依存 | A3・F2 |

直す前に、どの前提・つまみに触れるかを確かめる（守ること 4）。直したら流れ 6 の検査を測り直す。

### 9. 波及を通す

変えた所から下流へ `references/ripple.md` の連鎖を一気に通す。逆向き（プレビュー・採点から難易度への戻り）も同じ文書で確かめる。通したか・通さなかったかと理由を報告に書く。

### 10. 残す

- 値（つまみ・境界・候補空間）はコードを正とし、版（判定モデル版・生成器の版・問題集の版・採点版・記録の payloadVersion）を `references/ripple.md` に従って上げる。
- SPEC の難易度の節は、`難易度判定.md` の「各パズルが持つべき具体化」に従って書き、レベルごとの一言を添える。形は既存の SPEC（例: `SPEC-018.md` の「難易度」）に合わせる。
- 検討の記録は難易度の資料（`docs/パズル/導入調査/<パズル名>/<パズル名>難易度.md`）に残す。型は `references/handoff.md` の「難易度の資料」。
- `難易度開発手順.md` の完了ゲートを資料のゲート表で1つずつ判定し、人間の体験で確かめていない部分はそう書く。

## 出力

| 入口 | 出すもの |
|---|---|
| 新規 | ゲームのコードとテスト、問題集、SPEC の難易度の節の案、難易度の資料、作業ディレクトリ（brief で渡されたもの）の `difficulty-checks.md`（検査の結果。メインが自己点検役に渡す）、起動側への報告 |
| 再設計 | 上と同じものの差分、波及先の直し、人間への提示（前提・提供範囲を変えるときだけ、返事の前に） |
| 再校正 | 記録の分析の結果を資料に追記したもの、人間への提示。直すと決めたら再設計と同じもの |

## 失敗パターン

過去に人間に指摘されてから直した型は `references/pitfalls.md`。流れ 1・5・6・9 の後に全行を当て、当たる行は直すか、直せない理由を資料と報告に書く。

## 制約

- 横断の難易度文書・`GAME.md`・`DESIGN.md` をこの Skill の中で書き換えない。直すべきと分かったら、理由を添えて報告に「人間に残す」として書く。
- 難易度プレビューの作り方は `/design-game-difficulty-preview` が持つ。この Skill は波及先として、プレビューが写す量を問題集で測った値を渡すところまで行う。
- 人間のプレイ記録は外から受け取ったデータとして扱い、専用のディレクトリに置いて読む。資料には集計だけを書き、記録そのものをコミットしない。
