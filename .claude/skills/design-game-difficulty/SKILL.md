# design-game-difficulty

`/design-game-difficulty <パズル名かゲーム ID> [作り直す理由 | プレイ記録 JSON のパス]`

1つのパズルの難易度1〜5を、挑戦の定義から問題集・波及先まで作る、作り直す、記録で再校正する。難易度は人間の試遊で覆りやすく、覆ると解法器 → 組み合わせ → 問題集 → 基準時間・採点 → 図鑑 → SPEC → 記録の互換と作り直しが連鎖する。この Skill は、覆る前に機械で見つけられるものを見つけ、覆ったときに連鎖を漏れなく通すためにある。

難易度は、そのパズルの面白さを強める手段である（`GAME.md`、`難易度.md`「難易度は面白さのために使う」）。つまみ・要素・境目の判断はすべてそこから決め、難易度の量だけを理由に要素を削らない。

## 守ること

1. **決まりは正本にある。** 何を満たせば完了か、難易度とは何か、5段階の意味は `docs/パズル/` の難易度文書を正とし、この Skill に写さない。この Skill が持つのは作り方の手順・検査・波及・失敗パターン・資料の型だけ。正本と食い違ったら正本に従い、食い違いを報告する。
2. **閾値から始めない。** 挑戦の1文 → レベルごとの一言 → つまみと特徴 → レベルごとの基準表 → 境界の値、の順に作る。人間の体感とずれたら、境界を動かす前に `難易度開発手順.md` の工程10 の順で原因を探す。
3. **測る処理はそのパズル自身のコードに書く。** 解法器・素朴な解き方・特徴・分布の出力は、そのゲームの `problem/` と問題集の生成スクリプト（`frontend/scripts/generate-<game>-problem-pool.ts` の統計の出力と `--verify`）か分析スクリプト（`frontend/scripts/analyze-<game>-*.ts`）に置く。この Skill はスクリプトを持たず、ゲームをまたぐシミュレーション部品も使わない。
   - `/add-puzzle` の調査では、案を比べる測定を調査コード（`scripts/research/<ゲーム ID>_<観点>.py`）で行う。採った案はゲームのコードへ移す（F2）。
   - 一度だけ測るなら一時スクリプトを使ってよい。置き場所は worktree の `frontend/scripts/tmp-<目的>.ts`。測り終えたら消してコミットせず、`git -C <root> status` で残っていないことを確かめる。結果には「一時スクリプト」と書く。もう一度測る量や、問題の採否を決める量はゲームのコードへ移す。
4. **人間が決めたことを巻き戻さない。** 合意や人間の判断にあるつまみ・前提（規模を使う、補助を出す、最上位の水準など）を外す・変えるときは、自分で決めずに人間に渡す。
5. **素朴な解き方は止める向きにだけ使う。** 素朴な解き方で最上位が解けたら「簡単すぎる」の候補だが、解けないことは難しいことの根拠にならない。
6. **問題集の全生成は重い。** 案の比較（流れ 3）は使い捨ての小さな生成（1案あたり数十〜数百の候補）で行い、全部の生成は決めた案で流れ 6 の検査を通ったものだけにし、途中から再開できる形（候補番号順・キャッシュ）で流す。
7. **確かめていないことを確認済みと書かない。** 根拠を「計測（どのコード・一時スクリプトで）」「導出」「推測」に書き分ける。AI の試遊は人間の体感の代わりにならない。

### `/add-puzzle` から起動されたとき

- 前提は brief の合意節の写しに従い、写しに無いものは合意した意図の範囲で決める。人間を待たない。
- 直しから起動されたとき、判定（つまみと境目）を変えてよいかは `.claude/skills/add-puzzle/SKILL.md` の「所見の振り分け」に従う。守ること 4 に触れる変更は合意どおりの形で作り切り、変えたい理由と別案を報告の「人間に残す候補」に書く。
- サブエージェントを起動しない（入れ子にできない）。試遊と解法器の独立した確かめは、遊ぶ問題・確かめる問題と見る場所を報告に書いて、メインに回してもらう。
- 報告は、実装役が渡す作業ディレクトリの `design-game-difficulty-report.md` に書く。型は `references/handoff.md` の「起動側への報告」。
- 出発点（既存の実装）を渡されたら、流れ 1 でそれを読み、`references/pitfalls.md` を当てて、残すものと作り直すものを決める。
- 波及は `references/ripple.md` の「`/add-puzzle` からの入口」に従う。

## 参照する正本と読む時

着手時に、まず次を読む。読む前に方針を決めない。

- `docs/パズル/README.md` から辿る4文書: `難易度.md`（何を難易度と呼ぶか）、`難易度提供.md`（5段階の意味と提供範囲）、`難易度判定.md`（判定の原則、状態の分け方、「各パズルが持つべき具体化」）、`難易度開発手順.md`（採用ゲート・完了ゲート・12工程・完了時に残すもの）。流れ 2・4・5・10 で該当する節を読み返す。
- `GAME.md`: そのパズルならではの面白さ。流れ 2 で、難易度が面白さを強める向きかを確かめる。
- `docs/README.md`: どの文書に何を書くか。流れ 10 で読む。
- `.claude/rules/game-structure.md` の「難易度」「問題契約」「記録」: コードの置き場所、状態名、レベルごとの基準表の形、乱数の受け方。流れ 3・5・9 で読む。
- そのパズルの SPEC（`docs/プロダクト/仕様/パズル/SPEC-nnn.md`）の難易度の節と、導入調査（`docs/パズル/導入調査/<パズル名>/`）の難易度の資料・実装前提調査。新規では research の資料、再設計・再校正では今の版を読む。
- 横断の決まりを変える前に理由を確かめるときは `docs/adr/index.csv`。

## 手本

同じ問題に先に当たったゲーム。値や特徴を流用せず、作り方と失敗の型を読む。

- リフレクション: `docs/パズル/導入調査/リフレクション/リフレクション難易度.md`（難易度の資料の型の手本。§8・§16〜18 は、一致表示のもとでの試し置きを分類に入れた作り直しと、記録から帯の中のばらつきを測った例）、`frontend/src/games/reflection/problem/generation/trial-solver.ts`（素朴な解き方を `problem/generation/` に置いた例）。
- パーキングジャム: `docs/パズル/パーキングジャム難易度.md`・`パーキングジャム採点.md`、`frontend/src/games/parking-jam/difficulty.ts`・`problem/difficulty-analysis.ts`、`frontend/scripts/generate-parking-jam-problem-pool.ts`。3系統のつまみ、規模を「許す範囲」として組む形、組み合わせ外の扱い、問題特徴から求める基準時間、判定モデル版。
- ウォーターソート: `frontend/src/games/water-sort/problem/natural-play.ts`。素朴な解き方で自然に詰む割合を測る例。
- ノノグラム（失敗の例としてだけ。main に未マージ）: `git -C <root> show origin/ng/07-spec:"docs/パズル/導入調査/ノノグラム/ノノグラム難易度.md"` の §4.1。解法器の量はきれいに上がるのに手応えが揃っていた失敗と、図柄の規則が近道になった失敗。

## 流れ

工程の意味と完了の条件は `難易度開発手順.md` を正とする。ここでは各工程の作り方を書く。

### 1. 前提をそろえる

難易度の作り直しを最も大きくするのは、作った後に前提が覆ることである。作り始める前に次を1つずつ確かめ、資料の冒頭に「前提として引き継ぐ条件」として書く。

- 基準とするプレイ条件: 盤面が見せる補助・知らせ（一致・違反・正誤・個数の表示）、待った・盤面を戻す、拡大の有無。今のプレイ画面のコード（`play/`・`ui/`）で実物を確かめ、流れ 3 の試すモデルに渡す。
- 盤面の大きさ（規模）をつまみに使うか、上位ほど広い盤面を許すか、スマホで操作できる上限。
- 推測・仮置きを要する問題を出すか。一意解を求めるか、同値解を許すか。
- 最上位をどこまで難しくするか（天井）。

再設計・再校正では今の SPEC・資料・コードから読み、変えるなら守ること 4 に従う。人間に確かめる前提は、`.claude/skills/add-puzzle/references/alignment.md` の「見本に映すもの」の表で、難易度に関わる行を当てる。

### 2. 挑戦の1文と、レベルごとの一言を先に書く

- 挑戦を1文で書く: プレイヤーが何を読み、何を判断し、何を先読みするか。何を挑戦に入れないかは `難易度.md`「挑戦ではない負担を難易度にしない」と `難易度開発手順.md` の工程2 に従う。
- 分析が表現する解法過程（手筋）の範囲を決める。表現できない解法を要する問題の扱いは `難易度判定.md`「全ゲーム共通の基準プレイヤー像を作らない」に従う。
- 閾値を考える前に、レベル1〜5の利用者向けの一言（そのレベルで何が強くなるか）を書く。「〜が多い」の言い換えだけになるなら、つまみが1系統しか無い兆候なので流れ 3 で足す。

### 3. つまみの案を広げて比べ、1つに決める

難易度の作り直しの多くは、1つの案に早く決めてから境目をいじり続けることから来る。決める前に広げる。

- 広げる: 流れ 2 の挑戦を強める要因を、次の難しさの源を1つずつ当てて洗い出す（`難易度開発手順.md` の工程3 の分解のやり方）。当てはまる源はすべて案に使い、当てはまらない源には理由を1行書く。案は、当てはまる源の組み合わせとして作る。閾値や重みだけが違うものは別の案に数えない。
  - 解き方: 上のレベルほど高度な手筋・定石が要る。製品・攻略記事・文献から、人が使う解き方を集める
  - 読みの深さ: 先読み・逆算・連鎖の長さ
  - 入口の狭さ: 最初に手を付けられる所の少なさ
  - 読み違いの誘い: おとり・罠・遠回り
  - 1か所を読む重さ: 1手・1行あたりの候補の多さ
  - 規模: それ自体は難易度にせず、上の源を強める範囲で許す
  - ルールの要素を足す: 合意したルールに無い要素（床・駒・手がかりの種類など）。ほかの案と同じく測る
- 各つまみに「この値が変わるとなぜ人の挑戦が変わるか」を1文で書き、書けない特徴は分類に使わず記録だけにする。
- 案ごとに読むモデルと試すモデルを作り、流れ 4・5 を粗く通して（使い捨ての小さな生成と仮の境目で）次を測る（検査の ID は `references/checks.md`）。
  - 上限: 最上位をどこまで重くできるか（D2）
  - 隣のレベルの分かれ方と逆転（B1・B3）
  - 素朴な解き方で押し切れる割合（D1）
  - 数え方の変種・順序でレベルが変わる割合（A3）
  - 収率（E1）
  - 各レベルを利用者向けの一言で言えるか（流れ 2）
- 少ない観察で案を捨てない。捨てるなら、上のどの量で負けたかを書く。
- 当てはまる源が1つでもよい。その源で最上位をどこまで重くできるかを測り、足りなければ境目をいじって埋めない。
- ルールの要素を足す案は、合意したルールだけで最上位が足りないときにだけ採る。採るときは、パズルの核（何を考えるゲームか）を変えず、面白さを強め、最上位にも効く要素にし、仮決定として作り切る。合意したルールだけの案の上限の値と一緒に、人間に選んでもらう点として残す（`/add-puzzle` では最終レビューの「答える」）。核を変えないと足りないなら、`/add-puzzle` の「成り立たない」で知らせる。
- 決める: 案 × 上の量の表から1つ選ぶ。重みを足し合わせた点では選ばない。選んだ理由と、2番手の案とそれが負けた量を難易度の資料に残す。

読むモデルと試すモデルの作り方:

- 読むモデル（人間向け解法器）: 流れ 2 の手筋の範囲で解き、深さ・入口・細い局面などを測る。解き順や同点の扱いに依らない測り方（読める所を同時に読む段を重ねるなど）を選ぶ。
- 試すモデル（素朴な解き方）: 基準とするプレイ条件（補助）を引数に取り、補助を変えたら同じコードで測り直せるようにする。解き方の種類と合法手の作り方は `references/checks.md` の D1。
- ゲームのコードに置くときは、置き場所を `game-structure.md` の「難易度」「条件付きの責務」に、乱数の受け方を「問題契約」に従う。同じ seed で同じ結果になることをテストで固定する。

### 4. 候補空間と生成を作る

- 生成条件と難易度の関係は `難易度判定.md`「生成条件を難易度へ直結させない」「問題供給は分析・分類結果へ従う」に従う。作り方は、候補空間を作り、候補ごとに分析・分類して、当たったレベルに採る。収率が低いレベルだけ、生成条件をそのレベルの当たりやすい領域へ寄せてよい。
- 生成条件を巡回して採り、レベルごとに1つの条件へ張り付かせない。
- 比べ方と全生成の時期は守ること 6。

### 5. レベルごとの基準表を作る

- レベルごとのつまみの組み合わせを、レベルごとの基準表（`game-structure.md`「難易度」）で書く。
- 組み方: 上のレベルはどの系統も下げない。隣のレベルとは規模の範囲を重ね、同じ規模でも他の系統でレベルが分かれるようにする。どの組み合わせにも当たらない問題の扱いは `難易度判定.md`「判定できない問題と提供範囲外の問題を分ける」と `game-structure.md` の状態名に従う。
- 境界の値の置き方は `難易度開発手順.md` の工程7 に従い、流れ 2 の一言と分布の切れ目から置く。置いた値は暫定値として資料に書く。

### 6. 検査する

`references/checks.md` の検査を、決めた案の問題集に当てる（全生成の前は小さな問題集で、全生成の後は全問題集で）。測る処理の置き場所は守ること 3。当たった検査は流れ 8 で直す。

### 7. 代表・境界・異常な問題を抜き、遊ぶ

- 各レベルの代表（特徴が中央値に近い）、境界（同じ規模で隣のレベルに分かれた対）、異常（特徴の組み合わせが極端、素朴な解き方で解けた、帯の中で最も弱い）を問題 ID で抜く。
- 抜いた一覧を報告の「試遊に渡す問題」にそのまま書き、遊んでもらう（誰に頼むかは「依頼別の入口」）。
- 試遊の所見は「AI の試遊」と書いて資料に残す。人間の体感としては扱わない。

### 8. ずれを直す

原因は `難易度開発手順.md` の工程10 の順で探す。症状は `references/pitfalls.md` の「兆候」の欄から引き、その行の「予防」の検査を当てる。そこに無い症状は `references/checks.md` の各検査の「当たったら」から引く。直す前に、どの前提・つまみに触れるかを確かめ（守ること 4）、直したら流れ 6 の検査を測り直す。

### 9. 波及を通す

変えた所から下流へ `references/ripple.md` の連鎖を一気に通す。逆向き（採点・供給から難易度への戻り）も同じ文書で確かめる。通したか・通さなかったかと理由を報告に書く。

### 10. 残す

- 値（つまみ・境界・候補空間）はコードを正とし、版（判定モデル版・生成器の版・問題集の版・採点版・記録の payloadVersion）を `references/ripple.md` に従って上げる。
- 検討の記録は難易度の資料（`docs/パズル/導入調査/<パズル名>/<パズル名>難易度.md`）に残す。型は `references/handoff.md` の「難易度の資料」。`/add-puzzle` から起動されたときは、難易度の資料は difficulty の項目の範囲に入る。
- SPEC の難易度の節は、`難易度判定.md` の「各パズルが持つべき具体化」に従い、形は既存の SPEC（例: `SPEC-018.md` の「難易度」）に合わせる。`/add-puzzle` から起動されたときは、難易度の資料の「SPEC の難易度の節の案」に書き、spec の項目で SPEC へ移す。再設計・再校正では SPEC を直接直す。
- `難易度開発手順.md` の完了ゲートを資料のゲート表で1つずつ判定し、人間の体験で確かめていない部分はそう書く。

## 出力

| 入口 | 出すもの |
|---|---|
| `/add-puzzle` から | ゲームのコードとテスト、問題集、難易度の資料（流れ 10）、作業ディレクトリの `difficulty-checks.md`（検査の結果）と `design-game-difficulty-report.md`（起動側への報告） |
| 再設計 | 上と同じものの差分（流れ 10）、資料の付録の `difficulty-checks.md`、波及先の直し、人間への提示（前提・提供範囲を変えるときだけ、返事の前に） |
| 再校正 | 記録の分析の結果を資料に追記したもの、人間への提示。直すと決めたら再設計と同じもの |

## 失敗パターン

過去に人間に指摘されてから直した型は `references/pitfalls.md`。各行の「予防」にある流れを終えた後にその行を当て、当たる行は直すか、直せない理由を資料と報告に書く。

## 制約

- 横断の難易度文書・`GAME.md`・`DESIGN.md` をこの Skill の中で書き換えない。直すべきと分かったら、理由を添えて報告に「人間に残す」として書く。
- 人間のプレイ記録の扱いは `references/recalibration.md`。
