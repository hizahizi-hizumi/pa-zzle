# 人に渡す資料の型

この Skill が書く3つの資料の型。どれも、経緯を覚えていない人が読んで判断できるように書く。

## 難易度の資料

置き場所は `docs/パズル/導入調査/<パズル名>/<パズル名>難易度.md`。正本ではなく資料（`docs/README.md`「資料」）で、採用した契約は SPEC、値はコードを正とする。冒頭でそう書く。手本は `docs/パズル/導入調査/リフレクション/リフレクション難易度.md`（SKILL.md の「手本」）。新規では、この資料は difficulty の項目の範囲に入る。

`難易度開発手順.md`「完了時に残すもの」の各項目が、どの節で追えるかを満たすように、次の順で節を置く。

| 節 | 中身 |
|---|---|
| 冒頭 | 何の記録か、正本はどこか、根拠の見出し語（計測・導出・推測）、人間が遊んで確かめたかどうか |
| 1. 前提として引き継ぐ条件 | 流れ 1 の前提（盤面、問題成立性、補助・知らせ、供給方式）と、合意か AI の判断か |
| 2. 挑戦と基準とするプレイ条件 | 挑戦の1文、基準とするプレイ条件、分析が表現できる解法過程の範囲 |
| 3. 特徴 | 特徴ごとに、意味と「分類に使う／使わない（分布を見る）」 |
| 4. 状態と分類 | 状態（分類済み・提供範囲外・評価不能・不成立）と条件、レベルごとの基準表（検討時点の値として写す）、利用者向けの一言、組み方の理由 |
| 5. 問題集の分布 | 検査 B・C の表と、そこから言えること（逆転なし、同じ規模で分かれる、盤面の逆転なし、推論の種類） |
| 6. 供給 | 生成の仕方、検査 E の表、`--verify` の結果 |
| 7. 代表・境界・異常な問題 | 問題 ID、開くパス、特徴、見どころ（何と比べるか） |
| 8. 素朴な解き方 | 検査 D1 の表（解き方・補助・打ち切り・レベルごとの結果）、読み方と限界、再現の仕方（どのコードか） |
| 9. 採用ゲートと完了ゲート | ゲートごとに、条件・判定・根拠。人間の体験で確かめていない部分はそう書く |
| 10. 人間の試遊で確かめること | 7 の問題を使って確かめる問い |
| 11. 下流に渡す量 | つまみごと・レベルごとの 10 / 50 / 90 パーセンタイルと最小〜最大、その表を出したコードの場所（生成スクリプトの出力か `--verify`）。`/design-game-difficulty-preview` の流れ 1 と、採点の基準時間の見直しがこの節を読む |
| 12. SPEC の難易度の節の案 | 新規だけ。SPEC に入れる文の案（書く範囲は SKILL.md の流れ 10）。spec の項目で SPEC へ移し、移した後はこの節を消す |
| 13. 採用しなかった案 | 比べた案と、採らなかった理由と測った値 |

作り直したときは、古い版の定義と結果を「作り直す前の定義（版 n）」として節を分けて残し、今の節は今の版だけにする。記録で確かめたときは `recalibration.md` の 7 の節を足す。

## 起動側への報告

`/add-puzzle` の実装役から起動されたときに、実装役が渡す作業ディレクトリの `design-game-difficulty-report.md` に書くもの。実装役はこのパスを自分の報告に載せ、メインがここを読んで巡の記録・自己点検役・試遊役・最終レビュー資料へ振り分ける。上から順に置く。

1. **結論**: 5段階が成り立ったか（各レベルの問題数）、成り立たないならどのレベルで何が足りないか。
2. **決めたことと理由**: 合意に無く、合意した意図の範囲で決めたもの。覆すと作り直しが大きい順に、決めたこと・理由・比べた案・覆したときに作り直す範囲。
3. **検査の結果**: `difficulty-checks.md` のパスと、「当たる」「測れない」の行の要約。
4. **試遊に渡す問題**: レベル1〜5の各1問（代表）と、境界の対・異常な問題の問題 ID と開くパス。それぞれ何を見てほしいか。山場2の試遊はこの一覧を使う。
5. **頼むこと**: 自己点検役に独立して確かめてほしいこと（検査 F1 など）と、確かめる問題の ID・見る場所（解法器のコードのパス）。まだ作っていない項目（スコア・プレビュー・記録）に渡すもの（難易度の資料の「下流に渡す量」の節の場所と、レベルごとの一言）。
6. **波及**: `ripple.md` の段ごとに、通した／該当なし／通していない（理由）。
7. **人間に残す候補**: 天井を受け入れたこと、前提の解釈、計測で裏付けられない体感など。各点に推奨と別案。

## 人間への提示

再設計・再校正で、前提か提供範囲を変える案を人間に見せるとき。`/add-puzzle` の SKILL.md「人間への知らせ方」と同じ書き方にする。

- 最初の1〜2行で、何が分かったかと、何を決めてほしいか。
- 案は記号で呼ばず、判定に使うつまみと、レベルごとの利用者向けの一言で示す。
- 推奨を既定にし、推奨の理由をこのパズルで何が良くなるかで具体的に書き、不利な点も並べる。
- 難易度に影響する軸は1回に1つまで。案ごとの違いは、同じ分析コードにプレイ条件や基準表を引数で渡して測った表の要点（1〜2個の数値）で示す。
- 遊んで比べる問題（ラベルを伏せた代表・境界の対）を、開けるパスか URL で添える。
- 普通に遊んだ記録の JSON を貼ってもらえれば再校正に使うと添える。
- 返事が一部の点だけに触れていれば、ほかは推奨で合意とみなすと書く。
