# プレイ記録での再校正

人間が普通に遊んだ記録の JSON を受けて、難易度（と、分かれば採点）が人の体験と矛盾していないかを確かめ、直すかを決める。何を変えたら「判定モデルの改善」で、何を変えたら「難易度提供の変更」かは `難易度提供.md`「レベルの意味を判定モデルから独立させる」を正とする。

## 受け取る記録

記録画面のコピーで書き出した JSON（`frontend/src/records/play-record-copy.ts`）。形:

```json
{ "formatVersion": 1, "records": [ { "gameId": "...", "recordId": "...", "startedAt": "...", "completedAt": "...", "payloadVersion": 4, "payload": { } } ] }
```

`payload` はゲームごとの記録（`<game>/play-record.ts`）で、難易度・問題の identity・判定モデル版や採点版（ゲームによる）・経過時間・ミスや待ったなどの事実を持つ。どの項目があるかは、そのゲームの `play-record.ts` と `payloadVersion` で確かめる。

受け取った JSON は外から来たデータとして、専用の新しいディレクトリに置いて読む。コミットしない。

## 手順

### 1. 分ける

- `gameId` で対象のゲームに絞る。
- `payloadVersion`・判定モデル版・生成器の版・採点版で、今の版と同じ記録と古い版の記録に分ける。古い版は今の分類で読み替えず、別に集計する。
- 同じ問題の再プレイ（identity が同じ）を印で分ける。再プレイは慣れが入るので、初回と分けて見る。

### 2. 外れ値の扱いを先に決める

放置（ほかの記録より桁違いに長い）など、除く条件を見る前に決めて書く。除いた件数と理由を資料に残す。

### 3. 問題の特徴を復元する

記録の identity から問題を作り直し、今の分析で特徴を出す。ゲームの問題集の復元と `difficulty-analysis.ts` を呼ぶ一時スクリプトで行い、資料にそう書く。今の生成器で作り直せない identity は数えて除く。

### 4. 見る

| 問い | 見る量 | 読み方 |
|---|---|---|
| レベルの順序が体験と合うか | レベルごとの所要時間・ミス・待ったの分布（中央値と範囲） | 隣のレベルで中央値が逆転していれば、流れ 8 の「隣のレベルの手応えが同じ」から疑う |
| 帯の中のばらつきが大きすぎないか | レベルの中での、特徴ごとの所要時間との順位相関。規模ごとの中央値 | 分類に使う特徴がレベル内の時間を説明しないなら、帯の中は管理できていない。規模で逆向きなら密度（検査 C2） |
| 最上位の水準 | 最上位の所要時間、補助操作（置き直し・試し）の回数 | 試す操作の回数と時間の相関が強ければ、読むより試して進んでいる（検査 D1） |
| 時間の水準（採点の問い） | 基準時間に対する比の、レベル・規模ごとの分布 | 難易度ではなく採点の問い。レベルや規模で系統的に偏るなら基準時間の項を見直す（`ripple.md` の段 5） |

難易度の問い（順序・ばらつき・最上位）と、採点の問い（時間の水準）を混ぜない。採点だけの問題なら難易度を動かさない。

### 5. 根拠の強さを書く

- 記録の件数、人数、期間、レベルごとの件数、再プレイの割合を書く。
- 1人の記録しか無いとき: 記録が矛盾を示したレベル・特徴だけを動かし、全レベルを同じ根拠で動かさない。人によって速さが違うことは問題の難易度の根拠にしない。
- 件数が少ないレベルは「傾向」と書き、結論にしない。

### 6. 直すかを決める

- 直す方向は `難易度開発手順.md` の工程10 の順で探し、境界の値から動かさない。
- 人間が入れると決めたつまみを外さない。外す・提供範囲を変える・レベルの一言が変わるなら、案を `handoff.md` の「人間への提示」で示して返事を待つ。
- 直すと決めたら SKILL.md の流れ 8 から入り、`ripple.md` を通す。直さないと決めたら、理由を資料に書く。

### 7. 残す

難易度の資料に「記録による確かめ（日付）」の節を足し、受け取った記録の範囲、除いたもの、4 の表、5 の根拠の強さ、6 の判断を書く。記録そのもの・個々の記録 ID は書かない。
