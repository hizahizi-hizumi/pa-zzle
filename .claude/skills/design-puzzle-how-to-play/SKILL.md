# design-puzzle-how-to-play

`/design-puzzle-how-to-play <game>`

パズルの遊び方（ヘルプ）を作る、改める、または見直す。遊び方が保証することは `docs/プロダクト/仕様/ゲーム/SPEC-016.md`、コードの置き場所と共通の契約は `.claude/rules/game-structure.md` の「遊び方」が決める。

共通の部品は、`.claude/rules/game-structure.md` の「遊び方」で、2つ以上のゲームが使う遊び方を置く場所として決めた部品を指す。帯・タブ・開閉・ゴールの盤面の枠と見せ直すボタン・チュートリアルの入口・例の面と元に戻すボタン・判定・押せない図の流れ・操作の行・採点の行は、共通の部品が出す。このスキルは、その中に載せるパズルごとの中身を、一流の商用パズルアプリの遊び方としてそのまま出せる出来に仕上げる。

- `<game>`（`$ARGUMENTS`）は `frontend/src/games/` のディレクトリ名にする。`<Game>` は `frontend/src/games/<game>/ui/` の画面のファイル名の頭（例: `hitofude-puzzle` は `HitofudePuzzle`）にする。
- 該当パズルの仕様は、`frontend/src/games/<game>/display-name.ts` の表示名と `docs/プロダクト/仕様/パズル/` の各仕様の題名を照らして探す。
- 「新しい形」は、`HowToPlayOverlay` で作った遊び方を指す。新しい形のゲームは、`frontend/src/games/` を `HowToPlayOverlay` で Grep して探す。
- 「起点 URL」は、今のブランチで `AGENTS.md` の実行コマンドで起動した開発サーバーの URL を指す。
- 番号は、動作フローの手順を「5」、その中の小手順を「5-2」と書く。

## 決まりの重さ

- 必ず守る: SPEC-016、`.claude/rules/game-structure.md` の「遊び方」、`DESIGN.md`、`GAME.md`、`AGENTS.md`、「大原則」、「始め方」で決めた範囲の「動作フロー」。どれかを破っているか、動作フローを飛ばしていれば、作業は終わっていない。
  - 例外: 次のときは、動作フローを8まで進め、8で未達として報告する。
    - 「進め直し」の上限まで6を行っても、採点役の点数が 100 点に届かない。
    - プレイ画面・チュートリアルの側の呼び名の揺れで、H6 を遊び方だけでは満たせない。
- 迷ったらこうする: 「基本の形」。パズルに合わなければ、必ず守るものを破らない範囲で変えてよい。必ず守るもの（大原則・SPEC-016・game-structure.md など）に由来する所は変えない。変えたときは、項目の表のその行の「根拠」の欄にわけを書く。
- 書いていないこと: `AGENTS.md` の「進め方」に従って決める。

## 大原則

- H1. 一流の商用パズルアプリの遊び方としてそのまま出せる出来にし、採点役の点数を 100 点に届かせる。アプリの既存の画面の出来を上限にしない。
- H2. 本番のルール・操作・状態の知らせ・補助・数え方を、過不足なく載せる。仕様が「遊び方で説明する」としたものも載せる。
- H3. 1つの項目・1つの例には、1つのことだけを置く。
- H4. 文は、盤面と図で伝わらないことだけを、そのパズルに固有の言葉で言う。どのパズルにも当てはまる言葉（「ルールどおりに」など）は入れない。
- H5. 例とゴールの盤面が本番と一致することを、本番の関数と照らすテストで確かめる。
- H6. 物の呼び名と操作の動詞は、遊び方の中でも、プレイ画面のボタンや知らせとも、チュートリアルとも揺らさない。
- H7. 文字の大きさと太さは、遊び方の共通の部品が持つ。ゲームの側では文字の大きさと太さを決めるクラス（`DESIGN.md` の「文字階層」のクラスと、`font-` で始まる太さのクラス）を書かず、文は共通の部品の働きの合う所（ルールの一文、まとまりの見出し、例に添える言葉など）に渡す。合う所が無いときは、1つのゲームだけが使う働きでも、共通の部品に働きの名前で足す。
- H8. スマートフォン（iPhone 13 と幅 320px）と PC の幅で、欠け・崩れ・ずれ・重なりが無い。触った後と、動きの途中も含める。
- H9. 例・判定・手がかりの見せ方は、ほかのゲームから写さず、「基本の形」とそのパズルのルールの型から決める。共通の部品の使い方だけは、新しい形のゲームの実装に合わせる。

## 基本の形

### ルールの型

ルールの例の判定・手がかり・文は、ルールの型で決める。動作フローの1で、ルールごとにどちらの型かを決める。1つのパズルに両方の型のルールがあってもよい。

- 形のルール: 盤面の形が目指す形に合うかを決めるルール（バイナリパズルの「どの行も四角と丸が同じ数」など）。
- 手のルール: 注ぐ・動かすなどの手が通るか弾かれるかを決めるルール（水のパズルの「いちばん上が同じ色のボトルに注げる」など）。

### 入口

- 何をするパズルかの一文を「〜パズルです」と言い切り、盤面の何を何で埋める・つなぐ・動かすかを具体的に言う。
- ゴールの盤面は、SPEC-016 と `DESIGN.md` の「動き」に従って見せ、音は鳴らさず、見せ直しは終わった後の見せ直すボタンだけにする。盤面に最初からある物と遊ぶ人が変える物の見分けがあるパズルでは、その違いをここで見せる。終わりの姿が整って見える手順にする（水のパズルなら空のボトルを端に寄せて終える）。

### 触れる例

ルールと操作のタブの例は、本番と同じ判定・遷移・見た目で触れる例にする。

- 例の判定と遷移は `.claude/rules/game-structure.md` の「遊び方」に従って求め、遊び方の側で書き写さない。
- 例の押す所には、本番の盤面と同じ読み上げ名（aria-label）を付ける。
- 例を押したときの反応と音は、本番と同じにする（音の鳴らし方は `.claude/rules/game-structure.md` の「遊び方」に従う）。例の盤面の中で押しても変わらない物は、本番と同じ受け付けない反応と音を返す。本番のその入口（指・マウス）に無い反応を、ほかの入口（キーボードなど）から借りて返さない。
- 触った後も、判定と印を今の盤面から出し直し、黙らせない。手が通ったのに例が教えるルールに反して見える変化（押した所まで道が戻る、など）は、判定の場所で起きたことを言う。
- 例が見せる手は、次に押す所の手がかりで示す。
  - 手がかりどおりに押していく途中で、例が教えるルールと別のルールの違反が起きない盤面にする。
  - 本番に弾く反応が無い手（押すと別の操作になる所など）には手がかりを付けず、印だけで示す。
  - 文が2つの手を言うときは、手がかりも両方の手を順に示す。なぞる手の手がかりは、なぞったときだけ進める。
  - 触ったら、手の続きがあれば次に押す所へ移し、無ければ消す。弾かれたら、盤面が変わるか選び直すまで出さない。元の形に戻ったらまた出す。
- 例の面の元に戻すボタンは、面の中のどれかの例が最初の形と違う間だけ出す。
- 例の下には、判定と、判定に添える言葉（起きること・✕ のわけ・別のルールで弾かれたこと・凡例）だけを置く。操作の補足は例の下に置かず、文か、文に添える補足に入れる。
- 判定の言葉は、出しうる最長の言葉の幅で場所を取ったまま、どの言葉も例の盤面の中央に置く。凡例は盤面に出ている印だけを説明し、印が消えたら凡例の項目も消して残りを中央に寄せる（凡例の行の高さは取ったまま）。触ると出る言葉のために取った場所は、余りの空きに数えない。

### ルールのタブ

- 中心のルールを先に並べ、入口で伝わるもの（最初からある物のルールなど）は後ろに置く。
- 1つのルールは、一文と、背景差だけの面に置いた例の組にする。例の形は、次の3つから選ぶ。
  - できる形とできない形の対。見比べて違いが分かるようにする。
  - 違いが出る2つの形の対。どちらもできる形で違いが出るルール（移る量など）に使い、判定の代わりに、その例で起きること（「2つとも入る」など）を例の下に出す。
  - 1つの盤面で手ごとの ✓ / ✕。手のルールで、判定した手のほかに通る手がある盤面に使う。✕ の盤面に通る手が見えると、できるように読めるため。
- 対を1つの面に並べるときは、例と例の間を例の中の単位どうしの間の3倍以上とり、2つの盤面に見えるようにする。判定はそれぞれの例の真下に置く。共通の部品の間で足りないときは、共通の部品に働きの名前で足す。
- 形のルールの判定（✓ できる / ✕ できない）:
  - できる形の例は、最初は ✓ で静止させ、1回押すとルールに反する形になる所に手がかりを付ける。できない形の例は、最初から ✕ の形で静止させる。
  - 判定する所（行・列など）がまだ埋まっておらず、違反も無い間は、✓ を出さず「途中」にする。埋まる前に ✓ を出すと、目指す形に届いたと読めるため。
  - 判定の理由が盤面から読み取りにくいルールでは、数か見比べる所の印（凡例を添える）を出す。本番に違反の印があるパズルでは、例にも同じ印を出し、判定の言葉と数は印と同じ間合いで替える。本番の印だけでは盤面のどこが崩れているか読み取れないときは、遊び方だけの見せ方（多い方の単位を示す、など）を、`.claude/rules/game-structure.md` の「遊び方」に従って例の盤面に足す。数や見比べる所の凡例は、判定の言葉に混ぜず、判定の右に添える物として共通の部品に渡す（判定は盤面の中央に残る）。
- 手のルールの判定（✓ 注げる / ✕ 注げない など、その手の動詞）:
  - 試す前は、例が見せる手が通るかを出す。手を打った後は、今の盤面の答えと食い違わないよう、試した手の結果だと分かる言い方（✓ 選べた など）にする。手を打った後の盤面を形として判定すると、通った手の直後に ✕ が出て失敗に読めるため。
  - 判定は、どの手（どこからどこへ）の答えかが図で分かるように付ける。手ごとに付けて動詞が単位の下に収まらないときは、記号の意味を1行の凡例（✓ 注げる　✕ 注げない）で添える。
  - 2次元の盤面で手ごとに付けるときは、候補の単位（先端の隣のマスなど）の中央に、単位の大きさに比べて決めた札（下の線を隠す地を付ける）を置く。本番の阻まれた手の印がその単位に出ている間は、札を消す。
  - ✕ のわけが盤面から読み取りにくい手（満杯なのに上の色が同じ、など）は、押す前から ✕ の真下にわけを添える。わけは単位の幅に収まる短い言葉（満杯・色違いなど）にし、隣の単位のわけと重ねない。
- 触って、例が教えるルールと別のルールで弾かれた・崩れたときは、破ったルールをすべて判定の下に添える。

### 操作のタブ

- 置き方・動かし方は、本番と同じ見た目の図と、本番と同じ単位（マス1つ、ボトル1本など）の触れる例で示す。2回押して1手になる操作は、1手を打ち終えるまでを触れる例で示す。細かいポインターだけの操作（右クリック・キーボード）は、細かいポインターのときだけ出す。
- やり直しの操作は、本番のボタンとメニューと同じ見た目の押せない図で示し、例の面の外に置く。説明は、何をする操作かと、時間と回数がどうなるか（何が残り、何が0に戻るか）を言い、図のすぐそばに置く。似た操作は、名前の言い直しでなく違いを言い、同じ注記を繰り返さない。点への影響は採点のタブだけに書く。
- 補助（SPEC-017）は、本番でそれを使う操作の近くに、本番と同じ見た目の図で載せる。
- 状態の知らせは、ルールの触れる例で同じ反応を見せられるなら項目を立てない。見せられないもの（手詰まりなど）は、本番と同じ見た目の押せない図で、やり直しの操作の後に置く。

### 採点のタブ

- 結果画面の採点基準（`frontend/src/games/<game>/ui/result/<Game>ResultScreen/score-criteria.ts`）と同じ評価項目・満点・順でまとめ、点がどれだけ下がるかを `score.ts` の式から具体的に言う。言う場所は次のように分け、同じことを2か所で言わない。
  - 評価項目の見出しの下の一文: 点の決まり方（満点から引いていくか、比でどこまで下がりどこで0点になるか）。
  - 数えるものの行: 1回あたりの減点（「1回 −5点」）と、何を1回と数えるか。
- 数え方に例外があるパズルでは、例外が起きる操作の流れを、コマに分けて並べた押せない図で見せ、図に数え方（「数えない」「1回」など）を添える。流れを2つ以上並べるときは、どれも同じ始まりの盤面から始め、コマと矢印の列をそろえる。1つの矢印で2手以上進めるときは、手数を矢印の言葉（「2手注ぐ」など）で言い、そのコマはその手数でしか作れない姿にする。図に添える回数は、どの矢印で何回数えたかがコマと矢印から読めるようにする。

### 押せない図

- 押せない図（操作のタブの本番の部品の図、採点のタブの流れの図など）は inert にし、触れる例と見分けられるようにする。
- 押せない図には手がかり（破線の枠と指のアイコン）を置かない。手がかりは触れる例の合図なので、押せない図にあると押せそうに見えるため。操作した所は、本番の選んだ状態か、押した所を囲む無彩の枠と矢印の言葉で示す。
- 矢印の言葉は、1行3文字ほどの短い動詞句にし、`/` の文節でだけ行を分ける。操作の呼び名は `frontend/src/games/play-vocabulary.ts` の文節で区切った呼び名から使う。

### 盤面の大きさ

- 例と押せない図の盤面の単位（マス・駒・ボトルなど）は、ゴールの盤面の単位と見比べて同じ物に見える大きさにする。単位どうしの間も、本番のプレイ画面と同じ比にする。
- 盤面部品が地を透かして描く所（穴など）があるパズルでは、例と図の下にプレイ画面と同じ地を敷く。
- 例の面の高さは中身から決め、持ち上げる・傾けるなど動く物が面の端に迫らない余白をとり、余りの空きを残さない。
- 例と図は、スマートフォンの幅（320px まで）の面に収める。触れる例や横に並べる対が収まらないときは、単位を小さくせず、例の盤面を短くする（使わない列を切り落とす、など）。押せない図のコマを並べて収まらないときだけ、収まる大きさまで単位を小さくする。

### 文

- 1項目1〜2文の敬体で、「〜します」「〜です」と言い切る。読点を外すために分けた文は数に含めない。
- 手のルールは、遊ぶ人が盤面でする手を動詞で言う。形のルールは、目指す形で言う。どちらも、禁止（〜てはいけません）ではなく、できることか目指す姿で言う。
- 物を定義する文（「〜は、…です」）と、実装・仕様の言葉（物を役割で呼ぶ言葉や、操作を仕組みで言う言葉）は使わない。人が盤面を指して言う呼び名と動詞にする。

  ```
  OK:
  - いちばん上の色が同じでまだ入るボトルに注げます。空のボトルにも注げます。
  - 1色でいっぱいになったボトルはもう選べません。
  NG:
  - 注ぎ先は、空のボトルか、いちばん上が同じ色のボトルです。
  - 1色で満杯のボトルは、注ぐボトルに選べません。
  ```

- 依頼（〜してください）と終助詞（ね・よ）、テーマで変わる色の名前は使わない。
- 画面の文は、入口の一文・図の下の流れも含めてすべて、文節の切れ目を `/` で区切って書き、`HowToPlayPhrases` で描く（`/` の間でだけ折り返す）。「の」で名詞にかかる語と名詞の間（「空のボトル」「別の問題」）には `/` を置かない。手で入れた改行と `word-break: auto-phrase` に頼らない（auto-phrase は iPhone の Safari では効かず、1文字ずつ折り返す）。矢印の言葉の区切り方は「押せない図」の決まりに従う。
- 読点は打たない。並べる語は中黒（・）でつなぐ。読点を外すと読み違える文は、文を分けるか、語順を変える。

  ```
  OK:
  - 問題ごとの/基準時間以内なら/満点です。/超えると/下がります。
  - いちばん上の色が同じで/まだ入るボトルに/注げます。/空のボトルにも/注げます。
  NG:
  - 問題ごとの/基準時間以内なら/満点で、/超えると/下がり、
  - いちばん上の色が同じで/まだ入るボトルか、/空のボトルに/注げます。
  ```

## 動作フロー

始め方:

- どの始め方でも、始めたときのブランチ（`git branch --show-current`）を控える（7-1 で使う）。
- 新しく作る・新しい形に移す: 1から進める。
- 改める: 対象が新しい形でない（「新しい形」の Grep に出ない）ときは、「新しい形に移す」として1から進める。新しい形のときは、1から進め、2で行を今の画面から書き起こす。その遊び方を入れた PR の本文に表があれば、`【PO】` の付いた文を、今も画面にある文にだけ引き継ぐ。
- 改めずに見直した結果だけを求められた: 5-2 と6を1回だけ行い、見つけた所と6の指摘は直さずに報告に載せる。PR は開かず、決まりの重さの例外もこの報告で述べる。報告は次に分ける。
  - 必ず守るものの違反と不具合
  - 遊ぶ側が迷った・止まった所と、言葉の引っかかり
  - 採点役の点数と指摘
  - 画面で見つけた崩れ

手順:
