# design-puzzle-how-to-play

`/design-puzzle-how-to-play <game>`

パズルの遊び方（ヘルプ）を作る・改める・見直す。遊び方が保証することは `docs/プロダクト/ゲーム/GAME-007-遊び方.md` が決める。コードの置き場所と共通の契約は `.claude/rules/game-structure.md` の「遊び方」が決める。

このスキルの言葉:

- `<game>`（`$ARGUMENTS`）は `frontend/src/games/` のディレクトリ名にする。`<Game>` は `frontend/src/games/<game>/ui/` の画面のファイル名の頭（例: `hitofude-puzzle` は `HitofudePuzzle`）にする。
- 該当パズルの仕様は `frontend/src/games/<game>/display-name.ts` の表示名と `docs/プロダクト/パズル/` の各仕様の題名を照らして探す。
- 「共通の部品」は `frontend/src/components/` の `HowToPlay` で始まる部品と `how-to-play-` で始まるモジュールを指す。置き場所と props の足し方は `.claude/rules/game-structure.md` の「遊び方」に従う。次の見せ方は共通の部品で描きゲームの側では描かない。共通の部品で足りないときはゲームの側で補わず1つのゲームだけが使う働きでも共通の部品に働きの名前で足す。props の意味と選べる値はその部品の props の説明を読んで決める。
  - 層: 帯・タブとその出し入れ・開閉と Esc（`HowToPlayOverlay`）・ゴールの盤面の枠と見せ直すボタン（`HowToPlayGoalFrame`）・チュートリアルの入口（`HowToPlayOverlay` の `onOpenTutorial`）
  - 例: ルールの一文と例の面（`HowToPlayRule`）・例の面と元に戻すボタン（`HowToPlayExamplePanel`）・例と添える言葉（`HowToPlayExample`）
  - 例に添える物: 押す所の手がかり（`HowToPlayPressHint`）・判定（`HowToPlayVerdict`）・判定の ✓ / ✕ の記号（`HowToPlayVerdictMark`）・記号と言葉の1行（`HowToPlayVerdictLine`）・入れ替える言葉の層（`HowToPlayCaptionLayers`）・✓ / ✕ の凡例（`HowToPlayMarkLegend`）
  - 文と図: 文節で折り返す文（`HowToPlayPhrases`）・まとまり（`HowToPlaySection`）・押せない図の流れ（`HowToPlayFlowFigures`）・操作の行（`HowToPlayOperationRow`・`HowToPlayMenuOperations`）・採点の行（`HowToPlayScoreRow`）・キーの表（`HowToPlayKeyTable`）
- 「単位」は例の中で押す物1つ（マス・駒・ボトルなど）を指す。
- 「新しい形」は `HowToPlayOverlay` で作った遊び方を指す。新しい形のゲームは `frontend/src/games/` を `HowToPlayOverlay` で Grep して探す。
- 「起点 URL」は今のブランチで `AGENTS.md` の実行コマンドで起動した開発サーバーの URL を指す。
- 番号は動作フローの手順を「5」と書く。その中の小手順は「5-2」と書く。

## 決まりの重さ

- 必ず守る: GAME-007・`.claude/rules/game-structure.md` の「遊び方」・`DESIGN.md`・`GAME.md`・`AGENTS.md`・「大原則」・「始め方」で決めた範囲の「動作フロー」。どれかを破っているか動作フローを飛ばしていれば作業は終わっていない。
  - 例外: 次のときは動作フローを8まで進めて8で未達として報告する。
    - 「進め直し」の上限まで6を行っても採点役の点数が 100点に届かない。
    - プレイ画面・チュートリアルの側の呼び名の揺れで H6 を遊び方だけでは満たせない。
- 迷ったらこうする: 「基本の形」。パズルに合わなければ変えてよい。必ず守るものに由来する所は変えない。
- 書いていないこと: `AGENTS.md` の「進め方」に従って決める。

## 大原則

- H1. 一流の商用パズルアプリの遊び方としてそのまま出せる出来にする。採点役の点数を 100点に届かせる。アプリの既存の画面の出来を上限にしない。
- H2. 本番のルール・操作・状態の知らせ・補助・数え方を過不足なく載せる。仕様が「遊び方で説明する」としたものも載せる。
- H3. 1つの項目・1つの例には1つのことだけを置く。
- H4. 文は盤面と図で伝わらないことだけをそのパズルに固有の言葉で言う。どのパズルにも当てはまる言葉（「ルールどおりに」など）は入れない。
- H5. 例・押せない図・ゴールの盤面が本番と一致することを本番の関数と照らすテストで確かめる。
- H6. 物の呼び名と操作の動詞は遊び方の中でもプレイ画面のボタンや知らせともチュートリアルとも揺らさない。
- H7. 文字の大きさと太さは共通の部品が持つ。ゲームの側では文字の大きさと太さを決めるクラス（`DESIGN.md` の「文字階層」のクラスと `font-` で始まる太さのクラス）を書かない。文は共通の部品の働きの合う所（ルールの一文・まとまりの見出し・例に添える言葉など）に渡す。
- H8. スマートフォン（iPhone 13 と幅 320px）と PC（幅 1280px）で欠け・崩れ・ずれ・重なりが無い。触った後と動きの途中も含める。
- H9. 例・判定・手がかりで何を見せるかはほかのゲームから写さず「基本の形」とそのパズルのルールの型から決める。共通の部品の使い方は新しい形のゲームの実装に合わせる。

## 基本の形

### ルールの型

ルールの例の判定・手がかり・文はルールの型で決める。1つのパズルに両方の型のルールがあってもよい。

- 形のルール: 盤面の形が目指す形に合うかを決めるルール（バイナリパズルの「どの行も四角と丸が同じ数」など）。
- 手のルール: 注ぐ・動かすなどの手が通るか弾かれるかを決めるルール（水のパズルの「いちばん上が同じ色のボトルに注げる」など）。

### 入口

- 何をするパズルかの一文を「〜パズルです」と言い切る。盤面の何を何で埋める・つなぐ・動かすかを具体的に言う。
- 盤面に最初からある物と遊ぶ人が変える物の見分けがあるパズルではその違いをゴールの盤面で見せる。
- ゴールの盤面は GAME-007 と `DESIGN.md` の「動き」に従って見せる。音は鳴らさない。見せ直しは終わった後の見せ直すボタンだけにする。
- ゴールの盤面は終わりの姿が整って見える手順にする（水のパズルなら空のボトルを端に寄せて終える）。

### 動き

- 例・ゴールの盤面・押せない図は最初の姿を済んだ姿として静止で描く。動きは触った手とゴールの再生の手だけに流す。
- 開いたとき・元に戻したとき・タブを戻したとき・親が描き直したときに済んだ手の動きを流し直さない。動きを始める値（直前の手の知らせなど）は描くたびに作り直さない。タブを替えても中身と動きを保つ仕組みは `HowToPlayOverlay` が持つのでゲームの側に足さない。

### 触れる例

ルールと操作のタブの例は GAME-007 の例の決まりに従う触れる例にする。

- 判定と反応:
  - 例の判定と遷移は `.claude/rules/game-structure.md` の「遊び方」に従って求める。遊び方の側で書き写さない。
  - 例の押す所には本番の盤面と同じ読み上げ名（aria-label）を付ける。
  - 例を押したときの反応と音は受け付けない反応も含めて本番と同じにする。音の鳴らし方は `.claude/rules/game-structure.md` の「遊び方」に従う。本番に無い反応は例だけで返さない。本番のその入口（指・マウス）に無い反応をほかの入口（キーボードなど）から借りない。
  - 触った後も判定と印は今の盤面から出し直し続ける。手が通ったのに例が教えるルールに反して見える変化（押した所まで道が戻る など）は判定の場所で起きたことを言う。
- 指とキー:
  - 指のスクロールは例の操作が始まる物（なぞる・引く・スワイプする物）の上でだけ止める。盤面の全体で止めると例を並べたタブを指で送れる所が少なくなるため。止める所は単位が小さくても指で始められるよう 44px 四方からにする。押すだけの操作では止めない。本番の盤面は全体で止めたままにする。盤面部品への渡し方は `.claude/rules/game-structure.md` の「遊び方」に従う。
  - 本番の盤面が Esc で選び（駒・島を選ぶなど）を解くゲームでは例の選びを `useHowToPlayExampleSelection` で層に知らせて Esc で選びを解く。本番に Esc の選び解除が無いゲームでは知らせない。
- 手がかり:
  - 例が見せる手は次に押す所の手がかり（`HowToPlayPressHint`）で示す。
  - 手がかりどおりに押していく途中で例が教えるルールと別のルールの違反が起きない盤面にする。
  - 本番に弾く反応が無い手（押すと別の操作になる所など）には手がかりを付けず印だけで示す。
  - 文が2つの手を言うときは手がかりも両方の手を順に示す。なぞる手の手がかりはなぞったときだけ進める。
  - 触ったら手の続きがあれば次に押す所へ移す。続きが無ければ消す。弾かれたら盤面が変わるか選び直すまで出さない。元の形に戻ったらまた出す。
- 重ねる物:
  - 盤面に重ねる物（手がかりの指と枠・手ごとの札）は単位の中身（数字・メモ・枚数・文字・駒・道の線・始点や先端の印・向きの矢印）と互いを隠さない所に置く。
  - 手がかりの置き方は `HowToPlayPressHint` の `frame`・`outline`・`pointer`・`corner` の説明から単位の中身を隠さない値を選ぶ。
- 面と言葉:
  - 触れる例は元に戻すボタンのある面（`HowToPlayRule` の面か `resettable` を渡した `HowToPlayExamplePanel`）に置く。例は最初の形から変わったかを `useReportHowToPlayExampleChange` で面に知らせる。元に戻すボタンの置き場所は面が決めるのでゲームの側でボタンのための間を足さない。
  - 例の下には判定と判定に添える言葉（起きること・✕ のわけ・別のルールで弾かれたこと・凡例）だけを置く。操作の補足は例の下に置かず文か文に添える補足に入れる。
  - 入れ替わる言葉は出しうる言葉をすべて `HowToPlayCaptionLayers` の層として渡す。✓ / ✕ の凡例は `HowToPlayMarkLegend` に盤面に出ている印を渡して出す。

### ルールのタブ

- 中心のルールを先に並べる。入口で伝わるもの（最初からある物のルールなど）は後ろに置く。
- 1つのルールは `HowToPlayRule` に一文と例の組で渡す。例の形は次の3つから選ぶ。
  - できる形とできない形の対。見比べて違いが分かるようにする。
  - 違いが出る2つの形の対。どちらもできる形で違いが出るルール（移る量など）に使う。判定の代わりにその例で起きること（「2つとも入る」など）を例の下に出す。
  - 1つの盤面で手ごとの ✓ / ✕。手のルールで判定した手のほかに通る手がある盤面に使う。✕ の盤面に通る手が見えるとできるように読めるため。並べ方は `stacked` にする。
- 形のルールの判定（✓ できる / ✕ できない）:
  - できる形の例は最初は ✓ で静止させる。1回押すとルールに反する形になる所に手がかりを付ける。できない形の例は最初から ✕ の形で静止させる。
  - 判定する所（行・列など）がまだ埋まっておらず違反も無い間は ✓ を出さず「途中」にする。埋まる前に ✓ を出すと目指す形に届いたと読めるため。
  - 判定の理由が盤面から読み取りにくいルールでは数か見比べる所の印（凡例を添える）を出す。数や見比べる所の凡例は判定の言葉に混ぜず判定の右に添える物（`HowToPlayVerdict` の `aside`）として渡す。
  - 本番に違反の印があるパズルでは例にも同じ印を出す。判定の言葉と数は印と同じ描画で替える。
  - 本番の印だけでは盤面のどこが崩れているか読み取れないときは遊び方だけの見せ方（多い方の単位を示す など）を例の盤面に足す。足し方は `.claude/rules/game-structure.md` の「遊び方」に従う。
- 手のルールの判定（✓ 注げる / ✕ 注げない などのその手の動詞）:
  - 試す前は例が見せる手が通るかを出す。手を打った後は今の盤面の答えと食い違わないよう試した手の結果だと分かる言い方（✓ 選べた など）にする。手を打った後の盤面を形として判定すると通った手の直後に ✕ が出て失敗に読めるため。
  - 判定はどの手（どこからどこへ）の答えかが図で分かるように付ける。手ごとに付けて動詞が単位の下に収まらないときは記号の意味を凡例で添える。
  - 2次元の盤面で手ごとに付けるときは候補の単位（先端の隣のマスなど）に ✓ / ✕ の印を `HowToPlayVerdictMark` で置く。`placement` はその説明から選ぶ。大きさは単位の大きさに比べて決める。本番の弾かれた手の印がその単位に出ている間は消す。
  - 手ごとの印は中身の無い単位では中央に置く。中身のある単位では中身と手がかりの指を避けた角に置く。
  - ✕ のわけが盤面から読み取りにくい手（満杯なのに上の色が同じ など）は押す前から ✕ の真下にわけを添える。わけは単位の幅に収まる短い言葉（満杯・色違いなど）にする。隣の単位のわけと重ねない。
- 判定の下のわけ:
  - 例が教えるルールそのもののわけ（残ったマスの数・出た先の数字など）は `HowToPlayVerdict` の `ruleReason` で渡す。
  - 触って例が教えるルールと別のルールで弾かれた・崩れたわけは `reason` で渡す。破ったルールは幅 320px の1行に収まる短い言葉にまとめる。

### 操作のタブ

- 置き方・動かし方は本番と同じ見た目の図と本番と同じ単位（マス1つ・ボトル1本など）の触れる例で示す。2回押して1手になる操作は1手を打ち終えるまでを触れる例で示す。細かいポインターだけの操作（右クリック・キーボード）は `HowToPlaySection` の `availability` を `fine-pointer` にして出す。
- やり直しの操作は本番のボタンとメニューと同じ見た目の押せない図で示して例の面の外に置く。説明は何をする操作かと時間と回数がどうなるか（何が残り何が0に戻るか）を言う。説明は図のすぐそばに置く。似た操作は名前の言い直しでなく違いを言う。同じ注記を繰り返さない。点への影響は採点のタブだけに書く。
- 補助（GAME-008）は本番でそれを使う操作の近くに本番と同じ見た目の図で載せる。
- 状態の知らせはルールの触れる例で同じ反応を見せられるなら項目を立てない。見せられないもの（手詰まりなど）は本番と同じ見た目の押せない図でやり直しの操作の後に置く。

### 採点のタブ

- 結果画面の採点基準（`frontend/src/games/<game>/ui/result/<Game>ResultScreen/score-criteria.ts`）と同じ評価項目・満点・順でまとめる。点がどれだけ下がるかは `score.ts` の式から具体的に言う。言う場所は次のように分ける。同じことを2か所で言わない。
  - 評価項目の見出しの下の一文: 点の決まり方（満点から引いていくか・比でどこまで下がりどこで0点になるか）。
  - 数えるものの行: 1回あたりの減点（「1回 −5点」）と何を1回と数えるか。
- 数え方に例外があるパズルでは例外が起きる操作の流れをコマに分けて並べた押せない図で見せる。図に数え方（「数えない」「1回」など）を添える。
  - 流れを2つ以上並べるときはどれも同じ始まりの盤面から始める。
  - 1つの矢印で2手以上進めるときは手数を矢印の言葉（「2手注ぐ」など）で言う。そのコマはその手数でしか作れない姿にする。
  - 図に添える回数はどの矢印で何回数えたかがコマと矢印から読めるようにする。

### 押せない図

- 押せない図（操作のタブの本番の部品の図・採点のタブの流れの図など）は inert にして触れる例と見分けられるようにする。共通の部品が inert にしない図はゲームの側で inert の箱に入れる。
- 押せない図には手がかりを置かない。手がかりは触れる例の合図なので押せない図にあると押せそうに見えるため。操作した所は本番の選んだ状態で示すか押した所を無彩の枠で囲んで示す。どの手かは矢印の言葉で言う。
- 矢印の言葉（`HowToPlayFlowFigures` の `steps`）は `/` で行を分けた1行3文字ほどの短い動詞句にする。操作の呼び名は `frontend/src/games/play-vocabulary.ts` の文節で区切った呼び名から使う。

### 盤面の大きさ

- 例と押せない図の盤面の単位（マス・駒・ボトルなど）はゴールの盤面の単位と見比べて同じ物に見える大きさにする。単位どうしの間も本番のプレイ画面と同じ比にする。
- 盤面部品が地を透かして描く所（穴など）があるパズルでは例と図の下にプレイ画面と同じ地を敷く。
- 例の面の高さは中身から決める。持ち上げる・傾けるなど動く物が面の端に迫らない余白をとる。余りの空きを残さない。触ると出る言葉のために取った場所は余りの空きに数えない。
- 例と図はスマートフォンの幅（320px まで）の面に収める。
  - 横に並べる対が面に収まらず縦に積まれて見比べにくいときは単位を小さくせず例の盤面を短くする（使わない列を切り落とす など）。
  - 1つの触れる例が収まらないときも単位を小さくせず例の盤面を短くする。
  - 押せない図のコマを並べて収まらないときだけ収まる大きさまで単位を小さくする。

### 文

- 1項目1〜2文の敬体で「〜します」「〜です」と言い切る。読点を外すために分けた文はこの数に含めない。
- 手のルールは遊ぶ人が盤面でする手を動詞で言う。形のルールは目指す形で言う。どちらも禁止（〜てはいけません）ではなくできることか目指す姿で言う。
- 物を定義する文（「〜は…です」）と実装・仕様の言葉（物を役割で呼ぶ言葉や操作を仕組みで言う言葉）は使わない。人が盤面を指して言う呼び名と動詞にする。

  ```
  OK:
  - いちばん上の色が同じでまだ入るボトルに注げます。空のボトルにも注げます。
  - 1色でいっぱいになったボトルはもう選べません。
  NG:
  - 注ぎ先は、空のボトルか、いちばん上が同じ色のボトルです。
  - 1色でいっぱいのボトルは、注ぐボトルに選べません。
  ```

- 依頼（〜してください）と終助詞（ね・よ）とテーマで変わる色の名前は使わない。
- 折り返す文（入口の一文・ルールの一文・まとまりの一文・操作と採点の文・流れの図の下の言葉）は文節の切れ目を `/` で区切って共通の部品の文の props（`description`・`text`・`lead`・`note`・`measure`・`caption` など）に渡す。部品が `/` の間でだけ折り返す。
  - 「の」で名詞にかかる語と名詞の間（「空のボトル」「別の問題」）には `/` を置かない。
  - 手で入れた改行と `word-break: auto-phrase` に頼らない（auto-phrase は iPhone の Safari では効かず1文字ずつ折り返す）。
  - 判定・凡例・わけ・数え方の値は区切らず1行に収まる短い言葉にする。
- 読点は打たない。並べる語は中黒（・）でつなぐ。読点を外すと読み違える文は文を分けるか語順を変える。

  ```
  OK:
  - 問題ごとの基準時間/以内なら/満点です。/超えると/下がります。
  - いちばん上の色が同じで/まだ入るボトルに/注げます。/空のボトルにも/注げます。
  NG:
  - 問題ごとの基準時間/以内なら/満点で、/超えると/下がり、
  - いちばん上の色が同じで/まだ入るボトルか、/空のボトルに/注げます。
  ```

## 動作フロー

始め方:

- どの始め方でも始めたときのブランチ（`git branch --show-current`）を控える（7-1 で使う）。
- 新しく作る・新しい形に移す: 1から進める。
- 改める: 1から進める。対象が新しい形でないときは「新しい形に移す」として進める。2では表の行を今の画面から書き起こす。その遊び方を入れた PR の本文に表があれば `【PO】` の付いた文を今も画面にある文にだけ引き継ぐ。
- 改めずに見直した結果だけを求められた: 5-2 と6を1回だけ行う。見つけた所と6の指摘は直さずに報告に載せる。PR は開かない。「決まりの重さ」の例外もこの報告で述べる。報告は次に分ける。
  - 必ず守るものの違反と不具合
  - 遊ぶ側が迷った・止まった所と言葉の引っかかり
  - 採点役の点数と指摘
  - 画面で見つけた崩れ

手順:

1. パズルを知る:
   1. 「参照する正本」の表で動作フローの1に当たる文書とコードを読む。ルール・操作・状態の知らせ・補助・数え方と物の呼び名・操作の動詞を書き出す。ルールごとに「ルールの型」のどちらかを決める。
   2. `AGENTS.md` の実行コマンドで開発サーバーを起動してレベル1と2を1問ずつ解く。チュートリアルがあれば遊んで文の言い方・呼び名・盤面の見せ方を確かめる。
2. 項目を決める: 1で書き出したものを `assets/item-table.md` の形で書き出しの表・項目の表・呼び名の表にしてスクラッチのディレクトリの `how-to-play-<game>-tables.md` に書く。項目ごとに文と例を決める。書き終えたら表を読み直して `assets/item-table.md` の決まりに合っていることを確かめる。
3. 実装する:
   1. `.claude/rules/game-structure.md` の「遊び方」と「基本の形」に従って作る。
   2. テストは `.claude/rules/vitest.md` に従って書く。H5 のテストで次を確かめる。例の最初の姿の判定・触った後の遷移と違反の印と判定の言葉・手がかりの出し入れ・元に戻すの出し入れ・効果音・押せない図の各コマ・ゴールの盤面の再生と飛ばし。
   3. 共通の部品を直したときは新しい形のほかのゲームと新しい形でないゲームを控える。
4. 言葉を整える: 新しいサブエージェントに `references/review-requests.md` の「編集者役」で挙げさせて `【PO】` の言い回しを除いて直す。2回目からは前の回に採った言い回しと食い違う言い換えを採らない。前の回の言い回しが「文」の決まりに反しているときだけ替える。画面の文を変えたら2の表もそろえる。
5. 自分で通す:
   1. `AGENTS.md` の全品質検証を通す。
   2. `docs/開発/画面レビュー手順.md` に従って画面を確かめる。
      - 開く: 起点 URL の遊び方をゲームのホームとプレイ中のメニューの両方から開く。スマートフォンでは動きを減らす設定でも開く。
      - 撮る: H8 の幅で各タブを最後まで撮って1枚ずつ見る。例とゴールの盤面を押して触った後と動きの途中も撮る。開き直したとき・元に戻したとき・タブを戻したときも撮る。
      - 確かめる: H8・「動き」の決まり・文字の強弱と余白とバランス・文の折れ方と読点・例と押せない図の単位とゴールの盤面の単位の大きさの比。
   3. 3-3 で控えた新しい形でないゲームは遊び方をゲームのホームから開いて PC とスマートフォンの幅で撮る。崩れていないことだけを確かめる。
6. 見直す: `references/review-requests.md` の「作る側」「遊ぶ側」「採点役」をそれぞれ新しいサブエージェントに並行して頼む。3-3 で控えた新しい形のゲームがあれば作る側（表は「無し」として渡す）と採点役をそのゲームにも頼む。
   - 必ず守るものの違反と不具合は直す。同じ原因の所がほかに無いか探してまとめて直す。
   - 遊ぶ側が迷った・止まったと書いた所はどの大原則に反しているか原因を探して直す。言葉に引っかかった所はその感想を4の編集者役に渡してまとめて直す。
   - 採点役の指摘は必ず守るものに照らして採るものを決めて重い順に直す。前の回の採点役と食い違う指摘は前の回に採った方を保つ。必ず守るものに照らして前の方が誤っているときだけ替える。採点役が遊び方の中だけでは直せないとした指摘は直さずに控えて8で報告する。
   - 直したら「進め直し」に従う。
7. PR を開く:
   1. PR の base を決める。`git fetch origin main` の後で次のように決める。
      - 控えたブランチが `main` でなく `git merge-base --is-ancestor origin/<控えたブランチ> origin/main` が終了コード 1（まだ `main` に入っていない）で終わるとき: 控えたブランチ
      - 終了コード 128（控えたブランチが origin に無い）のときとそれ以外: `main`
   2. `review-changes` スキルを起動して確かめた指摘を直す。base が `main` でないときは `review-changes` が `main` と比べるので base の PR の差分に当たる指摘は除いて8で報告する。直したら「進め直し」の1つ目に従って5まで進め直す。`review-changes` はかけ直さずに 7-3 へ進む。
   3. `commit-pr` スキルを `baseBranch=<7-1 の base>` で起動してコミットし PR を開く。スクラッチの表と5で確かめたこと・確かめられなかったことを PR 本文に載せる。
8. PO に見せる: `AGENTS.md` の「検証」に従ったプレビュー URL・5-2 のスクリーンショット（PO が開ける形で渡す）・採点役の最後の点数を渡す。自分で決めたこと・直さなかった指摘・遊び方の中だけでは直せない指摘・「決まりの重さ」の例外に当たって未達のこと・3-3 で控えたゲームを短く添える。

進め直し:

- 直したら5まで進め直す。言葉を変えたときは4から進め直す。それ以外は5から進め直す。
- 6を終えて6の指摘で何かを直したときか採点役の点数が 100点に届いていないときはもう一度6を行う。
- 6は最初を含めて4回までにする。4回目は違反と不具合と遊ぶ側が迷った・止まった所だけを直す。5まで進め直して7へ進む。4回目の採点役の指摘で直さなかったものは8で報告する。

PO から指摘を受けたとき:

1. その遊び方を直して「進め直し」に従って5まで進め直してから6を行う。6の回数は PO の指摘ごとに数え直す。PO が言い回しを決めたときは表のその文に `【PO】` を付ける。6を終えたら変更を `AGENTS.md` の「Git運用」に従って PR に載せる。PR 本文の表をスクラッチの表に置き換えて8で PO にもう一度見せる。
2. 5と6で拾えなかった理由を探す。そのパズルだけのことでなければ `add-skill` スキルを起動してこのスキルを直す。直す所は理由で決める。
   - 大原則か基本の形が足りなかった: SKILL.md を直す。
   - 見直す側の目が届かなかった: `references/review-requests.md` の依頼を直す。
