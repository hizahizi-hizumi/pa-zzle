# 複数PR分割の境界判断ルール

## 目的

ひとまとまりの未コミット差分を、何PRに・どの順序で・どの依存関係で分けるかを決める。1PRで済むなら分けない。

## 分割判断

- 1PR = 1つの目的。1文で要約できないなら分割を検討する。
- 機械的変更と意味変更は原則別PR。
- 純粋なリファクタと挙動変更は原則別PR。
- 依存更新 / CI / 開発環境変更と学習者向け挙動変更は原則別PR。
- ロールバックのリスクが大きく異なるなら分ける。
- 独立してレビュー・マージできるなら分割候補。
- 小さいという理由だけで関連変更を不自然に分断しない。

## AmuQueryの凝集単位

次はディレクトリが異なっても、同じ目的を成立させるなら同一PRに置くことを優先する。

- 1問題の problem / fixture / answer path / manifest / oracle / 採点基準 / mutation
- 1LUの scope / 学習設計 / material / practice / TST / 学び直し導線 の整合変更
- 1つのruntime機能と、その契約・回帰テスト・CLI/Web導線
- 1つのlearner-facing変更と、それを成立させる表示・採点・進捗変更

逆に、同じファイル群でも変更理由が異なれば分割する。

## 分割戦略

### 垂直スライス

小さくても利用・検証可能な単位で完成させる。AmuQueryでは、新しい問題型やruntimeを problem → fixture → answer → runtime → grading → CLI/Web まで閉じるVertical Sliceを優先する。

### 段階導入

契約追加 → 利用側移行 → 旧経路削除のように、各段階でmainを壊さない形にする。

### スタックPR

後続PRが前PRの追加・リファクタを前提にする場合のみ使う。後続PRのbaseを前PRブランチにする。

## 依存判定

後続PRが次のいずれかを満たすなら前PR依存とみなす。

- 前PRで追加した関数・型・ファイル・schema・contractを参照する。
- 前PRなしでは `uv run --frozen python -m dev.tools.validate` や対応runtimeが成立しない。
- 前PRの移動・リファクタ後の構造を前提に差分が作られている。

該当しなければ、入力baseから切る独立PRを優先する。

## テスト・文書の扱い

- テスト、fixture、oracle、採点基準は対応する変更と同じPRに置くのが基本。
- 現在仕様の正本更新は、その仕様変更と同じPRに置く。
- ADRは判断理由の履歴であり現在仕様の代替ではない。ADRだけを別PRにして正本更新を欠落させない。

## 数の目安

- 1PRで済むなら1PR。
- 2〜4PRは通常範囲。
- 5PR超は、分割が本当にレビュー・revert・依存管理を改善するか再評価する。

## 禁止事項

- PR数を増やすこと自体を目的にする。
- 循環依存するPRセットを作る。
- Vertical Sliceをフォルダ境界だけで細切れにする。
- 巨大PRを許容したうえで「レビューが大変」とだけ書いて済ませる。
