# 複数 PR の境界

ひとまとまりの未コミット差分を、何 PR に、どの順序と依存関係で分けるかを決める。

## 分けるか

- 1PR を、1文で要約できる1つの目的にする。1文で要約できなければ分割を検討する
- 1PR で済むなら分けない
- 機械的変更と意味変更は原則別 PR にする
- 純粋なリファクタと挙動変更は原則別 PR にする
- 依存更新・CI・開発環境変更と利用者向け挙動変更は原則別 PR にする
- ロールバックのリスクが大きく異なるなら分ける
- 独立してレビュー・マージできるなら分割候補にする
- 同じファイル群でも変更理由が異なれば分ける
- 小さいという理由だけで関連する変更を分断しない
- PR 数を増やすこと自体を目的にしない

## 同じ PR に置くもの

次は、ディレクトリが異なっても同じ目的を成立させるなら同じ PR に置く。

- 1つの機能と、その契約・回帰テスト・UI / API の導線
- 1つのバグ修正と、その再発を防ぐテスト
- schema / API / 型の変更と、その新契約へ必須で追従する利用側
- テスト・契約文書と、対応する変更
- 文書・ルール・ADR の更新と、それを求める変更。どの変更がどの更新を求めるかは `AGENTS.md` の「文書」を読んで決める

## 分け方

- 垂直スライス: 小さくても利用・検証できる単位で完成させる。機能を成立させる実装・契約・テスト・利用導線を、フォルダ境界だけを理由に分断しない
- 段階導入: 契約追加 → 利用側移行 → 旧経路削除のように、各段階で `main` を壊さない形にする
- スタック PR: 後続 PR が前 PR の追加・リファクタを前提にするときだけ使い、後続 PR の base を前 PR のブランチにする
- 循環依存する PR の組を作らない

## 依存の判定

後続 PR が次のいずれかに当たるなら前 PR に依存するとし、どれにも当たらなければ入力の base から切る独立 PR にする。

- 前 PR で追加した関数・型・ファイル・schema・契約を参照する
- 前 PR なしでは変更範囲に対応するテスト・ビルドが成立しない
- 前 PR の移動・リファクタ後の構造を前提に差分が作られている

## 数

- 2〜4PR は通常の範囲とする
- 5PR を超えるときは、分割が本当にレビュー・revert・依存管理を改善するかを見直す
