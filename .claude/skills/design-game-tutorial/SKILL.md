# design-game-tutorial

パズルを知らない人が、小さな盤面を実際に操作してルールと操作を身につけ、そのパズルを遊びたくなるチュートリアルを設計・実装・見直す Skill。

## 起動

`/design-game-tutorial`

引数 `$ARGUMENTS` を対象ゲームとして扱う。引数が無ければ会話 context から対象ゲームを決める。既存チュートリアルの見直しだけを頼まれた場合は「10. 見直し」から、人間の指摘に対応する場合は「9. 指摘を受けたとき」から始める。

## 1. 原則

原則は、`APP.md` の最上位の体験軸（面白い・楽しい・ワクワク）をチュートリアルに当てはめたもの。チュートリアルの判断の拠り所はこの6つにし、原則で決まらないときだけ `APP.md`・`GAME.md` に戻る。2章以降は原則を満たすための具体的なやり方で、原則と食い違うときは原則を優先する。原則は短い一文と理由1文に保ち、例は書かない（例はチェックリストの確認点に置く）。

- **P1. 始まった時点で、何をするパズルか・ゴール・始まりの盤面が分かる。** 指示より先に目的を伝えないと、知らない人は何のために操作しているのか分からない。
- **P2. ルールは言い切ってから、すぐその盤面で使わせる。** 読んだだけのルールは身につかない。操作を教える手を除き、使う手はそのルールで決まる手にする。
- **P3. 人が横で教えるような、自然で1つにそろった言葉で話す。** 採点する先生の口調も、説明書の直訳も、言葉の揺れも、プレイヤーを遠ざける。
- **P4. 画面の反応が、言葉で教えたことと食い違わない。** 食い違いは、ルールの説明そのものを疑わせる。
- **P5. 遊んでみたくなる形で、本番へ正直につなぐ。** 完成をご褒美として見せ、本番の難しさを約束しすぎないことで、期待と実際がずれずに本番へ進める。
- **P6. 誰でも同じ体験にたどり着け、プレイを邪魔しない。** 設定や開いた場所によって、伝わることが欠けたり、プレイが乱れたりしてはいけない。

## 2. 目的と範囲

- **対象**: そのパズルを知らない人、ルールがうろ覚えの人。自分で開いた人だけ（自動では始めない）。
- **終わったときの状態**: ルールと操作が分かり、レベル1〜2を自分で始めて楽しめる。主目的は「遊んでみたくなる」ことで、ルールが分かることはその前提条件。
- **扱う範囲**: 基本ルールまで。基本ルールとテクニックの線引きはパズルごとに判断する。ルールそのものと、その直接の帰結（ルールを盤面に当てはめるだけで決まる読み）は基本に入れる。仮定を重ねる読みなど上位レベルで要る読みは、別機能のテクニック集に回す。
- **遊び方ダイアログとの分担**: ダイアログは知っている人が数秒で確認する場所。チュートリアルは知らない人が操作して1〜2分で体験する場所。

## 3. 体験の型

1枚の本物の盤面を、最初から最後まで使う（複数の小盤面を渡り歩かない）。次の順に進める。

1. **入口（P1）**: 名前とピクトグラムの下に何をするパズルかの一文、完成した盤面に「この形がゴールです」、始まりの盤面に「最初はこのように〜」を、絵と言葉の両方で見せてから本編に入る。
2. **最初の操作（P2）**: 入口で言ったことは言い直さない。最初のルールと操作だけを言い、1手目を実際に操作させる。操作の種類ごとに1手ずつ。
3. **ルールを1つずつ（P2）**: ルールを言い切り、そのルールで決まる手をすぐさせる。
4. **知っているルールだけで考える（P2）**: 新しいルールを足さずに、自分で考えて置く手を入れる。
5. **ヒントの知らせ（P6）**: 止まった人も自分で先へ進めるよう、迷ったら少し待つと印が出ることを伝える。
6. **自由に完成（P5）**: 残りを自分で解かせ、本番と同じ完成演出で締める。
7. **本番へ（P5）**: 開いた場所に合わせて「レベル1を遊ぶ」か「プレイに戻る」へつなぐ。「もう一度」も置く。

## 4. 盤面の条件（P2）

盤面と手順は次をすべて満たす。満たすかどうかは推測せず、総当たり探索と単体テストで確かめる。条件を満たす盤面は「存在しない」という結論を、自分で探索せずに受け入れない。

- **最初の配置だけで解が1つに決まる**（手を動かすパズルでは、最短の解き方が1通り）。操作を教える手が無くても一意性は崩れない。操作を教える手で置いた値を、後の手順の根拠に使うのはよい。
- **操作を教える手順を除き、各手順の手は、その時点で示したルールだけで決まる。** ルールを示す手順の手は、そのルールで決まり、それまでのルールでは決まらない。
- **プレイヤーの手が後の根拠になる。** 前の手順で動かした結果が、次のルールの説明に使われると、手順が一本の流れになる。
- **自由に解く残りは、教えたことだけで1手ずつ解き切れる。**

## 5. 文言（P3）

- **口調**: 短く言い切る、柔らかいですます調。プレイヤーと一緒に盤面を解いていく距離感にする。評価・褒め言葉、クイズ口調の問いかけ、促し・指図、中身のない一文、無機質な体言止めだけの文は書かない。お願いが要る操作だけ「〜してください」にする。
- **自然な日本語**: 声に出して読み、人が横で教えるときの言い方を基準にする。1行に収めるために言葉を削って不自然になったら、別の言い方を探す。
- **言葉をそろえる**: そのゲームで自然な動詞と呼び名を1つ選び、チュートリアル・チップ・違反の一言・遊び方ダイアログで混ぜない。
- **違反の一言（P4）**: 何が起きたかと、当たったルールを言う。後の手順で覆る言い切り（「〜だけ」など）はしない。
- 書いたら、知らない人の目と、上から目線・無機質に敏感な人の目で全文を読み直す。

## 6. 操作・反応・演出

- **誘導中の操作（P4）**: 印の手だけを受け付ける。ほかの操作をしても、教えたルールと食い違って見えないように応える。違う手をしても何も起きない手順にしない。
- **ヒント（P6）**: 手が止まったら、今のルールで決まる手に印を出す。
- **プレイ中から開く（P6）**: 経過時間は止めない。チュートリアルのプレイは記録・採点しない。
- **完成（P5）**: 完成した盤面と完成後の画面はご褒美として明るく見せる。
- **入口の演出（P1・P6）**: 一言を読める長さにし、いつでも飛ばせるようにする。動きを減らす設定でも、目的・ゴール・始まりを順に見せる。

演出の細かい決まり（反応の遅らせ方、「もう一度」で省くもの、動きの値など）は `references/checklist.md` の「細部」に置く。

## 7. コードの置き場所

| 置き場所 | 中身 |
|---|---|
| `frontend/src/games/tutorial.ts` | ゲームに依存しない契約と進行の純関数（手順、ルール、導入、手の結果、完成） |
| `frontend/src/components/TutorialOverlay.tsx`、`components/TutorialOverlay/` | ゲームに依存しない枠、入口の演出、チップ、一言欄、完成時の操作 |
| `frontend/src/games/<game>/tutorial/` | 盤面、手順、手の判定、決め手とヒントの導出、違反の一言（純粋な TypeScript） |
| `frontend/src/games/<game>/ui/<Game>Tutorial.tsx` | 盤面の表示、盤面の演出、`games/tutorial.ts` の進行関数での駆動 |

- 層の依存は `.claude/rules/game-structure.md` と Biome の依存規則（`frontend/scripts/dependency-rules.ts`）に従う。
- state の変化を見て演出を始める effect を書かない。開く・押すなどのイベントか、盤面からの完了通知で進める。
- 2つ目以降のパズルでは、共通の契約と部品をそのまま使えるかを確かめ、使えない部分だけを契約側で一般化する。

## 8. 進め方

1. **調べる**: 対象パズルの有名な実装のチュートリアルと、一般的な知見を先に調べる（事例と出典は `references/history.md`）。
2. **目的と範囲を決める**: 「2. 目的と範囲」をそのパズルに当てはめ、基本ルールとテクニックの線引きを決める。
3. **盤面を探索で作る**: 「4. 盤面の条件」を満たす盤面を総当たりで探し、候補から流れの良いものを選ぶ。
4. **実アプリで作る**: アーティファクトなど別の見た目の試作ではなく、本物の盤面部品で作る。見た目が違うと判断できない。
5. **自分で見直す**: 「10. 見直し」をすべて行う。サブエージェントの報告やテスト結果だけで「確認済み」と言わない。
6. **別のレビュー役に見せる**: 「11. レビューの回し方」に従う。
7. **人間に見せる**: プレビュー URL と、入口から完成までの一言の表、残っている細部、意見が割れた点を添えて渡す。

人間に聞くのは、本当にその人が決めることだけにする。全部入れれば済む選択肢を並べて聞かない。あいまいな指摘の解釈を一言で確かめるのは例外とする。

## 9. 指摘を受けたとき

1. **解釈を一言で確かめる**: 指摘があいまいなとき（「分かりにくい」など）は、何が分からないと受け取ったかを一言で返してから直す。
2. **原則に照らす**: どの原則に反していたかを決める。どの原則にも当たらず、原則を足すべき重さがあると考えたときだけ、原則を見直す案を人間に示す。
3. **スキルは重さに合わせて直す**:
   - 原則の言い方を直す・足すときは、自分では直さず、案を人間に示して決めてもらう。
   - 原則から導ける確認が抜けていただけなら、チェックリストの原則の確認点を言い換えて含める。
   - 細部の指摘は、既存の細部の項目の言い換えで含める。新しい項目にするのは、複数のパズルで繰り返し起きたものだけにし、細部は10項目以内に保つ。
   - 個別の事例（どの文言で、どの画面で起きたか）は `references/history.md` にだけ書く。
4. **直したスキルで全体を見直す**: 指摘された箇所だけをその場で直さず、同じ原則に反している箇所をまとめて直す。その後「10. 見直し」と「11. レビューの回し方」に戻る。

## 10. 見直し

`references/checklist.md` を、原則・細部・実画面での確認の順にすべて確かめる。特に「実画面での確認」は、サブエージェントに任せた場合でも、スクリーンショットとコマを自分の目で見る。

- **静的検証**: `bun run --cwd frontend check`、`typecheck`、`test` を通す。
- **画面確認の手段**: `bun run --cwd frontend dev` で開発サーバーを起動し、Playwright（Chromium は導入済み）で幅375pxを操作してスクリーンショットとブラウザのエラーを取る。ChatGPT 環境では `docs/メモ/ChatGPT画面確認.md` の手順と `scripts/chatgpt_playwright.py` を使う。
- **人間に見せる場所**: ブランチを push すると Cloudflare Workers のブランチプレビューができるので、その URL を渡す。

## 11. レビューの回し方

- **レビュー役**: 毎回、経緯を知らない新しいサブエージェントにする。このスキル、`references/checklist.md`、見直す画面の開き方（URL や起動コマンド、対象ゲーム）だけを渡し、`references/history.md` や会話は読ませない。作り手だけが確かめられる項目（盤面の探索など）は「確かめていない」と書けば足りる。自分の見直しの代わりにはしない。
- **報告の形**: 指摘を「重大（どの原則に反するか）」と「細部」に分けさせ、重大な指摘には反する原則の番号を付けさせる。
- **終わりの条件**: 重大な指摘が0件になったら終える。細部はまとめて直し、細部だけのためにレビューをやり直さない。
- **上限**: レビューは、人間に見せるまでの1サイクルにつき3回まで。重大な指摘を直したら「10. 見直し」を行ってから次の回に進む。3回目でも重大な指摘が残るなら、直さずに人間に相談する。
- **割れた意見**: レビュー役どうし、またはレビュー役と人間の指示で意見が割れた点は直さず、両方の言い分を添えて人間に判断を仰ぐ。人間がすでに決めた文言は、レビュー役の好みで変えない。

## 参照する正本

- `APP.md`、`GAME.md`: 体験の判断軸
- `DESIGN.md`: 視覚・操作フィードバック・動き
- `.claude/rules/game-structure.md`: ゲーム層の構成と `tutorial/` の責務
- `docs/パズル/`: 難易度の意味（どのレベルでどの読みが要るか）
- `references/checklist.md`: 見直し用チェックリスト（原則・細部の2段と、実画面での確認手順）
- `references/history.md`: バイナリパズル・スライドパズルでの経緯、0h h1 の事例、調査の出典

## 制約

- 自動でコミット・PRを作らない（ユーザーの指示に従う）。
- チュートリアルの仕様を正本（`docs/プロダクト/`）へ反映するのは、試作で形が固まってから行う。
