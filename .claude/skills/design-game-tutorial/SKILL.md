# design-game-tutorial

パズルを知らない人が、本物の小さな盤面を1枚解きながらルールと操作を身につけ、そのパズルを遊びたくなるチュートリアルを作る Skill。

## 起動

`/design-game-tutorial <game>`

`$ARGUMENTS` を対象ゲームとする。無ければ会話から決める。新しく作るときは「3. 作り方」の1から、既存の見直しだけなら「3. 作り方」の7の本人確認から始め、続けて「4. 見直し」を1サイクル回す。人間の指摘への対応は「5. 指摘を受けたとき」から始める。

この Skill は2つの層でできている。

- **体験の層**: 「1. 原則」「2. 体験の形」「3. 作り方」の2〜6、「7. 細部」、`references/checklist.md`。プレイヤーが受け取る体験を決める。「7. 細部」を除き、すべて P1〜P6 から導く。
- **進め方の層**: 「3. 作り方」の1・7〜9、「4. 見直し」、「5. 指摘を受けたとき」、「6. コードの置き場所」、「8. 検証」。体験の層を作り、品質を守る手続き。原則番号は付けない。

## 1. 原則

原則は `APP.md` の判断の軸（面白い・楽しい・ワクワク）をチュートリアルに当てはめたもの。体験の判断はすべてこの6つに戻し、原則で決まらないときだけ `APP.md`・`GAME.md` に戻る。体験の層の他の記述と食い違えば原則を優先する。

- **P1. 始まった時点で、何をするパズルか・ゴール・始まりの盤面が分かり、最初に何をすればよいか迷わない。** 指示より先に目的を伝えないと、知らない人は何のために操作しているのか分からない。
- **P2. ルールは言い切ってからすぐその盤面で使わせ、操作を教える手を除き、各手順の手はその時点までに言い切ったルールで決まり、新しいルールを出す手順ではそのルールが決め手になる。** 読んだだけのルールも、ルールで決まらない手も、身につかない。
- **P3. 盤面と操作で伝わらないことだけを、人が横で教えるような短く自然な言葉で、呼び名と動詞を1つにそろえて話す。** 言葉はほとんど読まれず、増えるほど盤面から目をそらす。採点する先生の口調も、説明書の直訳も、中身のない言葉も、言葉の揺れも、盤面のものを人のように言う飾りも、改行や短い文で足りる切れ目に打つ読点も、プレイヤーを遠ざける。
- **P4. 画面の反応が、言葉で教えたことと食い違わない。** 食い違いは、ルールの説明そのものを疑わせる。押せそうに見えて何も起きない見た目や、正しく操作しても何も返らない盤面も、プレイヤーには食い違いとして届く。
- **P5. 本番を始めるのに要るもの（ルールと、ルールを当てはめるだけで決まる読み）をここで渡しきり、自分で手を決める手応えと完成のご褒美を味わわせて、本番へ正直につなぐ。** 操作の練習で終わらせず、本番の難しさを約束しすぎないことで、遊んでみたくなる気持ちと実際がずれずに本番へ進める。
- **P6. 誰でも同じ体験にたどり着け、動きを減らす設定・画面幅・開いた場所によって、伝わることが欠けたりプレイが乱れたりしない。** 環境で体験が変わると、伝えたはずのルールや楽しさが一部の人に届かない。

指摘の重さは原則で分ける。原則に反するものを**重大**（原則番号を添える）、原則に反しない仕上げの問題を**細部**（「7. 細部」）とする。

## 2. 体験の形

原則から決まる、どのパズルにも共通の骨組み。パズルごとに変えるのは中身だけにする。

1. **入口**（P1）: 名前とピクトグラム、何をするパズルかの一文、完成した盤面（ゴール）、崩れた始まりの盤面を、操作より先に見せる。自動で進めても、読む速さに合わせて自分で先へ進められるようにする。
2. **手を引く手順**（P1・P2）: 最初に操作を教え、次からはルールを1つ言い切っては、そのルールで決まるマスをすぐ操作させる。新しいルールを足さず、それまでのルールだけで決まるマスを置かせる手順も入れてよい。手順の間は操作させるところに印を付け、他の操作は受け付けず、言葉を足さずに印を付け直して応える。
3. **手を離す**（P2・P5）: 手順を終えたら、残りを手に入れたルールだけで自分で解かせる。迷って止まったときだけ、少し待つと手がかりを出す。
4. **完成**（P5）: 本番と同じ手触りの完成演出で盤面を見せ、本番も同じルールであることを伝えて本番へつなぐ。

盤面は最初から最後まで本物の1枚だけにする（P2・P5）。小盤面を並べたり、手順ごとに盤面を替えたりすると、1つのパズルを解いた体験にならない。

## 3. 作り方

新しいパズルに作るときの流れ。2〜6 は体験の層で、括弧はその段が守る原則。1・7〜9 は進め方の層。

1. **パズルを知る**: 該当パズルの仕様（`docs/プロダクト/仕様/`）、`docs/パズル/README.md` から難易度文書、ルール実装と遊び方を読み、レベル1〜2を実際に解く。知らない人が最初につまずく所と、そのパズルならではの面白さ（`GAME.md`）を書き出す。`references/history.md` を読み、過去の失敗を知っておく。
2. **基本とテクニックを分ける**（P5・P2）: ルールそのものと、ルールを盤面に当てはめるだけで決まる読みを基本とし、チュートリアルで全部使わせる。仮定を重ねる読みはテクニックとして外す。
3. **流れを組む**（P1・P2・P5）: 「2. 体験の形」に、手順の表（印のマス・一言・決め手）を当てはめる。操作を教える手を除き、各手順のマスは、その時点までに言い切ったルールで決まり、新しいルールを出す手順ではそのルールが決め手になるようにする。手を離した後に新しいルールを出さない。表の例は `references/history.md` の「バイナリパズルの手順」。
4. **盤面を探して確かめる**（P2）: 本物と同じルールの小さめの盤面を、自分で総当たりして探す。始まりから解が1つに決まること、各手順のマスがその時点で手に入れたルールだけで決まること、手を離した後の残りが手に入れたルールだけで解けることを確かめ、`tutorial/` のテストに残す。他人の「ある」「無い」という報告はうのみにせず、自分の検索結果で判断する。
5. **文言を書く**（P3・P1）: まず盤面・印・反応で伝わることを言葉から外し、残った言葉を短くする。声に出して読み、人が横で教える自然な日本語に直す。遊び方の説明や本番の画面と呼び名をそろえる。
6. **実装する**（P4・P6）: 「6. コードの置き場所」に沿って、本物の盤面部品と演出で作る。画面の反応は、その時点で教えたことと食い違わないようにする。
7. **自分で確かめる**: 「8. 検証」のコマンドを通し、375px 幅で入口から完成まで全手順を自分で操作し、動きを減らす設定でも通しで見てから、`references/checklist.md` を全項目確かめる。他人のスクリーンショットで代えない。
8. **見直しを回す**: 「4. 見直し」の手順で1サイクル回す。
9. **オーナーに見せる**: ブランチを push し、Cloudflare Workers のブランチプレビューで本物の画面を見てもらう。案を並べて選ばせず、自分で決めて作り切ったものを見せる。

## 4. 見直し

作った本人の確認（「3. 作り方」の7）の後に、経緯を知らない目で見直す。本人の確認の代わりにはしない。

- 1回ごとに、新しいサブエージェント（Opus）を見直し役にする。渡すのはこの Skill、`references/checklist.md`、対象ブランチと画面の確かめ方だけにし、前の回の指摘は渡さない。見直し役は `references/history.md` を読まない。
- 見直し役は全手順を自分で操作し、指摘を **重大（P番号）** と **細部** に分けて報告する。重大には、どの原則のどの点に反するかを1文で添える。
- 重大はすべて「5. 指摘を受けたとき」の2〜3と同じ考え方で直す。細部は直す価値があるものだけ直す。見直し役と意見が分かれた点は自分で判断する。
- 直したら、同じサイクルの次の回として新しい見直し役に見直させる。重大が0件になったらサイクルを終える。
- 1サイクルは3回まで。3回目でも重大が残ったら止め、残った指摘を添えてオーナーに見せる。
- サイクルを終えた後（重大0件か3回到達）は、オーナーの指摘なしに次のサイクルを始めない。

サイクルを終えたら、オーナーに見せる前に、言葉と遊ぶ側の目で1回ずつ見直す。

**言葉の見直し**

- 新しいサブエージェント（Opus）を、日本語に厳しい母語話者の編集者にする。画面に出る一言を、出る順・出る場面・改行位置と一緒にすべて渡し、遊び方の説明も参考に添える。声に出して気持ち悪い所、呼び名や動詞の揺れ、一度で意味が取れない所、削れる言葉や盤面・印で代えられる言葉を、強い順に挙げさせる。オーナーが決めた言い回しは渡す前に印を付け、直す対象から外す。

**遊ぶ側の見直し**

- 新しいサブエージェント（Opus）に、何も知らない初めてのプレイヤーとして遊ばせる。渡すのは画面の開き方だけにし、この Skill・チェックリスト・経緯・コードは読ませない。
- どこを押すか・どこで止まるか・間違えるかは任せる。「わざと間違える」「印以外を押す」など、試す操作を指示しない。指示した操作から出た感想は、自然に遊ぶ人の体験を表さない。
- 感想は自由に書かせ、観点を渡さない。届いた感想は自分で原則に照らして重大・細部に分け、重大は「5. 指摘を受けたとき」と同じ考え方で直す。言葉に引っかかったという感想は、1か所でも P3 の重大として扱う。

## 5. 指摘を受けたとき

画面だけを直すと、同じ種類の問題が別の場所に残り、つぎはぎになる。

1. 指摘の読みが2通り以上ありえるときは、直す前に解釈を一言でオーナーに確かめる。
2. 指摘が反している原則を特定する。
3. 同じ原則に反している所をチュートリアル全体から探し、まとめて直す。
4. どの原則にも当たらない指摘は、原則か「7. 細部」を直して扱えるようにする。事例そのものを決まりにしない。
5. 指摘と原因・直し方を、事例として `references/history.md` のそのパズルの節の表に1行足す（無ければ節を作る）。
6. 直した後、「3. 作り方」の7からやり直し、見直しを新しいサイクルとして回す。

## 6. コードの置き場所

- 共通の契約と進行は `frontend/src/games/tutorial.ts`、共通の画面は `frontend/src/components/TutorialOverlay.tsx` と `frontend/src/components/TutorialOverlay/`。
- ゲーム固有の盤面・手順・手の判定・違反の言い方は `frontend/src/games/<game>/tutorial/` に純粋な TypeScript で置き、`puzzle/` のルールと遷移で盤面を進める。依存してよいのは `problem/`・`puzzle/`・`session/` とゲーム共通契約だけで、生成内部・難易度分類・採点・`play/`・保存・React・UI を知らない。
- ゲーム固有の画面は `frontend/src/games/<game>/ui/<Game>Tutorial.tsx` に置き、`games/tutorial.ts` の進行関数で進める。
- 共通の契約を広げるのは、新しいパズルが本当に違う所だけにする。既存のパズルに合わせた形を、別のパズルへ無理に当てはめない。
- 演出は操作のイベントハンドラから始める。state の変化を `useEffect` で監視して演出を始めない（`.claude/rules/react-hooks.md`）。
- 依存方向と配置は `.claude/rules/game-structure.md` を正とする。

## 7. 細部

原則に直接は関わらない、どのパズルにも当てはまる仕上げの決まり。10項目以内に保つ。

- 余白・色・文字・動きの値は `DESIGN.md` と `frontend/styles/globals.css` の `@theme` から選び、画面の端に要素を詰めない。
- 一言が変わっても、一言の欄の高さや盤面の位置が動かない。

## 8. 検証

```sh
bun run --cwd frontend check
bun run --cwd frontend typecheck
bun run --cwd frontend test
```

画面は `bun run --cwd frontend dev` で開き、Playwright で 375px 幅のスクリーンショットを撮って確かめる。ChatGPT 実行環境では `docs/メモ/ChatGPT画面確認.md` の手順と `scripts/chatgpt_playwright.py` を使う。

## 参照する正本

- 判断の軸: `APP.md`、`GAME.md`、UI は `DESIGN.md`
- パズルの振る舞い: `docs/プロダクト/仕様/` の該当パズル、難易度は `docs/パズル/README.md` から
- コードの配置と依存: `.claude/rules/game-structure.md`、`.claude/rules/react-hooks.md`
- 確かめる項目: `references/checklist.md`（本人の確認と見直し役の確認で使う）
- 失敗の事例と出典: `references/history.md`（作る本人だけが読む）

## 制約

- 試作もアーティファクトでは作らず、実アプリの部品で作ってブランチのプレビューで見せる。
- 原則や「7. 細部」を変えたときは、オーナーに見せるときに何をなぜ変えたかを示す。
