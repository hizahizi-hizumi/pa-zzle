# design-game-tutorial

パズルを知らない人が、本物の小さな盤面を1枚解きながらルールと操作を身につけ、そのパズルを遊びたくなるチュートリアルを作る Skill。

## 起動

`/design-game-tutorial <game>`

`$ARGUMENTS` を対象ゲームとする。新しく作るときは「3. 作り方」から、既存のチュートリアルを見直すときは「4. レビュー」から始める。

## この Skill の重み

書いてあることの重さは3段に分かれる。

1. **大原則**（「1. 大原則」）: 必ず守る。1つでも破っていれば完成ではない。
2. **基本の形**（「2. 基本の形」）: 迷ったらこの形にする。パズルに合わなければ、大原則を守る範囲で変えてよい。
3. **書いていないこと**: 見た目、言い回し、演出、手順の数などは、作る側が大原則に照らして決める。案を並べてオーナーに選ばせない。

個別のチュートリアルで受けた指摘は、そのチュートリアルを直して終える。この Skill に決まりとして足さない。

## 1. 大原則

- **P1. 本物の盤面を1枚、自分の手で解いて完成させ、本番へ正直につなぐ。** 説明を読ませるのでも、操作の練習をさせるのでもない。盤面は最初から最後まで、本番と同じルールの1枚にする。チュートリアルだけの手助けや、本番の難しさを約束しすぎる言葉で本番を語らない。
- **P2. 何をするパズルかとゴールを、操作より先に見せる。** 目的を知らないまま操作させない。
- **P3. ルールは1つずつ伝え、伝えたらすぐ盤面で使わせる。** 盤面の手を決めるルール（仕様と遊び方の説明にあるもの）は、自分で解かせる前にすべて伝える。まだ伝えていないルールが要る手を求めない。
- **P4. 言葉は、盤面と操作で伝わらないことだけにする。** 短く、人が横で教えるように話す。
- **P5. 画面の反応は教えたことと食い違わず、手が正しいかが盤面で分かる。** 教えていないルールで止めない。正しい手には盤面が応える。
- **P6. 誰がどの環境で開いても、同じことが伝わる。** 375px 幅でも、動きを減らす設定でも、欠けたり崩れたりしない。

## 2. 基本の形

1. **入口**: 名前、何をするパズルかの一文、ゴールの盤面、始まりの盤面を見せる。読む速さに合わせて自分で先へ進められるようにする。
2. **手を引く**: 最初に操作を教え、次からはルールを1つ伝えては、そのルールで決まるマスを打たせる。打つマスに印を付け、その間は印の操作だけを受け付ける。
3. **手を離す**: 残りを自分で解かせる。要るのは、伝えたルールを盤面に当てはめるだけで決まる読みまでにする。仮定を重ねる読みは求めない。止まったときだけ手がかりを出す。
4. **完成**: 本番と同じ完成演出を見せ、本番も同じルールで遊べると伝える。

手順で教えるのは、盤面の手を決めるルールと、最初の手に要る操作まで。操作の細かい決まり（取り消し方、長押しなど）は、遊び方の説明と本番に任せてよい。

## 3. 作り方

1. **パズルを知る**: 該当パズルの仕様（`docs/プロダクト/仕様/`）、遊び方の説明、ルールの実装を読み、レベル1〜2を解く。遊び方の説明と仕様にあるルールを書き出す。`references/history.md` に一度目を通す。
2. **手順の表を作る**: 手順ごとに「印のマス・一言・そのマスを決めるルール」を並べる。表の形は `references/history.md` の「バイナリパズルの手順」を参考にする。一言は古い版のものなので、そのまま使わない。
3. **盤面を探す**: 小さめの盤面を自分で総当たりして探し、次を `frontend/src/games/<game>/tutorial/` のテストに残す。他人の「ある」「無い」という報告は使わず、自分の探索結果で決める。
   - マスを埋めるパズルでは、始まりから解が1つに決まる。手を重ねて状態を進めるパズル（スライドパズル、ウォーターソートなど）では、手を離した後どう進めても詰まない。
   - 手を引く間の各手が、それまでに伝えたルールで決まる。
   - 手を離した後の残りが、伝えたルールだけで解ける。
4. **実装する**: 本番の盤面部品と演出を使う。置き場所は「6. コードの置き場所」に従う。
5. **自分で通す**: 「7. 検証」を通し、375px 幅で入口から完成まで自分で操作する。動きを減らす設定でも通す。
6. **レビューを回す**: 「4. レビュー」に従う。
7. **オーナーに見せる**: ブランチを push し、Cloudflare Workers のブランチプレビューを渡す。自分で決めたことと、レビューで直さなかった指摘を短く添える。

## 4. レビュー

作った本人が通した後に、実装する側と遊ぶ側の2つの視点で見直す。どちらも毎回新しいサブエージェント（Opus）に任せ、2つは並行して走らせてよい。

「画面の開き方」は、ブランチプレビューか `bun run --cwd frontend dev` でチュートリアルを開く URL と、375px 幅で開くことを指す。

### 実装する側

- **渡すもの**: この Skill、対象ブランチ、画面の開き方。`references/history.md` と前回の指摘は渡さない。
- **頼むこと**: 入口から完成まで自分で操作し、次を確かめる。
  - 大原則に反していないか。
  - ルールの扱いが本番の実装と一致しているか。
  - 「3. 作り方」の3の条件がテストで確かめられているか。
  - コードが「6. コードの置き場所」に沿っているか。
- **報告させるもの**: 大原則の違反（原則番号と、どこがどう反するかを1文）と、不具合だけ。好みの指摘は求めない。

### 遊ぶ側

- **渡すもの**: 画面の開き方だけ。Skill、コード、経緯は読ませない。
- **頼むこと**: 初めてのプレイヤーとして入口から完成まで遊び、感想を自由に書く。試す操作も、感想の観点も指示しない。
- **報告させるもの**: 自由な感想。どの場面（入口・手を引く間・手を離した後・完成）で感じたかが分かるように書かせる。
- **感想の読み方**: 作った本人が大原則に照らして読む。迷った、止まった、言葉に引っかかったという感想は、どれかの大原則に反していないか原因を探す。

### 指摘の扱い

- 大原則の違反と不具合は直す。同じ原因の所がほかにないか探し、まとめて直す。
- それ以外は、直す価値があるものだけ直す。直すかどうかは作った本人が決める。
- 大きく直したら、もう一度2つの視点で見直す。見直しは最初を含めて2回までにする。最後の回で出た大原則の違反と不具合は直し、作った本人が確かめて終える。直さないと決めた指摘は、オーナーに見せるときに判断を求めずに添える。

## 5. オーナーの指摘を受けたとき

1. 読み方が2通り以上ありえるときは、直す前に解釈を一言で確かめる。
2. どの大原則に反しているかを特定し、同じ原因の所をまとめて直す。
3. どの大原則にも当たらない指摘は、そのチュートリアルを直して終える。
4. 指摘と直し方を、`references/history.md` のそのパズルの節に1行残す。

大原則で説明できない指摘が、パズルをまたいで繰り返し出るときだけ、大原則の見直しをオーナーに相談する。

## 6. コードの置き場所

- 共通の進行は `frontend/src/games/tutorial.ts`、共通の画面は `frontend/src/components/TutorialOverlay.tsx` に置く（バイナリパズルのチュートリアル #493 で入る）。
- ゲーム固有の部分の配置と依存方向は `.claude/rules/game-structure.md` の `tutorial/` と `ui/` を正とする。React の書き方は `.claude/rules/react-hooks.md` を正とする。

## 7. 検証

```sh
bun run --cwd frontend check
bun run --cwd frontend typecheck
bun run --cwd frontend test
```

最後に `./scripts/verify.sh` を通す。画面は `bun run --cwd frontend dev` で開き、Playwright で 375px 幅のスクリーンショットを撮って確かめる。ChatGPT 実行環境では `docs/メモ/ChatGPT画面確認.md` の手順と `scripts/chatgpt_playwright.py` を使う。

## 参照する正本

- 判断の軸: `APP.md`、`GAME.md`。UI は `DESIGN.md` と `frontend/styles/globals.css` の `@theme`
- パズルの振る舞い: `docs/プロダクト/仕様/` の該当パズル。難易度は `docs/パズル/README.md` から
- コードの配置と依存: `.claude/rules/game-structure.md`、`.claude/rules/react-hooks.md`
- これまでの指摘と参考事例: `references/history.md`。作る本人が読む記録で、決まりではない
