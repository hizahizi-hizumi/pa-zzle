# design-game-tutorial

パズルを知らない人が、本物の小さな盤面を1枚解きながらルールと操作を身につけ、そのパズルを遊びたくなるチュートリアルを作る Skill。

## 起動

`/design-game-tutorial <game>`

`$ARGUMENTS` を対象ゲームとする。無ければ会話から決める。新しく作るときは「3. 作り方」の1から、既存の見直しだけなら「4. 見直し」から、人間の指摘への対応は「5. 指摘を受けたとき」から始める。

## 1. 原則

原則は `APP.md` の判断の軸（面白い・楽しい・ワクワク）をチュートリアルに当てはめたもの。判断はすべてこの6つに戻し、原則で決まらないときだけ `APP.md`・`GAME.md` に戻る。以降の章はすべて、どれかの原則を満たすためのやり方であり、食い違えば原則を優先する。原則を変えられるのはオーナーだけ。

- **P1. 始まった時点で、何をするパズルか・ゴール・始まりの盤面が分かる。** 指示より先に目的を伝えないと、知らない人は何のために操作しているのか分からない。
- **P2. ルールは言い切ってから、すぐその盤面で使わせる。** 読んだだけのルールは身につかない。操作を教える手を除き、使う手はそのルールで決まる手にする。
- **P3. 人が横で教えるような、自然で1つにそろった言葉で話す。** 採点する先生の口調も、説明書の直訳も、言葉の揺れも、プレイヤーを遠ざける。
- **P4. 画面の反応が、言葉で教えたことと食い違わない。** 食い違いは、ルールの説明そのものを疑わせる。
- **P5. 遊んでみたくなる形で、本番へ正直につなぐ。** 完成をご褒美として見せ、本番の難しさを約束しすぎないことで、期待と実際がずれずに本番へ進める。
- **P6. 誰でも同じ体験にたどり着け、プレイを邪魔しない。** 設定や開いた場所によって、伝わることが欠けたり、プレイが乱れたりしてはいけない。

指摘の重さは原則で分ける。原則に反するものを**重大**（原則番号を添える）、原則に反しない仕上げの問題を**細部**とする。

## 2. 体験の形

原則から決まる、どのパズルにも共通の骨組み。パズルごとに変えるのは中身だけにする。

1. **入口**（P1・P5）: 名前とピクトグラム、何をするパズルかの一文、完成した盤面（ゴール）、崩れた始まりの盤面を、操作より先に見せる。
2. **手を引く手順**（P1・P2）: 最初に操作を教え、次からはルールを1つ言い切っては、そのルールで決まるマスをすぐ操作させる。手順の間は操作させるところに印を付け、他は受け付けない。
3. **手を離す**（P2・P5）: 手順を終えたら、残りを手に入れたルールだけで自分で解かせる。迷って止まったときだけ、少し待つと手がかりを出す。
4. **完成**（P5）: 本番と同じ手触りの完成演出で盤面を見せ、本番が同じルールであることと、どこから始めればよいかを正直に伝えて本番へつなぐ。

盤面は最初から最後まで本物の1枚だけにする。小盤面を並べたり、手順ごとに盤面を替えたりしない（1つのパズルを解いた体験にならない）。

## 3. 作り方

新しいパズルに作るときの流れ。各段の括弧はその段が守る原則。

1. **パズルを知る**（全原則の前提）: そのパズルの仕様（`docs/プロダクト/仕様/`）、`docs/パズル/` の難易度文書、ルール実装と遊び方を読み、レベル1〜2を実際に解く。知らない人が最初につまずく所と、そのパズルならではの面白さ（`GAME.md`）を書き出す。
2. **基本とテクニックを分ける**（P2・P5）: ルールそのものと、ルールを盤面に当てはめるだけで決まる読みを基本とし、チュートリアルで全部使わせる。仮定を重ねる読みはテクニックとして外す。レベル1〜2で要る読みを目安にし、線が引けなければオーナーに確かめる。
3. **流れを組む**（P1・P2・P5）: 「2. 体験の形」に、手順の表（印のマス・一言・決め手）を当てはめる。各手順の決め手は、その手順で言い切ったルールにする。ルールの数だけ手順を置き、手を離した後に新しいルールを出さない。
4. **盤面を探して確かめる**（P2）: 本物と同じルールの小さめの盤面を、自分で総当たりして探す。始まりの盤面から解が1つに決まること、各手順のマスがその時点で手に入れたルールだけで1つに決まること、手を離した後の残りが手に入れたルールだけで解けることを確かめる。他人の「無い」「ある」という報告はうのみにせず、自分の検索結果で判断する。確かめた条件は `tutorial/` のテストに残す。
5. **文言を書く**（P3・P1）: 声に出して読み、人が横で教える自然な日本語にする。ですます調で言い切り、評価やクイズの口調、体言止めだけの無機質な文、中身のないつなぎの文を使わない。同じものには同じ呼び名と動詞を使い、遊び方の説明や本番の画面と呼び名をそろえる。
6. **実装する**（P4・P6）: 「6. コードの置き場所」に沿って、本物の盤面部品と演出で作る。画面の反応は、その時点で教えたルールとだけ一致させる（まだ教えていない違反は見せない、途中の一瞬の状態に反応しない、受け付けない操作で前の一言を残さない）。動きを減らす設定でも、伝わる中身は欠けずに同じ所へたどり着けるようにする。
7. **自分で確かめる**（全原則）: 検証コマンドを通し、375px 幅の画面で入口から完成まで全手順を自分で操作し、各画面を見てから `references/checklist.md` を全項目確かめる。動きを減らす設定でも通しで見る。他人のスクリーンショットで代えない。
8. **見直しを回す**（全原則）: 「4. 見直し」の手順で回す。
9. **オーナーに見せる**（全原則）: ブランチを push し、Cloudflare Workers のブランチプレビューで本物の画面を見てもらう。自分で決められる選択肢は自分で決めて作り、案を並べて選ばせない。オーナーに聞くのは、原則の解釈、線引き、見直しで決着しなかった点、オーナーが決める文言だけにする。

## 4. 見直し

作った本人の確認（3-7）の後に、経緯を知らない目で見直す。本人の確認の代わりにはしない。

- 毎回、経緯を知らない新しいサブエージェント（Opus）を見直し役にする。渡すのはこの Skill、`references/checklist.md`、対象ブランチと画面の確かめ方だけにし、これまでの経緯や前回の指摘は渡さない。
- 見直し役は、自分で全手順を操作し、指摘を **重大（P番号）** と **細部** に分けて報告する。重大には、どの原則のどの点に反するかを1文で添える。
- 重大はすべて「5. 指摘を受けたとき」と同じ考え方で直す。細部は直す価値があるものだけ直す。
- 重大が0件になったら止める。1サイクルは3回まで。3回で0件にならない重大、見直し役と意見が分かれた点、オーナーが決める文言は、直さずにまとめてオーナーに渡す。

## 5. 指摘を受けたとき

画面だけを直すと、同じ種類の問題が別の場所に残り、つぎはぎになる。

1. 指摘の読みが2通り以上ありえるときは、直す前に解釈を一言でオーナーに確かめる。
2. 指摘が反している原則を特定する。
3. 同じ原則に反している所をチュートリアル全体から探し、まとめて直す。
4. どの原則にも当たらない指摘は、原則の追加・変更案としてオーナーに出す。自分で原則や Skill の決まりを足さない。
5. 指摘と原因・直し方は事例として `references/history.md` の表に1行足す。事例を Skill 本文やチェックリストの項目にしない。
6. 直した後、3-7 からやり直し、見直しを新しいサイクルとして回す。

## 6. コードの置き場所

- 共通の契約と進行は `frontend/src/games/tutorial.ts`、共通の画面は `frontend/src/components/TutorialOverlay.tsx` と `frontend/src/components/TutorialOverlay/`。
- ゲーム固有の盤面・手順・手の判定・違反の言い方は `frontend/src/games/<game>/tutorial/` に純粋な TypeScript で置き、`puzzle/` のルールと遷移を使って盤面を進める。依存してよいのは `problem/`・`puzzle/`・`session/` とゲーム共通契約だけで、生成内部・難易度分類・採点・`play/`・保存・React・UI を知らない。
- ゲーム固有の画面は `frontend/src/games/<game>/ui/<Game>Tutorial.tsx`（部品が増えたら同名ディレクトリ）に置き、`games/tutorial.ts` の進行関数で進める。
- 共通の契約を広げるのは、新しいパズルが本当に違う所だけにする。既存のパズルに合わせた形を、別のパズルへ無理に当てはめない。
- 演出は操作のイベントハンドラから始める。state の変化を `useEffect` で監視して演出を始めない（`.claude/rules/react-hooks.md`）。
- 依存方向と配置は `.claude/rules/game-structure.md` を正とする。

## 7. 細部

原則に直接は関わらない、一般的な仕上げの決まり。ここに項目を足すのは、どのパズルにも当てはまる仕上げの決まりに限り、10項目以内に保つ。

- 余白・色・文字・動きの値は `DESIGN.md` と `frontend/styles/globals.css` の `@theme` から選ぶ。
- 画面の上下左右の端に要素が詰まらない。
- 一言が変わっても、一言の欄の高さや盤面の位置が動かない。
- 完成した盤面は、押せない盤面に見える沈んだ見た目のままにしない。
- 盤面の確かめ（解の一意性・各手順の決め手）はテストに残し、表示はコンポーネントのテストで確かめる。

## 8. 検証

```sh
bun run --cwd frontend check
bun run --cwd frontend typecheck
bun run --cwd frontend test
```

画面は `bun run --cwd frontend dev` で開き、Playwright で 375px 幅のスクリーンショットを撮って確かめる。ChatGPT 実行環境では `docs/メモ/ChatGPT画面確認.md` の手順と `scripts/chatgpt_playwright.py` を使う。

## 参照する正本

- 判断の軸: `APP.md`、`GAME.md`、UI は `DESIGN.md`
- パズルの振る舞い: `docs/プロダクト/仕様/` の該当パズル、難易度は `docs/パズル/README.md` から
- コードの配置と依存: `.claude/rules/game-structure.md`、`.claude/rules/react-hooks.md`
- 確かめる項目: `references/checklist.md`（自分の確認と見直し役の確認で使う）
- 失敗の事例と出典: `references/history.md`（指摘を受けたとき、作り始める前に一度読む）

## 制約

- 試作もアーティファクトでは作らず、実アプリの部品で作ってブランチのプレビューで見せる。
- 原則の文言と意味はオーナーの承認なしに変えない。
