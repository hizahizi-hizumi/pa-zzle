# コミット粒度・メッセージ・履歴品質ルール

## コア原則

- 1コミット = 1つの論理的変更。1文で説明できる単位にする。
- 無関係な変更を混ぜない。
- 機械的変更（整形・リネーム・移動）と意味変更を分ける。
- 純粋なリファクタと挙動変更を原則分ける。
- 依存更新・CI・開発環境変更と機能変更を原則分ける。
- 可能な範囲で各コミットを、変更範囲に対応する `AGENTS.md` の検証コマンドが通る状態にする。
- テストや契約を分離すると中間コミットが壊れる場合は、対応する実装と同じコミットに含める。
- main に `WIP` / `とりあえず` / `あとで直す` のような中間履歴を残さない。

## まとまりの判断

ディレクトリ境界ではなく、変更理由と成立単位で判断する。

同一コミットに置く候補:

- 1つの機能変更と、その変更を成立させる最小の回帰テスト
- schema / API / 型などの契約変更と、その新契約へ必須で追従する利用側
- 設定変更と、その設定を前提にしないと成立しない実装変更

分ける候補:

- 大規模なファイル移動と、その後の内容変更
- 純粋な用語置換と、意味論の変更
- 開発ツール導入と、利用者向け機能変更
- 独立してrevertしたい変更

## メッセージ規約

既存のリポジトリ規約があれば最優先する。特に無ければ、英語ラベル + 任意scope + 日本語の短い件名を使う。

形式:

```text
<label>(<scope>): <日本語の短い件名>
```

scope が不要なら省略可能。

### ラベル

| label | 用途 |
|---|---|
| `feat` | 利用者・開発者に新しい価値を追加 |
| `fix` | 不具合・回帰修正 |
| `refactor` | 挙動不変の内部改善 |
| `perf` | 性能・コスト改善 |
| `test` | テスト・検証基盤 |
| `docs` | ドキュメントのみ |
| `style` | 意味を変えない整形 |
| `chore` | CI・依存・運用・周辺設定 |
| `dev` | 開発体験向上 |
| `revert` | 既存変更の取り消し |

### scope 例

- `frontend`
- `backend`
- `api`
- `docs`
- `ci`
- `skills`

### 例

```text
feat(frontend): パズル選択画面を追加
fix(backend): 無効な難易度を拒否
test(frontend): クリア判定の回帰テストを追加
docs: PoCの検証観点を明確化
chore(skills): Git運用Skillを整理
```

## 履歴品質

- レビュー時に「何を」「なぜ」変えたか追えること。
- 1コミットを単独revertしても意図が理解できること。
- 移動だけのコミットでは可能な限り内容を編集しない。
- 大規模整形を機能変更に混ぜない。
- 公開済みブランチの履歴を force push 前提で書き換えない。

## 禁止事項

- 巨大な全部入りコミット。
- コミットを綺麗に見せるためだけの意味変更の混入。
- `main` / `master` / `staging` への直接コミット。
