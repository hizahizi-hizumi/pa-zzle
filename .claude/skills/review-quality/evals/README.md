# review-quality の評価

- `cases.json` の `prompt`・`ref`・`scope` だけを固定入力として、スキルなしとありを独立コンテキスト・同条件で各実行する。`ground-truth.md` と修正PR本文は結果が凍結するまでレビュアーに見せない。
- `kind: synthetic` のケースでは `contract` と `content` を指定ファイルにあるものとして扱い、ファイルは実際にはリポジトリに書き込まない。実履歴ケースでは、指定コミットのコード・文書だけを使う。
- `WATER-*` と `VIEWPORT-*` の不具合は実機・表示環境に左右される。静的な説明と実際に再現した事実を区別する。`TRACE-*` は特定入力で実行できる。
- 修正後に新規の問題が見つかれば独立に確認し、「正解にない」という理由だけで偽陽性としない。
- 入力に「白線」「縦スクロール」「巻き戻し」など修正対象を答えとして書かない。評価の目的は問題を教えられた後の確認ではなく、自律的な発見である。
- 判定は `.claude/skills/review/evals/README.md` の共通方法で行う。

## 確定評価と探索的評価

- `cases.json` の `scoring: primary` は入力と契約から独立に成否を確定できるケース、`scoring: exploratory` は環境依存または期待動作の根拠に未確認事項があるケースを表す。
- `exploratory` を既知欠陥の Recall の分母へ入れない。独立した証拠が得られたら正解候補を更新してから次の評価で primary に移す。
- 疑義として捉えた正しい問題の候補を即座に見逃しと数えず、「候補として発見したか」と「正しく確定したか」を別に記録する。

## 実行で確かめられる対照ケース

- 境界値（CLAMP）、引数の非破壊性（IMMUTABLE）、古い応答の無視（STALE）の修正前／修正後の3対を追加した。`scoring: primary` はこの6件のみ。実際の製品の欠陥ではなく、評価用の人工契約である。
- 評価者は `oracle-cases.json` をレビュー担当に渡さず、`node .claude/skills/review/evals/run-quality-oracles.mjs` で3件の欠陥側だけが再現し、正常側は全検査が成功することを確認する。
- 正解集合を固定する前に、記載の契約に反していても実際に動作が異ならないケースや、契約が不明確なケースを採用しない。
- 契約違反の発見だけでなく、正常実装の誤検出も各対で測る。一般的なコード品質を、この3種類だけで代表できるとは主張しない。
