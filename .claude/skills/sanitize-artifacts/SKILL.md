---
name: sanitize-artifacts
description: >
  既存の成果物から、プロンプト・会話・レビュー対応など制作過程の残骸を取り除き、
  成果物の目的・読者・責務に沿って、制作履歴を知らない読者にも単独で成り立つ形に書き直す。
  「成果物をサニタイズして」「会話の痕跡を消して」「プロンプト由来の記述を除去して」「レビュー対応の痕跡を消して」
  「sanitize this artifact」「remove prompt residue」「remove conversation residue」
  「make this stand alone without its production history」と明示的に頼まれたときに使う。
  一般的な推敲・校正・品質レビューだけを頼まれたときは使わない。
---

# sanitize-artifacts

1. 対象がこのリポジトリの文書なら、`.claude/rules/documents.md` と、対象のディレクトリと上位ディレクトリの `README.md` を読み、書き直しはそれに従う
2. 対象の成果物を読み、目的・読者・責務と、その成果物が正として保持するものを決める。成果物の種類は次を目安にし、最後はそのファイルの実際の責務で決める
   - 今の仕様・README・利用者向けの文書: 今成り立っている内容を書き、過去の編集の経緯や指示の理由は残さない
   - ADR などの意思決定の記録: 選択肢・判断理由・トレードオフを残し、会話上の都合や編集指示は残さない
   - PoC・実験の記録: 仮説・条件・手順・結果・失敗と、成果物の責務であれば検証が要る理由を残す
   - レビュー: 指摘の内容と根拠を残し、レビューを頼まれた経緯や会話上の都合は残さない
   - 調査・分析: 根拠・比較・未確定事項を残し、制作の指示を調査結果に混ぜない
3. 制作過程に由来する記述を探す。表面的な語の検索ではなく、文脈で判断する。次のものを探す
   - ユーザーのプロンプトや編集指示そのもの
   - 会話の経緯や応酬
   - 「指摘されたため追加した」のようなレビュー対応の履歴
   - 制作の途中でだけ要った制約や仮定
   - 採用しなかった案への不要な言及
   - ツールを選んだ制作上の事情
   - プロンプト設計上の指示
   - 中間の構造、仮の見出し、作業用の注記
   - 意図を説明するためだけに出された例
   - 前の版との差分を説明するだけの記述
   - 読者ではなく制作者に向いたメタコメント
4. 見つけた記述を、制作過程に由来するかではなく成果物の役割として要るかで、次の3つに分ける
   - 成果物の責務として要る情報: 残し、読者向けの自然な表現に書き直す
   - 制作には要ったが成果物に直接書かなくてよい情報: 構成・前提・命名・手順・設計に反映し、制作の事情は残さない
   - 制作過程で生じただけの残骸: 消す
5. 会話中の例は、要件として決まっていなければ成果物に固定しない。例からは求められる抽象度・想定読者・文体と説明の粒度・設計上の制約・避けるべき不自然さだけを読み取る
6. 制作上の制約は、注釈や言い訳ではなく完成形に反映する。制約そのものが読者に要る仕様・前提・注意事項であれば、制作の事情ではなく読者向けの情報として書く

   ```
   OK:
   専門用語を使わず、そのまま平易に説明する。
   NG:
   指示により、この節では専門用語を使いません。
   ```

7. 説明を足して制作の経緯を正当化せず、自然な完成形に書き直す
   - 継ぎ足しで崩れた構成・用語・前提・語調・粒度を揃える
   - 成果物本来の目的・技術的な正確さ・読者に要る仕様と制約・判断に要る根拠・検証できること・要る注意事項は損なわない
8. 書き直した成果物を次の観点で見直し、満たさない箇所を直す
   - 成果物だけを読んで、会話を知らない読者が理解できる
   - 「なぜこの書き方になったか」を制作側の視点で説明していない
   - 指示・会話・レビュー対応の履歴が要らないのに残っていない
   - 例を要件に取り違えていない
   - 複数回の修正を継ぎ足した痕跡が無い
   - 見出しと注記が対象の読者に向いている
   - 成果物の責務として要る判断理由・仕様・制約・履歴・検証の情報を消していない
9. 結果を返す。ユーザーや呼び出し元が出力の形式を指定していればそれに従う。指定が無ければ、対象がファイルなら書き換えたパスを伝え、会話に貼られた文章なら直した全文を返す。何を取り除いたかの説明や作業報告は成果物に書かず、求められたときだけ成果物とは別に示す
