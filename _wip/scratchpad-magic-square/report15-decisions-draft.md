## 2. 決めたことと理由（覆すと作り直しが大きい順）

1. **部品とその組み合わせの読みを、解析が1つずつ返し、分類が違うレベルの出た所で止める**（`MagicSquareDifficultyAnalysis.listAlternativeReadings`、`findMagicSquareDisagreeingReading`）。
   - 理由: 範囲内の問題では 5,507 通りを全部読む（1問 0.5〜5 秒）が、範囲外の多くは数通りで分かれる。特徴の解析（`problem/difficulty-analysis.ts`）と分類の方針（`difficulty.ts`）を分けたまま、調査コードの `classify_givens` と同じく早く止められる。
   - 比べた案: 解析で全部を読んで結果を渡す（範囲外の候補でも数秒かかり、生成が数倍遅くなる）。
   - 覆したら: `difficulty-analysis.ts`・`difficulty.ts` の境と、生成スクリプトの時間。
2. **磨き（`polishMagicSquareGivens`）は生成の内部（`problem/generation/candidate.ts`）に置き、点に梯子のレベル（`difficulty.ts` の `classifyMagicSquareReading`）を使う。**
   - 理由: 磨く点は 7 つの読み方で基準とレベルが違うごとに引く（調査の `_polish_value`）ので、梯子が要る。生成の内部から `difficulty.ts` への依存は依存規則で許されていて、循環しない（`difficulty.ts` は解析の型だけを読む）。生成器を単体テストできる。
   - 比べた案: 磨きを生成スクリプトに置く（製品のコードで生成器をテストできない）。
   - 覆したら: 置き場所だけ。
3. **問題集の1問は、与える数の文字列と、基準の読みの作業の量3つ（組を突き合わせた所の数・段3の所の数・巡の合計）の組にする**（`MagicSquareProblemPoolEntry`）。問題集から復元した問題は `readingWorkload` として返す。記録の `workload`（空きマスの数）はまだ変えない。
   - 理由: 資料 §11 の「下流に渡す量」を問題ごとに出せるようにする（次の score の項目で使う）。プレイ時に読むモデルを動かさない。記録の形を変えるのは採点の規則を決める score の項目。
   - 比べた案: 文字列だけにして、score の項目で読み直す（2,500問の読み直しは数秒なので作れるが、問題集の形が2回変わる）。
   - 覆したら: 問題集の JSON と `problem-pool.ts`（`--verify` が作業の量の一致も確かめる）。
4. **候補の乱数は、生成条件と番号から作る名前（例 `ms5-T3-polish5-17`）を `createProblemSeededRandom` に渡して作る。** 4×4 の答えは全部の魔方陣（7,040）から一様に、5×5・6×6 は乱択の探索。空ける順は `shuffleProblemValues`、戻すマスは空けたマスを並べ替えた先頭 k マス、磨きは `random()` と `pickProblemValue`。
   - 理由: 候補が生成条件と番号だけで決まり、止めても同じ順で再開できる（守ること 6）。調査コードの Python の乱数とは一致しないので、磨きの採否と素朴な解き方は値で突き合わせず、当たる割合と分布で比べる（資料 §2.6 のとおり）。
   - 覆したら: 問題集を作り直す。
5. **生成条件の名前は `<盤面>-T<段>-add<k>`（戻す）と `<盤面>-T<段>-polish<4|5>`（磨く）。** 調査の k = 12（L5 向け）・13（L4 向け）を、向けるレベルで書いた。
   - 覆したら: 名前と候補の乱数（問題集の作り直し）。
