# ゲーム品質

pa-zzle で提供する一つのゲームが、既存・新規を問わず満たすべき品質の判断軸を定義する。

この文書でいう `game` は、パズルのルールだけでなく、問題供給、難易度、操作、視覚表現、プレイ評価、結果、記録まで含む遊べる体験を指す。個々の `problem` の品質は、このゲーム品質の中核に含む。

現在の `docs/プロダクト/`、`APP.md`、`GAME.md`、`DESIGN.md` は重要な入力だが、現在も正本化途中である。品質判断では、それらだけでなく、過去の Issue、PR、Git 履歴、PoC、実プレイレビューで現在も有効と判断できる知見を合わせて使う。

この文書は未確定のプロダクト契約を勝手に確定するためのものではない。品質レビューから新しい現在契約が確定した場合は、最終的に適切なプロダクト正本へ還元する。

## 最上位品質: 面白い・楽しい・ワクワクする

RQ-001 が定める「面白く、楽しく、ワクワクしながら遊べること」を、ゲーム品質の最上位に置く。

問題が正しい、操作できる、結果を表示できる、記録できる、といった各品質はそれ自体が最終目的ではない。問題品質、難易度、操作、表現、結果、記録を含むすべての品質軸は、利用者が体験全体を通して面白さ・楽しさ・ワクワクを感じるためにある。

- **面白い**: そのパズル固有の判断、推論、発見、選択に取り組む価値があり、単純作業や退屈さへ落ちていない。
- **楽しい**: 考える、触る、変化を見る、解く、結果を受け取る一連の行為に余計な摩擦がなく、操作・反応・進行そのものを心地よく感じられる。
- **ワクワクする**: ゲームを見つける、遊び方を選ぶ、次の局面を考える、新しい問題へ進む、結果を受け取るといった先の体験への期待や好奇心が生まれる。

これらを、派手な演出、アニメーション、報酬量など特定の手段と同一視しない。ピクトグラム、動き、難易度選択、称賛等は、この最上位品質を強めるための手段であり、追加しただけで品質が上がったとは判断しない。

## 品質とは何か

ゲーム品質とは、機能が存在することやテストが通ることではない。

**利用者が、そのパズル固有の面白さを自分で考えて味わい、遊ぶ行為そのものを楽しみ、次の判断・問題・結果へ期待を持ちながら、達成と結果を納得して受け取れる状態を継続的に提供できること**を品質とする。

正しさ、操作性、再現性、性能等はそのための必要条件である。すべてが技術的に成立していても、退屈、作業的、触っていて気持ちよくない、次を遊びたいと思える期待が生まれないなら、pa-zzle のゲーム品質は成立していない。

品質は一問・一画面だけで判断しない。供給される問題のばらつき、難易度、端末、ゲーム選択から結果・記録までの導線を含めて、面白さ・楽しさ・ワクワクを安定して提供できるかを見る。

## 1. 問題品質

利用者へ出す問題そのものに、解く対象としての品質があり、そのパズル固有の面白さの核を持つこと。

### 正しさ

- ルール上成立している。
- 解の存在、一意性、推測不要性など、そのパズルで必要な条件を満たしている。
- クリア条件と実際の判定が一致している。

### 解く価値

- 解けるだけの自明問題や、単純作業だけの問題を通常供給しない。
- 理不尽な当てずっぽうや、実装上の偶然に依存しない。
- そのパズル固有の判断・推論・発見を必要とする。

「面白い問題」を機械指標だけで確定しない。自明性や重複など機械で落とせる品質不足を先に除去したうえで、人間が代表問題を実際に解いて確認する。

### 多様性

- 繰り返し遊んでも、同型問題の微差だけにならない。
- 同じ難易度でも、パズルとして意味のある異なる局面や判断を体験できる。
- 生成成功率だけでなく、実際に供給される問題集合の偏りを見る。

## 2. 挑戦品質

難しさが、そのパズルを考えることから生まれ、挑戦する面白さと先を読みたくなる期待を強めながら、利用者へ提示する難易度と対応していること。

- 盤面サイズ、色数、ヒント数などの生成条件を、そのまま人間難易度とみなさない。
- 機械探索量や solver 内部値だけで難易度を決めない。
- そのパズルで人間が何を判断し、どこで先読み・記憶・仮説修正を要求されるかを説明できる。
- 難易度を提供する場合、各帯が体験として意味のある差を持つ。
- 同じ難易度内で著しく簡単・難しい問題が混ざらないよう、ばらつきを把握する。
- 評価できない問題を便宜的に既存難易度へ押し込まない。

難しさの原因が、読みにくさ、狭いタップ領域、操作方法の分かりにくさなどUIの摩擦になっている場合、それは挑戦品質ではなく品質不足として扱う。

## 3. 思考の主導権

利用者が、自分で盤面を読み、自分で判断して解く余地を持ち、「自分で解いた」面白さを失わないこと。

- 通常UIが合法手、候補、正解に近い手を無条件に教えない。
- 操作不能化や強調によって、ルールエンジンの知識をそのまま答えとして露出しない。
- ヒント等の補助を提供する場合は、通常の思考と区別できる明示的な機能として扱う。
- 補助機能や入力支援が、そのパズルで本来楽しむ判断を消していないか確認する。

技術的に親切なUIでも、パズルを解く行為をUIが代行するなら品質を下げる。

## 4. 理解・操作品質

利用者が、何を見て何を操作しているかを理解し、意図した操作を過度な摩擦なく実行でき、遊ぶ楽しさをUI都合で失わないこと。

### 視認性

- 盤面、駒、数字、メモ、選択状態など、判断に必要な情報を識別できる。
- 状態の違いが、実際の表示サイズで十分に見分けられる。
- 外枠・格子・文字・メモ等の視覚階層が競合しない。
- スマートフォンで考える対象を把握するために、不必要なスクロールを要求しない。

### 操作性

- タップ領域同士が不自然に競合・重複しない。
- 主要操作と補助操作の優先順位が自然である。
- 誤操作から戻れる。
- 同じ意味の操作名が、異なる挙動を指さない。
- ページスクロールやブラウザジェスチャーがゲーム操作を妨げない。

### 操作の因果

- 選択、成立、不成立、状態変化を理解できるフィードバックがある。
- 操作した対象と変化した対象の関係が分かる。
- 内部状態だけ先に変わり、見た目が別の状態を示す時間を不必要に作らない。

## 5. テンポ・流れの品質

ゲームの技術都合が、考える・操作する・変化を見る・達成を受け取る楽しさとリズムを不必要に止めないこと。

- 演出完了待ちだけを理由に、ルール上独立した次操作を止めない。
- 一方で、最後の操作結果を見届ける前に結果画面へ切り替えない。
- 問題生成・解析が重い場合、ローディング表示で同期停止を隠すだけにしない。
- 「新しい問題」「リセット」「盤面を戻す」など、似た操作の意味を混同させない。
- 次の問題、再挑戦、難易度変更、ホーム等へ自然に進める。

速度を上げること自体を品質としない。そのゲームの思考と操作のリズムを壊さないことを見る。

## 6. 題材・表現・識別品質

そのゲームで何を見て何を扱っているかが形・色・動きから一貫して理解でき、見ること自体が興味や期待につながり、pa-zzle の中でもそのゲーム自身として識別できること。

- 内部データ構造ではなく、ゲームの題材として読める表現を使う。
- 状態変化やアニメーションが、実際に起きていることと一致する。
- 共通UIやブランド表現が、ゲーム固有の視覚表現より前へ出ない。
- ゲーム選択では、汎用アイコンや説明文だけに頼らず、そのゲームの視覚語彙で識別できる。
- ピクトグラムは既存ゲームと並べた実表示サイズで、意味的距離・識別性・光学的重量を確認する。
- 動きの面白さ、ゲームらしさなど、機械検査で決められない品質は人間が判断する。

一つのゲームの見た目を全ゲームの型へ押し込まず、共通化するのは表示条件や評価方法など再利用できる契約に留める。

## 7. 達成・評価品質

プレイを終えた利用者が、解いた楽しさを達成として受け取り、そのうえで今回の出来を納得して理解し、次のプレイへの期待につなげられること。

### 達成

- クリアが診断値や詳細情報に埋もれない。
- 最終操作から達成までが途切れず、一つの出来事として感じられる。
- 平常時より強い表現を使う場合も、情報量を増やすことだけで報酬感を作らない。

### プレイ評価

- 問題の難しさと、その問題に対するプレイヤーの出来を分ける。
- そのゲームで何を「良いプレイ」とするか説明できる。
- 評価軸同士が同じ失敗を重複して数えていない。
- 実感として良いプレイほど低く評価されるなど、明らかな逆転がない。
- 利用者へ採点基準を説明できる。
- 他ゲームと同じ式・同じ軸へ揃えることを品質としない。

### 称賛

- クリア成立と、高評価・自己ベスト等の称賛の強さを区別する。
- より良い出来事はより強く返せるが、何を褒めるかはゲーム固有の評価と一致させる。

## 8. 振り返り・上達品質

過去のプレイが単に保存されるのではなく、後から意味のある文脈で振り返り・比較でき、上達や再挑戦を楽しめること。

- 完了したプレイの事実を、ゲームと開始条件の文脈を保って残す。
- 採点式変更後も再解釈できるよう、導出値より必要な生の事実を優先して保存する。
- 再計算できない過去記録を推測で補わない。
- 自己ベストの比較単位と評価指標を、ゲーム固有の意味から定める。
- 同値を更新として扱うかなど、比較の意味が安定している。
- 記録画面は「保存しているから表示する」のではなく、利用者が何を振り返るかから情報を選ぶ。
- グラフ等の表現を、一般的な成績画面にありそうという理由だけで追加しない。

## 9. アプリ統合品質

各ゲームが個性を保ちながら、見つけて選ぶ段階から期待を高め、pa-zzle の一つのゲームとして自然に利用できること。

- ゲーム選択から開始条件、プレイ、結果、記録、次の行動まで面白さ・楽しさ・ワクワクの軸が途切れない。
- ゲームを見つけ、遊び方を選ぶ過程自体が楽しく、これから始まるプレイへの期待を高める。
- 一覧で抱いた期待と、開始条件・実際のプレイが一致する。
- 共通UIは同じ意味・振る舞いに限って共通化し、ゲーム固有の表現や評価を潰さない。
- 新しいゲームが既存契約へ不自然に収まらない場合、ゲーム側へ場当たり的な例外を足す前に共通設計を疑う。
- ゲーム数が増えても、一覧や記録などアプリ共通画面の情報構造が破綻しない。

## 品質を支える技術的性質

利用者が直接意識しない性質でも、上記品質を安定して提供するために必要なものがある。

### 再現性・診断性

- 同じ問題へ戻れる。
- seed だけで足りない場合は生成器版・生成条件・試行等を含む identity を持つ。
- 問題 identity とプレイ identity、ビルド情報を混同しない。
- 画面で見つかった問題を、テストやCLIから再現して原因責務へ戻せる。
- 診断情報を通常利用者向けUIへ常設しない。

### 応答性・性能

- 想定問題規模で、生成・解析・描画がプレイを妨げない。
- 平均だけでなく p50 / p95 / 外れ値を見る。
- メインスレッドを長時間占有して入力・描画を停止させない。
- 性能問題を、難易度や問題品質を下げることで隠さない。

### 状態・保存の信頼性

- ルール上の状態変更の正本が明確である。
- UIが別のルールを持たない。
- Undo 用履歴と監査・記録用途を混同しない。
- 保存領域が利用できない場合も、意図しないクラッシュを起こさない。

### 変更可能性

- 難易度モデル・採点式・生成器の変更を再校正できる。
- ゲーム固有責務とアプリ共通責務を分離する。
- 過去2ゲームの偶然の一致を、将来ゲーム向けの共通契約へ先回りして固定しない。

技術的性質がすべて満たされても、問題が退屈、操作が不自然、評価に納得できないならゲーム品質は成立していない。

## 品質の確認責務

品質項目ごとに、機械検証・セルフレビュー・人間レビューの役割を分ける。

### 機械検証

同じ入力・条件なら同じ結論を出せるものを担う。

例:

- 問題成立条件、可解性、一意性
- 再現性
- 生成成功率、性能分布、重複率
- 状態遷移、クリア判定
- 採点式の計算
- 保存・復元
- 型検査、テスト、ビルド、ブラウザエラー

### セルフレビュー

人間へ品質判断を渡す前に、開発側で発見できる明らかな不足を落とす。

例:

- 表示崩れ、重なり、読めない情報、狭すぎる操作対象
- タップ領域の競合
- 主要操作が通らない、戻れない、クリアできない
- 状態差が見分けられない
- 診断情報が通常UIへ露出している
- 既知のエラーや明らかな視覚破綻
- レビュー対象として不適切な問題集合

セルフレビューを通ったことは、人間が感じる面白さ・難易度・納得感を保証しない。

### 人間レビュー

実際に利用者として体験しなければ判断できないものを担う。

例:

- そのゲーム固有の何が面白いのかを実際のプレイから説明できるか
- 問題を解く行為に価値があり、退屈・単純作業になっていないか
- 難易度が実際の思考負荷と対応するか
- 考える対象へ自然に集中できるか
- UIがパズルを解きすぎていないか
- 操作とフィードバックが自然か
- 考える・操作する・変化を見る流れそのものを楽しいと感じられるか
- テンポが気持ちよいか
- 次の局面・問題・結果を見たいと思える期待や好奇心が生まれるか
- 題材と表現が一致しているか
- ゲーム選択や開始条件選択そのものが楽しく、プレイへの期待を高めているか
- ピクトグラムやアニメーションがゲームらしく魅力的か
- 採点に納得できるか
- 達成や自己ベストが適切な強さで返り、もう一度遊ぶ楽しみにつながるか
- 履歴や比較に振り返る価値があるか

人間レビューは、未完成の検査を押し付ける工程でも、感想を無条件に採用する工程でもない。違和感が出た場合は、問題生成、難易度モデル、操作設計、視覚表現、評価設計など原因を所有する責務へ戻して検証する。

## レビューへ渡す条件

- 今回どの品質を判断するレビューか明確である。
- レビュー対象そのものは、その判断ができる品質まで作られている。
- 機械検証とセルフレビューで落とせる既知の不足を残していない。
- 判断に必要な代表問題・境界問題・実プレイ事実を使っている。
- 利用者が実際に体験する文脈で確認できる。
- 対象外の未完成要素が判断を歪めない。

モックを使ってよいのは、今回の評価対象ではない周辺部分だけとする。

## 主な知見の由来

この品質モデルは現在の RQ / FR / SPEC / SCR / AC だけから作っていない。正本化前から実際の開発・レビューで繰り返し確認された知見も含む。

- 問題供給・導入成立性: #27〜#44、#54、PR #58、#59、#60
- 技術成立とゲーム体験成立の分離、盤面中心、思考の主導権、題材表現、操作フィードバック: #67、#68、PR #70
- 人間難易度と生成条件の分離、実プレイ校正: #7、#48、#69、#243、PR #128
- 再現性・診断性: #113 と再現契約修正の Git 履歴
- ゲーム一覧・ゲーム固有の視覚表現: #77、#90、#119、PR #105
- 人間へ粗い候補を渡さず、面白さを人間判断へ残す: #120、PR #123
- 結果を達成・称賛として返す: #93、#135、#183、PR #186
- 事実保存、自己ベスト、振り返り: #92、#142、#146、PR #143、#155
- 応答性: #196
- 補助操作の意味整理: PR #248
- ナンプレの実装・レビュー履歴では、メモの視認性、状態差、格子と外枠、操作間隔、クリア遷移等が段階的に修正されており、高位の要件だけでは拾えない局所品質も実画面レビューで確認する必要がある。
- ウォーターソートの Git 履歴では、連続操作、演出中の状態整合、再現契約等が後から修正されており、単に機能が動くことを完成条件にできないことが確認されている。

Issue #262〜#268 でプロダクト正本自体の未明文化知見を現在も棚卸し中であるため、現行 RQ / AC だけを品質モデルの完全な根拠とは扱わない。
