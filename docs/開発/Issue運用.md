# Issue運用

Issueには、一つの目的と、その判断に必要な確定事項を記す。作業者が考えた手順や解決案を、要求に置き換えない。

## 種類と目的

- **探索**: 現状・原因・可能性など、未知のことを明らかにする。仮説が否定された場合も、その根拠が成果になる。
- **設計・判断**: 課題に対して採用する方針を決める。採用前の候補を確定事項にしない。
- **実行**: 実現する内容が既に決まっている変更を行う。実装方法や検証手順は、確定した制約がなければ作業時に決める。

Issue作成時は `.github/ISSUE_TEMPLATE/` の該当するテンプレートを使う。GitHubのAPIなどテンプレートを適用しない経路でも、対応する項目と任意項目の扱いを守る。

## 作成・更新

- 目的、観測事実、仮説、候補、既決事項を区別して記す。
- Issue本文の候補・完了条件は、依頼内容や関連資料と照合して出所を確かめる。作業者の提案や根拠が不明な事項を、既決事項として扱わない。
- 完了条件・受け入れ条件は必須ではない。ユーザーの明示した要求や確定した仕様・判断に根拠がある場合だけ記す。
- AIが考えた手順・実装案・検証計画を、Issueの確定要件や完了条件として追加しない。
- 探索で見つかった別の問題や、設計判断後に必要になった実装など、独立した別目的の仕事は新しいIssueにする。元Issueの目的は書き換えない。
- 目的を維持したまま調査・試作・実装などの手段を変えるだけなら、新しいIssueに分ける必要はない。
- 親Issueは横断する目標を管理し、子Issueはそれぞれ自身の目的を持つ。親の最終目標を子の完了条件に置き換えない。

## 終了・引き継ぎ

- 完了判定はIssueの目的と確定した要件を基準にする。調査結果や作業都合に合わせて目的を読み替えない。
- 成立性の検証が目的なら、成立しないと分かったことも根拠のある成果になる。成立させることが目的なら、否定的な検証結果を目的達成と扱わない。
- 未検証事項は未検証として残す。別目的の未実施作業を、そのIssueの完了条件へ追加しない。
- 目的が達成された場合はCompleted、必要な作業や判断が残る場合はOpenとする。継続しないことが確定した場合だけNot plannedで閉じる。
- 方針の採用・中止など未決の判断は、確定した既存方針や明示的な委任の範囲でのみ行う。委任されていないときは根拠と選択肢を揃えて判断を求める。

## 作業の扱い

- Issueに列挙された調査観点や作業候補は、確定した要件と区別して扱う。
- 設計・再設計の判断前に、関連する現行仕様・実装と過去の採用・不採用の理由を確認し、現行維持も含めて判断する。
- 探索では、成立しない・採用しないという結論も根拠とともに残す。仮説を成立させるためだけに調査を延長しない。
- PR作成やチェック項目の消化は、Issueの目的を達成した証拠そのものではない。

作業手順と品質検証は `AGENTS.md`、`docs/開発/品質検証手順.md` および対象の規則を正とする。
