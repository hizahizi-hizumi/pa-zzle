# 変更時の品質検証手順

## 目的

実装・問題集・画面・文書を変更するとき、**何を保証する変更で、どこまで確かめたか**を、対象に合った根拠で判断できるようにする。

品質の基準は `docs/プロダクト/要求/`・`要件/`、`APP.md`・`GAME.md`・`DESIGN.md`、対象の仕様・画面文書を正とする。この手順は基準を新設せず、検証の選び方と結果の残し方を扱う。新規パズルの導入では[候補評価チェックリスト](新パズル候補評価チェックリスト.md)と `.claude/skills/add-puzzle/SKILL.md`、難易度の導入・変更では[難易度開発手順](../パズル/難易度開発手順.md)の詳細な工程を優先する。

## 1. 変更で影響する品質を特定する

1. 差分だけでなく、遊ぶ人の **選ぶ → 解く → 結果 → 次の問題** のどこへ影響するかを調べる。ゲーム固有の変更か、複数ゲームへの共通の変更かを区別する。
2. 関係する要求・要件（RQ / FR / NFR）と、仕様・画面の正本を読む。変更したファイルの置き場所だけで検証を選ばない。
3. 変更に応じて次の表から検証を選ぶ。ひとつの変更が複数の行に当たることもある。影響しない行をすべて実行する必要はない。

| 変更の種類 | 主な品質と確認すること | 既存の検証手段 |
| --- | --- | --- |
| **新しいパズル** | NFR-002・003・007〜009・016〜018：遊びの独自性、成立性、問題の質・量、難易度の深さ、実際のプレイ | [候補評価チェックリスト](新パズル候補評価チェックリスト.md) → `add-puzzle` Skill。横断手順だけで代用しない |
| **問題集・生成器** | NFR-003・004・017：問題として成立するか、重複・解法構造の偏りがないか、各難易度へ必要量を供給できるか | ゲーム固有の問題集テスト、生成器の検証機能、問題集合での分布と代表問題の解法確認。問題IDと旧記録への影響も確認 |
| **難易度モデル・提供範囲** | NFR-007〜009・018：挑戦の強さ・判定の再現性・安定供給、最上位が相対順位だけに終わっていないか | [難易度開発手順](../パズル/難易度開発手順.md)。典型・境界・異常問題と人間の解法を照合 |
| **ルール・採点・記録** | NFR-003・010・011：公開ルールとクリア判定、評価の一貫性、自己ベスト・過去記録・図鑑への影響 | 対象ゲームと記録のVitest、仕様照合、代表的なプレイ結果・旧履歴の確認 |
| **プレイUI・演出・音** | NFR-001・002・012〜015：盤面と操作の意味、途中状態、入力競合、画面幅、完成から結果まで | [画面レビュー手順](画面レビュー手順.md)、関連テスト、実ブラウザの操作・描画・エラー確認。実端末や音の確認が必要なものは区別して記録 |
| **図鑑・問題選択・連続プレイ** | NFR-004〜006・017：未挑戦／挑戦中／クリア済み、絞り込み、再挑戦、次問、問題の重複・収集への影響 | SPEC-014・026等の仕様と記録・選択テスト、複数の収集状態での実操作 |
| **共通UI・アプリの導線** | NFR-001・005・006・012〜015：複数ゲームを通した選択・操作・結果の一貫性 | `APP.md`・`GAME.md`・各画面正本、[画面レビュー手順](画面レビュー手順.md)。影響する複数ゲームを実際に操作 |
| **文書・開発環境のみ** | 変更した契約の重複・参照切れ、既存手順・コマンドとの不整合 | 文書の階層とリンク、実際の構成・コマンド、GitHub上の差分を確認。画面・プレイの変更がない場合はそれらの試遊を要求しない |

NFR-017の問題供給量は、対象ゲームの仕様に定めた測定可能な基準で判定する。**基準が未整備なら、現行の問題数だけで「成立」と判定しない。** NFR-018も、単にレベル5の問題があることだけを根拠にしない。数値や検証方法を恣意的に補わず、未確定の範囲を明示する。

## 2. 機械検証と体験検証を組み合わせる

- **機械で正しさを検査する**：変更されたルール・データ・記録・表示の契約について、既存のVitest等で正常系と破綻しやすい条件を確認する。PRのQuality Gateは `scripts/verify.sh`（Biome、型検査、Vitest、ビルド）を実行する。**Quality Gateの成功だけで問題の面白さや操作感が成立したとは判定しない。**
- **問題そのものの質を検査する**：問題成立性、難易度、多様性、問題量はそれぞれ別の観点で確認する。ソルバー・分類器の結果だけで人間の思考過程を代用せず、解法記録や代表問題の試遊と照らす。新ゲームや難易度変更の完了条件は上記の専用手順に従う。
- **画面と操作を検査する**：画面変更は完成状態だけでなく、入力途中・連続操作・演出途中・クリア後の遷移を実ブラウザで確認する。`pageerror`、意図しない `console.error`、失敗したネットワーク要求も確認する。スマートフォン相当幅を要する変更では実際に確認する。
- **実測の要否を判断する**：供給量、生成成功率、操作応答、数千件の履歴集計など数値が判断を左右する場合は、対象の問題集合・端末条件・測定方法と分布を残す。実測していない推定を計測結果として扱わない。

全問の高コストな検証を毎回のCIへ無条件に足さない。対象の変更時に必要な検証が既存のCIへ収まるかを計測し、収まらない場合はその理由と別の実行・記録先を明らかにする。

## 3. 判定と根拠を残す

既存の[候補評価チェックリスト](新パズル候補評価チェックリスト.md)と同じ判定語を使う。

| 判定 | 意味 |
| --- | --- |
| **成立** | 正本の品質を満たすことを、対象と条件を特定できる証拠で確認した |
| **不成立** | その品質を妨げる事実を確認した。再現条件と影響を特定する |
| **要検証** | 未実行、環境制約、基準未確定、標本不足などで判断できない。未実施を合格にしない |
| **対象外** | その変更では影響しない。対象外にした理由が説明できる |

検証の結果は原則として**変更を扱うPRのValidation欄や既存のIssue・検証記録・CI Artifact**に残し、根拠へたどれるようにする。全要件を機械的に列挙した台帳を新設する必要はない。記載は、影響の大きい品質から次を最小単位とする。

- **対象**：変更した振る舞い・ゲーム・問題ID・画面、および検証したコミット（またはArtifactのref）。
- **根拠**：対応するRQ/FR/NFR・仕様、検証方法、テスト名や実操作、結果・ログ・スクリーンショット等の参照先。
- **判定と残る事項**：成立／不成立／要検証／対象外、対象外・未実施の理由、不確実性の影響と次にどう確かめるか。

問題を確かめた結果が「仕様を満たす」ことと、「製品として魅力的である」ことは別に記録する。未確認のまま重大な品質保証を**成立**と書かない。確認済みの重大な不成立を放置して「品質確認済み」と報告しない。判断を保留した範囲がある場合は、その範囲・影響・扱いを明示する。

## 4. 実施例：問題集と表示だけを変える場合

あるゲームの問題集JSONを更新し、図鑑に出る問題も変わる変更では、次のように検証範囲を定める。

1. **NFR-003（成立性）**：対象ゲームの問題集検査を行い、可解性などの当該ゲームの条件を確認する。
2. **NFR-004（多様性）**：新旧の同型・特徴量・解法の分布を比べ、代表問題の解法が極端に偏っていないかを見る。
3. **NFR-017（問題量）**：対象難易度について供給方法と問題数を確認し、ゲーム別の基準に照らす。基準が未定なら**要検証**と明記する。
4. **SPEC-014・026（記録・図鑑）**：問題IDが変わる場合、過去の履歴が今の図鑑から引けなくなる範囲を調べる。履歴が残ることと収集へ反映されることを混同しない。
5. **図鑑の表示や選択へ影響する場合**、UIコードの変更がなくても実ブラウザで操作して[画面レビュー手順](画面レビュー手順.md)で確認する。

実例は検証の**選び方**を示したものであり、このファイルを作成した時点で上記検査を実行・合格したという意味ではない。
