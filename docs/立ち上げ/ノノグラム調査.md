# ノノグラムの基礎仕様と自動生成の成立性調査

Issue: #38

調査日: 2026-09-14

## 結論

**採用候補として次段階へ進めてよい。**

完成図から行・列ヒントを作る処理自体は決定的で軽い。一方、サービスとして問題を供給するには、生成したヒントに対して以下を別々に検証する必要がある。

1. 完成図がヒントを満たすこと
2. 完成図以外の解が存在しないこと（一意解）
3. 採用する人間向け推論だけで解けること
4. 難易度・見た目・類似度が供給基準を満たすこと

一般問題の求解・別解探索は計算量的には難しいが、人間向けに設計された問題では専用解法器による検証が十分高速に行われてきた実績がある。生成時に時間上限を設け、検証コストの高い候補を棄却できるため、オンラインサービスの問題供給を阻害する致命的な要因とは見なさない。

ただし、**無作為な完成図をそのまま問題化する方式は採用しない**。既存の大規模比較では、各マスを50%の確率で塗った30×30の5,000問のうち97.5%が複数解で、一意かつ行・列単位の推論だけで解けた問題は0.4%だった。対して人間が作成したWebPBNの2,491問では81.8%が一意かつ行・列単位で解けた。良問生成では完成図生成と解法器による選別・調整を一体で扱う必要がある。

一次調査の `パズル調査.md` にある「完成画像から行列ヒントを生成できるので自動生成しやすい」という評価は、ヒント生成だけを見れば正しいが、良問の安定供給まで含めると過大評価になる。ノノグラムの自動生成適性は **○: 自動生成可能。ただし一意解判定・論理解法判定・棄却生成が重要** と捉える。

## 基礎仕様

pa-zzle ではまず白黒ノノグラムを対象とする。多色ノノグラムは同じ考え方を拡張できるが、ヒント表現・隣接色の扱い・解法器が複雑になるため別検証とする。

盤面は `height × width` の長方形として扱い、正方形に限定しない。盤面サイズの製品上の上限・難易度別サイズはこの調査では固定しない。

各行・列のヒントは、左から右または上から下へ現れる**連続した黒マス群の長さを順番に並べた正整数列**とする。

例:

```text
..###.##..#  -> [3, 2, 1]
...........  -> []
```

解答データは各マスの `filled / empty` の2値で十分である。プレイヤーの盤面状態は次の3状態を持てる。

- 未確定
- 塗り
- 除外マーク（×）

除外マークは解答そのものではなく、プレイヤーの推論補助状態として扱う。

クリア条件は、**塗られているマスの集合が解答の黒マス集合と一致すること**とする。白マスをすべて除外マークにすることは要求しない。これにより除外マークの利用有無をプレイスタイルとして許容できる。

## 問題が成立する条件

完成図からヒントを生成した場合、その完成図自身が必ず解になるため「解が1つ以上存在する」ことは構成上保証できる。

ただし、同じ行・列ヒントを満たす別の完成図が存在する場合がある。最小例として、2×2ですべての行・列ヒントが `[1]` なら、2本の対角線配置がどちらも解になる。

したがって公開問題の必須条件を次とする。

- 解が存在する
- 解が一意である
- pa-zzle が許可する推論体系で解ける

「一意解」と「推測なしで解ける」は同義ではない。全体として解が一意でも、行・列単位の局所推論だけでは途中で停止する問題が存在する。難易度判定ではこの2つを分ける。

## 解法と一意性検証

基本となる解法器は、各行・列について現在の確定マスとヒントを満たすすべての配置を考え、すべての配置で同じ値になるマスを確定する**行・列単位の制約伝播**とする。

Batenburg / Kosters の定式化では、長さ `l`、ヒント数 `k` の1行が現在状態と両立するかを動的計画法で判定でき、計算量は `O(k * l^2)` とされる。この処理を行と列へ交互に適用し、固定点まで進めることで「行・列単位の推論だけで解ける問題」を判定できる。

一意性検証は局所推論だけでは足りない。実装候補は以下のどちらでもよい。

- 制約伝播 + 分岐探索で解を最大2件まで探索する
- SAT / 制約充足問題として解を1件求め、その解を禁止する制約を追加して2件目の有無を調べる

生成器は元の完成図を知っているため、実運用では「完成図が解であること」を再探索する必要はない。元画像と異なる解が1件でも見つかれば即棄却し、見つからないことを探索し切った候補だけ一意解として採用できる。

ノノグラム一般の求解はNP困難で、別解の存在判定にも計算量上の難しさがある。そのため盤面サイズだけから最悪計算時間を保証する設計にはしない。

一方、WebPBNの人間向け白黒2,491問を対象に、通常2解まで探索する条件で比較された専用解法器では、最速のものが99.9%を1秒未満、21問を除く全問を0.1秒未満で処理している。古い計測環境での結果であり現在環境の性能値としては使わないが、通常問題の検証が現実的である根拠にはなる。

生成処理ではさらに候補ごとの時間上限を設けられる。検証が病的に重い候補を問題として採用する必要はないため、最悪ケースをそのままオンライン応答時間へ持ち込まない構成にできる。

## 自動生成

最小パイプラインは次の通り。

```text
完成図候補を生成
  ↓
行・列ヒントを生成
  ↓
一意性を検証
  ↓
人間向け解法器で解法経路を取得
  ↓
難易度・品質・類似度を評価
  ↓
基準外なら棄却または完成図を調整して再検証
```

完成図候補の作り方は少なくとも次の3系統がある。

1. 手描き・既存素材を低解像度の二値図へ変換する
2. アイコン・図形などの生成規則から意味のあるシルエットを作る
3. 塗りパターンを計算的に生成し、解法器の評価を使って探索・最適化する

文献では、RGB画像から二値化・調整を行い、解法器で手解き可能性を評価しながらノノグラムを自動生成する方式や、入力画像への類似度とパズル条件を同時に最適化する方式が報告されている。したがって「意味のある絵」と「一意で解きやすい問題」を同時に満たす生成は既知の技術課題であり、原理的な障害ではない。

ただし単純なしきい値処理だけでは、一意解でなかったり分岐が必要になったりすることが報告されている。画像変換処理だけを生成器とみなさず、解法器からのフィードバックを必須にする。

## 盤面サイズと探索量

ノノグラム一般の最悪計算量は盤面サイズに対して単純な多項式では抑えられないため、「20×20なら常に何ms」のような保証は置かない。

一方、1行に対する制約伝播は動的計画法で多項式時間に処理でき、人間向け問題の大部分はこの処理を行・列へ反復するだけで大きく進む。WebPBNの比較でも、人間向け問題の大半は専用解法器で短時間に検証できている。

サービス設計では次の2段構えにする。

1. 通常の行・列制約伝播で解法・難易度情報を得る
2. 一意性確認では必要な候補だけ完全探索し、時間上限を超える候補は生成時に棄却する

そのため盤面サイズの拡大は「許可サイズを先に理論だけで決める」のではなく、次段階の実装で 5×5 / 10×10 / 15×15 / 20×20 程度を実測し、必要なら25×25以上へ広げる。

## 完成図の意味性

ノノグラムのゲーム性には「論理パズル」と「解いた結果として絵が現れる」の2要素がある。

制約問題としては抽象図形でも成立するが、pa-zzle でノノグラムを採用する理由には完成画像による体験差も含まれるため、**本番供給では意味のある完成図を品質目標とする**。

一方、成立性検証・解法器検証では意味性を要求しない。次段階では以下を分離して評価する。

- 制約品質: 一意性、論理解法、難易度、検証時間
- 画像品質: 認識可能性、見栄え、題材の多様性

これにより画像品質の問題を、解法器や自動生成アルゴリズムの成立性と混同しない。

## 多様性と重複

一意解問題では同一の行・列ヒントは同一完成図に対応するため、完全重複はヒント列または完成図の正規表現で検出できる。

回転・鏡映で同じ図形になる問題を同型として除外したい場合は、完成図の対称変換を列挙し、辞書順最小表現を正規形にすればよい。

「少しだけ違う」類似問題は完全一致とは別問題なので、後続では次のような指標を組み合わせる余地がある。

- 正規化後のマス単位距離
- ヒント列の類似度
- 連結成分・黒マス率・連続長分布などの形状特徴
- 完成図を画像として扱う類似度

生成時に候補を棄却できるため、類似度判定を生成アルゴリズムそのものへ埋め込む必要はない。

## 難易度制御・良問判定

盤面サイズや黒マス率だけを難易度とみなさない。

難易度評価は、人間向け解法器が実際に辿った経路から少なくとも以下を取得する方向が適切である。

- 行・列単位の制約伝播だけで完走できるか
- 固定点までの伝播回数
- 1回の推論で確定するマス数
- 次に進められる行・列の候補数
- より広い範囲を組み合わせる推論が必要か
- 仮定・背理法相当の探索が必要か

Batenburg / Kosters は、行・列単位の推論だけで解ける問題を `simple` と定義し、掃引回数などを難易度指標として扱っている。また、局所推論を2-SAT等で組み合わせ、分岐せずにより難しい問題を解く枠組みも示されている。

したがって難易度制御へ発展できる見込みは十分ある。ただし最終的な難易度区分は、解法器の内部指標だけで確定せず、実プレイ時間・ミス・離脱・ヒント利用などのデータと突き合わせる後続検証が必要である。

## ヒント・Undo・ミス判定との境界

- Undo / Redo: プレイヤー操作履歴。問題定義・解法器とは分離する
- ミス判定: 現在入力を保存済み解答と比較すれば実装可能。常時判定するかはゲーム設定の問題
- 答えを1マス開示するヒント: 保存済み解答から実装可能
- 論理的な次の一手を示すヒント: 人間向け解法器の推論結果を利用する
- 理由まで説明するヒント: 解法器が「どの行・列のどの制約で確定したか」を説明可能な形で記録する必要がある

よって、Undo・ミス判定・単純な答え開示はノノグラム固有の解法器から切り離せる。一方、学習的なヒントは解法器の設計要件になる。

## 次段階

採用可否: **GO**

次段階では実装前の小規模検証として、次を確認する価値がある。

- 行・列単位の制約伝播器を実装し、推論根拠を記録できるか
- 一意性確認用の完全探索を組み合わせ、候補を安定して棄却できるか
- 5×5 / 10×10 / 15×15 / 20×20 程度で生成・検証時間を計測する
- 意味のある完成図候補を複数方式で作り、一意かつ論理解法可能な採用率を比較する
- 推論経路から作った仮難易度と、人間が感じる難しさに対応があるかを確認する

盤面サイズの製品上限、最終的な難易度区分、画像生成方式の一本化、スコア式、UI詳細はこの結果を見て決める。
