# 迷路の導入成立性調査

Issue #42 の調査結果。

## 結論

迷路は pa-zzle の **実装候補に採用** と判断する。

| ゲート | 判定 | 根拠 |
|---|---|---|
| 1. 問題供給成立性 | 通過 | 完全迷路なら可解性と一意経路を構成上保証でき、生成・探索性能と多様性にも致命的問題がない |
| 2. 難易度運用成立性 | 通過 | 生成方式だけでも経路長・分岐・袋小路の分布を大きく動かせ、生成後の特徴量計測と棄却を組み合わせられる |
| 3. スマホプレイ成立性 | 通過 | 1マスを直接タップせず、盤面上のスワイプ入力を基本にすれば小さいマスでも操作対象を確保できる。15×15程度までは盤面全体表示との両立に余裕がある |
| 4. 導入判断 | 採用 | 問題供給が容易で、スマホ上の操作方式も既存実績があり、pa-zzle のプレイ計測とも相性がよい |

ただし、**自動生成できることと、長期的に面白いことは別**である。今回の採用判断は「実装候補として成立する」という意味であり、最終的な難易度式や継続プレイ時の面白さは実プレイデータで校正する。

## ゲート1: 問題供給成立性

### 基礎仕様

初期実装は **長方形の直交格子による完全迷路** を基準とする。

- 1マスを頂点とする。
- 上下左右に壁がなく隣接するマス間を辺とする。
- 1回の移動は隣接する1マスへの移動とする。
- 開始点とゴールを1つずつ持つ。
- 開始点からゴールへ到達した時点でクリアとする。
- 全マスが連結し、閉路を持たない完全迷路を基準とする。

完全迷路の通路グラフは全域木なので、任意の2マス間に経路がちょうど1つ存在する。生成時点で到達可能性と経路の一意性を保証できる。

開始点・ゴールは外周を基本とする。ただし常に左上・右下へ固定すると問題特性が偏るため、生成後に候補を選び、最短距離や分岐などの特徴量を見て決める。

多経路迷路は完全迷路へ辺を追加すれば生成できるが、最短経路以外も合法となり難易度評価が変わるため、初期仕様からは外す。

### 生成方式

| 方式 | 特徴 | 用途 |
|---|---|---|
| ランダム化深さ優先探索 | 長い通路が生まれやすい | 長い経路側の生成候補 |
| ランダム化Prim法 | 分岐・袋小路が多い | 分岐の多い生成候補 |
| ランダム化Kruskal法 | Union-Findで全域木を直接構成 | 追加候補 |
| Wilson法 | 一様全域木を生成 | 生成方式の偏りを抑えた比較基準 |
| Aldous-Broder法 | 一様全域木を生成 | 理論上の比較対象。初期採用の必然性は低い |

Wilson法と Aldous-Broder法は一様全域木を生成できる。一様であること自体は良問を意味しないが、特定の生成法の形状バイアスを避ける比較基準として使える。

### 解法探索

重みなしグラフなので幅優先探索で最短経路を求められる。頂点数を `V`、辺数を `E` とすると `O(V + E)`。完全迷路では `E = V - 1` なので盤面サイズに対して実質線形となる。

### 生成・探索実験

Python の単純実装で、方式間の傾向と桁感を確認した。本番実装の性能測定ではない。

20×20、各300問:

| 方式 | 生成時間平均 | 開始→ゴール経路長平均 | 正解経路上の分岐平均 | 全袋小路数平均 |
|---|---:|---:|---:|---:|
| 深さ優先探索 | 0.82 ms | 121.3 | 12.6 | 42.3 |
| Prim法 | 0.69 ms | 43.0 | 24.9 | 129.5 |
| Wilson法 | 4.40 ms | 59.4 | 28.3 | 116.1 |

40×40、各100問:

| 方式 | 生成時間平均 | 開始→ゴール経路長平均 | 正解経路上の分岐平均 | 全袋小路数平均 |
|---|---:|---:|---:|---:|
| 深さ優先探索 | 3.89 ms | 367.3 | 31.3 | 164.3 |
| Prim法 | 2.86 ms | 89.4 | 54.1 | 514.3 |
| Wilson法 | 28.20 ms | 142.3 | 69.8 | 468.4 |

Prim法で生成した完全迷路の幅優先探索:

| 盤面 | 平均探索時間 |
|---|---:|
| 20×20 | 0.11 ms |
| 40×40 | 0.45 ms |
| 80×80 | 1.90 ms |
| 160×160 | 11.90 ms |

各サンプル集合内では生成結果のハッシュ重複はなかった。重複が存在しない証明ではないが、通常利用で多様性が即座に枯渇する兆候はない。

回転・反転を同一問題として除外したい場合は、各変換後の盤面表現から代表表現を決め、そのハッシュを保存すればよい。厳密なグラフ同型判定は初期段階では不要。

**ゲート1判定: 通過。**

## ゲート2: 難易度運用成立性

### 難易度候補

構造から計測できる候補は次のとおり。

- 開始点からゴールまでの最短距離
- 正解経路上の分岐数
- 正解経路から伸びる誤経路の数
- 誤経路の深さ・総距離
- 最長の袋小路
- 正解経路上の曲がり回数
- 全通路に占める正解経路の割合
- 分岐の位置
- 長い一本道の割合

Yokota らの研究では、開始点からゴールまでの迷路コストや T 字分岐数が人間の課題成績と関係することが報告されている。単なる盤面サイズより、意思決定を要求する地点を特徴量として持つ根拠になる。

一方、Semizer らは、壁・経路の太さや直線・波線といった見た目だけでも迷路の解答時間が変化することを示している。したがって構造的難易度と視覚的難易度は分離する。

### 制御可能性

生成実験では同じ20×20でも、深さ優先探索とPrim法の間で正解経路長が平均121.3対43.0、正解経路上の分岐が12.6対24.9となった。40×40でも同じ傾向が確認できた。

つまり、少なくとも次のつまみで生成分布を意図的に動かせる。

1. 盤面サイズ
2. 生成方式
3. 開始点・ゴールの選択
4. 生成後の特徴量による棄却

難易度を「盤面サイズ = 難易度」と固定する必要はない。複数生成法から候補を作り、特徴量を測り、狙った帯だけ採用する生成パイプラインを構成できる。

```text
盤面サイズ・生成方式を選ぶ
  ↓
完全迷路を生成
  ↓
開始点・ゴール候補を選ぶ
  ↓
正解経路・特徴量を計算
  ↓
狙った特徴量帯・品質条件を満たすか判定
  ├─ 満たす → 採用
  └─ 満たさない → 再生成または端点を再選択
```

最終的な「初級・中級・上級」の閾値は今回決めない。構造特徴量を保存し、クリア時間、超過移動距離、戻り量、離脱などのプレイログで校正する。

**ゲート2判定: 通過。** 生成条件と棄却条件で難易度候補の分布を動かせるため、後続校正へ持ち込める。面白さそのものを構造指標だけで保証するものではない。

## ゲート3: スマホプレイ成立性

### 既存事例

スマホ向け迷路で「盤面上の小さい1マスを毎回タップする」方式に限定する必要はない。

- **Mazes & More** は iPhone / Android でスワイプまたはタップによる操作を提供し、Google Play では 5,000万以上のダウンロード実績がある。設定でタップ・スワイプ操作を選択できる。
- **Maze Swipe** は1本指のスワイプを主操作とし、Google Play で100万以上のダウンロード実績がある。
- **Swipe Mazes** も iPhone で1本指のスワイプ操作を採用している。

したがって、迷路をスマホで遊ぶこと自体や、スワイプによる方向入力には既存実績がある。

### 操作方式の比較

| 方式 | 長所 | 問題 | 判定 |
|---|---|---|---|
| 経路を指で直接なぞる | 視覚上の経路と操作が一致し、連続移動が速い | 指が先の経路を隠す。細かい盤面ほど誤入力しやすい。ドラッグだけを必須にすると代替操作が必要 | 補助候補 |
| 盤面上で方向へスワイプ | マス自体をタップ対象にしないため盤面を細かくできる。既存実績が多い | 1マスごとのスワイプでは回数が多い。どこまで連続移動するかの仕様が必要 | **基本候補** |
| 画面上の方向ボタン | 盤面サイズと入力領域を分離できる。44pt級の押下領域を確保しやすい | 長い経路では押下回数が多く、視線が盤面とボタン間で離れる | 代替操作候補 |
| 隣接マスをタップ | 実装・理解が単純 | 盤面が細かいとタップ領域が急速に小さくなる | 大盤面には不向き |
| 遠方をタップして自動移動 | 操作回数を減らせる | 分岐をまたぐ自動移動の仕様次第で探索をゲーム側が肩代わりする | 初期候補から除外 |

pa-zzle の初期候補は、**盤面上のスワイプを主操作、画面上の方向入力を代替操作**とするのが妥当。スワイプを「1マス」ではなく、指を離すまで入力方向へ進める、または次の分岐・壁まで進める方式は操作量を減らせるが、どちらが面白さを損なわないかは実装時に比較する。

### 画面幅と盤面規模

390 CSS px 幅のスマホ相当画面で、左右12pxずつの余白と2pxの外枠を持つ約360px四方の盤面を描画する最小試作を行った。

| 盤面 | 1マスの表示幅 | 評価 |
|---|---:|---|
| 10×10 | 約36px | 余裕あり |
| 15×15 | 約24px | 全体表示と細かさの境界候補 |
| 20×20 | 約18px | 直接タップには細かい。壁・通路の視認性も設計依存が大きくなる |

Apple は一般的な操作対象について44×44pt以上を推奨し、WCAG 2.2 のターゲットサイズ最小基準は原則24×24 CSS pxである。ただし迷路盤面のように位置を空間的に指定する領域は、WCAG上は盤面全体を1つの対象として扱える。ここで24pxを「迷路の各マスが必ず満たす規格」と解釈してはいけない。

それでも、15×15で1マス約24px、20×20で約18pxという差は、直接タップ・直接なぞりの操作精度を考える実用上の目安になる。20×20以上を全体表示したまま1マス単位の直接入力に頼る設計は避ける。

### 実ブラウザ確認

最小操作試作を Chromium / 390×844 CSS px / タッチ端末相当で描画し、10×10、15×15、20×20を確認した。

- 10×10 / 15×15 / 20×20 はいずれも横スクロールなしで全体表示できた。
- 方向ボタンを44px以上で配置し、盤面サイズに依存せず入力できることを確認した。
- Pointer Events で盤面上の連続移動を処理できた。
- `pageerror` と意図しない `console.error` は発生しなかった。
- 15×15では1マス約24px、20×20では約18pxとなった。

ブラウザーではタッチ操作をページスクロールやズームとして解釈することがある。Pointer Events を使う場合、盤面領域の `touch-action` を明示して競合を制御できる。ただし `touch-action: none` はブラウザーのズームを阻害し得るため、ページ全体へ無条件に指定せずゲーム盤面の入力設計とアクセシビリティを合わせて決める。

### 盤面サイズ上限

現時点の導入判断では、**全体表示を前提とする初期対象を10×10〜15×15程度**とするのが安全。20×20は生成・探索性能上は軽いが、スマホでは操作性能より視認性が先に制約になる。

20×20以上を必要とする場合は、拡大・パンを導入するより先に、スワイプ入力と壁の描画で十分読めるかを別途確認する。拡大・パンはゲームのスワイプ操作とブラウザー操作の競合を増やすため、初期仕様の前提にはしない。

**ゲート3判定: 通過。** 10×10〜15×15程度を全体表示し、盤面上のスワイプを主操作にする構成なら成立する見込みが高い。20×20以上は無条件に成立とは扱わない。

## ゲート4: 導入判断

### pa-zzle との相性

迷路は次の値を自然に計測できる。

- クリア時間
- 最短距離
- 実移動距離
- 最短距離との差分・比率
- 戻った距離
- ヒント使用
- やり直し回数
- 自己ベスト

生成・解法探索が軽く、問題供給を外部コンテンツへ依存しない。スマホ向け迷路ゲームにも大規模な既存実績があり、少なくとも「迷路はスマホでは遊べない」という導入阻害要因はない。

一方、迷路は古典的でルールが単純なため、**技術的成立性だけでは継続的な面白さを保証できない**。難易度の校正、生成問題の品質、プレイ評価やモード設計が差別化要因になる。

### 判定

**実装候補に採用。**

採用条件として、初期実装では次を前提にする。

1. 直交格子の完全迷路を基準にする。
2. 盤面全体を表示する初期規模は10×10〜15×15程度を中心にする。
3. 盤面上のスワイプを主操作候補とし、直接の小マスタップへ依存しない。
4. 難易度は盤面サイズだけで決めず、生成方式・開始/ゴール・構造特徴量・棄却条件で制御する。
5. 最終難易度と面白さはプレイログで校正する。

## ヒント・やり直し

完全迷路なら正解経路が一意なので、現在地から次の正しい方向や数マス分の経路を安価に提示できる。

通常の迷路では一歩戻ること自体が合法な探索行動なので、専用の「元に戻す」は必須ではない。実移動距離を記録すれば迷いや戻りを自然に観測できる。やり直しは開始点へ戻す操作として扱える。
