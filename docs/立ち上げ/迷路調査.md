# 迷路の導入成立性調査

Issue #42 の調査結果。

## 結論

迷路は pa-zzle の **実装候補に採用する**。

- ゲート1 問題供給成立性: **通過**。完全迷路なら可解性・一意経路を構成上保証でき、生成・探索性能と多様性に致命的な問題はない。
- ゲート2 難易度運用成立性: **通過**。生成方式・開始/ゴール・特徴量棄却で構造特性の異なる問題群を作り分けられる。詳細は [迷路の難易度制御可能性調査](./迷路難易度調査.md) を参照。
- ゲート3 スマホプレイ成立性: **通過**。10×10〜15×15程度の全体表示と盤面上のスワイプ操作を初期候補とする。
- ゲート4 導入判断: **実装候補に採用**。20×20以上の表示、最終難易度式、長期的な面白さは未確定事項として残す。

## ゲート1: 問題供給成立性

### 基本仕様

初期実装は **長方形の直交格子による完全迷路** を基準とする。

- 1マスを頂点とする。
- 上下左右に壁がなく隣接するマス間を辺とする。
- 1回の移動は隣接する1マスへの移動とする。
- 開始点とゴールを1つずつ持つ。
- 開始点からゴールへ到達した時点でクリアとする。
- 全マスが連結し、閉路を持たない完全迷路を基準とする。

完全迷路の通路グラフは全域木なので、任意の2マス間に経路がちょうど1つ存在する。生成した時点で開始点からゴールへの到達可能性と経路の一意性を保証できる。

多経路迷路も完全迷路へ辺を追加すれば生成できるが、最短経路以外の経路や難易度指標の意味が変わるため、初期実装では完全迷路に限定する。

### 生成方式

| 方式 | 特徴 | 初期用途 |
|---|---|---|
| ランダム化深さ優先探索 | 長い通路が生まれやすく、正解経路も長くなりやすい | 性質の異なる問題生成候補 |
| ランダム化Prim法 | 分岐や袋小路が多く、比較的短い通路が密に出やすい | 実装が簡単な基準候補 |
| ランダム化Kruskal法 | Union-Findで扱いやすく、全域木を直接構成できる | 追加候補 |
| Wilson法 | ループ消去ランダムウォークで一様全域木を生成する | 偏りの少ない比較基準 |
| Aldous-Broder法 | ランダムウォークから一様全域木を生成する | 理論上の基準 |

1種類へ固定せず、複数方式を同じ盤面表現へ出力し、後段の難易度・品質評価で選別できる構成がよい。

### 解法探索

通常の格子迷路は重みなしグラフとして扱えるため、幅優先探索で最短経路を求められる。

- 頂点数を `V`、辺数を `E` とすると `O(V + E)`。
- 完全迷路では `E = V - 1` なので実質線形。
- 完全迷路では開始点とゴールの間に1本しか経路がないため、その経路が最短経路になる。

### 生成・探索実験

Python の単純実装で確認した。最適化した本番コードの性能測定ではなく、方式間の傾向と桁感を見るための値。

#### 20×20、各300問

| 方式 | 生成時間平均 | 開始→ゴール経路長平均 | 正解経路上の分岐平均 | 全袋小路数平均 |
|---|---:|---:|---:|---:|
| 深さ優先探索 | 0.82 ms | 121.3 | 12.6 | 42.3 |
| Prim法 | 0.69 ms | 43.0 | 24.9 | 129.5 |
| Wilson法 | 4.40 ms | 59.4 | 28.3 | 116.1 |

#### 40×40、各100問

| 方式 | 生成時間平均 | 開始→ゴール経路長平均 | 正解経路上の分岐平均 | 全袋小路数平均 |
|---|---:|---:|---:|---:|
| 深さ優先探索 | 3.89 ms | 367.3 | 31.3 | 164.3 |
| Prim法 | 2.86 ms | 89.4 | 54.1 | 514.3 |
| Wilson法 | 28.20 ms | 142.3 | 69.8 | 468.4 |

Prim法で生成した完全迷路を幅優先探索した平均時間:

| 盤面 | 平均探索時間 |
|---|---:|
| 20×20 | 0.11 ms |
| 40×40 | 0.45 ms |
| 80×80 | 1.90 ms |
| 160×160 | 11.90 ms |

各サンプル集合内では生成結果のハッシュ重複はなかった。重複が存在しない証明ではないが、通常利用で多様性が即座に枯渇する兆候はない。

回転・反転を同一問題として除外したい場合は、各変換後の盤面表現から代表表現を決め、そのハッシュを保存すればよい。厳密なグラフ同型判定は初期段階では不要。

**ゲート1判定: 通過。**

## ゲート2: 難易度運用成立性

詳細な追加実験は [迷路の難易度制御可能性調査](./迷路難易度調査.md) に分離した。

追加実験ではスマホ想定の10×10・15×15を各方式5,000問生成し、以下を確認した。

- 同じ15×15でも、深さ優先探索は「長いが分岐が少ない」、Prim法は「短いが分岐が多い」という異なる構造分布を作れる。
- 15×15の外周対向辺から開始点・ゴールを選ぶと、同一盤面でも経路長と分岐数を広く動かせる。
- 特徴量による棄却で「短距離・判断少なめ」「短距離・判断多め」「長距離・深い誤経路」のような異なる構造帯を実際に抽出できる。
- 最も採択率の低かった仮条件でも4.8%で、生成性能上は継続供給可能。

最短距離と意思決定量は単調に連動しないため、盤面サイズや単一特徴量をそのまま難易度としない。生成側では構造特性の異なる問題群を供給し、最終的な難易度ラベルはクリア時間、超過移動距離、戻り量、離脱等のプレイログで校正する。

**ゲート2判定: 通過。** 狙った構造帯を生成側で再現・供給できることを実験で確認した。実ユーザーによる最終難易度校正はこのIssueでは行わない。

## ゲート3: スマホプレイ成立性

### 既存事例

スマホ向け迷路で「盤面上の小さい1マスを毎回タップする」方式に限定する必要はない。

- **Mazes & More** は iPhone / Android でスワイプまたはタップによる操作を提供し、Google Play では5,000万以上のダウンロード実績がある。設定でタップ・スワイプ操作を選択できる。
- **Maze Swipe** や **Swipe Mazes** など、スワイプを主操作にした迷路ゲームも存在する。

既存事例から、少なくともスワイプ操作自体はスマホ迷路で実績のある方式と判断できる。

### 操作方式の比較

| 方式 | 長所 | 主な問題 | 初期候補 |
|---|---|---|---|
| 経路を指でなぞる | 直感的で速い | 指で先が隠れる。細い通路で精度が必要 | ○ |
| スワイプで進む | 盤面上で完結し、セル自体を正確にタップしなくてよい | ページスクロール等との競合対策が必要 | **◎** |
| 方向入力 | 誤操作を抑えやすい。指で盤面を隠さない | 画面領域を消費。長い通路では入力回数が増える | ○ |
| 目的地タップ | 長い一本道を高速移動できる | どこまで自動移動するかという別ルールが必要 | △ |

初期候補は **盤面上のスワイプ**。必要なら方向入力を代替操作として用意できる構成がよい。

### ブラウザーとのジェスチャー競合

Pointer Events と CSS の `touch-action` を使えば、迷路盤面内のドラッグ・スワイプをアプリ側で扱い、ページのパン等との競合を抑制できる。

ただし、画面端から始まるOS・ブラウザー固有の戻るジェスチャーはWebページ側だけで完全制御できない場合がある。盤面を画面端へ密着させず余白を持たせ、主要操作を端から開始させない方が安全。

WCAG 2.2 の Dragging Movements はドラッグ操作に単一ポインターの代替を求め、Target Size (Minimum) はポインター入力対象に24×24 CSS px以上を原則として求める。したがって、スワイプだけを唯一の操作に固定するより、方向入力等を代替可能にしておく方がよい。

### 盤面サイズの最小操作試作

既存フロントエンドへ本実装を入れる前に、調査用の単一HTMLで以下だけを試作した。

- 迷路の壁と通路を描画
- 開始点・ゴールを表示
- 盤面上のポインター移動で隣接セルへ連続移動
- 上下左右の方向入力
- 盤面に `touch-action: none` を設定

Chromium を **390×844 CSS px、タッチ入力有効** のスマホ相当条件で描画・操作した。

盤面表示幅を約360pxとした場合:

| 盤面 | 1マスの幅 | 確認結果 |
|---|---:|---|
| 10×10 | 約36px | 壁・通路・現在地を十分識別できる |
| 15×15 | 約24px | 全体表示を維持でき、経路を追える |
| 20×20 | 約18px | 描画自体は可能だが、通路密度が上がり視認性低下が明確 |

方向入力は44px以上の押下領域で操作できた。盤面上の連続入力も動作し、確認中に `pageerror` と意図しない `console.error` は発生しなかった。

この確認から、**10×10〜15×15程度なら全体表示のままスマホで遊ぶ方式が成立する見込みが高い**。20×20以上は生成性能ではなく視認性が先に制約になるため、拡大・スクロールを導入するか、採用盤面サイズから外すかを別途判断する。

拡大・スクロールは迷路操作と同じ指ジェスチャーを奪うため、初期仕様では「盤面全体を一画面に収める」方を優先する。

### 行き止まり・戻り・やり直し

完全迷路では行き止まりから来た道を戻ること自体が探索の一部なので、専用の「元に戻す」は必須ではない。スワイプ・方向入力のどちらでも逆方向へ移動できる。

やり直しは開始点へ戻す独立操作として用意できる。プレイ評価では、最短距離とは別に実移動距離を記録すれば、誤経路への進入と戻りを自然に観測できる。

**ゲート3判定: 通過。** 10×10〜15×15程度を全体表示し、盤面上のスワイプを主操作とする方式が成立する。方向入力を代替操作にできる。20×20以上は無条件に成立とは扱わない。

## ゲート4: 導入判断

### 市場・実装・保守の観点

- 市場: スマホ向け迷路アプリに大規模ダウンロード実績があり、操作方式の前例もある。
- 問題供給: 完全迷路なら生成・可解性保証・最短経路計算が単純で、大量供給しやすい。
- 難易度: 単純なサイズ依存ではないが、生成方式・端点選択・特徴量棄却で構造帯を制御できる。
- 実装量: 盤面生成、幅優先探索、描画、入力処理が中心で、外部コンテンツや巨大な問題データを必要としない。
- 保守: パズル固有の主要部分がグラフ生成・特徴量計測・入力処理に閉じやすい。
- pa-zzleとの差異化: クリア時間だけでなく、最短距離との差、戻り量、ヒント等を共通のプレイ成績へ載せやすい。

懸念は、盤面を大きくしたときの視認性と、「生成できる」ことが長期的な面白さを保証しない点。前者は初期盤面サイズを制限でき、後者は実装後のプレイ評価で確認する問題であり、現時点で導入を止める未知ではない。

### 判断

**実装候補に採用。**

初期条件:

- 長方形の直交格子による完全迷路
- 10×10〜15×15程度を主要な盤面候補とする
- 全体表示を優先し、初期段階では拡大・スクロール前提にしない
- 盤面上のスワイプを主操作候補とし、方向入力を代替可能にする
- 難易度は単一指標で固定せず、構造特徴量を保存して校正可能にする

実装前に独立した追加PoCを必要とする未知は残っていない。

## この調査で確定しないこと

- 最終的な難易度区分・閾値・算出式
- 大量の実ユーザーデータを使った難易度校正
- 完成UIの見た目・アニメーション・演出
- 最終的なプレイ評価式
- 20×20以上を正式対応するか
- 保存・API・DB等の本番設計
- 共通ゲーム契約の最終形
- 本番品質の生成器・解法器の実装詳細
