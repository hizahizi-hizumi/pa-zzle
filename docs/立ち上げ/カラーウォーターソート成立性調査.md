# カラーウォーターソート 基礎仕様・自動生成成立性調査

Issue #27 の調査結果。カラーウォーターソートを本番運用を想定して実装する前提として、変えにくい基礎仕様、自動生成、最短解探索、計算量、多様性、難易度制御への発展余地を整理する。

## 結論

カラーウォーターソートは pa-zzle の対象パズルとして **GO** と判断する。

- 基礎ルールは固定容量のスタックとして明確に定義できる。
- 標準初期盤面は「色数と同数の満杯ボトル + 空ボトル2本」とする。
- 各色はボトル容量と同じ4単位を持つ。
- 問題生成は **標準形を乱数で生成し、最短解探索器で可解性と品質を確認して採用する方式** を第一候補とする。
- 最短手数は状態空間探索で算出可能。試作 A* では 3〜8色は十分小さく、9〜10色は実装言語での再測定が必要、11〜12色は秒単位の外れ値を前提に事前生成・キャッシュ・非同期化・探索最適化を視野に入れるべき領域だった。
- 完成状態からの逆生成は可解性を構成的に保証できるが、水の移動は一般に不可逆なので「通常の合法手を逆向きに行う」だけでは成立しない。逆遷移専用の生成処理が必要で、初期盤面の分布制御も複雑になるため第一候補にはしない。
- 難易度制御は、最短手数だけでなく分岐数・強制手・行き止まり・空き容量圧力などの探索指標を使って後続 #32 で検証できる。

最終的な難易度区分・プレイ評価式・UI詳細はこの調査では固定しない。

## 1. 採用する基礎仕様

### 1.1 盤面

- ボトル容量は4単位とする。
- 色数を `n` としたとき、初期盤面は以下とする。
  - 色入りボトル: `n` 本
  - 空ボトル: 2本
  - 合計: `n + 2` 本
- 各色は正確に4単位存在する。
- 初期の色入りボトルは4単位すべて埋まっている。
- 色入りボトルが最初から単色完成している盤面は生成時に棄却してよい。これは可解性ではなく、問題としての自明さを避ける品質条件として扱う。
- ボトルの位置そのものには意味を持たせない。状態探索ではボトル順を正規化して同型状態をまとめられる。

この「満杯 `n` 本 + 空2本」という初期形は、計算量研究で扱われる Water Sort Puzzle の定式化とも整合する。

### 1.2 注水可能条件

送信元 `source` から送信先 `destination` へ注げるのは、すべて次を満たす場合とする。

1. `source` が空ではない。
2. `destination` が満杯ではない。
3. `destination` が空、または `destination` の最上段の色が `source` の最上段の色と同じ。

### 1.3 1回の操作で移動する量

`source` 最上段から連続している同色部分を、`destination` の空き容量の範囲で **可能な限りまとめて移動する**。

例:

```text
source      destination
[A B B B]   [C B _ _]
```

上段を右端とすると、`source` 上部には B が3単位連続しているが、`destination` の空きは2単位なので2単位だけ移動する。

プレイヤーが移動量を任意に指定する仕様にはしない。

### 1.4 1手の定義

- 送信元と送信先を1回選び、規則に従った注水が成立したものを **1手** とする。
- 一度に1〜4単位移動しても1手である。
- 送信元を選んだだけ、同じボトルを再選択して解除しただけ、注水不成立の操作は手数に含めない。

この定義により、最短手数は状態グラフ上の最短経路長として扱える。

### 1.5 完成済みボトル

4単位すべて同色のボトルを完成済みとする。

pa-zzle では完成済みボトルからの注水を UI 上禁止してよい。通常ルールで完成済み4単位を空ボトルへ注ぐと、色入りボトルと空ボトルの位置が入れ替わるだけで、ボトル位置を区別しない状態としては同値だからである。

ゲームロジック側では、完成済みボトルを「ロックされた別種の状態」にする必要はない。完成判定から導出し、探索では完成ボトル→空ボトルの同値遷移を枝刈りする。

### 1.6 クリア条件

すべてのボトルが次のどちらかになったときクリアとする。

- 空
- 容量4まで満たされ、4単位すべて同色

各色が4単位、総量が `4n` と保存されるため、標準盤面では最終的に `n` 本の完成ボトルと2本の空ボトルになる。

## 2. 妥当な盤面と解ける盤面を分ける

初期盤面の静的な妥当性は、少なくとも次で判定できる。

- 各ボトルの要素数が0〜4。
- 初期盤面では色入りボトルが満杯、空ボトルが2本。
- 各色がちょうど4単位。
- 未知の色・欠損・過剰要素がない。

ただし、これらを満たすことと **解が存在することは別** である。

Water Sort Puzzle の一般化問題は NP 完全であり、論文でも「初期配置が可解か」を独立した判定問題として扱っている。したがって、生成器は色数や個数条件だけを見て可解とみなしてはいけない。

空ボトル2本については今回の試作標本では高い可解性を示したが、今回の条件全体に対する数学的保証として扱わない。生成時には探索器による可解性確認を残す。

## 3. 問題生成方式

### 3.1 第一候補: ランダム標準盤面 + 探索 + 棄却

採用候補の生成パイプラインは以下。

```text
seed
  ↓
各色4単位の配列を作る
  ↓
seed付き乱数でシャッフル
  ↓
4単位ずつ n 本のボトルへ分配
  ↓
空ボトル2本を追加
  ↓
静的妥当性・自明盤面を検査
  ↓
最短解探索
  ↓
可解性・最短手数・探索指標で採用 / 棄却
  ↓
問題確定
```

利点:

- 最初から標準初期形を満たす。
- seed から再現可能にできる。
- 生成器と探索器の責務が分離しやすい。
- 可解性確認と同じ探索結果から最短手数・難易度候補指標を得られる。
- 生成分布を後から制御しやすい。

欠点:

- 解けない盤面や品質の低い盤面を生成する可能性があるため棄却が必要。
- 色数が増えると探索時間が生成時間に直結する。

今回の標本では空ボトル2本のランダム盤面695件すべてが可解だったが、これは経験的結果であり保証ではない。可解性確認を省略する根拠にはしない。

### 3.2 代替案: 完成状態から逆遷移を構成する

可解性を構成的に保証する方法として、完成状態から「前向きの合法手で必ず元に戻せる前状態」を作る逆遷移生成がある。

ただし Water Sort の注水は一般に不可逆である。同色の水を一度まとめると任意量へ分割できないため、15パズルのように通常の合法手をそのまま逆方向へ適用することはできない。

逆生成する場合は、各候補前状態について

```text
候補前状態 --通常の合法手--> 現在状態
```

が成立することを確認しながら前状態を構成する必要がある。

今回の試作では、逆遷移ランダムウォークから「色入りボトルがすべて満杯 + 空2本」の標準初期形へ戻る状態はまれで、標準形だけを出力するには追加の制御が必要だった。また、逆操作回数は最短手数ではなく、生成経路の長さにすぎない。

そのため現時点では第一候補にしない。ただし、高難易度盤面を意図的に構成したい場合や、ランダム + 棄却方式の棄却率が将来問題になった場合の代替案として残す。

## 4. 解法探索と最短手数

### 4.1 状態表現

探索時の状態は各ボトルを「底→上」の色列として持てば十分。

```text
(
  (A, B, B, C),
  (C, A, D, A),
  ...,
  (),
  (),
)
```

ボトルの位置に意味がないため、各ボトル列をソートした正規形に変換することで、位置交換だけの同型状態を1状態へまとめられる。

### 4.2 探索方式

最短手数が必要なので、候補は以下。

- 幅優先探索: 最短性は明快だが状態数の増加に弱い。
- Dijkstra: 全遷移コストが1なので、この問題では幅優先探索と本質的に同じ。
- A*: 許容的な下界を与えれば最短性を保ったまま探索量を削減できる。
- IDA*: メモリ制約が厳しい場合の候補。

PoC の第一候補は A* とする。

### 4.3 試作 A* の下界

各ボトル内の連続同色部分を「色ブロック」と呼ぶ。

```text
[A A B C C] -> 3ブロック
```

全ボトルの色ブロック数を `B`、色数を `C` としたとき、

```text
h(state) = B - C
```

を下界として使った。

ゴールでは各色が1ブロックなので `B = C`。1手の注水で減らせる色ブロック数は最大1なので、残り手数は少なくとも `B - C`。したがってこの値は最短手数を過大評価しない。

この下界は強力ではないが、正しさ確認と成立性測定には十分だった。後続実装では追加下界・枝刈りを比較してよい。

### 4.4 最短性の確認

2〜4色のランダム盤面30件について、試作 A* の結果を全幅探索の最短距離と比較し、30件すべて一致した。

これは試作実装の検算であり、後続の本実装では独立したテストを持つ。

## 5. 実測

### 5.1 条件

- 容量: 4
- 空ボトル: 2
- 各色: 4単位
- 初期色入りボトル: すべて満杯
- 初期完成ボトルは生成時に棄却
- 乱数 seed: 最短性検算 `2026091501`、空2本 `2026091500 + 色数`、空1本 `2026091600 + 色数`
- 探索: A*
- 状態正規化: ボトル順を無視
- 枝刈り: 完成済み単色ボトル→空ボトルなど、状態として同値になる遷移を除外
- 下界: 色ブロック数 - 色数
- 実行環境: Python 3.13.5 / Linux x86_64 / ChatGPT 実行環境

数値は本番性能保証ではなく、アルゴリズム成立性と増加傾向を見るための参考値である。11〜12色は標本数が少ないため95%点を出さない。実験コードは製品実装ではないため残さず、後続 #30 では TypeScript 実装を独立に検証する。

### 5.3 空ボトル1本との比較

同じ生成法で空ボトルだけ1本にすると、探索を完走して「解なし」と判定される盤面が多数発生した。

| 色数 | 標本 | 可解 | 解なし |
|---:|---:|---:|---:|
| 3 | 100 | 77 | 23 |
| 4 | 100 | 52 | 48 |
| 5 | 100 | 24 | 76 |
| 6 | 60 | 6 | 54 |
| 7 | 30 | 0 | 30 |

空ボトル数は単なる表示上の差ではなく、可解性と探索空間を大きく変える基礎仕様である。pa-zzle の標準ルールは2本で固定する。

## 6. サービスとしての問題生成

### 6.1 再現性

問題生成は seed を入力として決定論的にする。

保存・共有・不具合再現に必要なのは最低限次の情報。

- 生成器の版
- seed
- 色数
- ボトル容量
- 空ボトル数
- 必要なら採用時の最短手数・難易度指標

同じ seed でも生成器の変更で盤面が変わり得るため、seed 単体を永続的な問題IDとして扱わない。

### 6.2 多様性

ランダム標準盤面は色4単位をシャッフルして分配するため、候補空間は十分大きい。実際の多様性を損なう主因は候補数そのものより、次になる。

- 色名の置換だけで同型な盤面
- ボトル順の置換だけで同型な盤面
- 最短解がほぼ同じ構造の盤面
- 特定の最短手数帯へ偏る生成条件

したがって、継続供給では seed の重複回避だけでなく、正規化盤面の重複排除と難易度指標の分布監視を行う余地を残す。

### 6.3 生成場所

PoC では生成・探索ロジックを UI から分離した純粋ロジックとして実装する。

ただし 10色超では秒単位の探索があり得るため、「ブラウザのメインスレッドで毎回生成する」ことを設計前提にはしない。

後続実装では次を測定して決める。

- TypeScript 実装での探索性能
- Web Worker へ逃がした場合の操作感
- サーバー生成 / 事前生成した場合の運用コスト
- 問題キャッシュのヒット率

初期 PoC は小〜中規模盤面を即時生成できる構成にしつつ、生成処理の呼び出し境界は後から非同期化できる形にする。

## 7. 難易度制御への発展余地

最短手数だけでは人間の難しさを十分表さない可能性が高い。

後続 #32 で少なくとも次を候補として記録できる。

- 最短手数
- 探索で展開した状態数
- 各状態の合法手数
- 最適解上の平均分岐数
- 強制手の割合
- 最適経路から外れる合法手の数
- 行き止まりへ到達する選択肢の数
- 空ボトルが両方埋まる局面の有無・長さ
- 一度まとめた色を再度分ける必要があるか
- 一時的に完成に近いまとまりを崩す必要があるか

探索器内部の展開状態数はアルゴリズム実装に依存するので、それ自体を難易度の正本にしてはいけない。盤面固有の指標と実プレイデータを優先し、探索器依存指標は補助情報として扱う。

今回の実測では色数が増えるほど最短手数中央値も増えたが、色数だけで難易度を決める根拠にはしない。

## 8. Undo・やり直し・ヒントとの境界

これらはゲームの状態遷移規則とは分ける。

### Undo

- 直前の成立した注水前の盤面へ戻す。
- Undo 自体は新しい「注水手」ではない。
- `undoCount` は注水手数とは別の生データとして記録する。
- Undo 後に別の手を選んだ場合は、その時点から新しい履歴として進める。
- `moveCount` を現在経路長として減算するか、試行中の実操作数として累積するかは基礎ルールでは決めず、#31 / #32 で成績の意味に合わせて固定する。

### やり直し

- 同じ問題・同じ seed の初期盤面へ戻す操作とする。
- `restartCount` は注水手数とは別の生データとして記録する。
- 手数・経過時間をリセットするか累積するかは基礎ルールでは決めず、#31 / #32 で「1プレイ」の境界と合わせて固定する。

### ヒント

- 基礎ルールではない。
- 最短解探索器を利用して「次の1手候補」を返せる。
- ヒント表示だけなら状態を変更しない。
- `hintCount` を記録できるようにする。
- ヒントの見せ方・自動実行有無は後続で決める。

## 9. 後続実装で守る不変条件

- UI がゲームルールを独自実装しない。
- `applyMove` は同じ入力状態と手に対して同じ結果を返す。
- 問題生成は seed から再現可能にする。
- 最短手数とプレイヤー手数で「1手」の定義を共有する。
- 可解性を色数・空ボトル数だけから推測しない。
- 完成ボトルの UI ロックを、別のゲーム規則として探索器へ混ぜない。
- 難易度式を生成器へ埋め込まず、生成候補の指標と採用ポリシーを分離する。
