# PoC知見台帳

## 目的

この文書は、PoCで得た知見を「今後の pa-zzle がどうあるべきか」という正の振る舞いとして棚卸しし、適切な正本・要件・設計へ移すための作業台帳である。

Issue、PR、調査文書、コード、テスト、実測は結論そのものではなく、各知見の根拠として扱う。PoC中の試行錯誤や不採用案を本文の主題にはせず、必要な場合だけ根拠から追跡できるようにする。

この文書自体は長期的な仕様の正本ではない。各項目は正本化・要件化・設計反映が完了したら、その参照先を正として扱う。

## 台帳の読み方

確度:
- 確定: 複数の実装・実プレイ・正本で確認でき、今後の前提として扱える。
- 有力: PoC上の根拠は強いが、要件・設計の確定または追加の横断確認が必要。
- 要検証: 仮説または特定ゲームでの成立までで、人間校正・実プレイ・別ゲーム比較等が残る。

扱い:
- 既存の正で十分: 文書、コーディング規約、Skill、チェックリスト、レビュー手順、コード上の型・API・テスト契約など、責務に合う既存の場所がすでに正を保持している。重複して別の正を作らない。
- 後続Issue所有: 要件・設計・規約・画面・語彙等を確定する既存Issueが責務を持つ。Issue自体は正ではなく、完了時に責務に合う文書・規約・コード契約へ反映する。
- 検証待ち: 実プレイ・人間校正・別ゲーム比較等が終わるまで結論自体を確定しない。

正の種別:
- 体験・デザイン・画面等の仕様は、その責務の正本文書で所有する。
- 実装者が繰り返し守る構造上の原則は、設計確定後にコーディング規約へ落とす。
- 型、API、状態遷移、ゲーム固有ルール等の正確な契約は、コードとその契約テストを正とする。
- 特定作業を繰り返す実行手順は Skill、判断観点だけを繰り返し使うものはチェックリスト、実画面の確認工程はレビュー手順で所有する。
- PoC調査文書やADRは根拠・判断理由であり、現在仕様そのものの正にはしない。

## 正本化・後続作業の優先順

1. 正本化済み 62 件は、文書・チェックリスト・レビュー手順・Skill・コード契約など現在の所有先を正として扱い、重複記述を増やさない。
2. 後続Issue所有 60 件は、Issue完了時に要件・設計・コーディング規約・画面正本・語彙正本・コード契約など責務に合う正へ反映する。
3. 検証待ち 4 件は、追加検証が終わるまで正本化しない。

## この台帳で正本化しないもの

- PoC中の一時的な閾値、計測環境依存の性能値、仮の配色・演出値。
- 特定PRの実装手順や修正経緯。
- 不採用案そのもの。必要な判断理由は根拠Issue / PR / 調査文書から辿る。
- 後続Issueで確定すべき要件・設計・コーディング規約・画面正本・語彙正本等を、この台帳だけを根拠に先取りした完成仕様。
