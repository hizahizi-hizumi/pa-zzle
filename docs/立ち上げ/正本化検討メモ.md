# 正本化検討メモ

この文書は、`APP.md` / `GAME.md` / `DESIGN.md` を長期的な正本として整理する過程で、正本から外した判断経緯、検証方針、具体例、後続Issueへの引き継ぎを残すための立ち上げ期の作業資料である。

現在有効な仕様は、必ずルートの `APP.md` / `GAME.md` / `DESIGN.md` と `frontend/styles/globals.css` の `@theme` を参照する。この文書はそれらを上書きしない。

未実施の作業はこの文書だけで管理しない。実行すると決めたものはIssueへ移し、以後の進捗管理はIssueを正とする。この文書に残す未確定事項は、再検討条件または受け皿が明確なものに限る。

## 1. 正本化の考え方

正本には「現在どうするか」を置き、次の情報は立ち上げ資料側へ残す。

- PoCでどのように判断へ到達したか
- 採用前の候補や比較対象
- 正本へ昇格しなかった理由
- 実プレイで確認した検証観点
- 特定ゲームで得た具体例
- 後続Issueへ引き継いだ論点

正本から記述を外すことは、その検討自体を無かったことにすることを意味しない。判断が確定した場合は正本を更新し、この文書は立ち上げ時の経緯として残す。

## 2. APP.md に関する検討

### 2.1 ゲーム一覧

ゲーム一覧は、汎用アイコンと説明文だけでゲームを代表させるよりも、そのゲームで実際に見る・触るものをゲームの顔として扱う方向で検証する。

たとえば、ウォーターソートなら色水と容器、ナンプレなら盤面と数字のように、ゲーム固有の視覚言語を一覧用に縮約する。

説明文は必要な場合に補助として使い、視覚表現そのものの代わりにはしない。

ただし、どの程度まで盤面やゲームオブジェクトを見せると選びやすいか、ゲーム数が増えたときに一覧性を保てるかは実画面で確認する必要がある。具体的な一覧再設計は Issue #77 でPoCとして扱う。

参考にした「世界のアソビ大全51」の考え方も、3Dの玩具表現を模倣することではなく、ゲームを抽象的な汎用アイコンへ置き換えず、盤・駒・サイコロなどゲーム自身の視覚表現で選ばせる点にある。

### 2.2 共通のプレイ評価

ここでいう共通のプレイ評価は、各ゲームの1プレイを `n/100` のように「高いほど、そのゲームにおいてよいプレイ」として返す評価を指す。

ウォーターソートでは一回のプレイ結果を即時の報酬として返す評価点が有効だった。ナンプレを含め、異なるゲームでも同じ評価契約を成立させられるかは Issue #8 で検証する。

ゲーム間で点数を直接比較できること、複数ゲームを集約した総合評価、長期的な利用者レーティングまではこの評価の意味に含めない。

### 2.3 当初検討したが追わない案

立ち上げ時には次の案も候補として考えたが、2026-09-17 の棚卸しで独立した要件・バックログとして追わないことにした。

- ゲーム間で直接比較可能な共通スコア
- 複数ゲームを横断した総合評価
- ランキングや競争を中心とした体験
- ゲーム一覧のおすすめ・継続要素
- 全ゲーム共通のプレイモード

必要性が将来あらためて発生した場合は、その時点の利用体験から新しく要件化する。現在の保留事項としては扱わない。

### 2.4 プレイ履歴

プレイ履歴そのものは作る方針とし、Issue #92 へ移した。

履歴の保存単位、クリア・途中終了・やり直しの扱い、ゲーム共通情報とゲーム固有情報の境界などは、履歴機能の要件として #92 で決める。

自己ベストの具体的な判定・表示は、この文書の独立した棚上げ項目としては追わない。プレイ評価側で必要になる範囲は Issue #8 の文脈で扱う。

### 2.5 内部識別子を通常UIへ出さない理由

PoCではseedが問題の再現に必要だったが、それだけを理由に通常UIへ出すと利用者にとって意味のない情報になる。

共有や公開問題IDなどの具体機能は現在のバックログとして追わない。将来その利用目的が発生した場合も、内部seedをそのまま公開契約にすることを前提にせず、その時点の目的に合う識別方法を検討する。

## 3. GAME.md に関する検討

### 3.1 原則の出所と更新

ゲーム体験原則は、机上で先に固定したものではなく、実際にゲームを実装し、遊び、改善するPoCから得た知見を優先して整理した。

ウォーターソートだけで全ゲームの原則を完成させたとは考えず、後続ゲームで再利用できる知見が確認されたときに正本を追加・修正する考え方で運用する。

この「原則は増減しうる」という制作上の前提は正本の仕様そのものではないため、`GAME.md` からは外した。

### 3.2 実プレイによる検証

ゲーム体験は単一画面の見た目だけでは判断しない。開始から複数手を操作し、クリアして次の行動へ進むまで連続して遊ぶ。

PoCでは主に次を確認する。

- プレイ対象が画面の主役になっているか
- UIがプレイヤーの判断を先回りしていないか
- 操作結果を自然に理解できるか
- 複数操作を続けたときのテンポが成立しているか
- アニメーション途中でも操作対象や状態変化が破綻しないか
- プレイ中の情報と結果・診断情報が分離されているか
- 難易度ラベルが実際の体験として意味を持つか
- クリア時に達成と次の行動が自然に伝わるか

正本ではこれらを「ゲームとしての成立条件」として記載し、検証手順としての文脈はこの文書に残す。

### 3.3 題材と視覚表現の具体例

ウォーターソートでは、単なる色ブロックではなく「液体を容器間で注ぐ」ことが見た目と操作から理解できる必要があった。

数字パズルでは、数字と盤面を読むことそのものが題材になる。

この具体例から、内部データ構造をそのまま表示するのではなく「プレイヤーが何を操作していると感じるゲームか」から表現を設計する原則へ抽象化した。

### 3.4 難易度の校正

盤面サイズ、色数、最短手数などの機械的な特徴量だけでは、利用者向けの難易度ラベルを確定できない。

PoCでは、各難易度がどの程度の判断、先読み、試行錯誤、失敗可能性を要求するかを考え、想定する熟練度のプレイヤーが実際に解いた感覚と照らして校正する。

機械的な難易度指数は問題生成・選別には利用できるが、ラベルの妥当性は実プレイで確認する、という役割分担を想定している。

カラーウォーターソートの具体的な難易度再設計は Issue #69 で処理しており、この文書の棚上げ項目ではない。後続ゲームの具体的な難易度式・閾値も、それぞれのゲーム開発で扱う。

### 3.5 結果と称賛

ウォーターソートでは、評価点を診断値の一つとして扱うより、結果画面の主要情報として返す方がプレイ後の報酬として機能した。

また、高い評価ほど色、動き、メッセージなどの称賛を強くする方向を試した。ただし、100点・90点台・80点台などPoCで使った具体的な閾値や演出強度はウォーターソート固有の検証値であり、全ゲーム共通仕様ではない。

「評価式がまだ調整中であること」と「何をプレイヤーへ褒めて返すか」は別の問題として考える。

評価式・閾値は各ゲーム側で扱い、評価結果をどのような称賛・報酬として返すかは MVP前PoC の Issue #93 で横断的に検証する。

## 4. DESIGN.md に関する検討

### 4.1 アクセシビリティ

立ち上げ時点では、アクセシビリティを最初から設計・実装範囲へ広げられるだけの開発資源を割かない方針とした。

そのため正本では、アクセシビリティをpa-zzleのデザイン要件に含めず、ブラウザ標準の意味付けや操作性は意図的に壊さない、という現在の扱いだけを記載している。

### 4.2 ブランド色と primary

`primary` は主要操作の優先順位を表す意味トークンとして扱い、ブランド色とは結び付けない。

ブランド色は当初、視覚人格「ミニマルで静か」だけから色相まで一意に決める根拠が不足していたため固定しなかった。

その後、ゲーム固有色を邪魔せず、共通UIに上質さと識別性を与える方向としてシルバーを検討した。ニュートラルな Quiet Silver と、わずかに青みを持つ Cool Silver を同一のゲーム一覧・プレイ・結果画面で比較し、Cool Silver を採用した。

採用理由は、Quiet Silver よりブランドとして認識できる輪郭がありながら、ゲーム固有色や結果画面の報酬色より前へ出ず、「ミニマルで静か」という視覚人格を保てたためである。具体値は `frontend/styles/globals.css` の `@theme` を正本とする。

ブランドトークンの既存画面への適用は Issue #94 へ移した。これは検討保留ではなく、定義済みトークンを実装へ反映する後続作業として扱う。

### 4.3 success と報酬を分ける理由

`success` は処理や操作の成立・完了、ゲームのクリアなど、成功した状態を表すために使う。

一方、高得点、自己ベスト、特によいプレイなどの称賛は「成功したか」だけでは表せない。単一の緑色へ還元すると、結果画面で返したい報酬の強弱やゲーム固有性を失う。

そのため `achievement` のような単一の共通色トークンは追加せず、結果名、スコア、過去との比較、ゲーム固有表現、色、動きなどを組み合わせる方向にした。

具体的な称賛・報酬表現は Issue #93 で検証する。

### 4.4 error と destructive を分ける理由

`error` は入力不備、処理失敗、アプリ上の異常など「起きた問題」の状態を表す。

`destructive` はリセットや削除など「利用者が選択する操作の性質」を表す。

現在の具体的な色値が同じでも意味は別であり、片方の表現だけを変更する必要が生じても意味を混同しないため、意味トークンを分離した。

### 4.5 共通部品を先に固定しない

`AppShell`、`PageHeader`、`Button`、`Card` など既存の共通部品は再利用可能な実装として存在するが、存在すること自体を全画面で使うデザイン契約にはしない。

フォーム、メニュー、ダイアログ、結果専用部品、通知なども「デザインシステムにありそうだから」という理由で先に契約化しない。複数画面で同じ意味と振る舞いが確認できたものを共通化する。

特にプレイ画面では、共通部品の統一よりゲーム体験を優先する。

将来の共通UI抽出そのものをバックログには置かない。実際に同じ契約が必要になった時点で共通化を判断する。

### 4.6 デザイン判断の検討順序

#73の整理では、次の順で判断する考え方を使った。

1. `APP.md` / `GAME.md` で守る体験を確認する。
2. `DESIGN.md` で視覚的優先順位、表現強度、色、面、文字、動きへ翻訳する。
3. 既存の `@theme` で同じ意味を表せるか確認する。
4. 既存トークンでは別の意味を混同する場合だけ、新しい意味を定義する。
5. 同じ意味と振る舞いが複数箇所にある場合だけ共通UIへ抽出する。
6. ゲームの題材、ルール、識別に由来する表現はゲーム固有に残す。
7. 実画面で情報の優先順位と操作時の見え方を確認する。

この手順は現在仕様そのものではないため `DESIGN.md` からは外し、立ち上げ期の判断過程としてここに残す。

### 4.7 配色ルールをどこで持つか

ブランド色を決めた後、「ゲーム一覧ではどこをブランド色にするか」「結果画面の主要操作をどの色にするか」まで `DESIGN.md` に固定する案を検討したが、これはデザイン言語とコンポーネント契約の責務を混ぜるため採用しない。

主要なデザインシステムを確認すると、共通する傾向は次の通りだった。

- Primer は色を base / functional / component・pattern token に分け、component・pattern token はコンポーネントCSS内で使うものとしている。
- Carbon は全体で使う core token と特定コンポーネント専用の component token を分け、各コンポーネントの design spec をその見た目・機能の正本として扱う。
- shadcn/ui は `primary` / `secondary` / `accent` / `destructive` などをテーマ側の意味トークンとして定義し、Button などの各コンポーネントが variant とトークンの対応を持つ。
- Fluent 2 は raw value を持つ global token と意味を与える alias token を分け、neutral / brand / status などの役割を基盤で定義しつつ、操作の強調は Button などのコンポーネント利用規則で扱う。

pa-zzle では次の責務分離で扱う。

- `DESIGN.md`: ブランド人格、色の意味体系、ブランド色・操作色・意味色・ゲーム固有色・報酬表現の境界
- `@theme`: 正確なトークン値
- コンポーネント: その部品の variant / 状態とトークンの対応
- 画面: 意味に合うコンポーネントを選んで組み合わせる

ブランド表示や操作部品の具体的な配色は、利用側へ任意クラスとして散らすのではなく、既存のコンポーネント規約に従ってコンポーネントまたは variant の契約へ寄せる。新しい共通部品は必要になった時点で作り、将来候補として先に抽出しない。

ブランド色と主要操作色の関係に業界共通の唯一解があるわけではない。shadcn/ui は `primary` を高強調操作とブランド面の双方に使う一方、Fluent 2 は brand / neutral / status を独立した役割として整理している。pa-zzle で Cool Silver と `primary` を分ける判断は、シルバーをゲーム固有色より前へ出さず、操作優先度とは別の責務として扱うという本プロダクト固有の理由による。

ブランドトークンを実画面へ適用する具体作業は Issue #94 で扱う。
