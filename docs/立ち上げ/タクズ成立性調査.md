# タクズ / バイナリパズル成立性調査

Issue #43 の調査結果。

確認日: 2026-09-14

## 結論

**技術的な成立性は GO。**

pa-zzle の将来実装候補として、バイナリパズルは次段階の「難易度制御・良問判定の検証」へ進めてよい。

理由は以下。

- 完成盤は単純な3種類の制約で定義できる。
- 一意解確認は完全探索・SAT・SMTなど既知の方法で扱え、実用盤面では十分小さい。
- 「完成盤を作る → ヒントを外す → 解数を2個まで数える」という一般的な生成方法で一意解を保証できる。
- 一意性確認とは別に、人間向けの論理解法器を通すことで「推測不要」を生成時に保証できる。
- 最小実験では、6×6〜14×14の各10問について、一意解かつ分岐なしの論理推論で完答できる問題を生成できた。
- 未最適化のPython実装でも、初期ヒントを40%残す条件で14×14の生成中央値は約1.57秒だった。事前生成を前提とするなら性能上の懸念は小さい。
- ルール由来の解法技法をそのまま難易度特徴量・ヒント説明へ利用できる。

ただし、この結論は**技術面の採用可否**である。PR #33 の一次選別ではタクズ / バイナリパズルの市場需要は未確認であり、実装優先度を上げる根拠にはまだならない。

## pa-zzle で採用する基礎仕様

初期候補では、ルール差を減らすため次を正とする。

- 正方形の偶数サイズを使う。
  - 初期候補: 6×6、8×8、10×10、12×12、14×14
  - 数学的には4×4以上の偶数サイズで定義できるが、4×4は問題空間が小さいため初期提供対象から外してよい。
- 各マスは `0` または `1` のどちらかになる。
- 各行・各列は `0` と `1` を同数含む。
- 横・縦とも、同じ値を3個以上連続させない。
- 完成した2行は同一であってはならない。完成した2列も同一であってはならない。
- 初期ヒントは固定値で、プレイヤーは変更できない。
- 全マスが埋まり、上記制約をすべて満たした時点をクリアとする。
- 配信する問題は一意解を持つことを生成時に検証する。
- 初期版では、対応する論理解法器が分岐なしで完答できる問題だけを配信対象にする。

矩形盤を許す実装例もあるが、サイズ・難易度・表示の契約を単純にするため、pa-zzle の初期仕様では正方形に限定する。

## 名称とルール差

### タクズ / Binary Puzzle / Binairo

一般には同系統のパズルを指し、標準的な3制約は次で共通している。

1. 各行・各列の0/1数が同じ
2. 同値を3個連続させない
3. 行同士・列同士を重複させない

一方で `Binary Puzzle` を名乗る公開例には、3の重複禁止を省いた変種もある。そのため、名称だけでルールを推測せず、pa-zzle 内では上記3制約を明文化する。

`BINAIRO` は少なくとも米国でパズル・オンラインゲーム等を対象に登録商標が確認できる。公開時の主名称には、権利確認を別途行わない限り **「バイナリパズル」** を使い、「タクズ」は検索・説明用の別名として扱うのが無難。

## 問題として成立する条件

### 完成盤

`n × n` の完成盤について、次のすべてを満たせば妥当。

- `n` は偶数
- 全セルが0/1
- 各行・各列で `0` と `1` がそれぞれ `n / 2` 個
- 水平・垂直の長さ3の部分列が `000` / `111` にならない
- 行がすべて異なる
- 列がすべて異なる

### 初期ヒント

完成盤から一部セルを残したものを問題とする。

最低条件は「少なくとも1解を持つ」ことだが、サービスとして配信する問題では以下を追加する。

- 解がちょうど1個
- 対応済みの論理技法だけで解ける

完全解探索で解を2個見つけた時点で打ち切れば、一意性判定に3個以上の解を列挙する必要はない。

### 論理だけで解ける条件

「一意解」と「人間が推測せず解ける」は別条件として扱う。

一意解問題でも、採用した論理技法だけでは途中で停止する可能性がある。したがって生成器では、完全探索器と論理解法器を分離する。

- **完全探索器**: 解数0 / 1 / 2以上を判定する正しさの基準
- **論理解法器**: 人間向けに許容する技法だけを適用し、分岐なしで完答できるかを判定

論理解法器が健全な強制手だけを使って完答できた場合、その経路自体も一意性の強い根拠になる。ただし実装初期は、バグ検出のためにも完全探索による一意性確認を独立して残す方が安全。

## 代表的な解法・検証方法

文献では以下が実用されている。

- 制約伝播付きバックトラック
- SATへの符号化
- SMTへの符号化
- 多項式方程式系 / Gröbner基底

2017年の Utomo / Makarim はバックトラック、SAT、Gröbner基底の3方式を比較している。別研究ではSMTによる解法も扱われている。

一般化した Binary Puzzle の解存在判定は NP 完全である。ただし、これは盤面サイズを任意に拡大した最悪計算量の性質であり、6〜14程度の固定されたサービス盤面が実用上重いことを意味しない。

pa-zzle では、初期実装として以下のどちらかが妥当。

1. 行・列の合法パターンを先に列挙し、制約伝播付きバックトラックで探索する
2. 将来パズル横断の制約ソルバーを採用するなら、SAT / CP-SAT 等へ寄せる

タクズ単体の初期実装なら1で十分軽い。

## 自動生成

### 基本手順

1. 妥当な完成盤を1つ生成する。
2. 全セルを初期ヒントとして開始する。
3. 削除候補セルをランダム順に並べる。
4. 1セルを仮に削除する。
5. 完全探索器で解数を最大2個まで数える。
6. 一意でなければ戻す。
7. 論理解法器で完答できなければ戻す。
8. 目標ヒント数・難易度条件を満たすまで繰り返す。

ヒント数を最小化する必要はない。サービス用途では、最小ヒント問題を作るより「目標難易度・生成時間・見た目」を満たした時点で止める方が扱いやすい。

### 合法な1行の候補数

「0/1が半数ずつ」「3連続禁止」を満たす1行だけを先に列挙すると候補数は次になる。

| サイズ | 1行の合法パターン数 |
|---:|---:|
| 6 | 14 |
| 8 | 34 |
| 10 | 84 |
| 12 | 208 |
| 14 | 518 |

セルを1個ずつ二分探索するより、この行候補を探索単位にすると大きく枝を減らせる。探索中は列側の合法パターン候補も同時に絞り込める。

## 最小実験

### 目的

文献上の成立性だけでなく、pa-zzle が想定する盤面で以下を同時に満たす生成が現実的かを確認した。

- 一意解
- 分岐なしの論理解法で完答
- 6×6〜14×14
- 生成時に一意性確認を繰り返しても極端に遅くならない

### 実装

検証用の使い捨てPython実装を作成した。リポジトリには追加していない。

- Python 3.13.5
- 単一プロセス
- 各サイズ10問
- 乱数seed固定
- 完成盤生成:
  - 各行の合法パターンを事前列挙
  - 行を順に割り当てる
  - 列側も合法パターン候補を保持し、置けない枝を即時除外
  - 行・列重複も検証
- 問題化:
  - 完成盤からランダムにヒントを削除
  - 各削除ごとに解を最大2個まで探索して一意性確認
  - 論理解法器で完答できることも確認
  - 初期ヒントが全セルの40%になるまで削除を試行
- 論理解法器:
  - 3連続回避
  - 行列内の0/1個数確定
  - 完成済み行列との重複回避
  - 合法な行列候補の共通部分から確定する強制手
  - 仮置き・分岐はしない

### 結果

| サイズ | ヒント数 | 10問中央値 | 10問最大 | 論理解法で完答 |
|---:|---:|---:|---:|---:|
| 6×6 | 15 / 36 | 4.04 ms | 5.51 ms | 10 / 10 |
| 8×8 | 26 / 64 | 17.24 ms | 26.16 ms | 10 / 10 |
| 10×10 | 40 / 100 | 88.55 ms | 119.67 ms | 10 / 10 |
| 12×12 | 58 / 144 | 365.14 ms | 670.76 ms | 10 / 10 |
| 14×14 | 79 / 196 | 1,565.61 ms | 3,197.62 ms | 10 / 10 |

40%は品質上の最適値ではなく、成立性確認用の固定条件。

### 解釈

- 10×10以下は未最適化Pythonでもオンデマンド生成が十分現実的。
- 12×12も十分現実的。
- 14×14は最悪数秒になったが、日次問題や問題プールを事前生成する用途では問題になりにくい。
- 専用SAT/CP系ソルバー、候補キャッシュ、対称性削減、並列事前生成などの最適化余地が大きい。
- 既存のGo実装には50×50の生成実績が報告されており、14×14が構造上の上限とは考えにくい。

この実験は「高品質な難易度分布」を証明するものではない。**自動生成・一意性確認・推測不要判定を組み合わせてもサービスサイズで成立する**ことだけを確認した。

## 人間向け論理解法

最低限、以下を別の技法として記録できる。

### 3連続回避

- `00_` / `_00` → 空欄は `1`
- `0_0` → 空欄は `1`
- 1についても同様

### 個数制約

例えば8マスの行ですでに0が4個あれば、残りはすべて1。

### 重複回避

完成済みの行・列と同一にならないよう、残りセルを確定する。

### 行列候補の絞り込み

その行・列についてルールを満たす完成パターンを列挙し、全候補で同じ値になるセルを確定する。

これは仮置きではなく、その行・列の制約から導かれる強制手として実装できる。説明可能なヒントへ発展させる場合は、内部で候補列挙を使っていても、表示上は「個数」「3連続」「重複回避」などユーザーが理解できる理由へ還元できるかを別途設計する。

## 難易度制御への発展

難易度制御は十分可能性がある。

候補となる特徴量:

- 解くために必要な最も強い論理技法
- 技法ごとの適用回数
- 次の強制手が見つかるまでに調べる行列候補数
- 連鎖的に自明なセルが埋まる割合
- 初期ヒント数・配置
- 解答ステップ数
- 盤面サイズ

初期の難易度区分は、例えば次のような技法階層から始められる。

- Easy: 3連続回避 + 個数制約だけで完答
- Medium: 重複回避が必要
- Hard: 行列候補の絞り込みが必要

ただし「技法の強さ = 体感難易度」とは限らない。最終区分・重みはプレイログと人手評価で補正する必要があるため、このIssueでは確定しない。

## 多様性・同型問題

完成盤とヒント配置の両方に乱数を入れられるため、問題供給量そのものは懸念しにくい。

明らかな同型として少なくとも以下がある。

- 0と1の全反転
- 上下反転
- 左右反転
- 転置
- これらから得られる回転・反射

つまり正方形盤では、盤面の二面体対称性と0/1反転を組み合わせた同型がある。配信上の重複を避けたい場合、これらの変換後のシリアライズ表現の最小値を正規形として重複排除できる。

任意の行入れ替え・列入れ替えは3連続制約を壊し得るため、数独のバンド交換のように一般の対称変換として扱わない。

ヒント配置を180度回転対称などに固定することもできるが、良問性との関係は未検証。見た目だけを理由に初期要件へ入れない。

## ヒント・元に戻す・ミス判定との境界

### ヒント

論理解法器が「次に確定できるセル」と理由を返せるため、相性がよい。

初期版では次の2段階を分けられる。

- 軽量: 確定セルを1つ埋める
- 発展: 「この列は0が半数に達したため残りは1」のように理由も返す

### 元に戻す

ゲーム固有ロジックは不要。プレイヤー入力履歴として共通機能化できる。

### ミス判定

2種類を区別する。

- **制約違反**: `000`、個数超過、完成行重複など、現在盤面だけで確定できる矛盾
- **正解との差**: 保存済み一意解と比較した不一致

前者は答えを見なくても警告できる。後者は「ミス表示」設定として任意に有効化できる。ゲーム仕様ではこの2つを同じ概念にしない方がよい。

## 実装時の推奨構成

初期実装は次の責務分離で十分。

- `validate_complete(board)`
  - 完成盤の3制約を検証
- `count_solutions(puzzle, limit=2)`
  - 完全探索
  - 一意性の基準
- `solve_logically(puzzle, allowed_techniques)`
  - 分岐なし
  - 手順と技法を記録
- `generate_solution(size, seed)`
  - 完成盤生成
- `generate_puzzle(solution, policy, seed)`
  - ヒント削除
  - 一意性・論理解法・難易度条件を満たすまで調整

問題データには少なくとも次を保存できる。

- 盤面サイズ
- 初期ヒント
- 一意解
- 生成seed
- 生成器バージョン
- 難易度用メタデータ

今日の問題を再現可能にしたい場合も、seedだけに依存せず最終問題そのものを保存する方が、生成器更新の影響を受けにくい。

## 残る課題

技術成立性を覆すものは見つからなかった。後続検証の中心は**生成できるか**ではなく**面白い難易度分布を安定して作れるか**になる。

次に確認する価値がある項目:

- Easy / Medium / Hard の技法集合を仮定し、狙った階層の問題を十分な採択率で生成できるか
- ヒント数と体感難易度の相関
- 同じ技法階層でも単調な問題を弾く良問指標
- 6×6〜14×14のどのサイズを実際の難易度段階へ割り当てるか
- ヒント説明を人間向けの理由へ変換できるか
- 市場需要の追加確認

## 採用判断

| 観点 | 判断 | 根拠 |
|---|---|---|
| 基礎ルール | GO | 3制約で明確に定義可能 |
| 完成盤生成 | GO | 合法行パターンを使った探索で実測済み |
| 一意解保証 | GO | 解数を2まで数える完全探索で判定可能 |
| 推測不要保証 | GO | 論理解法器を生成フィルターにでき、実測50/50で完答 |
| 生成時間 | GO | 6〜12はサブ秒中心、14×14も中央値約1.57秒 |
| 多様性 | GO | 完成盤・ヒント配置に十分な変化を持たせられる。明白な同型は正規化可能 |
| 難易度制御 | 次段階で検証 | 技法階層は作れるが体感難易度との対応は未検証 |
| 良問判定 | 次段階で検証 | 単調さ・採択率・プレイログとの相関が未検証 |
| 市場優先度 | 保留 | PR #33 時点で需要根拠が弱い |

**Issue #43 としては完了条件を満たす。技術面では採用候補として残し、難易度・良問生成の検証へ進めてよい。**
