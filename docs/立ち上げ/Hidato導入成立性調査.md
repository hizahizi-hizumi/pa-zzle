# Hidatoの導入成立性調査

Issue #44 の更新後スコープに対する追加調査。PR #56 の `Hidato調査.md` をゲート1（問題供給成立性）の証拠として利用し、難易度運用、スマホプレイ、最終導入判断を補う。

## 結論

**4ゲートすべて通過。Hidato系の連続数字経路パズルを実装候補に採用する。**

初期対象は正方形セル・全セル有効の5×5〜7×7とする。7×7のリアルタイム生成は必須にせず、探索予算または事前生成を許容する。難易度はヒント数だけで決めず、人間向け解法器の候補数・強制経路・推論連鎖・先読み量等で選別する。スマホ操作は「次数字の候補セルを直接タップ」を主方式とし、任意修正用のセル選択を併設する。

## ゲート1: 問題供給成立性

既存 `Hidato調査.md` の生成・探索実験を再利用する。

| 項目 | 判定 | 制約 |
|---|---|---|
| 完成経路生成 | GO | 長方形全セル盤から開始 |
| 一意解生成 | GO | ヒント削除ごとに最大2解探索 |
| 論理解 | GO | 人間向け解法器で別途確認 |
| 5×5〜6×6生成 | GO | 素朴探索でも実用域へ入り得る |
| 7×7 | 条件付きGO | 探索最適化または事前生成を許容 |
| 8×8以上 | 初期対象外 | 性能・スマホ操作の双方で初期採用理由が弱い |
| 多様性 | GO | 経路生成とヒント配置の両方を変える |

**ゲート1はGO。** 5×5〜7×7に絞れば継続供給に致命的な問題はない。

## ゲート2: 難易度運用成立性

### 難易度に効く要素

少なくとも次を分けて扱う。

- 有効セル数・盤面形状
- 初期ヒント数と密度
- 連続するヒント間の数値差
- ヒント間を結ぶ経路候補数
- 各未確定数字が置ける候補セル数
- 候補が1つに確定する数字・セルの数
- 1手の確定が次の確定を生む連鎖長
- 先読みや複数区間をまたぐ制約伝播が必要な回数
- 連続して自明に埋まる区間の割合

既存CSP実装の評価では、同じ6×6を中心とする問題群でも探索時間に大きな差があり、盤面寸法だけでは難しさを説明できない。また「次の数字から順番」より「候補領域が最小の数字を優先」する変数選択が概して高速で、候補領域の狭まり方が問題構造を表す。

公開問題でも、Medium #95 は37セル・15ヒント（41%）・最長ヒント間隔5で約5分、Medium #94 は43セル・13ヒント（30%）・最長間隔8で約8分、Hard #135 は56セル・20ヒント（36%）・最長間隔6で約9分、Hard #203 は54セル・16ヒント（30%）・最長間隔9で約10分とされる。ヒント密度が高くてもHardになり得るため、ヒント数だけの難易度閾値は採用しない。

### 解法器から計測する指標

人間向け解法器は全探索ノード数を難易度として流用せず、説明可能な推論を段階的に適用して次を記録する。

1. 各数字の候補セル数
2. 候補が1セルだけの数字・数字候補が1つだけのセルの数
3. 2つの固定値間で経路が1本に限定される区間数
4. 隣接する初期ヒント間の最大数値差
5. 1つの確定から連鎖して確定する最大手数
6. 基本推論を尽くしても未確定が残る回数
7. 先読み地点の候補数
8. 一意に絞るために必要な最大先読み深さ
9. 候補1つだけで連続的に埋まったセルの割合

公式解説も、1から順番に埋めるのではなく、複数のヒント区間から経路が一意に決まる場所を探し、必要なら逆向きに数えることを基本戦略としている。強制経路と推論連鎖はHidato固有の説明可能な指標になる。

### 生成側から分布を動かす

難易度を直接構成せず、生成条件を変えた候補を人間向け解法器で選別する。

```text
完成経路を生成
  ↓
ヒント削除条件を変える
  ├─ 残すヒント数
  ├─ 最大ヒント間隔
  ├─ 強制経路を残す / 減らす
  └─ ヒント配置の偏り
  ↓
一意性確認
  ↓
人間向け解法器で指標化
  ↓
狙った指標帯だけ採用
```

簡単側では短いヒント間隔、強制経路の多さ、候補数の少なさ、長い確定連鎖を増やす。難しい側では逆へ動かす。ただし単純なヒント削除だけでは、論理で解けず探索だけを要求する問題や局所的に停滞する問題になり得るため、停滞回数・先読み深さに上限を置いて棄却する。

現行のHidato専用サイトも、機械生成では問題が似通いやすく、ヒント配置が解き味を左右すると説明している。したがって難易度制御と良問選別は分離し、自明区間率や強制経路率などの単調性指標も棄却条件に使う。

**ゲート2はGO。** 最終的なEasy/Medium/Hardの境界は実ユーザーデータで校正する必要があるが、狙った難易度帯へ生成分布を動かし、解法過程から選別する現実的な方法がある。

## ゲート3: スマホプレイ成立性

### 既存事例

公式Google Play版Hidatoは、空きセルをタップして数字を追加し、誤入力も再タップで修正できる操作を案内している。別の現行Web実装も「セルをタップしてから数字をタップ」の二段階入力を採用し、Undo / Erase / Reset を提供している。

Hidatoでは次に置く数字が現在値の前後である場面が多いため、pa-zzleでは1〜Nを常設する巨大な数字パレットより、次数字の候補セルを直接タップする方式を第一候補とする。任意修正はセル選択方式を併設する。

### 最小操作試作

完成UIではなく成立性確認用として、正方形盤をスマートフォン相当の390×844 CSS pxで描画し、5×5 / 6×6 / 7×7 / 9×9を切り替え、セル選択と前後数字入力を行える最小HTMLを作った。

ChromiumをPlaywrightから起動した。直接HTTPアクセスは環境制約で拒否されたため `page.set_content` で同じHTMLを描画して操作した。`pageerror` と意図しない `console.error` は0件だった。

| 盤面 | 1セルの実測幅 | 判定 |
|---|---:|---|
| 5×5 | 約72.8 CSS px | 十分余裕あり |
| 6×6 | 約60.7 CSS px | 十分余裕あり |
| 7×7 | 約52.0 CSS px | タップ・2桁表示とも成立 |
| 9×9 | 約40.4 CSS px | 表示は成立するが操作余裕が減る |

7×7では盤面をスクロール・拡大せず、セル選択と44px高の操作ボタンを同一画面内で操作できた。9×9も390px幅へ収まるが数字密度が上がり、前後関係を追う認知負荷が増える。10×10以上は初期対象にしない。

### 入力方式

| 方式 | 長所 | 短所 | 初期判断 |
|---|---|---|---|
| セル選択 → 数字パレット | 任意の数字を直接修正できる | Nが大きいとパレットが大きい | 補助として可 |
| セル選択 → 前後数字 | 連番入力と一致し操作数が少ない | 離れた数字を直接入れにくい | 第一候補 |
| 次数字の候補セルを直接タップ | 連続入力が最短 | 修正モードとの区別が必要 | **主操作候補** |
| キーボード直接入力 | デスクトップでは速い | スマホ主操作には不向き | 併用 |

初期実装は「追跡中の数字 k を選ぶ → k+1 の候補セルを直接タップ」を基本にし、任意修正用にセル選択方式を併設する。誤入力は一旦受理し、消去・Undoで戻せるようにする。正解との不一致を即時表示するかは補助機能として分離する。

**ゲート3はGO。初期採用範囲は5×5〜7×7を推奨する。** 8×8以上は需要が出てから操作方式と生成方式をまとめて再検証する。

## ゲート4: 導入判断

PR #33 の候補整理では、Hidatoは市場実績の裏付けが他候補より弱い。一方、現在も公式系モバイルアプリが配信され、専用サイトでは複数難易度・19〜81セルの問題が継続提供されているため、デジタルプレイ自体の成立実績はある。

pa-zzle内の既存調査との構造差も大きい。Water Sortは状態遷移・移動手順、ナンプレは各セルの制約充足、Hidato系は盤面全体を1本の連続経路として復元する。共通ゲーム基盤に対して異なる入力・ヒント・難易度指標を検証できる。

実装・保守負荷の中心は完成経路生成、一意解確認、人間向け解法器、難易度・単調性の選別、7×7付近の探索外れ値管理である。ただし初期盤面を5×5〜7×7の正方形・全セル有効に限定すれば、不規則形、六角形、大盤面、拡大・パンを後回しにできる。

| ゲート | 判定 | 採用条件 |
|---|---|---|
| 1. 問題供給成立性 | GO | 初期5×5〜7×7。7×7は探索予算または事前生成を許容 |
| 2. 難易度運用成立性 | GO | ヒント数単独ではなく、人間向け解法指標で生成後選別 |
| 3. スマホプレイ成立性 | GO | 初期5×5〜7×7、連続入力中心 |
| 4. 導入判断 | **採用** | 市場規模の弱さは実装順序の材料であり、成立性の否定材料ではない |

**最終判定: 実装候補に採用する。**

採用時の初期仕様は、正方形セル・全セル有効、8近傍、5×5〜7×7、一意解必須、人間向け基本推論で解けない候補を棄却可能、次数字候補セルの直接タップを主操作、7×7のリアルタイム生成を必須にしない、という範囲を推奨する。

#44として追加PoCへ分離しなければ判断できない未知は残っていない。難易度閾値の校正、大盤面対応、完成UI、本番品質の生成器は採用後の設計・実装課題であり、導入成立性の判定を止めるものではない。
