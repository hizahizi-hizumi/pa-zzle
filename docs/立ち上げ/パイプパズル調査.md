# パイプパズル導入成立性調査

Issue #41 の4ゲートについて、既存実装・一次資料の調査と小規模実験で導入成立性を確認した結果をまとめる。

調査日: 2026-09-15

## 結論

**実装候補に採用する。**

4ゲートはいずれも通過と判断する。ただし、スマホで常時1画面に収めて直接タップする盤面は **7×7を標準上限** とし、8×8以上は端末幅に応じた拡大・パン等を設計してから採用する。難易度は初期回転量や必要タップ数だけで決めず、解法過程から得られる論理指標を中心に生成後の棄却で制御する。

| ゲート | 判定 | 根拠 |
|---|---|---|
| 1. 問題供給成立性 | 通過 | 全域木からの生成、一意解検証、同型除外が現実的な計算量で成立した |
| 2. 難易度運用成立性 | 通過 | 解法過程の指標で簡単・中間・難しい側を分離でき、棄却生成で狙った帯を供給できた |
| 3. スマホプレイ成立性 | 通過 | タップ回転、Undo、縦スクロール共存を実ブラウザで確認。7×7は狭幅でも実用的なタップ領域を確保できる |
| 4. 導入判断 | 実装候補に採用 | 技術リスクが低く、既存2種と異なるグラフ接続型のゲーム性を追加できる |

---

## ゲート1: 問題供給成立性

### 採用候補の基本ルール

Simon Tatham の `Net` を基準に、pa-zzle では次の仕様を候補とする。

- 長方形グリッド、端のラップなし
- 全マスにパイプタイルがあり、全タイルを1つのネットワークへ接続する
- 閉路は禁止する
- 始点・終点という役割は持たせない
- タイル種別は以下
  - 端点: 1方向
  - 直線: 対向2方向
  - 曲がり: 隣接2方向
  - T字: 3方向
- 4方向すべてへ接続する十字タイルは初期候補から外す
- 1回の操作は1タイルを時計回りに90度回転
- クリア条件は「全タイルが相互接続され、閉路がない」
- 一意解を要求する
- 固定障害線は標準問題では使わない。将来、ヒントまたは簡単側への調整手段として検討できる

`Net` の公式説明でも、完成形は「全体が接続され、閉路がないネットワーク」であり、中央タイルからのハイライトは視覚補助であって勝利条件ではない。したがって pa-zzle でも中央の電源や特別な始点はルールに含めない。

参考:

- Simon Tatham, Net: https://www.chiark.greenend.org.uk/~sgtatham/puzzles/doc/net.html
- Simon Tatham, Writing a solver for Net: https://www.chiark.greenend.org.uk/~sgtatham/quasiblog/net-solver/

### 生成方式

候補方式は次の通り。

```text
グリッドグラフ上にランダムな全域木を生成
  ↓
各頂点の接続辺からタイル種別・正解向きを決定
  ↓
各タイルをランダム回転して初期盤面を作る
  ↓
解法器で一意解を確認
  ↓
難易度指標を計測
  ↓
難易度帯・自明さ・同型重複で棄却
```

今回の実験では、T字までに限定するため各頂点の次数を3以下にした全域木を生成した。完成形そのものが全域木なので、生成時点で「全マス接続」「閉路なし」「解が少なくとも1つ存在」は保証できる。

初期回転は問題の見た目と操作量を変えるが、各マスのタイル種別は変わらない。そのため**論理問題としての難しさや同型判定では初期向きを無視する**。初期回転量は操作負荷の指標として別管理する。

### 一意解検証

各タイルについて取り得る向きを候補集合として保持し、次の制約を反復適用する解法器を試作した。

- 盤面外へパイプを出さない
- 隣接2マスの接続有無を一致させる
- 確定済み接続が閉路を作る向きを除外する
- 残り得る接続だけで全マス接続が不可能になる候補を失敗とする
- 論理確定だけで決まらない場合は候補の少ないマスから分岐し、2解目が見つかった時点で打ち切る

この構造は Tatham が公開している「各マスの可能な向きを削り、接続辺と閉路・全体接続を使って推論する」解法と同系統である。

### 生成・検証性能

Python の検証用実装で、ランダム生成した候補を一意解判定した。各サイズのサンプル数は小さいため本番性能のベンチマークではなく、成立性を見るための値である。

| 盤面 | 一意解採用数 / 候補数 | 一意解検証時間 中央値 | 最大 |
|---|---:|---:|---:|
| 5×5 | 30 / 31 | 0.62 ms | 1.18 ms |
| 7×7 | 30 / 31 | 1.84 ms | 3.44 ms |
| 9×9 | 20 / 24 | 4.37 ms | 9.60 ms |
| 11×11 | 10 / 16 | 9.00 ms | 24.89 ms |
| 13×11 | 8 / 21 | 16.80 ms | 66.22 ms |

少なくとも想定するスマホ盤面より大きい13×11でも、試作段階で候補1件の検証が数十ms程度に収まった。オンライン生成でも致命的な兆候はなく、必要なら事前生成でさらに回避できる。

### 多様性・同型問題

初期回転を無視し、各マスを `端点 / 直線 / 曲がり / T字` の種別だけで表現したうえで、盤面の回転・反転を正規化して重複を数えた。

| 盤面 | 採用問題数 | 向きを無視した完全一致 | 回転・反転まで含む重複 |
|---|---:|---:|---:|
| 5×5 | 5,000 | 0 | 1 |
| 7×7 | 3,000 | 0 | 0 |

今回の規模では同型除外後も供給量が痩せる兆候はない。自明すぎる問題についても、後述する推論段数などを使って棄却できる。

**ゲート1判定: 通過。**

## ゲート2: 難易度運用成立性

### 難易度指標

人間向け難易度の一次指標として、少なくとも次を生成時に計測できる。

- 盤面サイズ
- 端点・直線・曲がり・T字の構成比
- 初期状態で向きが1通りに確定するタイルの割合
- 局所制約を反復したときに全タイルが確定するまでの**推論段数**
- 誤った向きを仮定したとき、矛盾が表面化するまでの推論段数
- 論理推論だけでは確定しないマス数
- 探索が必要な場合の分岐数・深さ
- 初期回転による必要タップ数

このうち、初期回転量と必要タップ数は論理構造を変えない。したがって主難易度には使わず、操作量または副指標として扱う。

### 7×7での分布

ランダム生成し、今回の論理解法器だけで一意に確定できる7×7を1,000問採用した。採用には1,180候補を要した。

推論段数の分布:

- 最小: 2
- 第1四分位: 4
- 中央値: 5
- 第3四分位: 6
- 最大: 12

例として次の棄却条件を置いた。

- 簡単側: 推論段数 `<= 3`
- 中間: `5..6`
- 難しい側: `>= 9`

| 帯 | 採用数 | 採用率 | 推論段数平均 | 初期確定率平均 | T字平均 |
|---|---:|---:|---:|---:|---:|
| 簡単側 | 165 | 16.5% | 2.90 | 21.4% | 12.9 |
| 中間 | 410 | 41.0% | 5.41 | 17.5% | 13.8 |
| 難しい側 | 21 | 2.1% | 9.38 | 14.0% | 14.8 |

狙った帯を**生成後の棄却だけで明確に分離できた**。難しい側でも約48候補に1問は得られ、7×7の一意解検証が数ms級だったことを考えると事前生成・バッチ生成では十分現実的である。

9×9でも同様に600問を採用し、推論段数は `3 / 5 / 6 / 8 / 14`（最小 / 第1四分位 / 中央値 / 第3四分位 / 最大）に広がった。盤面サイズ自体も難易度分布を動かす手段になる。

### 代表問題の確認

7×7から代表問題を1問ずつ取り、同じ解法ルールで解き切るまでの依存の深さと誤りの発見しやすさを比較した。

| 帯 | 推論段数 | 初期確定タイル | 誤った向きの矛盾検出 最大段数 | ランダム初期向きからの時計回りタップ数 |
|---|---:|---:|---:|---:|
| 簡単側 | 3 | 12 / 49 | 1 | 72 |
| 中間 | 5 | 12 / 49 | 2 | 70 |
| 難しい側 | 9 | 3 / 49 | 5 | 73 |

難しい側ほど「最初から確定できる場所」が少なく、誤った仮定も後段まで破綻しにくくなった。一方、必要タップ数は70〜73でほぼ同じだった。**回転量を難易度とみなすと体感と乖離しやすい**ことも確認できた。

Tatham が公開している Net 解法器も、本人が手で解いた際に使った「盤面端からの確定」「確定済みタイルから隣へ制約を伝播」「閉路回避」等を機械化している。今回の推論段数も同種の人間向け論理の依存深さを測っているため、機械探索ノード数だけを難易度とするより校正しやすい。

最終的な区分・閾値は実プレイログで校正する必要があるが、#41 の範囲では「狙った難易度帯へ生成分布を動かせる」ことまで確認できた。

**ゲート2判定: 通過。**

## ゲート3: スマホプレイ成立性

### 操作方式

最小試作では次の方式を採用した。

- タイルを1回タップ: 時計回りに90度回転
- 永続的な「選択状態」は持たない。タップと同時に回転するため、選択モードの誤認を避ける
- Undoボタンを常設する
- 逆回転専用操作は必須にしない
  - 1タイルは最大3タップで任意の向きへ移せる
  - 誤操作はUndoで戻せる
- 接続中領域の強調は補助表示として追加可能だが、クリア条件そのものには使わない
  - 試作では背景だけでなく内側の輪郭も付け、色だけに依存しない表現を確認した

Tatham のデスクトップ版には時計回り・反時計回り・180度回転とロックがあるが、スマホの初期版ではジェスチャを増やすより、単一タップとUndoの方が誤操作を抑えやすいと判断する。逆回転やロックは実プレイで必要性が出た場合に追加する。

### タップ領域

Apple はタップ対象を44×44 pt以上、Android は48×48 dp以上を推奨している。WCAG 2.2 AA の Target Size (Minimum) は24×24 CSS pxである。

参考:

- Apple UI Design Tips: https://developer.apple.com/design/tips/
- Apple Human Interface Guidelines - Buttons: https://developer.apple.com/design/human-interface-guidelines/buttons
- Android accessibility: https://developer.android.com/guide/topics/ui/accessibility/apps
- WCAG 2.2: https://www.w3.org/TR/WCAG22/#target-size-minimum

Playwright + Chromium で、縦画面に盤面を描画して実測した。狭幅時は左右余白とマス間隔を縮めるレスポンシブ配置を使った。

| CSS viewport幅 | 7×7 1マス | 8×8 1マス | 9×9 1マス |
|---:|---:|---:|---:|
| 320 px | 44.56 px | 39.00 px | 34.66 px |
| 360 px | 47.42 px | 41.25 px | 36.44 px |
| 390 px | 47.70 px | 41.25 px | 36.22 px |
| 430 px | 53.42 px | 46.25 px | 40.66 px |

7×7なら320px幅でも44 CSS px級を確保でき、WCAG 2.2 AA の24 CSS px要件を十分上回る。Appleの44 pt、Androidの48 dpとは単位が同一ではないため、この数値だけで各プラットフォーム推奨への適合を断定はしない。360px以上では余白をさらに数px詰めることで48 CSS px級を確保できる。一方8×8・9×9をすべての狭幅端末で同じ直接タップ方式にするのは適さない。

したがって初期実装では次を基準にする。

- **1画面直接タップの標準上限: 7×7**
- 320px級まで48px相当を厳格に取りたい場合は6×6を選べる
- 8×8以上は、広い端末だけ許可するか、拡大・パン・別操作方式を設計してから導入する

### 実ブラウザ操作確認

Chromium の実レイアウト・タッチイベントで次を確認した。

- 320 / 360 / 390 / 430px幅で描画崩れなし
- タイル中央のタップで対象タイルのみ回転
- 連続30〜40回のタップで意図しないページスクロールなし
- タイル上から縦スワイプするとページはスクロールし、タイルは回転しない
- Undoが直前の回転を戻す
- 接続中領域を背景＋輪郭で強調し、接続が切れる操作で強調対象が更新される
- 7×7代表問題を簡単・中間・難しい側とも操作試作上で最後まで回転できる
- `pageerror` なし
- 意図しない `console.error` なし

開発サーバーへの `localhost` 遷移は実行環境の Chromium 管理ポリシーに遮断されたため、同じHTML/CSS/JavaScriptを Playwright の `setContent` で Chromium 内へ直接描画した。ブラウザエンジンによるレイアウト・ポインタイベント・タッチスクロールの確認自体は実施できている。

パイプ線は7×7で十分判別できた。最終UIでは色だけに接続状態を依存させず、線・背景・輪郭等を組み合わせて補助表示する。

**ゲート3判定: 通過。**

## ゲート4: 導入判断

### 市場実績

PR #33 の2026-09-15時点の調査では、代表例 `Water Pipes` が Google Play で **1,000万+ダウンロード / 3.63万レビュー**。日本 App Store では同一形式の代表例を特定できていない。

世界規模の需要シグナルはある一方、日本での需要根拠はナンプレやパーキングジャムほど強くない。したがって「初期リリースで最優先」という根拠にはしないが、技術的成立性を確認した実装候補から外す理由にもならない。

### 実装量・保守負荷

パズル固有部分は主に以下へ限定できる。

- 4bit程度の接続方向によるタイル表現
- 全域木生成
- 向き候補を削る解法器・一意解確認
- 難易度指標・重複正規化
- タップ回転UI

外部辞書、画像素材、物理シミュレーション、巨大な問題DBは不要。ルールも決定論的で、問題はシードから再現しやすい。パズル固有の保守負荷は比較的小さい。

一方、次は固有実装として必要になる。

- 全体接続・閉路を扱う解法ロジック
- 人間向け難易度指標の継続校正
- 盤面サイズと端末幅の組み合わせ制御

### 他候補との差異

既存PoC対象との違いが明確である。

- カラーウォーターソート: 状態遷移・手順探索
- ナンプレ: 候補数字・制約充足・論理手筋
- パイプパズル: **空間的な接続グラフを回転で復元する**

盤面上の局所接続と全体接続・閉路禁止を同時に扱うため、既存2種から得られない生成・解法・UI知見を追加できる。

### 最終判断

**実装候補に採用する。**

理由:

1. 問題生成、一意解検証、重複除外が現実的な時間で成立する
2. 推論過程を計測し、棄却生成で難易度帯を作り分けられる
3. 7×7までならスマホ縦画面の直接タップ操作が成立する
4. 外部コンテンツ依存がなく、固有保守負荷が比較的小さい
5. カラーウォーターソート・ナンプレとは異なるグラフ接続型の知見が得られる
6. 世界規模では代表アプリに1,000万+の実績がある

採用判断は「7×7を初期の標準上限」「一意解あり」「非ラップ」「閉路なし」を前提とする。8×8以上のスマホUIや最終難易度閾値は本Issueの完了条件外として、実装後の実機・プレイログで調整する。

## 実装時に引き継ぐ判断

- ルール: 全マス接続・閉路なし・非ラップ・一意解
- タイル: 端点 / 直線 / 曲がり / T字。十字なし
- 生成: 全域木を先に作り、回転して出題
- 検証: 2解目で打ち切る一意解判定
- 重複: 初期回転を無視したタイル種別配置を回転・反転で正規化
- 難易度: 推論段数、初期確定率、矛盾検出深さ等で評価し、生成後に棄却
- 操作: タップで時計回り、Undoあり。逆回転・ロックは必須にしない
- スマホ: 7×7を標準上限とする
- 接続ハイライト: 補助表示。勝利条件や解法に必須としない

## 今回決めていないこと

- 実ユーザーのプレイログによる難易度校正
- 完成UIの色、演出、アニメーション
- 8×8以上をスマホで扱う場合の拡大・パンUI
- 本番生成器・解法器の最適化と配置先
- 保存・API・DB設計
- 共通ゲーム契約
