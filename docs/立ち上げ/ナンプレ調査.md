# ナンプレの基礎仕様と自動生成の成立性調査

Issue #28 の調査結果。PoCでナンプレを実装するために、変更しにくい基礎仕様と、問題生成・一意解確認・難易度評価の成立性を整理する。

## 結論

**自動生成・一意解確認ともに成立する。#5 の実装へ進めてよい。**

標準的な9×9ナンプレは、完成盤を生成し、ヒントを削除するたびに解数を最大2件まで探索して一意性を確認するだけでも、PoCで必要な問題を十分高速に生成できる。

今回のJavaScript実験では、28ヒントの問題200件をすべて生成できた。生成時間は中央値約0.66ms、95パーセンタイル約1.50ms、最大約3.94msだった。生成後の一意解再確認は95パーセンタイル約0.17msだった。24ヒントまで削ると1回の貪欲な削除だけでは目標数へ届かない問題が増えたが、生成時間の95パーセンタイルは約7.21msであり、実行時間自体は問題にならない。

したがって、PoCで難しいのは「解ける一意解問題を作ること」ではなく、**人間にとって意図した難易度・解き味の問題を安定して選別すること**である。ヒント数だけでは難易度を決めず、人間向け解法手順を再現する評価器を後続PoCで実装する。

## 1. PoCで採用する基礎仕様

### 1.1 盤面

クラシックな9×9のみを対象とする。

- 81マス
- 9行 × 9列
- 3×3のブロックが9個
- 使用する数字は1〜9
- 各行・各列・各ブロックに1〜9が1回ずつ入ることが完成条件

16×16などの派生サイズや追加制約付き変種はPoC対象外とする。

ニコリが公開しているナンプレのルールも、空きマスへ1〜9を入れ、各行・各列・各3×3ブロックに1〜9を1つずつ入れるものとしている。

### 1.2 初期ヒント

問題開始時に与えられた数字を初期ヒントとする。

- 初期ヒントはプレイ中に変更できない
- 初期ヒント自体が行・列・ブロックの制約に違反していてはならない
- 初期ヒントから到達できる完成盤が厳密に1つ存在する問題だけを提供する

「17ヒント以上なら一意解」ではない。17は9×9ナンプレで一意解を持ち得る最小ヒント数であり、任意の17ヒント盤面が一意解になるという意味ではない。一意性は各問題ごとに探索して確認する。

### 1.3 プレイヤーの数字入力

初期ヒント以外のマスでは、次の操作を許可する。

- 1〜9の数字を入力する
- 入力済みの数字を別の数字へ変更する
- 入力済みの数字を消す

行・列・ブロックの制約に反する数字や、最終解と異なる数字であっても、**入力操作そのものは拒否しない**。制約違反や誤答は盤面状態・プレイ記録として検出する。

理由は、数学的なナンプレの制約と、デジタルUIが入力を受理するかどうかは別の責務だからである。入力を禁止すると、ミス状態、訂正、Undo、ミス計測といったPoCで確認したいプレイ体験を不必要に狭める。

### 1.4 競合とミスを分ける

「ルール上の競合」と「プレイ成績としてのミス」は別に扱う。

**競合**は、同じ行・列・ブロックに同じ数字が複数存在する現在盤面の状態とする。これは正解を知らなくても判定できる。

**ミス**は、初期版では、回答として確定入力した数字がその問題の一意な完成解と異なる入力イベントとする。

- 候補数字の追加・削除はミスに数えない
- 空欄化はミスに数えない
- PoCの仮ミス定義では、Undoは盤面状態を戻す操作とし、すでに発生したミス履歴は戻さない
- 誤答を入力直後に利用者へ知らせるか、クリア確認まで隠すかはUI・補助機能の方針として分離する

この分離により、将来「競合だけ表示」「自動誤答チェック」「ミス非表示」などのモードを追加しても、盤面ルールを変えずに済む。

### 1.5 候補数字

候補数字はナンプレ成立条件ではなく、プレイヤーの作業用メモとして扱う。

- 各編集可能マスに0個以上の1〜9を保持できる
- 候補数字は解の妥当性・クリア判定へ影響しない
- 手動メモと、自動算出した「現在の制約から入り得る数字」は概念上分離する

自動候補は現在盤面から導出可能だが、手動メモは利用者の状態なので同一データとして扱わない方がよい。

### 1.6 クリア条件

次をすべて満たした時点をクリアとする。

1. 81マスが埋まっている
2. 各行に1〜9が1回ずつ存在する
3. 各列に1〜9が1回ずつ存在する
4. 各3×3ブロックに1〜9が1回ずつ存在する

提供する問題は一意解を保証するため、この条件を満たす盤面は保存している完成解と一致する。実装では完成解との一致比較も利用できるが、ゲームルールとしてのクリア条件は上記の制約充足とする。

## 2. 「成立する問題」と「良問」は別

### 2.1 数学的に成立する問題

PoCで問題として最低限必要なのは次の条件である。

- 初期ヒント同士が矛盾しない
- 少なくとも1つ完成解が存在する
- 完成解が厳密に1つである

一意解確認は「1解見つける」だけでは足りない。解を列挙し、0件・1件・2件以上を区別する必要がある。ただし3件目以降を数える意味はないため、探索は2解見つかった時点で打ち切れる。

### 2.2 良問に必要な追加条件

一意解であっても、人間向け問題として良いとは限らない。

候補となる品質条件は次のとおり。

- 想定した人間向け解法だけで進められる
- 当てずっぽうを要求しない
- 意図した難易度帯に入る
- 特定箇所だけ極端に探索しづらくない
- 同型問題やほぼ同じ問題が過度に連続しない
- 必要なら初期ヒント配置に見た目上の対称性がある

ニコリもナンプレについて「答えが一つ」であることに加え、あてずっぽうではなく考えて解けることを案内している。したがって、pa-zzleでも一意性を品質判定の終点にはしない。

### 2.3 最小問題は要求しない

あるヒントを1つでも削ると一意性が失われる問題は「minimal」と呼ばれるが、PoCでは最小性を要求しない。

- 一意解問題に不要なヒントが残っていても、ゲームとして直ちに不成立にはならない
- 17ヒントという下限を目指す必要もない
- ヒント数の削減と人間向け難易度は一致しない

最小性が必要になった場合は、生成後に全ヒントを再走査して削除可能なものがないことを確認できる。これは後付け可能な生成方針である。

## 3. 問題生成

### 3.1 採用候補の生成パイプライン

PoCでは次の構成で十分である。

```text
seed
  ↓
決定的な疑似乱数列
  ↓
ランダム化した深さ優先探索で完成盤生成
  ↓
ヒント候補をランダム順に削除
  ↓
各削除ごとに解数を最大2件まで探索
  ├─ 1件: 削除を採用
  └─ 2件以上: 元に戻す
  ↓
人間向け解法器で解法手順を記録
  ↓
難易度・品質条件に合わなければ別候補を生成
  ↓
問題確定
```

完成盤生成と一意解確認には、行・列・ブロックで使用済みの数字をビット集合として保持し、候補数が最少の空きマスから探索する深さ優先探索で十分な性能が得られた。

### 3.2 seedからの再現性

#3 の設計方針に従い、ゲーム固有ロジックは外部乱数へ直接依存させず、`generatePuzzle(seed, ...)` で同じ入力から同じ問題を再生成できる形にする。

現在の `Seed` は128ビット相当の16進文字列として生成される。ナンプレ側ではこれを決定的な疑似乱数生成器の初期状態へ変換し、完成盤生成・削除順・再試行順をすべてその乱数列から決める。

疑似乱数生成器のアルゴリズムは問題再現性の一部になるため、実装後に不用意に差し替えない。将来アルゴリズムを変更するなら、生成方式の版を問題識別に含める余地を残す。

### 3.3 一意解確認

一意解判定は次の3値だけ分かればよい。

```text
0解      -> 不正な問題
1解      -> 一意解
2解以上  -> 一意でない
```

したがって、解法探索器は解数を無制限に数えず、2件で打ち切る。

代表的な実装方法には、制約伝播付きバックトラッキング、Exact CoverとしてのAlgorithm X / Dancing Links、SAT・制約充足問題への変換などがある。9×9固定のPoCでは、実装が単純で解数上限も扱いやすいビット集合 + 候補最少優先のバックトラッキングから始めるのが妥当である。

Dancing Links等へ置き換える必要が生じる性能根拠は今回の実験では見つからなかった。

## 4. 計算量と実測

### 4.1 理論上の注意

一般化したNumber Placeについては、別解探索がASP完全であり、NP完全性も含意されることが知られている。したがって、盤面サイズを一般化した問題に対して「探索は常に軽い」とは言えない。

一方、pa-zzleのPoCは9×9に固定する。入力サイズが固定で探索空間も小さく、理論計算量と実際のサービス性能は分けて判断する必要がある。

### 4.2 実験方法

本調査では、後続実装と同じJavaScript系ランタイムで成立性を確認するため、依存ライブラリなしのJavaScript実験コードを用いた。

環境:

- Node.js v22.16.0
- Linux x86_64
- 5 CPUが見える実行環境
- 単一プロセス

アルゴリズム:

- 完成盤: ランダム化バックトラッキング
- 空きマス選択: 候補数最少を優先
- 制約: 9ビットのビット集合
- ヒント削除: 81マスをランダム順に試す
- 一意解判定: 同じ探索器で解を最大2件まで数える
- 疑似乱数: xorshift32（実験用。後続実装の固定仕様ではない）
- 各条件200問
- 各問の実験seed: `20260914 + 目標ヒント数 × 100000 + 連番` を32ビット整数として使用

これは性能競争用の最適化実装ではなく、成立性を見るための小さな実装である。

### 4.3 実験結果

| 目標ヒント数 | 件数 | 目標到達 | 生成中央値 | 生成95%点 | 生成最大 | 一意解再確認95%点 |
|---:|---:|---:|---:|---:|---:|---:|
| 40 | 200 | 200 | 0.30ms | 0.84ms | 7.33ms | 0.03ms |
| 32 | 200 | 200 | 0.41ms | 0.68ms | 1.49ms | 0.04ms |
| 28 | 200 | 200 | 0.66ms | 1.50ms | 3.94ms | 0.17ms |
| 26 | 200 | 196 | 1.27ms | 4.42ms | 10.90ms | 0.39ms |
| 24 | 200 | 111 | 2.44ms | 7.21ms | 20.42ms | 0.72ms |

28ヒントでは、1問あたりの一意解判定回数は中央値61回だった。それでも生成時間はミリ秒単位に収まった。

24ヒントで「目標到達」が下がるのは探索性能不足ではなく、1つの完成盤に対して1回だけ貪欲に削る方式では、削除順によってそれ以上ヒントを外せない局所状態へ到達するためである。低ヒント数を必須にするなら、削除順の再試行・完成盤の再生成・より高度な生成法を追加できる。

PoCの難易度制御はヒント数を目的値にしないため、これは致命的な制約ではない。

### 4.4 実測の解釈

この結果は本番SLAを保証するベンチマークではない。ただし次は十分判断できる。

- 9×9の完成盤生成は軽い
- ヒント削除中に数十回の一意解確認を行っても軽い
- 一意解を最終確認するコストは小さい
- 生成候補を難易度判定で何回か棄却する余地がある

人間向け解法器を追加した後に生成時間が大きく増える可能性はあるため、後続PoCでは「難易度帯ごとの候補採用率」と「最終問題1件を得るまでの総時間」を改めて計測する。

## 5. 問題の多様性と同型

### 5.1 多様性の上限は十分大きい

完成した9×9ナンプレ盤は約6.67×10^21個存在する。数字の置換、回転・反転、行・列・バンド・スタックの許される交換などを同一視しても、約54.7億個の本質的に異なる完成盤があることが知られている。

したがって、サービスで継続供給する問題数そのものが組合せ上限へ近づく心配はない。

### 5.2 同型問題を増やさない生成法

1つの完成盤だけを用意して、数字置換・回転・反転・行列交換だけで完成盤を増やす方法は採用しない。これらはまさに同型変換なので、見た目は変わっても本質的には同じ完成盤の軌道に留まる。

PoCでは、完成盤そのものをランダム化探索で生成する。その上でヒント削除順も変える。

今回の実験では各条件200件の盤面文字列はすべて異なった。ただしこれは同型性まで正規化した重複検査ではなく、単純な完全一致がないことの確認に留まる。

### 5.3 正規化・重複除去

全対称変換を考慮した正規形計算は可能だが、PoC開始時点で必須とはしない。

まず記録すべき重複単位を分ける。

- 同一seed: 同一問題として扱う
- 盤面が完全一致: 重複として容易に除外できる
- 数字置換・回転・反転等だけが異なる同型問題: 将来必要なら正規化して除外する
- 同じ完成盤を共有するがヒント配置が異なる問題: 別問題として許容するかは製品方針

実プレイで「似た問題ばかり」と感じる兆候が出る前に、高コストな完全正規化を必須要件にしない。

## 6. 難易度制御

### 6.1 ヒント数だけでは決めない

ヒント数と難易度には傾向があっても、単調な対応関係はない。17〜18ヒントの問題が、21〜22ヒントの難問より簡単な例も報告されている。

したがって、次のような実装は採用しない。

```text
40ヒント以上 -> easy
30ヒント台    -> normal
20ヒント台    -> hard
```

ヒント数は生成条件・メタデータとして利用できるが、難易度の正本にはしない。

### 6.2 人間向け解法器を別に持つ

機械的な一意解確認用探索器と、人間向け難易度評価器は目的が異なる。

**一意解確認用探索器**

- 全探索してよい
- 仮置き・バックトラックしてよい
- 速く0/1/2解以上を判定することが目的

**人間向け解法器**

- 許可した解法テクニックを順番に適用する
- 各ステップで使ったテクニックと候補削除・数字確定を記録する
- 仮置きを許すかどうか自体を難易度方針として扱う
- 手順の複雑さ・依存関係を難易度評価へ使う

Pelánekの研究でも、人間の解答時間に対する難易度推定では、個々の論理操作の複雑さだけでなく、解法ステップ間の依存構造が重要とされている。

### 6.3 後続PoCでの最小構成

最初から全テクニックを実装しない。次の順で段階的に追加し、実際の問題群がどう分類されるかを見る。

1. 候補が1つだけのマス（Naked Single）
2. 行・列・ブロック内で数字の入る場所が1つだけ（Hidden Single）
3. Locked Candidates（Pointing / Claiming）
4. Naked Pair / Hidden Pair
5. 必要に応じてX-Wing等

各テクニックに固定の点数を置くだけでなく、少なくとも次を記録する。

- 使用回数
- 最も高度なテクニック
- 各ステップで検討対象となる候補数
- 連鎖の長さ
- 解法が途中で止まったか

最終的な難易度区分・算出式は #28 では決めず、生成した実問題とプレイ結果を見て調整する。

### 6.4 難易度指定生成

将来的な `generatePuzzle(seed, difficulty)` は、難易度から直接盤面を構成するのではなく、候補生成と評価を組み合わせるのが扱いやすい。

```text
候補問題を生成
  ↓
一意性を確認
  ↓
人間向け解法器で評価
  ↓
指定難易度なら採用
  └─ 違えば次の候補
```

この方式なら、難易度定義を変更しても完成盤生成や一意解判定を作り直さずに済む。

## 7. 基本ルールと付加機能の境界

| 項目 | 位置付け | 備考 |
|---|---|---|
| 9×9 / 3×3 / 1〜9制約 | 基本ルール | 完成盤の妥当性 |
| 初期ヒント固定 | 基本ルール | プレイヤーは変更不可 |
| 一意解 | 提供問題の品質条件 | 生成・検証時に保証 |
| 数字入力・消去 | 基本プレイ操作 | 誤答でも入力自体は受理 |
| 競合検出 | ルールから導出 | 正解を知らず判定可能 |
| クリア判定 | 基本ルール | 全制約を満たす完成盤 |
| 候補数字（メモ） | 付加プレイ機能 | クリア条件へ影響しない |
| 自動候補 | 補助機能 | 現在盤面から導出 |
| ミス数 | 成績計測 | 一意解との不一致イベント |
| 誤答の即時表示 | 補助・UI方針 | ミス計測と分離 |
| Undo / Redo | プレイ履歴機能 | ルール外 |
| やり直し | プレイ管理 | ルール外 |
| ヒント | 補助機能 | 人間向け解法器を利用可能 |
| 難易度 | 問題メタデータ | 人間向け解法手順から評価 |

## 8. 実装へ持ち込む責務分割

#3 のディレクトリ方針に沿うと、`frontend/src/games/nanpure/game/` 内で少なくとも次の責務を分けて検証できる。

```text
盤面・問題表現
  ├─ 初期ヒント
  ├─ 完成解
  └─ プレイ盤面

制約検証
  ├─ 候補計算
  ├─ 競合判定
  └─ クリア判定

機械解法探索器
  ├─ 解探索
  └─ 0 / 1 / 2解以上の判定

問題生成器
  ├─ 完成盤生成
  ├─ ヒント削除
  └─ seedによる再現

人間向け解法器
  ├─ テクニック適用
  ├─ 解法手順記録
  └─ 難易度評価材料

プレイ状態
  ├─ 回答
  ├─ 手動候補
  ├─ ミス
  └─ Undo等の履歴
```

機械解法探索器と人間向け解法器は統合しない。前者は完全性と速度、後者は人間の思考過程を説明可能に再現することが目的である。

## 9. #5 の後続実装順

調査結果から、#5 は次の縦方向に分解するのがよい。

1. **盤面表現・制約検証・一意解探索を実装する**
   - 問題/完成盤の表現
   - 候補計算
   - 競合・完成盤検証
   - 解数0/1/2以上の探索
2. **seedから一意解ナンプレを生成する**
   - 決定的疑似乱数
   - 完成盤生成
   - ヒント削除
   - 一意解保証
   - 生成性能を計測
3. **ナンプレの基本プレイを成立させる**
   - 盤面UI
   - 数字入力・消去
   - 初期ヒント固定
   - 候補数字
   - 競合・ミス・クリア
   - Undo / やり直し
4. **人間向け解法器で難易度評価材料を生成する**
   - 基本テクニックから段階追加
   - 解法手順の記録
   - テクニック、手順数、依存関係等の評価材料を出力
   - 難易度帯別の生成採用率・総生成時間を計測できるようにする
5. **ヒント・プレイ結果の生データを一連のプレイへ統合する**
   - 解法手順を使ったヒント
   - 解答時間、ミス、ヒント使用回数
   - クリア後表示へ渡すゲーム固有結果

難易度評価を問題生成器へ埋め込む前に、まず生成器と人間向け解法器を独立して成立させる。これにより、難易度定義の調整で生成・一意解確認を壊さずに済む。難易度区分そのものの検証は #7、プレイ評価式の検証は #8 で両ゲームを比較して行う。

## 10. 判断

| 調査項目 | 判断 | 根拠 |
|---|---|---|
| 基本ルール | GO | 9×9クラシックとして固定可能 |
| 完成盤生成 | GO | ランダム化探索で十分高速 |
| 一意解確認 | GO | 2解打ち切り探索で十分高速 |
| ヒント削除生成 | GO | 28ヒント200/200件を短時間で生成 |
| 低ヒント数の直接制御 | 条件付きGO | 貪欲削除1回では24以下の目標到達率が落ちるが、PoC要件ではない |
| 問題多様性 | GO | 本質的に異なる完成盤が約54.7億クラスあり、ランダム完成盤生成も可能 |
| 同型除去 | 後回し | 初期PoCでは完全正規化の必要性が低い |
| 人間向け難易度制御 | PoCへ進む | 既存研究・手法があり、機械探索と分離して評価可能 |
| ヒント数だけの難易度 | NO-GO | 人間難易度を十分に表さない |
| 候補・Undo・ヒント等の分離 | GO | 盤面制約と独立したプレイ機能として扱える |
