# 画面設計

`docs/画面/` は、pa-zzle の**画面種別ごとの体験・情報構造・共通とゲーム固有の境界・成立条件**を定義する正本である。

## 位置づけ

画面設計は上位の正本を具体化する。

- `APP.md`: アプリ全体でどの体験を提供するか。
- `GAME.md`: 個々のゲームで共通して守るゲーム体験。
- `DESIGN.md`: 視覚、情報階層、操作フィードバック、動きの全体原則。
- `docs/画面/*.md`: 特定の画面種別で、上位原則をどう成立させるか。
- `frontend/styles/globals.css` の `@theme`: 正確なデザイントークン値。
- 実装コード: コンポーネントの正確な公開API、型、ルーティング、振る舞い。

上位の正本と矛盾する場合は `APP.md` / `GAME.md` / `DESIGN.md` を優先する。

## 文書の単位

ルートやゲーム単位ではなく、**同じ役割を持つ画面種別**ごとに1ファイルを作る。

例:

- ゲーム一覧
- 開始条件選択
- プレイ
- 結果

ゲームごとに見た目や入力方法が異なっても、画面としての役割が同じなら同じ文書で扱う。逆に、役割が異なる画面を実装都合だけで同じ文書へまとめない。

## 各画面文書に書くこと

必要な項目だけを使い、画面固有の判断を記述する。

### 役割

- なぜその画面が存在するか。
- アプリの体験フローの中で何を受け取り、何を決めて次へ渡すか。

### 達成したい体験

- 画面を見た利用者に何を理解・判断してほしいか。
- 画面を離れる時に何が成立しているべきか。

### 視覚・情報の優先順位

- 最初に何を見てほしいか。
- 次に何を認識してほしいか。
- 何を補助情報として退かせるか。

### 情報と操作

- 必須の情報・操作。
- 通常は置かない情報。
- 操作可能な範囲やフィードバックに必要な意味。

### 共通とゲーム固有の境界

- アプリ共通層が所有する意味と振る舞い。
- 各ゲームが所有する題材、視覚、入力、ルール由来の差分。
- 共通化してはいけないもの。

### レスポンシブ・操作反応

- スマートフォンを基準にした成立条件。
- PCで広い画面をどう使うか。
- hover / press / focus など、操作されたことを返す方法。

### 成立条件

- 実装・レビュー・実ブラウザ確認で満たすべき観測可能な条件。

## 書かないこと

- `APP.md` / `GAME.md` / `DESIGN.md` の一般原則の再掲。
- Tailwind のクラス名や正確なトークン値。
- TypeScript の props や型定義の複製。
- 一つのゲームだけに由来する実装詳細を、全ゲームの規格として固定すること。
- 制作・実装手順。
