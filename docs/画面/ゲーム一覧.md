# ゲーム一覧画面

## 役割

ゲーム一覧画面は、複数のゲームから**次に遊びたいゲームを見つけて選ぶ画面**である。

各ゲームのルール、開始条件、成績を詳しく確認する場所ではない。ゲーム同士の違いを認識し、興味を持ったゲームを選択して、そのゲームの開始へ進むための入口として扱う。

ゲームを選んだ後は、そのゲームに開始前の選択が必要なら開始条件選択へ進み、不要なら直接プレイへ進む。

## 達成したい体験

利用者が次を長い説明に頼らず行えることを目指す。

1. どのようなゲームが遊べるか見渡せる。
2. ゲーム同士が異なる遊びであることを視覚的に認識できる。
3. 興味を持ったゲームを迷わず選べる。
4. 画面外にも候補がある場合、それに気づいて探索できる。
5. 選んだゲームの次の体験へ自然に進める。

ゲーム数が増えたときも、説明や補助情報を増やして一覧性を補わない。各ゲームを識別するために必要な情報を保ちながら、候補を探索できる構造で成立させる。

## 視覚・情報の優先順位

優先順位は次の順とする。

1. ゲーム固有の代表表現。
2. ゲーム名。
3. ゲームを選択するために必要な操作上の手掛かり。
4. ゲーム選択以外の補助情報・補助操作。

ゲーム名や説明文だけでゲームの違いを理解させず、ゲーム固有の代表表現を識別の主な手掛かりとする。

代表表現は、プレイ画面や開始条件選択画面を縮小したものではない。ゲームを識別するために必要な視覚言語を、一覧で比較・探索できる情報量へ縮約したものとする。

具体的なピクトグラムやゲーム固有表現の描画原則は `DESIGN.md` を正本とする。

ゲーム一覧、開始条件選択、プレイへ進むにつれて、ゲーム固有表現は段階的に具体化する。

- ゲーム一覧では「何のゲームか」を識別できる。
- 開始条件選択では「どのような体験を選ぶか」を比較できる。
- プレイでは実際の問題・状態・操作を扱う。

一覧で後続画面の情報まで先取りしない。

## 情報と操作

通常必要なのは次の情報・操作である。

- 選択可能なゲーム。
- 各ゲームのゲーム名。
- 各ゲーム固有の代表表現。
- ゲームを選択し、次の画面へ進む操作。

ゲームの代表表現とゲーム名は、どのゲームを選ぶ操作なのかを一体として認識できるようにする。

ゲームを選ぶために中間的な選択状態を設けることは必須ではない。

追加の情報や表現を確認してから開始すること自体に利用者上の意味がある場合は中間状態を持てるが、同じ情報を見せ直すだけのために操作を一段増やさない。

### 補助情報

補助情報は、ゲーム固有の代表表現とゲーム名だけでは、利用者がゲームを識別・選択できないことを確認した場合に追加する。

「情報が存在する」「将来使いそう」「表示する場所が余っている」といった理由では追加しない。

通常は次を一覧へ常設しない。

- ゲームルールや遊び方の説明。
- 開始条件や難易度。
- プレイ中に使う情報。
- プレイ評価。
- 自己ベスト。
- プレイ履歴。
- ランキングや他利用者との比較。
- seed、内部ID、内部特徴量などの診断情報。
- ゲームの識別に不要な説明文。

これらの機能へ進む導線が必要な場合も、ゲームを探して選ぶという画面の主目的より強くしない。

## 一覧向けのゲーム固有表現

一覧では、そのゲームで実際に見る・触る対象との意味的なつながりを持つ代表表現を使う。

実際の盤面やゲームオブジェクトをそのまま縮小する必要はない。一覧での識別に不要な状態や細部は省き、そのゲームらしさを識別するために必要な要素へ縮約する。

縮約するときは次を守る。

- ゲームを識別する主要な形・構造・対象を失わせない。
- 別のゲームにも当てはまる汎用記号だけへ置き換えない。
- 一覧だけのために、実際のゲームには存在しない特徴を作らない。
- すべてのゲームを同じ構図・同じ図形へ無理に揃えない。
- 他のゲームと並べた実表示サイズで識別性と視覚的な強さを確認する。

一覧専用の表現を持てるが、ゲーム本体とは異なる別の視覚人格を作らない。

## 共通とゲーム固有の境界

### 共通層が所有するもの

複数ゲームで同じ意味と振る舞いを持つものだけを共通層で扱う。

- 複数のゲームを一覧として提示すること。
- 候補を探索できること。
- ゲーム名とゲーム固有の代表表現を、一つのゲーム候補として扱うこと。
- どこが操作可能か理解できること。
- ゲームを選択して次の画面へ進むこと。
- 一覧の配置とスクロール。
- hover / press / focus など、共通UIとしての操作反応。
- ゲーム同士を比較・探索できるための基本的な情報階層。

共通層はゲーム固有表現の内部構造や意味を解釈しない。

一覧で表示するためだけに、各ゲームの盤面、駒、セル、ボトルなどを共通のデータ構造や共通UIへ変換しない。

### ゲーム側が所有するもの

- ゲーム名。
- 何を見せればそのゲームを識別できるか。
- ゲーム固有の代表表現。
- 題材に由来する形、構造、色。
- ゲームを識別するために必要な視覚情報。

代表表現はゲーム本体のコンポーネントをそのまま再利用する必要はない。

共通層との境界を保ちながら、一覧に適した専用表現をゲーム側で所有できる。

## レスポンシブ・探索

### スマートフォン

スマートフォンでは、ゲーム候補を横方向に探索できる一覧を基本とする。

ページ全体をゲーム数に比例して縦長にすることで候補数の増加を吸収しない。

横方向へ続く候補がある場合は、利用者が画面外にも候補があると理解できることを成立条件とする。横スクロールできる実装であることだけでは十分としない。

候補数を増やすために、ゲーム固有の代表表現を識別できない大きさまで縮小しない。

横スクロールだけで将来あらゆるゲーム数に対応できるとはみなさない。現在想定する一覧体験では扱えない規模になった場合は、分類・検索など別の探索方法をその時点で設計する。

### PC

PCでは、スマートフォン向けの一覧を狭い領域へそのまま置かない。

広い画面は、同時に認識できるゲーム候補を増やすことや、各ゲームの代表表現を識別しやすい大きさで見せることへ使う。

具体的な配置をスマートフォンと同一にする必要はない。

PCでも、共通UIや余白そのものよりゲーム候補が画面の主役になることを保つ。

## 操作反応

ゲーム候補は、どこが操作対象かを視覚的に理解できるようにする。

代表表現やゲーム名の一部分だけを小さな操作対象にせず、一つのゲーム候補としてまとまりを持たせる。

hover / press / focus では、操作対象と入力を受け付けたことを明確に返す。具体的な反応は `DESIGN.md` の操作原則に従う。

## 成立条件

ゲーム一覧画面は、少なくとも次を満たす。

- 利用者が、どのようなゲームがあるか見渡せる。
- 長い説明を読まなくてもゲーム同士の違いを認識できる。
- 各ゲームが、ゲーム自身につながる固有の代表表現を持っている。
- 代表表現が実盤面の単純な縮小になっておらず、一覧での識別に必要な情報量へ縮約されている。
- 代表表現とゲーム名から、どのゲームを選ぶ操作なのか理解できる。
- ゲームを選ぶためだけの不要な中間操作を要求していない。
- 複数ゲームを並べても、それぞれのゲーム固有性を失っていない。
- 共通UIがゲーム固有表現より強く主張していない。
- 画面外に候補が存在する場合、その存在と探索方法が分かる。
- スマートフォンでは横方向の一覧を操作しやすく、候補を識別できる大きさが保たれている。
- PCでは広い画面が候補の認識・比較へ使われている。
- 一覧へ開始条件、ルール説明、成績、診断情報を先回りして載せていない。
- 一覧より開始条件選択、開始条件選択よりプレイの方が、ゲーム固有表現を具体的に扱える。
- hover / press / focus などの操作反応によって、操作対象と入力結果を理解できる。
- 新しいゲームを追加するとき、既存ゲームの画面構成や内部実装を模倣しなくても、そのゲーム自身に適した代表表現を追加できる。
