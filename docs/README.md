# 文書

pa-zzle の文書は、同じ仕様を複数箇所へ複製するのではなく、判断の種類ごとに正本を分けて管理する。

新しいパズルや画面を追加するときは既存実装を規格としてコピーせず、上位の正本から必要な判断を導く。既存実装と正本が食い違う場合も、現在の実装を正当化するために文書を合わせない。

## 正本の責務

### [`APP.md`](../APP.md)

複数のパズルを一つのアプリとして提供するための、アプリ全体の体験を正本化する。

ゲームの発見、開始、結果、記録、次の行動など、ゲームをまたいでも同じ意味を持つ体験と、アプリ共通層が担う責務を書く。

個々のパズルのルールや操作、特定画面の情報構造、具体的な視覚表現はここで固定しない。

これにより、新しいパズルを追加してもアプリ全体の体験がばらばらにならず、同時にゲーム固有の事情をアプリ共通仕様へ押し込まないことを担保する。

### [`GAME.md`](../GAME.md)

pa-zzle に載せる各ゲームが、ゲームとして共通して守る体験を正本化する。

プレイヤーが何を見て考えるか、操作と反応、ゲーム固有の題材、難易度、結果の受け取り方など、パズルの種類が変わっても守る原則を書く。

特定パズルの基礎仕様や難易度判定式、特定画面の構成、具体的な色や寸法はここで固定しない。

これにより、新しいパズルが技術的に動くだけのものにならず、既存パズルの実装をそのまま「ゲーム共通仕様」として一般化しないことを担保する。

### [`DESIGN.md`](../DESIGN.md)

`APP.md` と `GAME.md` の体験を、視覚、情報階層、操作フィードバック、動きへ翻訳する原則を正本化する。

アプリ共通UIの視覚人格、情報の強弱、色の意味、面・文字・動きの扱いなど、画面やゲームをまたいで同じ意味を持つデザイン判断を書く。

特定画面の情報構造や、特定ゲームの盤面・駒などに由来する表現、正確なデザイントークン値はここで固定しない。正確な値は `frontend/styles/globals.css` の Tailwind CSS `@theme` を正本とする。

これにより、新しい画面やパズルでも既存画面の見た目をコピーせず、一貫した原則から表現を設計できることを担保する。

### [`画面/`](画面/)

ゲーム一覧、開始条件選択、プレイ、結果、記録など、画面種別ごとの設計判断を正本化する。

その画面が何のために存在するか、利用者がそこで何を達成するか、何を主要な情報・操作として扱うか、アプリ共通とゲーム固有のどちらが責務を持つかを書く。

全画面に共通の章立てや部品構成は規定しない。特定パズルだけに必要なルールや操作を、画面種別そのものの仕様として固定しない。

これにより、新しいパズルを既存のウォーターソートやナンプレの画面構成へ機械的に合わせず、同じ役割の画面として必要な一貫性だけを保つ。また新しい画面種別を追加するとき、その役割が既存画面とどう異なるかを設計上説明できる状態を保つ。

### [`パズル/`](パズル/)

個々のパズルについて、採用や実装の判断に必要な調査・検証知見を残す。

基礎仕様候補、問題生成、解法、成立性、難易度制御、スマートフォンでの操作検証、導入判断など、そのパズル固有の不確実性を調査した結果を書く。

調査時点の仮説や検証結果を、現在仕様の正本として固定しない。実装後の現在仕様を確認するときは `GAME.md`、対象の画面正本、コード・設定を優先する。

これにより、パズル固有の知見を失わずに、新しいパズルで得た事情をアプリやゲーム全体の共通仕様へ不用意に昇格させないことを担保する。

### [`立ち上げ/`](立ち上げ/)

アプリ立ち上げ期のPoC、仮説、比較、正本化までの経緯を残す。

現在の判断に至った背景を追跡するために使い、長期的な現在仕様の正本として保守しない。正本へ昇格した内容は `APP.md`、`GAME.md`、`DESIGN.md` などを優先する。

### [`adr/`](adr/)

重要な技術・設計判断について、選択肢、判断理由、結果を残す。

ADRは「なぜその判断をしたか」を追跡するための記録であり、現在の仕様そのものを重複して保持しない。現在仕様は対応する正本・コード・設定を参照する。

### [`メモ/`](メモ/)

他の正本や履歴文書へ置くほどの責務を持たない、開発上の参考情報を置く。

メモだけを根拠に製品仕様や設計契約を決めない。継続して守る必要が生じた内容は、責務に対応する正本・規約・手順へ移す。

## 新しいパズル・画面を追加するとき

新しいパズルでは、まず `APP.md` と `GAME.md` に反しないゲーム体験を設計し、パズル固有の不確実性は `docs/パズル/` で検証する。画面として共通の役割がある部分は対象の `docs/画面/` を参照し、ゲーム固有の題材・ルール・操作まで既存ゲームへ合わせない。

新しい画面種別では、まず `APP.md` / `GAME.md` 上で必要な役割を確認し、その画面固有の目的・情報・操作・責務境界を `docs/画面/` の正本として定義する。既存画面のレイアウトや部品構成を、新しい画面を作る理由にはしない。

視覚表現は `DESIGN.md`、正確なデザイントークン値は `@theme`、実装上の型・API・振る舞いはコードと設定を正本とする。文書にはそれらから機械的に確認できる内容を重複して固定しない。
