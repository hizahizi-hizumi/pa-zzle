# プロダクト文書

このディレクトリは、pa-zzle の現在のプロダクト定義の正本を置く。

## 構成

```text
利用者要求
   ├──→ システム要件 ──→ 仕様 ──→ 画面 / 実装
   └──→ ユーザーストーリー ──→ 受入条件
                 └────────→ 画面
```

利用者要求は利用者が実現したい状態を、システム要件はそのために製品が保証する能力・性質を定義する。ユーザーストーリーは要求を具体的な利用行動として切り出し、受入条件はその行動・価値が成立したと判断する条件を定義する。仕様は採用された要件を現在の具体的な契約へ落とし、画面は要求・要件・仕様を利用者との接点へ統合する。

上流は下流の実現方法を先回りして固定しない。下流は、どの上位目的・要件を実現する判断かを辿れるようにする。

各文書群の意味・粒度・含める情報は、それぞれの README を正本とする。共通テンプレートは設けない。

## 正本の原則

- 同じ事実を複数の文書で正本化しない。
- 現在の実装を正当化するために上位文書を書き換えない。
- 実装から機械的に導ける型・API・設定値はコードや設定を正本とし、文書へ複製しない。
- 調査・検証から採用した結論だけを適切なプロダクト文書へ反映する。
- Issue は作業範囲と完了条件を管理し、恒久的なプロダクト仕様の正本にはしない。
- 変更時は意味が変わった層だけを更新する。

## 識別子と参照

利用者要求、機能要件、非機能要件、ユーザーストーリー、仕様、受入条件、画面は、それぞれ `RQ-nnn`、`FR-nnn`、`NFR-nnn`、`US-nnn`、`SPEC-nnn`、`AC-nnn`、`SCR-nnn` のリポジトリ内で一意な識別子を持つ。番号に機能名・パズル名・開発段階などの意味を埋め込まず、一度割り当てた識別子は移動や改名でも変更・再利用しない。

識別子体系は文書種別の責務を識別できることを優先し、機能要件と非機能要件を同じ名前空間へ畳まない。

参照は原則として下位から上位へ持つ。システム要件は関連する利用者要求、ユーザーストーリーは関連する利用者要求・システム要件、仕様は関連するシステム要件、画面は関連する利用者要求・ユーザーストーリー・システム要件・仕様、受入条件は検証対象となる利用者要求・ユーザーストーリー・システム要件を参照する。双方向の対応表は持たない。
