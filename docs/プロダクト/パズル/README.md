# パズル仕様

パズルごとに `PZL-nnn` の識別子を持つ。ファイル名と文書の表題には同じ識別子を付け、YAML フロントマターの `id` と一致させる。

パズル仕様は、コードからは読み取れない、そのゲーム固有の設計判断と意図を残すための文書とする。実装の説明書にはしない。

- コードとテストで確認できるルール、操作手順、問題生成条件、計算式、閾値、配点の数値は書かない。
- 何を楽しませたいか、何を先回りして伝えないか、どの挑戦やプレイを重視するかを残す。
- 共通仕様・`GAME.md`・`DESIGN.md` を繰り返さず、パズル固有の判断だけを書く。
- 先に決まりを短い一文で書き、必要な理由や補足だけを子リストに置く。
- 確認できない意図を推測して書き足さない。調査や比較の過程は `docs/パズル/導入調査/` に置く。

## 記述形式

各パズルは、次の大見出しをこの順番で持つ。固有の判断がない項目には「個別の設計判断なし。」と書き、埋めるための説明を足さない。

1. `## 遊びの核`: 何を考え、発見し、楽しむゲームにするか。
2. `## 出題方針`: どんな問題体験を提供し、どんな偏りやつまらなさを避けるか。生成条件は書かない。
3. `## プレイ体験`: 操作、知らせ、補助、表現について、守るべきゲーム固有の判断。実装の振る舞いを列挙しない。
4. `## チュートリアル`: そのゲームで特に体験させたい理解と、共通の進め方から外れる重要な判断。盤面データやステップ表は書かない。
5. `## 難易度`: 基準とするプレイ、挑戦、段階ごとの体験の違い。
6. `## 評価`: 称えたいプレイ、採点観点とその採否、重視する程度、自己ベストに固有の判断。

### 難易度

`## 難易度` は次の小見出しをこの順番で持つ。

1. `### 基準とするプレイ`: どんなプレイを基準とし、何を難しさに含めないか。
2. `### 挑戦`: プレイヤーに必要な判断や読み。
3. `### 段階設計`: 難易度1〜5の挑戦の違いと、段階を分ける判断の理由。

段階ごとの挑戦は、必要なら5行の表で示す。分類条件・特徴量の計算式や数値の境界はコードを正とする。

### 評価

`## 評価` は次の小見出しをこの順番で持つ。

1. `### 称えたいプレイ`: どのような解き方を称えるか。
2. `### 採点項目`: 何を評価し、何を採点から外すか。
3. `### 配点`: どの項目を相対的に重視し、その理由は何か。
4. `### 自己ベスト`: パズル固有の比較方針や、記録を残す判断があればその理由。

配点の点数、減点量、基準時間の係数、評価段階の数値境界はコードを正とし、文書へ複製しない。称えたいプレイから採点項目と配点へつながる判断を読めるようにする。

既存の判断の理由が確認できない場合は、現在の方式を正当化する理由を作らず、別途評価する。
