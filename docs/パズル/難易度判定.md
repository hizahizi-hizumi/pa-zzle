# 難易度判定

## 役割

この文書は、[難易度.md](難易度.md) で定めた人間の挑戦強度という概念を、各パズルで再現可能に扱い、[難易度提供.md](難易度提供.md) で定めた難易度提供へ接続するための判定原則を定める。

各パズル固有の特徴量、閾値、分類規則、実装ファイルは、そのパズルの現在仕様とコードを正とする。

## この文書で実現すること

多数のパズルを追加しても、同じ特徴量や同じ計算式を強制せずに、各パズル固有の挑戦を機械的に扱える状態を作る。

難易度判定を、測りやすい値への置き換えではなく、人間の挑戦を再現可能に近似する責務として保つ。

## 判定の責務

難易度を扱うときは、少なくとも次の責務を分ける。

1. 問題がルール上成立しているかを確認する。
2. その問題が要求するパズル固有の挑戦を分析する。
3. 分析結果から難易度を判定する。
4. 必要な難易度の問題を生成・選択して供給する。

問題成立性、難易度分析、難易度判定、問題供給を、一つの値や一つの処理へ混ぜない。

## 原則

### 各パズルで挑戦の中身を先に定義する

特徴量を探す前に、そのパズルで何を考えることが面白さを生み、何がその挑戦を強くするのかを言語化する。

既存ゲームの特徴量や、取得しやすい数値から逆算して難易度の意味を決めない。

### 特徴量は難易度そのものではない

難易度特徴量は、人間の挑戦強度を機械的に観測するための代理値である。

特徴量が安定して計算できても、人間の挑戦との意味的なつながりを説明できなければ、それだけを難易度判定の根拠にしない。

### 生成条件を難易度へ直結させない

盤面サイズ、色数、ヒント数などの生成条件は、特定の挑戦強度を持つ問題が現れやすい候補領域を作るために使える。

ただし、生成条件の値をそのまま難易度ラベルへ対応させない。生成された問題そのものを分析し、難易度を判定する。

### 計算機上の難しさを人間の難しさと同一視しない

探索状態数、探索時間、最短手数などの solver 内部値は、それが人間の挑戦と対応する理由を説明できる場合に限って難易度の根拠として使う。

計算機にとって探索が重いことだけを理由に、人間にとって難しいと判定しない。

### 必要な次元を一つの数値へ無理に潰さない

パズル固有の挑戦が複数の性質から成る場合、判定内部では複数の観点を保持できる。

利用者向けに一つの難易度帯を返す必要があっても、内部の理由まで一つの加算スコアにすることを共通要件にはしない。

単一指標へまとめる場合は、その指標が挑戦の違いを失っていないことを確認する。

### 判定は再現可能にする

同じ問題を同じ判定条件で評価したとき、同じ分析結果と難易度判定を得られることを基本とする。

人間の主観そのものを実行時判定へ持ち込まず、人間の挑戦との対応を検討した結果を再現可能な判定へ落とす。

### 判定できない問題を高難易度へ押し込まない

現在の分析方法で挑戦強度を評価できない問題は、「難しい問題」とは別である。

評価できない問題を最上位の難易度へ分類して処理を終えず、判定不能として扱える設計を持つ。具体的な状態名や取り扱いは各パズルで定める。

### 問題供給は判定結果へ従う

必要な難易度帯の問題を供給するときは、生成条件だけで帯を決めるのではなく、生成・取得した候補を判定した結果に基づいて選択する。

候補生成と難易度判定は協調してよいが、両者の責務は分ける。

## 各パズルが持つべき具体化

各パズルの現在仕様では、少なくとも次を説明できる状態にする。

- そのパズル固有の挑戦は何か。
- 挑戦強度が何によって変わると考えるか。
- それをどのような特徴で観測するか。
- 問題成立性をどのように確認するか。
- 特徴から難易度をどのように判定するか。
- 判定できない問題をどう扱うか。
- 必要な難易度帯の問題をどのように供給するか。

具体的な実装方式や値はゲームごとに異なってよい。

## この文書で固定しないこと

- 全パズル共通の特徴量
- 全パズル共通の難易度計算式
- 全パズル共通の閾値
- 単一の difficulty score の採用
- 特定の solver や探索方式
- 実装ファイル名やモジュール構成
- モデル識別子や版管理の一律導入
