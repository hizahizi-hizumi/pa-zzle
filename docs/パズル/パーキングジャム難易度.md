# パーキングジャム難易度判定

> **人間校正前の暫定モデル**: `challenge-levers-v1` は問題特徴だけから機械的に分類するモデルであり、ラベルを伏せた人間の実プレイ・ペア比較による校正はまだ行っていない。レバーの境界とレベルの組合せ（閾値）はすべて暫定値として扱う。設計の経緯・比較した案・実測は [パーキングジャム難易度5段階調査](導入調査/パーキングジャム/パーキングジャム難易度5段階調査.md)（第2版、14〜22章）を参照する。

挑戦の定義、難易度の3つの観点、各レベルで利用者が出会う挑戦、分析結果の状態の区別は [SPEC-018](../プロダクト/仕様/パズル/SPEC-018.md) を正とする。この文書は、それを判定する特徴・境界・組合せ、問題集の生成と実測、検証の根拠と限界、校正の計画を扱う。

## 基準とするプレイ条件と分析の範囲

- ルールと操作（スワイプ・車近傍の前後操作）を理解している。
- 不成立操作で試さずに読むことを基準にする。待った・盤面を戻すは解法上不要なので前提にしない。
- 分析は、誰が誰の進路を塞ぐかの遮断関係と、単調削除の全到達状態（最大16台で 2^16 状態）を扱う。表現できるのは「遮断関係を逆向きにたどる読み」と、盤面の静的な形から数えた「読み違いを誘う車」までである。
- 視覚探索そのもの（見落とし・視線移動・密集の見た目）は直接測っていない。盤面の広さと読む対象の数（規模レバー）と、1車線ずれの開口（読み違いレバー）で近似している。

## 問題成立性

生成器 version 2 は、車を1台ずつ「置いた時点で出庫できる」位置へ置く逆向き構築で問題を作り、並列削除で全車を出庫できることを確かめる。成立性（可解性）と難易度の分類は分離している。

## `challenge-levers-v1`

### 特徴

`frontend/src/games/parking-jam/problem/difficulty-analysis.ts` が問題から特徴を求め、`frontend/src/games/parking-jam/difficulty.ts` が次の特徴だけを分類に使う。

| 特徴 | 意味 |
| --- | --- |
| 段数 `dependencyDepth` | その時点で出せる車を全部同時に出す操作を繰り返した回数。段数2は「最初に出せる車を出せば残りは全部出せる」 |
| 最少先行台数の最大 `maximumPrerequisiteVehicleCount` | 各車が出せるようになる到達状態のうち、既に出た車が最も少ないものの台数。その全車での最大 |
| 読み違いを誘う車 `misreadInducingVehicleCount` | 次の3種のいずれかに当たる車。(a) 開口のない側が同じ辺の隣の車線の開口に接している（固定物に塞がれない側だけ）。(b) 両側に開口があり、初期盤面で片側だけ塞がれている。(c) 初期盤面で塞がれていて、最も塞がれ方の少ない進路で最初の遮断車が2マス以上先にある |
| 初期遮断車数 | 初期盤面で出庫できない車の数（車両数 − 初期合法車数） |
| 盤面のマス数・車両数・固定物数 | 規模レバーに使う |

### レバー

挑戦を強めるレバーを3系統に分け、それぞれ強さ1〜3で表す。

| レバー | 1 | 2 | 3 |
| --- | --- | --- | --- |
| 依存の深さ・広さ | 段数2で、最少先行台数の最大が1（塞いでいる車はすぐ出せる） | 段数2で最少先行台数の最大が2以上（2台以上を先に出す車がある）、または段数3で枝分かれ1以下 | 段数4以上、または段数3で枝分かれ2以上 |
| 読み違いの誘発 | 読み違いを誘う車が車両数の1/4未満 | 1/4以上1/2未満 | 1/2以上 |
| 規模 | 広さ（36マス以下=1、48マス以下=2、それより広い=3）と読む対象（車両数＋固定物数が8以下=1、11以下=2、それより多い=3）の弱い方 | | |

枝分かれは「最少先行台数の最大 −（段数 − 1）」で、1本の連鎖だけなら0になる。読み違いは車両数で割った割合なので、車が多いだけでは上がらない。規模は弱い方を取るので、広いだけ・多いだけでは上がらない。

### 難易度1〜5への分類

各レベルは依存と読み違いの強さがちょうど一致し、規模が許す範囲に入る問題だけを採る。各レベルで利用者が出会う挑戦は SPEC-018 の表のとおり。

| レベル | 依存 | 読み違い | 規模（許す範囲） |
| ---: | ---: | ---: | --- |
| 1 | 1 | 1 | 1〜2 |
| 2 | 1 | 2 | 1〜2 |
| 3 | 2 | 2 | 1〜3 |
| 4 | 2 | 3 | 2〜3 |
| 5 | 3 | 3 | 2〜3 |

依存と読み違いを1段ずつ交互に上げ、規模の許す範囲の両端も下げない。したがって上位のレベルはどのレバーも下位より弱くならず、下位の挑戦をすべて含む。規模レバーは単独でレベルを決めない（規模2の問題はレベル1〜5のどれにも入れる）。

### 評価可能範囲・提供範囲

| 判定 | 条件 | 扱い |
| --- | --- | --- |
| 評価不能（`unsupported`） | 車両数が厳密解析の上限16台を超え、最少先行台数を求められない | 提供しない |
| 軽すぎ（`too-light`） | 段数1（全車がすぐ出せる）、または初期遮断車数1以下 | 提供しない。出す順序を読む挑戦がほぼない |
| 重すぎ（`too-heavy`） | 段数7以上 | 提供しない。候補空間の0.1%しか現れず、人が遊んで確かめていないため（根拠は弱い） |
| 組合せ外（`unlisted-levers`） | 上の表のどのレベルの組合せにも当たらない（例: 依存3・読み違い1、依存1・読み違い3、レベル4・5のレバーで規模1） | 提供しない。近いレベルへ寄せると「上位が下位の挑戦を含む」が問題単位で崩れるため |

範囲外の問題をレベル1や5へ押し込まない。現行の候補空間では、生成できた問題の約2割が組合せ外になる。

盤面規模・生成条件はレバーを通してだけ効き、段の条件には直接入れない。

### 機械的に確認していること

- レバーの境界とレベルの組合せ、範囲外の各理由（`difficulty.test.ts`）
- 読み違いを誘う車の3種と最少先行台数を盤面から数えること（`difficulty-analysis.test.ts`）
- 隣り合うレベルでどのレバーも弱まらず、依存か読み違いの一方だけが強まること
- 問題集の各レベルから抜き出した問題が、分析でそのレベルに分類されること（`problem-selection.test.ts`。全問は後述の `--verify`）

これらは分類規則が意図どおり動くことの確認であり、人間にとっての難しさの正しさを示すものではない。

## 問題供給

全レベルを事前生成問題集から供給する（マインスイーパー・ウォーターソートと同じ方式）。プレイ時には難易度判定や全状態の解析をしない。

- 問題集: `frontend/src/games/parking-jam/problem/problem-pool.json`（各レベル1,000問）。生成条件の表と、各問の「条件表の番号・候補番号・生成試行」の3整数を持つ。seed は候補番号から `pj-pool-<候補番号>` として再構成し、本番の生成器で盤面を復元できる。
- 選択: `frontend/src/games/parking-jam/problem-selection.ts` の `selectParkingJamProblemForDifficulty` が、プレイごとの seed のハッシュでレベルの問題集から1問を選び、identity から盤面だけを復元する（`restoreParkingJamProblemWithoutAnalysis`）。
- 生成: `bun run --cwd frontend generate:parking-jam-pool`（`frontend/scripts/generate-parking-jam-problem-pool.ts`）。難易度に依らない候補空間（盤面6×6 / 6×8 / 8×8、車両8 / 11 / 14台、道路開口数3 / 4・幅2 / 3、固定物0 / 1個、遮断配置バイアス0 / 0.5 / 1の216条件）から、車をすべて長さ2として数えた最低車セル数と固定物セル数が盤面の3分の2を超える条件を除いた192条件で、候補番号0, 1, 2, … ごとに各条件最大2生成試行の問題を作り、本番の判定でレベルに分類する。候補番号の周回順・条件の定義順に並べ、各レベルの先頭から、回転・反転で同型の問題を除いて1,000問を採る。レベルで生成条件を絞らないので、各レベルの盤面規模は候補空間での現れやすさ（とレバーの定義）に従う。
- 検証: `bun run --cwd frontend generate:parking-jam-pool -- --verify` は、同梱の全問を復元→分析→判定してレベルの一致と同型重複を確かめ、選択＋復元の時間を測る。

## 旧3段階（`visual-local-load-v1`）の記録

3段階（かんたん / ふつう / むずかしい）時代の記録の扱いは [SPEC-001](../プロダクト/仕様/アプリ/SPEC-001.md) と [SPEC-014](../プロダクト/仕様/ゲーム/SPEC-014.md) を正とする。旧区分をレベル1〜5へ読み替えないのは、旧ラベルとレベルの一対一の対応がないためである（調査 18.5）。

## 難易度選択プレビュー

難易度選択のプレビューは実問題の縮小ではなく、本番盤面と同じ駐車場・車・縁石・道路開口の描画部品で描いた手設計の簡略図とし、判定要因の差だけを見せる。全レベルで同じ4行7列の駐車場を使い、上位のレベルは下位の車と道路開口をすべて同じ位置に残す。

| レベル | 配置（上の行から） | 足したもの | 依存 / 読み違い |
| ---: | --- | --- | --- |
| 1 | `.......` `aa.b...` `cc.b...` `.......`（開口: 右の上3行、上の列4〜6） | 縦の b が a と c の出口を塞ぐ。b はすぐ出せる | 1 / 1 |
| 2 | 同上 | 下辺の列3に1マスの開口。b の隣の列なので、b が下へ出られそうに見える | 1 / 2 |
| 3 | `..dd...` `aa.b...` `cc.b...` `.......` | d が b の出口を塞ぎ、a・c は2段待つ | 2 / 2 |
| 4 | 同上 | 左辺の行1に1マスの開口。a の隣の行なので、a も左へ出られそうに見える | 2 / 3 |
| 5 | `eeddff.` `aa.b...` `cc.b...` `.......` | e・f が d の両側を塞ぎ、a・c は3段待つ | 3 / 3 |

足した開口はどの車の出庫にも使われないので、依存を変えずに読み違いだけを強める。

**規模レバーはプレビューで表さない**。プレビューは難易度選択の行の中の小さな図で、規模レバー2以上（6×8以上かつ車と固定物が9以上）の配置は密集して判定要因の差が読めなくなる。駐車場を広げるだけでは規模レバーの判定値を満たさず、満たさない広さの違いを見せると「広いほど難しい」という単一軸の印象を与えるため、全レベルで同じ大きさにする。このため、プレビューの盤面そのものはレベル4・5の規模の許す範囲に入らない（依存と読み違いはそのレベルの組合せに一致する）。

配置は `frontend/src/games/parking-jam/ui/ParkingJamDifficultyPreview.tsx` に置き、各盤面が盤面検証を通り全車を出庫できること、段数2以上・初期遮断車数2以上であること、依存と読み違いのレバーがそのレベルの組合せに一致すること、隣り合うレベルで両レバーが弱まらず一方だけが強まること、上位が下位の車と開口を含むことをテストで確認する。判定モデルのレバー・境界を変えた場合はこれらの性質を保てるよう配置を見直す。

## 検証根拠と限界

- 根拠は、現行候補空間と固定物拡張空間の計約10,800問での特徴の分布・レバー同士の独立性・案の比較（調査 15〜18章）と、上の問題集の実測である。
- 人間の実プレイによる確認はまだない。読み違いレバー・規模レバーが人の難しさに効くかは仮説である。
- レベル4はレベル3と依存の強さが同じで読み違いだけが上がり、平均合法車率はむしろ高い。人が読み違いを依存1段分の難しさと感じなければ、レベル4がレベル3より易しく感じるおそれがある（調査 18.4）。
- 読み違いを誘う車の3種は盤面の静的な形から数えており、人が実際にどこで不成立操作をするかとは照合していない。
- 規模レバーの境界（36 / 48マス、8 / 11台）は候補空間の刻みに合わせた仮の値である。
- 重すぎの上限（段数7以上）の根拠は弱い。

## 人間校正

未実施である。次を行うまで、レバーの境界・レベルの組合せ・提供範囲は暫定とする。

- ラベルを伏せた実プレイ（[遊び比べ問題](導入調査/パーキングジャム/パーキングジャム難易度5段階_遊び比べ.md) を使う。リンク先にある製品の画面を URL で開く手順はもう使えないため、盤面図で遊ぶ）
- 代表・境界問題、1つのレバーだけが違う対のペア比較
- 完答時間、最初の操作までの時間、不成立操作、待った、盤面を戻した回数、中断の併記

確かめたい観点は調査 20.3 の通り（読み違いレバーが効くか、読み違い3が依存1段分に相当するか、規模が依存・読み違いを揃えても効くか、組合せ外の扱い、下限・上限）。

## 将来の再校正

記録には難易度、判定モデル版、採点版、問題識別情報、プレイ事実を保存している。実プレイ記録が集まったら、同じ判定モデル版の記録について問題識別情報から特徴を復元し、完答時間・不成立操作・待った・盤面を戻した回数と照合してレバーの境界と組合せを見直す。

モデルの意味・特徴・境界を変える場合は `PARKING_JAM_DIFFICULTY_MODEL_VERSION` を更新し、問題集を生成し直す（問題集は判定モデル版を持ち、テストで現在の版と一致することを確かめる）。
