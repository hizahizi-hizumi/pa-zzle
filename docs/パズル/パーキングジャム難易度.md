# パーキングジャム難易度判定

## 目的

パーキングジャムの難易度は、盤面サイズや車両数などの生成条件ではなく、**現在出せる車を見つけながら遮断関係を順にほどく負荷**として扱う。

今回の静的 Parking Jam 3D 型では、合法に出庫できる車を選んだことで後から手詰まりになることはない。したがって、最短手数や「正解手を外す危険度」ではなく、どの車が現在出せるかを見抜くための依存構造を評価する。

## `dependency-v1`

### 特徴量

`frontend/src/games/parking-jam/problem/difficulty-analysis.ts` で次を取得する。

- `dependencyDepth`: 現在出せる車を同時に1層として除いたとき、全車を除くまでに必要な層数
- `initialLegalVehicleRatio`: 初期盤面で出庫可能な車両数 / 全車両数
- `vehicleBlockingEdgeCount`: 車が別車の出口経路を塞いでいる関係数
- `initialBlockedExitDirectionRatio`: 静的に利用可能な出口方向のうち、初期状態で別車に塞がれている割合
- `legalOrderCount`: 合法な車両退出順の総数
- `solutionOrderFreedom`: `log(legalOrderCount) / log(vehicleCount!)`

`solutionOrderFreedom` は1に近いほど順序制約が弱く、0に近いほど強い。

合法順総数は部分集合動的計画法で厳密に数える。初期実装では16台以下を厳密評価対象とし、それを超える問題は `unsupported` とする。

### 分類

初版では、人間が感じる負荷へ直接つながる次の3点を分類に使う。

- 依存が何段続くか
- 最初から出せる車がどれだけ残っているか
- 全体として退出順がどれだけ制約されているか

遮断辺数と遮断出口方向率は診断値として保持するが、初版の分類条件には直接入れない。固定集合ではこれらが依存深さ・解順自由度と重なりつつ局所配置の影響も受けたため、分類条件を増やす根拠にはしなかった。

| 難易度 | 条件 |
| --- | --- |
| easy | `dependencyDepth <= 2` かつ `initialLegalVehicleRatio >= 0.75` かつ `solutionOrderFreedom >= 0.90` |
| hard | `dependencyDepth >= 4` かつ `solutionOrderFreedom <= 0.86`、または `initialLegalVehicleRatio <= 0.60` かつ `solutionOrderFreedom <= 0.78` |
| normal | 上記以外 |

hard を2系統に分けるのは、縦に深い依存連鎖だけでなく、依存深さが3程度でも広い範囲で順序制約が強い盤面があるためである。

## 固定集合での初期校正

generator version 1 の8×8・14台・障害物4個を固定し、候補生成の性質だけを変えた3母集団を各30問生成した。

| 母集団 | `exitProbability` | `blockingPlacementProbability` | seed |
| --- | ---: | ---: | --- |
| open | 0.80 | 0 | `parking-jam-calibration-open-0` 〜 `29` |
| baseline | 0.45 | 0 | `parking-jam-calibration-baseline-0` 〜 `29` |
| dependency | 0.45 | 1 | `parking-jam-calibration-dependency-0` 〜 `29` |

`blockingPlacementProbability` は、逆向き構築中に既存車の出庫経路を新しく塞ぐ配置を優先する度合いである。これは難易度ラベルではなく、目的の特徴を持つ候補を効率よく供給するための生成条件として扱う。

90問の初期分類は次になった。

| 難易度 | 問題数 | `dependencyDepth` 中央 | `initialLegalVehicleRatio` 中央 | `solutionOrderFreedom` 中央 |
| --- | ---: | ---: | ---: | ---: |
| easy | 18 | 2 | 0.857 | 0.940 |
| normal | 59 | 3 | 0.643 | 0.867 |
| hard | 13 | 4 | 0.500 | 0.739 |

等分するために閾値を置いたものではない。easy は浅く自由度が高い、hard は依存が深いか順序制約が強い、という意味を優先した結果である。

## 問題生成・選別

`generateParkingJamProblemForDifficulty` は、難易度ごとに成立率の高い生成プロファイルから候補を作り、`dependency-v1` が指定難易度と判定した問題だけを採用する。

hard 向けでは、逆向き構築時に遮断依存を作る候補のうち、より後から配置された車を塞ぐ配置を優先する。これにより依存を横に増やすだけでなく、縦に連鎖させやすくする。

生成プロファイルは難易度そのものではない。同じ dependency 母集団から easy が生成される例もあり、最終分類は必ず特徴量から行う。

供給安定性の健全性確認として、hard を固定30 seedで連続生成し、30/30件を供給できた。採用された候補の `generationAttempt` は平均4.63、最大12だった。

## 人間確認用の代表・境界問題

固定集合から次を再現可能な確認対象とする。

| 用途 | seed | 依存深さ | 初期合法率 | 解順自由度 |
| --- | --- | ---: | ---: | ---: |
| easy代表 | `parking-jam-calibration-dependency-19` | 2 | 0.857 | 0.956 |
| normal代表 | `parking-jam-calibration-baseline-27` | 3 | 0.643 | 0.862 |
| hard代表 | `parking-jam-calibration-dependency-15` | 4 | 0.571 | 0.739 |
| easy側境界 | `parking-jam-calibration-open-0` | 2 | 0.786 | 0.915 |
| normal側のeasy境界 | `parking-jam-calibration-open-17` | 2 | 0.714 | 0.901 |
| normal側のhard境界 | `parking-jam-calibration-baseline-26` | 3 | 0.571 | 0.798 |
| hard側境界 | `parking-jam-calibration-baseline-0` | 4 | 0.643 | 0.826 |

### 実ブラウザ確認（2026-09-20）

本番プレイUIへ固定seedと固定生成条件を流し、代表3問と境界4問をすべてクリアまで操作した。

- easy / normal / hard の代表問題はすべて最後までプレイできた
- 代表問題を同じ機械的な探索順で操作したとき、不成立操作は easy 9回、normal 36回、hard 78回だった
- easy側境界 → normal側のeasy境界、normal側のhard境界 → hard側境界のいずれも、依存を解く操作上の明らかな逆転は確認しなかった
- 境界問題の不成立操作数は探索順・車両の走査順・方向の試行順に強く依存し、難易度に対して単調ではなかった。したがって不成立操作数を問題難易度の特徴量へ逆輸入しない
- 車の見た目上の密集度も難易度に対して単調ではなかった。初版どおり、依存深さ・初期合法率・解順自由度を主な分類根拠とする
- 360×640 と 1280×800 の双方でプレイし、ページスクロールや画面外へのはみ出し、pageerror、意図しない console.error、failed request は確認しなかった

この確認は ChatGPT の実ブラウザ操作による機械的・視覚的検証であり、人間プレイヤーによる主観的な体感校正そのものではない。人間確認で違和感が出た場合は、閾値だけを動かす前に特徴量・生成方法・分類条件の不足を見直す。

## 将来の再校正

実プレイ結果を取得できるようになったら、少なくとも完答時間、失敗操作数、Undo、やり直し、中断を難易度特徴量と照合する。

モデルの意味または分類条件を変更する場合は `PARKING_JAM_DIFFICULTY_MODEL_VERSION` を更新する。問題生成器の性質を変更した場合も固定集合を再生成し、分布と代表・境界問題を取り直す。
