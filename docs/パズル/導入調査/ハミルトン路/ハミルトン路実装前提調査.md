### 事実と推測の書き分け

根拠の種類を次の見出し語で区別する。

- **事実（リポジトリ）**: 現在のリポジトリの文書・コードから確認したこと。
- **事実（計測）**: 調査用スクリプト・PoC で測った結果。条件と限界は [供給・難易度実験](ハミルトン路供給・難易度実験.md) と [スマホ操作PoC](ハミルトン路スマホ操作PoC.md) に書いた。数値は研究用 Python と合成タッチによるもので、製品コードの性能・人の指の動きを表すものではない。
- **外部知見**: 市販アプリ・公開資料で確認したこと。
- **推測**: 上の3つから導いたが、実プレイや問題集合で検証していないもの。
- **AI判断（仮決定）**: 人間の判断を待たずに本実装を進めるため、関係文書の原則に沿って AI が推奨案で決めたもの。§18「仮決定一覧」に理由・比較した案・最終レビューで判断してほしい点を残す。

### 本実装の進め方（AI判断）

本実装は、各段を前段の上に積む PR スタック（§19）で進める。人間のレビューは全段の実装後に1回だけ行う前提で、途中で判断を求めず、各論点は §18 の仮決定で進める。差し戻し時の手戻りを小さくするため、次を作りの条件にする。

- 5段階の組み合わせ定義（解法器の帯 × 盤面サイズ × 壁率など）はデータとして持ち、分類コードへ埋め込まない（§13.3）。
- 取り残し（孤立マス・分断）の検出は `puzzle/` のルール側に置き、表示するかどうかは UI の1か所で切り替えられるようにする。初期は表示しない（§10.3）。
- ドラッグ入力の補間・不感帯の値は1か所の定数として持ち、実機確認で変えられるようにする（§9.2）。
- スコアの配点は仮置きと明記し、保存するのは生のプレイ事実だけにする（§15）。
- 利用者に見える名称は1か所の定義から参照する（§17）。
- ピクトグラムは採用案だけでなく代替案と検討記録を残す（§19 段07）。

## 3. 守る遊びの核

このパズルで残すべき体験は、**盤面の形（壁・仕切り・始点）だけを手掛かりに、取り残されるマスを出さない1本の道筋を先に見通し、引き切ること**である。

面白さの中心は次にある（事実（計測）: 解法器の推論段階。外部知見: 同型アプリの遊び方）。

- 角・通路・袋小路のように通り方が1通りに決まるマスを見つけ、そこから道を確定させていく
- 袋小路から終点を見抜く
- 道片の両端を結んで輪にしない
- この方向へ進むと未通過の領域が切り離されないかを読む
- 決まらないときに、数手先の破綻を確かめて手を選ぶ

pa-zzle では、UI が「この先は詰む」「ここを通れば正解」と教える体験にしない。取り残しの検出・正解経路との照合は、プレイヤーが読むべき部分を代行する（§10）。

### 3.1 GAME.md の原則への対応（AI判断）

| GAME.md の原則 | ハミルトン路での具体化 |
| --- | --- |
| そのパズルならではの面白さを強める | 道を引く手応え（指に吸い付くように伸び、戻すと縮む）と、塗りが盤面を埋めていく見た目を主役にする。数字・順序付き通過点は足さない（Hidato・Zip と分ける） |
| 盤面が主役 | 盤面をスマホ幅いっぱいに置き、盤面の外にはやり直しの操作だけを置く。経過時間と残りマス数はヘッダーに控えめに置く |
| 盤面で分からせる | 通ったマスの塗り・道の線・先端の印・仕切りの棒で状態を見せる。仕切りに阻まれた・行き止まり・クリアは盤面の動きと形で返し、文章で知らせない（§10） |
| 内部のデータ構造をそのまま描かない | 仕切りを「辺フラグの線」ではなく、マスとマスの間に置かれた短い柵として描く。壁マスは格子から抜けた暗い面として描く |
| 考える部分を奪わない | 取り残し・分断・正解との照合を通常UIで示さない。経路を自動で引く操作（目的マスをタップして自動経路）を持たない |
| 操作の迷いや負荷を難しさにしない | 補間つきドラッグで速い指でもマスを飛ばさない。不感帯で手ぶれによる戻りを防ぐ。ドラッグを必須にせず、タップと矢印キーでも全操作できる（§9） |
| 繰り返し遊べる | 事前生成した問題集から毎回別の問題を出し、回転・反転の同型を除く（§7） |
| 達成とプレイの出来を分ける | クリアは「全マスを1本で通した」こととして返し、スコアは引き直しの少なさと速さで別に返す（§15） |

## 4. 経路接続（PUZZLE-019）との関係

**事実（リポジトリ）**: 経路接続は候補台帳で「実装候補」だが未実装である（`frontend/src/games/` に無い）。[経路接続調査](../経路接続/経路接続調査.md) は全マス被覆を必須とする Flow 型を基礎仕様候補とし、操作は端点からのドラッグと直前セルへの戻りで、本候補の PoC と同じ型である。

**AI判断（仮決定）**: **ハミルトン路は経路接続と独立したゲームとして実装する。** 内部ID は `hamiltonian-path`。

- 理由:
  - 遊びの核が違う。経路接続は「複数ペアの経路の割り振り」が中心で、ハミルトン路はペアの割り振りが無いぶん「1本の道の順序の計画と取り残し回避」に絞られる。端点1組の経路接続は始点・終点指定のハミルトン路と同じになるが、本候補は終点を指定せず仕切りを使う（§5）ため、経路接続の1本モードとは問題の作り方も難易度の中身も違う。
  - 経路接続は未実装で、統合先の契約（問題・入力・難易度）がまだ無い。1本モードとして作るには経路接続の設計を先に決める必要があり、本スタックの範囲を超える。
  - 統合が必要になった場合も、経路接続の実装時に判断できる。入力処理（補間・不感帯・ポインターキャプチャー）は、2つ目のゲームで同じ責務が現れた時点で共通モジュールへ上げる（`game-structure.md`「同じ横断責務が複数ゲームに現れたら、同じ責務名と標準位置を使う」）。
- 比較した案: (a) 独立ゲーム（採用）、(b) 経路接続の1本モードとして実装する（経路接続を先に実装する必要がある）、(c) 経路接続を実装するまで本候補を止める。
- 最終レビューで判断してほしい点: ゲーム一覧に線を引くゲームが2つ並ぶこと（経路接続を実装した場合）を許すか。経路接続の実装時に統合を再検討するか。

## 5. 採用ルール

**AI判断（仮決定）**: 導入成立性調査の推奨基礎仕様候補をそのまま採る。

- 長方形の正方形格子。初期は正方形盤だけ（§14）。
- 各マスは有効マスか壁マス。隣接する2つの有効マスの間に仕切り（通れない辺）を置ける。
- 上下左右に隣接し、仕切りのないマスへだけ進める。
- 指定された始点から、全有効マスをちょうど1回ずつ通る1本の道を引く。終点は指定しない。
- 問題の解は一意。ただしクリア判定は保存解との一致ではなく、規則を満たすかで行う（§12）。

### 初期実装から外す変種

| 変種 | 外す理由 |
| --- | --- |
| 始点のみ・一意解・マス壁のみ（仕切りなし） | 7×7 を超えると一意解の生成が破綻し、できた問題の94%が帯1に偏る（事実（計測）） |
| 始点と終点を指定 | 一意化はしやすいが帯1に偏り、終点が強い手掛かりになる。易しい帯の補助候補として残すが、初期は採らない |
| 始点なし | 一意解がほぼ作れず、始点探しという別の作業が加わる |
| 一意性を問わない（どの正しい道でもクリア） | 市販アプリに近いが、道筋で帯が大きく揺れ（約半数で帯差2以上）、難易度を再現可能に決められない |
| 数字・順序付き通過点（Zip・Hidato・Numbrix 型） | 別のパズル（Hidato）に近づく。挑戦が「数字の連続性」に移る |
| 閉路（全マスを回って始点へ戻る） | 別のルール（ループ系）。始点・終点の推論が無くなる |
| 縦長の長方形盤（例: 8列×10行） | 一意解供給と帯の分布を測っていない。マス数を増やしたいときの次の候補 |

## 6. 問題成立条件

**AI判断（仮決定）**: 次を問題成立条件とする。

1. 盤面は正方形で、有効マスは上下左右の隣接（仕切りを除く）で連結している。
2. 始点は有効マス。
3. 始点から全有効マスをちょうど1回ずつ通る道が存在し、それがただ1つである。
4. 仕切りはすべて、隣接する2つの有効マスの間にある。どの仕切りも、外すと解が一意でなくなる（不要な仕切りを残さない。生成の thin 方式の「不要な仕切りを外す」工程で保証する）。
5. 回転・反転で同型の問題を問題集内で重複させない。
6. 壁も仕切りもない全面盤は供給しない（始点だけで問題が決まり重複するうえ、一意解にならない）。

**導出**: 回転・反転の8通りで、壁マス・始点は位置を、仕切りは辺を変換する。90度回転では横の辺（上下に隣り合うマスの間）と縦の辺（左右に隣り合うマスの間）が入れ替わる。正規化キーは8通りの変換後の（壁・仕切り・始点）のうち辞書順で最小のものとする（段02で実装し、段06で問題集の重複除外に使う）。

## 7. 問題identityと供給方式

本番は**事前生成問題集**とする（リフレクション段06と同じ）。

- 理由（事実（計測））: 一意化（thin）の成功1問あたりの生成時間は 5×5〜8×8 で1.3秒以下だが、高い帯は出現率が低く、8×8 の帯4・帯5は1問あたり約6.7秒（研究用 Python）。プレイ開始時にブラウザーで生成・難易度分析する方式は待ち時間が読めない。
- 事前生成なら、配信前に全問の一意性・難易度分類・同型重複を検証できる。

### 7.1 問題識別情報（AI判断（仮決定））

既存ゲーム（`game-structure.md` の `<Game>Problem` と `<Game>ProblemIdentity` の分離）に揃え、次の形を第一候補とする。

```text
HitofudePuzzleProblem = {
  size: 5 | 6 | 7 | 8,
  walls: 壁マスの位置,
  partitions: 仕切りのある辺（隣接2マスの組）,
  start: 始点の位置,
}

HitofudePuzzleProblemIdentity = {
  generatorVersion: string,
  seed: ProblemSeed,
  conditions: { size: 5 | 6 | 7 | 8, wallRatio: number },
}
```

- `wallRatio` は生成器へ渡す壁率（実験では 0 と 0.15）。取り得る値の一覧は段05・06で分布を見て決め、`problem.ts` に定数として持つ。
- 問題集には問題（壁・仕切り・始点）と、難易度分類・基準時間に使う分析結果（作業の量）を保存し、実行時に生成器・解法器を呼ばない。解の道は持たない（クリア判定は規則で行い、検証では一意解の探索で求め直す）。
- 生成は `games/problem-seed.ts` の `ProblemRandom` で行い、同じ identity から同じ問題を作る。研究用 Python と乱数列は一致しないので、Python の seed で作った問題は再現しない。移植の正しさは、Python が出力した固定盤面に対する解数・解法器の結果の一致で確かめる（段02・段05）。
- 問題集に無い identity（生成器の版が変わった後の古い記録など）は遊び直せない記録として扱う（SPEC-014）。
- 診断ビルドでは、問題 identity を URL で指定して固定問題を開く入口を持つ（リフレクション段03と同じ。段03）。

### 7.2 問題集の規模（推測）

1レベルあたり 500問を目安とする（リフレクションと同じ）。1問は 8×8 で壁マス（64ビット）・仕切り（内部辺112本のビット列）・始点・分析結果程度なので、2,500問でも JSON 数百KB 未満、gzip で数十KB と見込む。実際のバンドル増分は段06で記録する。

生成時間（推測）: 最も出にくい 8×8 の帯5は研究用 Python 1プロセスで1問あたり約6.7秒なので、500問で約1時間、4並列で約15分。製品コード（TypeScript / Bun）の性能は未測定で、段06で記録する。

## 8. 視覚表現

**事実（計測）**: PoC で次を確かめた（[スマホ操作PoC](ハミルトン路スマホ操作PoC.md)「仕切りの見分けやすさ」）。

- 仕切りは暗色の短い棒（マス幅の約16%、両端をマス幅の18%ずつ空ける）にすると、1本ずつ「このマスとこのマスの間」と読め、隣り合う仕切りがつながって迷路の壁に見えることもない。辺いっぱいの太線はつながってL字・T字になり、迷路の壁の断片に見えた。
- 仕切りは道の線より上の層に描くと、道が仕切りに沿って走っても隠れない。始点の印も道より上の層に描く。
- 赤系の仕切りは始点の橙と紛れ、アプリ共通のエラー色と意味がぶつかる。

**AI判断（仮決定）**:

| 要素 | 表現 |
| --- | --- |
| 未通過の有効マス | 明るい地と細いマス境界線 |
| 通過済みのマス | 道の色の淡い塗り。盤面が塗られていく見た目を主役にする |
| 道 | マスの中心を結ぶ太い1本の線（角は丸める） |
| 始点 | 道より上の層に描く塗りの円。道が始まっていない状態でも「ここから」と分かる |
| 先端 | 指の外側からも見える大きさの印（道の色の濃い円と外輪）。先端は指で隠れるため、マス幅に対して大きめにする |
| 壁マス | 格子から抜けた暗い面。マス境界線を描かない |
| 仕切り | 暗色の短い棒（PoC の推奨値）。道より上の層 |

- 色はゲーム固有色として `frontend/src/games/hitofude-puzzle/` 側で持ち、`primary`・`success`・`error` などの共通トークンを流用しない（`DESIGN.md`）。ライト／ダークの両方で確認する。PoC の色（道 `#2e6bd1`、塗り `#d5e4fb`、仕切り `#22201c`、壁 `#3b3833`）は出発点で、`@theme` の値とは別に段04で決める。
- 仕切りと壁マスは「通れない」という同じ意味なので同系の暗色にする（PoC で比1.39。仕切りの両側は有効マスなので壁マスと接して見分けられなくなる場面は少ない）。
- リフレクションの人間レビューでは「パズル画面はもう少し色を使ってよい」との指摘があった（[リフレクション実装前提調査](../リフレクション/リフレクション実装前提調査.md) §9）。道の色を始点から先端へ少しずつ変える案（通った順が見える）を段04で単色案と比べる。
- 迷路（PUZZLE-051 など）とは、迷路側を辺いっぱいの連続線、こちらを短い棒とマスの塗りで描き分ける。ピクトグラムには仕切りを入れず、盤の枠の中に始点から蛇行する1本の道と、まだ通っていないマスを表す淡色の点で表す（段07。[ハミルトン路ピクトグラム検討](ハミルトン路ピクトグラム検討.md)）。

## 9. 操作

### 9.1 操作の割り当て（AI判断（仮決定））

PoC で検証した組み合わせを採る。

| 入力 | 対象 | 結果 |
| --- | --- | --- |
| ドラッグ | 先端から始める | 指の通過した隣接マスへ道を延ばす。直前マスへ戻ると1マス縮む |
| ドラッグ | 道の途中のマス（始点を含む）を押して始める | そのマスまで巻き戻し、続けてそこから延ばせる |
| ドラッグ | 先端に隣接する未通過マスを押して始める | そのマスへ1マス延ばし、続けて延ばせる |
| ドラッグ中 | 道の途中のマス（直前マス以外）へ指が入る | 何もしない（巻き戻さない） |
| タップ | 先端に隣接する未通過マス | 1マス延ばす |
| タップ | 道の途中のマス | そのマスまで巻き戻す |
| タップ | 先端・離れた未通過マス・壁マス | 道は変わらない（§10.1 の反応を返す） |
| 矢印キー | ― | 先端からその向きへ1マス延ばす。直前マスの向きなら1マス縮む |

- ドラッグ中の巻き戻しを直前マスへの戻りに限るのは、手ぶれで蛇行した道の隣の列へ触れると一気に巻き戻り、10×10・σ8px で完走できなくなったため（事実（計測））。途中からの引き直しは「押して始める」操作に限る。
- 目的マスをタップして自動で経路を引く操作は持たない。経路の自動決定は解答の一部を代行する。
- 指を離したらリセットする厳格型は採らない。スマホで指を離す事故に弱い。
- スマホの方向ボタンは置かない。画面を使い、60手前後を1つずつ入力することになる。矢印キーは PC 向け。

### 9.2 入力処理（AI判断（仮決定））

- 補間: 前回の指座標から今回の座標までをマス幅の1/6刻みでたどり、通過したマスを順に処理する。それでも斜めに1マスずれた場合は、仕切りに塞がれていない側の角マス（移動の主方向を優先）を経由する。両側が塞がれていれば延ばさない。補間は指の通過したマスを追うだけで、経路を推測して埋めない。
- 不感帯: 今のマスから隣のマスへ切り替えるのは、指がマスの縁から幅の15%以上内側へ入ったときだけ。
- 指が仕切り・壁の向こうへ外れた後は、先端に隣り合うマスへ戻るまで道を延ばさない。道を推測して回り込ませない。
- 盤面だけに `touch-action: none`、`user-select: none`、`-webkit-touch-callout: none`、`contextmenu` 抑止を指定し、ポインターキャプチャーで盤面外へ出た指も追う。ページ全体には指定せず、盤面外のスワイプはスクロールにする。盤面の祖先に `overscroll-behavior: none` を付けるかは実機確認で決める。
- 補間の刻み・不感帯の幅は1か所の定数として持ち、`puzzle/` のルール（隣接・仕切り・再訪禁止）とは分ける。入力処理は `ui/` に置き、道を変える操作は session の操作（延ばす・縮める・巻き戻す）だけを呼ぶ。
- 待ったの単位は、1ストローク（押してから離すまで）、1タップ、1キー入力とする（PoC と同じ）。

### 9.3 タッチ直後の click（AI判断（仮決定））

**事実（計測）**: Chromium で、指を動かしたまま離した直後に「元に戻す」をタップすると、その `click` が次のタッチまで届かなかった。タッチは `pointerup` で受けると直後のタップでも動いた。

- 盤面は Pointer Events（`pointerdown` / `pointermove` / `pointerup`）だけで扱い、`click` を受けない。
- 盤面の外のボタン（待った・盤面を戻すなど）は、タッチ・ペンを `pointerup` で受け、直後に届く `click` を捨てる。リフレクションの `frontend/src/games/reflection/ui/touch-tap.ts`（`useTouchTap`）と同じ方針。
- 別ゲームの実装は直接 import できない（`game-structure.md`）ため、段04で `useTouchTap` をゲームの外の共通位置（例: `frontend/src/lib/touch-tap.ts`）へ移し、リフレクションとハミルトン路の両方から使う。振る舞いは変えない。
- 比較した案: (a) 共通位置へ移す（採用）、(b) ハミルトン路へ写す（同じ処理が2か所になる）。

### 9.4 ジェスチャー競合（推測）

- 画面端からの戻るジェスチャーは Web ページから止められない。端で**始まる**タッチで判定されるため、盤面の左右に余白（PoC は16px）を取り、操作の開始点を画面端に置かない。
- 長押しによる選択・コールアウトは §9.2 の指定で抑える。
- いずれも実機（iOS Safari / Android Chrome）では未確認。段04の画面確認と最終レビューで確かめる（§20）。

## 10. 誤りの扱いと状態の知らせ

SPEC-017 に沿って、今の盤面とルールだけから分かることは状態の知らせとして示し、正解や先の展開を使うものは示さない。

### 10.1 仕切り・壁に阻まれたとき（AI判断（仮決定））

- 仕切りを越える方向へ延ばそうとした（ドラッグ・タップ・矢印キー）ときは、道を延ばさず、**阻んだ仕切りの棒を短く強調し、先端をその向きへ小さく揺らす**。壁マスへ向かったときは先端だけを揺らす。離れた未通過マスや通れないマスのタップも、先端を揺らして「先端からしか延ばせない」ことを返す。
- 揺れは共通の `playRejectionShake`（`@/lib/motion`）で、揺れ方と長さはゲームが渡す。動きを減らす設定では揺らさず、仕切りの強調だけを返す。
- ドラッグ中は、同じ仕切りに阻まれ続けても1回だけ返し、指が先端のマスへ戻ってから再び阻まれたときに返し直す（反応が連続して盤面が騒がしくならないように）。
- 理由: 仕切りを越えられないことは盤面から事前に分かるので、事前に無効表示を増やす必要はない。操作後に不成立を返す（`DESIGN.md`）。PoC は理由を表示せず「道が延びないだけ」で、指の腹で仕切りが隠れたときに何が起きたか分かりにくかった。
- 阻まれた回数は記録しない（評価にも難易度にも使わない）。

### 10.2 先端から進めないとき（AI判断（仮決定））

- 全有効マスを通る前に、先端に隣り合う未通過マスが仕切り・壁を除いて1つも無くなったら、**先端の印を「行き止まり」の見た目へ変える**（例: 外輪を欠けた輪にし、色を沈める）。文は出さない。巻き戻すと元の見た目に戻る。
- これは「今の盤面からもう進められないこと」（SPEC-017 の状態の知らせ）で、先の展開を使わない。
- 赤いエラー表示にはしない（`DESIGN.md`: ゲーム固有の失敗はゲームの意味で表す）。

### 10.3 取り残し（孤立マス・分断）は示さない（AI判断（仮決定））

先端の他にも、未通過マスで隣り合う未通過マスが1つ以下になったもの（孤立マス・余分な袋小路）や、道で切り離された未通過の領域は、今の盤面から機械的に検出できる。しかし「このまま進んでも完成しない」ことを示すのは**この先の手詰まり**の提示で、SPEC-017 の補助にあたる。取り残しを出さないように読むことがこのゲームの挑戦の中心（§3）なので、通常UIでは示さない。

- 検出関数は `puzzle/` のルール側に置く（解法器の枝刈りにも使う）。表示を足す場合の変更が UI の1か所で済むようにする。
- 比較した案: (a) 示さない（採用）、(b) 孤立マスを薄く示す、(c) 分断された領域を示す、(d) 補助として「取り残しを確かめる」操作を置き、使った回数を結果に示す。
- 最終レビューで見てほしい点: 行き止まりになるまで気づけないことが「UIの迷い」に見えないか。リフレクションでは人間レビューで外周ヒントごとの一致表示（状態の知らせ）を足した経緯がある（[リフレクション実装前提調査](../リフレクション/リフレクション実装前提調査.md) §11.4）。足す場合は (b) か (d) を候補にする。

### 10.4 誤りを記録しない

一意解の問題なので、引いた道が正解の道と違うかを裏で判定できる。しかし表示しないまま「誤り」として数えることはしない。引いて確かめることと、確信して引くことを区別できず、引き直しの回数（§15）が同じ事実をより素直に表すため（AI判断）。

## 11. 補助操作

**AI判断（仮決定）**: SPEC-007 の4つをすべて提供する。呼び名は `games/play-vocabulary.ts` の `PLAY_OPERATION_LABELS` を使う。

| 操作 | 提供 | 振る舞い |
| --- | --- | --- |
| 待った | する | 直前の1ストローク・1タップ・1キー入力を取り消す。巻き戻しも取り消せる。何段でも戻せる。`undoCount` を数える |
| 盤面を戻す | する | 同じプレイのまま、道を始点だけに戻す。経過時間は続く。`restartCount` を数え、待ったの履歴を消す（既存ゲームと同じ） |
| リセット | する | 同じ問題を新しいプレイとして始める |
| 別の問題 | する | 同じ難易度で別の問題を始める |
| 難易度選択・ホーム・検証情報 | する | 既存のプレイメニューと同じ |
| ヒント（次の一手・正しい道の提示） | しない | 通常UIが確定手を提示しない（`GAME.md`、SPEC-017 の補助） |
| 正解との照合 | しない | §10.4 |

- 待ったを提供する理由: 道の途中のマスを誤って押すと、一度に多くのマスを失う（PoC）。巻き戻しを取り消す手段が他に無い。
- 始点を押す巻き戻し（道を始点だけにする）は盤面操作なので待ったで取り消せる。メニューの「盤面を戻す」は待ったの履歴を消す点で違う。
- 比較した案: 待ったを提供しない（タクズ・リフレクション）。盤面を戻すを待ったで取り消せるようにする（PoC。既存ゲームと振る舞いが分かれるため採らない）。

## 12. クリア条件

**AI判断（仮決定）**:

- 道の長さが有効マス数に達した時点でクリアとする。入力処理が隣接移動・仕切り・再訪禁止を保証しているため、プレイ中の判定はこれで足りる。
- 記録・検証では入力処理を信頼せず、`puzzle/` のルールで独立に確かめる: 先頭が始点、連続する2マスが上下左右に隣接し間に仕切りがない、重複なし・壁マスなし、全有効マスを含む（PoC「クリア判定」）。
- 正解の道との一致は求めない。一意解なので結果は同じ。
- クリアした瞬間に入力を止め、始点から終点へ道をたどる短い演出（塗りが通った順に光るなど）を返してから結果画面へ進む（既存ゲームの `clearing` → `result`）。演出は `@/lib/motion` の `playAnimations` で再生し、動きを減らす設定では動かさない。
- 失敗（ゲームオーバー）は無い。

## 13. 難易度

### 13.1 挑戦の定義（AI判断（仮決定））

> 盤面の形（壁・仕切り・始点）から、通り方の決まるマスを見つけて道を確定させ、決まらないときは数手先の破綻（取り残し・分断・輪）を読んで道筋を選び、全マスを1本で通すこと。

挑戦にしないもの（`難易度.md`「挑戦ではない負担」）:

- 盤面サイズ・有効マス数だけによる作業量（なぞる長さ）の増加。単独ではレベルを決めない。
- 仕切りの見分けにくさ・指隠れ・マスの押しにくさ（UIで除く。§8、§9）。
- なぞる速さ・入力回数・所要時間そのもの。

### 13.2 基準とするプレイ条件（AI判断（仮決定））

- ルール（壁・仕切り・始点・全マスを1回ずつ）と操作を理解している。
- 待った・盤面を戻す・巻き戻しは使ってよいが、難易度の基準は「読んで道筋を決めてから引く」プレイとする。引いて詰まってから戻す試行錯誤の量は、難易度ではなくプレイ成績（§15）に表す。
- 行き止まりの状態の知らせ（§10.2）は見えてよい。取り残しの表示は無い（§10.3）。

### 13.3 5段階の組み合わせモデル（AI判断（仮決定））

**単一軸にしない。** 人間向け解法器の帯（推論の深さ）を主軸に、盤面サイズと壁率をレベルごとの「許す範囲」として組み合わせる。

- リフレクション（推論レベル × 盤面サイズ × ピース数）、パーキングジャム第2版（[パーキングジャム難易度5段階調査](../パーキングジャム/パーキングジャム難易度5段階調査.md) §14）と同じく、規模は単独では段を決めないレバーとして扱う。
- 主軸の帯は、[供給・難易度実験](ハミルトン路供給・難易度実験.md) の全体解法帯（人間向け解法器が段階1〜4で止まり、1段仮置きで進めた回数）を使う。帯1 = 局所推論（段階1〜2）だけ、帯2 = 段階3〜4 または仮置き1回、帯3 = 仮置き2〜3回、帯4 = 4〜6回、帯5 = 7回以上。帯が上がると、仮置きから矛盾までの最長手数（中央値）も 6 → 7 → 8 → 16 と伸びた（事実（計測））。
- 補助の条件として、仮置きから矛盾までの最長手数（先読みの長さ）を、レベル4・5で下限として使うかを段05で決める。仮置きの回数だけでは「同じ短い先読みの繰り返し」と「長い先読み」を区別できないため。

仮の組み合わせ定義（段05で TypeScript の解法器の分布を見て境界を調整する。値はデータとして持つ）:

| レベル | 解法器の帯（仮置き回数） | 盤面サイズ | 壁率（生成条件） | 利用者向けの挑戦の説明（案） |
| --- | --- | --- | --- | --- |
| 1 | 帯1（0回、局所推論だけ） | 5×5〜6×6 | 0〜0.15 | 角・通路・袋小路を見つければ、道が次々に決まる |
| 2 | 帯2（1回、または分断・パリティ） | 6×6〜7×7 | 0〜0.15 | 1か所だけ、少し先まで読んで進む向きを選ぶ |
| 3 | 帯3（2〜3回） | 7×7〜8×8 | 0〜0.15 | 何か所かで、数手先の取り残しを読んで道筋を選ぶ |
| 4 | 帯4（4〜6回） | 7×7〜8×8 | 0 中心 | 開けた領域で、先読みを重ねて道筋を決める |
| 5 | 帯5（7回以上） | 8×8 | 0 | 広い開けた盤面で、長い先読みを何度も重ねないと道筋が決まらない |

- 盤面サイズの範囲は、上のレベルほど両端とも下げない（リフレクション SPEC-013 と同じ考え方。見た目に大きい盤面が小さい盤面より易しくなる逆転を避ける）。
- 帯4・5は実質 7×7 以上でしか出ない（5×5・6×6 で帯4以上は各1問）。帯5は 7×7 で1%と出にくいので、レベル5は 8×8 に限る（事実（計測）から AI判断）。
- 壁率はレベルの判定条件ではなく、問題供給の生成条件（候補領域を寄せるレバー）として使う。壁率を上げると易しい側へ寄る（8×8 の帯4〜5は壁率0で 43問中18問、0.15で 50問中0問。事実（計測））。レベルの判定は生成した問題の分析結果で行う（`難易度判定.md`「生成条件を難易度へ直結させない」）。
- 有効マス数の範囲を条件に加えるか（壁で有効マスが減った大きい盤面の扱い）は、段05で分布を見て決める。
- 最終レビューで見てほしい点: レベル1→5で先読みの深さが概ね増えると感じるか。レベル4・5が「盤面が広い」「試行錯誤が長い」だけに感じないか。

### 13.4 評価不能・提供範囲外（AI判断（仮決定））

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| 成立しない | §6 の問題成立条件を満たさない | 問題集に入れない |
| 評価不能 | 一意解だが、解法器が2段仮置き（段階6）でも解き切れない、または計算の上限に達した | レベル5へ押し込まず、提供しない。実験では一意解 1,039問中0問（事実（計測）） |
| 提供範囲外 | 2段仮置きを要する（解けるが、人間が頭の中で2段の仮定を重ねる問題を基準プレイに含めない）。始点から引くだけで迷う場面が無い（描画視点の致命分岐が0）。上の組み合わせのどれにも入らない（`unlisted-combination`） | 提供しない |
| 分類済み | 上の組み合わせのどれか1つに入る | レベル1〜5 |

- 状態名は共通契約（`games/difficulty.ts` の `classified`・`out-of-range`・`unsupported`・`invalid`）を使う。
- 直進率（長さ4以上の直進区間に含まれるマスの割合）の高い問題は単調になりやすい（帯1で目立つ）。これは難易度分類ではなく問題供給（問題集の選び方）で一定割合以下に抑える（段06）。

### 13.6 未解消の論点と仮の扱い

1. **難しさの中身が「先読みの回数と長さ」に偏る**（分断・パリティ推論を要する問題は帯2〜4でも 2〜5%）。仮決定: 初期はこの軸のままにする。段05で、分断・パリティ推論が要る問題の割合を診断値として記録し、最終レビューで高帯が単調な試行錯誤に感じられた場合の改善候補（分断・パリティ推論を要する問題の生成）に使う。
2. **全体解法の視点と、始点から引き進める視点のどちらで帯を決めるか**。仮決定: 主軸は全体解法の帯とする。一意解なので道筋に依らず再現でき、引き進める視点の分析は致命手の判定に全解探索を要して重い。段05で描画視点の分岐分析（分岐数・致命分岐数・分岐の推論段階・最大誤進入）も診断値として求め、2つの視点の対応を記録する。
3. **帯4以上の問題を人が最後まで解いて所要時間を測っていない**。最終レビューの試遊で測る（§20）。

## 14. スマートフォン

**事実（計測）**: 1マスの幅は、390px 幅で 8×8 が44.1px、320px 幅でも35.5px。10×10 は 35.4px（320px で28.5px）で、自動操作は成立したが指隠れと手ぶれの余裕が小さい。12×12 は約30px で指先の円が先端周辺の5マスを覆う。

**AI判断（仮決定）**:

- 提供する盤面は 5×5・6×6・7×7・8×8 の4種。レベルとの対応は §13.3 の組み合わせ定義に従う。サイズを開始条件として利用者に選ばせない（SPEC-004）。
- 10×10 は対象外。実機確認を条件とする上位候補として残し、帯4・5の供給を増やしたいときに足す。12×12 以上は対象外。
- マス数を増やしたい場合は、正方形を大きくするより縦長盤（例: 8列×10行）を先に検討する（§5）。
- 本実装の各UI段では 320 / 360 / 375 / 390px で確認する。PC では盤面を大きくし、広い画面を盤面に使う（`DESIGN.md`「レスポンシブ設計」）。
- 判断と操作の対象（盤面とやり直しの操作）を1つの視野に収め、プレイ中にページをスクロールしなくてよいようにする。

## 15. プレイ評価

### 15.1 良いプレイの定義（AI判断（仮決定））

> 先を読んで道筋を決め、引き直しを少なく、迷わず速く引き切ること。

- 引き直しは、読みが外れて道を戻し、別の向きへ引いたことを表す。挑戦（§13.1）の結果がもっとも直接に表れる事実なので評価に入れる。
- ただし、高いレベルは解法器でも仮置きを要する問題で、引いて確かめること自体を強く罰すると遊び方そのものを罰する。リフレクションでは人間レビューで置き直しの減点をやめ、速さだけにした経緯がある（[リフレクション実装前提調査](../リフレクション/リフレクション実装前提調査.md) §16.3）。そこで速さを主にし、引き直しは軽く数える。

### 15.2 評価に使う事実（AI判断（仮決定））

| 事実 | 評価に使うか | 定義 |
| --- | --- | --- |
| `elapsedMs` | 使う（速さ） | プレイ開始からクリアまで。盤面を戻しても止めない（SPEC-006） |
| `backtrackCount` | 使う（正確さ） | 引き直しの回数。一度引いた道を戻し、同じ位置から**別のマス**へ引いたときに1回と数える。戻してすぐ同じマスへ引き直した場合（手ぶれ・確かめ）は数えない。ドラッグでの戻り、途中マスの巻き戻し、待った、盤面を戻すのどれで戻したかを問わない |
| `retractedCellCount` | 記録のみ | 戻したマスの数の合計。引き直しの大きさを後で分析するため |
| `undoCount` | 記録のみ | 待ったの回数。待ったで戻した結果の引き直しは `backtrackCount` 側で数えるため、二重に減点しない |
| `restartCount` | 記録のみ | 盤面を戻した回数（SPEC-007 の事実）。盤面を戻した後に別の向きへ引けば `backtrackCount` に入る |
| `inputCount` | 記録のみ | ストローク・タップ・キー入力の回数 |

- 「別のマスへ引いたときに数える」のは、手ぶれによる直前マスへの戻り（不感帯でも残り得る）や、引いて戻して同じ道を引き直す確認を罰しないため。
- 仕切りに阻まれた回数・行き止まりになった回数は記録しない（§10）。

### 15.3 評価規則（AI判断（仮決定）。配点は仮置き）

- 100点満点を **速さ 60点 + 正確さ 40点** で配分する（仮置き）。
  - 速さ: 問題ごとの基準時間以内で満点、超過に応じて減点（`games/score.ts` の `SpeedScoreRule`・`calculateSpeedScore`）。基準時間は有効マス数（なぞる量）と解法器の作業の量（仮置き回数など）から問題ごとに決め、**レベルの高さそのものを加点しない**。
  - 正確さ: 引き直し0回で満点。1回ごとに減点し、0点を下回らない。押し間違いを直した程度の引き直しでは評価段階を大きく落とさない減点幅にする。
- 係数・減点幅・基準時間は仮置きで、最終レビュー後の実プレイで校正する。評価は保存したプレイ事実から読み出し時に計算し直す（SPEC-006）ので、配点を変えても記録を移行しない。
- 比較した案: (a) 速さ60/正確さ40（採用）、(b) 速さだけ100（リフレクションの最終形）、(c) 正確さ60/速さ40（バイナリパズル。推測なしで解ける問題を基準にするゲームで、仮置きを要する本候補には重い）、(d) 正確さ・速さ・安定性（待った・盤面を戻す）の3観点（待ったと引き直しが同じ事実を二重に数える）。
- 自己ベストは評価点と基準時間との差で比べ、引き直し回数を比べるかは段09で決める。

最終レビューで見てほしい点: 引き直しを評価に入れることの是非（(b) の速さだけにするか）、配点比率、減点幅、基準時間。

## 16. 記録・再プレイ・診断

### 16.1 プレイ記録（AI判断（仮決定））

- 既存ゲームに揃え、記録 payload にはスコアや段階を保存せず、§15.2 の生のプレイ事実と、難易度、`HitofudePuzzleProblemIdentity`、基準時間の計算に要る問題の作業の量だけを保存する。スコアは読み出し時に再計算する。
- 問題集から引けなくなった記録も、記録した作業の量から評価し、自己ベストの比較に使う（リフレクション SPEC-013 と同じ）。
- 離脱したプレイ（SPEC-015）の進み具合は、離脱時の道の長さと有効マス数、引き直し回数を記録する（`play-attempt.ts`）。

### 16.2 再プレイ

問題 identity から同じ問題を復元し、新しいプレイとして始める。URL の問題IDで同じ問題を遊べる（SPEC-014）。

### 16.3 内部診断（AI判断（仮決定））

検証情報（既存ゲームのプレイメニュー「検証情報」）に次を出す。利用者のプレイ画面には出さない。

- generator version / 問題集の版 / seed / 生成条件（盤面サイズ・壁率）
- 壁マス数・仕切り本数・有効マス数・直進率
- 一意性検証結果と同型正規化キー
- 解法器の結果: 推論段階ごとの発火数、仮置き回数、仮置きから矛盾までの手数、2段仮置きの有無、分断・パリティ推論の有無
- 描画視点の分岐分析（分岐数・致命分岐数・分岐の推論段階・最大誤進入）
- 組み合わせ定義のどの条件でレベルが決まったか（帯・盤面サイズ・壁率）
- 正解の道（検証情報を開いたときに一意解の探索で求める）

## 17. 表示名

**外部知見**（[導入成立性調査](ハミルトン路導入成立性調査.md)「名称・権利」）: 日本語の「一筆書き」は辺を1回ずつ通る型（PUZZLE-054・055）を指すことが多く、本候補をそう呼ぶと混同する。製品名で避ける名称は Fill、One Line / 1LINE、Zip、Flow、ナンバーリンク、Hidato、Numbrix。

**AI判断（仮決定）**: 実装中の利用者向け表示名は作業名「ハミルトン路」とする。正式名は最終レビューの論点とし、公開前に J-PlatPat で登録状況を確認する。

- 内部ID・ディレクトリ・ルート・記録の `gameId` は `hamiltonian-path`（`frontend/src/games/hamiltonian-path/`、`/puzzles/hamiltonian-path`）とする。内部IDと表示名は分離する。
- ゲーム選択・プレイ画面・結果・記録・ページタイトル・ピクトグラムの代替テキストなど利用者に見える名称は `display-name.ts` の `HITOFUDE_PUZZLE_DISPLAY_NAME` 1か所から参照し、差し替えを1か所の変更で済ませる（`game-structure.md`）。
- 「ハミルトン路」は数学の一般用語で特定事業者の商標ではない（推測）が、遊ぶ人に何をするゲームかが伝わりにくい。正式名の候補（例: 「マス巡り」「全マス巡り」「ひとつなぎ」）は、「一筆」を含めない・避ける名称に近づけない・ジャンルとして通じる短い一般名（SPEC-003）の3点で選ぶ。
- 比較した案: (a) 作業名「ハミルトン路」のまま実装（採用）、(b) 実装前に別名を決める。(b) は名称候補の権利確認を実装前に要し、ゲーム体験の検証と切り離せる論点のため後回しにする（リフレクションと同じ）。
- 最終レビューで判断してほしい点: 正式名。URL の `hamiltonian-path` も見直すか。

**人間判断（2026-11-01）**: 表示名は「一筆パズル」にする。「ハミルトン路」は数学用語で遊ぶ人に通じにくいため。PUZZLE-054（辺の一筆書き）との混同より、遊ぶ人に何をするゲームかが伝わることを優先する。内部ID・URL の `hamiltonian-path` は変えない。公開前の J-PlatPat での確認は残す。

**人間判断（2026-11-01）**: 内部ID・URL・`gameId` を `hitofude-puzzle` にする（未公開のうちに表示名と揃える）。seed の接頭辞 `hp-` は変えない。

### 20.2 試遊の手順

1. A の代表と境界の問題（重複を除いて16問）を、レベルを伏せて無作為な順に並べて遊ぶ。
2. 1問ごとに、所要時間・引き直しの回数（結果画面に出る）・待ったと盤面を戻すの回数を記録し、「読んで決めた／引いてから戻した」の感触と、5段階でどのくらい難しかったかを書く。
3. 全問を遊んでから、レベルと照らして論点1 に答える。結果画面の点と評価段階で論点3 に答える。
4. B の問題を遊び、「確かめたいこと」に答える。
5. 遊んでいる間の気づき（取り残しに気づけない迷い、操作の誤り、見た目）で論点2・9〜13 に答える。

ずれがあったときの見直しの順は [難易度](ハミルトン路難易度.md) §12 に従い、閾値（範囲の端）を先に動かさない。

### 20.3 論点（優先度順）

**導入判断に直結するもの**

1. **5段階の順序と、高いレベルの挑戦**（導入成立性調査の保留理由1）
   - 既定: 局所の推論だけで決まるか・仮置きの回数・盤面サイズの範囲の組み合わせで分類し、レベル5 には最も長い先読み9手以上を加える。全体解法の帯を主軸にし、始点から引き進める視点（描画視点）の分析は「迷う分岐が無い問題を出さない」判断だけに使う（[難易度](ハミルトン路難易度.md) §8.2、§13.6）。
   - 比べた案: 帯だけ、盤面サイズだけ、描画視点の分岐数・最大誤進入を主軸に加える（難易度 §8.1、§12）。
   - 判断してほしい点: レベル1→5 で先読みが深くなると感じるか。境界の組で下位と上位に違いを感じるか。レベル4・5 が「盤面が広い」「試行錯誤が長い」だけに感じないか。所要時間・引き直しがレベルの順と系統的に逆転しないか。引き進めるプレイの体感が、全体解法の帯と描画視点のどちらに合うか。
   - 確かめ方: §20.1 A・B、§20.2。
2. **取り残し（孤立マス・分断）を示さないこと**
   - 既定: 行き止まりだけを状態の知らせとして示し、取り残しはこの先の手詰まりを示す補助として示さない（SPEC-020、§10.3）。検出はルール側にあり、表示は UI の1か所で足せる。
   - 比べた案: 孤立マスを薄く示す、分断された領域を示す、補助として「取り残しを確かめる」操作を置き、使った回数を結果に示す。
   - 判断してほしい点: 行き止まりになるまで気づけないことが UI の迷いに見えないか。示すなら「孤立マスを薄く示す」か「確かめる操作」を候補にする。示すと、SPEC-020 の状態の知らせ・難易度の基準とするプレイ・評価も見直す（リフレクションは人間レビューで外周ヒントごとの一致表示を足した）。
3. **評価（引き直しを評価に入れるか、配点、基準時間）**
   - 既定: 速さ60（基準時間以内で満点、基準時間の3倍で0点）+ 正確さ40（引き直し1回 −3点）。待った・盤面を戻すは減点しないが、戻した後に別のマスへ引けば引き直しに数え、待ったで前の道筋へ戻したことも数える。基準時間の中央値はレベル1〜5 で 0:27 / 0:54 / 1:26 / 1:50 / 2:45。自己ベストはスコア・基準時間との差・引き直し回数（[成績評価](ハミルトン路成績評価.md) §2〜§6）。係数はすべて仮置き。
   - 比べた案: 速さだけ100（リフレクション）、正確さ60・速さ40（バイナリパズル）、2倍で0点、引き直し −5点、自己ベストに引き直し回数を入れない（リフレクション）。
   - 判断してほしい点: 引き直しを評価に入れるか。入れるなら1回の重さと、速さとの配分。0点になる倍率。基準時間の水準（熟練者が基準時間の前後で解けるか）とレベルによる偏り。待ったで前の道筋へ戻したことを数えるのが体感と合うか。自己ベストに引き直し回数を入れるか。
   - 確かめ方: §20.2 で遊んだ各問題の結果画面（点・評価段階・内訳）と、記録画面の自己ベスト。
4. **経路接続（PUZZLE-019）と独立したゲームにすること**（導入成立性調査の保留理由2）
   - 既定: 独立ゲーム `hitofude-puzzle`。ドラッグの入力処理は、2つ目のゲームで同じ責務が現れた時点で共通化する（§4）。
   - 比べた案: 経路接続の1本モードとして作る（経路接続の設計を先に決める必要がある）、経路接続を実装するまで止める。
   - 判断してほしい点: 経路接続を実装したとき、ゲーム一覧に線を引くゲームが2つ並ぶことを許すか。経路接続の実装時に統合を再検討するか。
5. **穴のルール（段13）**
   - 既定: 正方形の枠・穴（盤面に無いマス。通れず、通らなくてよい。外周の穴は外形を欠く）・始点のみ・終点自由・一意解。仕切りは使わない（§18「穴のルール（段13）」）。穴は塗らずに盤面の外の地を見せ、通れるマスの外形を太い線で縁取る（§18「穴の描き方（段13）」）。
   - 比べた案: 仕切りで一意にする（段12 まで。利用者の判断で外した）、穴＋仕切り最大2本（易しい側に寄る）、外周に穴を置かない（一意にできる割合が 8×8 で 29%）、始点と終点を指定（帯1 に偏り、終点が強い手掛かり）。
   - 判断してほしい点: 穴の散らばり方と外形の欠けが、見た目と遊びとして受け入れられるか。内側の穴が「盤面に開いた穴」、外周の穴が「外形の欠け」として、同じものに読めるか。ダークの明るい外形の線が強すぎないか。穴の問題の先読みが、仕切りの問題と同じレベルの体感になるか（論点1）。

**難易度・問題集の調整**

6. **レベル5 の「最も長い先読み9手以上」**
   - 既定: レベル5 だけに使い、レベル4 には使わない（難易度 §8.3）。
   - 比べた案: 使わない（短い先読みを7回以上重ねる問題もレベル5 になる）、レベル4 にも使う（段12 の仕切りの問題ではレベル4 の59%が外れた）。
   - 判断してほしい点: 短い先読みの繰り返しがレベル5 の体感と変わらなければ下限を外す。違いが大きければレベル4 にも長さの条件を足す。§20.1 B の `57jur1cicn`・`eafhid0pr7`・`941knflpiv` で比べる。
7. **問題集の生成条件と盤面サイズの範囲**
   - 既定: レベル1 は 6×6・目標0、レベル2 は 7×7・目標0 と 6×6・目標0、レベル3・4 は 7×7・目標4 と 8×8・目標7 が半々、レベル5 は 8×8・目標7 だけ。5×5 は使わない。組み合わせ表（盤面サイズの範囲）は段12 のまま。盤面は 8×8 まで（難易度 §16.5）。
   - 比べた案: レベル1 の盤面サイズを 7×7 まで広げる（局所の推論だけで解ける 7×7 を使える）、レベル5 に 7×7 を含める、9×9・10×10 を足す（9×9 は一意にできる割合 57%・1問20秒、10×10 は一意にできなかった）。
   - 判断してほしい点: レベルの中の盤面の偏りが気になるか。7×7 でもレベル5 の体験になるなら、レベル5 の盤面を広げる（§20.1 B の `66jmss5jja`）。
8. **単調な道（直進率0.6以上）の抑制**
   - 既定: 各レベルで問題集の先頭から数えたどの範囲でも10%以下に抑える（難易度 §9.2）。穴の問題では直進率0.6以上は候補の0〜3%で、抑制はほとんど働かない（難易度 §16.4）。
   - 比べた案: 除き切る、閾値0.7で除き切る、抑えない。
   - 判断してほしい点: 単調に感じないなら抑制を外し、強く感じるなら上限の割合を下げる（§20.1 B の `avv7ta1sv4`）。

**見た目・操作**

9. **実機での操作**
   - 既定: 補間つきドラッグ（1/6マス刻み）・不感帯15%・ドラッグ中の巻き戻しは直前マスだけ・途中マスを押して巻き戻し・盤面の左右に16pxの余白（§9、§18「盤面の左右の余白（段04）」）。Chromium の合成タッチでしか確かめていない。
   - 判断してほしい点: iOS Safari / Android Chrome で、画面端の戻るジェスチャー、プル・トゥ・リフレッシュ、長押し、ドラッグ直後のボタンのタップ、人の指の手ぶれで誤操作が多くないか。8×8 で 320px 幅の1マス36pxが押し分けられるか。
10. **難易度選択のプレビュー**
    - 既定: 盤面の上の3行の帯に、迷わずに引ける所まで（局所の推論で決まる辺の割合の中央値）の道を引き、残りを空けた模式図（[難易度](ハミルトン路難易度.md) §15）。割合は段13 で穴の小さな問題集の値に測り直した（難易度 §16.11。全量の問題集で測り直す）。
    - 指摘: プレイヤーから「進み具合の表示に見える」「壁のある盤や難しさの中身が伝わらない」と言われている。段13 では模式図の作りを変えていない。
    - 比べた案: 問題集の代表問題の盤面まるごと、道の折り返しの回数を増やす帯。
    - 見直す候補（AI の案。描いて比べていない）: 帯に穴を置き、局所の推論で決まる辺を、始点から1本につながる道ではなく、穴や角のまわりの短い道の断片として描く（つながっていないので進み具合に見えにくく、穴が手掛かりになることも見える）。上のレベルほど断片が減る。上のレベルが下のレベルの構成を含む形にするには、帯の穴の置き方をレベルで共有する必要がある。
    - 判断してほしい点: 空けたマスが「先を読まないと引けない所」として伝わるか。「進み具合が少ない」とだけ受け取られないか。模式図の規則的な蛇行が単調に見えないか。作りを見直すか。
11. **道の色**
    - 既定: 道と通ったマスの塗りを、始点の青緑から全マスを通り終える所の紫へ、通った順に移す（§18「道の色（段04）」）。
    - 比べた案: 単色、虹色、道の長さに対する位置で色を決める。
    - 判断してほしい点: 色の移りが騒がしくないか。終点側の紫が「ゴール」を連想させ、解の手掛かりに見えないか。
12. **阻まれたときの反応**
    - 既定: 先端の輪を進もうとした向きへ突き当てて戻し、進もうとしたマス（穴・離れたマス・通ったマス）に先端の色の×を短く点ける（§18「阻まれたときの返し方（段12・プレイテスト）」）。段13 で仕切りを外したので、仕切りの光は無くなった。
    - 比べた案: 無反応（PoC）、先端の揺れだけ（段12 まで）。
    - 判断してほしい点: 反応が騒がしくないか。外周の欠け（盤面の外の地）に出る×が、穴へ進もうとして阻まれたと読めるか。
13. **ピクトグラム**
    - 既定: 枠の中の一筆の道と、残りのマスを表す点（Q1）。段13 で枠の右上の1マスを欠き、穴のある盤の外形にした（§18「ピクトグラム（段13）」）。調査時点の方向（塗られていく格子と道）は代替 A として同じ品質で残した（[ピクトグラム検討](ハミルトン路ピクトグラム検討.md) §5.2、§6）。
    - 判断してほしい点: プレイ画面の「マスが塗られていく」見た目を描いていなくてよいか。点つなぎ遊びやスマホのパターンロックに見えないか。欠けた枠が穴のある盤に見えるか（欠けの無い Q1 に戻すか）。

**運用・共通部品**

14. **問題 ID を指定して開いたプレイも記録すること**
    - 既定: 記録し、結果で難易度も出す。問題 ID はプレイ画面の難易度の問題集でしか引けず、難易度と問題のレベルが食い違わない（§18「問題を指定して開いたプレイの記録（段10）」、ADR-0001）。
    - 比べた案: 内部診断で問題を指定したプレイは記録しない（リフレクション段09・10の当初の扱い）。
    - 判断してほしい点: 遊び比べで問題 ID を指定して遊ぶと、その記録が自己ベストに入る。遊び比べ専用の扱いが要るか。
15. **共通の待ったボタンを、タッチの `pointerup` で受けること**
    - 既定: `useTouchTap` を `frontend/src/components/touch-tap.ts` へ移し、全ゲームの待ったボタンに効かせた（§18「タッチ直後の click の受け口の置き場（段04）」）。
    - 比べた案: ハミルトン路だけ専用の待ったボタンを作る。
    - 判断してほしい点: 待ったボタンの受け方を全ゲームで変えてよいか。
16. **ゲーム選択の並び**
    - 既定: `gameCatalog` の末尾（リフレクションの後）。並びの方針は決まっていない。
    - 判断してほしい点: 一覧の中の位置。
17. **PC で検証情報を閉じた後の矢印キー**（段04から。段10の画面確認で気づいた）
    - 今の振る舞い: 検証情報のダイアログを閉じるとフォーカスがメニューのボタンに戻り、そのままでは矢印キーで道を延ばせない。盤面か空白を一度押せば延ばせる。
    - 判断してほしい点: 直すか（内部診断を使うときだけの操作で、利用者のプレイには影響しない）。
