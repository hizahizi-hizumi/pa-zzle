# ハミルトン路ピクトグラム検討

ハミルトン路のゲーム選択ピクトグラムをどう検討したかの記録。どの着眼点を探索し、どの候補を比べ、なぜ Q1（枠の中の一筆の道と、残りのマスを表す点）を推奨するかをまとめる。見直すときに、同じ比較をやり直さずに論点から始められるようにする。

この文書は導入調査の資料であり、現在仕様の正本ではない。採用したピクトグラムの形は `frontend/src/games/hitofude-puzzle/assets/pictogram.svg` を正とする。制作手順と評価方法は `.claude/skills/design-game-pictogram/`（`SKILL.md`、`references/method.md`）を正とする。

記述は次のように区別する。

- **事実（リポジトリ）**: 現在のコード・文書から確かめたこと。
- **事実（実測）**: 候補 SVG を実表示サイズで描画して比べたときに見えたこと。見え方の記述は、比較画像を AI が見て書いたもの。候補 SVG は代表案だけをリポジトリに残している（§6）。
- **判断**: 上から導いた推奨と理由。

人間による方向の選択はまだ行っていない。Skill は方向を人間に選ばせる手順だが、本実装では人間のレビューを全段の実装後に1回だけ行うので、AI が推奨案で仮に決めた（[ハミルトン路実装前提調査](ハミルトン路実装前提調査.md)「本実装の進め方」、§18「ピクトグラム（段07）」）。最終レビューで選び替えられるように、代替の候補も同じ品質まで仕上げている（§5.2、§6）。最終レビューの論点は前提調査 §20.3 の論点13 にまとめた。

採用した SVG は、ゲーム選択の一覧・ヒーローと、結果画面の見出し（`currentColor`、48px）で使っている。

## 1. 結論

> 注記（段13）: 穴のルールに合わせ、採用した SVG は Q1 の枠を右上の1マスが欠けた外形にし、そのマスの点を消した（[実装前提調査](ハミルトン路実装前提調査.md) §18「ピクトグラム（段13）」）。以下の記述と `ピクトグラム検討/q1-path-dots.svg` は欠けの無い段07 の Q1 のまま。§5.1 の「壁マスを描くか」は、穴を外形の欠けとして描く形で答えた。

- 推奨案は **Q1（枠の中の一筆の道と、残りのマスを表す点）**。濃色の太い枠（盤）の中に 4×4 のマスを想定し、左上の始点（濃色の塗りの円）から濃色の太い線が上下に蛇行して10マスを通り、盤の中ほどで止まる。まだ通っていない6マスには淡色の点を置く。
  - 始点の円と道の線は、プレイ画面の始点マーカーと道の線（太い1本線）と同じ役割を持つ。
  - 「始点から1本の道を引き、全部のマスを1回ずつ通る」という、このゲームの題材を、途中の局面で示す。残った点は「これから通るマス」で、道の先端はそこへ向かっている。
- 推奨の理由は次の3つ（§4.2）。
  - 1本の道と、通っていないマスの対比で、「全マスを1本で通る」ことが分かる。
  - 迷路・経路接続（Flow 型）・Hidato のどれにも寄らない（§4.2）。
  - 一覧の 46〜56px でも、始点・道・点が見分けられ、既存ピクトグラムと重さがそろう。
- 調査時点の[実装前提調査](ハミルトン路実装前提調査.md)は、段07の方向を「塗られていく格子と1本の道」としていた（同 §18.1）。その方向は代替 A として同じ品質まで仕上げた。Q1 は格子と塗りを点に置き換えた案で、調査時点の方向からは外れる。外した理由は、格子と塗りを描くと一覧で最も重くなり、格子の盤が並ぶ既存ピクトグラムの中で埋もれるため（§3.3、§5.1）。
- 見直すときの主な論点は次の4つ（§5.1）。有力な代替は A（塗られていく格子と道）と B（枠なし）（§5.2）。
  - 残りのマスを点で描くか、格子で描くか。
  - 通ったマスの塗りを描くか。
  - 盤の枠を描くか。
  - 壁マスを描くか。

## 2. 目的と制約

### 2.1 目的

ゲーム一覧でハミルトン路を素早く見分けられ、ゲーム自身の姿を保ち、既存のピクトグラムと並べても強さが突出しないこと（`DESIGN.md`「ゲームピクトグラム」、`references/method.md` §1）。

### 2.2 制約（事実（リポジトリ））

- 共通描画契約（`SKILL.md`）
  - `viewBox="0 0 120 120"`。
  - 線幅は 4 と 2 だけ。
  - 色は `var(--game-pictogram-strong)` と `var(--game-pictogram-soft)` の2色だけ。
  - `check_svg.py --max-colors 2 --forbid-gradients --forbid-filters --forbid-external-images --forbid-text` を通す。
- 色は `GamePictogram` が与える。ライトとダークでは前景色と補助情報色、結果画面では `currentColor` になる。どのテーマでも読める形にする。
- 実表示サイズ（[リフレクションピクトグラム検討](../リフレクション/リフレクションピクトグラム検討.md) §2.2 の実測値と `GameSelectionGallery.tsx` のクラス）
  - ゲーム選択のヒーロー: 177px（1280px 幅）/ 138px（390px 幅）。
  - 一覧のカード: 56px（1280px 幅）/ 46px（390px 幅）。
  - 結果画面: 48px。
  - 一覧の 46〜56px が最も厳しい。
  - ハミルトン路をゲーム選択に載せ、結果画面に出すのは段10（[実装前提調査](ハミルトン路実装前提調査.md) §18「ゲームカタログへの掲載（段03）」）。それまでピクトグラムを表示する画面は無い。
- 比べる既存ピクトグラム: ウォーターソート、ナンプレ、マインスイーパー、パーキングジャム、リフレクション、スライドパズル、バイナリパズル。ウォーターソート以外の6つは濃色の太い外枠を持ち、ナンプレ・マインスイーパー・スライドパズル・バイナリパズルはその中を格子で区切る。リフレクションは枠の中に淡色の折れ線と点（入口）を持つ。
- プレイ画面の見た目（[ハミルトン路スマホ操作PoC](ハミルトン路スマホ操作PoC.md)、[ハミルトン路導入成立性調査](ハミルトン路導入成立性調査.md)「他候補との差異とリスク」）
  - 正方形格子。壁マスは暗色の塗り。始点は塗りの円、道は太い1本線で、通ったマスは塗られていく。先端は輪の円。
  - 仕切り（通れない辺）は暗色の短い棒。
  - 調査時点では、段07の方向を「塗られていく格子と1本の道」としていた（[実装前提調査](ハミルトン路実装前提調査.md) §18.1。AI判断（仮決定））。
  - 見分けたい近いパズル: 経路接続（色ごとの複数の線で全マスを埋める）、迷路（壁に囲まれた細い通路）、Hidato（数字が並ぶ格子）。
  - ピクトグラムには仕切りを入れない（迷路に見えるのを避ける）。数字も入れない（Hidato・Zip に近づくのを避ける）。
- 表示名は作業名「ハミルトン路」で、`display-name.ts` の `HITOFUDE_PUZZLE_DISPLAY_NAME` から参照する（[実装前提調査](ハミルトン路実装前提調査.md) §17）。正式名は最終レビューで決める。SVG の `aria-label` もこれに合わせる。`GamePictogram` は SVG を `aria-hidden` で描画するので、読み上げには使われない。製品名が決まったら SVG の `aria-label` も直す。

## 3. 比べた方向と分かったこと

| 方向 | 候補 | 比べたこと |
| --- | --- | --- |
| 完成した道を描く | 枠＋格子＋全マスを通る線（4×4・5×5）、壁マスつき、格子なし、太い帯 | 全マスを通り終えた形が何に見えるか |
| 途中の道と残りのマスを描く | 格子＋塗り帯＋線、塗り帯だけ、塗りのマス、残りのマスを輪郭の四角で、Q1〜Q6（点） | 「まだ通っていないマス」をどう描くか、塗りを描くか |
| 道だけを描く | 枠なしの線と始点 | 盤なしでゲームが分かるか |

### 3.1 着眼点

次の着眼点から候補を作った。

- 道: 全マスを通り終えた蛇行、途中まで引いた蛇行、渦巻、往復（牛耕式）、始点の円と先端の輪、1本線の両端。
- マス: 通ったマスの塗り、塗りの帯、塗りのマスを1つずつ、残りのマスを空の格子・輪郭の四角・点で、残り1マス。
- 盤の手がかり: 壁マス（濃色の塗り）を避ける道、壁で欠けた盤の外形、仕切り。
- 抽象: 点の格子を一筆でつなぐ（グラフの頂点）、指でなぞる手、ペン。
- 失敗: 取り残されたマス。

候補にしなかったもの（判断）:

- 仕切り: 迷路の壁に見える（§2.2 の方針）。
- 数字・順番: Hidato・Zip に近づく。
- 指・ペン: なぞる操作の汎用記号で、ほかの線を引くパズルと区別できない。
- 取り残されたマス（失敗の図）: 説明に頼る。
- 閉じた道（ハミルトン閉路）: 終点を指定しないこのゲームと違う。

### 3.2 完成した道（事実（実測））

- 枠と淡色の格子の中に、全16マスを通る濃色の線を描くと、46〜56px では平行な濃い線が枠の中に詰まり、迷路の通路に見えた。5×5 はさらに密で、模様になった。
- 格子をなくして壁マス（濃色の塗り）を1つ置いても、枠の中を折れ曲がる濃い線は迷路・渦巻に見えた。
- 全マスを通る淡色の太い帯にすると、帯が壁に囲まれた通路に見え、迷路に近づいた。
- 盤も枠もない線と始点だけでは、汎用の折れ線（ケーブル・回路のような図）に見え、マスを埋めるパズルだと分からない。
- 完成した道は、マスを「全部通った」ことと「迷路の通路」を形で区別できない。まだ通っていないマスを残す方が、マスを埋めることが伝わる。

### 3.3 途中の道と残りのマス（事実（実測））

- 残りのマスを淡色の格子で描き、通ったマスを淡色の帯で塗って濃色の線を重ねる（A 系）と、「道に沿ってマスが塗られていく」プレイ画面に最も近かった。ただし淡色の面と格子が増え、46px で一覧の中で最も重く、マインスイーパー（淡色の四角を並べた盤）と同じ系統に見えた。
- 通ったマスが多い（10マス）と、2列の往復で帯が1つの塊になり、帯の間の細い隙間が溝に見えた。通ったマスを7マスにし、1列目を上って2列目を下る形（∩）にすると、塊にならずに道の形が読めた。
- 帯だけで線を描かない案は、46px で灰色の塊になり、道の向きが読めなかった。線の太さを2にすると、帯に負けて線が消えた。
- 通ったマスを1つずつ淡色の四角で塗る案は、四角と格子と線が重なって 46px でざわついた。
- 残りのマスを輪郭の四角で描く案は、「埋めるマス」に見えるが、スライドパズルのタイルに近く、重さも増えた。
- 調査時点の方向に合わせ、A 系を Q1 と同じ道（10マス）で描き直して帯の幅を比べた（帯の半幅 6 / 7.5、全マス塗り）。半幅 7.5 と全マス塗りは 46px で2列が1つの灰色の塊になった。半幅 6 にすると帯の間に地が残り、蛇行した道と塗りの両方が読めた。格子を盤全体に引くと帯の隙間に格子の線が入ってざわつくので、格子は通っていないマスの周りだけに引いた。
- 残りのマスを淡色の点で描く（Q 系）と、46px でも点が粒としてそろって見え、「まだ通っていないマス」と読めた。濃色の線と淡色の点だけなので、一覧で格子の盤より一段軽く、ナンプレ・バイナリパズルと同じくらいの重さだった。

### 3.4 Q 系の細部（事実（実測））

| 比べたこと | 案 | 見え方 |
| --- | --- | --- |
| マスの間隔 | 21（枠いっぱい）/ 20（内側へ寄せる） | 21 は外側の線が枠に沿って二重線に見えた。20 にすると線と枠の間（線の中心から枠の中心まで12）が空き、46px でも枠と道が分かれた |

| 始点 | 右上の角から下へ / 渦巻（始点が盤の中） | 渦巻は迷路・記号に見えた。角の始点が最も読みやすい |

| 始点の半径 / 点の半径 | 6・7・8 / 4・5・6 | 始点 6 は線の端の丸と区別しにくく、8 は枠に近すぎた。点 4 は 46px で薄れ、6 は道に近づいて詰まった。7 / 5 を採った |

## 4. 推奨案 Q1

### 4.1 仕様（事実（実測））

- 盤: `x=18 y=18 width=84 height=84`、`rx=2`、濃色、線幅4。ナンプレ・バイナリパズル・スライドパズルと同じ枠。格子は描かない。
- マス: 4×4 を想定し、マスの中心を x・y とも 30 / 50 / 70 / 90 に置く（間隔20）。
- 道: 濃色、線幅4、線端と角は丸。左上の始点から下・右・上・右・下へ進む1本の折れ線（`M30 30V90H50V30H70V50`）。通るマスは10。
- 始点: 中心 (30, 30)、半径7、濃色の塗り。道の上に重ねる。
- 残りのマス: 淡色の塗りの点6つ、半径5。中心は (90, 30)・(90, 50)・(70, 70)・(90, 70)・(70, 90)・(90, 90)。道の先端 (70, 50) から (70, 70)→(70, 90)→(90, 90)→(90, 70)→(90, 50)→(90, 30) と進めば、残りを1回ずつ通って終われる（盤として成り立つ途中局面）。
- 光学中心の補正: なし。濃色の道が左に寄るが、枠が上下左右で均衡し、右の淡色の点が重さを受けるので、177px と 46px で偏りは目立たなかった。
- 色は strong / soft の2色だけ。`check_svg.py` の2色・gradient / filter / 外部画像 / text 禁止の検査を通る。

### 4.2 推奨理由（判断）

- **意味的距離**
  - このゲームの題材は「始点から1本の道を引き、全マスを1回ずつ通る」こと。Q1 は始点・1本の道・まだ通っていないマスを描き、途中の局面として示す。
  - 残りの点は、道がこれから全部を通ることを示す。完成した道（§3.2）より、「全マスを埋める」ことが伝わる。
  - 始点の塗りの円と太い1本の道は、プレイ画面の始点マーカーと道と同じ役割を持つ。
- **弁別性**
  - 迷路: 仕切りも格子も描かず、通路の壁に当たる線がない。濃い線は1本だけで、平行な線の詰まりを作らない（§3.2）。
  - 経路接続（Flow 型）: 線は1本、印は始点の1つだけ。端点の組や複数の線がない。
  - Hidato: 数字を描かない。
  - 既存ピクトグラム: 枠の中に格子を持たないのはリフレクション・パーキングジャムと Q1 だけ。リフレクションの淡色の折れ線と斜めの鏡に対し、Q1 は濃色の直角の蛇行と点の並びで、46px で見分けられた（事実（実測））。
- **実表示サイズ**: 要素は枠・始点・道・点6つだけ。46px でも点が1つずつ粒として残り、道の折れ方が読めた（事実（実測））。
- **光学的重量**: 濃色は枠・道・始点、淡色は点だけ。ナンプレ・バイナリパズルとほぼ同じ重さで、格子と面を持つマインスイーパー・スライドパズルより軽い（事実（実測））。
- **一覧の描画言語**: 主形状（濃・4：枠と道）と補助情報（淡：点）の2段階。既存の「外枠が主形状、中身が補助」の階層に、道を主形状として加える。

### 4.3 弱点（判断）

- 点の格子を一筆でつなぐ図は、スマホのパターンロック（3×3 の点を線でつなぐ）や点つなぎ遊びにも見えうる。4×4 と枠でパズルの盤に寄せたが、完全には消えない。
- プレイ画面の「通ったマスが塗られていく」見た目は描いていない。プレイ画面ではマスは四角で、点ではない。
- 盤の手がかり（壁マス・仕切り）を描いていない。何を手がかりに道を決めるパズルかは伝わらない（§3.4 の壁マスの比較）。
- 経路接続（Flow 型）を将来実装するとき、そのピクトグラムも「枠＋線＋点」になりやすい。経路接続側は複数の線と端点の組で描き分ける必要がある。
- ダークテーマでは道と始点が明るい前景色になる。既存ピクトグラムも同じ前景色の規則に従うので、ここだけ変えることはしない。

## 5. 再検討するときの論点

### 5.1 論点

- **残りのマスを点で描くか、格子で描くか**: 点（Q1・B）は 46px で粒として残り、軽い。格子（A）はプレイ画面のマスに近いが、一覧に格子の盤が5つ並ぶ。
- **通ったマスの塗りを描くか**: 塗り（A）はプレイ画面の「道に沿ってマスが塗られていく」に最も近く、調査時点の方向（§2.2）どおり。代わりに一覧で最も重く、マインスイーパーと同じ系統に見える。プレイ画面との対応を一覧の軽さより重く見るなら A を採る。
- **盤の枠を描くか**: 枠あり（Q1）は盤のパズルに見え、パターンロックから離れる。枠なし（B）は一覧で枠を持たないのがウォーターソートとの2つだけになって目立つが、一段軽く、盤らしさが弱い。
- **壁マスを描くか**: 壁マスは手がかりを示すが、濃色の塗りの四角がバイナリパズルの四角と同じ形になる（§3.4）。描くなら角を落とす・大きさを変えるなど形で分ける必要がある。

### 5.2 候補の一覧と代替案

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **Q1 一筆の道と残りの点**（推奨） | 濃色の枠、左上の始点から10マスを通る濃色の道、残り6マスに淡色の点 | 全マスを1本で通ることが途中局面で分かる。迷路・経路接続・Hidato に寄らない。重さがそろう | パターンロックに見えうる。マスの塗りを描かない。壁マスなし |
| A 塗られていく格子と道 | 濃色の枠、Q1 と同じ道で通った10マスを淡色の帯（半幅6）で塗り、その上に濃色の道と始点。残りのマスは淡色の格子 | 調査時点の方向どおり。プレイ画面の見た目（道に沿ってマスが塗られる）に最も近い | 一覧で最も重い。格子の盤の系統に入り、マインスイーパーに近い |
| B 枠なしの道と点 | Q1 と同じ道と点を、枠なしで少し大きく描く（マスの間隔23、右へ2補正） | 一覧で唯一に近い軽い形。道と点がいちばん大きく見える | 盤らしさが弱く、点つなぎ・パターンロックに寄る。一覧で一段軽い |
| 完成した道 | 枠＋格子＋全マスを通る線（壁マスつきも） | ゲームの答えの形そのもの | 迷路に見える（§3.2） |
| 道だけ | 枠も点もない線と始点 | 最も単純 | 汎用の折れ線に見える |

推奨順は Q1 > A > B（判断）。A と Q1 は道を同じにしてあり、違いは「残りのマスを点にするか格子にするか」「通ったマスを塗るか」だけ。部分採用もできる（例: A の塗りを外して格子と道だけにする、Q1 の残りの点の1つを壁マスに替える）。

## 6. 代表案の SVG と選び替え

[ピクトグラム検討/](ピクトグラム検討/) に、候補ごとの代表案だけを置く。

| ファイル | 内容 |
| --- | --- |
| `q1-path-dots.svg` | 推奨案 Q1（採用 SVG と同じ） |
| `a-painted-band.svg` | A 塗られていく格子と道 |
| `b-path-dots-frameless.svg` | B 枠なしの道と点 |

色は製品と同じ CSS 変数（`var(--game-pictogram-strong)` / `var(--game-pictogram-soft)`）のまま置いている。GitHub などで CSS 変数なしに見る場合は、ライトテーマの近似値に置き換えたコピーを作る。

```sh
sed -e 's/var(--game-pictogram-strong)/#0a0a0a/g' -e 's/var(--game-pictogram-soft)/#737373/g' \
  docs/パズル/導入調査/ハミルトン路/ピクトグラム検討/a-painted-band.svg > /tmp/a.svg
```

### 6.1 選び替える手順

1. 採る候補の SVG を `frontend/src/games/hitofude-puzzle/assets/pictogram.svg` へ複製する。`aria-label` は表示名に合わせる。
2. 最終検査を通す。

   ```sh
   python3 .claude/skills/design-game-pictogram/scripts/check_svg.py frontend/src/games/hitofude-puzzle/assets/pictogram.svg \
     --max-colors 2 --forbid-gradients --forbid-filters --forbid-external-images --forbid-text
   ```

3. 既存ピクトグラムと同じサイズ・同じテーマで並べて見比べる（`references/method.md` §4「弁別性」「実表示サイズでの成立」）。サイズは §2.2 の 177 / 138 / 56 / 46 / 48px を使い、ライトとダークの両方で見る。

   ```sh
   python3 .claude/skills/design-game-pictogram/scripts/make_review_sheet.py \
     --output /tmp/hitofude-puzzle-pictogram-review.html --size 112 \
     docs/パズル/導入調査/ハミルトン路/ピクトグラム検討/*.svg \
     frontend/src/games/*/assets/pictogram.svg
   ```

4. この文書の §1 と §4 を、採った案に合わせて直す。
