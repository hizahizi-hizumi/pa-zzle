# ソリティア 調査: 図鑑と問題の特徴

調べた版: main 4b9cf7ee から分けた作業ブランチ。難易度の分類は版7 (a)（組札への自動送りなし）を `solitaire_difficulty.py` から import して使い、定義は変えていない。

書いたもの:

- 調査コード: `docs/パズル/導入調査/ソリティア/調査コード/solitaire_zukan.py`（`measure` で下の計測をすべて出す。`expected` で期待値を書く）
- 移植の期待値: `docs/パズル/導入調査/ソリティア/調査コード/solitaire_zukan.expected.json`（採る2つの特徴の、配り方ごとの値。128件）

## 結論

合意した前提（52枚・7列で全レベル同じ盤面、列は全部表向き、山札は裏向き）は崩れない。盤面の大きさ・列の札の数・山札の枚数はどの問題も同じなので、特徴にはならない（図鑑では選択肢が1つの軸は出ない）。特徴は列の28枚の並びから取る。

採る特徴は2つ。

- 「A の上の札」: 列ごとに、一番奥の A より上（手前）にある札の数を足したもの。同じ札は1回だけ数える。列に A が無ければ 0。A を組札へ出すまでにどかす札の量を表す。
- 「K の下の札」: 列ごとに、一番上（手前）の K より下（奥）にある札の数を足したもの。同じ札は1回だけ数える。列に K が無ければ 0。K を空いた列へ動かすまで取り出せない札の量を表す。

問いごとの結論は次のとおり。

- レベルの中で値が分かれるか: 成り立つ。
  - 分類した105件では、どのレベルでも値が6〜13種類あり、最も多い値でも40%以下。
  - 1レベルが数百問なら、幅3でまとめて選択肢は5つ。最も多い選択肢でも約38%になる（配るだけの2万件から抜き出して測った）。
- ほかの案と重ならないか: 成り立つ。
  - 2つの特徴の順位相関は −0.02（解ける364件）、−0.09（分類済み105件）。
  - 同じ系統の案どうしはよく重なる（例: A の上の札と、一番深い A の上の札は 0.92）。系統ごとに1つだけ採る。
- 難易度の写しにならないか: 条件つきで成り立つ。
  - レベルとの相関は 0.03 と 0.14 で、どちらも信頼区間が0をまたぐ。段 T とは 0.12 と −0.05、罠の後の進み G とは −0.18〜0.19。
  - 条件は、同じ段 T の L4 と L5 の対の中で |ρ| が約0.35 になり、信頼区間がわずかに0を外れること（34件）。L4 と L5 を分ける G の段と弱く連動する。
- 値の書き方と数をまとめる幅:
  - 数で書き、単位は「枚」（例: A の上の札 4枚、範囲は 3〜5枚）。
  - まとめる幅は両方とも3。8種類以下は値ごとに示す決まりなので、1レベルの問題が少ないうちは値ごとに出る。
  - 幅は 2〜6 を比べて決めた。前提は、1レベル100〜1,000問で、各レベルの値の分布が無作為な配り方の分布に近いこと（上の「写し」の測り方から）。
- 特徴にしない量:
  - 解き筋の手数（GAME-009 で示さないもの。しかも解き方は自由なので1つに決まらない）。
  - 初手で置ける手の数（山札の並びで決まり、始めたときには見えない）。

- 「400配り」: 難易度の観点のキャッシュ（`v7_random.jsonl` を `v7big_random.jsonl` で置き換えたもの）。分類は L1〜L5 が 10 / 29 / 32 / 15 / 19。新しい解法器や網の計算はしていない。

## 事実と推測

- [事実] 図鑑の特徴は「始めたときの盤面で分かる」もの。解かないと分からないもの（最短手数・要る手筋）は示さない。値の種類が多い特徴は、パズルごとに決めた幅でまとめる: `docs/プロダクト/ゲーム/GAME-009-図鑑.md`
- [事実] 絞り込みの選択肢の決め方:
  - 1レベルの値が8種類以下なら値ごとに出す。9種類以上で幅があれば `floor(値 / 幅)` でまとめ、各範囲は入る値の最小〜最大で示す。
  - 選択肢が1つの軸は出さない。
  - 出典: `frontend/src/features/zukan/zukan-filter.ts`（`MAX_EXACT_COUNT_OPTION_COUNT = 8`・`listCountOptions`・`collectZukanLevelFeatures`）
- [事実] 特徴の単位に「枚」がある。既存の幅は 2〜5 で、3 が最も多い（色・島・穴・初期数字・車・初期配置・盤上の駒）: `frontend/src/components/problem-features.ts`、`frontend/src/games/*/ui/problem-features.ts`
- [事実] 図鑑で項目を分ける案を退けた理由は、項目が難易度の写しや全問に当たるものになったこと: `docs/adr/ADR-0004-zukan.md`
- [事実] 前例として、リフレクションはピースの数を特徴にしている。ピースの数と最高推論レベルの順位相関は約0.67（作り直す前の計測では0.71）: `docs/パズル/導入調査/リフレクション/リフレクション実装前提調査.md`、`frontend/src/games/reflection/ui/problem-features.ts`
  - この調査の「写しでない」の目安（\|ρ\| < 0.3）は、この前例より厳しい（AI判断）。
- [事実] 詰将棋の特徴は、問題集の索引から求めている（問題集の本体を読み込まない）: `frontend/src/games/tsume-shogi/problem/problem-pool.ts`
- [事実] 採る2つは列の28枚だけで決まり、山札の並びに依らない。山札の並びを含めて1問とする難易度とは違う: 定義から（導出）
  - 列と山札が同じ札で並びだけ違う2問は、特徴が同じでも別のレベルになり得る。
- [事実] 配るだけの分布で、A の上の札と K の下の札はほぼ同じ形になる。無作為な配り方では、列の中の位置を上下逆に数えても分布が変わらないため（A の上の札は列の上からの位置、K の下の札は奥からの位置）: 導出と計測
- [推測] 「A の上の札」は掘り出す量の目安になり、「K の下の札」は空いた列が要る量の目安になる。遊ぶ人は「早く組札を始められる配り」「空いた列をどう作るかが鍵の配り」として選べる。
  - 根拠: 解き筋の手数・列を空ける手との相関（0.35・0.21）。どちらも解法器の1本で、最短ではない。
  - 確かめ方: 試遊で、値の大小を見比べて遊べば確かめられる。
- [推測] L4 と L5 の対の中で A の上の札が負に相関するのは、A が深いと致命の手の後に組札が進みにくく、G（組札の枚数で数える）が小さくなるため。
  - 根拠: L4・L5 の中でも G と負の相関（−0.30〜−0.57）。15〜19件なので幅が広い。
  - 確かめ方: 問題集を作った後、各レベルの数百問で測り直せば確かめられる。
- [推測] 各レベルの値の分布は、無作為な配り方の分布に近い。
  - 根拠: レベルとの相関が小さく、分類済み105件の幅3の割合が配るだけの割合と大きくは違わない。各レベル 10〜32件なので、差は見分けられない。
  - 確かめ方: 問題集の生成の統計で確かめられる。

## 仮決定の候補

- 特徴の切り口:
  - 推奨: 「A の上の札」と「K の下の札」の2つ
  - 理由: 3つの計測をすべて満たし、互いにほぼ独立（−0.02）。どちらも、このパズルの挑戦の「列の奥に埋まった札をどの順で掘り出すか」「空いた列をいつ使うか」に結びつく盤面の形で、始めたときの列を見れば分かる。見出しが「A の上／K の下」で対になり、覚えやすい（推測）。
  - 比べた案:
    - 埋まった A と下に札がある K（0〜4 の数）: 一目で数えられるが、最多の値が 38〜53% に偏り、選択肢がほぼ2つに集まる（配るだけで 1・2 が71%）。埋まった A は G との相関が −0.26 / −0.28 と、採る案（−0.17 / −0.18）より大きい。
    - 列の A と列の K: 埋まり方を表さない。列の A はレベルとの相関の信頼区間が0を外れる。
    - 一番深い A の上の札: A の上の札と 0.92 で重なる。
    - A・2 の上の札、A〜3 の上の札: G との相関が −0.27〜−0.32 で写しに近づく。数えるのも重い。
    - 一番奥が K の列: 0〜2 にほぼ収まり、L3 で 0 が69%。
    - 並んだ所: 0〜3。0 が約半分で、何を選ぶ切り口かが弱い。
    - 始めに列で動かせる手: 探さないと分からず、最初のめくりで意味が変わる。
    - 同じマークの小さい札の上の札: 見出しで意味が伝わりにくい。
    - 解き筋の手数・初手で置ける手: 始めたときに見えない。
    - 3つ目の軸は足さない（並んだ所が最も独立だが、選ぶ理由が弱い）。
  - 覆したときに作り直す範囲: zukan の項目だけ（特徴の型と軸 `problem/problem-pool.ts`、見出しと幅 `ui/problem-features.ts`、索引に持つなら問題集の索引、テストと期待値）。難易度と問題集の中身は変わらない。
- 数え方（同じ札を何回数えるか）:
  - 推奨: 列ごとに一番奥の A（一番上の K）を基準に、同じ札は1回だけ数える
  - 理由: 見出しの「A の上の札」を「A の上にある札の数」と読んだとき、実際の札の数と一致する。
  - 比べた案: A ごと・K ごとに数えて足す。採る形との相関 0.99 / 0.98、配るだけで値が一致するのは85%。3つの計測はほとんど変わらない。
  - 覆したときに作り直す範囲: 特徴を求める関数と期待値だけ
- 値の書き方:
  - 推奨: 数（`createCountFeatureValue`）、単位「枚」、見出し「A の上の札」「K の下の札」。0 も値として出す（列に A が無い、またはすべて一番上）
  - 理由: 既存の単位で書ける。0 は「掘り出しが要らない」という意味がある。
  - 比べた案: 新しい単位（「列」など）を足す（要らない）
  - 覆したときに作り直す範囲: 見出しと単位の表示だけ
- まとめる幅:
  - 推奨: 両方とも3（`rangeWidth: 3`）
  - 理由: 1レベル100〜1,000問で選択肢が5つになり、最も多い選択肢が約38%で、比べた幅の中で偏りと数のつり合いが最もよい（0〜2・3〜5・6〜8・9〜11・12〜14）。既存で最も多い幅とも同じ。端の 12〜14 は 0.7% なので、300問なら約2問の選択肢になる。
  - 比べた案:
    - 幅2: 6〜8個で多い
    - 幅4: 4個で、0〜3 と 4〜7 に 88% が集まる
    - 幅5: 3個で、最多60%
    - 幅6: 3個で、最多71%
  - 前提: 1レベルの問題数は問題供給の観点が決める。今の値は「各レベル数百問」と、各レベルの分布が配るだけの分布に近いことを前提にした比較実験の条件で、問題集ができたら、その分布で幅を確かめ直す。
  - 覆したときに作り直す範囲: `ui/problem-features.ts` の幅だけ
- 特徴の求め方:
  - 推奨: 問題の配り方（列の28枚）から求める。問題集の索引に持つか、その場で求めるかは実装で決める
  - 理由: 1問28枚を1回なめるだけで求まる。詰将棋は索引に持つ前例がある。
  - 比べた案: 生成時に求めて問題集に持つ
  - 覆したときに作り直す範囲: 問題集の形式（索引に持つ場合）

## 確かめていないこと

- 遊ぶ人がこの2つの切り口で次の1問を選びたくなるか、見出しの意味（どかす札・取り出せない札）が伝わるか: 誰も遊んでいない。最終レビューの「答える」で、おすすめ（この2つ）と別案（埋まった A・下に札がある K の 0〜4）を並べて聞くのがよい（推測）。
- 値の大小が、手応えや時間の違いとして感じられるか: 手数・列を空ける手との相関は解法器の1本で測った。人の時間は測っていない。
- 各レベル数百問での値の分布と幅3の選択肢:
  - 分類済みは各レベル10〜32件で、分布は配るだけの2万件で代わりに測った。
  - L4/L5 の対で見えた相関（\|ρ\| ≈ 0.35、34件）と、L4・L5 の中での G との相関（15〜19件）が本当にあるかは、件数が足りず決められない。
  - 問題集の生成の統計で確かめる。生成でレベルごとに配り方を寄せる場合も、測り直しが要る。
- 版7 の評価不能32件・範囲外の問題を、問題集を作るときに流し直して分類すると、分布が変わるか: 問題供給の観点の生成に依る。
- 移植した特徴が期待値と一致すること: ゲームのコードが無いので確かめていない。期待値は128件（同じ列に A か K が2枚ある配り方を含む）。
