## 結論

合意した前提（解けると確かめた配り方だけを、どのレベルも52枚・7列で出す）は、この観点でも成り立つ。件数は各レベル500問を推奨し、それをそろえる生成は条件つきで成り立つ（TS で4並列3〜10時間の見込み。推測）。

400配り・Python・4並列・調査の590秒の区切り・上限5倍の2回目は、比べるための実験の条件で、仕様に入れる値ではない。件数・並び・1問の表し方・打ち切りの上限は、それぞれ比べた案の中から推奨した（下の「仮決定の候補」）。

- 件数（もう1問になる件数）: 各レベル500問（計2,500問）を推奨する。条件つきで成り立つ。
  - 1問が長い（素朴な解き方で解けた配り方で、めくり以外76〜94手とめくり24〜47回。採点の前提の観点の計測2）。1問5〜10分なら、各500問は1レベルあたり約40〜80時間の新しい問題になる（推測）。
  - ランダム出題（全状態を対象に均等。GAME-002）で1つのレベルを100回遊んだ後も、次の1問がまだ遊んでいない問題である確率は 82%（300問なら72%、200問なら61%）。300回の後で55%（300問なら37%）。「未挑戦」だけに絞れば500回まで新しい問題が続く（導出）。
  - 件数と並びは図鑑の枠と番号を決め、公開後に変えると `/design-game-difficulty` の守ること 8 に当たる。足りなくなって増やす側の作り直しを避けるため、余裕のある側に置く。
  - レベルで件数を変える遊ぶ側の理由は見当たらない。リフレクションの L4・L5 300問は生成時間の都合（`generate-reflection-problem-pool.ts` のコメント）で、この観点の決め方とは違う。
  - 条件: 1問の所要時間と、1人が1つのレベルを何回遊ぶかは測っていない。試遊と公開後の記録で確かめる。
- 解けると確かめられる割合と収率で、各500問をそろえられるか: 条件つきで成り立つ。
  - 52枚・7列で解き筋を見つけた配り方は 364/400（91%）。収率（既定の上限）は L1 2.5%・L2 7.0%・L3 7.75%・L4 3.25%・L5 2.75%（難易度の観点と同じ値を再集計）。400配りなので幅が広い（95%区間 L1 1.4〜4.5%・L5 1.5〜4.9%）。
  - 各500問には候補が約20,000要り、L1 が候補の数を決める（区間の両端で約11,000〜36,000）。
  - 段 T で先に振り分け、読むモデル（時間の大半を占める部分）を振り分けの合う候補にだけ使い、比べる用の量を求めないと、各500問は Python で約115 CPU 時間（既定の上限だけ。内訳は解法器と網 15・段2 の読むモデルと致命の手 22・段3 の読むモデル 79）。1問あたりは L5 で 1,248 → 665、L4 で 1,056 → 563 CPU 秒に下がる。段3 の時間は読むモデルそのもので、比べる用の量を除いても縮まない（92配りで測った比 1.00。段2 は 0.78）。
  - TS では Python の3〜10倍速とみなし（既存ゲームの移植の実測からの推測）、約12〜38 CPU 時間、4並列で約3〜10時間。収率の区間の両端で、段3 の部分は約0.6〜1.8倍に動く。
- 打ち切りの上限: 局面数で置き、既定の上限（1回の問い合わせ4万局面・1問200万局面）の1回で流すことを推奨する。成り立つ（ただし難易度の観点へ返す論点が1つある）。
  - 時間で区切ると、生成する機械で問題集が変わる。難易度の観点の590秒の区切りは調査を流すための条件で、仕様に入れない。
  - 上限5倍の2回目は L5 を 2.75% → 4.75% に上げるが、L4 は 3.25% → 3.75% にしか上がらず、各500問では L4 が段3 の候補の数を決める側に移る。生成時間は減らず増える（115 → 138 CPU 時間。2回目を流していない段3 の16件を悲観すると312）。
  - 2回目で初めて決まった L5 8件の G_f は 7〜16（中央値9.5）で、既定の上限で決まった11件（7〜15、中央値8）と同じ範囲。G と読むモデルの局面数の順位相関は0.43で、重い問題ほど G がやや大きい向きはあるが、上限で L5 の G の帯が削られることは見えない（件数が少ない）。
  - 返す論点: 4変種とも段3 の候補の 36/86（42%）が既定の上限で評価不能で、2回目で決まった L5 8件は L5 19件の4割にあたる。`難易度開発手順.md` の「評価不能が提供範囲として扱いたい領域で恒常的に発生する」に当たり得る。上限ではなく読むモデルの速さの論点なので、難易度の観点（移植後の読むモデル）で扱う。
- L1・L4・L5 に生成を寄せる必要と、寄せたときの偏り: 配り方は寄せず、段 T の振り分けで分析だけを寄せることを推奨する。成り立つ。
  - L1 は候補の数を決めるが、読むモデルが要らない。1問あたり約110 CPU 秒（Python）で、寄せる必要は無い。
  - L4・L5 は、段 T（4変種とも段3）の候補にだけ読むモデルを使えばよい。振り分けは分類の手順の前半そのもので、受け入れる問題の集まりは全部を分析したときと同じ（導出。92配りで分類の食い違い 0）。レベルの性質は偏らない。
  - 配り方を静的な特徴（配った時に分かる量）で絞るのは採らない。最も効く絞り方でも L4 か L5 の一方の収率が1.3〜1.7倍になるだけで、もう一方は下がるか、そのレベルの半分以上を捨てる（例: A〜3 の上に乗っている札の数の合計 `buried_low` ≥ 12 で L4 1.48倍・L5 0.58倍）。絞った特徴の値がそのレベルの配り方に偏る（構成上）。
- 1問の表し方と問題集の大きさ: 候補番号の seed を、TS の共通の乱数（`createProblemSeededRandom`・`shuffleProblemValues`）で52枚の並びにして配る形を推奨する。成り立つ。
  - 問題集は各500問で JSON 約43 KB・gzip 約15 KB（seed と小さな整数4つの場合）。既存ゲーム（gzip 3〜111 KB）の小さい側。
  - 札の並びを持つと JSON 約143〜167 KB・gzip 約99〜110 KB で、詰将棋の本体（gzip 約105〜114 KB）と同じ大きさになる。詰将棋は本体を最初の読み込みから外し、索引を別に持つ仕組みを足した。並びを持つ利点（問題が乱数の実装に依らない）は、生成器の版（GAME-006）で既存ゲームと同じく扱える。
  - 山札の並びを含めた52枚の並び全体が1問であることは、どちらの表し方でも同じ（seed から52枚すべてが決まる）。
- レベルの中の並び: 候補番号の順を推奨する。成り立つ。
  - 遊ぶ人はランダム出題（均等）か図鑑（番号は問題集の並び。GAME-009）で出会う。並びが効くのは図鑑の番号だけ。
  - 生成条件は1つなので、既存ゲームの「条件を巡回して番号順に採る」形の巡回が要らず、番号順だけになる。G などで並べ替えると、番号の先頭に同じ帯の問題が固まり、作り直しや件数の追加で番号が付け直される。
- 生成時間の TS での見積もり: 上の「そろえられるか」。Python の計測からの推測で、移植後に生成スクリプトの統計で置き換える。

## 仮決定の候補

- 件数:
  - 推奨: 各レベル500問（計2,500問）
  - 理由: 1問が長く、各500問で1レベル約40〜80時間の新しい問題になる（推測）。ランダム出題で100回遊んでも次の1問の82%が新しく、「未挑戦」に絞れば500回まで続く。公開後に件数を変えると図鑑の枠と番号が変わる（守ること 8）ので、余裕のある側に置く。レベルで変える遊ぶ側の理由が無い。生成は TS で4並列3〜10時間の見込み（推測）で、そろえられる
  - 比べた案: 各300（ナンプレと同じ、1問の長いパズルの前例。100回の後に次が新しい確率72%・300回で使い切る。生成は約6割）、各1,000（短いパズルの前例。生成は2倍で、4並列6〜19時間の見込み）、500/500/500/300/300（リフレクション。生成時間の都合で上のレベルを減らした形で、遊ぶ側の理由が無い）、各200 以下（100回で4割が遊んだ問題）
  - 覆したときに作り直す範囲: 問題集（生成し直し）、図鑑の枠と番号（公開後は人間の判断）
- レベルの中の並び:
  - 推奨: 候補番号の順（生成した順）
  - 理由: 既存ゲームの番号順と同じ。生成条件が1つなので巡回が要らない。配り方は無作為なので、番号の並びに帯の偏りが出ない。件数を増やすときは末尾に足すだけで、前の番号が変わらない
  - 比べた案: G や手数の順（図鑑の先頭に同じ帯が固まり、作り直しで番号が付け直される）、質の点の順（橋をかけろ。この観点で質の点を決めていない）
  - 覆したときに作り直す範囲: 問題集の並びと図鑑の番号
- 1問の表し方:
  - 推奨: seed は候補番号の文字列。配り方は `createProblemSeededRandom`（接頭辞つきの seed）と `shuffleProblemValues` で52枚を並べ、列1〜7 に1〜7枚、残り24枚を山札（先頭が次にめくる札）にする。問題集の1問は [seed, 図鑑と採点に要る小さな値] にする（値は図鑑・採点の観点で決める）
  - 理由: 既存ゲームと同じ形で、問題集が gzip 約15 KB と小さく、本体を分けて読む仕組みが要らない。52枚の並び（山札の並びを含む）は seed から1つに決まる。乱数の実装は変えない決まりがあり、変えるときは生成器の版を上げる（既存ゲームと同じ）
  - 比べた案: 52枚の並びの文字列を持つ（問題が乱数に依らず、調査の `deal_cards` と同じ形。gzip 約99〜110 KB で、詰将棋と同じく本体を分ける仕組みが要る）、並びの番号の base64url（gzip 約76 KB。BigInt で戻す手間）、Python の `random` に合わせる（調査の seed と同じ配り方になるが、Mersenne Twister と Python の shuffle の移植が要り、TS の共通の乱数と別のものを持つ）
  - 覆したときに作り直す範囲: 問題集の読み書き・identity・問題 ID（公開前なら記録への影響は無い）
- 生成の流れ:
  - 推奨: 候補番号の順に配り、(1) 素朴な解き方の網を4変種で作って段 T を求める、(2) 4変種とも段1 なら L1（勝ち筋を解き筋として1手ずつ確かめ直す）、変種で段が変わるなら範囲外として止める、(3) 段2 は L2・L3 が埋まっていなければ読むモデルで G を求める（勝ち筋を解き筋として確かめ直す）、(4) 4変種とも段3 は解法器で解き筋を探し（無ければ成立しない）、L4・L5 が埋まっていなければ読むモデルで G を求める。候補ごとの結果を JSONL に貯め、途中から同じ順で続けられるようにする。比べる用の量は求めない
  - 理由: 受け入れる問題は全部を分析したときと同じで、L5 1問あたりの時間がほぼ半分になる（1,248 → 665 CPU 秒）。比べる用の量を除くと段2 の時間が0.78倍になる（段3 は変わらない）。途中から続けられる形は守ること 6 と既存の生成スクリプト（一筆パズル・橋をかけろ・詰将棋）と同じ
  - 比べた案: 全候補をすべて分析（難易度の観点の求め方。各500問で約191 CPU 時間、約1.7倍）、配り方を静的な特徴で寄せる（効きが1.3〜1.7倍で、レベルの配り方が偏る）
  - 覆したときに作り直す範囲: 生成スクリプトだけ（問題集は同じになる）
- 打ち切りの上限:
  - 推奨: 局面数で置き、難易度の観点の既定の上限（1回の問い合わせ4万局面・1問200万局面）で1回だけ流す。評価不能は出さず、生成の統計に振り分けごとの評価不能の数を出す
  - 理由: 期待値（`solitaire_difficulty.expected.json`）と同じ上限で、移植の突き合わせがそのまま使える。時間で区切ると機械で問題集が変わる。各500問では2回目で生成時間が減らない（115 → 138、悲観で312 CPU 時間）。2回目で増える L5 の G は既定で決まる L5 と同じ範囲
  - 比べた案: 評価不能を上限5倍で流し直す（全部 (ii) 143 CPU 時間・段3 だけ (iii) 138）、上限5倍で1回だけ流す（測っていない。既定で決まる問題も重くなる）
  - 覆したときに作り直す範囲: 問題集と `--verify`（分類が変わるのは評価不能だった問題だけ）
- 生成時間の目標と見直しの条件:
  - 推奨: 各500問の全量の生成を、TS・4並列で一晩（10時間）以内を目安にし、生成スクリプトの統計（候補の数・振り分けごとの数と時間・収率）を残す。超えるときは、読むモデルの移植を詰める（キーを詰めた形）を先に行い、件数は下げない
  - 理由: Python からの見積もりは3〜10時間（推測）で、収率の幅（L5 1.5〜4.9%）で段3 の部分が0.6〜1.8倍に動く。件数は遊ぶ側で決めたので、時間で動かさない
  - 比べた案: 時間に合わせて上のレベルの件数を下げる（リフレクションの形。供給の都合で図鑑の枠が決まる）
  - 覆したときに作り直す範囲: 生成スクリプトの並列と読むモデルの実装

## 確かめていないこと

- 1問の所要時間と、1人が1つのレベルを何回遊ぶか: 誰も遊んでいない。件数の根拠（1レベル約40〜80時間）は操作の数からの推測。試遊と公開後の記録で確かめる
- TS の生成の速さ: 移植していない。Python の計測と既存ゲームの移植の比からの推測
- 400配りより大きな生成での収率: 新しい大きな生成は回していない（指示による）。L1・L4・L5 は 10〜19件で、95%区間が約3倍に広い。製品の生成スクリプトの統計で置き換える
- 上限5倍の2回目を流していない24件（段3 16・段2 8）と、590秒で止めた 50 の結果と時間: (iii') は既定の5倍の時間・0問とみなした悲観の見込み
- 上限5倍で1回だけ流す形の時間と収率: 測っていない
- 段1・段2 の勝ち筋を解き筋として使う形の時間: 解法器の時間の7割は解けない配り方（4変種とも段3 に入る）で、変わるのは解ける配り方の212秒（400配り）だけと見込んだ（推測）。解けない配り方の網の時間はキャッシュに無い（`v7` は解ける配り方だけを流した）
- 静的な特徴の組み合わせで寄せる形: 1つずつの閾値だけを見た
- 図鑑と採点で1問に持つ値: 図鑑・採点の観点で決める。問題集の大きさは小さな整数4つを仮に置いて測った
- TS の乱数で配った配り方の収率が、Python の `random` で配った400配りと同じこと: どちらも一様な並べ替えとみなした（導出）。TS の乱数の質は確かめていない
