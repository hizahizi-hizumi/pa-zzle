# ソリティア 調査: スマホ操作

## 結論

- **最小幅での札の大きさ**: 成り立つ。
  - アプリが想定する最小幅は 320px（`frontend/src/index.css` の `body` に `min-w-[320px]`）。
  - 7列を左右 8px・列の間 4px・縦横比 1.4 で並べると、札は 320px で 40.0×56.0px、390px で 50.0×70.0px になる。
  - 一番手前の札と、山を押せる幅（札＋列の間 44px）は、既存ゲームの最大盤面の押す対象より大きい。320×568 で比べると、マインスイーパー12列 20.3、橋をかけろ10×10 29.2、タクズ8×8 33.5、ナンプレ 33.7、一筆8×8 36.0px、ウォーターソート14本のボトルの幅 33.7px。
  - ただし、重ねた札の見えている帯は、既存と同じ帯 112px の 320×568 で 11.6〜16.8px しかなく、どの既存の押す対象よりも低い。だから札を1枚ずつ押させない（次の項）。
- **押し方**: 条件つきで成り立つ。
  - 条件: 置き元は札ではなく山（7列・捨て札・組札の1つ）で選び、置き先の山を押したときに、動かす札をルールで決める。
  - 置き元の山と置き先の山の組で打てる手は、いつも1つ以下になる。性質検査では 90,000 局面・374,548 組で例外が 0 だった。並びの中の札は数が全部違うので、置き先の札の1つ下の数で色が逆の札は1枚しかない。空いた列へは K だけ、組札へは手前の1枚だけが動く。
  - 指が狙った所に入る確率（手ぶれ σ8px）は、帯 14.2px の札1枚なら 62.5%、44px の山なら 99.4%。
- **盤面と全操作が一画面に収まるか**: 条件つきで成り立つ。
  - 横は 320px でも収まる。上の段は「山札・捨て札・空き・組札4つ」で、7列の格子にそのまま入る。
  - 操作は、盤面の山、下の帯の待った、見出しのメニューの「盤面を戻す」で、全部が画面の中にある。
  - 縦は、列の長さと画面の高さで決まる（次の項）。
- **長い列（最大19枚）の重ね方**: 条件つきで成り立つ。
  - 19枚は実際の手で作れる。列を長くする方へ探すと、上限が19枚の配り方 13回のうち 4回で届いた。組札へ送るのを後回しにする素朴な遊び方でも、200回のうち 2回で 19枚になった。だから、19枚でも盤面がはみ出さないよう、長い列だけずらし幅を詰める。
  - 既存と同じ待ったの帯（112px）での、19枚のずらし幅: 390×664 15.3、375×667 15.8、360×640 14.7、320×568 11.6、375×548 9.2、320×460 5.6px。
  - 待ったの丸だけの帯（64px）にすると: 18.0 / 18.5 / 17.3 / 14.2 / 11.9 / 8.2px。
  - ずらし幅 12px（字の大きさで約 11px）を目安にすると、19枚は、帯 112px では 390×664・375×667・360×640 で入り、320×568 では入らない。帯 64px なら 320×568 でも入る。ツールバーを出した短い画面（375×548・320×460。高さは推測）では、どちらの帯でも入らない。
  - 実際の長さはそこまで伸びにくい。1回のプレイでいちばん長くなった列は、解いた手順で中央値12枚（最大16）、「置ける所に置き、無ければめくる」で中央値11枚（最大16）だった。帯 64px なら、375×548 でも 13枚を 17.8px、320×460 でも 12枚を 13.5px で置ける。
- **操作とスクロールの競合**: 前例どおりにすれば成り立つ。
  - プレイ画面の外枠は `fixed inset-0 overflow-hidden` なので、ページはスクロールしない。盤面もスクロールさせず、長い列を詰めて収める。
  - 押すだけで遊ぶなら、ウォーターソートのボトルと同じく `touch-manipulation` を付け、`useTouchTap`（指を離した所で受ける）で受ける。iOS Safari は、近くを続けて押すと2回目の click を1回目の所へ送る。置き元と置き先は隣り合う山（44px おき）を続けて押すことが多いので、この扱いが要る。
  - ドラッグを足すなら、盤面に `touch-none` を付け、Pointer Events とポインターの捕捉で受ける（一筆・橋をかけろと同じ）。
  - ダブルタップで組札へ送る操作は入れない。代わりに「置き元を押してから、組札の並び（4つのどれでも）を押す」で同じ手になる。

- [事実] 最小幅は 320px。出典は `frontend/src/index.css` の `body`（`min-w-[320px]`）。

  - 要件は「スマートフォンとPCで主要な体験が成立する」だけで、幅の数字は持たない（`docs/プロダクト/要件/NFR-012-スマートフォンとPCで主要な体験が成立する.md`）。

- [事実] 列から列への手は、置き元の列と置き先の山で1つに決まる。置き先の手前の札が X なら、動かせる並びの中で「X より1つ小さく、色が逆」の札は高々1枚しかない（並びの中の数はどれも違う）。空いた列へは並びの先頭の K だけ、組札へは手前の1枚だけ、捨て札・組札からは1枚だけが動く。`solitaire_mobile.py moves` の性質検査でも例外は 0 だった。

- [推測] ブラウザ表示の縦画面では、safe-area-inset は上も下も 0 とみなした。下端が 34px になる場合（ツールバーを畳んだ Safari やホーム画面に置いた表示）は、別表で計算した。
- [推測] 1行にした手詰まりの知らせ（「手詰まり」＋「待った」＋「盤面を戻す」）は、320px で幅 276px になると見積もった。帯の内側は 288px。字を 14px 角とし、ボタンは `px-3`＋アイコン 16px＋間 8px とした。実際の字の幅で確かめる。
- [推測] 人の遊び方での列の長さは、DFS の解いた手順と素朴な遊び方2種で代用した。組札へ早く送る人ほど列は短い。後回しにする人ほど長く、19枚まで届く。

## 仮決定の候補

- **札と列の並べ方**
  - 推奨: main は左右 `px-2`（8px）、列の間 4px、札の縦横比 1.4。上の段は「山札・捨て札・空き・組札4つ」にして、7列と同じ格子に置く。
  - 理由:
    - 320px で札が 40px あり、既存ゲームの最大盤面のどのマスより広い。
    - 押すだけなら、画面端から始まる戻る操作には当たらない。左右 8px は橋をかけろ・マインスイーパーと同じ。
    - 上の段の空きは、捨て札を2〜3枚ずらして見せる場所に使える。
  - 比べた案:
    - 左右 16px（一筆と同じ）: 札が 37.7px に縮む。ドラッグを入れるときの候補。
    - 左右 4px・列の間 2px: 札は 42.9px になるが、列の間が細く、隣の列との境が見えにくい。
    - 縦横比 1.3: 19枚のずらし幅が 0.4〜0.6px 増えるだけで、札の形がトランプから離れる。
  - 覆したときに作り直す範囲: 盤面の寸法の定数とレイアウトのクラスだけ。
- **縦の重ね方**
  - 推奨: 盤面はスクロールさせない。
    - 列に余裕があるときのずらし幅は、札の高さの 0.3 倍（320px で 16.8px、390px で 21.0px）。
    - 列に入りきらない長い列だけ、その列のずらし幅を「（列に使える高さ − 札の高さ）÷（枚数 − 1）」に詰める。
    - 選んだ印は、持ち上げで場所を取らない形（縁取りや色）にする。
  - 理由:
    - 列はどれも表向きで、奥の札を読むのがこのパズルの考えどころなので、どの札も同じ帯で数とマークを見せる。
    - 19枚は実際に作れる（探索で 4/13、素朴な遊び方で 2/200）ので、詰める仕組みは要る。
    - 詰まるのは長い列のときだけで、ふだんの列はゆとりのある幅のまま並ぶ。
    - ウォーターソートのように持ち上げると、上に 14px 取っておく分だけ列に使える高さが減る。
  - 比べた案:
    - 盤面を縦にスクロールさせる: 失敗パターン集の「一つの視野に収まらない」「スクロールとの競合」に当たる。
    - 全列を同じずらし幅にする: 短い列まで詰まり、長い列が無い間も読みにくい。
    - 並びの所だけ薄く詰める2段のずらし幅: 帯 112px の 320×568 の19枚で、奥の6枚を 15px にすると並びは 9.8px になり、均すより得が無い（計算）。
  - 覆したときに作り直す範囲: 列の描画のずらし幅の計算だけ。
- **下の帯と手詰まりの知らせ**
  - 推奨: 下の帯は、待ったの丸（`UndoButton`）だけを置く 64px（`h-14` の行＋`pb-2`）にする。手詰まりの知らせは同じ帯の中に1行で出す（「手詰まり」の言葉と、待った・盤面を戻すのボタン）。
  - 理由:
    - 19枚のずらし幅が、320×568 で 11.6 → 14.2px、375×548 で 9.2 → 11.9px、390×664 で 15.3 → 18.0px に広がる。
    - 待ったは、既存の多くのゲームと同じ下の中央に残り、共通の `UndoButton` をそのまま使える。
    - 知らせを1行にしても、320px で幅は足りる見込み（推測）。
  - 比べた案:
    - 既存と同じ帯 112px: 見た目は既存とそろう。320×568 の19枚が 11.6px で、目安の 12px を割る。
    - 帯 84px: 今の2段の知らせがそのまま入るが、得は 28px（320×568 で 13.1px）にとどまる。
    - 帯なしで、待ったを上の段の空きに置く: 320×568 で 17.3px と最も広い。ただし上の段の場所は 40px・間隔 44px で、48px の `UndoButton` が入らない。また、手詰まりの知らせの置き場所が無くなる。
    - 待ったを見出しの右（`trailingAction`）に置く: 見出しの端の列は 5.25rem（84px）で、48px の待ったと 40px のメニュー（`size="icon-lg"`、`frontend/src/components/PlayHeader/PlayMenu.tsx`）が、間 4px を足すと 92px になり並ばない。
  - 覆したときに作り直す範囲: プレイ画面の footer と、手詰まりの知らせの並びだけ。盤面の寸法は列に使える高さから求めるので、帯の高さを変えても自動で追従する。
- **押し方**
  - 推奨: 置き元の山を押してから、置き先の山を押す。
    - 列は、どの札を押してもその列を選んだことにする。動かす札は、置き先が決まった時にルールで決める。
    - 選んだときの印は、その列の動かせる並び（赤黒交互・降順の所）全体に付ける。
    - 組札へ送るときは、組札の並びのどこを押しても、その札のマークの組札へ置く（320px で 172×56px の的）。
    - 山札を押すと1枚めくる。空なら捨て札を山札へ戻す。
    - 同じ山をもう一度押すと選び直しになる。
  - 理由:
    - 置き元の山と置き先の山の組で、手はいつも1つ以下になる。だから、11.6〜16.8px の帯を狙わせなくてよい。σ8px の手ぶれでも、山なら 99.4% 入る（帯 14.2px の札1枚なら 62.5%）。
    - 並びの途中から動かす手も、置き先が決めるので取りこぼさない。
    - ウォーターソートと同じ「置き元を押し、置き先を押す」形で、アプリの中で操作がそろう。
  - 比べた案:
    - 札1枚ずつを押す: 帯が狭く、隣の札を選びやすい。
    - 1回押すと置き先を自動で決める: 置き先が2つ以上ある置き元が 21.5% ある。どこへ置くかはこのパズルの考えどころで、合意の「次の手や正しい手は出さない」と、GAME-008 の補助に当たる。
    - ダブルタップで組札へ: 2回目を「選び直し」と見分ける待ちが、どの押し方にも要る。iOS の2回目の click の送り先の問題とも重なる。組札の並びを押す形で、同じ手が2回押しでできる。
  - 覆したときに作り直す範囲: 盤面の入力層と、選んだ印の描き方だけ。
- **ドラッグ**
  - 推奨: 最初の版は押すだけにする。ドラッグは、play-ui の試遊で要ると分かったら足す。
    - 足すときは、押した札が動かせる並びの中ならその札から下を持ち上げ、そうでなければ並び全体を持ち上げる。
    - 落とした山で、動かす札を押し方と同じ規則で決める。
    - 盤面に `touch-none` を付け、左右の余白を 16px にして測り直す。
  - 理由:
    - ドラッグは持ち始めに帯を狙う必要があり、狭い画面で外しやすい。
    - 端から始まるドラッグはブラウザの戻る操作と競合する。
  - 比べた案: ドラッグを主にする。左右の余白を広げると、札が縮む。
  - 覆したときに作り直す範囲: 盤面の入力層だけ。
- **ページスクロール・ブラウザの操作との競合**
  - 推奨: 盤面の山は `touch-manipulation select-none`。押した札は `useTouchTap` で受ける（指を離した所で受け、直後の click を捨てる）。
  - 理由:
    - ダブルタップの拡大を止められる。
    - 隣り合う山を続けて押したとき、iOS が2回目を1回目の山へ送るのを避けられる。
  - 比べた案: `onClick` だけで受ける（ウォーターソートのボトル）。置き元と置き先が 44px 隣を続けて押す形なので、取り違えが起きうる。
  - 覆したときに作り直す範囲: 盤面の入力層だけ。
- **短い画面の扱い**
  - 推奨: ツールバーを出した短い画面（375×548・320×460 の推測の高さ）で長い列が 12px を割ることは、既知の制約として残す。play-ui で撮って、読めるか確かめる。
  - 理由:
    - 帯 64px なら、ふだんの長さ（中央値 11〜12枚）は 375×548 で 19.5〜20.1px、320×460 で 13.5〜14.8px ある。
    - 割るのは、375×548 では 19枚のとき、320×460 では 14枚以上のときだけ。
    - 既存ゲームも、この高さでは縮むか収まらない（マインスイーパー・一筆・橋をかけろ）。
  - 比べた案: 短い画面だけ上の段の札を小さくする。画面の高さで盤面の形が変わり、作りと確認が増える。
  - 覆したときに作り直す範囲: 列の描画のずらし幅の計算だけ。

## 確かめていないこと

- **ずらした帯（12〜18px）で数とマーク（10♥ など）が読めるか、赤と黒・♥と♦が見分けられるか**: ブラウザで撮っていない。字の大きさは推測の式で見積もった。play-ui で 320 / 360 / 375 / 390px を撮って確かめる。
- **実機（iOS Safari・Android Chrome）での押し分けと、隣り合う山を続けて押したときの取りこぼし**: 実機を使えない。play-ui で Playwright のタッチ操作と、最終レビューの「遊ぶ」で確かめる。
- **端末の実際の表示の高さと safe-area**: 実機を使えない。高さと下端の 34px は推測として置いた。
- **Android Chrome の引っ張って更新**: `touch-manipulation` の盤面で下へスワイプしたときに起きるか、確かめていない。プレイ画面の外枠には `overscroll-behavior` の指定が無い。play-ui で確かめる。
- **1行にした手詰まりの知らせの実際の幅**: 字の幅を 14px 角とみなした見積もり。
- **人の遊び方での列の長さと、並びの途中から動かす手の頻度**: DFS の手順は遠回りで、素朴な遊び方は人ではない。試遊で、いちばん長くなった列を記録すれば確かめられる。
- **手ぶれの模擬**: x・y 独立の正規分布で、真ん中を狙うとした。人の狙い方は測れていない。
- **PC と横画面での札の大きさ**: この観点の問いに無いので計算していない。PC は高さで札の大きさが決まる（推測）。
- **「組札へ運べない」の判定をスマホで手早く計算できるか**: 合意の「まだ分からないこと」にあるが、この観点（画面の大きさと操作）の外。判定の計算量を扱う観点で確かめる。
