# タクズ / バイナリパズル成立性調査

Issue #43 の調査結果。

確認日: 2026-09-15

## 結論

**4ゲートすべて通過。実装候補に採用する。**

- ゲート1 問題供給成立性: **GO**
  - 6×6〜14×14で一意解かつ分岐なしで解ける問題を生成でき、性能・多様性にも致命的な問題はない。
- ゲート2 難易度運用成立性: **GO**
  - 解法器から手筋・手順数等を計測でき、ヒント密度を変えた追加実験で難易度指標の分布を意図的に動かせた。生成後の棄却条件を組み合わせれば難易度帯を作り分けられる。
- ゲート3 スマホプレイ成立性: **GO（初期推奨は6×6 / 8×8、10×10は許容、14×14は非推奨）**
  - 390 CSS px幅の実ブラウザ試作で8×8は44.4px/セルを確保できた。10×10は35.3px、14×14は24.9pxまで縮み、14×14は誤タップ・行列比較の負荷が大きい。
- ゲート4 導入判断: **実装候補に採用**
  - 市場規模は上位候補より小さいが、複数の現役アプリで10万+ダウンロードが確認できる。実装・保守負荷が比較的小さく、問題供給・難易度・スマホ操作の3点が成立しているため候補から外す理由はない。ただし実装順を上げる根拠にはしない。

この判断は「今すぐ実装する」という優先度判断ではない。PR #33 の一次選別で市場需要が弱いとした相対評価は維持し、**採用可否と実装順を分離する**。

## pa-zzle で採用する基礎仕様

初期候補では、ルール差を減らすため次を正とする。

- 正方形の偶数サイズを使う。
  - 初期候補: 6×6、8×8、10×10、12×12、14×14
  - 数学的には4×4以上の偶数サイズで定義できるが、4×4は問題空間が小さいため初期提供対象から外してよい。
- 各マスは `0` または `1` のどちらかになる。
- 各行・各列は `0` と `1` を同数含む。
- 横・縦とも、同じ値を3個以上連続させない。
- 完成した2行は同一であってはならない。完成した2列も同一であってはならない。
- 初期ヒントは固定値で、プレイヤーは変更できない。
- 全マスが埋まり、上記制約をすべて満たした時点をクリアとする。
- 配信する問題は一意解を持つことを生成時に検証する。
- 初期版では、対応する論理解法器が分岐なしで完答できる問題だけを配信対象にする。

矩形盤を許す実装例もあるが、サイズ・難易度・表示の契約を単純にするため、pa-zzle の初期仕様では正方形に限定する。

## 名称とルール差

### タクズ / Binary Puzzle / Binairo

一般には同系統のパズルを指し、標準的な3制約は次で共通している。

1. 各行・各列の0/1数が同じ
2. 同値を3個連続させない
3. 行同士・列同士を重複させない

一方で `Binary Puzzle` を名乗る公開例には、3の重複禁止を省いた変種もある。そのため、名称だけでルールを推測せず、pa-zzle 内では上記3制約を明文化する。

`BINAIRO` は少なくとも米国でパズル・オンラインゲーム等を対象に登録商標が確認できる。公開時の主名称には、権利確認を別途行わない限り **「バイナリパズル」** を使い、「タクズ」は検索・説明用の別名として扱うのが無難。

## 問題として成立する条件

### 完成盤

`n × n` の完成盤について、次のすべてを満たせば妥当。

- `n` は偶数
- 全セルが0/1
- 各行・各列で `0` と `1` がそれぞれ `n / 2` 個
- 水平・垂直の長さ3の部分列が `000` / `111` にならない
- 行がすべて異なる
- 列がすべて異なる

### 初期ヒント

完成盤から一部セルを残したものを問題とする。

最低条件は「少なくとも1解を持つ」ことだが、サービスとして配信する問題では以下を追加する。

- 解がちょうど1個
- 対応済みの論理技法だけで解ける

完全解探索で解を2個見つけた時点で打ち切れば、一意性判定に3個以上の解を列挙する必要はない。

### 論理だけで解ける条件

「一意解」と「人間が推測せず解ける」は別条件として扱う。

一意解問題でも、採用した論理技法だけでは途中で停止する可能性がある。したがって生成器では、完全探索器と論理解法器を分離する。

- **完全探索器**: 解数0 / 1 / 2以上を判定する正しさの基準
- **論理解法器**: 人間向けに許容する技法だけを適用し、分岐なしで完答できるかを判定

論理解法器が健全な強制手だけを使って完答できた場合、その経路自体も一意性の強い根拠になる。ただし実装初期は、バグ検出のためにも完全探索による一意性確認を独立して残す方が安全。

## 代表的な解法・検証方法

文献では以下が実用されている。

- 制約伝播付きバックトラック
- SATへの符号化
- SMTへの符号化
- 多項式方程式系 / Gröbner基底

2017年の Utomo / Makarim はバックトラック、SAT、Gröbner基底の3方式を比較している。別研究ではSMTによる解法も扱われている。

一般化した Binary Puzzle の解存在判定は NP 完全である。ただし、これは盤面サイズを任意に拡大した最悪計算量の性質であり、6〜14程度の固定されたサービス盤面が実用上重いことを意味しない。

pa-zzle では、初期実装として以下のどちらかが妥当。

1. 行・列の合法パターンを先に列挙し、制約伝播付きバックトラックで探索する
2. 将来パズル横断の制約ソルバーを採用するなら、SAT / CP-SAT 等へ寄せる

タクズ単体の初期実装なら1で十分軽い。

## 自動生成

### 基本手順

1. 妥当な完成盤を1つ生成する。
2. 全セルを初期ヒントとして開始する。
3. 削除候補セルをランダム順に並べる。
4. 1セルを仮に削除する。
5. 完全探索器で解数を最大2個まで数える。
6. 一意でなければ戻す。
7. 論理解法器で完答できなければ戻す。
8. 目標ヒント数・難易度条件を満たすまで繰り返す。

ヒント数を最小化する必要はない。サービス用途では、最小ヒント問題を作るより「目標難易度・生成時間・見た目」を満たした時点で止める方が扱いやすい。

### 合法な1行の候補数

「0/1が半数ずつ」「3連続禁止」を満たす1行だけを先に列挙すると候補数は次になる。

| サイズ | 1行の合法パターン数 |
|---:|---:|
| 6 | 14 |
| 8 | 34 |
| 10 | 84 |
| 12 | 208 |
| 14 | 518 |

セルを1個ずつ二分探索するより、この行候補を探索単位にすると大きく枝を減らせる。探索中は列側の合法パターン候補も同時に絞り込める。

## 最小実験

### 目的

文献上の成立性だけでなく、pa-zzle が想定する盤面で以下を同時に満たす生成が現実的かを確認した。

- 一意解
- 分岐なしの論理解法で完答
- 6×6〜14×14
- 生成時に一意性確認を繰り返しても極端に遅くならない

### 実装

検証用の使い捨てPython実装を作成した。リポジトリには追加していない。

- Python 3.13.5
- 単一プロセス
- 各サイズ10問
- 乱数seed固定
- 完成盤生成:
  - 各行の合法パターンを事前列挙
  - 行を順に割り当てる
  - 列側も合法パターン候補を保持し、置けない枝を即時除外
  - 行・列重複も検証
- 問題化:
  - 完成盤からランダムにヒントを削除
  - 各削除ごとに解を最大2個まで探索して一意性確認
  - 論理解法器で完答できることも確認
  - 初期ヒントが全セルの40%になるまで削除を試行
- 論理解法器:
  - 3連続回避
  - 行列内の0/1個数確定
  - 完成済み行列との重複回避
  - 合法な行列候補の共通部分から確定する強制手
  - 仮置き・分岐はしない

### 結果

| サイズ | ヒント数 | 10問中央値 | 10問最大 | 論理解法で完答 |
|---:|---:|---:|---:|---:|
| 6×6 | 15 / 36 | 4.04 ms | 5.51 ms | 10 / 10 |
| 8×8 | 26 / 64 | 17.24 ms | 26.16 ms | 10 / 10 |
| 10×10 | 40 / 100 | 88.55 ms | 119.67 ms | 10 / 10 |
| 12×12 | 58 / 144 | 365.14 ms | 670.76 ms | 10 / 10 |
| 14×14 | 79 / 196 | 1,565.61 ms | 3,197.62 ms | 10 / 10 |

40%は品質上の最適値ではなく、成立性確認用の固定条件。

### 解釈

- 10×10以下は未最適化Pythonでもオンデマンド生成が十分現実的。
- 12×12も十分現実的。
- 14×14は最悪数秒になったが、日次問題や問題プールを事前生成する用途では問題になりにくい。
- 専用SAT/CP系ソルバー、候補キャッシュ、対称性削減、並列事前生成などの最適化余地が大きい。
- 既存のGo実装には50×50の生成実績が報告されており、14×14が構造上の上限とは考えにくい。

この実験は「高品質な難易度分布」を証明するものではない。**自動生成・一意性確認・推測不要判定を組み合わせてもサービスサイズで成立する**ことだけを確認した。

## 人間向け論理解法

最低限、以下を別の技法として記録できる。

### 3連続回避

- `00_` / `_00` → 空欄は `1`
- `0_0` → 空欄は `1`
- 1についても同様

### 個数制約

例えば8マスの行ですでに0が4個あれば、残りはすべて1。

### 重複回避

完成済みの行・列と同一にならないよう、残りセルを確定する。

### 行列候補の絞り込み

その行・列についてルールを満たす完成パターンを列挙し、全候補で同じ値になるセルを確定する。

これは仮置きではなく、その行・列の制約から導かれる強制手として実装できる。説明可能なヒントへ発展させる場合は、内部で候補列挙を使っていても、表示上は「個数」「3連続」「重複回避」などユーザーが理解できる理由へ還元できるかを別途設計する。

## 難易度制御への発展

難易度制御は十分可能性がある。

候補となる特徴量:

- 解くために必要な最も強い論理技法
- 技法ごとの適用回数
- 次の強制手が見つかるまでに調べる行列候補数
- 連鎖的に自明なセルが埋まる割合
- 初期ヒント数・配置
- 解答ステップ数
- 盤面サイズ

初期の難易度区分は、例えば次のような技法階層から始められる。

- Easy: 3連続回避 + 個数制約だけで完答
- Medium: 重複回避が必要
- Hard: 行列候補の絞り込みが必要

ただし「技法の強さ = 体感難易度」とは限らない。最終区分・重みはプレイログと人手評価で補正する必要があるため、このIssueでは確定しない。

## 多様性・同型問題

完成盤とヒント配置の両方に乱数を入れられるため、問題供給量そのものは懸念しにくい。

明らかな同型として少なくとも以下がある。

- 0と1の全反転
- 上下反転
- 左右反転
- 転置
- これらから得られる回転・反射

つまり正方形盤では、盤面の二面体対称性と0/1反転を組み合わせた同型がある。配信上の重複を避けたい場合、これらの変換後のシリアライズ表現の最小値を正規形として重複排除できる。

任意の行入れ替え・列入れ替えは3連続制約を壊し得るため、ナンプレのバンド交換のように一般の対称変換として扱わない。

ヒント配置を180度回転対称などに固定することもできるが、良問性との関係は未検証。見た目だけを理由に初期要件へ入れない。

## ヒント・元に戻す・ミス判定との境界

### ヒント

論理解法器が「次に確定できるセル」と理由を返せるため、相性がよい。

初期版では次の2段階を分けられる。

- 軽量: 確定セルを1つ埋める
- 発展: 「この列は0が半数に達したため残りは1」のように理由も返す

### 元に戻す

ゲーム固有ロジックは不要。プレイヤー入力履歴として共通機能化できる。

### ミス判定

2種類を区別する。

- **制約違反**: `000`、個数超過、完成行重複など、現在盤面だけで確定できる矛盾
- **正解との差**: 保存済み一意解と比較した不一致

前者は答えを見なくても警告できる。後者は「ミス表示」設定として任意に有効化できる。ゲーム仕様ではこの2つを同じ概念にしない方がよい。

## 実装時の推奨構成

初期実装は次の責務分離で十分。

- `validate_complete(board)`
  - 完成盤の3制約を検証
- `count_solutions(puzzle, limit=2)`
  - 完全探索
  - 一意性の基準
- `solve_logically(puzzle, allowed_techniques)`
  - 分岐なし
  - 手順と技法を記録
- `generate_solution(size, seed)`
  - 完成盤生成
- `generate_puzzle(solution, policy, seed)`
  - ヒント削除
  - 一意性・論理解法・難易度条件を満たすまで調整

問題データには少なくとも次を保存できる。

- 盤面サイズ
- 初期ヒント
- 一意解
- 生成seed
- 生成器バージョン
- 難易度用メタデータ

今日の問題を再現可能にしたい場合も、seedだけに依存せず最終問題そのものを保存する方が、生成器更新の影響を受けにくい。

## 難易度運用成立性の追加検証

### 難易度指標

論理解法器から少なくとも以下を問題ごとに機械計測できる。

- 使用した最強手筋
- 手筋別の確定マス数
- 解答が進んだ反復回数
- 初期ヒント数・密度
- 未確定マス数
- 盤面サイズ
- 各時点で候補を調べる必要がある行・列数

初期の生成制御は、単一の点数に潰すより「許可手筋 + ヒント密度 + 手順量」の条件として持つ方が扱いやすい。例えば Easy は3連続回避・個数制約だけ、Hard は行列候補の絞り込みを最低1回要求する、といった棄却条件を生成器に与えられる。

### ヒント密度を変える小実験

6×6 / 8×8について、完成盤から一意性を維持しながらヒントを削除し、目標ヒント密度を65% / 55% / 45% / 35%へ変えた。各条件5問、計40問の小実験を行った。生成後、同じ論理解法器で手筋を記録した。

| サイズ | 目標密度 | 実密度平均 | 論理解法で完答 | 基本手筋のみ | 行列候補絞り込み使用 |
|---:|---:|---:|---:|---:|---:|
| 6×6 | 65% | 63.9% | 5/5 | 5/5 | 0/5 |
| 6×6 | 55% | 55.6% | 4/5 | 4/5 | 1/5 |
| 6×6 | 45% | 44.4% | 3/5 | 3/5 | 1/5 |
| 6×6 | 35% | 36.1% | 1/5 | 1/5 | 1/5 |
| 8×8 | 65% | 65.6% | 4/5 | 4/5 | 0/5 |
| 8×8 | 55% | 54.7% | 4/5 | 4/5 | 0/5 |
| 8×8 | 45% | 45.3% | 3/5 | 3/5 | 2/5 |
| 8×8 | 35% | 34.4% | 1/5 | 0/5 | 4/5 |

ここで「完答できない」は問題が不正という意味ではない。一意解は維持しているが、今回実装した論理手筋集合だけでは分岐なしで最後まで進めなかった問題である。配信時はこのような問題を棄却できる。

密度を下げると基本手筋だけで解ける割合が下がり、行列候補の絞り込みが必要な問題や、現手筋集合では完答できない問題が増えた。**ヒント密度だけを難易度とみなすことはできないが、生成パラメータとして難易度分布を動かす作用は確認できた。**

### 代表問題の比較

8×8から、指標上の簡単側・難しい側を1問ずつ抽出した。

- 簡単側: 42ヒント。3連続回避11マス、個数制約11マスで完答。行列候補の絞り込み不要。3反復で終了。
- 難しい側: 22ヒント。3連続回避24マス、個数制約12マスに加え、行列候補の絞り込み6マスが必要。8反復で終了。

盤面を追うと、簡単側は初期状態から局所的な強制手が多数見えるのに対し、難しい側は途中で行・列全体の候補比較が必要になる。少なくともこの2問では、**「必要手筋が強い・反復が深い」という指標と、盤面を読む負荷の大小が逆転していない**。

この小実験だけで Easy / Medium / Hard の最終閾値は決めない。一方、Issueの通過条件である「狙った難易度帯を作り分け、後続で校正できる方法」は確認できた。

## スマホプレイ成立性の追加検証

### 既存事例

Google Play の `Mr. Binairo - Binary Sudoku` は6×6 / 8×8 / 10×10 / 12×12を提供し、セルのタップで `0 → 1 → 空欄` を循環する方式を採用している。つまり、この方式自体には実運用例がある。

一方、pa-zzleではタップ循環だけに固定する必要はない。比較用に以下2方式を試した。

1. セルを直接タップして `空欄 → 0 → 1 → 空欄` を循環
2. `0入力` / `1入力` モードを選び、その後セルをタップ

連続して同じ値を入れる局面では入力モード方式の方が操作数を減らせる。一方、値が交互に変わる局面ではモード切替が増える。初期実装では**タップ循環を基本操作**とし、入力モード方式は必要性が出た場合の追加候補とする。

### 実ブラウザ試作

完成UIではなく、盤面サイズと入力精度だけを見る使い捨てHTMLを作り、Chromium / Playwrightで390×844 CSS px、タッチ入力有効のスマートフォン相当条件で描画・操作した。試作コードはリポジトリには残していない。

左右12pxの余白、盤面外枠2px、セル間1pxの条件で実測したセル寸法は以下。

| 盤面 | セル実測 | 判定 |
|---:|---:|---|
| 6×6 | 59.5 × 59.5 CSS px | GO |
| 8×8 | 44.4 × 44.4 CSS px | GO |
| 10×10 | 35.3 × 35.3 CSS px | 条件付きGO |
| 14×14 | 24.9 × 24.9 CSS px | 初期提供は非推奨 |

Appleは通常のタップ対象として44×44pt以上を推奨し、ゲーム向け資料では重要度の低い操作でも28×28ptを最小値として示している。WCAG 2.2のTarget Size (Minimum)は24×24 CSS pxを基準とする。

このため8×8までは盤面全体を横スクロールなしで表示しながら、Appleの推奨44相当も満たせる。10×10はWCAGの24px基準を上回り、盤面全体も見えるが、頻繁に押すセルとしては44相当を下回るため実装時の誤タップ確認が必要。14×14は約24.9pxでWCAG基準には収まるものの、Appleがゲームで示す28ptの最小値も下回り、隣接セルを連続操作する盤面として余裕がない。

14×14を44pxセルにすると盤面だけで616px必要になる。横スクロールや拡大を導入すれば入力面積は確保できるが、タクズで重要な「行・列全体を比較する」操作と競合する。したがって、**スマホ初期版の上限は8×8を推奨し、10×10は実装時の操作確認を通して採否、12×12以上は初期対象外**とする。

試作ではタップ循環の `空欄 → 0 → 1` と入力モードでの0入力を実際に操作し、意図したセルだけが変化することを確認した。`pageerror` と `console.error` は0件だった。

## 市場実績と導入判断

PR #33では需要未確認だったため追加確認した。2026-09-15時点でGoogle Playには、標準3制約を採用する `Mr. Binairo - Binary Sudoku` が10万+ダウンロード・約950レビュー、同系統の `Rumba: Daily Binary Puzzle` が10万+ダウンロード・約2,300レビューで掲載されている。複数製品で継続利用されているため「市場が存在しない」とは言えない。

ただし、PR #33で上位に置いたパーキングジャム100M+、マインスイーパー10M+、ノノグラム50M+等と比べると桁が小さい。日本App Storeでも、今回確認できた専用アプリから強い国内需要を示す評価件数は得られなかった。**市場実績は採用を否定しないが、実装順を上げる根拠にもならない。**

実装面では、盤面は二値グリッド、入力は単一セル、ルールは3制約で閉じる。固有の重いUIや物理挙動を必要とせず、生成器・完全探索器・論理解法器を分離できるため、パズル固有の実装・保守負荷は比較的小さい。ナンプレと同じ論理グリッド系で新規性は小さめだが、二値入力と行列重複制約は異なるプレイ感を持つ。

以上から、**実装候補には採用する。ただし優先度は上げない。**

## 採用後に残る課題

以下は導入可否を保留する未知ではなく、実装時または運用開始後に詰める項目。

- Easy / Medium / Hard の最終閾値と算出式
- 実ユーザーのプレイ時間・離脱・ヒント利用等による難易度校正
- 同じ難易度帯でも単調な問題を弾く良問指標
- 10×10をスマホ初期提供に含める場合の実装UIでの誤タップ確認
- ヒント説明を人間向けの理由へ変換する表示設計

これらはIssue #43の4ゲート判定を覆す前提条件ではない。

## 4ゲート判定

| ゲート | 判断 | 根拠 |
|---|---|---|
| 1. 問題供給成立性 | GO | 6×6〜14×14で生成・一意性・推測不要を実測。多様性・同型抑制も実装可能 |
| 2. 難易度運用成立性 | GO | 手筋・手順量を計測可能。ヒント密度変更で指標分布が動き、生成後の棄却で帯を作り分け可能 |
| 3. スマホプレイ成立性 | GO | 390px幅で6×6 / 8×8が十分なセル寸法。10×10は条件付き、14×14は初期非推奨 |
| 4. 導入判断 | 実装候補に採用 | 市場は上位候補より小さいが複数10万+実績あり。3ゲート成立かつ固有実装負荷が比較的小さい |

**Issue #43 の結論は「実装候補に採用」。実装優先度はPR #33の相対評価を維持し、上げない。**
