# タクズ導入前提調査

タクズ（Takuzu / Binairo / バイナリパズル。2値を置くロジックパズル）を pa-zzle のゲームとして導入するための前提調査。

## 目的

タクズを、ゲーム選択 → 難易度選択（`難易度 1`〜`難易度 5`）→ プレイ → クリア → 結果（スコア）→ プレイ記録・自己ベスト・再プレイ・内部診断まで、既存ゲーム（ナンプレ・ウォーターソート・マインスイーパー）と同じ水準で成立させる。そのための前提を、現在の pa-zzle の契約（`APP.md`、`GAME.md`、`DESIGN.md`、`docs/プロダクト/`、`docs/パズル/` の難易度文書）、既存の [タクズ成立性調査](タクズ成立性調査.md)、外部の実装例、この調査で行った小規模な実測から導く。

この文書は導入調査であり、現在仕様の正本ではない。後続の実装・検証を経て採用した契約だけを `docs/プロダクト/仕様/パズル/` の現在仕様へ反映する。

### 事実と推測の書き分け

根拠の種類を次の見出し語で区別する。

- **事実（リポジトリ）**: 現在のリポジトリの文書・コードから確認したこと。
- **事実（実測）**: この調査のために一時コードで測った結果。条件と限界は §15 に書く。
- **外部知見**: 既存製品・公開資料で確認できること。この調査では検索結果の要約で確認し、原典の全文は読み直していないものを含む。
- **導出**: 定義から論理的に導けること。
- **推測・仮説**: 上の4つから導いた判断で、実プレイや問題集合での検証が済んでいないもの。

判断が必要な点は関係文書の原則に沿って決め、§16「仮決定一覧」に理由・見直す条件と一緒に残す。後続の実装は §16 に従う。

## 結論

タクズは引き続き実装を進める。ただし、[タクズ成立性調査](タクズ成立性調査.md) の「4ゲート通過」は3段階（Easy / Medium / Hard）の難易度を前提にした判断で、現在の採用条件である5段階の難易度提供（`難易度提供.md`、`SPEC-005`）を確認していない。そこで難易度運用ゲートを `確認中` へ戻し、導入判断は `条件付き保留` とする（§17）。5段階の供給は難易度段階の実装で確かめる。

実装は次を前提に進める。

- 表示名は **「バイナリパズル」** とする。「タクズ」「Binairo」は EU 等で商標とされているため、利用者に見える名称には使わない。コード上のゲームID・ディレクトリ・ルートは計画どおり `takuzu` のままにする（§3）。
- ルールは **正方形・偶数サイズ・各行各列で2種が同数・同じものの3連続禁止・同一の行どうし／列どうしの禁止** の標準3制約とする。問題は固定の初期配置（手がかり）を持ち、一意解で、推測（仮置きと後戻り）なしに解ける（§4）。
- 2値は **数字の 0/1 ではなく、明度と形が異なる2種類のタイル** で表す。色だけに頼らない（§5）。
- 操作は **マスのタップで `空 → A → B → 空` を巡回** する。入力モード切替は置かない。PC では右クリックで逆順に巡回する（§6）。
- 盤面だけから分かるルール違反（3連続・個数超過・完成した行／列の重複）は **その場で盤面に示す**。解答との照合結果は **表示も計数もしない**。2値のパズルでは照合結果がそのまま答えになるため（§7）。
- **元に戻す・ヒント・自動補助・行列の個数表示は提供しない**。やり直すと新しい問題は提供する（§8）。
- 盤面は **全難易度で 8×8 に固定** する。サイズを難易度にしない（§10）。
- 難易度が表す挑戦は **「盤面から次に確定できるマスを見つけ出し、必要ならより遠い関係（行全体の残り個数、完成済みの行との比較）まで読んで確定させること」** とする（仮説）。人間向け解法器が使う手筋の段階と、各局面で確定できるマスの見つけやすさで観測する（§11）。
- 問題は **事前生成した問題集** から供給する（§12）。
- プレイ評価は **速さと、置き直しの少なさ（正確さ）** の2観点で作る（仮説。§13）。難易度の高さそのものを加点しない。

## 1. 現在の pa-zzle から導かれる条件

### 1.1 事実（リポジトリ）: 守るべき契約

- `GAME.md`: パズルそのものを主役にする。プレイヤーが考える部分を奪わない。UI自体の迷いや操作負荷をゲームの難しさにしない。題材と表現を一致させる。操作結果を自然に返す。難易度を人間の体験として扱う。達成とプレイの出来を分ける。
- `SPEC-003`: パズル・ゲーム・問題・プレイセッションを区別する。
- `SPEC-004`: 難易度はすべてのゲームに共通の開始条件。ゲーム固有の開始条件は追加してよい。
- `SPEC-005` / `難易度提供.md`: 採用するパズルは、難易度1〜5のそれぞれに意味のある挑戦差を持ち、各レベルの問題を意図的かつ継続的に供給できなければならない。
- `SPEC-006`: 評価は100点満点。100点 = `perfect`、90点以上 = `great`、80点以上 = `good`、それ未満のクリア = `clear`。評価は保存したプレイ事実から計算し直せる。何を良いプレイとして称えるかから評価観点を決める。
- `SPEC-007`: 元に戻す・やり直す・新しい問題は別の操作。すべてを提供する必要はない。
- `SPEC-008`（ナンプレ）: 入力が完成解と異なる場合をミスとして記録し、盤面上の制約競合と完成解に対する誤答を別の意味として扱う。
- `SPEC-010`（マインスイーパー）: 旗は利用者のメモで正誤を判定しない。ヒント・自動旗・確定マスの提示は通常UIで提供しない。問題は推測なしに解ける。問題集から供給する。
- `難易度.md`: 手数・所要時間・盤面サイズなどの作業量や複雑さは、それだけでは難易度ではない。
- `難易度判定.md`: 高度な手筋を必要とすることを高難易度とするなら、その手筋を分析で表現できなければならない。分析で扱えない解法過程を要する問題は評価不能として扱う。
- `.claude/rules/game-structure.md`: `puzzle/`・`problem/`・`session/`・`play/`・`ui/`・`difficulty.ts`・`score.ts`・`problem-selection.ts`・`play-record.ts` の責務分離と、`<Game>Problem` と `<Game>ProblemIdentity` の分離。

## 2. ゲームの核と守る体験

### 2.1 ルール（外部知見）

- n×n（n は偶数）の盤面の各マスに、2種類の記号のどちらかを置く。
- 各行・各列には、2種類を同数（n/2 個ずつ）置く。
- 横・縦のどちらにも、同じ記号を3つ以上続けて置かない。
- 同じ並びの行を2本作らない。列も同様。
- 初期配置（手がかり）は変更できない。

### 2.2 遊びの核（推測・仮説）

タクズで考える面白さは、次の点にあると考える。

1. **局所の形から確定させる爽快さ**: 「同じものが2つ並んだら両隣は反対」「同じもので1マス挟んだら間は反対」のように、形を見た瞬間に1マスが決まる。決まったマスが次の形を作り、連鎖して盤面が埋まっていく。
2. **次の一手を探す読み**: 盤面のどこかに必ず確定できるマスがあるが、それが目立たない局面がある。行・列を見渡して手がかりを探すこと自体が考えどころになる。
3. **行全体を読む推論**: 局所の形で決まらなくなったとき、行の残り個数（「この行はもう1つしか A が入らない」）や、完成済みの行との比較（「このままだと上の行と同じ並びになる」）を使って確定させる。

1 が遊びの基本的な気持ちよさ、2 と 3 が挑戦の強さを変える部分だと仮定する（§11）。

### 2.3 タクズで守る体験（GAME.md への対応）

| GAME.md の原則 | タクズでの具体化 |
| --- | --- |
| パズルそのものを主役にする | 8×8 盤面を画面の主役にし、スマホ幅いっぱいに置く。経過時間などはヘッダーに控えめに置く。行・列ごとの個数表示などの計測値を盤面の周りに並べない。 |
| プレイヤーが考える部分を奪わない | 確定できるマス、正解との一致、次の一手を通常UIで示さない。盤面を見れば読めるルール違反だけを示す（§7）。 |
| UIの迷いや操作負荷を難しさにしない | 1マスの入力をタップだけで完結させ、入力モードを持たない。押し間違えても同じマスを押し続ければ空に戻る。セルは 44px 前後を確保する。固定マスは見た目で区別し、押しても何も起こさない。 |
| 題材と表現を一致させる | 0/1 の数字ではなく、2種類のタイルが盤面を埋めていく見た目にする。数字にすると「計算するパズル」に見え、ナンプレとの違いも薄れる（§5）。 |
| 操作結果を自然に返す | タイルが置かれる短い変化、ルール違反のマスへの印、完成時に盤面全体が揃う演出で返す。説明文に頼らない。 |
| 演出待ちでテンポを損なわない | 置く演出の最中も次の入力を受け付ける。状態は即時に更新する。 |
| 繰り返し遊べる | 問題集から毎回別の問題を出し、同型（回転・反転・2種の入れ替え）の重複を問題集から除く（§12）。 |
| 達成とプレイの出来を分ける | クリアは「盤面を完成させた」こととして返し、スコアは速さと置き直しの少なさで別に返す（§13）。 |

## 3. 表示名

### 3.1 外部知見

- このパズルは Binairo、Takuzu、Binero、Tohu-Wa-Vohu、Eins und Zwei、Binary Puzzle、Binoxxo、Tic-Tac-Logic、Sudoku Binary など多くの名前で知られる。
- 「Binairo」と「Takuzu」は EU で商標とされている（英語版 Wikipedia「Takuzu」の記述。検索結果の要約で確認）。「Binero」はフランスで商標とされている。
- 「BINAIRO」は米国でもパズル・オンラインゲーム等を対象とする登録が確認されている（[タクズ成立性調査](タクズ成立性調査.md)）。
- 「Takuzu」は日本語風の響きを持たせた名称で、英語圏では検索語として最も一般的になっている。日本語圏での一般的な呼び名は定まっていない。
- LinkedIn の「Tango」は、2値に加えて「=」「×」の隣接制約を持つ派生で、別のパズルとして扱う。

### 3.2 判断

表示名は **「バイナリパズル」** とする。

- 「Binary Puzzle」は複数の出版物・アプリで一般名称として使われており、特定事業者の商標として確認できなかった。
- 「タクズ」は Takuzu の読みで、Takuzu が EU で商標とされている以上、利用者に見える主名称にするには権利確認が要る。この調査では権利者と指定商品を確認しきれていない。
- 「バイナリ」は2状態を置くというルールの核を表す。タイル表現（§5）にしても意味が通る。

扱い:

- 利用者に見える名前（ゲーム選択、プレイ画面、結果、記録、ページタイトル、ピクトグラムの代替テキスト）はすべて「バイナリパズル」とする。
- コード上のゲームID・ディレクトリ・ルート（`takuzu`、`/puzzles/takuzu`）は既定の計画どおり変えない。URL に `takuzu` が見える点は、権利確認の結果に応じて見直す候補として残す（§18）。
- 文書（この導入調査・正本仕様の本文）では、同じパズルを指す通称として「タクズ」を併記してよい。

## 4. ルール（採用するルール）

### 4.1 盤面と完成条件

- 盤面は正方形で、一辺は偶数とする。製品で提供するのは 8×8（§10）。
- 各マスは A か B のどちらか（内部表現は `0` / `1` でよい。§5 の見た目と分ける）。
- 完成盤は次をすべて満たす。
  1. 各行・各列に A と B がちょうど n/2 個ずつある。
  2. 横・縦に同じ値が3つ以上続かない。
  3. どの2行も同じ並びでない。どの2列も同じ並びでない。
- 初期配置は固定で、利用者は変更できない。

### 4.2 問題の成立条件

- 解がちょうど1つある（完全探索で2個目の解が無いことを確認する）。
- 人間向け解法器（§11.3）が、推測（仮置きと後戻り）なしに完答できる。
- 「一意解」と「推測なしで解ける」は別の条件として両方確認する。

**導出**: 固定の初期配置を持つ問題に解が1つしかないなら、ルールをすべて満たして全マスが埋まった盤面はその解と一致する。したがってクリア判定は「全マスが埋まり、ルールをすべて満たす」ことと「解と一致する」ことのどちらで行っても同じ結果になる（§9）。

### 4.3 採らない変種

- 重複禁止を省く変種は採らない。重複禁止はルールの一部で、それを使う推論（§11.3 の手筋 D）が挑戦の上側を支えると見込むため（§15）。
- 長方形盤、奇数サイズ、隣接制約（Tango の「=」「×」）は採らない。

## 5. 視覚表現

### 5.1 外部知見

- 0h h1 は赤と青のタイルで2値を表す。固定マスには鍵の印を表示・非表示できる。
- Unruly は黒と白のマスで表す。
- LinkedIn の Tango は太陽と月の記号で表す。
- 新聞・書籍の Binairo は 0 と 1 の数字で表すことが多い。

### 5.2 判断: 数字ではなく、2種類のタイル

- **2種類のタイル（A / B）で表す**。数字の 0/1 は使わない。
  - 数字は「足し算・数合わせ」の印象を与え、ナンプレと同じ見た目になる。2種類の物が交互に並ぶ感覚は形と色の方が伝わりやすい（`GAME.md`「題材と表現を一致させる」）。
  - 3連続や重複の読み取りは、形と色の塊として見えた方が速い（推測。UI段階で確認する）。
- **色だけで区別しない**。A と B は次の3点すべてで区別する。
  - 明度差（グレースケールにしても見分けられる）。
  - 形の差（例: A は塗りつぶしの面、B は輪郭を持つ明るい面や中に印のある面）。
  - 色相差（2色覚でも区別しやすい組み合わせ。青系と橙・黄系など。赤と緑の組は使わない）。
- 色はゲーム固有色として `frontend/src/games/takuzu/` 側で持つ。`primary`・`success`・`error` などの共通トークンやブランド色を流用しない（`DESIGN.md` §5）。ライト／ダークの両方で、A・B・空マスの3状態が区別できるようにする。
- **空マス** は盤面の地の色の穴として見せ、A・B より弱くする。
- **固定マス** は、置いたマスと同じ A / B の見た目に、固定であることが分かる控えめな差（例: 角の小さな印、わずかに沈んだ面、枠の有無）を付ける。0h h1 の鍵のように常時目立つ記号は置かない。
- 具体的な色値・形・寸法は、プレイUI段階で複数案を比較して決め、ライト／ダーク・390×844 / 1280×800 で確認する。

## 6. 操作

### 6.1 外部知見

- 0h h1、Mr. Binairo は、マスのタップで `空 → A → B → 空` のように巡回する方式。
- Unruly はマウスの左クリックと右クリックで2値を置き分ける（スマホ版では巡回）。
- 成立性調査の実ブラウザ試作では、タップ巡回と「A入力 / B入力」モード方式の両方を試し、どちらも意図したマスだけが変わることを確認した。モード方式は同じ値を続けて置く局面で操作が減る一方、値が交互に変わる局面では切り替えが増える。

### 6.2 判断

- **マスのタップで `空 → A → B → 空` を巡回する**。入力モードは持たない。
  - 1マスの入力が盤面の中で完結し、盤面の外の状態（現在のモード）を覚えておく必要がない。モードを見失う迷いは UI の負荷で、挑戦ではない。
  - 押し間違えても、同じマスを押し続ければ空に戻る。
  - B を置くには2回押す必要があるが、完成盤では A と B が同数なので、どちらを先にしても平均の操作量は変わらない（導出）。操作回数は評価に使わない（§13）。
- **PC では右クリックで逆順（`空 → B → A → 空`）に巡回する**。キーボードでは矢印キーでマスを移動し、決まったキーで A / B / 空を直接置けるようにする（キー割り当てはUI段階で決める）。
- **長押し・スワイプ・ドラッグでの連続塗りは初期実装に入れない**。ページのスクロール・選択と競合しやすく、盤面が 8×8 なら1マスずつのタップで足りると推測する。実ブラウザで操作量が負担になると分かった場合の追加候補として残す。
- **固定マスを押しても何も変えない**。不成立を強く返す必要はないが、押せないことが分かる小さな反応（ごく短い揺れ等）は UI 段階で検討する。ミスとして数えない。
- 盤面は 390px 幅で 1マス 44px 前後を確保する（成立性調査の実測: 左右12px余白で 44.4px）。

## 7. 誤りの扱い

### 7.1 2種類の「誤り」

- **ルール違反**: 3連続、行／列の個数超過、完成した2行（2列）の一致。今の盤面だけから分かる。
- **解答との不一致**: 置いた値が一意解と違う。盤面だけからは分からない。

### 7.2 判断: 解答との不一致は表示も計数もしない

- 2値のパズルでは、あるマスの A が「解答と違う」と示すことは、そこが B だと教えることと同じ（導出）。ナンプレ（9択）と違い、照合結果の表示が答えの表示になる。1マスずつ試すだけで全マスの答えが分かってしまい、`GAME.md`「考える部分を奪わない」に反する。
- 表示しないまま裏で「解答と違う値を置いた回数」を数える案も採らない。巡回入力では、B を置く途中で必ず A を経由するので、どの時点の値を「置いた値」とみなすかを決めないと数えられない。押し間違えもそのまま誤りになり、操作の負荷がゲームの難しさへ混ざる。
- この点でナンプレ（`SPEC-008`: 完成解と異なる入力をミスとして記録）とは扱いが違う。マインスイーパー（`SPEC-010`: 旗の正誤を判定しない）と同じく、「盤面にない正解情報を UI から漏らさない」側に揃える。

### 7.3 判断: ルール違反は盤面にその場で示す

- 盤面だけから分かるルール違反は、**違反が生じた時点で、関係するマス・行・列に印を付けて示す**。違反が解消したら印を消す。
  - 3連続: 続いている3つ以上のマス。
  - 個数超過: A または B が n/2 個を超えた行・列。
  - 重複: 全マスが埋まり、並びが一致した2行（2列）。
- 理由:
  - 盤面に見えている事実を強調するだけで、盤面にない情報を加えない。
  - 違反に気づかず先へ進み、後で盤面全体をやり直す手戻りは、挑戦ではなくプレイ摩擦と考える。
  - Unruly はルール違反を強調表示し、LinkedIn の Tango も誤りのある行・列を強調する（外部知見）。慣れた利用者にとって自然な流儀である。
- 限界と対策:
  - 同じマスで A を置いて違反の印が出たら B にする、という「試して見る」使い方ができる。ただしこれで分かるのは、3連続・個数超過のように **盤面を見ればすぐ分かる直接の違反** だけで、盤面を読む手間を少し省く程度にとどまる（推測）。行の残り個数を使う推論や重複を避ける推論（§11.3 の C・D）は、違反が出る前の段階で判断が要るので、印からは分からない。
  - 巡回入力では、B を置く途中で一瞬 A の状態を経由する。その一瞬に出る違反の印が点滅のように見えないよう、表示の出方（短い遅れ・弱い出現）を UI 段階で調整する。状態の判定自体は即時に行う。
- 違反の見せ方は、共通の `error` 色ではなくゲーム固有の表現にする（`DESIGN.md` §11「ゲーム固有の失敗、不正解、非合法手は、それぞれのゲームの意味に従って表現する」）。色だけに頼らず、マス上の印（斜線・破線の縁など）や行・列の端の印を併用する。
- ルール違反の発生回数は評価に使わない（巡回途中の一瞬の違反も数えてしまうため）。

## 9. クリア判定と完成

- **全マスが埋まり、§4.1 の3制約をすべて満たした時点でクリア** とする。一意解の問題なので、これは解との一致と同じ（§4.2 の導出）。実装では解との一致を判定に使ってよい。
- 全マスが埋まってもルール違反が残っていればクリアにしない。違反の印（§7.3）がそのまま手がかりになる。
- クリアした瞬間に入力を止め、盤面全体が揃ったことを短い演出で返してから結果画面へ進む（ウォーターソートの `clearing` → `result` と同じ進行）。演出の具体はUI段階で決める。
- クリアしない終わり方（失敗）は無い。途中でやめる場合は既存ゲームと同じくメニューから離れる。

### 9.1 プレイUIの実ブラウザ比較・確認結果（事実（実測）+ 判断）

プレイUI段階で、§5〜§9 で UI 段階へ残した見せ方を実ブラウザで比べて決めた。Chromium（Playwright）で、同じ固定問題の同じ途中盤面（1行目に3連続と個数超過の違反がある）を 390×844 のライト／ダークで撮って比べた。確認は自動操作によるもので、人間の実プレイでの見やすさ・誤タップの頻度は未確認である。

**タイルの見た目（§5.2）**: 次の3案を比べ、**案2** を採った。

1. A は青の角丸四角、B は黄の輪（プレイ縦断で置いた仮の見た目）
2. A は濃い青の角丸四角、B は明るい黄の円。どちらも塗りで、マスの 86% の大きさ
3. A・B とも角丸四角。B は黄の地に輪の印

案1 は B の輪が細く、320px 幅（1マス 36px）では B が A より軽く見える。ダークでは A（明るい青）と B（ほぼ白の地）の明度が近くなり、明度で区別するという §5.2 の条件を満たさない。案3 は外形が同じなので、3連続を「同じ形の塊」として読めず、色と中の印に頼る。案2 は四角が並ぶと帯に、円が並ぶと玉の列に見え、3連続が形のまとまりとして読める。ダークでも A（青）を B（明るい黄）より暗く保ち、明度・形・色相のどれか1つだけでも見分けられる。

**固定マスの印（§5.2）**: マスの左上の点と、タイル中央の小さな点を比べ、**タイル中央の点** を採った。タイルをマスいっぱいに近づけると、左上の点は四角いタイルの角に重なり、盤面の端に散らばる雑音に見える。中央の点はタイルの外形を変えず、A・B のどちらでも同じ位置に見える。置いたタイルには点が無いので、固定と自分で置いたタイルを盤面全体で見分けられる。

**ルール違反の印（§7.3）**: 次の3案を比べ、**案3** を採った。

1. マスの破線の枠（プレイ縦断で置いた仮の見た目）
2. マスの実線の枠と、タイルの下に敷く斜線
3. マスの実線の枠と、タイルの上に重ねる斜線

違反は行・列の全マスへ印を付けることが多い（個数超過・重複）。その行・列がほぼ埋まっていると、案2 の斜線はタイルに隠れて空きマスにしか見えず、残るのは細い枠だけになる。案1 の破線は細く、違反の無いマスとの差が弱い。案3 は埋まったマスでも斜線が見え、斜線の下のタイルの形と色は読める。色は共通の `error` ではなくゲーム固有の赤系（rose）とし、枠と斜線で色だけに頼らない。違反の種類（3連続・個数超過・重複）で印を変えることはしていない。3連続だけならその3マス、個数超過・重複なら行・列の全マスに同じ印が付くので、範囲の違いから読める。

**巡回途中の一瞬の違反（§7.3）**: 違反の印は、違反が生じてから 240ms 待って 150ms で出し、解消したら待たずに消す。判定と読み上げ用の名前（「ルール違反」）は即時に変わる。空きマスを押して A（3連続になる）にし、同じマスをもう一度押して B（違反なし）にする操作で、印の不透明度を描画ごとに測った。

| 2回目を押すまでの間隔 | 印の不透明度の最大 |
| --- | --- |
| 120ms | 0（出ない） |
| 200ms | 0（出ない） |
| 400ms | 1（A の間に一度出て、B で消える） |

連続して押す限り、途中の A の違反は見えない。A のまま手を止めれば、その違反は 240ms 後に見える。

**操作フィードバック（§6.2）**

| 観点 | 結果 |
| --- | --- |
| タイルを置く | 置いたタイルだけが 75% の大きさから短く（100ms）膨らんで出る。押している間はマスが少し縮む（94%）。状態は即時に変わり、連続して押しても入力を取りこぼさない |
| 固定マス | 押すとそのマスだけが小さく横に揺れる（220ms）。盤面・入力回数は変わらない。固定マスには押下の縮みとホバーの色変化を付けない |
| 右クリック | PC で逆順に巡回する。タッチの長押しでは逆巡回しない（プレイ縦断のまま） |
| 動きを減らす設定 | `prefers-reduced-motion: reduce` では、置く・縮む・揺れる・完成の動きを再生しない |

**キーボード（§6.2）**: 盤面は Tab で1マスだけに入り（最後にフォーカスしたマス。初めは左上）、矢印キーでマスを移動する。端では止まる。`1` で A、`2` で B、`0`・Backspace・Delete で空きにする。Enter・Space はタップと同じ順方向の巡回になる。`1` / `2` は巡回の順（A → B）に合わせた。修飾キー付きの入力は盤面へ流さない。フォーカスは `ring` の色の 3px の枠で示す。1280×800 で、全空きマスをキーボードだけで解き、完成まで進めることを確かめた。

**ヘッダーとメニュー**: 既存ゲームと同じく、左に戻る、中央に表示名と計測値、右にメニューを置く。計測値はプレイ縦断のまま「難易度 N · 時間 mm:ss」とする。既存ゲームのヘッダーは難易度を出さず、ミス・手数・待った・地雷・旗などプレイの計測値を並べる点が異なる。置き直し回数をプレイ中に見せるかは決めておらず、スコア段階で扱う。やり直す（盤面を戻す）はヘッダーのボタンからメニューへ移した。メニューは「盤面を戻す（経過時間は続く）」「リセット（同じ問題を始めから）」「ホーム」。「別の問題」「難易度変更」「検証情報」は受け口だけを用意し、問題集・難易度選択・診断をつなぐ段階でメニューに出す。それまで戻るボタンはホームへ戻る。

**完成演出（§9）**: 最後のタイルが揃うと入力を止め、盤面の左上から右下へ、マスを小さく持ち上げて明るくする斜めの波を送る（1マス 380ms、行＋列ごとに 35ms ずらし、波は全体で約 0.9 秒。波のあと 240ms 置き、完成から約 1.1 秒で次へ進む）。行・列が揃ったことを盤面全体で確かめる動きにした。そのあと、結果画面を導入するまでの仮表示として、盤面の上に「完成！」と「同じ問題をもう一度」を出す。動きを減らす設定では波を再生せず、完成後すぐ（実測 5ms）仮表示へ進む。

**盤面の大きさ**: 盤面はヘッダーを除いた領域の幅と高さの小さい方に合わせ、左右の余白は 8px とする。PC では 40rem（640px）まで広げる。

| 画面 | 盤面 | 1マス | はみ出し |
| --- | --- | --- | --- |
| 320×568 | 304px | 36.3px | なし |
| 360×780 | 344px | 41.1px | なし |
| 375×667 | 359px | 42.9px | なし |
| 390×844 | 374px | 44.7px | なし |
| 1280×800 | 640px | 76.4px | なし |

どの画面・ライト／ダークでも、pageerror と console.error は 0 件だった。スマートフォン縦画面では盤面の上下に余白が残る。

## 10. 盤面サイズ

### 10.1 事実と外部知見

- 390px 幅での実測セル寸法（成立性調査）: 6×6 は 59.5px、8×8 は 44.4px、10×10 は 35.3px、14×14 は 24.9px。
- Apple は通常のタップ対象に 44×44pt、ゲームでも重要度が低い操作で 28pt を最小としている。WCAG 2.2 の最小ターゲットは 24×24 CSS px。
- 0h h1 は 4×4〜12×12、Mr. Binairo は 6×6〜12×12 を利用者がサイズとして選ぶ。LinkedIn の Tango は 6×6 固定。

### 10.2 判断: 全難易度で 8×8 固定

- 盤面サイズを難易度帯に対応させない。大きい盤面は手数と探す範囲が増えるだけで、`難易度.md` が退ける「複雑さによる難しさ」になりやすい。
- 8×8 は、スマホ縦画面で盤面全体を横スクロールなしに見渡しながら 44px 前後のセルを確保できる最大のサイズ。
- 6×6 は1行の合法パターンが 14 通りしかなく、行全体を読む推論（§11.3 の C・D）が現れる余地が小さいと見込む（§15 で確認）。
- 10×10 は 35px 前後のセルになり、誤タップの負担が増える。
- 8×8 で5段階の挑戦差を作れるかは §15 の実測で見込みを確かめ、難易度段階で確定させる。作れない場合でも、先に手筋の分析と供給方法を見直し、サイズを変えるのは最後の手段とする（`難易度開発手順.md` 工程 11）。
- サイズ選択をゲーム固有の開始条件（`SPEC-004`）として加えることは、初期実装では行わない。

## 11. 難易度

### 11.1 タクズ固有の挑戦（仮説）

> 盤面から次に確定できるマスを見つけ出し、局所の形で決まらないときは、行・列全体の残り個数や完成済みの行・列との比較まで読んで確定させること。

これを強めると考える要因:

1. **必要な手筋の深さ**: 隣接の形だけで決まるか、行の残り個数を使う必要があるか、完成済みの行との比較まで要るか。
2. **見つけにくさ**: 各局面で確定できるマスがいくつあるか。少ないほど、盤面を見渡して手がかりを探す負担が大きい。
3. **深い手筋が要る局面の多さ**: 深い手筋を1回だけ使えば後は流れるのか、何度も要るのか。

挑戦にしないもの（`難易度.md`「挑戦ではない負担」）:

- 盤面サイズ（8×8 固定）。
- 空きマスの数そのもの（作業量）。
- タップ回数・所要時間そのもの。
- 2値の見分けにくさ・セルの押しにくさ（UIで除く）。

### 11.2 問題難易度の基準とするプレイ条件（判断）

- ルールと、タップ巡回の操作を理解している。
- ヒント・自動補助・個数表示は存在しない（提供しない）。
- ルール違反の印（§7.3）は表示されるが、それに頼らずに盤面を読んで確定マスを置くプレイを基準にする。
- 仮置きと後戻りは使わない。

### 11.3 人間向け解法器の手筋段階（仮説）

解法器は、各局面で最も弱い手筋から順に確定できるマスを探し、見つかった段階の手筋で確定するマスをまとめて置く（1ラウンド）。これを全マスが埋まるまで繰り返し、使わざるを得なかった手筋の段階と回数、各ラウンドで確定できたマスの数を記録する。

| 記号 | 手筋 | 内容 |
| --- | --- | --- |
| A | 隣接・挟み | `AA_` / `_AA` / `A_A` の空きマスは反対の値。 |
| B | 個数の完成 | 行（列）に A が n/2 個あれば、残りの空きマスはすべて B。 |
| C | 残り1個 | 行（列）に置ける A（または B）が残り1個のとき、その1個をどこに置くと3連続や個数違反になるかを読み、確定するマスを決める。解法器上は「残り個数の少ない方が1個の行・列」について、ルールを満たす並びを列挙した共通部分で表す。 |
| D | 重複の回避 | 完成済みの行（列）と同じ並びになる置き方を除くと確定するマスを決める。 |
| E | 一般の行候補 | 残り個数が両方2個以上の行（列）で、ルールを満たす並びを列挙した共通部分から確定する。 |
| ― | 2本以上の行・列の組み合わせ | 解法器は扱わない。これが要る問題は **評価不能** とし、提供しない。 |

- A・B は盤面の小さな形を見れば分かる手筋、C・D・E は行・列全体を読む手筋と考える。
- 手筋 C は人間向けの説明で「残り1個をどこに置けるか」と言い換えられる。E は同じ列挙を一般の場合へ広げたもので、人間には説明しにくいと推測する。
- 段階の順序（D と E のどちらを深いとみなすか）は仮置き。§15 の実測では A → B → C → E → D の順に試した。§15 の実測では、8×8 の問題で E が最も深い手筋になる問題はほとんど現れなかった。

### 11.4 特徴量の候補（仮説）

| 特徴量 | 表すと考える挑戦 | 扱い |
| --- | --- | --- |
| 最も深い手筋の段階 | 必要な推論の深さ | 分類の主軸 |
| 深い手筋（C 以上）が要るラウンド数 | 深い推論を繰り返す必要 | 主軸の補助 |
| 手筋 D が要るラウンド数 | 重複回避を読む必要 | 上位レベルの区別 |
| 1ラウンドあたりの確定可能マス数の平均・最小 | 見つけやすさ | 同じ手筋段階内の区別（特に下位レベル） |
| ラウンド数 | 連鎖の長さ | 補助。単独では難易度の根拠にしない |
| 初期配置の数 | 生成条件 | 候補領域の調整にだけ使い、難易度の根拠にしない |

### 11.5 レベル1〜5の定義案（仮説）

| レベル | 分類条件（仮） | 利用者向けの挑戦の説明（案） |
| --- | --- | --- |
| 1 | A だけで解け、各ラウンドで確定できるマスが多い | 並んだ2つ・挟まれた1つを見つければ次々に決まる |
| 2 | A・B で解けるが、確定できるマスが少ない局面がある | 行の個数を数えて埋める場面があり、次の一手を探す必要がある |
| 3 | C が要る | 行の残り1個をどこに置けるかを読む場面がある |
| 4 | D が要る（1〜2回程度） | 完成した行と同じ並びにならないよう読む場面がある |
| 5 | D を何度も要する、または C・D が連続して要る | 行全体を読む推論を何度も重ねないと進めない |

- 境界は内部値の等分ではなく、各段階で「新しい種類の読み」が加わるように置く仮説。§15 の実測で、8×8 の最小に近い初期配置の問題に A だけ・A〜B・A〜C・A〜D の各段階が現れることを確認した。
- レベル1とレベル2の差（見つけやすさ）と、レベル4とレベル5の差（深い手筋の回数）が、実プレイで意味のある差になるかが最大の不確実性。難易度段階で代表・境界の問題を実際に解いて確かめる（`難易度開発手順.md` 工程 8〜9）。
- 各レベルは、同じ「確定マスを見つけて置く」挑戦が段階的に深くなるものとして説明する。

### 11.6 判定の状態（判断）

`難易度判定.md` に従い、少なくとも次を区別する。

- 成立しない: 解が無い、または2つ以上ある。
- 評価不能: 一意解だが、解法器の手筋（A〜E）だけでは完答できない。
- 提供範囲外: 分析できるが、レベル1〜5のどの条件にも入らない（例: 初期配置が多すぎて挑戦がほぼ無い）。
- 難易度1〜5: 分析でき、提供範囲に入る。

## 12. 問題供給

### 12.1 判断: 事前生成の問題集

- ウォーターソート・マインスイーパーと同じく、**事前生成した問題集 JSON を同梱** し、実行時は要求された難易度の問題集から seed で1問選ぶ。
  - 実行時生成も性能上は可能と見込まれる（8×8 は1問あたり数十〜数百 ms。§15）。ただし上位レベルの候補は棄却が多く、端末性能によって待ち時間がばらつく。
  - 問題集にすると、配信前に全問の一意性・解法器での完答・レベル分類を確かめられ、同じ seed から同じ問題を再現できる。
- 生成の手順（成立性調査の方式を踏襲）:
  1. 完成盤を seed から1つ作る（行の合法パターンを列挙し、列の制約で枝を刈るバックトラック）。
  2. 全マスを初期配置として始め、seed で決まる順にマスを1つずつ消す。
  3. 消した結果が一意解でなくなるか、許可する手筋で完答できなくなれば戻す。
  4. 消し終えたら解法器で分析し、レベルへ分類する。生成時に許可した手筋でレベルを決めない。
- 同型の重複を除く: 盤面の回転・反転（8通り）と A / B の入れ替え（2通り）の計16通りの変換で得られる表現の最小値を正規形とし、同じ正規形の問題を問題集に2つ入れない。行・列の任意の入れ替えは3連続の制約を壊し得るので同型として扱わない。
- 量の目安: 1レベル 100〜200 問。8×8 の問題は初期配置の文字列（64文字）と解（64文字）程度なので、全体で数百 KB 未満と見込む（推測）。

### 12.2 問題識別情報（判断）

```text
TakuzuProblemIdentity = {
  generatorVersion: "1",
  seed: ProblemSeed,
  conditions: { size: 8 },
}
```

- 同じ identity からは同じ問題を再現する。問題集に初期配置と解を保存し、実行時に生成器を呼ばない。
- 問題集に無い identity（生成器の版が変わった後の古い記録など）は再プレイ不可として扱う。

## 13. プレイ評価

### 13.1 良いプレイの定義（仮説）

> 盤面を読んで確定したマスだけを置き、置き直しをせずに、迷いなく解き切ること。

- 推測不要の問題なので、上手なプレイは「確定させてから置く」ことに表れる。試しに置いて後で直す回数が少ないほど、読みが正確だったと考える。
- 次の確定マスを素早く見つけられるほど、経過時間が短くなる。
- 「解けたかどうか」はクリアとして別に返す（`GAME.md`「達成とプレイの出来を分ける」）。

### 13.2 プレイ事実の候補

| 事実 | 評価に使うか | 理由 |
| --- | --- | --- |
| 経過時間 `elapsedMs` | 使う（速さ） | 次の一手を見つける速さ |
| 置き直し回数 `correctionCount` | 使う（正確さ） | 一度置いた値を別の値や空へ変えた回数。同じマスを続けて押す間は1回の入力とみなし、別のマスを押した時点でそのマスの値を「置いた値」とする。そのマスへ後で戻って値を変えたら1回と数える。解答との照合は使わない |
| やり直し回数 `restartCount` | 使う（正確さ） | 盤面全体を捨てた回数。やり直しで消えたマスは置き直しに数えない |
| 入力回数 `inputCount` | 記録のみ | 巡回入力では B に2回押す必要があり、評価に使うと値の種類で差が付く |
| ルール違反の発生回数 | 記録しない | 巡回途中の一瞬の違反も数えてしまい、操作の揺れと区別できない |
| 固定マスへの入力 | 記録しない | UI摩擦で挑戦ではない |

- 置き直し回数は、押し間違えたマスを後から空へ戻した場合も1回と数える。押し間違いが評価へ混ざる余地は残るが、セルの寸法（§6.2）で頻度を下げ、1回あたりの減点を小さくして影響を抑える（仮説）。

### 13.3 評価規則の方向性（仮説。数値はスコア段階で決める）

- 100点満点を **速さ** と **正確さ** の2観点で配分する（例: 速さ 50 + 正確さ 50）。
- 正確さ: 置き直し0回・やり直し0回で満点。1回ごとに減点し、0点を下回らない。
- 速さ: 問題ごとの基準時間以内で満点、超過に応じて減点。基準時間は、空きマスの数と解法器の分析結果（深い手筋が要るラウンド数など）から問題ごとに決める。
  - 難しい問題ほど基準時間を長くし、**難易度の高さそのものを加点しない**。高いレベルを選んだだけで点が上がる、または下がる規則にしない。
- 自己ベストの比較単位は難易度。スコアは高いほど、経過時間と置き直し回数は少ないほど良い値として比較する。
- 係数は代表的なプレイ例と実プレイで校正する前提の仮置き。評価は保存したプレイ事実から計算し直せる（`SPEC-006`）。

## 14. 記録・再プレイ・診断

- 記録 payload には、難易度、`TakuzuProblemIdentity`、プレイ事実（`elapsedMs`、`correctionCount`、`restartCount`、`inputCount`）を保存する。スコアや段階は保存しない。
- 再プレイは記録の identity から同じ問題を復元する。
- 内部診断では、盤面サイズ、初期配置の数、解法器の分析結果（最も深い手筋、手筋ごとのラウンド数、確定可能マス数）を表示できるようにする。利用者のプレイ画面には出さない。

## 15. 実測

### 15.1 条件

- 環境: Python 3（Linux コンテナ）。スマートフォン実機の性能ではない。一時コードはリポジトリに残していない。後続の難易度段階で、製品コード（TypeScript）の解法器・分析スクリプトとして実装し直し、測り直す。
- 完成盤: 行の合法パターンを列挙し、列の個数・3連続で枝を刈るバックトラック。行・列の重複を検証する。
- 問題化: 完成盤から seed で決まる順にマスを1つずつ消し、一意解（解を2個まで数える完全探索）と、許可した手筋までの解法器での完答を保てる限り消し続けた（初期配置を最小に近づける）。
- 許可する手筋の上限を A / A〜B / A〜C / A〜E / A〜D（D は E の後に試す）の5条件に分け、各条件 40 問（8×8）を作った。
- 解法器は §11.3 の順（A → B → C → E → D）で最も弱い手筋を探し、その手筋で確定するマスをまとめて置く。

### 15.2 結果（8×8、各条件 40 問、計 200 問）

**実際に必要だった最も深い手筋ごとの集計**

| 最も深い手筋 | 問題数 | 初期配置の数（最小 / 中央値 / 最大） | ラウンド数（中央値） | 1ラウンドの確定可能マス数（中央値） | C 以上が要るラウンド数 |
| --- | ---: | --- | ---: | ---: | --- |
| A | 40 | 19 / 22 / 25 | 6 | 6.8 | 0 |
| B | 55 | 13 / 16 / 21 | 16 | 2.9 | 0 |
| C | 66 | 12 / 16 / 18 | 20 | 2.4 | 1〜5（中央値 2） |
| E | 1 | 14 | 23 | 2.2 | 2 |
| D | 38 | 11 / 13.5 / 16 | 22 | 2.3 | 2〜9（中央値 4） |

**許可した手筋の上限ごとの生成時間**（1問あたり、完成盤生成・消去・一意性確認・解法器を含む）

| 上限 | 中央値 | 最大 |
| --- | ---: | ---: |
| A | 19 ms | 28 ms |
| A〜B | 63 ms | 802 ms |
| A〜C | 84 ms | 477 ms |
| A〜E | 92 ms | 458 ms |
| A〜E + D | 134 ms | 693 ms |

§15.3 に 6×6・10×10 の比較を載せる。

### 15.3 盤面サイズの比較

同じ方法で 6×6（各条件 40 問）と 10×10（各条件 12 問）も作った。

| サイズ | 最も深い手筋ごとの問題数 | C 以上が要るラウンド数（最小〜最大） | 1ラウンドの確定可能マス数（A のみ / それ以外の中央値） | 生成時間（最上位条件の中央値 / 最大） |
| --- | --- | --- | --- | --- |
| 6×6 | A 40、B 93、C 28、E 0、D 39 | C: 1〜2、D: 1〜6 | 4.8 / 2.1〜2.5 | 17 ms / 31 ms |
| 8×8 | A 40、B 55、C 66、E 1、D 38 | C: 1〜5、D: 2〜9 | 6.8 / 2.3〜2.9 | 134 ms / 693 ms |
| 10×10 | A 12、B 13、C 17、E 7、D 11 | C: 1〜7、E: 5〜9、D: 2〜13 | 9.5 / 2.4〜3.4 | 2,057 ms / 26,664 ms |

- 6×6 では、C を許しても 40 問中 23 問が B までで解ける問題になり、C が要る問題の C 以上のラウンドは1〜2回にとどまった。行全体を読む推論の現れ方が浅い。
- 10×10 では E が要る問題も現れ、深い手筋のラウンド数の幅が広がる。一方でラウンド数（連鎖の長さ）と生成時間が大きく増える。

### 15.4 読み取れること

- 事実: 8×8 で、最も深い手筋が A・B・C・D の各段階になる問題を、許可する手筋を変えるだけで作り分けられた。手筋 D（重複回避）を許すと、40 問中 38 問で D が要る問題になった。
- 事実: 手筋 E（残り個数が両方2個以上の行の一般列挙）が最も深い手筋になる問題は 200 問中1問だけだった。8×8 では、C が使えない局面の多くで D も同時に要るか、C で先に進めると推測する。
- 事実: 同じ最も深い手筋の中でも、C 以上が要るラウンド数は C で 1〜5、D で 2〜9 とばらつく。レベル4とレベル5を回数で分ける余地がある。
- 事実: A だけで解ける問題は1ラウンドの確定可能マス数が多く（中央値 6.8）、B が要る問題は少ない（2.9）。レベル1とレベル2を見つけやすさで分ける余地がある。
- 事実: 初期配置の数は深い手筋ほど少ない傾向があるが、範囲は重なる（B と C はともに中央値 16）。初期配置の数だけでは段階が決まらない。
- 推測: 8×8 固定で5段階の候補は作れる見込みがある。ただし、これは解法器上の段階が分かれることの確認で、人間の体験として5段階の差があることの確認ではない。
- 事実: 8×8 の生成は、上位の条件でも1問あたり最大1秒未満だった。1レベル 200 問の事前生成は数分で終わる見込み。
- 推測（§15.3）: 6×6 は行全体を読む推論の回数に幅が無く、レベル3〜5 を分けにくい。10×10 は手筋の幅が広がるが、連鎖の長さ（作業量）も一緒に増え、スマホでのセル寸法も小さくなる。8×8 固定（§10.2）は、手筋の段階が一通り現れる最小のサイズとして妥当と見込む。

### 15.5 限界

- 標本数が少ない（条件ごとに 40 問）。
- 初期配置を最小に近づける生成だけを試した。レベル1〜2 向けに初期配置を多めに残した問題の分布は見ていない。
- 人間の実プレイとの照合はしていない。
- 手筋 C の実装は「残り個数の少ない方が1個の行の列挙」で、人間が実際にこの形で読むかは未確認。

| 導入判断 | `条件付き保留`。5段階の難易度提供と人間レビューを経て正式採用を判断する | §17 | 5段階の供給と代表問題の試遊で破綻が無いと確認できた |

## 17. 成立性ゲートと導入判断

`docs/棚上げ/README.md` のパズル候補の段階（問題供給・難易度運用・スマホプレイ・導入判断）ごとに、この調査の時点の状態を整理する。

| ゲート | 状態 | 根拠 | 残っていること |
| --- | --- | --- | --- |
| 問題供給 | 通過 | 一意解・推測不要の 8×8 問題を1問あたり1秒未満で作れた（§15）。同型の正規化で重複を除ける（§12.1） | 製品コードでの再実装と問題集の生成 |
| 難易度運用 | 確認中 | 解法器の手筋段階で、8×8 の問題に A・B・C・D の各段階が現れ、同じ段階の中でも回数・見つけやすさがばらつく（§15）。5段階の仮説を立てた（§11.5） | 5段階の分類・供給の実装と、代表・境界問題の試遊 |
| スマホプレイ | 確認中 | 8×8 は 390px 幅で 44px 前後のセル（成立性調査の実測）。タップ巡回だけで操作が完結し、スクロールと競合しない（§6） | 実際のプレイUIでの誤タップ・視認性の確認 |
| 導入判断 | 条件付き保留 | 問題供給は通過したが、難易度運用とスマホプレイが確認中。体験価値は、局所の形からの連鎖と行全体を読む推論を面白さの核とする仮説（§2.2）で、ナンプレ（9択の候補消去）と違い2値を形として読むので判断が速く連鎖しやすいと見込む | 5段階の供給、プレイUIでの確認、人間の試遊による体験価値の確認 |

成立性調査は「4ゲート通過・実装候補」としたが、難易度運用は3段階を前提にした判断だった。現在の採用条件（5段階）では確認中に戻るため、導入判断は `条件付き保留` とする。残る確認は実際に遊べる盤面と問題集が要るので、プレイ・難易度・問題集の実装を進め、その上で人間が確認する。パズル候補台帳（`PUZZLE-007`、`パズル候補.csv`）は、実装の結果に合わせて正本化の段階で更新する。

## 18. 後続へ残すこと

- タイル・固定マスの印・違反の印・印の遅れ（§9.1 で決めた）が、人間の実プレイで見やすいかの確認。
- 人間向け解法器の製品実装と、5段階の分類条件・境界の決定、代表・境界・異常な問題の抽出と試遊（難易度段階）。
- レベル1〜2 向けに初期配置を多めに残した問題の分布確認（難易度段階・問題集段階）。
- スコアの係数と基準時間の校正（スコア段階）。
- 「タクズ」の名称・URL の権利確認（必要になった場合）。
- 元に戻す・個数表示・ドラッグ入力の追加要否（UIレビューの結果次第）。
