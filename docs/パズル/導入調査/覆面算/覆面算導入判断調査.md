## 仮決定の候補

- 別ゲームとして作るか: 推奨は独立ゲーム `fukumenzan` / 理由: (1) 実装済みの11ゲームにも未実装の候補にも統合先が無い。(2) いちばん近い数式穴埋めとは、推理の核（文字の同一性と「違う文字は違う数字」）が違う（計測: 外すと解が 1 → 数千〜数千万通り）。(3) ナンプレとは、決めるもの・手がかり・途中の知らせが違う。合意も別ゲーム / 比べた案: 数式穴埋め・虫食い算と1つのゲームにする（どちらも未実装で、手がかりの種類が違う） / 覆したときに作り直す範囲: 統合するなら `frontend/src/games/fukumenzan/` 全体・カタログ・ルート
- 表示名: 推奨は合意どおり「覆面算」で実装し、`display-name.ts` の1か所から参照する / 理由: ジャンル名そのもので GAME-001 に合う。ニコリの登録一覧に無い。詰将棋と同じく伝統名を使う前例がある。ゲーム ID と読みが揃う / 比べた案: 「文字算」（ジャンル名として通じにくい）、「アルファメティック」（なじみが薄い） / 覆したときに作り直す範囲: `display-name.ts` の定数1つと、表示名を書いた仕様・遊び方・調査の文書。ゲーム ID・ルート・記録はそのまま
- 名前の確かめ方: 推奨は「公開前に人間が J-PlatPat で『覆面算』と称呼『フクメンザン』を第9・28・41類で確かめる」を最終レビューの確認に入れる / 理由: この環境では J-PlatPat を引けない。前例（詰将棋・箱入り娘・ブリッジパズル）と同じ扱い / 比べた案: 調査で確かめたことにする（できない） / 覆したときに作り直す範囲: 登録が見つかったら表示名だけを変える（代わりの名前の比較は上の代替候補から人間が決める）
- 台帳の導入判断の置き場所: 推奨は CSV に列を足さず、`詳細/PUZZLE-014.md` の「## 導入判断」の節に書く（箱入り娘と同じ） / 理由: (1) CSV には 2026-11-08 から `導入判断` の列が無く、README は現在状態を管理しないとしている。(2) 候補ファイルの導入判断は「調査当時の結論」として README が認めている。(3) 直近の前例と揃う / 比べた案: CSV に `導入判断` の列を戻す（README の整理を覆す。全候補の値が要る）、導入判断をどこにも書かない（build-order.md の spec 行と食い違う） / 覆したときに作り直す範囲: 候補ファイルの1節。なお build-order.md の spec 行と README の食い違い自体は、このパズルの範囲の外で扱いを決める（Skill を直すなら別の変更）
- 台帳の更新の仕方: 推奨は台帳（CSV の1行・候補ファイル・カタログの見出し）に docs 層で最終の値を一度だけ書き、途中の状態は実装前提調査の「成立性」に持つ / 理由: 台帳は最後の層に入るので、途中の値を書いても main に届かない。二重管理を避ける（ブリッジパズルの前例） / 比べた案: research 層で途中の値を書き、層ごとに直す / 覆したときに作り直す範囲: 台帳の1行と候補ファイル
