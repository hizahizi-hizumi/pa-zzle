# 覆面算スマホ操作調査

調査日: 2026-11-22。導入調査であり、今の決まりの正本ではない。仮決定は [覆面算実装前提調査](覆面算実装前提調査.md) の仮決定一覧を正とする。

## 結論

- **認識合わせで見せた「式＋文字×数字の表」は、短いスマホ画面で一画面に収まらない**（合意した前提ではなく、確定していない UI の形の話。人間の「これがベストではない」を計測で裏づけた）。
  - 表のマスを幅で決めると、375px で 30.4px、320px で 24.9px になる。既存の最小（リフレクション 10×10、マインスイーパー 12列の 25〜30px）並みで、押し分けの大きさは足りる。
  - 収まらないのは高さ。375×548（iPhone SE の Safari を推測した高さ）では、6文字の L1 でも式に 85px しか残らず、式のタイルが 23.5px になる。10文字の L5 では表だけで画面を 41px はみ出す。
  - 式のタイルを 32px に保つと、表のマスは 11.7px まで縮む（σ4px の手ぶれで命中率 73%）。
  - プレイ画面の外枠は `overflow-hidden` なので、収まらない分はスクロールで見るのではなく、切れて見えなくなる。
  - 代案として、**式の文字に、0〜9 の札を1枚ずつ運んで入れる形（C 札）** を推奨する。× は「文字を選んで札を軽く押す」で付ける。
- **スマホ縦画面の最小幅でのマスの大きさ**: C 札（B 鍵盤も同じ寸法）なら成り立つ。
  - 式の文字のタイルは、L5 の見本（5桁×3つ＝6桁）で 375×548 なら 49.8px、320×460 なら 40.5px。ナンプレのマス（同じ端末で 39.1px / 29.3px）より大きい。
  - 札（鍵盤）を1段に10個並べると、1つが 31.5×56px（375px）、26.0×56px（320px）。ナンプレの数字ボタン（9個、35.4×56px / 29.3×56px）よりやや細い。
- **盤面と全操作が一画面に収まる上限**: 条件つきで成り立つ。C 札・B 鍵盤の形で、6つの端末すべてで式のタイルが 34px 以上になる上限は「足す数3つまで、答え7桁まで」。文字は 10 個まで（数字の数で決まる）。
  - 足す数4つは 320×460 で 31.6px、5つは 26px に縮む。
  - 答え8桁は、320px では高さに依らず 29.5px になる。
- **合意した推理（× で候補を消し、決まってから入れる）の自然さ**: C 札がいちばん合う。
  - × は「文字を選んで札を軽く押す」、入れるは「札を文字へ運ぶ」。2つの操作の手つきがはっきり違い、決めて入れる手が重くなる。
  - 使った札は列から文字へ移るので、「違う文字は違う数字」が札の数で目に見える。
  - × を全部書く人で、L5 の操作数の中央値は 88回（表 A は 110回、ナンプレ型の B 鍵盤は 103回）。× を書かず入れるだけの人は 10回（B 鍵盤は 20回）。
- **表（A）の ◯→×→空白 の順の問題**: 成り立たない。× を付けるたびに、途中で ◯ を通る。
  - L5 の中央値で 1問 50回、式の文字に数字が一瞬入り、使い回しの赤が点きうる。
  - 表を残すなら、×→◯→空白 の順にする（A'）。
- **操作とスクロールの競合**: 前例どおりにすれば成り立つ。
  - プレイ画面の外枠は `fixed inset-0 overflow-hidden` で、ページ自体はスクロールしない。
  - 札を運ぶ操作は、ブリッジの盤面と同じく `touch-none` と Pointer Events で受ける。
  - × を書くときは、同じ文字のまま隣の札を素早く続けて押す。iOS Safari のダブルタップの click の送り先の問題が出る形なので、`useTouchTap`（pointerup で受ける）を使う。

## 事実と推測

- [事実] 対応する最小幅は 320px（`frontend/src/index.css` の `min-w-[320px]`）。
- [事実] プレイ画面の外枠は `fixed inset-0 ... overflow-hidden` で、縦は次の3つで決まる（`frontend/src/components/GamePlayFrame.tsx`、`BrandIdentityHeader.tsx`、`PlayHeader.tsx`、`BrowserBottomSurface.tsx`）。合計 112px。
  - ブランドの帯 `h-[calc(1.75rem+env(safe-area-inset-top))]`
  - 見出し `h-[4.5rem]`
  - 下端の面 `h-3`
- [事実] `frontend/index.html` の viewport は、今は `viewport-fit=cover` を含む。ブリッジ調査の時点（「無い」と書いた）から変わっている。縦画面の Safari で safe-area が 0 になるかは、実機で確かめていない。
- [事実] ブリッジ調査のマスの値は、下端の面 12px を引いていない。この調査の既存ゲームの値は、12px を引いて計算し直した（`docs/パズル/導入調査/橋をかけろ/調査コード/bridges_mobile.py` と比べて、高さで決まる値だけが小さい）。
- [事実] ナンプレの入力欄は `NanpureInputPanel` で、次のとおり（`frontend/src/games/nanpure/ui/NanpurePlay/NanpureInputPanel.tsx`、`ui/play/NanpureDigitPad.tsx`、`ui/play/PlayActionButton.tsx`）。
  - 操作の段は `min-h-16` に、待った・消す・メモの3つ。
  - 数字の段は `grid-cols-9 gap-x-1`、`h-14`。
  - メモは切り替え（`notesMode`）で入れる。
  - メモの数字は `text-[clamp(0.58rem,2.4vw,0.9rem)]`（375px で約 9px）で、マスの中に 3×3 で描く（`ui/board/NanpureCellNotes.tsx`）。
- [事実] ナンプレの数字ボタンとマスは `onClick` で受けている（`NanpureDigitPad.tsx`、`NanpureCell.tsx`）。iOS Safari は近くを続けて押すと、2回目の click を1回目の位置へ送る（`frontend/src/components/touch-tap.ts` のコメント）。`useTouchTap` は pointerup で受けて、これを避ける。
- [事実] 札を運ぶ（なぞる）操作の前例はブリッジと一筆パズル。盤面に `touch-none` を付け、Pointer Events で受ける（`frontend/src/games/bridges/ui/board/BridgesBoard.tsx`、`docs/パズル/導入調査/橋をかけろ/橋をかけろスマホ操作調査.md`）。
- [事実] 認識合わせの見本の表は、空白→◯→×→空白 の順で回る（認識合わせのページのスクリプトの `next = (marks[c][d] + 1) % 3; if (marks[c][d] === 0) next = 1;`）。◯ を付けると、式の文字がその数字になる。そのため、× にする途中で必ず ◯ を通る。
- [事実] 見本ページの「375px で表の1マスは約31px」は、罫線を含めたこの調査の計算 30.4px と合う。ただしこの値は、表を画面の高さに収める前提で出したものではない（見本ページはスクロールするページの中に置いている）。
- [事実] GAME.md は「何を見て何を動かすゲームか（題材）が、盤面の姿と操作から分かるようにする。内部のデータ構造をそのまま描かない」と、「一つのゲームで成り立った見た目・実装を別のゲームへそのまま当てはめない」を求めている。
- [推測] 文字×数字の表は、解く対象（式）とは別の「対応表」というデータ構造で、触る所と考える所が上下に分かれる。C 札は、触るのも式の文字で、手元の札が「0〜9 を1枚ずつ配る」という覆面算の約束そのものになる。GAME.md の題材の項に、より合うと見る。遊ぶ人の試遊で確かめられる。
- [推測] B 鍵盤はナンプレの入力欄をそのまま当てはめた形に近く、GAME.md の「やらないこと」に触れやすい。寸法は C と同じなので、差は手つきと見た目だけになる。
- [推測] 表の強みは、全部の文字の候補を一度に見られること。計測では、10文字の問題の約半数で「この数字が入りうる文字は1つだけ」を1〜3回使う。C 札では、この推理のために文字を1つずつ選んで見て回ることになる。
  - 補う案: 札を押さえている間、その札に × を付けていない文字を光らせる。プレイヤー自身のメモから出す表示なので、正解を先回りして示すことにはならない。
  - play-ui の試作で、遊ぶ人に確かめる。
- [推測] 推理の近似（桁ごとの足し算を、組み合わせを全部試して絞る）は人より強い。人はもっと少ない × で、もっと多く場合分けをする。操作数の値は「× を全部書く人」の上限の目安で、入力の形どうしの比べ方（同じ記録を各形に直す）は変わらない。
- [推測] 端末の高さ（390×664、375×548、360×640、320×460）は、ツールバーを出したブラウザの表示領域の目安。ブリッジ調査と同じ値を使い、実機では測っていない。

## 仮決定の候補

- **入力の形**
  - 推奨: C 札。式を盤面とし、その下に 0〜9 の札を1段に並べる。
    - 入れる: 札を式の文字へ運ぶ（その文字の全部の場所に入る）。
    - × を付ける: 式の文字を押して選び、札を軽く押す（選んだ文字について、その札に × が付く）。
    - 使った札は列から抜け、入れた文字の上にある。別の文字へ運び直せる。
  - 理由:
    - 一画面に収まる。L5 で、375×548 なら式のタイル 49.8px、320×460 なら 40.5px。
    - 押す所が既存並みか、それ以上。札は 31.5×56px（375px）で、σ8 でも 95% 当たる。
    - 操作数が少ない。× を書く人で L5 88回（A 110、B 103）、入れるだけの人で 10回（B 20）。
    - × と入れるの手つきが分かれ、切り替えのボタンが要らない。決めて入れる手（運ぶ）が、軽い × の手より重い。
    - 「違う文字は違う数字」が、札の残りで目に見える。
  - 比べた案:
    - A 表: 押し分けの大きさは足りる。10文字では短い画面に収まらず、× の途中で ◯ を通る。
    - A' 表（×→◯→空白）: 操作数は少ない（L5 70回）。収まらないのは同じ。
    - B 鍵盤＋メモの切り替え（ナンプレ型）: 収まる。切り替えの手間で操作が増え（L5 103回、入れるだけで 20回）、ナンプレの当てはめに近い。
    - B' 鍵盤の長押しで入れる: 隠れた手つきで、遊び方での説明が要る。iOS の長押しメニューを止める必要もある。
    - D 式に表を重ねる: 候補が 9×16px で、σ4 でも 72% しか当たらない。
    - E 文字を押すと、その場に 0〜9 の候補を出す: 測っていない。式の上に重なって、繰り上がりを読む桁が隠れる。
  - 覆したときに作り直す範囲: 盤面の下の入力欄と、入力の操作の型（session の操作）。式の描画は共通にできる。

- **式の大きさの上限**
  - 推奨: 足す数は3つまで、答えは7桁まで、文字は10個まで。
  - 理由: 6つの端末すべてで、式のタイルが 34px 以上になる。ナンプレのマスの最小（320×460 で 29.3px）を下回らない。
  - 比べた案:
    - 足す数4つ: 320×460 で 31.6px。リフレクション（22.7px）よりは大きいので、難易度が要るなら条件つきで入れられる。
    - 答え8桁: 320px 幅で 29.5px。
  - 覆したときに作り直す範囲: 難易度の式の形の定義と問題集。

- **候補（×）の見せ方**
  - 推奨: 選んだ文字の × は札の上に描く。式の文字のタイルには、決まった数字か文字だけを描く。
  - 理由:
    - 式のタイルの中に 2×5 の候補を描くと、L5・320px で1つ 7.3px になり、ナンプレのメモ（約 9px）より小さい。
    - 札の上なら 26〜33px の幅に描ける。
  - 比べた案: タイルに残りの候補の数だけを小さく出す。表の「全体を見渡せる」強みを少し補える。play-ui で見て決める。
  - 覆したときに作り直す範囲: 盤面と札の描画だけ。

- **表を残す場合の回し方**
  - 推奨: 空白→×→◯→空白。
  - 理由: × のたびに ◯ を通る（L5 で1問 50回）のをなくせる。× を書く人の操作は L5 で 110回から 70回に減る。
  - 比べた案: 認識合わせの見本の ◯→×→空白。
  - 覆したときに作り直す範囲: 盤面の入力の関数だけ。

- **タッチの受け方**
  - 推奨: 次の3つ。
    - 札と式の文字は `useTouchTap`（pointerup）で受ける。
    - 札を運ぶ操作は、ブリッジと同じく `touch-none select-none [-webkit-touch-callout:none]` と Pointer Events で受ける。動いた距離のしきい値で、押す（×）と運ぶ（入れる）を分ける。
    - 指で札が隠れるので、運んでいる札は指より上に描く。
  - 理由: × を続けて書くとき、隣の札を素早く押す。iOS のダブルタップの click の送り先の問題が出る形。
  - 比べた案: ナンプレと同じ `onClick`。隣の札の連打で取り違えうる（推測。実機では確かめていない）。
  - 覆したときに作り直す範囲: 入力層だけ。

## 確かめていないこと

- **実機（iOS Safari・Android Chrome）での表示の高さ・押し分け・連打の取りこぼし**: ブラウザを使っていない（計算と解析的な模擬だけ）。play-ui で Playwright のタッチ操作と、最終レビューの「遊ぶ」で確かめる。
- **札を運ぶ操作の速さ・誤り（押すつもりが運ぶになる、またはその逆）と、しきい値の値**: 模擬していない。試作で測る。
- **人が実際に書く × の数と順番**: 推理の近似は人より強く、書く順も推理の順か、文字ごとにまとめた順の2つで仮に置いた。試遊の記録で確かめる。
- **C 札で、文字をまたぐ推理（この数字が入りうる文字は1つだけ）がどれだけ手間になるか、札を押さえて文字を光らせる案が要るか**: 遊ぶ人の判断が要る。play-ui の試作で確かめる。
- **4+4+4=5（9文字）など、ほかの形の操作数**: ランダムな数から、ちょうど9文字の一意解が打ち切りの時間内に出なかった。配置の大きさ（`layout`）は測ってある。
- **問題の母集団**: ランダムに作った一意解の問題で、本番の問題集（難易度で選んだもの）ではない。L5 の見本の形では、場合分け1段で解けたのは 15/30 問だった。操作数は解けた問題だけで数えた。
- **viewport-fit=cover で、縦画面の safe-area が 0 になるか**: 実機を使えない。0 でなければ、上下の余白の分だけ式のタイルが縮む。
- **意味のない文字の読みやすさ**: この資料の生成では、札と紛れやすい I・O・Q・V を仮に外した。使う文字は実装前提調査の D-03 で、難易度の生成器と同じ21文字（I・O・Q・S・Z を除く）に決めた。V が札と紛れないかは play-ui の画面で確かめる。
