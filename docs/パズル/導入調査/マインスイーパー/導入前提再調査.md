# マインスイーパー導入前提 再調査

Issue #339 の調査結果。

## 目的

旧調査の結論を現在仕様として引き継がず、現在の pa-zzle のゲーム体験・問題・難易度・成績の契約と、現在利用できる外部知見から、マインスイーパー実装の前提を再導出する。

この文書は導入調査であり、現在仕様の正本ではない。後続実装・検証で採用した契約だけを `docs/プロダクト/` 配下の現在仕様へ反映する。

## 結論

マインスイーパーは引き続き実装候補として進める。

ただし、旧調査の実装前提をそのまま採用しない。プレイ画面へ進む時点では次を採用候補の基準とする。

- pa-zzle では **推測不要の問題を通常提供の前提** とする。
- 通常プレイは、問題に含まれる初期開示領域がすでに開いた状態から開始する。
  - 利用者の最初のタップを問題生成条件にしない。
  - 問題を再プレイしたとき、同じ問題・同じ開始状態を再現できることを優先する。
- 旗は利用者のメモであり、置いた時点で正誤を判定しない。
- クリア条件は全非地雷マスの開示とし、全地雷への旗付けは要求しない。
- 開示済み数字の周囲に数字と同数の旗がある場合、周囲の未開示・未旗マスを一括開示する chord を基本操作に含める。
  - 誤った旗が含まれていれば通常どおり地雷を開いて失敗し得る。
- 地雷マスの開示を失敗とし、通常プレイに死亡後の Undo / 復活は入れない。
- スマートフォンでは、タップ開示と旗操作を区別できる明示的な入力方法を持つ。
  - `開示 / 旗` のモード切替を基本候補とする。
  - 長押しによる旗の付け外しは補助入力として併用候補にする。
  - 最終的な操作感は #340 の実ブラウザレビューで確定する。
- 盤面全体の総地雷数は利用者が使える問題情報として扱う。
- #340 の画面レビュー用盤面は 9×9 を使用してよいが、**9×9を製品の提供範囲として確定したとはみなさない**。
- 製品で提供する盤面規模、地雷数、5段階難易度、問題生成方式、難易度分析モデルは #342 で改めて成立させる。

旧調査の生成性能・難易度実験は歴史的な観測結果として残すが、現行の採用根拠にはしない。旧実験の一時コードはリポジトリに残っておらず、現在の条件で再現可能な証拠になっていないため、#342 で再実装・再測定する。

## 1. 現在の pa-zzle から導かれる条件

### 1.1 マインスイーパーで守るべきゲーム体験

`GAME.md` と現在の要件から、マインスイーパーでは少なくとも次を守る。

- 利用者が見るべき主対象は盤面である。
- 数字から地雷・安全マスを判断する部分を通常UIが先回りしない。
- UI操作の迷い、誤入力しやすさ、極端に小さいセル等を問題の難しさへ混ぜない。
- 難易度は盤面サイズ・地雷数・操作量そのものではなく、マインスイーパー固有の挑戦強度として扱う。
- 問題は繰り返し供給でき、同じ問題の再プレイ時には同じ問題を再現できる。
- クリアという達成と、プレイの出来の評価は分ける。

このため、古典的なルールを忠実に再現すること自体より、数字と未開示領域から自分で確定手を見つける体験を安定して提供できることを優先する。

### 1.2 問題・セッション境界

現在の `SPEC-003` では、問題とプレイセッションを別概念としている。

旧調査では「最初のタップを受け取ってから盤面を生成し、問題識別に初手座標を含める」案を採っていた。これは通常のマインスイーパーらしい自由な初手を残せる一方、最初の操作まで問題が確定しない。

今回の基準案では、問題に次を含める方向へ変更する。

- 地雷配置を再現する情報
- 総地雷数
- 初期開示状態、またはそれを再現する開始位置
- 問題生成規則の版など、再現に必要な情報

セッションは初期開示領域が見えている状態から開始する。

この方式なら、最初のクリックというゲーム性の薄い選択を省き、開始直後から数字を読む判断へ入れる。同一問題の再プレイ、問題難易度の再現、プレイ履歴の再現も単純になる。

実際の問題identityの型・生成タイミング・保存形式は #342 で確定する。

## 2. 基本ルールの再確認

Simon Tatham の `Mines`、Minesweeper Online、現在のモバイル実装を比較しても、ゲーム核は概ね一致している。

### 採用候補

- 正方格子を使う。
- 各マスは地雷または非地雷。
- 開示された非地雷マスは、周囲8マスの地雷数 `0..8` を示す。
- 地雷数0のマスを開いた場合は、連続する0領域とその境界を自動開示する。
- 未開示マスへ旗を付けたり外したりできる。
- 旗付きマスは通常の開示操作では開かない。
- 開示済み数字の周囲に数字と同数の旗があれば chord を実行できる。
- 全非地雷マスを開示するとクリア。
- 地雷を開示すると失敗。

### 旗を正解判定に使わない

旗は真の盤面状態ではなく、利用者が「ここは地雷だ」と判断したメモとして扱う。

したがって次を採用する。

- 誤った旗を置いても、その時点では何も通知しない。
- 正しい旗だけを数える挙動にしない。
- 全地雷に旗を付けることをクリア条件にしない。

これは盤面にない正解情報をUIから漏らさず、旗を使わないプレイも成立させる。

Minesweeper Online でも、勝利条件は非地雷マスをすべて開くことであり、No Flags というプレイ様式が独立して成立している。

### chord を基本操作に含める

chord は数字の周囲の旗数が一致したとき、残りの周囲マスをまとめて開く操作である。

これは新しい正解情報を与える機能ではなく、利用者が個別に行える複数の開示を短縮する入力である。Minesweeper Online では効率的なプレイの中核として扱われ、現在のモバイル実装でも広く提供されている。

そのため #340 の基本操作に含める。

誤った旗を含めて数だけ一致している場合は、安全性をUI側で補正しない。開いた中に地雷があれば失敗する。

## 3. 推測を通常提供へ含めるか

### 通常のマインスイーパーには2つの技能系統がある

現在の実装・コミュニティを見ると、少なくとも次の2系統がある。

1. 数字・総地雷数・既知情報から安全マスや地雷を確定する論理
2. 確定手がない局面で、地雷確率や次に情報が得られる可能性を考えて選ぶ確率判断

Minesweeper Online は通常モードと No Guessing モードを分け、通常モード向けには50/50・確率計算・guessingのガイドがあり、No Guessingにも独立ランキングがある。

2026年のコミュニティ議論でも意見は割れている。

- 推測不要を「運で失うことがなく、論理パズルとして明快」と評価する意見
- 通常モードの確率判断・guessingにも高い技能上限があり、No Guessだけではパターンが限定されやすいとする意見

したがって「推測はマインスイーパーではない」「No Guessが一般に上位」という判断はしない。

### pa-zzle では推測不要を採用する

pa-zzle の通常提供では、確率判断を同じ5段階難易度へ混ぜず、**論理的に確定できる問題を提供範囲とする**。

理由:

- `FR-004` では、問題側の挑戦強度を5段階として再現可能に評価し、継続供給する必要がある。
- 強制的な50/50での死亡は、問題の挑戦強度とは別に結果の運を増やす。
- `FR-005` と `GAME.md` が重視する「自分で考え判断する」体験を、確定可能な論理へ集中させやすい。
- 同じ問題の再プレイ・成績比較で、不可避な運の影響を混ぜずに済む。
- 難易度分析では、必要な人間向け解法過程を明示して5段階へ対応させる必要があるため、評価可能範囲を定義しやすい。

ただし、No Guess化により盤面の多様性や出現パターンが狭くなる可能性は残る。Simon Tatham も、生成規則で盤面を過度に制約すると多様性を失う点を問題視している。コミュニティにもNo Guessを単調と感じる意見がある。

したがって #342 では、推測不要性だけで採用せず、5段階ごとの多様性・反復感も問題供給成立性として検証する。

将来、確率判断を主役にする遊びを提供する場合は、現在の難易度1〜5へ暗黙に混ぜず、別のゲームモード・別契約として検討する。

## 4. 推測不要性の意味

「推測不要」は、単に特定の簡易solverが最後まで進めたこととは同一にしない。

製品上の意味としては、少なくとも次を要求する。

- 利用者に見えている数字
- 利用者が利用可能な総地雷数
- それまで論理的に確定した情報

から、確率に頼らず安全または地雷だと確定できる進行が存在し、最後まで完了できる。

一方、人間が実際にどの手筋としてその確定を発見するかは別問題である。

#342 では次を分けて設計する。

- 問題成立性としての推測不要保証
- 人間の挑戦を近似する難易度分析
- 現在の分析で扱える問題の評価可能範囲
- 実際に通常提供する提供範囲

高度な制約充足でしか確定を証明できない盤面を「推測不要だから難易度5」として自動採用しない。難易度分析が人間の必要な解法過程を説明できない場合は評価不能または提供範囲外として扱う。

## 5. 初手の扱い

### 外部実装

現在の実装では次が混在している。

- 最初の1マスだけ安全
- 最初のマスを0にして周囲も安全
- No Guessモードで指定開始位置を与える
- 最初のクリック後に盤面を生成し、選んだ位置から解ける盤面へする

Simon Tatham の `Mines` は最初のセルを安全にし、選んだ開始地点から推測せず解けることを保証するため、生成判断を最初のクリックまで遅延させている。

Minesweeper Online の No Guessing モードでは開始位置が与えられる。

### pa-zzle の判断

#340 では、**問題が持つ初期開示領域をセッション開始時に表示する**方式を採用候補とする。

利用者に「どこを最初に押すか」を選ばせない。

理由:

- 最初の空の盤面では、どこを押すかに論理的根拠がない。
- 自由な初手を残すためだけに問題確定をセッション開始後へ遅らせる必要がなくなる。
- 同じproblemを同じ開始状態で再現しやすい。
- 難易度分析も同じ開始状態を前提にできる。
- 「初手が運よく広く開いたため簡単だった」という問題条件の差を明示的に問題側へ持てる。

初期開示をどのように生成するか、開始位置をidentityへどう含めるかは #342 で問題供給と合わせて確定する。

## 6. スマートフォン操作

### 外部実装で多い操作

2026年時点のモバイル向け実装では、次の組み合わせが多い。

- タップ: 開示
- 長押し: 旗
- 旗モード: タップを旗操作へ切り替える
- 数字タップ / ダブルタップ / 長押し: chord
- 大盤面ではパン・拡大縮小

タップ開示 + 長押し旗だけの実装もあるが、旗モードを併設する実装も複数確認できる。

### #340 での候補

#340 では次を基本候補として実装・レビューする。

- 通常は開示モード。
- 画面上に現在の `開示 / 旗` モードを常時分かる形で置く。
- 開示モードの未開示マスタップ: 開示。
- 旗モードの未開示マスタップ: 旗の付け外し。
- 未開示マスの長押し: 旗の付け外しを行う補助入力候補。
- 開示モードで開示済み数字をタップ: chordを試行。
- デスクトップでは右クリックによる旗操作も提供候補とする。

モード切替だけ、長押しだけのどちらかへ調査だけで固定せず、両方を触れる状態で実ブラウザレビューし、誤操作・速度・分かりやすさを比較する。

### 操作対象サイズ

Appleのゲーム向けガイドではiPhone/iPadの標準タップ対象として44×44pt、重要度が低い要素でも28ptまでを目安としている。Androidは48dp以上を推奨している。

WebのCSS pxとpt/dpはそのまま同一視しないが、盤面を収めるために操作対象を極端に縮小する設計は避けるべき根拠になる。

したがって次を採用する。

- #340 のレビュー用fixtureは、スマートフォン幅で全体を無理なく見渡せる9×9を使う。
- 盤面を縮小して大盤面を無理に1画面へ収める実装は #340 で作らない。
- パン・ズームが必要な盤面を製品範囲へ含めるかは #342 の提供範囲確定後に判断する。
- 盤面規模を難易度1〜5を埋めるためだけに拡大しない。

9×9採用そのものは確定していない。あくまでプレイ画面をレビューするためのfixtureである。

## 7. プレイ中に利用できる情報

### 総地雷数

総地雷数は隠し情報ではなく、マインスイーパーの問題情報として利用できる状態にする。

Simon Tatham の `Mines` でも、全体の残り地雷数を考える必要がある推論が明示されている。Minesweeper Onlineも残り地雷カウンターを基本UIに持つ。

したがって #340 では、総地雷数・旗数などから利用者が残り地雷数を把握できる表示を持つ候補とする。

具体的に「残り地雷数」と表示するか、「地雷総数」と「旗数」を分けるかは画面レビューで決める。誤旗が存在し得るため、UI上の値が真の未発見地雷数を意味するような表現は避ける。

### タイマー

タイマーはマインスイーパーの既存実装で一般的だが、時間をどの程度プレイ成績へ用いるかは #343 の責務である。

#340 では、タイマーをマインスイーパー固有のゲームルールとして固定しない。既存の共通プレイ体験上必要な経過時間表示がある場合は利用できるが、「速さが成績の中心である」という意味までは持たせない。

## 8. Undo・ヒント・自動補助

### Undo / 復活

通常プレイでは採用しない。

- 地雷を開示した時点でセッション失敗とする。
- 地雷開示後に同一セッションへ復帰するUndo・復活は提供しない。
- 同じ問題を最初からやり直す操作は `SPEC-007` の「やり直す」として別に扱える。

死亡後Undoを採用すると、失敗の意味と後続の成績設計が変わるため、基本プレイの一部として先に入れない。

### ヒント・自動旗

#340 の通常UIでは提供しない。

確定手の提示、自動旗、正解判定付き補助はプレイヤーが考える部分を代行するため、必要になった場合は別の補助機能として目的・成績への影響を定義する。

## 10. #340 へ渡す実装前提

#340 の最初の縦断実装では、問題生成・正式難易度・成績を待たず、固定problem / fixtureで次を実装する。

### problem fixture

- 9×9
- 固定地雷配置
- 固定初期開示領域
- 総地雷数を持つ
- 最後までプレイ可能
- chordを試せる局面を含む
- 誤旗と失敗を確認できる

このfixtureは製品の難易度・盤面規模を表さない。

### session / puzzle

- 開示
- 0領域の連鎖開示
- 旗の付け外し
- chord
- 全非地雷開示によるクリア
- 地雷開示による失敗
- 旗の正誤を開示前に判定しない

### UI

- 初期開示領域が見えた状態から開始
- 未開示 / 開示済み / 数字 / 旗 / 地雷の状態を区別
- 開示 / 旗モード
- 長押し旗を補助入力候補として実装・比較
- 数字タップによるchord
- 総地雷数・旗数等、全体地雷数推論に必要な情報を失わない
- スマートフォン幅で9×9を実操作できる
- パン・ズームは入れない

#340 の実ブラウザレビューで、特に次を確認する。

- モード切替と長押しのどちらが主操作として自然か
- 現在モードを見失わないか
- chordが誤操作を生まないか
- 数字・旗・未開示マスを瞬時に区別できるか
- 盤面セルがスマートフォンで正確に押せるか
- 総地雷数・旗数表示が盤面より目立ちすぎないか
