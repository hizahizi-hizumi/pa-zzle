# 魔方陣供給実験

調べた版: 作業ブランチ `magic-square/work`。難易度は版 4（C2）。候補は `magic_square_difficulty.py` の `generate_candidate` で作り、分類は `classify_v4` と同じ判定（範囲外と分かった所で打ち切る `classify_fast`）で行った。書いたもの:

- 調査コード: `docs/パズル/導入調査/魔方陣/調査コード/magic_square_supply.py`（標準ライブラリだけ。候補の seed は `candidate_seed(n, T, k, i)`、ほかの乱数も seed を固定）
- 移植の期待値: `docs/パズル/導入調査/魔方陣/調査コード/magic_square_supply.expected.json`

数値は研究用 Python 3.13 の実測。時間は1プロセスの CPU 時間（`time.process_time`）で書く。計測の間、同じ 4 コアで難易度の反例探し（A4 の3回目）が走っていたので、壁時計の時間は参考にとどめる。問題集は2通り作った。v0 は規則なし（同じ問題と例の魔方陣だけを除く）、v1 は推奨の規則つき。

## 結論

合意した前提（図鑑はレベルごとに500問、答えは1つ、どのレベルも推理だけで解ける）は、測った範囲で成り立つ。版 4 の分類で各レベル500問を実際に作り切り、採った2,500問は全部、完全な解法器で答えが1つだった。

- **件数（各レベル500問・計2,500問）: 成り立つ。**
  - 合意の値で、毎日1問でも500日かかる。無作為に選ぶ「別の問題」で30回遊んで、重なりは 0.9回（導出）。
  - 推奨の規則つき（v1）で作り切った。研究用 Python の CPU で合計 3,411 秒。94% は候補を作って磨く処理。最も重い L4 は採った1問あたり 6.5 秒、L1・L2 は合わせて 162 秒。
  - TypeScript に型付き配列で移せば約10分の1で、1コアで6分ほどの見込み（推測、氷の床迷路の前例から）。6×6 の数の集合は 37 ビット要り、JavaScript のビット演算（32 ビット）にそのまま乗らない。
- **一意解の割合: 成り立つ。** 調べた候補 11,092 の全部が答え1つだった。読むモデルで解き切れた盤面だけを候補にする作り方なので、構成上そうなる。完全な解法器の200万節点の打ち切りに届いた候補は0で、採った問題の節点は最大 5,374（6×6）。
- **盤面の内訳: 成り立つ。** 2つの盤面を許すレベルは半分ずつにした（L2 は 4×4・5×5、L3〜L5 は 5×5・6×6 を250ずつ）。当たる割合が最も低いのは L4 の 5×5 で、13〜14%。
- **並び: 成り立つ。** レベルの中は、盤面ごとに採った順を保ち、件数の比で均等に混ぜる。問題は無作為に選ぶので、並びは図鑑の番号の見え方にだけ効く。
- **似すぎないか: 条件つきで成り立つ。**
  - 5×5・6×6 は、規則が無くても、同じ問題も答えが同じ問題も0。答えどうしを写して一致するマスは、代表の形が最も近い組でも 12/25（5×5）・10/36（6×6）で、似た魔方陣も出ていない。
  - 4×4 は、答えが回転・裏返しを除くと 880 通りしかない。規則が無いと似た問題が出て、L1 の500問（v0）には次の組があった。
    - 回転・裏返しで同じ答えの組: 134
    - 答えが同じで、与える数が2つ以内しか違わない組: 98
  - 規則を2つ置くと、4×4 の750問（L1 500・L2 250）で両方とも0にできる。費用は L1・L2 の CPU 162 秒（v0 では 99 秒）。
    - 答えが同じ類で、与える数のある所の違いが4以下の問題を採らない。
    - 4×4 の答えは、回転・裏返しで同じものを1度だけ使う。
  - 同型は回転・裏返しの8通りではなく、列の構造の自己同型 G（4×4・5×5 は32、6×6 は192）× 補数でまとめる。
    - 写して分類し直しても、1,440 回ともレベルは変わらなかった。
    - 8通りでは見逃す同じ問題が、L2 の 4×4 に2組あった。
  - L1 は、与える数の置き場所で解く順が決まる。置き場所の類は上限 171 のうち 162 を使い、1つの置き場所に最多9問（1.8%）。上限は置かない。
- **問題集の大きさ: 成り立つ。** 今の実装の形（与える数を `.` でつないだ文字列）で、2,500問 170,026 B（gzip -9 で 39,821 B、1問 68 B）。既存の問題集（29,228〜375,765 B、gzip 3,492〜110,961 B）の範囲に入る。
- **例の魔方陣**: 4×4 は、チュートリアルと遊び方の図がすでに使っている魔方陣にする。5×5 は、問題集の流れが届かない候補番号で作った L3 の候補 `ms5-T2-k0-9009` の答えにする。どちらも G × 補数で移る64通りを問題集から除く（4×4 では 7,040 のうち64）。

## 事実と推測

- 事実: 合意で、図鑑はレベルごとに500問（毎日1問でも1年以上集められ、全部埋める前提にはしない）と、認識合わせのページで示した。人間の返事は「他はOKなので進めて」: 合意ファイルの「認識合わせ」「人間の返事」
- 事実: 集めることは「埋め切ることを課されるノルマではなく、もう1問遊びたくなる理由」であってほしい: `docs/プロダクト/要求/RQ-010-遊んできた問題を自分の跡として集め、次の1問を自分で選びたい.md`
- 事実: 図鑑は今の問題集の全問を1問1枠で載せる。番号は難易度の昇順で、各難易度の中は問題集の並びで、1から付ける。空き枠からも遊べる: `docs/プロダクト/ゲーム/GAME-009-図鑑.md`
- 事実: 次の問題は、乱数の seed のハッシュを問題集の件数で割った余りで選び、直前の問題だけを避ける（最大8回選び直す）: `frontend/src/games/problem-selection.ts`、`frontend/src/games/problem-seed.ts`
- 導出: 上の選び方では、1つのレベルで m 回「別の問題」を選んだときに出会う問題の数の期待値は、件数 ×（1 −（1 − 1/件数）^m）。30回での重なりは、500問なら 0.9回（300問 1.4回、1,000問 0.4回）。100回では 9.3回（同 14.8回・4.8回）

- 事実: 列の構造の自己同型は 4×4・5×5 で32、6×6 で192（導入判断の観点と同じ値）。4×4 の 7,040 通りは G × 補数で166類: `magic_square_supply.py groups`、`魔方陣導入判断調査.md`
- 事実（計測）: 計測の表のとおり。
- 導出: G の元と補数は、列を列へ、列の合計 n(n²+1)/2 を同じ合計へ移す。読むモデルの単位（列・鎖）と組も1対1に移るので、読むモデルの量は写し方で変わらない。計測でも 1,440 回とも同じレベルだった。違反の知らせ（`viol1`・`viol2`）は大きい数の側だけを知らせるので、補数で移した問題では知らせの効き方が変わりうる。それでも範囲内ではレベルが変わらなかった
- 導出: 4×4 の答えを回転・裏返しで1度だけ使うと、4×4 の問題は 880 − 8（例の魔方陣の8類）= 872 問までしか作れない。L1 500 と L2 の 4×4 250 の750問は収まる
- 外部知見: デューラーの版画「メレンコリア I」の 4×4 の魔方陣のように、広く知られた 4×4 の魔方陣がある（出典は確かめていない）
- 事実（前例）: 氷の床迷路の製品コード（難易度分析）は Python の約13分の1だった。状態の探索を型付き配列で移すと約9〜13分の1、`Map` とタプルのままでは約3〜4分の1: `docs/パズル/導入調査/氷の床迷路/氷の床迷路実装前提調査.md`（TypeScript での速さ）
- 事実（言語仕様）: JavaScript のビット演算は 32 ビットの整数で行う。調査コードは数 v の集合をビット v の整数で持つ（`Geometry.full`）。6×6 は1〜36 で 37 ビット要るので、そのままでは移せない
- 推測: TypeScript に型付き配列で移すと、生成は研究用 Python の CPU の約10分の1になる（3,411 秒 → 1コアで約6分）。`Map` のままなら約3〜4分の1（約14〜19分）。`--verify` は 83 秒 → 約8秒。根拠は上の前例と、魔方陣の生成の時間が整数の集合の演算と配列の走査に集まること。6×6 の数の集合を2つの 32 ビットの整数で持つか配列で持つかで変わる。problem-pool の項目の生成スクリプトの統計で確かめる
- 推測: 製品の乱数は Python の random と一致しないので、TypeScript で作る問題集の中身は調査のものと変わる。当たる割合と規則で除く数は同じ水準になる見込み。候補の作り方と規則が同じで、乱数の質に依らない量のため。生成スクリプトの統計で確かめる
- 推測: 4×4 で答えが同じ類で、与える数の所が5個同じ（近さ 6）の問題どうしは、G × 補数で写すと見た目が変わる。遊ぶ人が似ていると気づくことは少ないと考え、規則は2個以内の違い（近さ 4 以下）を除くまでにした。試遊で確かめる

## 仮決定の候補

- レベルごとの件数: 推奨 各レベル500問（計2,500問）。
  - 理由:
    - 認識合わせで示し、人間が「他はOK」とした値。
    - 毎日1問でも500日かかる。全部埋める前提にしないまま、空き枠が「もう1問」の理由として残る（RQ-010）。
    - 無作為に選ぶ「別の問題」で30回遊んで、重なりは 0.9回（導出）。
    - 各レベル500問を、規則つきで作り切れた（計測）。
    - 4×4 の答えを回転・裏返しで1度だけ使う規則と両立する（L1 500 と L2 の 4×4 250 で 750 ≤ 872）。
    - 橋をかけろ・一筆パズル・タクズと同じ件数。
  - 比べた案:
    - 300問: 毎日1問で1年に届かない。30回で重なり 1.4回。
    - 1,000問: L1 だけで 4×4 の答えの 872 類を超え、同じ答えの向き違いが避けられない。30回で重なり 0.4回。
  - 覆したら: 問題集を作り直す。図鑑の枠と番号が変わる（公開前なので、遊ぶ人の記録は変わらない）。
- 盤面の内訳: 推奨 2つの盤面を許すレベルは半分ずつ（L2 は 4×4・5×5 を250ずつ、L3〜L5 は 5×5・6×6 を250ずつ）。
  - 理由:
    - 「このレベルは2つの大きさが半分ずつ」と言え、図鑑の盤面の絞り込みでどちらも同じ数になる。
    - L1 から L2 へ、半分は同じ 4×4 のまま、新しい読み（2マス空きの列の組）を始められる。
    - L2 の 4×4 を250にしても 4×4 の答えの規則に収まり、L1・L2 の CPU は 162 秒。
  - 比べた案:
    - L2 の 4×4 を100（v0）: L2 の大半が 5×5 で、L1 からの段差が盤面と読みの2つになる。
    - 当たる割合のまま採る: 盤面の比が生成条件の都合で決まり、遊ぶ人に説明できない。
  - 覆したら: 問題集を作り直す。D-04 で 6×6 を外すなら、L3〜L5 は 5×5 を500ずつにする。L4 の 5×5 は当たる割合 約13%で、研究用 Python の CPU 約2,990 秒の見込み。
- 並び: 推奨 レベルの中は、盤面ごとに採った順（生成条件の巡回の順）を保ち、盤面の件数の比で均等に混ぜる。盤面ごとの j 番目（0 始まり）に (j+0.5)/その盤面の件数 を付けて小さい順に並べ、同じ値なら小さい盤面を先にする。
  - 理由:
    - 図鑑の番号が、盤面の大きさやレベルの中の難しさの順を表さない。
    - 問題は無作為に選ぶので、並びは図鑑の見え方にだけ効く。
    - 氷の床迷路も、生成条件を交互に並べた（`generate-ice-floor-maze-problem-pool.ts` の `interleave`）。
  - 比べた案:
    - 盤面ごとにまとめる: 図鑑の前半と後半で大きさが分かれ、番号が大きさを表す。
    - 与える数などの特徴の順: 番号が易しさの順に見えるが、その順の意味を約束できない。
  - 覆したら: 問題集の並びと図鑑の番号だけ。
- 同型のまとめ方: 推奨 列の構造の自己同型 G × 補数（4×4・5×5 は64通り、6×6 は384通り）で、問題と答えのキーを作る。
  - 理由:
    - 写しても分類が変わらず（1,440 回とも同じ）、推理の流れも同じ（導出）。
    - 回転・裏返しの8通りでは、L2 の 4×4 で同じ問題を2組見逃した（補数と列の並べ替えで移る組）。
    - キーは1問 384 通り × 36 マスで軽い。
  - 比べた案: 回転・裏返しの8通り（導入判断の観点の比べた案と同じ）。
  - 覆したら: 重複の判定と問題集。
- 近い問題: 推奨 答えが同じ類（G × 補数）の問題を先に採っていて、その問題との近さ（与える数のある所の対称差の最小）が4以下なら採らない。レベルをまたいで当てる。
  - 理由:
    - 与える数が2つ以内しか違わない問題（L1 の8個なら、6個以上が同じ所）を除く。規則なしの L1 には98組あった。
    - 前例の橋をかけろも、「位置の違う島が2つか、島の数の1割まで」を近い問題として除いた。
    - 費用は小さい。L1 で調べる候補は 897（規則なしは 508）。
  - 比べた案:
    - 2以下: 与える数1つ違いだけを除く。規則なしの L1 で6組。
    - 6以下: L1・L2 で調べる候補が 8,061 から 41,187 に、CPU が 162 秒から 659 秒に増え、L2 の流れだけで 39,032 候補を調べた。推測: 4×4 の答えは165類しかなく、近さ 6 以下まで避けると採れる問題が尽きかけている。
  - 覆したら: 問題集の 4×4。5×5・6×6 には答えが同じ問題が無いので、変わらない。
- 4×4 の答えの向き違い: 推奨 4×4 の答えは、回転・裏返しで同じものを問題集の中で1度だけ使う（レベルをまたぐ）。
  - 理由:
    - 「同じ魔方陣の向き違い」は、解き終えた盤面で見える。広く知られた 4×4 の魔方陣もある（外部知見）。
    - 規則なしの L1 には、回転・裏返しで同じ答えの組が134あった。
    - 4×4 の750問は872類に収まる。
    - G × 補数で写した答えは、数の並びも数そのものも変わるので、1度だけにはしない（166類しかなく、750問に足りない）。
  - 比べた案:
    - 規則なし。
    - G × 補数で1度だけ: 作れない。
    - レベルの中だけで1度だけ: L1 と L2 の間で、同じ答えの向き違いが残る。
  - 覆したら: 問題集の 4×4。4×4 の問題を872問より多くする案（L1 を1,000問など）とは両立しない。
- 置き場所と指紋の上限: 推奨 置かない。
  - 理由:
    - L1 の1つの置き場所の最多は9問（1.8%）で、橋をかけろの「同じ流れは問題数の2%まで」より低い。
    - L1 は、与える数の置き場所で解く順が決まる。置き場所の類は、上限171のうち162を使っている。
    - 解く手順の指紋（段と巡の並び）は、L1 で4種しかない。L1 の定義そのもの（難易度の観点）。
    - L2 の 4×4 の置き場所の最多は12問（250問の4.8%）。L2 は段2の読みが数の値で変わるので、置き場所だけでは解く順が決まらない。
  - 比べた案: 置き場所ごとに上限を置く（たとえば L1 で4問まで）。
  - 覆したら: 問題集の L1。
- 例の魔方陣: 推奨 次の2つにし、どちらも G × 補数で移る64通りを問題集から除く。
  - 4×4: 今のチュートリアルと遊び方の図の魔方陣（14 4 5 11 / 9 2 7 16 / 8 13 12 1 / 3 15 10 6）。
  - 5×5: `ms5-T2-k0-9009` の答え（1 9 8 24 23 / 21 15 10 3 16 / 25 17 12 5 6 / 11 20 13 19 2 / 7 4 22 14 18）。
  - 理由:
    - 4×4 は実装済みで、変えずに済む。
    - 5×5 は、その候補の盤面（与える数10、L3）の初手が、2マス空きの列の組を交わる列と突き合わせる読み。遊び方の「組を探す」図に使える。
    - 5×5 は、難易度の資料の試遊の問題（§7）と別の魔方陣にした。遊び方で見た盤面を、試遊で解くことが無い。
    - 除く 4×4 の魔方陣は 7,040 のうち64（0.9%）で、v1 で除いた候補は L1 11・L2 11。
  - 比べた案:
    - 5×5 に、難易度の資料の L3 の代表 `ms5-T2-k0-51` を使う: 試遊の問題と同じ答えになる。
    - 例を問題集の問題から選ぶ: その問題を問題集から外すことになる。
  - 覆したら: 例の盤面と、問題集の除外だけ。
- 問題集の組み立て: 推奨 次の手順で、上の規則に当たらない先着の候補を採る。
  - レベルごとに生成条件を巡回し、候補番号の順に調べる。
  - 候補は (盤面, T, k, 候補番号) で決まるので、レベルの間で同じ候補をキャッシュで共有する。
  - 並列に調べても、採る順は1つずつ調べたときと同じにする（先読みし、盤面が埋まって巡回する条件が変わったら、先読みをやり直す）。
  - 理由:
    - 決定的で、止まっても同じ順で再開できる（`/design-game-difficulty` の守ること 6）。
    - L3 と L5 の候補は L4 の流れと同じ生成条件なので、L4 を作る間にほぼそろう。
    - 橋をかけろのように質の点で並べ直す方法は、魔方陣には並べる点が無い。
  - 比べた案:
    - 1つの流れで全レベルに配る: レベルごとの生成条件の内訳を決められない。
    - 質の点で並べ直す: 点が無い。
  - 覆したら: 生成スクリプトだけ。
- 問題集の形: 推奨 今の実装の形（与える数を `.` でつないだ文字列、答えは持たない）。
  - 理由: 2,500問で 170,026 B（gzip 39,821 B）と既存の範囲に入り、読みやすい。答えは `--verify` で数え直せる。
  - 比べた案:
    - 与える数の位置のビット列と、数の36進: 生の JSON は小さくなるが、gzip ではほぼ同じ見込み（測っていない）。
    - seed の番号だけ: 生成器の版を変えると、全問が変わる。
  - 覆したら: 問題集の読み書きと問題集。

## 確かめていないこと

- 遊ぶ人の手応え: 近さ 6（L1 で与える数の所が5個同じ）の組や、L1 の置き場所162種（1つの置き場所に最多9問）を、遊ぶ人が「同じような問題」と感じないか。人のプレイが無いので測れない。作り込みの試遊と最終レビューで確かめる。
- TypeScript での生成時間・`--verify` の時間・問題集の実際の大きさ: 研究用 Python で測り、移した後の値は前例からの推測。problem-pool の項目で、生成スクリプトの統計で測る。
- 製品の乱数で作る問題集: 中身は調査のものと変わる。当たる割合・規則で除く数・答えの類の数が同じ水準かは、生成スクリプトの統計で確かめる。
- 難易度の定義が変わったとき: A4 の3回目で定義が変わると、分類とこの観点の値（当たる割合・時間・内訳）が変わる。磨いていない候補（k = 0〜2）はキャッシュに与える数があるので、分類し直して組み直せる。磨いた候補（k = 12）は磨く点が分類に依るので作り直しになり、CPU の大半（v1 で L3〜L5 の約3,250 秒）がかかる。
- D-04 で 6×6 を外したとき（L3〜L5 を 5×5 だけにする）: 当たる割合と時間からの見込みだけで、問題集を作っていない。
- 5×5・6×6 の答えの偏り: 乱択の深さ優先探索は一様ではない。答えどうしを写して一致するマスの数（無作為の組と、代表の形が最も近い組で 12/25・10/36）と、重複が0であることだけを確かめた。全部の組を全部の写し方で比べてはいない。
- 作業の量（基準時間）を問題集に持つか: score の項目で決まる。持てば1問 11 B ほど増える（4つの数で測った）。
- 5×5 の例の盤面を、遊び方の図に使えるか: 初手が2マス空きの列の組で決まることだけを確かめた。図の作りは遊び方の項目。
- 図鑑で、レベルの中の盤面が交互に並ぶ見え方: 画面で見ていない。zukan の項目で確かめる。
- 生成条件の偏り（E2）の手応え: L3〜L5 は全部、磨いた候補（k = 12）から出る（難易度の観点と同じ）。L5 は盤面ごとに1つの生成条件（T3 k12）だけから出る。磨いていない候補を巡回に足す案（難易度の資料 §6.2 で、5×5 T2 k0〜2 は L3 に 13〜20% 当たる）は測っていない。
