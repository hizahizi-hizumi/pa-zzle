# 魔方陣スマホ操作調査

## 結論

合意した前提（数は残っているものから選ぶ、使った数は数の欄で薄くする、盤面と数の欄を一緒に見せる）は、スマホ縦画面で成り立つ。合意のまま進めてよい。ただし、見本の「置いた数をタップすると外せる」には変えたほうがよい所がある（仮決定の候補「置いた数を外す操作」）。

- **最小幅でのマスの大きさ**: 4×4・5×5 は成り立つ。6×6 は条件つきで成り立つ。7×7 は最小幅では成り立たない。
  - どの端末・どの盤面でも、マスの大きさを決めるのは幅ではなく高さ。1〜n² の数の欄が高さを使うため。
  - 数の欄を盤面の大きさごとに1つに決め、列の端の欄なしで測った。マスの大きさ（px）は次のとおり。

    | 端末 | 4×4 | 5×5 | 6×6 | 7×7 |
    |---|---|---|---|---|
    | 390×664 | 83.0 | 66.4 | 47.3 | 40.6 |
    | 360×640（推測の高さ） | 77.0 | 61.6 | 43.3 | 37.1 |
    | 320×568（推測の高さ） | 59.0 | 47.2 | 31.3 | 26.9 |

  - 既存ゲームの最大盤面のマスとの比べ:
    - 390px: ナンプレ 9×9 は 41.2、リフレクション 10×10 は 31.8、マインスイーパー 12列は 31.2。
    - 320px: ナンプレは 33.7、ブリッジは 30.4、リフレクションは 26.0、マインスイーパーは 25.3。
    - 6×6 は 320px でブリッジ並み。7×7 の 26.9 はリフレクション並みだが、数の欄のボタンが 26.8px 幅になり、ナンプレの数字のボタン（29.3px）を下回る。
- **盤面と全操作が一画面に収まる上限**: 条件つきで 6×6。7×7 は幅 360px 以上の端末に限られ、最小幅 320px では成り立たない。
  - 全操作を置いた配置で測った。全操作は、盤面・1〜n² の数の欄・待った、見出しのメニューの「盤面を戻す」、置いた数を盤面で外す操作。
  - 標準の目安（ナンプレの 390px 並み。マス 40px・ボタン 36×44px 以上）を満たす上限:
    - 390×664 で 6×6。
    - 320×568 と 375×548（どちらも推測の高さ）で 5×5。
  - 下限の目安（既存ゲームの 320px 並み。マス 30px・ボタン 29×40px 以上）を満たす上限:
    - 390×664 で 8×8、360×640 で 7×7、320×568 で 6×6。
  - 6×6 の条件: 320px 幅では下限の目安ぎりぎり。下に safe-area が 34px 出る端末では、320×568 の上限が 5×5 に下がる。
- **数の入れ方**: 「マスを選んでから数を選ぶ」（認識合わせの見本）が成り立つ。比べたほかの案は勧めない。
  - 押す回数: 「マス→数」と「数→マス」はどちらも1つ置くのに2回で、指の道のりも同じ（1つ置くのに平均 599〜622px、390×664）。違いは別の所に出る。
    - 「マス→数」は、選んだマスの列を盤面で示せる。示すのは解き方の助けではなく、今見ている列。
    - 「数→マス」で数を選んでも、盤面に示せるものが無い。入る所を示すと、答えを先回りして示すことになる。
  - 「なぞって運ぶ」は押す回数が半分になる。ただし次の不利があり、主な操作にしない。
    - 指の道のりは変わらない。
    - 置く先のマス（27〜66px）が指先（約60px と仮定）に隠れる。
    - 数の欄にも `touch-none` と画面端の余白が要る。
  - 「0〜9 のキー」は合意と食い違う。
    - 盤面は最も大きくなる（7×7・390px で 53.4px）。
    - 押す回数が 1.25〜1.45 倍になる（1つ置くのに 2.5〜2.9回）。
    - 使った数を欄で薄くする見せ方ができず、合意の「数は残っているものから選ぶ」と食い違う。
- **列の端の「あと いくつ」の欄**: 出すと、マスが 10〜15%（5×5〜7×7）小さくなる。置き方は sides がよい。
  - 置き方の案: 行の欄を右、縦の列の欄を下、斜め2本の欄を左下と右下の角に置く（sides）。
  - 測った値: 390×664 で 5×5 が 66.4→56.7px、7×7 が 40.6→36.4px。
  - 高さで決まる画面なので、上に1段を足す置き方（right）は損が大きい。5×5 で −24%、7×7 で −19%。
  - 6×6 の 111 と 7×7 の 175 は3字になる。欄の幅をマスの 0.8 倍にすると、12px の字が入らない（390px で 11.7px・9.9px）。字に合わせて欄を広げても、高さで決まる 390px ではマスは変わらない。
- **操作とスクロールの競合**: 前例どおりにすれば成り立つ。
  - タップだけの案では競合しない。プレイ画面の外枠は `fixed inset-0 overflow-hidden` で、ページ自体がスクロールしない。
  - なぞる案を採るときは、盤面と数の欄の両方に `touch-none select-none [-webkit-touch-callout:none]` を付け、ポインターを捕まえる（一筆パズル・ブリッジの前例）。

## 事実と推測

### プレイ画面の共通部分

- [事実] プレイ画面の外枠は `fixed inset-0 z-(--layer-overlay) flex min-h-svh flex-col overflow-hidden`。
  - 上からブランドの帯（`h-[calc(1.75rem+env(safe-area-inset-top))]`）、`PlayHeader`（`h-[4.5rem]`）、ゲームの中身、下端の面（`BrowserBottomSurface` の `h-3`）が並ぶ。
  - 出典: `frontend/src/components/GamePlayFrame.tsx`、`BrandIdentityHeader.tsx`、`PlayHeader.tsx`、`BrowserBottomSurface.tsx`。
- [事実] 「盤面を戻す」は見出しのメニューにある（`frontend/src/components/PlayHeader/PlayMenu.tsx`、`frontend/src/games/play-vocabulary.ts`）。待ったを置く場所はゲームが決める。
  - 一筆パズル・タクズ・ブリッジは、盤面の下の `h-28` に `UndoButton`（48px の丸）を置く。
  - 詰将棋は、持駒の台の端（`leadingAction`）に置く（`frontend/src/games/tsume-shogi/ui/TsumeShogiPlay.tsx`）。
  - 見出しの右端に、ゲームの操作を足す口（`trailingAction`）がある。マインスイーパーが入力の切り替えに使っている（`MinesweeperPlay.tsx`）。
- [事実] 最小幅は 320px（`frontend/src/index.css` の `min-w-[320px]`）。`frontend/index.html` の viewport は `viewport-fit=cover`。
- [事実] 試遊の端末は Playwright の `devices['iPhone 13']`（390×664）と pc（1280×800）（`.claude/skills/share/playtest-driver.mjs`）。

### 前例（ナンプレの数字の入力）

- [事実] ナンプレの数字の入力（`frontend/src/games/nanpure/ui/play/NanpureDigitPad.tsx`、`NanpurePlay/NanpureInputPanel.tsx`）は次の形。
  - 1〜9 を `grid-cols-9 gap-x-1`・高さ `h-14` の1行に並べる。上に、待った・消す・メモの操作の行（`min-h-16`）がある。
  - 押した数字は `onClick` で受ける。
  - マスを選んでいないときは、数字をすべて押せない見た目（`disabled`）にする。
  - 盤面の幅は `w-[min(96vw,calc(100svh-12rem),38rem)]`。
- [推測] ナンプレは、盤面の幅の式から引く高さ（12rem＝192px）が、実際に盤面以外が使う高さ（268px）より小さい。
  - そのため、高さが 268px＋0.96×幅 より短い画面では、下の数字の欄がはみ出す。
  - 計算では 320×568 で 7px、375×548 で 76px はみ出す（高さは推測）。
  - 魔方陣でこの式を当てはめず、一筆パズル・ブリッジのように main を `[container-type:size]` にして `min(100cqw,100cqh)` で収める。実際の表示は play-ui で撮って確かめる。

### タッチの受け方

- [事実] iOS Safari は、近くを続けて素早く押すと、2回目の click を1回目の位置へ送る。
  - リフレクションのストックと詰将棋の持駒は、`useTouchTap`（指を離したときに受ける）と `touch-manipulation` で避けている。
  - 出典: `frontend/src/components/touch-tap.ts`、`frontend/src/games/reflection/ui/ReflectionStock.tsx`、`TsumeShogiHand.tsx`。
- [事実] なぞる操作の前例（一筆パズル・ブリッジ）は次のとおり。
  - 盤面は `touch-none select-none [-webkit-touch-callout:none]` で、ポインターを捕まえて受ける（`frontend/src/games/bridges/ui/board/BridgesBoard.tsx`）。
  - 一筆パズルは「画面端から始まるタッチはブラウザの戻る操作に取られる」ため、左右に 16px の余白を取る（`HitofudePuzzlePlay.tsx` のコメント）。
  - 画面端の戻るジェスチャーは、Web ページからは止められない（`docs/パズル/導入調査/ハミルトン路/ハミルトン路スマホ操作PoC.md`）。

### 決まり

- [事実] 状態が変わっても、周りの要素の位置と大きさを変えない（`DESIGN.md`「すべきこと・避けること」）。
  - 数の欄では、使った数を消して詰めず、同じ位置のまま薄くする。合意の「使った数は欄で薄くなる」とも合う。
- [事実] 「答えどおりか」「次に置く所」を先に示すと、プレイヤーの代わりに解くことになる（`GAME.md`「判断の優先順位」、`docs/プロダクト/ゲーム/GAME-008-状態の知らせと補助.md` の「補助」）。
  - 使った数を薄くする表示は、今の盤面から分かることなので「状態の知らせ」に当たる。

### 計算の前提にした推測

- [推測] 端末の高さは、390×664 のほかは推測（ツールバーを出したブラウザの表示領域の目安）。実機では測っていない。
  - どの盤面でもマスは高さで決まるので、高さの誤差がそのまま効く。
  - 高さ 1px あたりの効き方: 5×5 ではマスが 0.2px、7×7 では 0.14px 動く（盤面の高さを n で割るため）。
  - 実機の表示か、play-ui の Playwright で端末の大きさを変えて確かめる。
- [推測] safe-area の扱い。
  - Playwright の iPhone 13 では safe-area は 0。
  - 実機の Safari でツールバーが畳まれると、下に 34px 程度が出ると見る。ただし、プレイ画面はスクロールしないので、ツールバーが畳まれる場面は少ないと見る。
  - 確かめていない。`--inset-bottom 34` の表が、その場合の値。
- [推測] 手ぶれのモデル。
  - 手ぶれは x・y が独立な正規分布とした。狙うのは的の中心。
  - 人の実際のぶれは測っていない。数の欄は、目的の数を探してから押すので、盤面より狙いが甘くなりうる。
- [推測] なぞる操作の時間。
  - 指先の直径を約60px とした（ハミルトン路 PoC の仮定）。
  - 外部の知見（未確認）では、なぞる操作は、同じ距離を押す操作より遅く、外れやすい。そのため、押す回数が半分でも、時間は半分にならないと見る。
  - 試作のなぞりで確かめられる。
- [推測] 最初から置いてある数の個数は、5×5 の試作（11個）の割合を、ほかの大きさに当てた値。供給・難易度の観点の問題集ができたら、その数で同じ表を出し直せる。
- [推測] 3字（111・175）を 12px で入れるときの字の幅は、等幅の数字で 0.6em と置いた。書体を決めたら、外接矩形で測り直す。

## 仮決定の候補

- **数の入れ方**
  - 推奨: マスを押して選び、下の数の欄で数を押して置く（認識合わせの見本）。
    - 選んだマスは、盤面のゲーム固有の表現で示す。
    - 選んだマスを通る列（行・縦の列・斜め）も、薄く示す。
    - マスを選んでいないときも、数の欄は「使った / 残っている」の違いを見せたままにする。
  - 理由:
    - 押す回数（1つ置くのに2回）と指の道のりは、「数→マス」と同じ。
    - 選んだマスの列を示せるのは、この順だけ。示すのは解き方の助けではなく、今見ている列。核の読み（空きの列で「あと」になる組を探す）が、選んだマスから始まる。
    - 数の欄は、入力の場であると同時に「残っている数」を見せる場になる。ナンプレのように、マスを選ぶまで欄を押せない見た目にすると、残っている数が読めない。
  - 比べた案:
    - 数→マス: 押す回数は同じ。数を選んだ間に盤面で示せる物が無い。入る所を示すと、答えを先回りして示すことになる。
    - なぞって運ぶ: なぞる回数が半分になる。代わりに次の不利がある。
      - 置く先が指に隠れる。
      - 数の欄にも `touch-none` と画面端の余白（左右 16px）が要る。余白の分、7×7・320px のボタンは 26.8→25.2px に細る。
      - 外すには別の操作が要る。
    - 0〜9 のキーで2桁を打つ: 盤面は 5×5 で +8px、7×7 で +13px（390×664）大きくなる。代わりに次の不利がある。
      - 押す回数が 1.25〜1.45 倍になる。
      - 1桁で決定が要る数ができる。
      - 使った数を欄で薄く見せられず、合意と食い違う。
    - 盤面の上の選び窓: 盤面は最も大きい。選ぶ間に、考えている列を窓が覆う。閉じている間は、残っている数が見えない。
  - 覆したときに作り直す範囲: 入力の層（盤面の受け口と数の欄）と、遊び方・チュートリアルの操作の説明。

- **置いた数を外す操作**
  - 推奨: 置いた数のマスを押すと、まずそのマスを選ぶ。
    - 外すのは、選んだまま同じ数を数の欄で押したときにする。
    - 別の数を押せば置き換える。どちらも2回。
  - 理由:
    - 見本どおり押した瞬間に外すと、隣の空きマスを狙った押し間違いで数が外れる。σ8 で、320×568 の 6×6 は 9.8%、7×7 は 17.8%（隣が置いた数なら外れる）。
    - 合意では、外すと少し減点する。押し間違いが減点になる。
    - 置き換えは、見本の形だと「外す→選ぶ→置く」の3回になる。
  - 比べた案: 見本どおり1回で外す。外すのは速いが、上の押し間違いが減点になる。
  - 覆したときに作り直す範囲: 入力の状態遷移だけ。採点の「外した回数」の数え方は、採点の観点と合わせる。

- **数の欄の並びと待ったの置き場所**
  - 推奨: 1〜n² を小さい順に、問題の間は位置を変えずに並べる。使った数は同じ位置で薄くする。
    - 列数は盤面の大きさごとに決める。
      - 5×5: 7列×4行
      - 6×6: 8列×5行
      - 7×7（採るなら）: 10列×5行
      - 4×4: 8列×2行。盤面と同じ 4×4 に並べると、2つ目の盤面に見えるおそれがあるため。390×664 でマス 93.0・ボタン 43.2、320×568 で 69.0・34.5（待ったは下の行）。
    - 待ったは、数の欄の最後の数の後ろの枠に、`UndoButton` の丸い形で置く。
    - ボタンは `useTouchTap` と `touch-manipulation` で受ける。
  - 理由:
    - 5×5〜7×7 では余った枠に入るので、盤面にもボタンの幅にも響かない。下の行にすると、マスが 390×664 で 5×5 は 66.4→55.2、7×7 は 40.6→32.6 に縮む。
    - 位置が変わらないので、残っている数を位置で読める（`DESIGN.md` の位置を変えない決まり）。
    - 数の欄の数は隣り合って並ぶ。iOS の click の送り先を避けるため、リフレクション・詰将棋の受け方にそろえる。
  - 比べた案:
    - 待ったを下の行（一筆パズルの形）: 揃うが、上のとおりマスが縮む。
    - 左（詰将棋の形）: ボタンが 5×5 で 50.0→42.0、7×7 で 33.8→28.2 に細る。
    - 見出しの右端（`trailingAction`）: 盤面に響かない。親指から遠く、押す手が上下に分かれる（推測）。
    - 最初から置いてある数を欄に並べない: マスが 390×664 で +7〜18px 大きくなる。代わりに、問題ごとに数の位置が変わる。
    - 9列にして 5×5 を3行にする: マスが 390×664 で 74.8 に育つが、ボタンが 38.0（320px で 30.2）に細る。
  - 覆したときに作り直す範囲: footer の配置の定数と、数の欄の部品だけ。

- **盤面の上限**
  - 推奨: 上限は 6×6 とする。7×7 は入れない。
    - 6×6 を使うのは、5×5 で足りない難しさがあると難易度の観点が示したときだけにする。
  - 理由:
    - 6×6 は、390×664 で標準の目安を満たす（マス 47.3・ボタン 43.2）。最小幅 320px でも下限の目安を満たす（31.3・34.5。ブリッジ 10×10 の 30.4 並み）。
    - 7×7 は、320×568 でマス 26.9・ボタン 26.8 になる。ボタンが既存の最小（ナンプレの数字 29.3）を下回り、σ8 で隣のマスに 17.8% 入る。
  - 比べた案:
    - 5×5 で止める（認識合わせのページの初めの案）: どの端末でも標準の目安を満たす。人間は「5×5 に固定する意味は特にない」と返したので、難易度の観点の結果で決める。
    - 7×7 まで入れる: 幅 360px 以上なら下限の目安を満たすが、320px で欠ける。
  - 覆したときに作り直す範囲: 難易度の盤面の定義・問題集、配置の定数（数の欄の列数）。

- **列の端の「あと いくつ」の欄（出すと決めた場合）**
  - 推奨: sides の置き方にする。
    - 行の欄は盤面の右、縦の列の欄は下に置く。
    - 左上→右下の斜めは右下の角、右上→左下の斜めは左下の角に置く。
    - 欄の幅はマスの 0.8 倍を基本に、12px 以上の字が入る幅を下限にする。
  - 理由:
    - 高さで決まる画面なので、高さに足すのは1段だけにする。マスの縮みは、390×664 で 5×5 が −15%、7×7 が −10%。上に1段を足す right では −24%・−19%。
    - 6×6・7×7 の3字は、0.8 倍のままでは 12px に届かない。
  - 比べた案: right（右上の角に斜め）。欄の並びが右と下にそろうが、マスの縮みが大きい。
  - 覆したときに作り直す範囲: 盤面の格子の定義（外周の帯の数と幅）だけ。

- **ページスクロールとブラウザの操作**
  - 推奨: タップだけで遊べるようにし、盤面と数の欄に `touch-manipulation select-none [-webkit-touch-callout:none]` を付ける。
  - 理由: 外枠がスクロールしないので、ダブルタップの拡大と長押しのメニューを止めれば足りる。
  - 比べた案: なぞる操作を足す。`touch-none` とポインターの捕捉、左右 16px の余白が要る（一筆パズル・ブリッジの前例）。
  - 覆したときに作り直す範囲: 入力の層だけ。
