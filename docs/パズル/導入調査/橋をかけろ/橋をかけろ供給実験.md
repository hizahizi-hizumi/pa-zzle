# 橋をかけろ供給実験

調査日: 2026-11-02。スクリプト: `scripts/research/bridges_supply.py`（標準ライブラリのみ、Python 3.13、1プロセス）。数値はすべて研究用 Python の実測で、製品コード（TypeScript）の性能を表すものではない。seed は既定の `20261102`（条件ごとに `"<seed>-<盤>-<密度>-<2本の割合>-<閉路の割合>"` の文字列 seed）。盤面は「幅x高さ」で書く（7x9 は幅7・高さ9の縦長）。

## 結論

- **一意解の問題を作れる割合: 成り立つ。** 完成グラフ先行の生成で、7x7〜10x10・縦長（7x9・8x10）のどの大きさでも、生成候補の 43〜77%（既定の条件 2本の割合0.3・閉路の割合0.2、密度目標0.15〜0.35）が一意解になった。打ち切り（20万ノード）は全条件で0件。1候補の生成＋一意性確認＋推理の判定は中央値 0.2〜3.5ms（分割ありの高密度で 4.4〜5.9ms）。
- **推理だけで解ける一意解の割合: 成り立つ。** この調査の定義（下の「推理の定義」R1+R2）で解き切れる問題は、既定の条件で全候補の 41〜76%。1段仮置き（R3）が要る一意解は全候補の 0〜6% で、R3 でも解き切れないものは全条件で0件。
- **必要な問題数をそろえる時間: 成り立つ。** 既存の問題集の前例（各レベル500問が多数）に合わせ、レベル想定の盤（7x7・8x8・9x9・10x10・10x10）で各500問・計2,500問を、推理だけで解ける一意解・回転反転の同型除外つきで **15秒**（研究用 Python 1プロセス）で集めた。同型の重複は0件。
- **問題集の大きさ: 成り立つ。** 2,500問で、島の位置のビット列＋数字列の形式なら JSON 163KB（gzip 52KB）、全マスを1文字ずつの形式なら 262KB（gzip 52KB）。既存の問題集（JSON 29〜201KB、gzip 3〜81KB）の範囲に入る（コンパクト形式の場合）。
- **生成法と一意性検証の方式: 成り立つ。** 「木として島を育てて橋を架け、閉路の橋を足し、本数から数字を出す」完成グラフ先行で連結・可解は構成上保証される。一意性は交差・連結込みの完全解法器（区間の締め込み＋連結の枝刈り＋分岐で解を2つまで数える）で確かめ、小盤 1,000盤×2（分割なし・あり）で素朴な全探索と解の数が全件一致した。
- **島の密度・橋2本の割合の影響: 条件つきで成り立つ。** 2本の割合が「数字だけで解ける（R1）」と「つながりの推理が要る（R2）」の配分をほぼ決める強いレバーになった（10x10 で 2本の割合 0→0.7 で R1 だけで解ける割合 1〜2% → 55〜65%）。島の密度は、今の生成法では素の成長で 10x10 が約24島（0.23）で頭打ちになり、橋の途中に島を差す「分割」を足すと約29〜30島（0.29）まで上がるが、一意解の割合が 12〜50% に下がる（それでも推理だけで解ける1問は 6〜52ms）。密度を 0.3 より上げるには生成法の改良が要る。

### 推理の定義（この調査だけのもの。難易度の観点の定義とは揃えていない）

- R1 数字の推理: 各辺の本数を区間 [下限, 上限]（0〜2）で持ち、島ごとに「数字 − 他の辺の上限の和」で下限を、「数字 − 他の辺の下限の和」で上限を締める（3 で行き先2つなら各1本以上、1 と 1 の間は1本まで、などを含む）。橋が確定した辺と交差する辺は0本にする。
- R2 つながりの推理: R1 に加え、(a) 架けうる辺のグラフで除くと分断される辺は1本以上、(b) その本数を架けると、確定した橋でつながった島の群が全部ちょうど満たされて閉じ、全島ではない群になるなら、その本数は架けない。架けうる辺のグラフが分断したら矛盾。
- R3 1段仮置き: 未確定の辺の下限か上限の値を仮定して R2 まで進め、矛盾すればその値を外す。
- 「推理だけで解ける」= R2 までで全辺が確定する。各規則は解の一意性に頼らず健全なので、R2 で解き切れた盤は自動的に一意解になる（計測でも全件一致）。

## 事実と推測

- [事実] 既存の問題集は、各レベル 500問が3ゲーム（hitofude-puzzle・takuzu・reflection の L1〜3）、1,000問が3ゲーム、300問・200問が各1ゲーム。形式は `generatorVersion` と `levels`（"1"〜"5"）の下に1問1行の配列: `frontend/src/games/*/problem/problem-pool.json`
- [事実] 一筆パズルの問題集は盤面そのもの（始点と穴の16進ビット列）と分析結果を持ち、実行時に生成器・解法器を呼ばない。生成は `frontend/scripts/generate-hitofude-puzzle-problem-pool.ts`（各レベル既定500問、`--verify` で全問を分析し直す）: `frontend/src/games/hitofude-puzzle/problem/problem-pool.ts`、`docs/パズル/導入調査/ハミルトン路/ハミルトン路実装前提調査.md` §7
- [事実] パーキングジャムは seed の番号だけを持ち本番の生成器で復元する方式: `docs/パズル/パーキングジャム難易度.md`
- [事実（計測）] 上の「計測」の表のとおり。
- [推測] TypeScript の製品の生成器でも 2,500問は数十秒〜数分でそろう。根拠は研究用 Python で15秒、TS は一般にこの種の計算で Python より速いこと。段の実装で `generate-bridges-problem-pool.ts` の実測で確かめる。
- [推測] 2本の割合を上げると R1 だけで解ける問題が増えるのは、2本の橋が多いと数字が行き先の上限（行き先数×2）に近づき、区間の締め込みだけで決まりやすいため。逆に2本0・木（閉路0）では一意解が98〜99%と高いが、ほぼ全問が R2 を要する。表Aから導いた。2本が無い問題集が遊んで単調でないかは実プレイで確かめる。
- [推測] L5 の「つながりの読みが要る問題にそろえる」は、問題供給の側では2本の割合を下げる・分割で密度を上げることで R2 が要る問題を全候補の 45〜96% まで寄せられるので、量としては足りる見込み。ただし R2 が要る＝面白い孤立回避の読みがある、かは別問題で、難易度の観点で R2 の使われ方（回数・場所）を測って確かめる。
- [推測] 島が 10x10 で約24個（素の成長）で頭打ちになるのは、新しい島を「既存の島から1本の橋で届き、橋のマスに乗らず、島と4近傍で接しない」位置に限っているため。失敗許容を増やしても変わらなかったので、乱択の不足ではなく到達できる空きマスが尽きている。

## 仮決定の候補

- 生成法: [推奨] 完成グラフ先行（木で島を育てる＋閉路の橋＋必要なら分割）→ 推理の解法器で解き切れたものだけ採る → 完全解法器で一意性を確かめ直す / [理由] 連結・可解が構成上保証される、推理で解き切れれば一意解も保証され（各規則が健全）、受理率 11〜90%・1問数ms〜50msで供給に余裕がある、完全解法器との二重確認で判定器の誤りを検出できる（失敗パターン「判定の誤りが下流に波及する」の予防） / [比べた案] 数字を先に置いて解けるまで直す方式（試していない。完成グラフ先行で受理率が十分なので要らない見込み）、受理しなかった候補の島を足し引きして一意化する方式（同じく受理率が十分なので不要） / [覆したときに作り直す範囲] 生成器と問題集。判定器・解法器は残る
- 一意性検証: [推奨] 辺ごとの本数の区間を島の数字と交差で締め、架けうる辺のグラフの連結を枝刈りに使い、最も幅の狭い辺で分岐して解を2つまで数える / [理由] 研究用 Python でも打ち切り0件、1候補 p95 12ms 以下。素朴な全探索と 2,000盤で一致 / [比べた案] 葉でだけ連結を見る素朴な全探索（小盤の検算用。10x10 では辺が50本前後あり実用にならない見込み。未計測） / [覆したときに作り直す範囲] 解法器だけ
- 問題集の件数: [推奨] 各レベル500問（計2,500問） / [理由] 一筆パズル・タクズと同じで前例が最も多い。研究用 Python で15秒とそろえる時間に問題が無い / [比べた案] 1,000問（マインスイーパー等。時間・大きさとも可能、3,000問で 194KB） / [覆したときに作り直す範囲] 問題集の再生成だけ
- 問題集の形式: [推奨] 1問1行の配列に、盤の幅・高さ・生成条件と候補番号・「島の位置の16進ビット列＋島の数字の列」・分析結果。解は持たない / [理由] 一筆パズル（盤面を持ち実行時に解法器を呼ばない）と同じ。65B/問で 2,500問 163KB と既存の範囲に入る。全マス1文字形式（105B/問）より生 JSON が4割小さい（gzip ではほぼ同じ） / [比べた案] 全マス1文字（リフレクション型。読みやすいが 262KB）、seed 番号だけ（パーキングジャム型。最小だが生成器の版を変えると全問が変わる） / [覆したときに作り直す範囲] 問題集の読み書きと問題集
- 島の密度・橋2本の割合: [推奨] レベルの判定条件にはせず、生成条件（候補を寄せるレバー）として使う。試作の条件（この調査の 2本0.3・閉路0.2・密度0.25）は比較実験の条件であり完成仕様ではない / [理由] 2本の割合が R1/R2 の配分を大きく動かす（表A）ので難易度の候補領域を寄せるのに使える。一筆パズルも壁率を生成条件として扱った（`ハミルトン路実装前提調査.md` §13） / [比べた案] 密度・2本の割合でレベルを直接決める（`難易度判定.md` の「生成条件を難易度へ直結させない」に反する） / [覆したときに作り直す範囲] 生成条件の表と問題集

## 確かめていないこと

- 製品の TypeScript での生成時間と問題集の実サイズ（分析結果の列を含む）: 研究用 Python だけで測った。段の実装で測る。
- 推理の定義を難易度の観点と揃えること: 観点カードの指示どおり自分の定義で測った。R1 の区間の締め込みは人が島ごとに考える推理より強い可能性があり、R1/R2 の割合は難易度の観点の定義で測り直すと変わりうる。
- 密度 0.3 より上（既製のブリッジパズルの 10x10 によくある島数）の問題: 今の生成法では作れない。既製の問題の島数も確かめていない（外部の問題を参照していない）。必要なら生成法（例: 島を先に散らしてから全域木を張る）を比べる。
- 縦長の 9x10・10x8 など他の縦横比: 7x9・8x10 だけを測った。面積が同じ正方形と傾向は同じだった。
- 生成した問題の見た目の偏り（数字の分布、島の偏在、2の多さ、分割で生じる 2・4 の多さ）と単調さ: 数えていない。難易度の観点か実装時の `--verify` で見る。
- 盤面の大きさの上限 10x10 とスマホでの押し分け: 操作の観点の担当。
