# 橋をかけろスマホ操作調査

## 結論

- **最小幅**: 成り立つ。既存の前提は幅 320px（`frontend/src/index.css` の `body` に `min-w-[320px]`）。既存の調査も 320 / 360 / 375 / 390px で測っている。10×10 のマスは 390px で 35.8px、360px で 32.8px、320px で 28.8px。一筆パズルと同じ骨格（左右 16px の余白、下に待った）で計算した。既存ゲームの最大盤面より小さいが、出題済みのリフレクション 10×10（390px で 31.8px）やマインスイーパー 12列（31.1px）よりは大きい。
- **一画面に収まるか（10×10）**: 成り立つ。一筆パズルの骨格では、盤面以外に 228px を使う（ブランドの帯 28、見出し 72、盤面の上下の余白 16、待った 112）。待ったは下、「盤面を戻す」は見出しのメニューにある。10×10 は 390×664 でも幅でマスが決まる。高さで縮むのは、ツールバーを出した Safari の短い画面だけ（推測の高さ。375×548 で 32.0px、320×460 で 23.2px）。
- **縦長（10×12 など）**: 条件つきで成り立つ。390×664 でも 360×640 でも、10×12 までは 10×10 と同じマスの大きさで入る（盤面に使える高さはそれぞれ 436px と 412px）。10×13 からは高さで縮む。375×548 の短い画面では 10×12 が 26.7px まで縮む。合意は最大 10×10 なので、縦長は入れない方を推奨する。
- **島の間をタップで押し分けられるか**: 条件つきで成り立つ。条件は次の3つ。
  1. 縦横に隣り合う島を作らない（間に1マス以上空ける）。供給の生成器 `scripts/research/bridges_supply.py` も同じ規則。隣り合う島を許すと、10×10・390px で間に見える線は 7.2px、安全半径は 3.6px しかない。手ぶれ σ4px での成功率は 86%（最悪の候補では 56%）で、タップでは押し分けられない。
  2. 押した位置は、最も近い候補の線に割り当てる。島の丸を先に判定し、線から 0.5マスより遠い所は何も選ばない。
  3. 2つの候補が交わるマスでは、橋のある方を選ぶ。こうすると全候補で、狙う点の周り 0.5マスが安全になる（390px で半径 17.9px、320px で 14.4px）。
- **交わる2候補のどちらにも橋が無い場合**: 押せる範囲が狭いまま残る。間が1マスの組が、ちょうどその1マスで別の候補と交わる場合で、安全半径は 0.247マス（390px で 8.9px、320px で 7.1px）に落ちる。10×10・密度 0.25 では候補の 7.9%、1問あたり中央値2組（最大9組）。なぞる操作は島ごと・向きごとに相手が1つに決まるので、この場合もなぞれば確実に架けられる。
- **島の丸と線を押せる幅**: 成り立つ。島の丸を半径 0.40マスにすると、10×10 で直径 28.6px（390px）、23.0px（320px）。線を押せる幅は1マス分（390px で 35.8px、320px で 28.8px）。丸の大きさを 0.35〜0.45 の間で変えても、押し分けへの影響は小さい（交わりが無い所はどれも 0.5マス）。
- **なぞる操作とページスクロールの競合**: 前例どおりにすれば成り立つ。前例は次の3つ。
  - プレイ画面の外枠は `fixed inset-0 overflow-hidden` で、プレイ中はページ自体がスクロールしない。
  - 一筆パズルの盤面は `touch-none select-none [-webkit-touch-callout:none]`。Pointer Events とポインターの捕捉で受け、右クリックのメニューを止める。
  - 一筆パズル PoC では、盤面のドラッグ中も `scrollY = 0` のままだった。

## 事実と推測

- [事実] 対応する最小幅は 320px（`frontend/src/index.css` の `min-w-[320px]`）。過去の調査も 320〜390px で測っている（`docs/パズル/導入調査/ハミルトン路/ハミルトン路スマホ操作PoC.md`、`docs/パズル/導入調査/リフレクション/リフレクション実装前提調査.md`）。
- [事実] プレイ画面の外枠は `fixed inset-0 ... overflow-hidden` で、見出しは高さが固定されている（ブランドの帯 `h-[calc(1.75rem+env(safe-area-inset-top))]`、`PlayHeader` は `h-[4.5rem]`）。出典は `frontend/src/components/GamePlayFrame.tsx`、`BrandIdentityHeader.tsx`、`PlayHeader.tsx`。
- [事実] `index.html` の viewport に `viewport-fit=cover` が無いので、ブラウザ表示では safe-area の余白が 0 になる（`frontend/index.html`）。
- [事実] 一筆パズル（手本）の骨格は次のとおり。出典は `frontend/src/games/hitofude-puzzle/ui/HitofudePuzzlePlay.tsx`。
  - main は `px-4 py-2 [container-type:size]`、盤面は `aspect-square w-[min(100cqw,100cqh,40rem)]`。
  - footer は `h-28` で、中は `UndoButton`（48px の丸）。
  - 左右の余白は「画面端から始まるタッチはブラウザの戻る操作に取られる」ため。
  - タクズとウォーターソートも同じ footer（`frontend/src/games/takuzu/ui/TakuzuPlay.tsx`）。
- [事実] 「盤面を戻す」（restart）は見出しのメニューにある（`frontend/src/components/PlayHeader/PlayMenu.tsx`、`frontend/src/games/play-vocabulary.ts`）。待ったは盤面の下。
- [事実] 縦長の盤面には前例がある。マインスイーパーは最大 16行×12列（`frontend/src/games/minesweeper/difficulty.ts`）で、幅 `max-w-[27rem]` に合わせて縦に伸びる（`MinesweeperPlay.tsx`）。
- [事実] リフレクションはレベル5 で 9〜10（`frontend/src/games/reflection/difficulty.ts`）。10×10 のマスは 390px で 31.8px で、調査の記録とも一致する（`リフレクション実装前提調査.md` の「8×8以上の盤面」）。
- [事実] なぞる操作の前例（一筆パズル）。出典は `frontend/src/games/hitofude-puzzle/ui/board/HitofudePuzzleBoard.tsx` と `ハミルトン路スマホ操作PoC.md`。
  - 盤面全体の1要素で Pointer Events を受け、`setPointerCapture` で指を捕まえ、座標をマス単位に直してマスを決める。
  - クラスは `touch-none select-none [-webkit-touch-callout:none]`、`contextmenu` は止める。
  - PoC では、盤面のドラッグ中は `scrollY = 0` のまま、盤面の外ではスクロールできた。
- [事実] 同じ所を素早く何度も押して状態を回す前例はタクズ（`frontend/src/games/takuzu/ui/board/TakuzuBoard/TakuzuCell.tsx`）。
  - タッチは pointerdown で受ける。
  - `touch-manipulation` でダブルタップの拡大を止める。
- [事実] iOS Safari は、近くを続けて押すと2回目の click を1回目の位置へ送る（`frontend/src/components/touch-tap.ts` のコメント）。ボタンごとに click で受けると、橋の 1本 → 2本 の連打で取り違えが起きうる。
- [事実] 供給の生成器 `scripts/research/bridges_supply.py`（別の観点のスクリプト）は、縦横に隣り合う島を作らない（`blocked_for_island`）。
- [推測] 端末の高さ（390×664、375×548、360×640、320×460）は、ツールバーを出したブラウザの表示領域の目安。実機では測っていない。幅で決まる結論（10×10 は 390px で 35.8px）は高さに依らない。高さで縮む値は、実機の表示で確かめる。
- [推測] 手ぶれは x・y 独立の正規分布で模した。狙う点は「線の上で最も安全な点」なので、人が線の見た目の中央を狙う場合より甘い。見た目の中央が交わる点にあると、そこは境界の上なので取り違えはほぼ五分になる（模していない）。人間の実プレイか、ブラウザでの自動操作で確かめられる。
- [推測] 隣り合う島を禁じても、L5 の推理（つながりの読み）は保てると見る。根拠は、供給の生成器がすでにこの規則で問題を作っていること。成否は供給・難易度の観点の計測で確かめる。
- [推測] 当たり判定をボタンの集まりにせず、盤面1要素で座標から決めれば、iOS のダブルタップの click の送り先の問題は起きない。根拠は、一筆パズルの盤面が pointerdown の座標で決めていること。実機では確かめていない。

## 仮決定の候補

- **プレイ画面の骨格**
  - 推奨: 一筆パズルと同じにする。main は `px-4 py-2` で、盤面は縦横比を保って `min(100cqw,100cqh)` に収める。footer は `h-28` で待ったを置き、「盤面を戻す」は見出しのメニューに置く。
  - 理由:
    - 10×10 が 320〜390px の幅で横にはみ出さず、待ったの位置もそろう。
    - 画面端から始まる戻る操作を避ける余白が、すでに入っている。
  - 比べた案: リフレクションの細い footer（60px）にして盤面の高さを稼ぐ案。短い画面で約50px の得になる。待ったが他ゲームの位置と違ってしまう。
  - 覆したときに作り直す範囲: プレイ画面のレイアウトのクラスだけ。
- **盤面の上限**
  - 推奨: 合意どおり正方形の 10×10 までにする。縦長は入れない。
  - 理由:
    - 10×12 は 390×664 なら同じマスで入るが、375×548 では 26.7px まで縮む。
    - 押せる範囲が狭い候補の割合も、10×10 の 7.9% から 10.8% に増える。
  - 比べた案: 10×12 まで許す。マインスイーパーの縦長の前例はある。
  - 覆したときに作り直す範囲: 難易度の盤面の定義、問題集、レイアウトの縦横比。
- **島の配置**
  - 推奨: 縦横に隣り合う島を作らない（間に1マス以上空ける）。
  - 理由:
    - 隣り合う島の間は線が 7.2px しか見えず、σ4px でも 14% 外れる。
    - 供給の生成器もすでにこの規則。
  - 比べた案: 隣り合う島を許し、その組はなぞる操作だけで架ける。タップだけでは解けない問題ができ、合意の「タップで 1本 → 2本 → なし」と食い違う。
  - 覆したときに作り直す範囲: 生成器と問題集。
- **タップの当たり判定**
  - 推奨: 盤面1要素で座標から決める。順番は次のとおり。
    1. 島の丸の中なら、島（なぞりの始点）。
    2. それ以外は、線までの距離が最も近い候補にする。0.5マスを超えたら何もしない。
    3. 交わる2候補の一方に橋があれば、交わるマスではその候補を選ぶ。
    4. どちらにも無ければ、マスを対角線で4つに分けて選ぶ。
  - 理由:
    - 交わりが無い所はすべて、線から半マスまで押せる（390px で幅 35.8px）。
    - 規則3で、架けた後の 2本目・取り外しが交わる所でも確実になる。
    - 交わらない最小の組でも、狙える長さが 43px ある（390px）。
  - 比べた案: 島の間ごとにボタンを置く。ボタンの形が交わる所で重なる。iOS の click の送り先の扱い（`useTouchTap`）も要る。
  - 覆したときに作り直す範囲: 盤面の入力層だけ。
- **交わる所でどちらにも橋が無い場合**
  - 推奨: 規則4（対角線で分ける）を使い、なぞる操作を確実な手段として遊び方で見せる。
  - 理由: なぞりは島ごと・向きごとに相手が1つに決まり、4方向のどれかを選ぶだけでよい。
  - 比べた案:
    - 何もしない: 押しても反応が無く、壊れて見える。
    - 生成器で「間が1マスの組がその1マスで交わる」配置を避ける: 盤面が偏る。1問あたり中央値2組で、避けるのは重い。
  - 覆したときに作り直す範囲: 当たり判定の関数だけ。
- **島の丸の大きさ**
  - 推奨: 半径 0.40マス（10×10 で 390px 28.6px、320px 23.0px）。
  - 理由:
    - 0.35〜0.45 で押し分けの差は小さい。
    - 数字1桁（1〜8）を読める大きさを優先した。
    - 320px でほぼ 24px（WCAG 2.5.8 の最小）に届く。
    - なぞりの始点は丸より広く取れる（隣り合う島が無いので、島のマスを始点にできる）。
  - 比べた案: 0.35（線が長く見える）、0.45（数字が大きい）。
  - 覆したときに作り直す範囲: 見た目の定数だけ。
- **ページスクロール・ブラウザの操作との競合**
  - 推奨: 盤面に `touch-none select-none [-webkit-touch-callout:none]` を付け、`contextmenu` を止め、Pointer Events とポインターの捕捉で受ける（一筆パズルと同じ）。
    - 島から始めて動けばなぞり、島の外で押せばタップとする。
    - タップはタクズと同じく pointerdown で受ける。連打 1本 → 2本 を速く返すため。
  - 理由: 前例で、スクロール・ダブルタップの拡大・長押しのメニューを止めた実績がある。
  - 比べた案: `touch-manipulation`（タクズ）。拡大は止まるが、なぞる操作でパンが起きうる。
  - 覆したときに作り直す範囲: 盤面の入力層だけ。

## 確かめていないこと

- **実機（iOS Safari・Android Chrome）でのマスの大きさ・押し分け・連打の取りこぼし**: ブラウザが使えない（計算と模擬だけ）。play-ui で Playwright のタッチ操作と、最終レビューの「遊ぶ」で確かめる。
- **端末の実際の表示の高さ（ツールバーの出し入れ、ホーム画面に置いたとき）**: 実機を使えない。高さの値は推測として置いた。
- **人が線の見た目の中央を狙ったときの取り違え**: 模擬の狙う点は最も安全な点で、人の狙い方は測れない。
- **なぞる操作の手ぶれへの強さ**: 計測していない。4方向の選択なので、一筆パズルのマス単位の追跡より甘い（推測）。
- **2本の橋を平行な2線で描いたときに、細いマス（320px で 28.8px）で読めるか**: 見た目の観点で、play-ui で撮って確かめる。
- **生成器の配置**: 本番の問題集（一意解・推理だけで解ける問題）の配置とは同じでない。割合は供給の問題集ができたら同じスクリプトの関数で数え直せる。
