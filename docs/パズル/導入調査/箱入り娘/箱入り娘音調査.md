# 箱入り娘 調査: 音

## 結論

- **どの瞬間に何を返すか: 条件つきで成り立つ。** `DESIGN.md`「音」の決まりのまま当てはまる。鳴らすのは次の3つだけにする。
  - 駒がなぞりの途中で新しいマスへ移った瞬間: 短く小さい木の駒のすべり音。揺らぎを付ける。
  - 娘が出口の前に着いた完成演出: クリア音。
  - 動けない駒をなぞったとき: 合意では「動かないだけ」なので画面は変わらず、鳴らさない。不成立の音は、押し返しの動きを付けると決めたときだけ足す。
  - 「1手戻す」「最初から」、駒に触れるだけ、手数の更新には鳴らさない。
  - 条件は1つある。1マス移るごとに鳴らすので、プレイフックはなぞりの途中で駒の位置が変わるたびに `id` 付きの知らせを出す必要がある。一筆パズルの `extended` と同じ形。
- **題材の素材: 成り立つ。** 木の箱の中を木の駒がすべって止まる音で作る。すべり音は「軽いこすれ＋小さなこつ」、クリアは「娘が箱の口から抜け出るごとん＋木の箱の胴鳴り」。前例を見ると、木の音は合成では本物らしさが出ず、詰将棋は CC0 の録音（VCSL のスラップスティック・カホン＝木の箱の胴）に切り替えている。箱入り娘も録音を加工して作るのがよい。
- **本数と大きさの目安: 成り立つ。** 既存10ゲームはゲームごとに 3〜14本・17.7〜81.8KB（中央値 8.5本・21.0KB）。目安は **6〜9本・合計 30KB 以下** とする。全効果音（今の合計 93本・450.3KB）はタイトルで上限 4000ms のうちに読み込むので（ADR-0011）、1ゲーム分が増えるとほかのゲームの音が間に合わなくなる余地が広がる。
- **鳴る回数: 成り立つ。** 1マスごとに鳴らす案でも、最短解では1手あたり平均 1.46〜1.69回。横刀立馬を最短で解いても計 118回なので、1手1回の案（81回）より 1.5倍に収まる。

## 事実と推測

- [事実] 鳴らす・鳴らさないの決まり。前進（中心の操作が成立した）には短く小さく鳴らす。待った・戻す・リセット・対象を選ぶだけの操作には鳴らさない。画面が変わる瞬間だけ鳴らす。回数の多い音ほど小さく短くし、機械的に繰り返さない。題材から作る: `DESIGN.md`「音」
- [事実] 音声ファイルは `assets/` に同梱して `playSound` で鳴らし、コードで合成しない。回数の多い音には `REPEATED_SOUND_VARIATION`（±30セント・±12%）を渡す。動きを減らす設定で画面が変わらない操作の音と、演出の無いクリア音は鳴らさない: `.claude/rules/game-structure.md`「効果音」、`frontend/src/lib/sound-effects.ts`
- [事実] 全ゲームの `*.flac` は `import.meta.glob("./**/*.flac")` で一括して集め、タイトルで読み込む。待つ上限は `SOUND_LOADING_LIMIT_MS = 4000`。上限を過ぎた音は読み込み終えるまで鳴らない: `frontend/src/frontend.tsx`、`frontend/src/lib/app-launch.ts`、`docs/adr/ADR-0011-app-title-sound-loading.md`。カードには「大きさが効く理由は game-structure.md」とあったが、そこに大きさの話は無い。理由の正本は ADR-0011 とコード。
- [事実] なぞりの途中で1マスごとに鳴らす前例がある。一筆パズルは道を1マス延ばすごとに `path-extended` を揺らぎ付きで鳴らす。「なぞり1回に1つの音」は指を離すまで手応えが無いとして採らなかった: `docs/パズル/導入調査/ハミルトン路/ハミルトン路実装前提調査.md` §18、`frontend/src/games/hitofude-puzzle/ui/HitofudePuzzlePlay/use-hitofude-puzzle-sound-effects.ts`
- [事実] 木の駒の音は合成（モード合成）では重厚感と本物らしさが出ず、CC0 の録音（VCSL のスラップスティック・カホン・スリットドラム）を加工して作った。手順は `VCSL.CC0.txt` と `scripts/assets/tsume_shogi_sounds.py` にある。元の録音はリポジトリに入れない: `docs/パズル/導入調査/詰将棋/詰将棋名称・権利調査.md`、`frontend/src/games/tsume-shogi/assets/sounds/VCSL.CC0.txt`
- [事実] 既存のゲームの音をそのまま使うことは「題材から作る決まりに反する」として採らなかった: ハミルトン路実装前提調査 §18
- [事実] 認識合わせの試作では、なぞる間、駒は指にいちばん近い行けるマスへ飛び、位置が変わるたびに描き直す。指を離したとき、元の位置から動いていれば1手と数える: `認識合わせのページ` の pointermove/end
- [推測] 1回のポインタの動きで2マス以上飛ぶことがある（速くなぞったとき・遠くの行けるマスへ寄るとき）。音は「位置が変わった知らせ1回に1音」にし、マスの数だけ重ねないほうがよい。根拠は試作の寄せ方。試作の寄せ方は比べていない条件なので、そのまま完成仕様にしない。実装の操作の観点で決めたあと、実機で確かめる。
- [推測] 今の 450KB に 30KB を足すと 480KB。仮に 1Mbps（125KB/s）なら 3.6秒→3.8秒で、上限の 4秒に近づく。回線の速さは測っていない机上の計算で、HTTP の並列や cache は考えていない。ここから「本数・大きさは中央値（21KB）近くに抑える」という目安を出した。
- [推測] 娘だけ `playbackRate`（例 0.85 前後）で低く鳴らせば、ファイルを増やさずに重い駒らしさを出せる。娘は見た目でも区別される駒なので、視覚と同じ意味を超えない（`DESIGN.md`「伝えるのは同じ瞬間の視覚の知らせと同じ意味まで」）。値は聞いて決める。

## 仮決定の候補

- **鳴らす瞬間（すべり音）**
  - 推奨: なぞりの途中で駒の位置が変わるたびに1音。指を離したときには別の音を足さない。
  - 理由:
    - 駒が動いた瞬間が画面の変化そのもの。
    - 一筆パズルの前例（1マスごと）とそろう。
    - 最短解でも1手あたり 1.5〜1.7回で、うるさくなりにくい（計測）。
    - なぞって元に戻した場合（手数に数えない）も、動いた分だけ鳴って画面と合う。
  - 比べた案:
    - (a) 指を離して1手が成立したときに1音（離すまで手応えが無い。一筆パズルで採らなかった）
    - (b) 1マスごと＋離したときに「止まる」音（1手で2系統が鳴り、回数の多い操作が重くなる）
  - 覆したときに作り直す範囲: プレイフックの操作の知らせ（なぞりの途中の知らせを出すか）と、音のフック。
- **すべり音の作り方**
  - 推奨: 木と木の短いこすれに小さなこつを重ねる。0.05〜0.1秒、最大 -22〜-25dBFS 前後（slide `slid`・hitofude `path-extended` と同じくらい）。テイク2〜3本を `REPEATED_SOUND_VARIATION` と合わせ、機械的な繰り返しを避ける。娘は同じファイルを低い `playbackRate` で鳴らす。
  - 理由:
    - 回数の多い音は既存でも 0.05〜0.08秒・2KB 前後に収まっている（計測）。
    - 詰将棋の `piece-moved`（0.17秒・最大 -19.5）は1手に1回の音で、1マスごとに鳴らすには長く大きい。
  - 比べた案:
    - 駒の大きさごとに別ファイル（本数と KB が増える）
    - 揺らぎだけで1本（テイクが無いと、横刀立馬の 118回以上で単調になりやすい）
  - 覆したときに作り直す範囲: 音声ファイルと音のフックだけ。
- **素材の出どころ**
  - 推奨: CC0 の録音を加工する。詰将棋と同じ VCSL の木の打楽器でよいが、詰将棋の駒音と聞き分けられる加工にする。出典と加工の手順は同じ形で残す。
  - 理由:
    - 木の音の合成は前例で本物らしさが出なかった。
    - CC0 で表示の義務が無い。
    - 加工のスクリプトの前例をそのまま使える。
  - 比べた案:
    - 合成（前例で失敗している）
    - 詰将棋の音を流用（決まりに反する）
  - 覆したときに作り直す範囲: 音声ファイルと素材の記録（`*.CC0.txt`・加工のスクリプト）。
- **クリア音**
  - 推奨: 完成演出の始まりに合わせて、娘が出口へ抜けるごとんと、木の箱の胴鳴り（カホン系）の余韻を1〜3本。0.3〜0.9秒、最大 -11〜-20dBFS 程度。動きを減らす設定では、完成した盤面を止めたまま見せるならその姿に合わせた1本を `playReducedMotionClearSound` で鳴らし、すぐ結果へ進むなら鳴らさない。
  - 理由: 決まりにより、クリア音は完成演出に合わせて「達成」の段階で鳴らす。既存のクリア音の長さ・大きさもこの範囲にある（計測）。
  - 比べた案: 音階を駆け上がる型（スライドパズル・一筆パズル）。題材の木の箱から離れる。
  - 覆したときに作り直す範囲: クリア音のファイルと、演出に合わせる時刻。完成演出の形が決まってから決める。
- **不成立の音**
  - 推奨: 置かない（合意「動けない方向には動かないだけ」で画面が変わらないため）。
  - 比べた案: 動けない駒に小さな押し返しを付け、責めない鈍い木の音（0.08〜0.12秒、最大 -30dBFS 前後。slide `invalid`・ice `blocked` 並み）を足す。
  - 覆したときに作り直す範囲: 操作の知らせに不成立の種類を足し、音を1本足す。動きを減らす設定では鳴らさない処理も要る。
- **本数・大きさの目安**
  - 推奨: すべり 2〜3本＋クリア 1〜3本（＋不成立を置くなら1本）で、6〜9本・合計 30KB 以下。
  - 理由:
    - 既存の中央値は 8.5本・21.0KB（計測）。
    - 全効果音をタイトルで 4秒上限のうちに読み込む（ADR-0011）。
  - 比べた案: 詰将棋並みの 14本・82KB。全体が約 18% 増え、上限に近づく。
  - 覆したときに作り直す範囲: 音声ファイルだけ。

- 音と演出の時刻: クリアの音は、盤面の演出と同じ時刻（クリアした描画）を始まりに、娘が抜け始める 350ms にこすれ、抜け切る 1050ms にごとんを予約する。演出は始まりを次の描画まで待たずにその時刻へそろえる（Web Animations の `startTime`）。iPhone 13 の大きさの Chromium で、CPU を 1・4・6 倍遅くして、ごとんの予約時刻と箱が沈み始めた描画の間（1フレーム 17ms）を測ると、どれも同じフレームの間に入った（ずれ 17ms 以内）。こすれと娘が抜け始めた描画も同じ。音の出口の遅れ（端末ごとに一定）は含めていない。

## 確かめていないこと

- VCSL に木のこすれ・すべりの録音があるか: GitHub の `sgossner/VCSL` はこのセッションでは読めなかった（403）。無ければ、打音を短く切って重ねる・帯域雑音を録音で畳み込むなど、加工でこすれを作る必要がある。
- 実機で 1マスごとの音がうるさくないか、速くなぞったときに音が詰まらないか: 音を聞いていない。一筆パズルにも「速くなぞったときに1マスごとの音がうるさくないか」が残っている。
- LUFS での大きさ: 前例の目標（詰将棋 `piece-moved` -46.5 LUFS など）に合わせて測っていない。測ったのは dBFS のピークと平均だけ。
- 実際の回線での読み込み時間: 測っていない。上の秒数は机上の計算。
- 完成演出の形（娘が出口から出ていくか、止まって光るか）: 演出の観点で決まっていないので、クリア音の時刻と、動きを減らす設定での扱いは決めていない。
