# 箱入り娘 調査: スマホ操作

## 結論

- **最小幅でのマスの大きさ: 成り立つ。** 既存のプレイ画面の外枠（ブランドの帯 28px＋見出し 72px＋下の操作欄 112px＋main の上下 16px）に 4×5 の盤を置くと、320px 幅の1マスは 320×640 で 67〜74px（幅で決まる）、320×568 で 61〜68px（高さで決まる）。どれも同じ画面のハミルトン路 8×8（36px）より大きく、スライドパズル 5×5（59px）と同じかそれ以上になる。縦が短い画面では高さで決まる。Safari のバーが出た 320×460 の目安（推測）でも 41〜46px。
- **盤面と全操作が一画面に収まるか: 成り立つ。** 既存の外枠（`GamePlayFrame`）は画面に固定され（`fixed inset-0 overflow-hidden`）、盤は main の残りに縦横比を保って縮む。「1手戻す」は下の操作欄の待ったボタン（`UndoButton`）、「最初から」は見出しのメニューの「盤面を戻す」、メニューは見出しの右端にある。どの幅でも盤のほうが縮むので、はみ出さない。
- **なぞる操作とスクロールの競合: 条件つきで成り立つ。** ハミルトン路と同じ指定（盤面に `touch-action: none`・`user-select: none`・`-webkit-touch-callout: none`、`contextmenu` の抑止、`setPointerCapture`、Pointer Events だけで受ける）をすれば、盤面でのなぞりでページは動かない。外枠は固定でスクロールもしない。ただし iPhone 実機ではまだ確かめていない（合意の「まだ分からないこと」は残る）。画面の端から始まる戻るジェスチャーはページからは止められないので、左右の余白は 16px（`px-4`。ハミルトン路と同じ）にする。
- **なぞって角を曲がる操作（指を離すまで1手）: 成り立つ。入力処理は「C: 隣接だけ」を推す。** 合成した指の軌跡で3案を比べると、ねらった所へ着く割合はどれも 97〜100% でほぼ同じだった。差が出たのは、塞がれた向きへ押し込んだとき。認識合わせの見本の方式（A: 押した時点の到達先のうち指に最も近い所）だと、3.0〜4.7% で駒が障害物を回り込んで別の場所へ跳んだ。B と C では 0〜0.2% だった。押し込んでから直角に曲がった指で2マス以上離れた所まで行った割合は、C が 1.1% で最も低かった（A 2.9〜3.2%、B 2.1〜2.3%）。タップ（4px の揺れ）で駒が動いたことは、どの案でも無かった。
- **合意の読み方の確認（成り立たないわけではない）:** 「指を離すまでが1手」と「同じ駒の連続した移動は1手」は、同じ駒を一度離してもう一度なぞったときに食い違う。最短手数を出す解法器は後者で数えている。下の「仮決定の候補」で、同じ駒が続いたなぞりはまとめて1手と数える案を推す。

## 事実と推測

- [事実] プレイ画面の外枠は画面に固定され、スクロールしない（`fixed inset-0 ... overflow-hidden ... pb-[env(safe-area-inset-bottom)]`）。上から順に、ブランドの帯（`h-[calc(1.75rem+env(safe-area-inset-top))]`）、見出し（`h-[4.5rem]`。左に戻る、右にメニュー）、盤面（`main`）、ゲームごとの操作（`footer`）が並ぶ: `frontend/src/components/GamePlayFrame.tsx`、`frontend/src/components/PlayHeader.tsx`、`frontend/src/components/BrandIdentityHeader.tsx`
- [事実] 待ったのあるゲーム（パーキングジャム・氷の床・ウォーターソート・ハミルトン路）は、どれも `footer className="grid h-28 shrink-0 items-end px-4 pb-2"` に `UndoButton`（48px の丸ボタン）を置く。待ったのボタンはタッチを指を離したとき（`useTouchTap`）に受けるので、盤面をなぞった直後に押しても効く: `frontend/src/games/hitofude-puzzle/ui/HitofudePuzzlePlay.tsx`、`frontend/src/components/UndoButton.tsx`
- [事実] アプリの操作の呼び名は、1手戻すが「待った」、最初からが「盤面を戻す」、同じ問題を新しいプレイで始め直すのが「リセット」。「盤面を戻す」と「リセット」は見出しのメニューに入る: `frontend/src/games/play-vocabulary.ts`、`frontend/src/components/PlayHeader/PlayMenu.tsx`
- [事実] 既存のなぞり・ドラッグの扱い:
  - ハミルトン路: 盤面のルートで Pointer Events だけを受け、`touch-none select-none [-webkit-touch-callout:none]`、`contextmenu` を抑え、押した時点で `preventDefault` と `setPointerCapture` をする。主でない指は無視する。指の位置はマス幅の 1/6 刻みで補間し、隣のマスへ移るのは縁から 15% 入ってから。斜めへ移ったときは主な向きの角を先に通る: `frontend/src/games/hitofude-puzzle/ui/board/HitofudePuzzleBoard.tsx`、`frontend/src/games/hitofude-puzzle/ui/board/finger-trace.ts`
  - パーキングジャム: 車の上で押して離したときの移動量（18px 以上）で向きを決める。向きは車の向きに沿った軸だけで、1回のなぞりで1方向。SVG に `touch-action: none`: `frontend/src/games/parking-jam/ui/board/ParkingJamBoard.tsx`、`parking-jam-board.css`
  - 氷の床: プレイ領域の全体（盤の外の余白と下の操作欄も含む）で、18px を越えた時点で縦横の大きいほうへ1回だけ動かす。ボタンから始めた指は受けない: `frontend/src/games/ice-floor-maze/ui/IceFloorMazePlay/IceFloorMazeSwipeArea.tsx`
  - スライドパズル: タイルをタップして動かす（`touch-manipulation`）。なぞりは受けない: `frontend/src/games/slide-puzzle/ui/board/SlidePuzzleBoard/SlidePuzzleTile.tsx`
- [事実] ハミルトン路は、画面の端から始まるタッチが戻るジェスチャーに取られるため、左右の余白を 16px にした。実機（iOS Safari／Android Chrome）では確かめていない: `docs/パズル/導入調査/ハミルトン路/ハミルトン路実装前提調査.md` §9.4・§18（段04 の行）
- [事実] 認識合わせの見本は、押した時点で駒の行き先を BFS で全部求め、指のずれを足した位置に最も近い行き先へ駒を置く（案 A）。盤には `touch-action: none` を付けている: `認識合わせのページ`
- [事実（計算）] 1マスの値はクラス名の寸法からの計算で、ブラウザーでは描いていない。ハミルトン路 8×8 の 320px での計算値 36.0px は、実装前提調査 §18 で画面確認した 36.0px と一致した: `docs/パズル/導入調査/ハミルトン路/ハミルトン路実装前提調査.md`
- [推測] Safari のバーが出たときの高さ（320×460・375×548・390×664）は目安で、端末・iOS の版・バーの状態で変わる。実機か Playwright の端末プロファイルで確かめられる。
- [推測] 合成した指は、画面を見ながら直す人の指より悪い条件になる（駒を見て止める位置を直すことを入れていない）。ねらい通りの率の絶対値は低めに出ているとみる。案どうしの差は、押し込みのときの違い（A だけが回り込む）として計算の仕組みから説明でき、条件を変えても向きは変わらなかった。
- [推測] 1マス 60px は約 9.4mm（iPhone の 1pt ≒ 1/163 インチとして換算）。指の腹（ハミルトン路の PoC で直径約 60px と仮定）で1×1の駒は隠れる。なぞる間は駒を浮かせて見せる（影など。見本の `.drag` と同じ）と、隠れた駒が動いていると分かる。
- [外部知見] Apple の Human Interface Guidelines は、押せる部品の大きさを最小 44×44pt としている。320×460 の目安で枠ありの 41px はこれを下回る。

## 仮決定の候補

- 入力処理: **C（隣接だけ）**。指のいるマスをハミルトン路と同じ不感帯（縁から 0.15）と補間（1/6 刻み）で1マスずつ追い、駒は指のマスが隣で空いているときだけ移る。斜めは主な向きの角を先に試し、塞がれていれば反対の角を通る。回り込ませない。指が2マス以上離れたら、隣に戻るまで待つ。 / 理由: (1) 塞がれた向きへ押し込んでも駒が跳ばない（A 3.0〜4.7%、C 0〜0.2%）。(2) 押し込んでから曲がったときも、離れた所まで行く率が最も低い（1.1%）。(3) ねらい通りの率と曲がる手の率は A・B と同じ。(4) 定数と考え方がハミルトン路の `finger-trace.ts` と同じで、同じ説明・同じ調整で済む。 / 比べた案: A 見本の最も近い到達先（押し込みで回り込んで跳ぶ）、B 追いかけ（押し込みは跳ばないが、押し込んだ後に曲がると回り込みやすい） / 覆したときに作り直す範囲: `ui/` のなぞりの入力処理とそのテスト。ルール（`puzzle/`）と手数は変わらない。
- 手の数え方: **同じ駒が続くなぞりは、指を離してもまとめて1手と数える。** 待ったは、まとめた1手を1回で戻す。 / 理由: (1) 最短手数は解法器の「同じ駒の連続移動 = 1手」で出し、解いた後に見せる。ここを揃えないと、最短の道順で解いても手数が最短より多くなる。(2) 横刀立馬の最短解の 11% は1手の中で曲がる。一度離してから曲げた人が損をしない。(3) 合意の括弧書き（同じ駒の連続した移動は1手）と合う。 / 比べた案: なぞり1回を1手にする（合意の「指を離すまでが1手」の文字どおり。実装は簡単だが、最短との食い違いが起きる） / 覆したときに作り直す範囲: session の手数の数え方・待ったの単位、結果画面の手数の比べ方、そのテスト。**合意の言い回しに関わるので、人間の確認を勧める。**
- 待った・盤面を戻すの置き場所と呼び名: 既存と同じにする（待ったは下の操作欄、盤面を戻すは見出しのメニュー。呼び名は `PLAY_OPERATION_LABELS`）。認識合わせの見本の「1手戻す」「最初から」は呼び名を変える。 / 理由: 全ゲームで同じ位置・同じ語で、新しい部品が要らない。 / 比べた案: 盤の下に2つのボタンを並べる（見本と同じ。下の操作欄の高さを変えずに置けるが、ほかのゲームと違う並びになる） / 覆したときに作り直す範囲: プレイ画面の footer と遊び方の文言。
- 左右の余白: 16px（`px-4`）。 / 理由: 端の戻るジェスチャーをよける（ハミルトン路と同じ）。320×640 で 1マスが 74px から 72px になるだけ。 / 比べた案: 12px（`px-3`。パーキングジャム・氷の床と同じ） / 覆したときに作り直す範囲: main のクラス1か所。
- 押し場所: 駒を押せる範囲は、見た目の隙間に関わらず駒のマスの全体にする。空きマスを押しても何もしない。主でない指は無視する。 / 理由: 狙いが縁に寄ると、別の駒に落ちる率が上がる（σ8px で、縁から0.15マス内側をねらうと 2.0%、0.3マス内側なら 0.2%）。押せる範囲を見た目より狭めない。 / 比べた案: 見た目の駒の形だけを押せる範囲にする / 覆したときに作り直す範囲: 盤面の当たり判定。
- 盤の枠と出口の大きさ: 縦が短い画面では高さで決まるので、枠と出口の印は小さく（計算の例では四方0.15マス＋下0.3マス）し、プレイ画面の確認は 320×568 と 375×548 程度の高さでも行う。 / 理由: 枠を足すと 320×568 で 68px から 61px になる。 / 比べた案: 枠を描かない（出口が分からない） / 覆したときに作り直す範囲: 盤の描画の寸法。

## 確かめていないこと

- iPhone 実機（iOS Safari）で、なぞる途中にページが動かないか、端の戻るジェスチャーやプル更新と競合しないか、長押しの選択が出ないか: 実機を使えない。ブラウザーでの画面確認もしていない（計算と Python の模擬だけ）。実装の画面確認と最終レビューで、合意の「まだ分からないこと」として確かめる。
- 1マスの値をブラウザーで描いた値: 盤の枠・出口の描き方が決まっていない。実装の画面確認で 320／360／375／390px 幅と、短い高さで測る。
- 人の指で、C の不感帯（0.15）と補間がちょうどよいか: 合成の指だけで比べた。画面を見て直す動き、片手で親指を使うときの癖は入れていない。
- 80手前後の問題をスマホで最後まで遊んでもらえるか（合意の「まだ分からないこと」）: この観点の計測では扱っていない。1手の最大は横刀立馬の最短解で2マス、曲がる手は 11% と分かっただけ。
- 「戻しても手数は減らさない（スライドパズルとそろえる）」がスライドパズルの今の振る舞いと合うか: スライドパズルには待ったが無く、盤面を戻すだけがある（`PlayableSlidePuzzle` に待ったが無い）。手数の扱いはこの観点の外なので調べていない。
