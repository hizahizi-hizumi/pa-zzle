## 2. 守る遊びの核

このパズルで残すべき体験は、**どこでも止まれるわけではない駒を、止まれる場所だけを足場にして、ゴールで止める道筋を盤面から読むこと**である。

面白さの中心は、駒を動かして結果を見ることではない。

- 今の位置から各方向へ滑ったとき、どこで止まるかを読む
- ゴールで止まるには、どの方向からどの位置で滑り込む必要があるかを逆算する（ゴールの先に止め役の岩や壁があるか）
- ゴールへ向かう素直な手が通過や行き過ぎになり、わざと遠回りして足場を作る必要に気づく
- 一度入ると戻れない場所を、入る前に見抜く

pa-zzle では、UIがこの読みを代行しない。どこで止まるかの先出し、正解の道筋の表示、最短手数の常時表示は通常のプレイで出さない（§8.4）。

### 2.1 ふつうの迷路との違い

| | ふつうの迷路（[迷路調査](../迷路/迷路調査.md)） | 氷の床迷路 |
| --- | --- | --- |
| 1手の移動 | 隣の1マス | 岩か外壁にぶつかるまで何マスでも |
| 止まれる場所 | 通路ならどこでも | 岩の手前と壁際だけ |
| 見えているもの | 道が分岐して先が見通しにくい | 盤面は全部見えている |
| 考えどころ | 道をたどる | 止まれる場所を逆算する。わざと遠回りする |
| 戻ること | 逆方向へ進めば戻れる | 逆方向へ滑っても元の位置へ戻るとは限らない |

最後の行は、待ったの要否（§9）と詰み（§8.3）に効く。ふつうの迷路では「来た道を戻る」こと自体が探索の一部で専用の待ったは要らなかったが、氷の床迷路では逆方向へ入力して元の停止点へ戻れない手が4〜5割ある（事実（実験）。スマホ操作PoC）。

### 2.2 GAME.md の原則への対応（AI案）

| GAME.md の原則 | 氷の床迷路での具体化 |
| --- | --- |
| そのパズルならではの面白さを強める | 滑る・ぶつかって止まるという動きそのものを、手応えとして返す。止まった位置と通った跡が盤面で読めることを優先する |
| 盤面が主役 | 盤面を画面の中心に大きく置く。手数・時間はヘッダーに控えめに置き、最短手数や評価はプレイ中に出さない（`DESIGN.md` §3 プレイ） |
| 盤面で分からせる | 「動けません」「ゴールを通過しました」のような文はプレイ中に出さない（参考デモは文で知らせている）。成立しない方向は駒の小さな揺れ、通過は滑った跡、クリアは駒がゴールで止まる演出で返す（§8） |
| 内部のデータ構造をそのまま描かない | 格子と記号ではなく、氷の床・岩・外壁・駒・ゴールとして描く（§6） |

## 3. 初期実装へ採用するルール

### 合意済みのルール

- 盤面は格子。駒が1つ、ゴールが1マス。
- 上下左右のどれかを選ぶと、駒は岩か外壁にぶつかるまで止まらずに滑る。プレイヤーは止まる位置を選べない。2マス先に岩があるときなど、結果として1マスで止まる滑りは起こる（8×8で到達停止点からの滑りの25.3%。供給実験）。
- ゴールのマスで止まったらクリア。ゴールを通過しただけではクリアにならない。

### 床・障害物の種類

**初期実装は氷と岩だけにする（AI案）。** 盤面のマスは氷か岩で、外壁は岩と同じく滑りを止める。開始位置とゴールは氷のマスに置く。

供給実験は (a) 氷と岩だけ、(b) +ふつうの床、(c) +穴、(d) +矢印床を同じ枠組みで比べた。詳細は [供給実験「床の種類の比較」](氷の床迷路供給実験.md#床の種類の比較) を参照する。要点は次のとおり。

| 種類 | ルール上の意味 | 比較の結果 | 扱い |
| --- | --- | --- | --- |
| 氷と岩だけ | 滑る床と止める岩 | 5段階すべて出る。説明は2文で済む。見分けるのは氷・岩と駒・ゴールだけ | 採用 |
| ふつうの床 | その上で駒が止まる | 供給と難易度の分布は (a) と同程度。止まる場所を増やし、「どこで止まれるか」を読む挑戦を薄める。氷との見分けを色・質感に頼る | 拡張候補 |
| 穴 | 落ちたら失敗 | 採用率が下がり（8×8で78.9%）、ランダム操作の48.9%が落下で終わる。難しさを先読みでなく失敗の罰として増やす。穴と岩・駒を取り違えやすい | 拡張候補 |
| 矢印床 | 乗ると向きが変わる | 循環する盤面の除外が要る（8×8で3.9%）。説明と、1マス約36〜45pxでの向きの読み取りの負担が増える | 拡張候補 |

追加の床は、問題供給を改善せず、高難度の供給源にもならない（レベル5の割合は (a) の±1.6ポイント以内）。初期版を遊んで単調と分かった場合の拡張候補として残し、入れるときは種類ごとに難易度分析が扱う解法過程を広げてから入れる（供給実験）。

### 初期実装から外すもの（AI案）

- ふつうの床・穴・矢印床（上の表）
- 駒が複数ある、駒同士がぶつかる変種
- 鍵・扉・スイッチなど、盤面の状態が操作で変わる仕掛け（割れる氷を含む）。状態が駒の位置だけでなくなり、難易度分析・視覚・説明のコストが同時に増える
- 時間制限・移動中の割り込み操作など、反応の速さを問う要素
- 利用者が問題を作る機能

## 4. 品質条件

pa-zzle で問題として成立させる条件（AI案。供給実験と難易度PoCの提案に沿う）。

1. ゴールは、開始位置から到達できる停止点の中から選ぶ（可解を構成で保証する）。
2. 開始位置とゴールは別の氷のマスに置く。
3. 最短1〜2手の問題は出さない。最短15手以上の問題も、手数（作業量）が多いだけになりやすいので提供範囲外とする。計画深さ7以上の問題は評価不能としてどのレベルにも入れない（§11）。
4. 無関係な岩（到達できる停止点からのどの滑りも止めず塞がない岩）は取り除いて正規化する。8×8で85.1%の問題にあり、岩の21.6%を占める。取り除いても停止点間の移動は変わらない（1,500盤面で変化0件）。
5. 回転・反転で同型の問題を、同じ問題集の中で重複させない（§5.4）。

次は要求しない。

- **最短の道筋が1つであること**: クリア条件は道筋によらず、最短手数は幅優先探索で一意に決まるので、評価（§13）にも要らない。最短解が一意の問題はもともと8×8で93.7%ある。難易度の分析（計画深さ）も一意性を使わない。
- **ゴールの先に止め石（岩）があること**: ゴールを外壁だけで止める問題は28〜43%ある。外壁で止まるゴールでも通過や遠回りは起こるので、止め石の有無ではなく難易度の分析で扱う。
- **ゴールを通過する滑りがあること**: レベルと単調な関係が無かった（8×8でレベル1の36%〜レベル3の63%）。分類には使わず、試遊で体感と食い違う問題を探す補助の観点として残す（難易度PoC）。
- **詰みが無いこと**: 詰みは上のレベルほど多く、除くと高いレベルの供給と「戻れない場所を見抜く」挑戦を同時に削る（§8.3）。

無関係な岩を除いた盤面と、除かずに残した盤面のどちらが自然に見えるかは試遊で確かめる（§17）。

## 5. 問題identityと供給方式

### 5.1 事前生成問題集で供給する

ADR-0001 により、プレイ画面の URL は `/puzzles/<game>/play/<難易度>?problem=<問題ID>` とし、問題 ID は identity 全体からの一方向のハッシュ（`frontend/src/games/problem-id.ts` の `createProblemId`）である。問題 ID から問題へは問題集の索引（`createProblemPoolIdLookup`）でしか引けない。今の7ゲームはすべて `problem/problem-pool.json` を持つ（事実（リポジトリ））。

生成は軽い（8×8の1盤面の生成とBFSで約0.16 ms、全ゴール候補の難易度分析込みで約8.6 ms。Python PoC）。ただしレベルは生成後の難易度分析で決めるので、seed から生成し直す方式では問題の同一性が生成器だけでなく分析器の版にも依存する。1問の中身は小さい（8×8なら岩配置64ビットと開始位置・ゴールで約10バイト）。

したがって、**レベルごとの問題集を事前生成して同梱し、問題集に盤面そのものを持つ**（供給実験の推奨。盤面を問題集に持つ点はリフレクションと同じ形）。プレイ時には生成・難易度分析をしない。

生成は、岩をランダムに置き、開始位置から停止点のBFSを1回行い、到達できる停止点からゴールを選ぶ方式（供給実験のG1）を使う。ゴールから逆向きに手順を組む方式（G2）は近道ができて意図が崩れ、最短手数を伸ばす局所探索（G3）はレベル5の供給を増やさないので使わない。岩密度は18〜26%で長い問題が出やすく、実験は20%に固定した。

### 5.2 identity の形（AI判断（仮決定））

`.claude/rules/game-structure.md` の問題契約と、`games/problem-id.ts` の `RecordedProblemIdentity`（`generatorVersion`・`seed`・`conditions`）に揃える。名前の `<Game>` はゲーム ID `ice-floor-maze` の型名 `IceFloorMaze`（§15）で置き換える。

```text
<Game>Problem = {
  width, height, // 盤面の列数・行数。縦長（height ≥ width）を含む（§11）
  rocks,         // 岩の位置。無関係な岩を除いた正規化盤面
  start, goal,
}

<Game>ProblemIdentity = {
  generatorVersion: "1",
  seed: ProblemSeed,       // 正規化盤面（岩・開始位置・ゴール）の符号化
  conditions: { width, height },
}

<Game>PooledProblem = <Game>IdentifiedProblem & {
  optimalMoveCount: number,
  // 速さの基準時間に使う作業の量（§13.4）
}
```

- identity には無関係な岩を除いた正規化盤面を使う。同じ盤面は同じ問題 ID になり、どの岩も意味を持つ盤面だけが問題になる。identity から盤面を復号できるので、問題の復元に生成器を走らせない。
- `<Game>Problem` は1問を遊ぶのに要る情報だけを持つ。最短の道筋や探索の履歴は持たず、`optimalMoveCount` のような意味のある値へ縮約する（game-structure.md「問題契約」）。
- 採点に盤面の大きさを使うなら、`<Game>RecordedProblemIdentity` は `RecordedProblemIdentity<{ width: number; height: number }>` とし、生成器の版が違う記録からも読めることを確かめる（スライドパズルの `SlidePuzzleRecordedProblemIdentity` と同じ）。
- 問題集を作る生成スクリプトの乱数は `games/problem-seed.ts` の `ProblemRandom`（`createProblemSeededRandom`）で受け、並べ替えは `shuffleProblemValues` を使う。

### 5.3 問題集の項目（AI案）

1問を、正規化盤面の符号化・盤面の大きさ・最短手数・速さの基準時間に使う作業の量の組で持つ。生成スクリプトは `frontend/scripts/generate-<game>-problem-pool.ts` とし、全問を identity から復号して、可解・最短手数・分類・同型重複・無関係な岩が無いことが問題集と一致することを確かめる検証を持つ。

各レベルの問題数は実装時に決める。供給は足りる。8×8で最も希少なレベル5でも、Python PoCで1問約34 msで得られ、各レベル数千問の確保は数分以内で済む（難易度PoC）。各レベル1,000問を同梱しても約50KBと見積もる（供給実験）。最も広い12×14では1問が岩配置168ビットと開始位置・ゴールで約25バイトになり、8×8の約2.5倍になる（推測）。広い盤面でも、レベル5は盤面の66.2%から1問約83 msで得られる（難易度PoC「追加計測: 盤面の大きさと形」）。

段04で確定（事実（実測））: 各レベル500問、計2,500問。1問は `[seed, 幅, 高さ, 最少手数]` で、`seed` は identity の盤面の符号。問題集の JSON は 138,982 bytes（gzip 36,333 bytes）、本番ビルドの JS は +119.7 kB（gzip +37.95 kB）。全問の検証（分類・最少手数・形・無関係な岩・同型）はテスト（`problem-selection.test.ts`）が持つ。詳細は [氷の床迷路難易度](氷の床迷路難易度.md) §5。

### 5.4 同型除外

盤面の形ごとに、形を変えない変換で正規化したキーで重複を除く（AI判断（仮決定））。キーは無関係な岩を除いた盤面から作る。

- 正方形（8×8）は回転・反転の8通り（リフレクションと同じ）。
- 縦長の長方形は、恒等・左右反転・上下反転・180度回転の4通り。90度・270度の回転は縦横が入れ替わった横長の盤面になる。横長の盤面は出さない（§11）ので、それらは問題集に現れず、同型として扱う必要がない。左右反転と上下反転の組み合わせが180度回転なので、4通りで閉じる。
- 形が違う問題（9×12 と 10×13 など）は同型になり得ないので、キーは形ごとに分けてよい。identity の `conditions` が形を持つ。
- 方向に意味のある床（矢印床）を将来入れるときは、反転・回転に合わせて矢印の向きも変換する（調査コードの `transform`・`transform_rectangle` が扱う）。

実測では、最短3手以上・最短6手以上のどちらでも、各サイズ2,000問で完全一致・同型の重複は0件で、レベル別に採った問題でも、正方形・長方形のどの形でも0件だった（供給実験・難易度PoC）。問題集の作成時の保険として入れる。

## 6. 視覚表現

最低条件（AI案）。

- 氷の床・岩・外壁が、色だけでなく形と質感で見分けられる。外壁も「ぶつかって止まる面」として岩と同じ意味に読める。
- ゴールは「ここで止める」場所として、通り道の床と見分けられる。開始位置は印を残さなくてよい（駒がそこにいる）。スマホ操作PoCでは、ゴールを氷の上の輪と中心の点、駒を白い縁取りの円にして、12×12・320pxとグレースケールでも見分けられた。
- 駒は盤面のどのマスの上でも、跡やゴールの印と重なっても見失わない。
- 直前の滑りで通ったマスを跡として示し、止まった後も残す。跡は今の盤面と直前の操作の事実で、先の展開を示さない（SPEC-017 の状態の知らせ）。
- ゴールを通過した滑りは、ゴールの前後に続く跡で「通ったが止まっていない」と読める（§8.2）。
- 12×12 級ではマスの斜めの光沢など細かい装飾が雑音になる。氷の模様は小さいマスで省ける形にする（スマホ操作PoC）。
- 将来、床・障害物を増やすときは、駒・ゴール・穴を同じ「暗い円」の系統にしない、ふつうの床とゴールの背景を同じ色系統にしない（スマホ操作PoCで取り違えた例）。

動き（AI案）。

- 滑りは距離に比例する時間で、等速で動かす。目安は「基準 40〜50ms + 1マス 30〜35ms、上限 380〜420ms」（スマホ操作PoC）。一定の短い時間（150ms）や加減速では、長い滑りの途中のマスが描かれず、通過が動きから読めなかった。時間と緩急はゲーム固有の名前付き定数とし、`DESIGN.md` §12 のとおり共通UIの遷移時間（`--duration-*`）に合わせない。
- 動きを減らす設定では滑りもクリア演出も動かさない（game-structure.md「クリア演出」）。この設定でも跡は残るので、通過は伝わる（スマホ操作PoC）。
- クリア演出は `@/lib/motion` の `playAnimations` で再生し、完了の決め方と時間（`completion`・`reducedMotionHoldMs`・`unanimatedHoldMs`）はゲームが渡す。

ピクトグラムは `.claude/skills/design-game-pictogram` の手順で作る。氷の床・岩・駒と、滑った跡の折れ線が候補になる（推測）。

難易度選択のプレビューは本番の盤面描画部品で描き、上位レベルが下位の構成を含み挑戦の差で違いを見せる（`DESIGN.md` §3 難易度選択）。見せる差の中心は計画深さで、手数の長さではない。上のレベルほど広い盤面まで許す（§11）ので、盤面の広さの違いは計画深さの差に添えて見せる。低いレベルはゴールへ近づく手を重ねれば止まれる盤面、高いレベルはゴールが見えていても一度離れて別の方向から入り直す盤面にする（難易度PoCの代表問題が素材になる）。

## 7. 操作方式

必要な操作は「方向を1つ選ぶ」だけで、盤面の特定のマスを狙う必要はない。

**主操作は盤面スワイプ、代わりの操作は常に表示する方向ボタンとし、PCでは矢印キーも受ける（AI案。スマホ操作PoC）。** 駒の周りのタップは採らない。

| 方式 | 扱い | 根拠（スマホ操作PoC） |
| --- | --- | --- |
| 盤面スワイプ | 主操作 | 320px・12×12 と 390px・10×10 で、角度のずれ ±40° まで 40/40 が正しい方向。18px 未満の揺れとタップでは動かなかった。盤面の外の余白から始めたスワイプも認識した |
| 方向ボタン | 代わりの操作。常に表示 | 48px 角・逆T字形で、ずれ 9px でも 40/40 が正しい方向。操作欄 112px に収まり、盤面の大きさを削らない。片手でも押しやすい |
| 駒の周りのタップ | 採らない | 指で隣のマスと駒が隠れる。「タップしたマスへ行く」と受け取られやすいが、実際は通り過ぎる |
| キーボードの矢印キー（PC） | 代わりの操作 | スライドパズル（`SlidePuzzlePlay.tsx`）の `keydown` の扱いに倣う |

- スワイプは盤面だけでなく、プレイ画面の盤面の領域全体（盤面の外の余白を含む）で受け、`touch-action: none` を付ける。390×844 では盤面が上側に寄るので、下側の余白でも受けると親指で操作できる。
- 方向は、指が閾値（18px。パーキングジャムの `SWIPE_THRESHOLD` と同じ値）を超えた時点で1回だけ確定し、指を離すまで待たない。1回の指の動きで動かせるのは1手だけにする。
- 方向ボタンは既存の `UndoButton`（`size-12`、48px）と同じ大きさにし、待ったと並べる。
- スワイプを採っても、単一ポインターで操作できる代わりの操作（方向ボタン）を持つ（迷路調査、WCAG の Dragging Movements）。
- 操作の callback props は入力手段ではなく操作の意味で名付ける（例: `onSlide(direction)`。game-structure.md「プレイ画面と結果画面の共通契約」）。

### 滑っている途中の連続入力

**即時方式にする（AI案。スマホ操作PoC）。** 入力した時点で session を進め、受け付けた入力を捨てない（NFR-014）。表示中の滑りは終点へ飛ばしてから次の滑りを始める。クリアした後の入力は受け付けない。

- 即時方式は、素早い3手の入力で最終位置が入力どおり（各10/10）で、表示の遅れは最後の1手分（約200ms）だった。
- 滑っている間の入力を捨てる方式は、入力した手の3分の2を失った（5/10）。誤った方向への入力と同じく取り返しがつかないので採らない。
- 待ち行列方式は表示が最大約0.5秒遅れ、素朴な実装では入力の順序が入れ替わった。
- CSS の transition の行き先を途中で差し替えると、駒が滑りの途中から次の終点へ斜めに動き、岩をすり抜けて見える。これは使わない。

盤面へ渡す操作の結果は、スライドパズルの `SlidePuzzleOperation` やパーキングジャムの `ParkingJamOperation` に倣い `play/` から渡す。中身は滑りの始点・終点・通ったマス・成立しなかった方向などとし、`ui/` で滑りの経路をルールから計算し直さない。

## 8. 誤りの扱い（状態の知らせと補助）

SPEC-017 に従い、今の盤面とルールだけから分かることを状態の知らせ、正解や先の展開を使うものを補助とする。

### 8.1 成立しない方向

すぐ隣が岩か外壁で1マスも動けない方向（スマホ操作PoCの「すぐ壁」）を選んだ操作は、成立しないものとする（AI案）。到達できる停止点では平均約1.7方向がこれにあたる（8×8の平均出次数 2.31。供給実験）ので、頻繁に起こる。

- 盤面を変えず、手数にもミスにも数えない（スライドパズルで空白と同じ行・列にないタイルを選んだ操作と同じ扱い。SPEC-011）。
- 成立しなかったことは、駒を入力方向へ少し押して戻す揺れで返す（`@/lib/motion` の `playRejectionShake`。揺れ方と時間はゲームが渡す）。SPEC-017 の「操作が成立しなかったこと」にあたる状態の知らせ。押し戻しはマスの割合で決めると小さい盤面で3〜4pxになり見えないので、目安5〜6px以上を確保する（スマホ操作PoC）。

### 8.2 ゴールの通過

通過は無効（合意済み）。通過は手数としては数える（成立した滑りなので）が、ミスには数えない（AI案）。止まった位置がゴールでない、という今の盤面の事実だけを示し、文では知らせない（`GAME.md`）。

通過は、滑った跡がゴールの前後に連続して残ることで伝える。跡は止まった後の静止画でも、動きを減らす設定でも読める。スマホ操作PoCでは駒がゴールを通る時刻にゴールの輪を一度脈打たせる演出も試したが、跡より弱かった。これを足すかは、クリアに近いと誤読させないかを含めて試遊で決める（§17）。いずれにしても、遊び方（SPEC-016）で「止まらないとクリアにならない」ことを図で示す。

### 8.3 詰み（ゴールへ戻れない位置へ入る）

到達できる停止点のうち、そこからゴールへ二度と到達できないものを詰みと呼ぶ（供給実験と同じ定義）。

詰みは構成上避けられない（事実（実験）。供給実験）。

- 8×8で28.2%、10×10で32.1%の問題に、到達範囲の詰みがある。約1割の問題は最初の1手で詰みに入れる。
- 難易度の仮レベルでは、詰みがある問題の割合はレベル1の21%からレベル5の45%へ増える（8×8。難易度PoC）。
- 方向を一様に選び続ける操作では、8×8で約1〜2割の試行がゴールより先に詰みへ入る。
- 逆方向へ入力しても元の停止点へ戻れない手が4〜5割ある（スマホ操作PoC）。

詰みのない問題だけに絞る案は、高いレベルの供給と「戻れない場所を入る前に見抜く」挑戦を同時に削るので採らない。詰みに入ってもプレイヤーは動き続けられるので、自力で戻る手段として待った・盤面を戻す・リセットを必ず提供する（§9）。

詰みを画面で知らせるかは、ユーザーが判断を保留したので AI判断で仮決定する。選択肢は次のとおり。

| 案 | 内容 | 根拠・懸念 |
| --- | --- | --- |
| 知らせない | 盤面だけで気づかせる | FR-015。詰みを見抜くことは読みの一部（§2）。気づかずに滑り続ける時間が長くなり得る |
| ウォーターソートと同じ範囲で知らせる | 今の位置から行けるどの位置も今の位置へ戻れ、その中にゴールが無いとき（閉じ込められたとき）だけ知らせ、待ったと盤面を戻すへ導く。この先いずれ詰む位置でも、まだ戻れない先へ進める手がある間は知らせない | SPEC-009 の手詰まりと同じ線引き（`water-sort/puzzle/deadlock.ts` の強連結成分の判定）。SPEC-017 の「今の盤面からもう進められないこと」にあたる |
| 詰みへ入った時点で知らせる | ゴールへ行けない位置へ入った瞬間に知らせる | この先の手詰まりを先回りして示すので補助にあたる（SPEC-017）。採るなら補助として仕様に明示する必要がある。供給実験は、先読みの挑戦を弱めるかを仕様検討に残した |

**AI判断（仮決定。ユーザーレビュー待ち）: ウォーターソートと同じ範囲で知らせる。** 今の位置から行けるどの位置も今の位置へ戻れ、その中にゴールが無いとき（閉じ込め）だけ、そのことを知らせ、待ったと盤面を戻すへ導く。停止点の移動のグラフでは、今の位置の強連結成分が出口を持たず、ゴールを含まないことにあたる。

閉じ込めの頻度を測った（事実（実験）。[難易度PoC「閉じ込めの頻度」](氷の床迷路難易度PoC.md#閉じ込めの頻度)）。

- 閉じ込めは珍しくない。詰みがある問題は 8×8 で25%、提供する最大の12×14で37%あった。方向を一様に選ぶ素朴な操作では、試行の17〜25%が詰みに入り、レベル5では28〜52%に上がる。詰みに入った試行のほぼすべて（98%以上）が閉じ込めに至った。
- 詰みの停止点の7〜8割は、それ自体が閉じ込めである。閉じ込めの領域は中央値で3〜4停止点と小さく、詰みに入った時点で閉じ込めになる割合は71〜84%だった。多くの場合、詰みに入った手の直後に知らせることになる。
- 残りの2〜3割の詰みの停止点は出口のある循環の中にあり、まだ別の位置へ進める。そこでは知らせず、閉じ込めに至るまで（p90で3〜11手）滑り続けられる。

理由:

- 知らせるのは「今の位置から行ける範囲」という今の盤面の事実で、SPEC-017 の「今の盤面からもう進められないこと」にあたる状態の知らせである。ウォーターソートの手詰まりと同じ線引きなので、ゲームをまたいで知らせの意味が揃う。
- 閉じ込めの領域は小さく、数手滑れば確かめられる事実を早く伝えるだけで、先の展開を示さない。「戻れない場所を入る前に見抜く」挑戦（§2）は入る前の読みにあり、入った後の知らせはそれを先回りしない。
- 閉じ込めは素朴な操作で2割前後、上のレベルでは3〜5割の試行に起きるので、知らせない案では、閉じ込められたことに気づかないまま滑り続ける場面が少なくない（推測）。

レビューで見てほしい点: 詰みに入った直後に知らせることが多いので、実際には「詰みへ入った時点で知らせる」案に近く感じられる。読みの手応えを損なうなら、知らせない案へ戻す。人間はランダム操作より先を読むので、実プレイで閉じ込めに至る頻度はこれより低いと見込む（推測）。

判定は `puzzle/` に置き、毎手の位置から行ける停止点の強連結成分で求める（到達できる停止点は 12×14 でも中央値39個なので、探索量の上限は要らない見込み）。表示はウォーターソートの `water-sort/ui/WaterSortPlay/DeadlockNotice.tsx` と同じ役割の部品を氷の床迷路の `ui/` に持つ。別ゲームの実装は import しない。

### 8.4 採用しない補助（AI案）

- **止まる位置の先出し**（方向を選ぶ前に、各方向へ滑ったら止まる位置を示す）: 今の盤面とルールから分かることなので状態の知らせの形はとれるが、このパズルの読みの中心（§2）を置き換える。リフレクションでは光路の表示が試し置きを促す懸念を本実装まで持ち越した。氷の床迷路では最初から出さない。
- **答えを見る・次の一手のヒント**: 参考デモにはあるが、FR-015 により通常のプレイで出さない。既存ゲームにもヒントは無い。
- **最短手数のプレイ中の表示**: 参考デモは「最短 N 手」をプレイ中に出しているが、評価の詳細はプレイ中に出さない（`DESIGN.md` §3 プレイ）。スライドパズル・ウォーターソートもプレイ中は手数と時間だけを出す。結果画面で最短との差として示す（§13）。

## 9. 待った・盤面を戻す・リセット・ヒント

SPEC-007 の4つの操作から、どれを提供するかをパズル仕様で決める。

| 操作 | 提供 | 理由 |
| --- | --- | --- |
| 待った | する（必須） | 詰みが3割前後の問題にあり、逆方向へ滑っても元の停止点へ戻れない手が4〜5割ある（§8.3）。ふつうの迷路と違い、盤面の操作だけでは1手前へ戻れない。リフレクションで待ったを削った理由（置いたピースを直接動かせば1手戻せる）が成り立たない。すぐ押せる位置に置く（§7） |
| 盤面を戻す | する（必須） | 駒を開始位置へ戻す。同じプレイの続きとして経過時間と計数を引き継ぐ |
| リセット | する（必須） | 同じ問題の新しいプレイ |
| 別の問題 | する | 全ゲームが提供する（SPEC-007） |
| ヒント | しない | §8.4 |

- 難易度の基準とするプレイも、待った・盤面を戻すを使える状態とした（難易度PoC。§11）。
- 待った・盤面を戻すを評価でどう扱うかは §13 で決める。
- 待ったの履歴は位置の列で持てる（ウォーターソートの `history` と同じ）。

## 10. クリア条件

1回の滑りが止まった位置がゴールのマスであれば、その時点でクリアとする。滑りの途中でゴールを通過しても、止まった位置がゴールでなければクリアにしない。

氷と岩だけの初期実装では、駒が止まるのは、滑る方向の次のマスが岩か外壁のときだけである。床・障害物を拡張するときも「止まった位置がゴールか」で判定し、新しい床ごとに「止まる」の定義（ふつうの床ならそのマスで止まる、矢印床なら向きを変えた後に最終的に止まったマス）を決める。

## 11. 難易度

[氷の床迷路難易度PoC](氷の床迷路難易度PoC.md) の仮案を初期実装の第一候補とする。機械側の成立性は確認済みで、人間の試遊が残る。

### 基準とするプレイと挑戦

- **基準とするプレイ**: 待った・盤面を戻すを使える状態。ヒントは使わない。既存仕様は「待ったと盤面を戻すを使わないプレイ」を基準にしている（SPEC-009・SPEC-018）が、氷の床迷路では詰みが3割前後の問題にあり、戻す手段なしでは挑戦ではなく行き詰まりになるため（難易度PoC）。
- **挑戦**: 止まれる場所を何手先まで頭の中で繋いで、ゴールで止まる道筋を組み立てる必要があるか。これを**計画深さ**で測る。
- **計画深さ**: 今の停止点から k 手先までを読み、ゴールがあればそこへ、無ければ k 手先までの最もよい停止点（「近づく」＝ゴールとのマンハッタン距離、または「揃える」＝ゴールと同じ行・列で間に岩が無い位置を優先）へ向かう手を選び、待ったを使わず一度止まった停止点へは戻らない素朴な先読みプレイヤーが、解ける最小の k。2方針と同点時の方向優先順位4通りの最小値をとり、探索順による揺れを判定へ持ち込まない。待ったを使わずに先を読むプレイを測るので、試し滑りに頼る解き方は難易度の基準にならない。
- **規模の扱い**: 最短手数・盤面の広さ・岩の数はそれ自体では難易度にしない（`難易度.md`「挑戦ではない負担を難易度にしない」）。最短手数と計画深さの Spearman 相関は 0.19〜0.22 と弱く、最短9手以上の問題の58%は計画深さ1で解ける。最短手数は、レベル1・2の境界と提供範囲を決める補助にだけ使う。盤面の広さは、単独ではレベルを決めず、上のレベルほど広い盤面まで許す範囲として組み合わせる（下の「盤面の形との組み合わせ」）。

### 5段階（仮案）

| 区分 | 条件 | 体験の説明（仮） |
| --- | --- | --- |
| 提供範囲外 | 最短1〜2手、または最短15手以上 | 前者は挑戦がない。後者は手数（作業量）が多いだけになりやすい |
| 評価不能 | 計画深さ7以上 | 素朴な先読みモデルでは説明できない。難しいと推定せずレベル5へ入れない |
| レベル1 | 計画深さ1、最短3〜4手 | ゴールへ近づく手を選べば、短い手数で止まれる |
| レベル2 | 計画深さ1で最短5手以上、または計画深さ2 | 近づく手を重ねれば着くが道のりが長い。または2手先の止まり方を見ればよい |
| レベル3 | 計画深さ3 | 3手先の止まる場所まで読んで道筋を組み立てる |
| レベル4 | 計画深さ4 | 目先の近づく手が4手先まで報われない |
| レベル5 | 計画深さ5〜6 | ゴールが見えていても、一度離れて別の方向から入り直す道筋を5手以上先まで組み立てる |

- 8×8・1盤面1問の分布は、レベル1から順に 47.1% / 36.6% / 7.7% / 4.4% / 3.2%（評価不能 0.9%）。目的のレベルを得るときは1盤面のゴール候補をすべて分析して選べるので、レベル5でも盤面の25.0%から得られる。
- 計画深さとは別に作った試行手数（待った込みで近づく順に試す探索の手数）の中央値は、8×8でレベル1→5に 4 / 8 / 12 / 15 / 17 と単調に増えた。
- 遠回り・ゴールの通過・最短解の数はレベルと単調な関係が無く、分類に使わない（§4）。

### 盤面の形との組み合わせ（AI判断（仮決定）。ユーザーレビュー待ち）

盤面サイズを8×8に固定しても5段階すべてが現れる（難易度PoC）。一方、ユーザーから「10×10 では簡単すぎて面白くないのではないか」という指摘があり、上のレベルほど広い盤面を使う前提で、正方形（8×8〜14×14）とスマートフォンの縦長の画面に合う長方形（8×10〜12×16）を測った（[難易度PoC「追加計測: 盤面の大きさと形」](氷の床迷路難易度PoC.md#追加計測-盤面の大きさと形)）。形は「幅×高さ」（列数×行数）で書く。

測ったこと（事実（実験））:

- 盤面を広げても、ランダムな問題の7割前後は計画深さ1のままである（8×8 75%、12×14 71%、14×14 68%）。1問の読みが一様に深くなるわけではない。
- 深い問題は出やすくなる。計画深さ5以上は 8×8 の4.2% から 12×14 の8.4%、14×14 の11.2%へ増え、レベル5を選べる盤面は25.0%から66〜68%へ増える。
- 同じレベルの中では、到達できる停止点（各手で比べる止まり先）と試行手数が増える。レベル5の到達停止点の中央値は 8×8 の21から 12×14 の40へ、試行手数の中央値は17から28へ増える。最短手数の中央値は6から8へ2手増えるだけである。レベル1の試行手数はどの形でも中央値4、レベル2は8〜11で、ほとんど増えない。
- 評価不能（計画深さ7以上）は 0.9% から 3〜5% へ増えるが、大半は7〜10手読めば解け、10手でも解けない問題は1%未満。試行手数はレベル5と変わらない。

解釈（推測）: 盤面を広げると、計画深さ（何手先まで読むか）は同じでも、各手で頭の中で滑らせて比べる止まり先が倍になる。これは手数（作業量）そのものではなく先読みの挑戦を強める負担なので、上のレベルの盤面を広げる根拠になる（`難易度.md`「挑戦ではない負担を難易度にしない」の、挑戦を強める場合）。一方、盤面の広さだけでレベルを上げると、計画深さ1の長いだけの問題が上のレベルに入る。このため計画深さを主軸に保ち、盤面の形は「上のレベルほど広い盤面まで許す」範囲として組み合わせる（リフレクションの `reflection/difficulty.ts` の `reflectionLevelCombinations` と同じ作り方）。

仮決定:

| レベル | 計画深さ（主軸） | 盤面の形（幅×高さ） | 320×568 の1マス | 390×844 の1マス |
| --- | --- | --- | ---: | ---: |
| 1 | 1（最短3〜4手） | 8×8〜8×10 | 33〜36px | 45px |
| 2 | 1（最短5手以上）または2 | 8×10〜9×12 | 28〜33px | 40〜45px |
| 3 | 3 | 9×12〜10×13 | 26〜28px | 36〜40px |
| 4 | 4 | 10×13〜12×14 | 24〜26px | 30〜36px |
| 5 | 5〜6 | 12×14 | 24px | 30px |

- 提供する形は 8×8・8×10・9×12・10×13・12×14 の5つ。縦長（高さ ≥ 幅）だけで、横長は出さない。1マスの幅は §12。
- 隣のレベルと形を1つずつ重ね、範囲の両端を下げない。重なった形では計画深さでレベルが分かれる。
- レベル5は最も広い12×14だけにする。10×13 ではレベル4と5の試行手数の中央値が20と19で並び、レベル4と5の差が小さい（難易度PoC）。レベル5を広い盤面に寄せて、比べる止まり先の数でもレベル4と差をつける。12×14 のレベル5は盤面の66.2%から得られる。
- 判定の主軸は計画深さのままで、形は「そのレベルで許す範囲」として問う。組み合わせは基準表のデータとして持ち、分類コードへ埋め込まない。どのレベルの組にも当たらない問題は提供範囲外とする。
- 1つのレベルに形が2つあるときは、形ごとに同じ数ずつ問題集へ採る（段04で決定。[氷の床迷路難易度](氷の床迷路難易度.md) §5.1）。
- 評価不能（計画深さ7以上）は広い盤面でもどのレベルにも入れない（§4）。供給は評価不能を除いても足りる。提供範囲外（最短15手以上）も変えない（12×14 で0.9%）。

決めきれない点（レビューで判断してほしい）:

- **下限の画面を 320×568 にするか。** 320×568 では盤面の領域の高さが約340pxで、最大は12×14（高さで決まり23.9px）。360×640 を下限にすれば、レベル5を12×16（360×640 で25.4px）まで広げられるが、320×568 では20.9pxになり、14×14 と同じく読む余裕がない（スマホ操作PoC）。仮決定は 320×568 を下限にする案。
- **レベル1を 8×8 だけにするか。** 短い手数で止まる体験を小さい盤面に揃える案。仮決定は 8×10 まで許す案（レベル1とレベル2を形でも重ねる）。
- **縦長を使わず正方形だけにするか（8×8・10×10・12×12）。** 縦長は 320×568 では1マスを広げないが、360×780 以上の縦長の画面では余った高さを行に使え、同じ1マスの幅でマス数を増やせる。マス数が近ければ縦長と正方形で計画深さの分布に目立った差は無かった（難易度PoC）。仮決定は縦長を使う案。

### 残る確認（試遊）

難易度PoCの「難易度ゲートの判断」が挙げた次を、代表・境界問題をラベルを伏せて遊んで確かめる。

- レベル1→5で、先読みの深さが概ね増えると感じられること。
- レベル2にまとめた「深さ1で長い問題」と「深さ2の短い問題」が、同じ帯として違和感がないこと。
- レベル4と5の差が体感として区別できること（試行手数の差が8×8で2手、10×10で4手と小さい）。
- 同じレベルの狭い盤面と広い盤面（例: レベル4の 10×13 と 12×14）の体感がそろうこと。隣のレベルと重ねた形で、広い盤面の下のレベルが狭い盤面の上のレベルより難しく感じられる逆転がないこと。
- ゴールから逆向きに「どの岩で止まれるか」を考える解き方で、前向きだけのモデルが計画深さを過大評価しないこと。
- ゴールの通過・詰みの罠が、計画深さの外で体感難易度を大きく変えていないこと。

## 12. スマートフォン

[氷の床迷路 スマホ操作PoC](氷の床迷路スマホ操作PoC.md) で、pa-zzle のプレイ画面と同じ寸法の枠に盤面を置き、Playwright / Chromium（タッチ入力を有効にした headless）で 320×568 / 360×640 / 360×780 / 390×844 を確かめた。全条件で `pageerror` 0、意図しない `console.error` 0、failed request 0、横・縦のスクロールなし。

正方形の盤面の幅は画面幅で決まり、高さには余裕があった。方向ボタンを置いても操作欄は既存ゲームと同じ112pxに収まり、盤面の大きさは変わらない。

入力はスワイプと方向ボタンで、マスの大きさに依存しない。上限を決めるのは、止まる位置を行・列ごとに読む視認性である。スマホ操作PoCは、10×10（320pxで29px）を岩の並び・駒・ゴールを余裕をもって読める大きさ、12×12（320pxで24.2px）を氷と岩だけなら表示上は成立する大きさ、14×14（320pxで20.7px。駒15px・ゴールの輪12pxほど）を読む余裕がない大きさとした。

縦長の盤面を含めた1マスの幅は次のとおり（難易度PoC「追加計測: 盤面の大きさと形」。スマホ操作PoCの枠からの計算で、PoCの正方形の実測値を再現する）。

| 盤面 | 320×568 | 360×640 | 360×780 | 390×844 |
| --- | ---: | ---: | ---: | ---: |
| 8×8 | 36.2px | 41.2px | 41.2px | 45.0px |
| 8×10 | 33.4px | 40.6px | 41.2px | 45.0px |
| 9×12 | 27.8px | 33.8px | 36.7px | 40.0px |
| 10×13 | 25.7px | 31.2px | 33.0px | 36.0px |
| 12×14 | 23.9px | 27.5px | 27.5px | 30.0px |
| 12×16（範囲外） | 20.9px | 25.4px | 27.5px | 30.0px |
| 14×14（範囲外） | 20.7px | 23.6px | 23.6px | 25.7px |

**AI判断（仮決定。ユーザーレビュー待ち）: 320×568 で1マス24px程度を下限にし、提供する形を 8×8・8×10・9×12・10×13・12×14 とする（レベルとの対応は §11）。** これは前回の「基準は8×8、初期提供の上限は10×10」を置き換える。

- 縦長の盤面を使う。320×568 では盤面の領域の高さが約340pxしかなく、14行で24px程度になるので、高さは14行までとする。幅は12列までとする（320pxで24.2px）。
- 最大の12×14は 320×568 で23.9px（高さで決まる）、360×640 と 360×780 で27.5px、390×844 で30.0px。12×12 と同じく、氷と岩だけなら読める大きさと見込む（推測）。
- 12×16 と 14×14 は範囲外とする（320×568 で約21px）。360×640 を下限にする場合は12×16を使える（§11 の決めきれない点）。
- 迷路は15×15程度まで全体表示で成立したが、氷の床迷路では1手ごとに行・列の端までを読むので上限を下げる。
- 12×14 と縦長の盤面は、プレイ画面の段（段03）で実ブラウザで確かめ、320×568 の12×14（1マス23.7px）でも読めると判断した（下の「プレイ画面の実ブラウザ確認」）。上限は下げない。
- 方向ボタンや待ったなどのボタンは48px（`UndoButton` と同じ `size-12`）にする。

本実装でも 320 / 360 / 390px の幅で、スワイプ・方向ボタン・連続入力・クリアを Playwright で確認する。確認は ChatGPT 環境なら `docs/メモ/ChatGPT画面確認.md` と `scripts/chatgpt_playwright.py`、通常の開発環境なら Playwright / Chromium で、描画・操作・スクリーンショット・ブラウザエラーまで確かめる。実機（iOS Safari・Android Chrome）の画面端の戻るジェスチャーとの競合、120Hz 表示での見え方、45°付近の斜めのスワイプを判定しない範囲を設けるかは未確認で残る（§17）。

### 難易度選択と問題 ID の URL の実ブラウザ確認（段05。事実（実ブラウザ））

| スライドパズル（SPEC-011、`slide-puzzle/score.ts`） | 効率60: 最短手数 ÷ 総手数。総手数は盤面を戻す前の手も含む。最短の2倍で30点 | 40: 基準時間 = 盤面把握（3×3 5秒 / 4×4 10秒 / 5×5 15秒）+ 2秒 × 最短手数。基準の2倍で0点 | 盤面を戻すは別に減点しない。待ったは無い | 評価点・基準時間との差・最短手数との差（総手数 − 最短） |
| ウォーターソート（SPEC-009、`water-sort/score.ts`） | 効率40: クリアした盤面へ至った手数（待ったと盤面を戻すで消えた手を除く）の最短超過で線形に減点 | 40: 基準時間 = 5秒 + 1.5秒 × 色数 + 5秒 × 最短手数。基準の2倍で0点 | 正確性20: 手戻り（待ったで取り消した手と盤面を戻す前の手）の多さで減点。待った・盤面を戻すの回数そのものは減点しない | 評価点・基準時間との差・最短手数との差 |

共通の扱い。

- 基準時間は問題の作業量だけから決め、難易度そのものを理由にしない（SPEC-009・010・012・013）。
- 最短手数は問題集に持ち、記録の `performance` にも保存する。問題集から外れた記録も評価と自己ベストに残す（スライドパズルの `play-record.ts`、SPEC-012・013）。
- 評価点と評価段階は保存せず、記録した事実から今の規則で導く（SPEC-006）。

### 13.2 何を称えるか

ユーザーが判断を保留したので、AI判断で仮決定する（13.3）。論点は、称えるのが「最短の道筋で止める」ことか、「迷わず（試し滑りせずに）止める道筋を見つける」ことかである。

- 最短を称えると、ゴールで止まれる道筋を見つけた後も、さらに短い道筋を探す挑戦が加わる。氷を滑るパズルでは最短手数を目安にした評価がよく見られ、最短手数は幅優先探索で厳密に求まるので、評価の基準として揺れない。
- 一方、難易度は「止まる道筋を何手先まで読んで組み立てるか」（計画深さ）で定義した。最短を求める評価はそれと別の挑戦を測ることになり、上のレベルほど最短から外れやすく、満点が遠くなる（推測）。ただし8×8では最短解が一意の問題がどのレベルでも9割を超え（難易度PoC）、計画深さの深い問題でも最短の道筋は1本に決まりやすい。

### 13.3 評価案

手数は「成立した滑り1回を1手」と数え、滑った距離によらない。成立しない方向（§8.1）は数えない。ゴールを通過した滑りは1手に数える。待ったは手を減らさない（取り消した手も総手数に残る）。

| 案 | 配点 | 合う称え方 | 懸念 |
| --- | --- | --- | --- |
| A スライドパズル型 | 効率60（最短 ÷ 総手数。総手数は待ったで取り消した手と盤面を戻す前の手も含む）、速さ40 | 最短で、試し滑りなく止める | 待った・盤面を戻すを別に減点しないので、1つの事実（総手数）で説明できる。最短の道筋を外すと `perfect` に届かない |
| B ウォーターソート型 | 効率40（クリアした道筋の手数 vs 最短）、速さ40、正確性20（手戻り = 待ったで取り消した手と盤面を戻す前の手） | 最短の道筋を見つけることと、手戻りの少なさを分けて称える | 項目が増える。待ったで道筋を整えると効率が戻り、手戻りは正確性だけで測る |
| C 速さ型（リフレクション型） | 速さ100。手数は評価に使わず事実として示す | 止まる道筋を早く見つける | 試し滑りが安いので、盤面を読まない総当たりでも速ければ高く評価される（推測）。NFR-010（より良いプレイほど良い評価）に反しやすい |
| D 正確さ型（パーキングジャム型） | 正確さ（ミス）+ 速さ | 失敗せずに止める | 氷と岩だけでは、成立しない方向もゴールの通過もミスに数えないので、ミスにあたる事実が無い。採らない |

**AI判断（仮決定。ユーザーレビュー待ち）: 案A（効率60 + 速さ40）。** 称えるのは「試し滑りせず、最短の道筋で止める」こと。

- 効率 = 最短手数 ÷ 総手数。総手数は成立した滑りの数で、待ったで取り消した手と盤面を戻す前の手も数える。最短の2倍で30点（スライドパズルと同じ `calculateLinearScore` の形）。
- 速さ = 基準時間との比較（13.4）。基準の2倍で0点。
- 待った・盤面を戻すの回数は別に減点しない。取り消した手は総手数に残るので、二重に数えない。
- 配点・係数は仮置き。記録には生のプレイ事実だけを保存する（§14）ので、配点や評価案を変えても記録を移行しない。

理由: 氷の床迷路の1手は「止まる位置を読んだ」1回の判断で、試し滑りはそのまま手数に表れる。待ったを提供しても取り消した手を数えるので、待ったを使った総当たりで評価が上がらない（案Cの懸念を避ける）。1つの事実（総手数）で説明でき、自己ベストの「最短手数との差」（`records/ui/play-record-display.ts` の `moveDeltaMetricPresentation`）とも同じ事実で一致する。8×8では最短解が一意の問題がどのレベルでも9割を超え（難易度PoC）、計画深さの深い問題でも最短の道筋は1本に決まりやすいので、「止まれる道筋を読む」ことと「最短で止める」ことは大きくずれない（推測）。

比較した案: B（効率40・速さ40・正確性20。項目が増え、待ったで道筋を整えると効率が戻る）、C（速さ100。試し滑りの総当たりでも速ければ高く評価される）、D（ミスにあたる事実が無いので採らない）。

レビューで見てほしい点: 上のレベル（広い盤面・深い計画）で最短の道筋を外すと満点に遠く、厳しすぎないか。「見つける」を称える方が合うなら、B か、最短の代わりに基準とするプレイの手数と比べる案へ変える。

- 詰みへ入ったことは、A では手数の超過として自然に減点される。別に数えない（AI案）。
- 穴を拡張で入れる場合は、落ちた回数をミスとして数えるかをそのときに決める。

### 13.4 速さの基準時間

既存と同じく、盤面把握の時間 + 最短1手あたりの時間を第一候補とする。氷の床迷路では時間の大半が読みで、操作の手間は小さいと見込む（推測）。盤面把握は盤面の広さ（マス数。縦長の盤面を含めるので一辺ではない）か到達できる停止点の数で決める。係数は、§11 の組み合わせで作った代表問題の実測で校正する（§17）。

### 13.5 自己ベスト（AI案）

比較単位は同じ難易度（SPEC-002）。指標は評価点（高い）・基準時間との差（小さい）・最短手数との差（小さい。A なら総手数 − 最短）。待った・盤面を戻すの回数は比べない。

### 後段への申し送り

ルール・ドメイン（段02）:

- 盤面は `{ width, height }` で持ち、正方形を前提にしない（添字は `y * width + x`）。調査コード `scripts/research/ice_floor_supply_experiment.py` の `slide`・`explore`・`coreachable`・`relevant_rocks`・`canonical_key`（長方形は `transform_rectangle`）と、`ice_floor_difficulty_experiment.py` の `strongly_connected`・`trap_structure` を基準にし、固定 seed の盤面で停止点・最短手数・詰み・閉じ込め・正規化キーが一致することをテストで確かめる。
- 1マスも動けない方向は「成立しない操作」で、停止点の移動に含めない（調査コードの `BLOCKED`）。ゴールは開始位置以外の、到達できる氷の停止点から選ぶ（`goal_candidates`）。
- 閉じ込めの判定は「今の位置の強連結成分が出口を持たず、ゴールを含まない」。詰み（ゴールへ到達できない）とは別の判定として持つ。
- 同型の正規化キーは、正方形で8通り、長方形で4通り。長方形の90度回転を足さない。

プレイ縦断（段03。段02で確定）:

- session は `slideIceFloorMazePiece` の結果を使う。`blocked` は成立しない操作として session を変えず、手数にも数えない。`slid` の `path`（最後が止まったマス）と `from`・`to` を、演出に要る操作の結果として `play/` から盤面へ渡す。
- クリアは止まった位置で `isIceFloorMazeCleared` を使う。ゴールの通過は `doesIceFloorMazeSlidePassGoal` で分かる。
- 閉じ込めの知らせは毎手 `classifyIceFloorMazeDeadlock` が `trapped` を返すときに出す。`goal-unreachable`（閉じ込めでない詰み）では知らせない（§8.3）。
- 固定問題は `parseIceFloorMazeBoard`（`.` が氷、`#` が岩）で書け、identity は `createIceFloorMazeProblemIdentity` で作り、`restoreIceFloorMazeProblem` で復号できる。

プレイ画面（段03で確定）:

- `problem-selection.ts` の `selectIceFloorMazeProblemForDifficulty` は仮の盤面の形で `generateIceFloorMazeProblem` を呼ぶだけ。問題集の段で、問題集からの選択と問題 ID での引き当て（`selectIceFloorMazeProblemById`）に置き換え、`play/` は `IceFloorMazeGeneratedProblem` の代わりに問題集の問題（`IceFloorMazePooledProblem`）を受ける。
- `game-catalog/ice-floor-maze/PlayableIceFloorMaze.tsx` は `usePlayableGame` を使わず、ホームへの遷移だけをつないでいる。カタログ項目・記録・離脱・診断を足す段で `usePlayableGame` に置き換え、`views/IceFloorMazePlayView/InvalidDifficulty.tsx` を共通の `PlayUnavailableNotice`（難易度選択へ戻る）に置き換える。段05で、`PlayUnavailableNotice`・難易度選択への遷移・問題 ID の URL・検証情報はつないだ（記録に依る部分は残る。下の段05の申し送り）。
- `IceFloorMazePlay` は評価と結果画面が無いので結果に関わる props を受けず、クリア後も盤面を見せる。結果画面の段で `GamePlayScreenProps` をそのまま受け、`renderResultScreen` に結果画面を渡す。`createIceFloorMazeResult` は今はプレイの事実と最短手数だけを返す。
- 盤面の描画（`ui/board/IceFloorMazeTerrain`・`IceFloorMazeTrail`・`IceFloorMazeGoalMark`・`IceFloorMazePieceMark`）は遊び方の図と共用している。難易度選択のプレビューとピクトグラムも同じ部品と色（`ui/ice-floor-maze-tone.ts`）から作れる。
- 仮の問題はゴールを計画深さを問わず選ぶので、レベル5の盤面でも短い問題が出る。12×14 の見た目の判断は盤面の大きさについてのもので、レベルの手応えは問題集の段の後に確かめる。

問題生成と難易度（段05・段06）:

- 生成は G1（岩の密度20%のランダム配置、開始位置をランダムに選び、停止点のBFS）。1盤面のゴール候補をすべて分析して、目的のレベルのゴールを選ぶ。1盤面から各レベル1問までとする。
- 計画深さは調査コードの `analyze` と同じ定義（近づく・揃えるの2方針、同点時の方向優先順位4通りの最小値、読み手数の上限6、手数の上限 `4 × 最短 + 8`、一度止まった停止点へは戻らない）。試行手数は4通りの中央値。移植後、固定 seed の問題で Python と一致させる。
- 分類は計画深さ（主軸）と最短手数（レベル1・2の境界と提供範囲）で行い、盤面の形を「そのレベルで許す範囲」として基準表で問う（§11）。最短15手以上は提供範囲外、計画深さ7以上は評価不能。
- 計画深さのモデルは各手で比べる止まり先の数を数えない。広い盤面の同じレベルが体感で難しすぎる・易しすぎると分かったら、読む範囲の広さ（計画深さまでに到達できる停止点の数など）を補助の特徴量として加える。
- Python PoC では12×14の1盤面の処理が約55 ms、レベル5の1問が約83 ms。生成は事前に行い、プレイ時には行わない。

難易度分析と問題集（段04で確定）:

- 問題は `problem-selection.ts` の `selectIceFloorMazeProblemForDifficulty`（問題集から seed で選ぶ）・`selectIceFloorMazeProblemById`・`canSelectIceFloorMazeProblemById`（問題 ID で引く）で得る。`play/` は `IceFloorMazePooledProblem`（問題・identity・最少手数）を受ける。問題 ID の URL・カタログ項目の遊び直し先は、`usePlayableGame` へ置き換える段でこれらへつなぐ。`useIceFloorMazePlay` は最初の問題を引数で受けないので、その段でスライドパズルと同じく `initialProblem` と `avoidedProblemId` を足す。
- 難易度選択のプレビューは、レベルごとの盤面の形を `iceFloorMazeLevelCombinations[difficulty].boardShapes`（`isIceFloorMazeBoardShapeOfDifficulty`・`listIceFloorMazeBoardShapes`）から作れる。プレビューに問題集の問題を出すなら `listIceFloorMazePoolEntries` と `restoreIceFloorMazePoolEntry` を使う。
- 内部診断は `createIceFloorMazeDiagnosticSnapshot` が作れる。検証情報のダイアログ（`useInternalDiagnosticsDialog`）と、特徴を読む表示はまだ無い。
- 速さの基準時間に使う作業の量は問題集に持たせていない。盤面の広さ（マス数）と到達できる停止点の数は問題から実行時に求まる（停止点の BFS は軽い）。計画深さや試行手数を基準時間に使うなら、問題集の項目に足すか、記録の `performance` に保存するかを評価の段で決める。問題集の項目を足すと JSON が大きくなる（§5.3）。
- 12×14 のレベル4と5は試行手数・到達できる停止点・最少手数がほぼ同じで、差は計画深さだけ（[氷の床迷路難易度](氷の床迷路難易度.md) §5.4）。基準時間を作業の量から決めると、レベル4と5の基準時間もほぼ同じになる。

難易度選択・掲載・問題 ID の URL・検証情報（段05で確定）:

- `useIceFloorMazePlay(difficulty, initialProblem?, avoidedProblemId?)` は、スライドパズルと同じく URL の問題 ID で引いた問題か、避ける問題を除いて選んだ問題で始める。
- `PlayableIceFloorMaze` は `usePlayableGame` を使っていない。評価・記録の段で、`ice-floor-maze-catalog-entry.tsx` に `id`（`play-record.ts` の記録定義の `gameId`）・`playRecordDisplay`・`recordProblemPlayTarget`・`attemptProblemPlayTarget`（`canSelectIceFloorMazeProblemById` を `resolveRecordProblemPlayTarget` へ渡す）・`renderRecordResult` を足して `gameCatalog` の末尾へ加え、`PuzzleSelectionView` の末尾の追加と `game-catalog.test.ts` の `gamesNotInCatalogYet` を外す。`PlayableIceFloorMaze` は `usePlayableGame` に置き換え、今直に使っている問題 ID の URL・画面遷移・検証情報のつなぎを外す。離脱の記録（`play-attempt.ts`）もそこでつながる。
- `IceFloorMazePlay` は今も結果に関わる props（`difficulty`・`result`・`recordOutcomeNotice`・`onOpenRecords`）を受けない。結果画面の段で `GamePlayScreenProps` をそのまま受け、`usePlayableGame` の `screenProps` を渡す。
- 検証情報は `createIceFloorMazeDiagnosticSnapshot` を開いたときだけ作る（`useInternalDiagnosticsDialog`）。`Recorded<Game>Result` も同じ `IceFloorMazeDiagnostics` を使える。
- 難易度プレビューの道筋（`ui/IceFloorMazeDifficultyPreview.tsx` の `previewStrip`）は、レベルの盤面の形を `iceFloorMazeLevelCombinations` から読む。形の基準表を変えたら、道筋がルールどおりに滑れ、帯の中に収まり、上のレベルが下のレベルを含むことをテストが確かめる。
