## 2. 良いプレイの定義

> 試し滑りをせず、止まる位置を読んで、最短の道筋でゴールに止めること。速く読めればなお良い。

- 氷の床迷路の1手は「どこで止まるか」を読んで選ぶ1回の判断で、読まずに滑らせた手（試し滑り）はそのまま手数に表れる（前提調査 §13.3）。
- 待ったで1手前へ戻せるが、取り消した手も総手数に残る。待ったを使った総当たりでは効率が上がらない。
- 閉じ込められて盤面を戻した場合も、それまでの手は総手数に残る。詰みへ入ったことは手数の超過として自然に減点され、別に数えない。
- ゴールで止まれば必ずクリアで、失敗の条件は無い。クリアしたプレイだけを評価する。

## 3. 観点とプレイ事実

`session/session.ts` の `IceFloorMazeSessionResult` がクリア時に返す事実と、問題の事実を使う。

| 事実 | 意味 | 評価での扱い |
| --- | --- | --- |
| 経過時間 `elapsedMs` | 開始からクリアまで。盤面を戻しても引き継ぐ | 速さ |
| 総手数 `moveCount` | 成立した滑りの回数。待ったで取り消した手と盤面を戻す前の手も含む。1マスも動けない向きは数えない | 効率（最短手数との比） |
| 待った `undoCount` | 待ったを使った回数 | 結果の内訳に出すだけ。減点しない（取り消した手は総手数に残る） |
| 盤面を戻す `restartCount` | 同じプレイのまま開始位置へ戻した回数 | 結果の内訳に出すだけ。減点しない |
| 最短手数 `optimalMoveCount`（問題の事実） | 開始位置からゴールで止まるまでの最少手数。問題集が持つ | 効率と基準時間 |
| 盤面の形 `width`・`height`（問題の事実） | identity の `conditions` | 基準時間 |

## 4. 評価式

| 観点 | 満点 | 規則 |
| --- | ---: | --- |
| 効率 | 60 | 総手数が最短手数以下で満点。それより多ければ `60 × 最短手数 ÷ 総手数`。最短の2倍で30点 |
| 速さ | 40 | 問題ごとの基準時間以内で満点。超過に応じて線形に減らし、基準時間の2倍で0点 |

```
効率     = round(60 × min(1, 最短手数 ÷ 総手数))
速さ     = round(40 × clamp(1 − max(0, 経過時間 − 基準時間) / 基準時間, 0, 1))
基準時間 = 0.2秒 × 盤面のマス数（幅 × 高さ） + 2.5秒 × 最短手数
```

評価段階は既存ゲームと同じ（100 `perfect` / 90以上 `great` / 80以上 `good` / それ未満 `clear`）。

この式から導かれる性質（導出。`score.test.ts` で固定）:

- `perfect` は、最短手数で、基準時間以内にクリアしたときだけ。
- 待った・盤面を戻すを使っても、同じ総手数と時間なら同じ点になる。待ったで取り消した1手は、取り消さずに続けた1手と同じだけ効率を下げる。
- 時間と手数が基準時間・最短手数に対して同じ倍率なら、盤面の広さや最短手数が違っても速さの点は同じ。高いレベルを選んだことだけでは点は上下しない。
- 最短手数が短い問題ほど、1手の超過が効率に大きく響く（最短3手で1手超過すると45点、最短7手なら53点）。§6・§8。

実装: `frontend/src/games/ice-floor-maze/score.ts`。形はスライドパズル（`slide-puzzle/score.ts`）と同じで、基準時間の盤面把握だけを盤面サイズ別の表からマス数の比例に変えた。

## 5. 基準時間

### 5.1 使う量

| 量 | 出どころ | 採否 |
| --- | --- | --- |
| 盤面のマス数（幅 × 高さ） | 記録の identity の `conditions` | **使う**。広い盤面ほど止まり先が多く、各手で比べる範囲が広い |
| 最短手数 | 問題集。記録の `performance` にも保存 | **使う**。止まる位置を確かめて滑らせる回数 |
| 到達できる停止点の数 | 問題から停止点の BFS（`puzzle/stop-graph.ts`）で求まる | 使わない。マス数とほぼ同じ動きをする（§5.2 の T5）。記録だけから求め直すには問題を復元する必要があり、生成器の版が違う記録では求められない |
| 試行手数・計画深さ | 難易度分析（`problem/generation/planning-player.ts`）。問題集に持たせていない | 使わない。通常プレイから `problem/generation/` を参照しない決まり（game-structure.md）と、計画深さはレベルの定義そのものであること。使うなら問題集と記録の両方に作業の量を足す（リフレクションの `workload` と同じ形）ことになる。§10 |

マス数と最短手数はどちらも記録に残る事実なので、問題集から外れた記録や生成器の版が違う記録でも、記録だけから基準時間を求め直せる（`getIceFloorMazePlayRecordTimeDelta`）。

### 5.2 案の比較

案を比べる物差しとして、1問ずつ所要時間を見積もる **参照モデル** を置いた（推測。係数は仮定）。

- 盤面把握 0.1秒 × マス数 + 操作と止まりの確認 1.5秒 × 最短手数 + 読み 1秒 × 試行手数。
- 試行手数（待ったを使って近づく順に試す試行錯誤の手数）を、頭の中で滑らせて確かめる回数の目安とみなした。上のレベルほど多い（中央値 4 / 9 / 20 / 24 / 26）。

参照モデルは「同じ腕前の人が、どの問題にどれだけ時間がかかりそうか」を表すための仮定で、絶対値は当てにしない。見たいのは、同じ腕前の人がどのレベルでも同じくらいの速さの点を取れるか。

| 案 | 式（秒） | 基準時間の中央値（1 / 2 / 3 / 4 / 5） | 基準時間 ÷ 参照モデル（中央値。1 / 2 / 3 / 4 / 5） | 参照モデルの1.3倍で解く人の速さの点（中央値） |
| --- | --- | --- | --- | --- |
| T1 | 0.1 × マス + 3 × 最短 | 17.0 / 25.8 / 25.8 / 34.0 / 37.8 | 1.10 / 1.00 / 0.69 / 0.72 / 0.74 | 33 / 28 / **5 / 7.5 / 10** |
| T2 | 0.15 × マス + 3 × 最短 | 21.0 / 30.0 / 31.5 / 40.5 / 46.2 | 1.32 / 1.19 / 0.84 / 0.87 / 0.90 | 40 / 36 / 18 / 20 / 22 |
| T3 | 0.2 × マス + 2 × 最短 | 21.4 / 29.6 / 34.0 / 43.6 / 47.6 | 1.27 / 1.13 / 0.87 / 0.88 / 0.92 | 39 / 34 / 20 / 21 / 23 |
| **T4（採用）** | **0.2 × マス + 2.5 × 最短** | 23.1 / 31.6 / 36.0 / 46.1 / 51.1 | **1.39 / 1.25 / 0.93 / 0.96 / 0.99** | 40 / 38 / 24 / 26 / 27.5 |
| T5 | 0.5 × 到達停止点 + 2.5 × 最短 | 18.5 / 25.5 / 28.0 / 34.5 / 40.0 | 1.09 / 0.95 / 0.68 / 0.71 / 0.72 | 32 / 25 / 4 / 7 / 7.5 |
| 参照モデル | 0.1 × マス + 1.5 × 最短 + 1 × 試行手数 | 16.5 / 26.8 / 41.0 / 49.0 / 55.3 | 1 | 28 / 28 / 28 / 28 / 28 |

（事実（実測）: 問題集 2,500問で、難易度分析の特徴から各案を計算して比べた（一時スクリプト、コミットしていない）。参照モデルの係数は仮定。）

- マス数と最短手数だけの式は、レベル2→3 の読みの増え方（試行手数 9 → 20。マス数と最短手数はほとんど増えない）を追えない。どの係数でも、レベル1・2 に甘く、レベル3〜5 に厳しい形になる。係数を選ぶことは、どちらの側で参照モデルに合わせるかを選ぶことになる。
- **T1・T5 を採らない**。レベル3〜5 で基準時間が参照モデルの7割に届かず、同じ腕前の人の速さの点がレベル3以上でほぼ0になる。「高いレベルを選んだだけで点が下がる」規則になる。
- **T4 を採る**。上のレベル（3〜5）で基準時間 ÷ 参照モデルが 0.93〜0.99 に収まり、同じ腕前の人の速さの点がレベル3〜5 でほぼ揃う。レベル1・2 には 1.25〜1.4倍の余裕が出るが、短い問題は効率（1手の超過が大きく響く。§4）で差がつくので、速さを甘くしても `perfect` は最短手数で解いたときだけに保たれる。
- T2・T3 は T4 より上のレベルで1割ほど厳しく、レベル1・2 の甘さはあまり変わらない。
- 注意: 参照モデルは「試行手数が多い問題ほど読みに時間がかかる」と仮定しており、T4 がよく合うことはその仮定のもとでの確認にすぎない。仮定そのものは §8 の実プレイで確かめる。

## 6. 代表的なプレイ例

レベルごとに、狭い形で最短手数が中央値の問題で計算した（導出）。点は「効率 + 速さ = 合計」。

| 例 | 総手数 | 時間（基準比） | L1 8×8 最短3（基準 0:20.3） | L3 9×12 最短5（基準 0:34.1） | L5 12×14 最短7（基準 0:51.1） |
| --- | --- | --- | --- | --- | --- |
| a 最短で速い | 最短 | 0.8倍 | 60 + 40 = 100 perfect | 100 perfect | 100 perfect |
| b 最短で少し遅い | 最短 | 1.2倍 | 60 + 32 = 92 great | 92 great | 92 great |
| c 1手試し滑りして待ったで戻した | 最短 + 1 | 1.0倍 | 45 + 40 = 85 good | 50 + 40 = 90 great | 53 + 40 = 93 great |
| d 2手の試し滑り | 最短 + 2 | 1.0倍 | 36 + 40 = 76 clear | 43 + 40 = 83 good | 47 + 40 = 87 good |
| e 最短だが遅い | 最短 | 1.5倍 | 60 + 20 = 80 good | 80 good | 80 good |
| f 最短の2倍の手数（閉じ込められて盤面を戻した など） | 最短 × 2 | 1.0倍 | 30 + 40 = 70 clear | 70 clear | 70 clear |
| g 最短の3倍の手数で遅い | 最短 × 3 | 2.0倍 | 20 + 0 = 20 clear | 20 clear | 20 clear |

- 速さの点は基準時間に対する倍率だけで決まり、レベルによらない（a・b・e）。
- 効率は最短手数が短いほど1手の超過に厳しい（c・d）。レベル1（最短3〜4手）では、試し滑り1回で `good`、2回で `clear` に下がる。§8 の確認点。

明らかに良い／悪いプレイとの矛盾が無いかの確認（導出。`score.test.ts` の「代表的なプレイ例」で順序を固定）: 最短で速い > 最短で少し遅い > 1手試し滑りして速い > 最短で1.5倍 > 閉じ込められて盤面を戻し解き直した > 最短の2倍の手数で速い > 最短の3倍で遅い。

## 7. 記録と自己ベスト

実装: `frontend/src/games/ice-floor-maze/play-record.ts`。共通の記録に `gameId: "ice-floor-maze"`・`payloadVersion: 1` で載せる。

| payload | 内容 |
| --- | --- |
| `difficulty` | `"1"`〜`"5"` |
| `problemIdentity` | `{ generatorVersion, seed, conditions: { width, height } }`。再プレイで問題集から同じ問題を引く。盤面の形は基準時間に使う |
| `performance` | `{ elapsedMs, moveCount, undoCount, restartCount, optimalMoveCount }`。プレイの事実と、問題集から外れても評価できるよう残す最短手数 |

記録の id は `ice-floor-maze:<開始時刻>:<完了時刻>:<seed>`。

- 評価点・評価段階・基準時間・基準時間との差は保存しない。記録から現在の評価規則で導出する（`SPEC-006`）。配点・係数を変えても記録を移行しない。
- 作業の量（`workload`）は持たない。基準時間に使う量（マス数・最短手数）は identity と `performance` から読める（§5.1）。基準時間に試行手数などを足すときは、`payloadVersion` を上げて `workload` を足す。
- 生成器の版が今と違う記録も、盤面の形が読めれば読み込み、評価と自己ベストに残す。結果画面の作り直し（`restoreIceFloorMazeRecordedResult`）と再プレイだけをしない。
- 読み込み時の検証: ゲーム ID・payload の版・難易度・identity（今の版なら盤面の形がその難易度の形か）・事実（経過時間が有限の0以上、総手数と最短手数が1以上の整数、待ったと盤面を戻すが0以上の整数、待ったと最短手数が総手数以下）。
- 離脱したプレイ（`play-attempt.ts`）は、経過時間・総手数・待った・盤面を戻すの回数を進み具合として残す。最短手数は評価にだけ使うので保存しない。記録画面では経過時間と手数を出す。

**自己ベスト**（比較単位は難易度）:

| 指標 ID | 良い向き | 理由 |
| --- | --- | --- |
| `play-score` | 高い | 評価そのもの |
| `time-delta-ms` | 小さい | 問題ごとに基準時間が違うので、実時間ではなく差で比べる |
| `move-delta` | 小さい | 総手数 − 最短手数。効率と同じ事実（前提調査 §13.5） |

## 9. 限界

- **実プレイをしていない**。配点・基準時間の係数・0点になる倍率・参照モデルはすべて仮定。
- 基準時間はマス数と最短手数だけから決めるので、読みの深さ（計画深さ）と試行錯誤の量（試行手数）の違いを表さない。同じ盤面の形と最短手数なら、レベル4 とレベル5 は同じ基準時間になる。
- 参照モデルは試行手数を読みの量の目安とした。試行手数は「待ったを使って近づく順に試す」プレイヤーモデルの値で、人間が頭の中で確かめる回数と同じとは限らない。
- 最短の道筋が一意でない問題（1割前後）でも、効率は最短手数だけと比べる。最短でない道筋を読み切ったプレイは、最短の道筋を外した分だけ下がる。
- 経過時間は開始からクリアまでで、アプリを離れていた時間も含む（既存ゲームと同じ）。

## 10. ずれた場合の見直し方針

1. 良いプレイの定義（§2）が遊ぶ人の感覚と合っているか。「最短で止める」より「止まる道筋を見つける」を称える方が合うなら、案 B（前提調査 §13.3）へ切り替える。記録に `completionMoveCount`（最後に盤面を戻してから、待ったで取り消されずに残った手数）を足して `payloadVersion` を上げる。
2. 基準時間の量（§5.1）がレベルで偏るなら、作業の量（試行手数や、計画深さまでに到達できる停止点の数）を問題集の項目に足し、記録にも `workload` として保存して基準時間に入れる（リフレクションと同じ形）。問題集の JSON が大きくなる（前提調査 §5.3）。
3. そのうえで係数を動かす。係数だけを変える場合、記録は事実だけを持つので、過去の記録も新しい規則で評価し直される（`SPEC-006`）。

## 11. 作り直し後の評価（段5、2026-11-01）

もろい岩・薄い氷を足した作り直し（前提調査 §20）で、効率の式と速さの基準時間を変えた。配点（効率60・速さ40）・0点になる倍率・待った・盤面を戻すの扱い・自己ベストの指標は変えない。**効率のゆとりと基準時間の係数はすべて仮置き**で、作り直した問題集を実アプリで試遊したときに校正する（§11.8）。実装は `frontend/src/games/ice-floor-maze/score.ts`。

### 11.1 何を変えたか

| 論点 | 初期版（§4・§5） | 作り直し後 | 状態 |
| --- | --- | --- | --- |
| 効率 | `round(60 × 最短 ÷ 総手数)` | `round(60 × (最短 + 10) ÷ (総手数 + 10))`（前提調査 §20.6 の案 E2） | 決定（方向。ユーザー）／AI判断（仮決定）（ゆとり10） |
| 基準時間のマス数 | 幅 × 高さ | 盤面として描くマスの数（盤面の外を除く） | AI判断（仮決定） |
| 基準時間の要素の項 | ― | 8秒 × 要素（もろい岩・薄い氷）の数 | AI判断（仮決定。係数は仮置き） |
| 基準時間のほかの係数 | 0.2秒 / マス、2.5秒 / 最短1手 | 変えない | 仮置きのまま |
| 総手数の数え方 | 待ったで取り消した手・盤面を戻す前の手も含む | 変えない | 残す |
| 記録の `payloadVersion` | 1 | 1 のまま（§11.6） | AI判断 |

### 11.2 評価式

```
効率     = 総手数 ≤ 最短手数 なら 60、それ以外は round(60 × (最短手数 + 10) ÷ (総手数 + 10))
速さ     = round(40 × clamp(1 − max(0, 経過時間 − 基準時間) / 基準時間, 0, 1))
基準時間 = 0.2秒 × 描くマスの数 + 2.5秒 × 最短手数 + 8秒 × 要素の数
```

この式から導かれる性質（導出。`score.test.ts` で固定）:

- `perfect` は、総手数が最短手数で、基準時間以内にクリアしたときだけ。1手でも多ければ、効率は丸めた後も59点以下になる（最短手数が108手以下のとき。109手以上では最短+1手の効率が丸めで60点になるが、問題集の最短手数はその数分の一）。
- 待った・盤面を戻すを使っても、同じ総手数と時間なら同じ点になる（初期版と同じ）。
- 速さの点は基準時間に対する倍率だけで決まり、盤面の広さ・要素の数・最短手数によらない。
- 試し1回の減点は、丸める前で 60 ÷ (最短 + 11) 点。最短3手で約4.3点、15手で約2.3点。

**効率の点（導出）**: 括弧は初期版（案 A）。

- 短い問題ほど初期版より軽くなり、長い問題では初期版とほぼ同じになる。大きな試行錯誤は今も比で下がる（最短の3倍で25〜41点）。
- 代表的なプレイ例の順序（`score.test.ts`。最短6手・基準41秒の問題）: 最短で速い 100 > 1手試して待ったで戻し速い 96 > 最短で基準を少し超えた（50秒）91 > 閉じ込められて盤面を戻し、10手で解き直した 88 > 最短の2倍の手数で速い 84 > 最短で基準の1.5倍 80 > 最短の3倍の手数で遅い 34。初期版から、「1手試して速い」が「最短で少し遅い」より上に、「最短の2倍の手数で速い」が「最短で1.5倍の時間」より上に入れ替わった。試した手への減点を軽くした（ユーザーの決定）ことの帰結で、試遊で違和感が無いかを見る（§11.8 の3）。

### 11.6 記録

- **`payloadVersion` は上げない（1 のまま）。** 記録の payload の項目と意味は変えていない。描くマスの数と要素の数は、記録に前からある identity の seed から求め直せる。`.claude/rules/game-structure.md` は「項目を足す・消す・意味を変えるとき」に版を上げると決めており、評価の式や係数の変更は当たらない。先例: リフレクションの基準時間の校正（`429920b`）は係数を変え、`payloadVersion` を上げなかった。
- 評価点・評価段階・基準時間は保存していないので、作り直し前の記録も新しい式で評価し直される（`SPEC-006`）。版 `"1"` の記録は描くマス = 幅 × 高さ・要素0 なので基準時間は初期版と同じで、効率だけが E2 で変わる（例: 最短6手を9手・51秒は 70点 → 81点）。自己ベストの `play-score` も新しい式で比べ直す。`time-delta-ms`・`move-delta` は版 `"1"` の記録では変わらない。
- 結果（`IceFloorMazeResult`）は、盤面の形（`boardShape`）の代わりに基準時間に使う量（`speedReference`: 描くマスの数・要素の数）を持つ。`createIceFloorMazeResult` は identity を受け、プレイ中の結果と記録から作り直す結果で同じ数え方をする。

### 11.7 結果画面の採点基準

実装: `ui/result/IceFloorMazeResultScreen/score-criteria.ts`。内訳の項目（効率・速さ・最短手数・基準時間・待った・盤面を戻す）は変えない。

| 項目 | 採点基準の文（例: 最短17手、描くマス99、要素7個） |
| --- | --- |
| 効率 | 「最短17手で60点。総手数が増えるほど (最短手数 + 10) ÷ (総手数 + 10) の割合で減らし、44手で30点。総手数には「待った」で取り消した手と「盤面を戻す」前の手も含む。」 |
| 速さ | 基準時間・0点になる時間と、「基準時間は盤面99マス × 0.2秒 + 最短17手 × 2.5秒 + もろい岩・薄い氷7個 × 8秒。」。要素の無い問題では要素の項を出さない |

半分の点になる総手数は `2 × 最短 + 10`（導出）。

### 11.9 限界

- 係数は、1人の試遊6問（うち当てはめに使ったのは3問）から決めた仮置き。作り直した問題集では測っていない。
- 要素の数は、使う順序の依存やおとりの効き方など、問題ごとの読みの差を表さない（v4 の w01 は要素7個で18秒）。
- 速さの点は基準時間の倍率で決まるので、基準時間がレベルによって甘い・厳しいと、そのレベルを選んだことだけで点が上下する（初期版の §9 と同じ限界）。
