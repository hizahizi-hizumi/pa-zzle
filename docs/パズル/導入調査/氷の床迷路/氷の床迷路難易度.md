# 氷の床迷路難易度

氷の床迷路の `レベル 1`〜`レベル 5` を、[難易度開発手順.md](../../難易度開発手順.md) の工程4〜8・11 に沿って製品コードで組み立てた検討記録。

## 1. 目的と位置づけ

[氷の床迷路難易度PoC](氷の床迷路難易度PoC.md)（以下「PoC」）の計画深さのモデルを製品コードへ移植し、[氷の床迷路実装前提調査](氷の床迷路実装前提調査.md)（以下「前提調査」）§11 の5段階と盤面の形の組み合わせを基準表のデータとして実装した。そのうえで問題集（第1版）を作り、レベル別の分布・供給・本番ビルドの増分を測り、人間が試遊で確かめるための代表・境界・異常な問題を残す。

この文書は現在仕様の正本ではない。採用した契約（基準とするプレイ、挑戦の定義、計画深さを主軸に盤面の形を各レベルで許す範囲として組み合わせる分類の考え方）だけを [SPEC-019 氷の床迷路](../../../プロダクト/仕様/パズル/SPEC-019.md) の「難易度」へ反映した。正確な組み合わせの値（計画深さ・最少手数・盤面の形）はコード（`frontend/src/games/ice-floor-maze/difficulty.ts` の `iceFloorMazeLevelCombinations`）を正とし、SPEC-019 には複製していない。盤面の形の組み合わせはユーザーレビュー待ちの仮決定（[前提調査](氷の床迷路実装前提調査.md) §18）。試した案、比較結果、試遊で確かめることはこの文書に残す。

**作り直し中（2026-11-01〜）。** この5段階（初期版）は試遊でレベル5でも易しかったため、もろい岩・薄い氷を足して作り直す（[前提調査](氷の床迷路実装前提調査.md) §20、[氷の床迷路難易度再設計PoC](氷の床迷路難易度再設計PoC.md)）。この文書は初期版の記録である。

| 条件 | 内容 |
| --- | --- |

| 問題成立性 | ゴールは開始位置以外の、到達できる停止点。無関係な岩を除いた盤面を問題にする（段02） |
| 基準とするプレイ | 待った・盤面を戻すを使える。ヒントは無い（前提調査 §11） |

| 生成 | 岩の密度20%のランダム配置、開始位置をランダムに選び、停止点のBFS（供給実験の G1）。ゴールの候補は最少手数3〜14の停止点 |

## 3. 分析モデル（`problem/difficulty-analysis.ts`）

PoC の `analyze` をそのまま移した。

- **計画深さ**: 今の停止点から k 手先までを読み、ゴールがあればそこへ、無ければ各手の後 k−1 手以内に行ける停止点のうち最もよいもので手を比べ、待ったを使わず一度止まった停止点へは戻らない素朴な先読みのプレイヤーが、解ける最小の k。よさは「近づく」（マンハッタン距離）と「揃える」（同じ行・列で間に岩が無い位置を優先し、次に距離）の2方針で別々に求め、小さい方をとる。同点の手は向きの順位4通りを試し、最も小さい値をとる。読む手数の上限は6、プレイヤーが諦める手数は 4×最少手数+8。上限まで読んでも解けない問題は評価不能（`unsupported`）。
- **補助の特徴**: 最少手数、最少手数の道筋の数、到達できる停止点の数、試行手数（待ったを使って近づく順に試す試行錯誤の手数。向きの順位4通りの中央値を切り捨て）、遠回り（最少手数の道筋のうちゴールとの距離を縮めない手の最小数）、ゴールを通過する滑りを持つ停止点の数、詰みの停止点の数。分類には使わない。
- 先読みのプレイヤーと試行錯誤は生成と診断でだけ使うので `problem/generation/planning-player.ts` に置いた。読む範囲（起点から k 手以内の停止点）は盤面と開始位置だけで決まるので、同じ盤面の全ゴールを分析するときに使い回す。

### 3.1 研究用 Python との一致（事実（実測））

- `difficulty-analysis.test.ts` に、研究用 Python の `random_board_candidates` で作った 8×8・8×10・9×12・10×13・12×14 の固定盤面7問（レベル1〜5と評価不能）を置き、全特徴が `analyze` と一致することを確かめた。期待値は岩を除く前の盤面で求め、テストは岩を除いた盤面で分析するので、無関係な岩を除いても特徴が変わらないことも併せて確かめている。
- 一時スクリプトで、5つの形それぞれ40盤面の、最少手数3〜14の全ゴール 3,575問（Python の分類でレベル1 1,099 / 2 1,681 / 3 256 / 4 217 / 5 189 / 評価不能 133）を突き合わせ、全特徴が一致した（不一致0）。TS の分析は1問あたり約0.3 ms（bun）。
- 「揃える」の判定（同じ行・列で間に岩が無いか）は盤面の岩を見るが、比べる位置はどれも到達できる停止点で、その間にある最も近い岩は必ずその停止点からの滑りを止める岩なので、無関係な岩を除いても結果は変わらない。上の突き合わせとも整合する。

## 4. 5段階の分類（`difficulty.ts`）

| 区分 | 条件 | 盤面の形 |
| --- | --- | --- |
| 提供範囲外（`too-light` / `too-long`） | 最少手数2以下 / 15以上。計画深さより先に判定する（評価不能でも同じ） | ― |
| 評価不能（`unsupported`） | どちらの方針でも6手読んで解けない | ― |
| 成立しない（`invalid`） | ゴールへ止まれない | ― |
| レベル1 | 計画深さ1かつ最少手数3〜4 | 8×8・8×10 |
| レベル2 | 計画深さ1かつ最少手数5以上、または計画深さ2 | 8×10・9×12 |
| レベル3 | 計画深さ3 | 9×12・10×13 |
| レベル4 | 計画深さ4 | 10×13・12×14 |
| レベル5 | 計画深さ5〜6 | 12×14 |
| 提供範囲外（`unlisted-combination`） | 計画深さと盤面の形の組がどのレベルにも当たらない（例: 8×8 の計画深さ3、12×14 の計画深さ1） | ― |

- 基準表は「計画深さと最少手数の組（どれか1つに当たればよい）」と「そのレベルで出す盤面の形」のデータで持つ。レベル2の「計画深さ1で長い」と「計画深さ2」は2つの組として書いた。
- 隣のレベルとは盤面の形が1つ重なるが、計画深さの組は重ならないので、1問のレベルは1つに決まる。
- 評価不能と、形の組から外れる問題をレベル5へ押し込まない（`難易度判定.md`）。

## 5. 問題集（第1版）

### 5.1 作り方

`bun run --cwd frontend generate:ice-floor-maze-pool` で作る（`frontend/scripts/generate-ice-floor-maze-problem-pool.ts`）。

- 盤面の形ごとに、決定的な乱数列（`ice-floor-maze-pool:<幅>x<高さ>` から作る `ProblemRandom`）で盤面の候補を作る。
- 1盤面のゴールの候補をすべて分析・分類し、レベルごとにゴールの番号が最も小さい1問まで採る（PoC の `supply` と同じ）。
- 回転・反転の同型（正方形8通り、縦長4通り）を全レベルを通して除く。第1版では重複は0件だった。
- **1つのレベルに形が2つあるときは、形ごとに同じ数ずつ採り、形を交互に並べる**（AI判断（仮決定））。理由: 形の範囲は「そのレベルで許す範囲」で、どちらの形も同じレベルの挑戦として出す前提だから、片方へ寄せる根拠が無い。均等なら試遊で「同じレベルの狭い盤面と広い盤面」の両端を同じ頻度で見られる。試遊で広い側が難しすぎる・狭い側が易しすぎると分かったら、配分より先に形の範囲を見直す。
- 問題集の1問は `[seed, 幅, 高さ, 最少手数]`。`seed` は identity の盤面の符号（段02）なので、実行時に生成器・難易度分析を走らせずに問題を復元できる。問題 ID は identity からのハッシュで、問題集の索引（`createProblemPoolIdLookup`）で引く。

全問の検証は `problem-selection.test.ts` が持つ。全2,500問を identity から復号し、分析・分類してそのレベルになること、保存した最少手数が分析と一致すること、そのレベルの形であること、無関係な岩を含まないこと、形ごとの問題数の差が1問以内であること、全レベルを通して同型が無いことを確かめる（分析が軽いので全問を毎回確かめられる。約1秒）。

### 5.2 問題数と本番ビルドの増分（事実（実測））

**各レベル500問、計2,500問**にした。先例はリフレクション 500 / 500 / 500 / 300 / 300、タクズ各500、スライドパズル各200、ウォーターソート・マインスイーパー・パーキングジャム各1,000。供給は足りる（§5.3）ので、ビルドの大きさで決めた。

| 項目 | 値 |
| --- | --- |
| 問題集の JSON | 138,982 bytes（gzip 36,333 bytes） |
| 本番ビルドの JS（vite の表示） | 1,885.00 kB → 2,004.69 kB（+119.7 kB）、gzip 590.99 kB → 628.94 kB（+37.95 kB） |
| 生成時間 | 約7〜8秒（bun、1プロセス） |

増分のほとんどは問題集で、問題の選択・復元のコードは小さい（難易度分析は生成と診断でだけ使い、プレイ画面からは参照しない）。1問は 8×8 で約40 bytes、12×14 で約70 bytes（岩の配置を4マス1桁の16進で持つため）。リフレクション（2,100問、gzip 約29 kB）と同程度で、各レベル1,000問にすると gzip でさらに +36 kB ほど増える見込み（推測）。「別の問題」は今の問題を避けて選び直すので、各レベル500問で同じ問題が続くことは無い。

| レベル | 盤面の形 | 計画深さ | 最少手数 中央値 [最小〜最大] | 試行手数 中央値（p90） | 到達できる停止点 中央値 | 最短解が一意 | 詰みがある | ゴールを通過する滑りがある |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 8×8 250 / 8×10 250 | 1: 500 | 3 [3〜4] | 4（8） | 20 | 91.4% | 27.8% | 25.4% |
| 2 | 8×10 250 / 9×12 250 | 1: 351、2: 149 | 5 [3〜14] | 9（22） | 24 | 87.6% | 31.0% | 38.6% |
| 3 | 9×12 250 / 10×13 250 | 3: 500 | 5 [3〜14] | 20（47） | 31 | 90.4% | 45.8% | 61.2% |
| 4 | 10×13 250 / 12×14 250 | 4: 500 | 6 [4〜14] | 24（52） | 38 | 88.2% | 51.4% | 53.2% |
| 5 | 12×14 500 | 5: 304、6: 196 | 7 [5〜14] | 26（55） | 42 | 86.6% | 41.8% | 56.4% |

形ごとの中央値（最少手数 / 試行手数 / 到達できる停止点）:

| レベル | 狭い形 | 広い形 |
| --- | --- | --- |
| 1 | 8×8: 3 / 4 / 19 | 8×10: 4 / 4 / 21 |
| 2 | 8×10: 5 / 8 / 22 | 9×12: 5 / 9 / 27 |
| 3 | 9×12: 5 / 20 / 29 | 10×13: 5 / 20 / 35 |
| 4 | 10×13: 6 / 22 / 35 | 12×14: 6 / 25 / 41 |
| 5 | ― | 12×14: 7 / 26 / 42 |

- 試行手数（計画深さとは別に作った試行錯誤の量）の中央値は、レベル1→5で 4 / 9 / 20 / 24 / 26 と単調に増えた。到達できる停止点（各手で比べる止まり先）も 20 / 24 / 31 / 38 / 42 と増えた。最少手数の中央値は 3〜7 で、上のレベルが長いだけにはなっていない。
- **同じ 12×14 のレベル4とレベル5は、試行手数（25 と 26）・到達できる停止点（41 と 42）・最少手数（6 と 7）がほぼ同じ**で、差は計画深さ（4 と 5〜6）だけにある。PoC の 8×8 でもレベル4と5の試行手数の差は2手と小さかった。レベル4と5を体感で区別できるかは試遊の最重要の確認点（§8）。
- 同じレベルの中で、広い形は狭い形より到達できる停止点が2〜6多く、試行手数は同じか少し多い。隣のレベルと重なった形の中でも、試行手数の順は保たれた（8×10: レベル1 4・レベル2 8、9×12: 9・20、10×13: 20・22、12×14: 25・26）。ただし差は上のレベルほど小さい。
- 遠回り・最短解の数・ゴールの通過・詰みは、PoC と同じくレベルと単調な関係が無かった（詰みはレベル4 51.4% に対してレベル5 41.8%）。分類に使わず、診断で見られるようにしておく。

| 320×568 | 5 | 12×14 | 23.7px | 6 / 8 / 21 | クリア |

どの条件もゴールで止まると方向ボタンが無効になり、ページのスクロールは0のまま、`pageerror`・`console.error` は0件だった。

**レベル5の見た目の手応え（推測。開発者の目視）: 短すぎない。** 320×568 の問題はゴールが駒の5行下の同じ列に見えるのに、駒のすぐ下の岩で真下へは滑れず、ゴールの真下にも岩があるため、ゴールの列へ上から入り直す位置を探して8手かかる。390×844 の問題はゴールが右上の隅で左と下を岩に囲まれ、右の外壁沿いから入る道筋を11手かけて組み立てる。どちらも「見えているのに止まれない」形で、この2問には段03の仮の問題（計画深さを問わない）で見えたような短いレベル5は無かった。ただし解いたのは BFS で、人間が読んで解いたわけではない。

## 8. 試遊で確かめること

前提調査 §11「残る確認」に、本書の計測で分かったことを足した。

1. レベル1→5で、先読みの深さが概ね増えると感じられること。
2. **12×14 のレベル4と5が体感で区別できること。** 同じ形では試行手数・到達できる停止点・最少手数がほぼ同じで、差は計画深さだけ（§5.4）。区別できなければ、レベル5を計画深さだけでなく「計画深さまでに到達できる停止点の数」など読む範囲の広さでも絞る案を検討する（前提調査 §19 の申し送り）。
3. レベル2の「計画深さ1で長い問題」と「計画深さ2の短い問題」（§6.2）が、同じ帯として違和感が無いこと。
4. 同じレベルの狭い形と広い形（レベル4の 10×13 と 12×14 など）の体感がそろうこと。重なった形で、広い盤面の下のレベルが狭い盤面の上のレベルより難しく感じられる逆転が無いこと。
5. 試し滑りが安い問題（§6.3 のレベル5）で、レベル5の手応えが損なわれないこと。試行手数が多いレベル1（§6.3）が、レベル1として重すぎないこと。
6. ゴールから逆向きに「どの岩で止まれるか」を考える解き方で、前向きだけのモデルが計画深さを過大評価しないこと。
7. ゴールの通過・詰みの罠が、計画深さの外で体感難易度を大きく変えていないこと。

## 9. 前提調査から変えた点・決めた点

- 盤面の形の配分を「レベル内で形ごとに同数」に決めた（§5.1）。
- 問題数を各レベル500問に決め、本番ビルドの増分を測った（§5.2）。
- 提供範囲外の理由を `too-light`（最少2手以下）・`too-long`（15手以上）・`unlisted-combination`（計画深さと形の組が無い）に分けた。最少手数の判定は評価不能より先に行う（PoC の `classify` と同じ順）。
- 分析結果に、計画深さを与えた方針（`strategies`）を添えた。PoC の `greedy_solves`（1手読みの「近づく」で解けるか）は「近づく」の計画深さが1かと同じなので持たない。`goal_reach_dirs`（ゴールに止まれる進入方向の数）は PoC の表で使っていないので移さなかった。
- 内部診断の snapshot は、パーキングジャムと同じく、診断を開いたときに identity から分析し直した特徴と分類を持つ。問題集の問題は分析が軽い（約0.3 ms）ので、分類を問題集に持たせない。

## 10. 再現方法

```sh
bun run --cwd frontend generate:ice-floor-maze-pool -- --examples  # 問題集を作り直し、供給・分布・代表を出す
bun run --cwd frontend test -- src/games/ice-floor-maze            # Python との一致と、問題集の全問の検証
```

生成は決定的で、同じコードからは同じ問題集になる。
