# 氷の床迷路 スマホ操作PoC

調査日: 2026-10-31

名称は作業名。

## 目的

上下左右のどれかを選ぶと、駒が岩か外壁にぶつかるまで滑り、ゴールで止まればクリアになる「氷の床迷路」が、スマートフォン幅で操作できるかを実ブラウザで確認する。

迷路調査のゲート3（`docs/パズル/導入調査/迷路/迷路調査.md`）で、操作方式の一般的な比較、画面端の戻るジェスチャー、WCAG の扱いは確認済みである。本書ではそれを繰り返さず、氷の床迷路に固有の次の点を確かめる。

- 1回の入力で何マスも動く。このため、誤った方向へ入力したときの損失が大きい。
- 止まる位置を読むために、盤面の行・列の並びを一目で読める必要がある。
- 滑っている途中の連続入力、ゴールの通過、すぐ壁で動けない方向を、盤面上で伝える必要がある。

## 操作試作

調査用の単一 HTML を `/tmp` に作り、pa-zzle のプレイ画面と同じ寸法の枠に盤面を置いた。リポジトリには追加していない。

- 枠: ブランドの帯 28px、プレイの見出し 72px、盤面の領域（左右 12px・上下 8px の余白）、下部の操作欄 112px。既存のパーキングジャム・ウォーターソートの操作欄（`h-28`）と同じ高さにした。
- 盤面: 6×6〜14×14。岩の割合は約16%。開始位置から最も手数のかかる止まれるマスをゴールにした（最短 8〜12 手）。
- 入力方式（URL パラメーターで切り替え）
  - 盤面スワイプ: 盤面を含む領域全体（`main`、`touch-action: none`）で受ける。指が 18px 動いた時点で、縦横の大きい方の向きを1回だけ確定する。指を離すまで待たない。
  - 方向ボタン: 48px 角のボタンを逆T字形に4つ並べる（間隔 4px）。左に 48px の待ったボタンを置く。
  - 駒の周りのタップ: 盤面内をタップすると、駒の中心からタップ位置への縦横の大きい方の向きへ滑らせる。駒の上をタップしたときは何もしない。
  - 矢印キー
- 滑る時間: 距離比例（基準 50ms + 1マス 30ms、上限 380ms）と一定（150ms）を切り替える。緩急も切り替える。
- 滑っている途中の入力: 3方式を切り替える。
  - 即時: 入力した時点で盤面の状態を進める。表示中の滑りは終点へ飛ばして、次の滑りを始める。
  - 待ち行列: 表示中の滑りが終わってから次の入力を処理する。
  - 捨てる: 滑っている間の入力を無視する。
- フィードバック
  - 滑った跡: 直前に通ったマスを薄く塗る。
  - ゴール通過: 駒がゴールを通る時刻に、ゴールの輪を一度だけ脈打たせる。
  - すぐ壁: 駒を入力方向へ少し押して戻す。手数は増やさない。
  - クリア: ゴールのマスを塗り替え、輪を広げる。0.7秒後に結果の表示へ移る。クリア後の入力は無視する。
- 床の見分け: 盤面にふつうの床（そこで止まる床）、穴、矢印床を散らして描く表示も作った（ルールには使わない）。

操作試作は調査用であり、本番の画面構成や見た目として採用するものではない。

## 実ブラウザ結果

Playwright と Chromium（headless）を使い、タッチ入力を有効にして（`hasTouch` / `isMobile`）測った。スワイプは CDP の `Input.dispatchTouchEvent` で発生させ、ブラウザーの Pointer Events として受け取った。

全条件で `pageerror` 0、意図しない `console.error` 0、failed request 0 だった。横スクロールと縦スクロールは生じず、スワイプ後も `scrollX` / `scrollY` は 0 のままだった。

### 盤面の寸法

盤面の幅はどの viewport でも画面幅で決まり、高さには余裕があった。方向ボタンを置いても、操作欄の高さは既存ゲームと同じ 112px に収まる。そのため、方向ボタンの有無で盤面の大きさは変わらなかった。

| viewport | 盤面 | 8×8 | 10×10 | 12×12 | 14×14 | 盤面下〜操作欄の余白 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 320×568 | 296px | 36.3px | 29.0px | 24.2px | 20.7px | 30px |
| 360×640 | 336px | 41.3px | 33.0px | 27.5px | 23.6px | 46px |
| 360×780 | 336px | 41.3px | 33.0px | 27.5px | 23.6px | 116px |
| 390×844 | 366px | 45.0px | 36.0px | 30.0px | 25.7px | 133px |

表の 8×8〜14×14 の値は1マスの幅。駒の直径はマスの 72% で、12×12 の 320px では 17px、14×14 では 15px になる。

### 操作方式の比較

試行回数は条件ごとに 40 回。タップの位置には、指の接触誤差を仮定した正規分布のずれ（標準偏差 6px / 9px）を加えた。仮定に基づくモデル試験であり、人のプレイ試験ではない。

| 方式 | 結果 | 主な問題 |
| --- | --- | --- |
| 盤面スワイプ | 320px・12×12 と 390px・10×10 で、角度のずれ 0° / ±30° / ±40° のすべてが正しい方向になった（各 40/40）。18px 未満の揺れとタップ 30 回では一度も動かなかった。390px では約3割のスワイプが盤面の外の余白から始まり、すべて認識された | 45° 付近の斜めのスワイプは、どちらの向きにもなり得る。端から始まる横スワイプは、OS やブラウザーの戻るジェスチャーと競合し得る（後述） |
| 方向ボタン | 48px 角。ずれ 0 / 6 / 9px で、どちらの viewport でも 40/40 が正しい方向になった | 盤面から視線が離れる。盤面と同時に視野に入るが、操作のたびに目を盤面とボタンの間で動かす |
| 駒の周りのタップ | 隣のマス・2マス先・3マス先を狙って、ずれ 9px でも誤った方向は 0。320px・12×12 で隣のマスを狙うと、40 回中 2 回が駒の上に当たり何も起きなかった | 隣のマスを狙うと、指の接触面（直径約10mmと仮定、約38px）だけで隣のマスと駒の半分が隠れる。手のひら側はさらに隠れる。また、「タップしたマスへ行く」と受け取られやすく、実際には駒がそのマスを通り過ぎる。迷路の目的地タップとも意味が食い違う |

モデル上はどの方式も方向を正しく判定できた。差が出るのは、指で盤面が隠れること、意味の受け取り方、片手で操作できるかである。

- 片手操作: 390×844 では盤面が y=233〜599px にあり、親指が届きにくい上側に寄る。スワイプを盤面の外の余白（盤面の下 133px を含む）でも受けると、親指の届く下側で操作できる。方向ボタンは y=736px 以降にあり、片手でも押しやすい。
- 画面端: headless の Chromium では、画面端 0〜8px から始めた横スワイプも 10/10 認識された。ただし、実機の OS やブラウザーの戻るジェスチャーは検証できていない。氷の床迷路のスワイプは1回ごとの方向だけを決め、始める位置を問わない。迷路の「なぞる」操作と違って端から始める理由がないので、実害は小さい見込み。代わりの操作として方向ボタンがある。
- 誤った方向への入力の重さ: 生成した盤面（8×8〜12×12、各8問）で到達できる局面の全手を調べた。逆方向へ入力して元のマスへ戻れる手は、8×8 で 59.5%、10×10 で 58.2%、12×12 で 52.8% だった。4〜5割の手は逆方向へ入力しても戻れない。迷路では来た道を戻れば済むが、氷の床迷路では待ったが欠かせない。

### 滑る時間

最長の滑り（12×12 で 11 マス）について、`requestAnimationFrame` ごとに駒の中心がどのマスにあるかを記録し、途中のマスが何フレーム映るかを数えた。headless でのフレーム間隔は約 16.4ms（約60Hz）で、各条件を3回測った。

| 時間の決め方 | 緩急 | 11マスの時間 | 途中のマスの最少フレーム | 一度も映らないマス |
| --- | --- | ---: | ---: | ---: |
| 一定 150ms | 加減速あり `cubic-bezier(0.3, 0, 0.2, 1)` | 150ms | 0 | 10マス中4 |
| 一定 250ms | 等速 | 250ms | 1 | 0 |
| 距離比例 50 + 30ms/マス（上限 380ms） | 加減速あり `cubic-bezier(0.3, 0, 0.2, 1)` | 380ms | 1 | 0 |
| 距離比例 50 + 30ms/マス（上限 380ms） | 弱い加減速 `cubic-bezier(0.25, 0.1, 0.45, 1)` | 380ms | 1 | 0 |
| 距離比例 50 + 30ms/マス（上限 380ms） | 等速 | 380ms | 2 | 0 |
| 距離比例 40 + 35ms/マス（上限 420ms） | 等速 | 420ms | 2 | 0 |

時間を一定にすると、長い滑りで途中のマスが映らない。スライドパズルと同じ 150ms では、11マス中4マスが一度も描かれなかった。そのため、ゴールを通過したことが動きから読めない。加減速をつけると、中間の速度が上がり、1フレームしか映らないマスが出る。

距離比例かつ等速にすると、どのマスも2フレーム以上映った。距離ごとの時間は 1マス 80ms、3マス 140ms、5マス 200ms、7マス 260ms、11マス 380ms で、短い滑りが間延びしない。上限があるので、上限を超える距離（13マス以上）ではマスあたりのフレームが減る。12×12 までなら上限 380ms 以内に収まる。

### 滑っている途中の連続入力

12×12・390px で、途中でクリアしない3手（各2マス以上）を素早く入力した。方向ボタンは約 50ms 間隔で、3手を約 200ms で入力した。スワイプは1回約 30ms で、3手を約 300ms で入力した。各方式 10 試行で、最終位置が「3手をすべて順に適用した位置」と一致したかを数えた。

| 方式 | 入力 | 最終位置が入力どおり | 適用された手 | 最後の入力から表示が止まるまで |
| --- | --- | ---: | ---: | ---: |
| 即時 | 方向ボタン | 10/10 | 30/30 | 約 200ms |
| 即時 | スワイプ | 10/10 | 30/30 | 約 210ms |
| 待ち行列（素朴な実装） | 方向ボタン | 10/10 | 30/30 | 約 510ms |
| 待ち行列（素朴な実装） | スワイプ | 9/10 | 30/30 | 約 430ms |
| 待ち行列（順序を直した実装） | 方向ボタン / スワイプ | 10/10 / 10/10 | 30/30 / 30/30 | 約 510ms / 約 450ms |
| 捨てる | 方向ボタン | 5/10 | 10/30 | 約 80ms |
| 捨てる | スワイプ | 5/10 | 11/30 | 約 50ms |

- 捨てる方式では、入力した手の3分の2が失われた。誤った方向への入力と同じく取り返しのつかない結果になり得るので、採らない。
- 待ち行列方式は、表示が入力より最大 0.5 秒ほど遅れる。素朴な実装では入力の順序が入れ替わった。表示中の滑りが終わってから、終了の通知で待ち行列を処理するまでの間に次の入力が来ると、待っている入力より先に処理されてしまう。
- 即時方式では、盤面の状態が入力の順序だけで決まる。表示の遅れは最後の1手分だけになる。

### フィードバック

320px・10×10 で確認した。

- ゴール通過: 9マスの滑りでゴールを通過したとき、ゴールの輪の脈打ちが再生された。通過後も、滑った跡がゴールの前後に連続して残る。そのため、ゴールを通り抜けたことは止まった後の静止画でも読める。輪の脈打ちは控えめで、跡より弱い。
- すぐ壁: 押し戻しの動きが再生され、手数は 0 のまま変わらなかった。押し戻しはマスの 14%（10×10 の 320px で約 4px）で、静止画ではほとんど見えない。12×12 では約 3px まで小さくなる。
- クリア: 最短 9 手を方向ボタンで入力すると、ゴールのマスの塗り替えと輪の広がりが見えた。0.7 秒後に結果の表示へ移り、その後の入力は無視された。
- 動きを減らす設定（`reducedMotion: 'reduce'`）では、動きを再生せずに駒が即座に移動した。最短手順で入力してもクリアに到達した。この設定でも滑った跡は残るので、通過は伝わる。

## 視覚確認

320px と 390px で、6×6・10×10・12×12・14×14 のスクリーンショットを確認した。

- 10×10（320px で 29px）は、岩の並び・駒・ゴールを余裕をもって読める。
- 12×12（320px で 24px）でも、行・列に並ぶ岩、駒、ゴールの輪を識別できる。ゴールの輪は 14px 程度まで小さくなる。マスの斜めの光沢模様は、この大きさでは雑音になる。
- 14×14（320px で 21px）は、駒が 15px、ゴールの輪が 12px ほどになる。止まる位置を行・列ごとに読む密度が高く、余裕がない。

追加の床を描き分けたときの見分けやすさも、320px の 8×8〜12×12 と、グレースケールで確かめた。

- 最初の案では、穴（暗い円）と駒（濃い青の円）が、色でも形でも紛らわしかった。グレースケールでは区別できなかった。
- ふつうの床をゴールと同じ系統の砂色にすると、ゴールの背景色と競合した。
- 改善案で確認した。穴は角の丸い四角のくぼみにし、駒は白い縁取りの円にした。ふつうの床は灰緑に点模様を入れた。ゴールは氷の上の輪と中心の点にした。この案では、12×12・320px とグレースケールでも、5種類（氷・岩・ふつうの床・穴・矢印床）と駒・ゴールを見分けられた。
- 改善案でも、穴（濃い四角）と岩（灰色の四角）は、明るさの差だけで分けている。14×14 では紛らわしくなる。
- 矢印床の矢印は、12×12 の 320px で 13px 程度。向きは読めるが、盤面に多いと密度が上がる。

## 盤面上限の判断

**スマホプレイ成立性は通過とする。**

入力はスワイプと方向ボタンで、マスの大きさに依存しない。上限を決めるのは操作の精度ではなく、止まる位置を行・列ごとに読む視認性である。

- 通常提供の標準上限: 10×10（320px で 29px）
- 12×12（320px で 24px）: 氷と岩だけの盤面なら、上限として提供できる。矢印床や穴のように記号を持つ床を入れるなら、10×10 を上限の目安とする。
- 14×14 以上: 初期提供の範囲外とする。

迷路は 15×15 程度まで全体表示で成立するとしたが、氷の床迷路では上限を下げる。迷路は隣の通路を局所的にたどればよいが、氷の床迷路では1手ごとに行・列の端までを読む必要がある。

## 本実装への申し送り

- 主操作は盤面スワイプ、代わりの操作は方向ボタンとし、両方を常に使えるようにする。駒の周りのタップは採らない。
  - スワイプは盤面だけでなく、プレイ画面の盤面の領域全体（盤面の外の余白を含む）で受け、`touch-action: none` を付ける。
  - 方向は、指が閾値（試作では 18px。パーキングジャムの `SWIPE_THRESHOLD` と同じ値）を超えた時点で1回だけ確定する。1回の指の動きで動かせるのは1手だけにする。
  - 方向ボタンは、既存の操作欄の高さ 112px に収まる 48px 角の逆T字形にし、待ったと並べる。`@theme` にタップ領域のトークンは無いので、既存の `UndoButton`（`size-12`、48px）の大きさに揃える。
- 1回の入力で何マスも動き、逆方向でも戻れない手が4〜5割ある。待ったはすぐ押せる位置に置く。
- 連続入力は即時方式にする。
  - 入力した時点で session を進め、受け付けた入力を捨てない。クリアした後の入力は受け付けない。
  - 表示中の滑りは終点まで飛ばしてから次の滑りを始める。
  - スライドパズルのように CSS の transition の行き先を途中で差し替えると、駒が滑りの途中から次の終点へ斜めに動き、岩をすり抜けて見える。これは使わない。
  - 待ち行列にする場合は、終了の通知より前に来た入力が割り込まないように、待っている入力があれば必ずその後ろへ並べる。
- 滑る時間は距離に比例させ、等速にする。目安は「基準 40〜50ms + 1マス 30〜35ms、上限 380〜420ms」。演出の値はゲーム固有の名前付き定数にする（共通の `--duration-*` に合わせない）。
- 盤面へ渡す操作の結果は、スライドパズルの `SlidePuzzleOperation` やパーキングジャムの `ParkingJamOperation` に倣い、`play/` から渡す。中身は滑りの始点・終点・ゴール通過・すぐ壁などとする。`ui/` で滑りの経路をルールから計算し直さない。
- フィードバック
  - ゴール通過は、滑った跡（通ったマスの塗り）を主にする。跡は止まった後も残し、動きを減らす設定でも伝わるようにする。
  - すぐ壁は `@/lib/motion` の `playRejectionShake` に入力方向へ押し戻す keyframes を渡して再生し、手数を増やさない。押し戻しはマスの割合ではなく、小さい盤面でも見える量（目安 5〜6px 以上）を確保する。
  - クリアは `playAnimations` で再生する。
- 既存実装から再利用できるもの
  - キーボード: スライドパズルの `SlidePuzzlePlay` の `keydown` の扱い。プレイ画面の範囲内だけで受け、修飾キー付きと `defaultPrevented` を除く。
  - スワイプの判定: パーキングジャムの `getSwipeDirection` は車の向きに縛られ、指を離した時点で判定する。別ゲームの実装は直接 import しない。共通化する場合は、共通の責務として名前を付けて置き場所を決める。
- 床を描き分けるときは、駒・ゴール・穴を同じ「暗い円」系統にしない。ふつうの床とゴールの背景を同じ色系統にしない。12×12 では、氷の模様などの細かい装飾を省く。
- 本実装でも 320 / 360 / 390px の幅で、スワイプ・方向ボタン・連続入力・クリアを Playwright で確認する。

## 未確認の事項

- 実機（iOS Safari、Android Chrome）での画面端の戻るジェスチャーとの競合、120Hz 表示での見え方。
- 45° 付近の斜めのスワイプを、判定しない（何もしない）扱いにするか。誤った方向への入力の損失が大きいので、判定しない範囲を設ける案がある。
- すぐ壁の入力や、ゴール通過を手数・評価に含めるか（仕様・成績評価の担当で決める）。
- 床の種類の採否と、それぞれの最終的な見た目。本書の改善案は、見分けられるかを確かめただけである。
- ダークテーマでの盤面の色。

## 検証方法

Claude Code の実行環境で、導入済みの Playwright（`require('playwright')`）と Chromium を使い、`/tmp` に置いた調査用 HTML を `file://` で開いた。実アプリへの組み込み、Vite の起動、依存の導入はしていない。

各試験は viewport を 320×568 / 360×640 / 360×780 / 390×844（`deviceScaleFactor: 2`、`hasTouch`、`isMobile`）にして新しいコンテキストで行った。`pageerror`、`console.error`、`requestfailed` を収集した。スクリーンショットは盤面・フィードバック・床の描き分け（カラーとグレースケール）を目視で確認した。
