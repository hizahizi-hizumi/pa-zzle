[詰将棋調査](詰将棋調査.md) の4ゲートの先で、本実装に入る前に決めておく前提を整理する。導入調査であり、現在仕様の正本ではない。本文は調査時点の判断と、本実装の各段で追記した仮決定を記録する。実装・検証を経て採用した契約は [SPEC-015 詰将棋](../../../プロダクト/仕様/パズル/SPEC-015.md) を正とし、調査時点の判断から実装で変わった点は §10.4 にまとめる。

### 事実と推測の書き分け

根拠の種類を次の見出し語で区別する。

- **事実（リポジトリ）**: 現在のリポジトリの文書・コードから確認したこと。
- **事実（計測）**: 調査用PoCで測った結果。条件と限界は各PoC文書に書く。
- **外部知見**: 将棋の公式ルール・公開資料・外部OSSで確認したこと。
- **推測**: 上の3つから導いたが、実プレイや問題集合で検証していないもの。
- **AI判断（仮決定）**: 人間の判断を待たずに本実装を進めるため、関係文書の原則に沿って AI が推奨案で決めたもの。§10「仮決定一覧」に理由・比較した案・最終レビューで判断してほしい点を残す。

見出し語を付けていない §1〜§9 の記述は、調査時点の判断として各節の本文と参照先PoCの区分に従う。§1〜§9 と §10 が食い違う場合は §10 を優先する。

### 本実装の進め方（AI判断）

本実装は、[リフレクション](../リフレクション/リフレクション実装前提調査.md) と同じく、各段を前段の上に積む PR スタック（§11）で進める。人間のレビューは全段の実装後にまとめて行う前提で、途中で判断を求めず、各論点は §10 の仮決定で進める。差し戻し時の手戻りを小さくするため、次を作りの条件にする。

- 将棋のルール（合法手・王手・禁手）はルールエンジンの薄い境界の内側に閉じ、詰み探索・生成・UIはその境界だけを使う（§10「ルールエンジン」）。
- 5段階の数値境界は分析器のコードを正とし、文書へ固定値を書かない（§10「難易度」）。
- スコアの配点は仮置きと明記し、保存するのは生のプレイ事実だけにする（§8）。
- 利用者に見える名称は1か所の定義から参照する（§10「ゲームIDと表示名」）。

## 1. 初期提供範囲

V1では、詰将棋の全作品領域を一度に扱わず、validator・難易度分析・供給が説明可能なsupported subsetへ限定する。

第一候補:

- 主に1 / 3 / 5手
- 攻方は毎手王手
- 玉方は最長抵抗
- 玉方は駒箱を持つ
- 二歩・打歩詰・行き所なし等の通常の禁手を守る
- 作意手数より短い詰みを持たない
- accepted範囲では攻方の正解を一意に扱える
- 駒余りを棄却
- validator / oracleで解釈が割れる灰色問題を通常提供しない
- 玉方の駒打ちが作意に現れる問題は初期supported subset外

1手詰はルール学習・チュートリアルにも使えるが、「1手だから難易度1」とはしない。

### 1.1 V1 supported subset（AI判断（仮決定））

主に3手・5手詰を通常難易度の対象にする。1手詰は通常難易度の手数対応として扱わず、供給上必要なら混ぜてよいが「1手だから易しい」とはしない。その他の条件（毎手王手・最長抵抗・駒箱・早詰なし・攻方正解一意・駒余り棄却・玉方合駒が作意に現れる問題は対象外・灰色問題は提供しない）は上の第一候補のまま採る（§10「V1 supported subset」）。

## 2. オフライン供給アーキテクチャ

重いsolverを通常プレイ時に毎回動かす必要はない。

```text
候補生成
  ↓
strict validator
  ↓
独立 oracle cross-check
  ↓
supported / unsupported / invalid
  ↓
難易度分析
  ↓
品質・多様性フィルタ
  ↓
レベル1〜5の事前生成問題集
  ↓
初期局面 + 作意/応手木 + 誤手反証情報
  ↓
ブラウザ
```

ブラウザ側は、盤面状態、合法性、入力、事前生成された玉方応手・反証線の再生を中心にする。

### 2.1 実行時の役割分担（AI判断（仮決定））

問題は事前生成の問題集（`problem-pool.json`）から出し、実行時に generator は走らせない。ブラウザに持つのは初期局面と作意・玉方の最長抵抗の応手木までとし、合法だが不正解の王手への玉方の反証手は、ブラウザで残り手数以内の小さな探索で求めてよい（V1 は短手数なので軽い）。誤王手ごとの反証線を問題集へ全部持たない（§10「合法だが不正解の王手」）。

独立 oracle は外部OSSをローカルでの照合にだけ使い、製品・CIには入れない（§10「独立oracle」）。

## 3. 問題identity

少なくとも次を追跡できる形にする。

- generator version
- seed / parent identity
- validator version
- difficulty analyzer version
- canonical position fingerprint
- solution-tree fingerprint
- motif fingerprint
- problem pool version / index

独立oracleをCIや生成時に使う場合は、oracle名・versionも記録候補とする。

### 3.1 問題識別情報（AI判断（仮決定））

問題identityは generator version / seed / 生成条件を基本にし、canonical position・solution-tree・motif の fingerprint で重複を管理する。独立 oracle はローカル照合だけに使うため、問題 identity には含めず、照合の記録（oracle名・版・照合件数・不一致）を問題集生成の記録に残す（§10「問題identity」）。

## 4. プレイ契約

### 攻方だけを操作する

利用者は攻方だけを操作し、玉方は事前検証済みの最長抵抗線を自動で応手する。

### 非合法入力

- 動けない駒
- 王手にならない着手
- 二歩
- 打歩詰
- 行き所のない駒

等は、パズルの誤答ではなく入力 / ルール違反として着手させない。

### 合法だが不正解の王手

即座に「不正解」とだけ戻すのではなく、玉方の反証手を盤面で見せる。必要なら数手進め、「この筋では詰まない」ことを理解して攻方の判断地点へ戻れるようにする。

正解候補や全合法王手を通常UIで常時強調しない。考える部分を補助機能で置き換えない。

### 4.1 プレイ契約の採用（AI判断（仮決定））

上の3項をそのまま採る。合法だが不正解の王手では、玉方の反証手を盤面で見せ、攻方の判断地点へ戻れるようにする。非合法入力は着手させず、誤答として数えない（§10「操作する側」「非合法入力」「合法だが不正解の王手」）。

## 5. ヒント・答え

候補:

- 段階的ヒント
- 正解初手のみ表示
- 作意手順の再生

補助を使った事実は記録する。ヒントが難易度分析の前提を変える場合は、補助ありプレイを問題難易度そのものへ混ぜない。

### 5.1 V1 では入れない（AI判断（仮決定））

ヒント・答え表示はV1では入れない。合法だが不正解の王手への反証の再生が、詰まったときに考え直す手がかりを担う（§10「ヒント・答え」）。

## 6. オンボーディング

詰将棋は既存のpa-zzle候補より前提知識が多い。

少なくとも説明が必要:

- 各駒の動き
- 成り / 不成り
- 持駒と駒打ち
- 攻方は毎手王手
- 玉方は盤上に無い全駒を使える
- 玉方は最長抵抗
- 二歩 / 打歩詰等

ルール学習の負荷を問題難易度へ混ぜない。1手詰を使った短いチュートリアルを通常難易度とは別に持つ案を優先する。

### 6.1 遊び方（AI判断（仮決定））

V1 は既存ゲームと同じ形式の遊び方（初めて遊ぶときだけ自動で開き、読んでいる時間は経過時間に含めない）に、駒の動き・毎手王手・駒箱・最長抵抗・二歩 / 打歩詰を載せる。1手詰チュートリアルは後続にする（§10「遊び方」）。

## 7. 難易度

導入調査では5段階の成立見込みまで確認し、最終閾値は決め切らない。

製品実装では [詰将棋難易度PoC](詰将棋難易度PoC.md) の仮説を起点に、[難易度開発手順](../../難易度開発手順.md) に従って代表・境界・異常問題を人間の実プレイと照合する。

評価不能な高度手筋をレベル5へ押し込まず、supported外または要レビューにする。

### 7.1 5段階の軸（AI判断（仮決定））

手数ではなく、初手の王手候補数（rootChecks）・もっともらしい誤王手（plausibleWrong）・深く続く紛れ（deepDecoyCount）・玉方の応手分岐（defenseBranching）・手筋で5段階に分ける。数値境界は分析器のコードを正とし、段07で [詰将棋難易度](詰将棋難易度.md) に根拠を残した（§10「難易度」「難易度分析」「5段階の分類」）。

## 8. 成績・記録

保存候補となる生の事実:

- 経過時間
- 合法な誤王手の回数
- 誤筋を反証まで進めた回数
- 戻った回数
- やり直し回数
- ヒント利用
- 答え表示
- 非合法入力回数（UI摩擦の診断用）

スコア式は調査段階で固定しない。誤王手の試行はデジタル詰将棋の学習・反証体験でもあるため、回数をそのまま大きな減点へ結び付けない。

### 8.1 成績と記録（AI判断（仮決定））

読みの確かさ20点（誤王手1回 −5点、4回で0点）と速さ80点（問題ごとの基準時間以内で満点、3倍で0点）の100点満点にする。反証を見た回数・戻った回数・元に戻した回数・盤面を戻した回数は減点せず、非合法入力の回数は評価に使わない。記録には生の事実・identity・問題集の版と番号・作業の量を保存し、点は読み出し時に計算する。自己ベストは難易度ごとに、評価点・基準時間との差・誤王手の回数で比べる。根拠・比べた案・プレイ例は [詰将棋成績評価](詰将棋成績評価.md)（§10「スコアの観点と評価式」「基準時間」「プレイ記録」）。

## 9. スマホUI

- 盤上駒タップ → 移動先タップ
- 持駒タップ → 打つ升タップ
- 成 / 不成は必要なときだけ選択
- 選択中の駒は明瞭に示す
- 正解 / 王手候補を通常表示で漏らさない

320pxでは1升約34pxになるため、本番の誤タップ実測が必要。問題が出る場合のみ盤面領域ズームを検討する。

### 10.1 詰み探索・strict validator の計測と外部 oracle 照合（段03）

**事実（計測）**: 開発コンテナ（4コア）で、`bun` から1プロセスで測った。別の計測と並行した時間帯を含むので、目安として読む。

| 対象 | 結果 |
| --- | --- |
| 王手・受けの列挙 | 乱数で王手と受けを進めた5,920局面で、`search-position.ts` の列挙は `moves.ts` の全合法手から選ぶ列挙と全局面で同じ手を返した。合計時間は 4,477ms → 612ms（1局面 約0.76ms → 約0.10ms、局面の複製を含む） |
| 5手詰の検証（採用される問題） | 固定テストの5手詰1問で `validateTsumeShogiProblem` 1回 約90〜180ms |
| 5手として検証（乱数局面） | 玉の周りに駒を乱数で置いた206局面: 不詰の局面 p50 34ms / p90 199ms / p99 473ms / 最大 508ms、詰むが不採用の局面 p50 13ms / p90 294ms / 最大 676ms |
| 3手として検証（乱数局面） | p50 約5ms / p90 約20ms |
| 誤王手への反証 | 5手詰の初手の誤王手11通りで1回 0.8〜21ms、3手詰の誤王手10通りで1回 0.2〜4ms |

**事実（計測）**: 外部 oracle（shtsume v1.2.7e）との照合。`bun scripts/compare-tsume-shogi-oracle.ts --oracle <shtsume> [--plies 3|5] [--count N] [--verdict accepted]` を `frontend/` で実行した。照合の分類は、oracle の答えが自作の判定と同じもの（一致）、合駒・無駄合・2手変長・駒余りの見方の違いで説明できるもの（解釈差）、説明できないもの（不一致）に分ける。

| 照合した局面 | 一致 | 解釈差 | 不一致 |
| --- | --- | --- | ---: |
| 乱数局面を3手として500局面 | 不詰 401、作意 1（採用）、合駒の数え方の範囲内の手数 18、詰む（作意は比較対象外）79 | 長い変化 1 | 0 |
| 乱数局面を5手として300局面 | 不詰 236、合駒の数え方の範囲内の手数 12、詰む（作意は比較対象外）51 | 長い変化 1 | 0 |
| 自作が採用した3手詰105局面（乱数局面30,000から） | 作意 60、変化同手数で作意の手数と初手 36 | oracle が駒余りとした参考手順 9 | 0 |

shtsume の探索レベルは 20、1局面の制限時間は1〜3秒（時間切れ 0）。

- 「長い変化」は、oracle の手順の途中で玉方が2手長く逃れて詰む応手があり、oracle が短い手順を作意とした局面（2手変長など）。自作は最長を作意とし、その局面は採用していない（不詰・余詰で `invalid`）。
- 「合駒の数え方の範囲内の手数」は、oracle の手数が「合駒をすべて数える」自作の手数と「合駒をどれも数えない」自作の手数の間に入る局面。無駄合の判定の違いで説明できる。
- 「oracle が駒余りとした参考手順」の9局面は、自作では駒余りの無い一意の作意（例: `7k1/9/6+B2/9/9/9/9/9/9 b SN...` の ▲2二銀打 △1二玉 ▲2四桂打）を持つが、shtsume は駒余りと判断して別の参考手順（5手）を返した。手で読んだ範囲では自作の作意が正しく、shtsume の駒余りの判断（証明駒の扱い）との違いと見ている（**推測**）。
- 無駄合を「王手した駒で合駒を取って、合駒をしなかったのと同じ残り手数で詰む」とする1段だけの判定を使っていた途中の版では、同じ採用3手詰158局面のうち22局面で作意が食い違った（shtsume は遠い飛打ちなど、玉方の利きの無い合駒を無駄合とみなし、最終手に別の詰みを持つ）。この差が「合駒と無駄合」の行の判断の根拠。

手順（ローカルだけで行う。CI・製品には入れない）:

1. `git clone https://github.com/hkijin/shtsume` し、`make` でビルドする（gcc。macOS・MinGW 向けの Makefile だが Linux でもそのまま通った）。
2. `frontend/` で `bun scripts/compare-tsume-shogi-oracle.ts --oracle <shtsume の実行ファイル> --plies 3 --count 500` のように実行する。shtsume は探索レベル（`--level`）が低いと最短でも作意でもない詰み手順を返すことがある（レベル0では、採用した5手詰1問で7手の手順を返した）。段03の照合はレベル20で行った。既定は段04で3にした（§10「oracle の探索レベル」）。`--input` に `{"sfen": ..., "plies": ...}` の JSONL（段04の生成スクリプトの `--details` の出力など）を渡すと、その局面を照合する。
3. 「不一致」が1件でもあれば終了コード 1 で終わる。不一致の局面は自作の判定と oracle の手順を並べて出す。

### 10.2 逆算 generator の計測（段04）

**申し送り**:

- 段07・段08: 起点の作り方（最終手の駒打ちの多さ）と、逆算で作りやすい「捨てて玉で取らせる」筋の偏りを、難易度別の選抜と指紋の上限で補う。変化同手数は3手・5手の半数を超えるので、提供してよいかを判断する（§10「玉方の最長抵抗」）。

| 論点 | 確定 | 理由 |
| --- | --- | --- |
| ヒント・答え | 入れない（現状維持） | `GAME.md`「プレイヤーが考える部分を奪わない」: ルールエンジンが知っている候補・正解を通常UIが無条件に提示しない。既存ゲームも通常UIでヒントや確定できるマスの提示を持たない（SPEC-010・SPEC-012）。詰まったときの手がかりは誤王手への反証の再生が担う |
| 選んだ駒の移動先 | 示さない（現状維持） | 同上。どの手が王手になるかを読むことが詰将棋の考えどころで、移動先を示すと王手の候補が絞れる。一方の「UI自体の迷い」には、指せない手を押したときに理由を示すことで応える（SPEC-015「指せない手」） |
| 変化同手数の問題 | 提供し、玉方は作意の応手を指す（現状維持） | 生成した3手・5手の半数を超え（§10.2）、外すと供給が細る。玉方の応手を1つに決めれば利用者の手順は一意で、攻方の正解の一意性（問題の契約）は変わらない |
| 誤王手の筋の最後の王手 | 玉方は応手を指し、その後に「この筋では詰みません」を出す（現状維持） | `GAME.md`「操作結果を自然に返す」: 詰まないことを説明文だけでなく盤面（玉が逃れた局面）で返す。誤王手の筋のほかの王手と同じ規則で、例外を作らない。内部の残り手数は0で止める（段14） |
| 最終手の余詰 | 棄却する（現状維持） | 攻方の正解を各手番で一意にし（SPEC-015「問題」）、誤王手には必ず反証がある、という playable contract を最終手でも保つ。伝統的な作品との違いは、提供する問題の範囲の選び方で、ルールの違いではない |
| 無駄合の解釈で作意が入れ替わる問題 | 対象外にする（現状維持） | 解釈で答えが変わる問題（灰色問題）は提供しない（SPEC-015「問題」）。入れ替わるのは玉方の作意の応手で、自動応手の正当性を説明できなくなる。除いたのは9問で供給への影響は小さい（§10.5） |
| `tsshogi` への依存とバンドルの増分 | 製品依存のまま、増分（JS gzip +60.0 kB、+10.3%）を許容する | ルールエンジンを自作しない方針（ユーザー合意済み）。MIT で、`puzzle/` の3ファイルだけが import する。生成器と strict validator は本番ビルドに入らない。版上げは依存更新の通常の手順で追い、`puzzle/` の固定テストで確かめる |
| 独立 oracle | ローカルの照合だけに使い、CI・製品に入れない（現状維持） | ユーザー合意済みの方針。品質保証の主体は自作の strict validator と `--verify` で、oracle は問題集を作るときの独立した確認。説明できない不一致の局面は問題集に採らない |
| 問題供給のゲート | `通過` のまま | 問題集の全問を identity から作り直して成立性・分類・作業の量・重複と偏りの上限を確かめ（版 3 でも同じ。§10.6）、分類済みの候補を独立 oracle と照合した。人間が判断すべき体験の論点は残っていない |
| 難易度プレビューの駒の文字の大きさ | 1升 16px（320px）・17px（360px 以上）・26px（PC）のまま | `DESIGN.md` と `@theme` に最小の文字サイズ・最小の押せる大きさの基準は無い。`@theme` の最小の文字（`text-meta` 0.75rem）は共通UIの情報階層の段階で、盤面上の文字はゲーム固有表現として別に判断する（`DESIGN.md` §7）。プレビューは押す対象ではなく、駒の数と配置で読み比べる量を見せる模式図で、1文字ずつ読めなくても伝わる。既存ゲームのプレビューも小さい文字を使う（ナンプレ・スライドパズル 11px）。駒の形（五角形）と成駒の赤で見分けを補う |
| 難易度とスコアの細かい論点 | 今の値のまま、伏せ問題（[最終レビュー](詰将棋最終レビュー.md) §4）の実プレイの結果を受けて調整する | 境界の値、基準時間の係数、誤王手の減点の重さ、0点になる倍率は、人間の実プレイの記録なしに動かしても根拠が増えない。伏せ問題で体感レベルとスコアの納得感がずれたら、[詰将棋難易度](詰将棋難易度.md) §12 と [詰将棋成績評価](詰将棋成績評価.md) §9 の順に見直す |
