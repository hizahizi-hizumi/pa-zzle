## 調査対象

ここでいう「詰将棋」は、実戦局面からの単なるN手詰ではなく、攻方が毎手王手を続け、玉方が最長抵抗し、玉方が駒箱を使える古典的な詰将棋を基本とする。

## ゲート1: 問題供給成立性

### 結論

逆算法による自動生成は成立する。素朴なランダム配置からの完全検証は効率が悪く、**詰み上がりから逆算し、候補を再検証する方式**が本命になる。

独立PoCでは、当初の「盤上駒の非捕獲移動だけ」の逆算から、攻方駒打ち、成り、攻方/玉方の駒取りまで広げた。3手・5手の完全作候補を継続的に作れ、難易度条件を与えた生成も成立した。

一方、玉方の駒打ちを作意に含む問題は現PoCの供給経路では成立しなかった。V1はここを無理に含めず、**玉方合駒が作意に現れないsupported subset**を第一候補とする。これは最終ルール仕様ではなく、初期供給の安全な境界である。

詳細は [詰将棋供給実験](詰将棋供給実験.md)。

**ゲート1判定: 確認中。** 小規模供給は成立。製品用strict validatorと独立oracleの一致、大規模プールの供給率・重複率・性能を実装フェーズで確認する。

本実装後に `通過` とした（冒頭の「状態」の表）。

## ゲート2: 難易度運用成立性

### 手数を難易度にしない

1手、3手、5手という手数は読みの長さの一要素だが、pa-zzleの5段階そのものにはしない。同じ5手でも、初手王手候補の数、もっともらしい誤手、玉方の応手、手筋の組み合わせで大きく体験が変わる。

PoCで最も安定した観測は、**正解以外の王手がどれだけもっともらしく、どこまで読みを続けないと反証できないか**だった。深さだけでは中〜高帯で飽和するため、深く続く紛れの本数も分けて扱う。

暫定的な体験差は次の通り。

| レベル | 体験仮説 |
| --- | --- |
| 1 | 初手王手候補がほぼ正解1本で、局所確認で進められる |
| 2 | 浅く読むと崩れるもっともらしい誤王手がある |
| 3 | 少数の誤王手が数手続き、比較が必要 |
| 4 | 深く続く紛れが複数あり、玉方応手や手筋を比較する |
| 5 | 多数の深い紛れを比較し、複数手筋・非局所的な利きを扱う |

これは最終閾値ではない。導入調査で必要なのは、5段階の意味ある挑戦差と供給の見込みであり、数値境界の確定は難易度開発で行う。

5手詰だけを使った小規模プールで、各帯10問、計50問を作り、各帯で解答木fingerprint 10/10ユニークまで確認した。

詳細は [詰将棋難易度PoC](詰将棋難易度PoC.md)。

**ゲート2判定: 確認中。** 5段階成立の見込みは確認できた。最終分類、代表・境界問題の人間照合、大規模供給は難易度実装フェーズへ持ち越す。

## ゲート3: スマホプレイ成立性

9×9盤、攻方持駒、玉方駒箱、盤上駒選択、持駒打ち、成/不成の基本操作を持つPoCを320 / 360 / 375 / 390pxで確認した。

- 390px: 盤面約374px、1升約41px
- 320px: 盤面約306px、1升約34px
- 横スクロールなし
- 2段階の「駒を選ぶ → 行き先を選ぶ」で成立

320pxでは一般的な44pxタップ目標より小さいため、製品UIで誤タップを再確認する。必要なら盤面領域だけのズーム/パンをfallbackにする。

詳細は [詰将棋スマホ操作PoC](詰将棋スマホ操作PoC.md)。

**ゲート3判定: 通過。** 盤面サイズ自体は導入阻害要因ではない。

## ゲート4: 導入判断

### pa-zzleでの価値

詰将棋の中心は、駒を動かす操作量ではなく、**複数の王手候補を比較し、玉方の最善応手を読み、もっともらしい誤手を反証すること**にある。既存の数字・配置・ソート系パズルとは異なる「先読みと反証」の体験を追加できる。

### 導入上の主なリスク

- 余詰、駒余り、無駄合、変同、変別、非限定など、問題品質の契約が通常のN手詰より細かい
- 駒の動き、成り、持駒、二歩、打歩詰等の前提知識が多く、オンボーディング負荷が高い
- 高品質な問題供給では、局面重複だけでなく詰み筋・手筋の多様性を管理する必要がある
- 玉方合駒を含む作品は現PoCのsupported subset外

### 現在の判断

**条件付き保留。** 実装候補へ進める技術的価値は高いが、候補台帳上はまだ正式な `実装候補` にしない。

実装フェーズで最低限次を成立させる。

1. strict validatorと独立oracle harnessを作り、accepted候補で重大不一致を出さない。
2. V1のsupported subsetを明示し、余詰・駒余り・無駄合等の品質状態を別々に扱う。
3. 難易度PoCの5段階仮説を製品用分析器へ移し、代表・境界問題を人間の実プレイと照合する。
4. 事前生成プールの規模、重複率、生成・検証時間を本番条件で決める。
5. 操作とルール学習のオンボーディングを本番UIで確認する。

本実装は、上の5項を段ごとに成立させる前提で、[詰将棋実装前提調査](詰将棋実装前提調査.md) §10 の仮決定と §11 の実装スタックで進める。独立oracleは外部OSSをローカルの照合にだけ使い、CIには入れない。正式な `実装候補` への変更は、全段の実装と人間レビューの後に判断する。本実装後の各ゲートの状態は冒頭の「状態」の表にまとめた。

実装前提は [詰将棋実装前提調査](詰将棋実装前提調査.md)、名称・権利は [詰将棋名称・権利調査](詰将棋名称・権利調査.md) を参照する。
