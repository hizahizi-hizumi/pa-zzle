### 事実と推測の書き分け

根拠の種類を次の見出し語で区別する。

- **事実（リポジトリ）**: 現在のリポジトリの文書・コードから確認したこと。
- **事実（計測）**: 調査用スクリプト・PoC で測った結果。条件と限界は各PoC文書に書く。
- **外部知見**: BGA版・原型・公開資料で確認したこと。
- **推測**: 上の3つから導いたが、実プレイや問題集合で検証していないもの。
- **AI判断（仮決定）**: 人間の判断を待たずに本実装を進めるため、関係文書の原則に沿って AI が推奨案で決めたもの。§19「仮決定一覧」に理由・比較した案・最終レビューで判断してほしい点を残す。

見出し語を付けていない既存の節（§2〜§17 の PoC 由来の記述）は、各節の本文と参照先PoCの区分に従う。

### 本実装の進め方（AI判断）

本実装は、各段を前段の上に積む PR スタック（§20）で進める。人間のレビューは全段の実装後に1回だけ行う前提で、途中で判断を求めず、各論点は §19 の仮決定で進める。差し戻し時の手戻りを小さくするため、次を作りの条件にする。

- 5段階の組み合わせ定義（推論レベル × 盤面サイズ × ピース数）はデータとして持ち、分類コードへ埋め込まない（§14.4）。

- ピクトグラムは採用案だけでなく代替案と検討記録を残す（§20 段07）。
- スコアの配点は仮置きと明記し、保存するのは生のプレイ事実だけにする（§16）。
- 利用者に見える名称は1か所の定義から参照する（§18）。

## 2. 守る遊びの核

このパズルで残すべき体験は、**外から観測できるレーザーの結果だけを手掛かりに、見えない光学系の配置を逆算すること**である。

面白さの中心は、単に鏡を置いて結果を合わせることではない。

- 短い光路から置ける位置を絞る
- 同じレーザー経路の入口と出口を対応付ける
- 1つの鏡が複数の外周ヒントを同時に説明する
- 複数レーザーの交差・共有マスから候補が連鎖的に減る
- 手持ちピースの残数が新たな制約になる
- 仮置きをする場合も、どの仮定がどのヒントと矛盾するかを追う

pa-zzleでは、UIが「この配置は正解に近い」と逐次教える体験にしない。

BGA版は現在の配置で目標と一致しない外周ヒントを赤枠表示する。これは高速対戦では便利だが、配置を試して赤枠の増減を見るだけの試行錯誤を促進できる。実際、BGAについて「プログラムが値を再計算するので試し置きを繰り返した」という利用者レビューもある。

pa-zzleでは、**思考の結果として置き、結果の物理的な光路を確認すること**と、**正誤を機械が教えること**を分ける。

### 2.1 GAME.md の原則への対応（AI判断）

| GAME.md の原則 | リフレクションでの具体化 |
| --- | --- |
| パズルそのものを主役にする | 盤面と四辺の外周ヒントを画面の主役にし、スマホ幅いっぱいに置く。ピースのストックは盤面の直下にまとめる。経過時間などの計測値はヘッダーに控えめに置き、盤面の周りに並べない。 |
| プレイヤーが考える部分を奪わない | 正解配置との比較、ヒントごとの一致・不一致、置ける位置の候補を通常UIで示さない。光路表示は現在配置の物理的帰結だけを示し、目標との照合結果を付けない（§11）。 |
| UIの迷いや操作負荷を難しさにしない | ドラッグを必須にせず、ストック選択 → セルタップで完結させる。ストックは44px級とする。セルは調査PoCの7×7・390pxで約45pxだったが、本実装では外周ヒントとの隙間を取ったため約42pxになる（§15、§19「外周と盤面の余白」）。ピースの機能は形だけで読めるようにする（§9）。 |
| 題材と表現を一致させる | 内部の遷移表を記号で描かず、鏡・二重鏡・反射体・吸収体として形で見せる。光路は盤面上をレーザーが進み、曲がり・跳ね返り・吸収される線として描く。 |
| 操作結果を自然に返す | 配置・移動・回収は短い状態変化で返す。光路表示は線が伸びる動きで返し、演出中も次の入力を受け付ける。クリアは全光路が揃う演出で返す。 |
| 難易度を人間の体験として扱う | 推論の深さを主軸に、盤面サイズとピース数は許す範囲として組み合わせる。盤面サイズやピース数だけでレベルを決めない（§14）。 |
| 繰り返し遊べる | 事前生成した問題集から毎回別の問題を出し、回転・反転の同型を除く（§7、§8）。 |
| 達成とプレイの出来を分ける | クリアは「配置を復元した」こととして返し、スコアは置き直しの少なさと速さで別に返す（§16）。 |

## 3. 初期実装へ採用するルール

### 採用候補

移動可能なピースは次の6種を第一候補とする。

- `/` 斜め鏡
- `\\` 斜め鏡
- `||` 垂直二重鏡
- `=` 水平二重鏡
- 全方向反射体
- ブラックホール

外周ヒントは次を持つ。

- 通過マス数
- 別位置から退出
- 同じ位置へ反射して戻る
- ブラックホールへ吸収

**AI判断（仮決定）**: 上の6種と4種の外周ヒントを本実装のルール範囲とする。盤面に固定ピース（初期配置）は置かず、手持ちピースをすべてプレイヤーが置く。外周ヒントは四辺のすべての位置（盤面一辺 n に対して 4n 本）に表示する。遷移表・通過マス数の数え方は `scripts/research/reflection_supply_experiment.py` と一致させる（段02でTS移植し、出力一致を確認する）。

### 初期実装から外すもの

- ライトワープ
- 三角形の特殊ミラー
- プレイヤーによる問題作成対戦
- 複数人リアルタイム競争

ライトワープや三角形は、基本ルールだけでは高難易度や多様性が不足すると判明した場合の拡張候補とする。

初期から特殊要素を増やすと、難易度分析・視覚識別・説明コストを同時に増やすため、基本6種だけで5段階を成立できるかを先に検証する。

## 4. BGA版から変更する品質条件

pa-zzleでは次を問題成立条件とする第一候補とする。

1. 与えられたピースをすべて使う。
2. 全外周ヒントを満たす。
3. 解は一意である。
4. 各ピースは少なくとも1つの外周ヒントへ影響する。
5. 回転・反転で同型の問題を問題集内で重複させない。

BGA版では全ヒントが一致すれば作成時と異なる配置も正解で、設定によっては未使用ピースも許す。これは対戦ゲームとして成立するが、pa-zzleでは問題品質、再プレイ、難易度分析、ヒント提供を安定させるため一意解を第一候補とする。

**AI判断（仮決定）**: 上の5条件を本実装の問題成立条件とする。

## 5. 一意解供給の追加実験

公開実装コードをコピーせず、公開ルールから独立してレーザー遷移と制約解法器を試作した。

解法器は次を扱う。

- 各外周ヒントが許す光路
- 各マスのピース候補
- 全ピースを正確に使う在庫制約
- 2解目が見つかった時点で打ち切る一意性判定

4×4の小盤面では全列挙結果と突き合わせ、解集合が一致することを確認した。

ランダム完成配置について、さらに「各ピースを外したときヒントが変わる」条件を通ったものを20問ずつ採用して一意性を確認した。

| 5×5 / 6 | 30 | 20 | 0 | 2.2 ms | 2.9 ms | 3.8 ms |
| 5×5 / 8 | 23 | 20 | 0 | 2.2 ms | 6.7 ms | 9.0 ms |
| 6×6 / 8 | 23 | 20 | 0 | 6.1 ms | 15.9 ms | 34.5 ms |
| 6×6 / 10 | 23 | 17 | 3 | 12.2 ms | 43.9 ms | 72.1 ms |
| 7×7 / 8 | 23 | 20 | 0 | 20.5 ms | 76.5 ms | 361.6 ms |
| 7×7 / 10 | 25 | 20 | 0 | 40.6 ms | 108.0 ms | 124.3 ms |
| 7×7 / 12 | 31 | 19 | 1 | 67.2 ms | 250.8 ms | 541.7 ms |

追加の各10問では次の傾向だった。

- 8×8 / 12: 一意9、複数解1、中央値約0.32秒
- 8×8 / 15: 一意7、複数解3、中央値約0.61秒

### 判定

一意解を要求しても供給率は十分高い。

一方、8×8以上・ピース増加で検証時間の裾が急に伸びるため、**本番プレイ開始時にブラウザで生成・一意性判定する方式は採らず、事前生成問題集を第一候補とする。**

## 6. ピース構成の比較

7×7 / 10ピースで、各構成について「全ピースがヒントへ影響する」問題を30問得るまで生成した。

| 構成 | 有効30問 / 生候補 | 一意 / 複数解 | 生候補に対する一意問題率 | 一意性判定中央値 | 外周結果の傾向 |
| --- | ---: | ---: | ---: | ---: | --- |
| 斜め鏡 + 二重鏡 | 30 / 35 | 26 / 4 | 74.3% | 35.8 ms | 退出596、反射244 |
| + 全方向反射 | 30 / 38 | 26 / 4 | 68.4% | 106.1 ms | 退出502、反射338 |
| + ブラックホール | 30 / 37 | 29 / 1 | 78.4% | 54.3 ms | 退出510、吸収120、反射210 |
| + 全方向反射 + ブラックホール | 30 / 46 | 30 / 0 | 65.2% | 67.0 ms | 退出442、吸収105、反射293 |

基本6種を含めても問題供給は成立する。ブラックホールは吸収という別種の外周制約を増やし、全方向反射は反射ヒントを増やすため、推理の種類を増やす要素として残す価値がある。

## 7. 多様性と同型除外

7×7 / 10ピースについて、「一意解」「全ピースがヒントへ影響」を満たす200問を生成した。

- 200問採用までの生候補: 261
- 外周ヒント完全一致の重複: 0
- 盤面を回転・反転した同型解の重複: 0
- 一意性判定中央値: 約27.9 ms
- p90: 約144.4 ms

少なくともこの規模では多様性不足の兆候はない。本番問題集では念のため8種類の回転・反転を正規化したキーで重複除外する。

**導出**: 盤面を回転・反転すると、`/` と `\\`、垂直二重鏡と水平二重鏡は変換に応じて入れ替わる。正規化キーは配置を変換するときにピース種も対応させて変換したうえで取る（段02で実装し、段06で問題集の重複除外に使う）。

## 8. 問題identityと供給方式

本番候補は**事前生成問題集**とする。

生成時に次を固定・検証する。

- generator version
- seed
- 盤面サイズ
- ピース在庫
- 正解配置
- 外周ヒント
- 一意解
- 全ピース有効
- 対称同型キー
- 難易度分析結果

プレイ時には問題を再解析せず、問題集から難易度に対応したidentityを選択する。

記録から同じ問題を復元できるよう、少なくとも問題集バージョンと問題IDまたは生成identityを保存する。

### 8.1 問題識別情報（AI判断（仮決定））

既存ゲーム（`.claude/rules/game-structure.md` の `<Game>Problem` と `<Game>ProblemIdentity` の分離）に揃え、次の形を第一候補とする。

```text
ReflectionProblemIdentity = {
  generatorVersion: string,
  seed: ProblemSeed,
  conditions: { size: 5 | 6 | 7, pieceCount: number },
}
```

- 問題集に正解配置と外周ヒントを保存し、実行時に生成器・完全解法器を呼ばない。
- 問題集に無い identity（生成器の版が変わった後の古い記録など）は再プレイ不可として扱う。
- 診断ビルドでは、問題 identity を URL で指定して固定問題を開く入口を持つ（パーキングジャム #406 と同じ方式。段03）。

### 8.2 問題集の規模（推測）

1レベルあたり100〜200問を目安とする。7×7でも正解配置（49マス）と外周ヒント（28本）程度なので、全体で数百KB未満と見込む。実際のバンドル増分は段06で記録する。

**段06の結果（事実（実測））**: 各レベル500問、計2,500問を同梱した。JSON 135 KB（gzip 約28 KB）、本番ビルドの JS は gzip で +29.9 kB。外周ヒントと手持ちは解から求めるので持たない。内訳と検証は [リフレクション難易度](リフレクション難易度.md) §9.1。

## 9. 視覚表現

BGAの素材は使わず、各ピースの光学機能が形だけで読める独自表現を作る。

最低条件:

- `/` と `\\` の向きを色なしでも識別できる
- 垂直/水平二重鏡の透過方向と反射方向が読める
- 全方向反射体とブラックホールを形で区別する
- 外周の退出・反射・吸収を色だけに依存させない
- レーザー表示がピース形状と重なっても経路を追える

外周ヒントの結果種別には色に加えて形・記号を持たせる。

**AI判断（仮決定）**:

- 色はゲーム固有色として `frontend/src/games/reflection/` 側で持ち、`primary`・`success`・`error` などの共通トークンを流用しない（`DESIGN.md`）。ライト／ダークの両方で確認する。
- 7×7・320pxでセルが約35pxまで縮むため（§15）、ピースは線・面の少ない単純図形にし、細部の描き込みで機能を表さない。
- 外周ヒントは「数字 + 結果種別の形」で表す。結果種別の形の具体案（例: 退出=外向き矢印、反射=U字、吸収=塗り円）は段04で複数案を比較して決める。

**人間判断（2026-09-28、最初の人間レビュー）**: 段04では形だけで区別し色を付けなかったが、プロダクトオーナーから「パズル画面はもう少し色を使ってよい。記号だけでは分かりにくい」との指摘を受け、結果種別とピースに色を付けた。形の区別は残し、色だけに頼らない（最低条件はそのまま満たす）。色の割り当ては §19「ゲーム固有色」の行。

## 10. 操作方式

第一候補は、BGAのドラッグ必須にはせず、**ストック選択 → 盤面タップ**を基本にする。

必要操作:

- ストックからピース種を選ぶ
- 空きマスへ配置する
- 配置済みピースを別マスへ移す
- 2マスのピースを入れ替える、または一度ストックへ戻す
- 配置を取り消す
- 外周ヒントを選び、現在配置におけるレーザー経路を表示する

ドラッグは補助操作として追加してよいが、正確なドラッグを必須にしない。

### 10.1 操作の割り当て（AI判断（仮決定））

| 状態 | タップ対象 | 結果 |
| --- | --- | --- |
| 何も選んでいない | ストックのピース種 | その種を選択する（残数0の種は選べない） |
| ストックの種を選択中 | 空きマス | そのマスへ配置し、残数を1減らす。残数が残っていれば選択を保つ |
| ストックの種を選択中 | 配置済みマス | そのマスのピースをストックへ戻し、選択中の種を置く（置き直し） |
| 何も選んでいない | 配置済みマス | そのピースを選択する |
| 配置済みピースを選択中 | 空きマス | そこへ移す（置き直し） |
| 配置済みピースを選択中 | 別の配置済みマス | 2つを入れ替える（置き直し） |
| 配置済みピースを選択中 | ストック領域 | ストックへ戻す（置き直し） |
| 選択中 | 同じ対象 | 選択を解除する |
| 任意 | 外周ヒント | そのヒントの光路を表示する（§11.3） |

- 回転操作は持たない。`/` と `\\`、垂直と水平の二重鏡は別の種としてストックに置く（BGA版と同じ在庫の考え方）。
- ドラッグは初期実装に入れない。ページのスクロールと競合しやすく、タップで全操作が完結するため。
- PC ではキーボードでセル移動と配置をできるようにする（割り当ては段04で決める）。

## 11. 誤りの扱い

### 採用しない

- 正解配置とのセル単位比較
- 「このピースは正しい / 間違い」の表示
- 現在の外周ヒントが目標と一致しないことを常時赤表示するBGA方式

これらは試し置きによる正解探索を強くし、pa-zzleが測りたい推理をUIが代行する。

> **人間判断で変更（2026-09-28）**: 最初の人間レビューで、プロダクトオーナーから「盤面の正誤が分かりにくい。配置したタイミングで合っているかどうかが分かる方がよい。数字の背景に色が付くなど」との指摘を受けた。これにより、外周ヒントごとに今の配置の光が目標と一致しているかを示す表示（§11.4）を採用した。正解配置とのマスごとの比較・ピースごとの正誤・赤い常時エラー表示は引き続き採らない。§11.1 の「何も示さない」は §11.4 に置き換わった。

### 候補

外周ヒントを選んだとき、**現在の配置から実際にレーザーがどう進むか**だけを表示する。

これは現在状態の物理的帰結であり、隠れた正解との比較ではない。ただし、使い放題だと試行錯誤を促進する可能性があるため、通常操作として扱うか補助機能として扱うかはプレイ試作で確認する。

### 11.1 全ピースを置いても揃わない場合（AI判断（仮決定）。2026-09-28 の人間判断で §11.4 に置き換え）

> 以下は段01の仮決定の記録として残す。現在の扱いは §11.4。

全ピースを置いてもクリア条件（§13）を満たさない場合、「まだ揃っていない」ことを示すメッセージや、どのヒントが違うかの表示は出さない。ストックが空で盤面が完成演出に進まないこと自体が状態を伝える。

- 理由: どのヒントが違うかを示すとBGA方式の赤枠と同じ効果になる。「全体として違う」ことだけでも、1手ずつ置き換えて完成するまで試す使い方を促すため。
- 比較した案: (a) 何も出さない（採用）、(b) 「まだ揃っていません」を控えめに出す、(c) 不一致のヒント数だけ出す。
- 最終レビューで見てほしい点: (a) で「全部置いたのに何も起きない」ことが UI の迷いに見えないか。迷いに見える場合は (b) へ変える。

### 11.2 誤りを記録しない

一意解の問題なので、置いたピースが正解配置と違うかを裏で判定することはできる。しかし、表示しないまま「誤配置」として数える案も採らない。仮置きとして置いたピースと、確信して置いたピースを区別できず、置き直しの回数（§16）が同じ事実をより素直に表すため（AI判断）。

### 11.3 光路表示（AI判断（仮決定））

**光路表示は補助機能として提供する。通常操作として扱う案へ設定1つで切り替えられる作りにする。**

| 項目 | 補助（採用） | 通常操作（切替先） |
| --- | --- | --- |
| 呼び出し | 外周ヒントをタップ | 外周ヒントをタップ |
| 表示内容 | 現在配置での光路の線（入口の点、外へ出た位置の矢印）。2026-09-28 の人間判断で、出た位置・通過マス数・結果種別を文字で出す1行はやめた | 同じ |
| 目標との照合 | 光路表示では出さない（外周ヒントの一致は §11.4 で常に示す） | 同じ |
| 回数の記録 | `laserCheckCount` として記録する | 記録する |
| スコアへの反映 | しない | しない |
| 遊び方・結果画面での扱い | 「補助」として説明し、結果画面に回数を事実として出す | 基本操作として説明し、結果画面に回数を出さない |

- 実装では表示の可否・説明文・結果画面の出し分けを1つのモード値（例: `laserPathMode: "assist" | "normal"`）から導き、各部品に分岐を散らさない。
- 理由: 光路表示は正解を漏らさないが、使い放題だと試し置き + 光路確認の繰り返しで解けてしまう余地がある。一方で使えないと、複数の光路を頭の中で追い続ける作業記憶の負担がゲームの難しさへ混ざる。補助として提供しつつ回数を事実として残せば、最終レビューで通常操作へ寄せるか、回数を評価へ入れるかを記録を見て判断できる。
- 比較した案: (a) 補助として提供・回数記録（採用）、(b) 通常操作として無制限提供、(c) 提供しない、(d) 回数制限つき。(d) は制限回数の根拠がなく、使い切った後に作業記憶の負担が急に増えるため除外した。
- 最終レビューで見てほしい点: 光路表示が推理の置き換え（試し置きで解く）になっていないか。通常操作とした方が自然か。
- 一致表示（§11.4）との関係（2026-09-28 追記）: 一致表示は「どの外周ヒントが今合っているか」を、光路表示は「その光が今どこを通るか（なぜ合わないか）」を示す。役割は重ならないので光路表示は残す。`laserCheckCount` の意味（外周ヒントを押して光路を表示した回数）は変えない。一致表示によって光路を確かめなくても合否が分かるようになったため、回数は「合わない理由を探した回数」に近い事実になり、段01で想定した「光路で合否を確かめる試し置き」の量は表さなくなった。

### 11.4 外周ヒントごとの一致表示（人間判断、2026-09-28）

最初の人間レビューでのプロダクトオーナーの指摘（要旨: 盤面の正誤が分かりにくい。配置したタイミングで合っているかが分かる方がよい。数字の背景に色が付くなど）を受けて採用した。

- 判定: 盤面が変わるたびに、各外周ヒントについて今の配置での光の結果（行き先の種別と通るマスの数）を求め、目標の外周ヒントと両方が同じなら「一致」とする。ピースを置き切っていなくても、その時点の光で判定する（`listReflectionClueMatches`、`puzzle/rules.ts`）。何も置いていない盤面でも、まっすぐ抜ける外周ヒントは一致になる。
- 表示: 一致している外周ヒントは数字の地をゲーム固有の一致色（緑）にする。スクリーンリーダーには外周ヒントの名前の末尾に「一致」を付ける。不一致の外周ヒントは通常の見た目のまま（赤いエラー表示にはしない）。
- 全ピースを置いても揃わないとき: 盤面の外周ヒントはそのまま（緑の付いていないものが不一致）で、画面下の1行（光路の状態の行）に「合っていない外周ヒントがn本あります」を控えめな文字色で出す。光路を表示している間は光路の状態を優先する。赤い表示や外周ヒントごとの不一致の印は付けない。緑が付かない外周ヒントを探せば不一致が分かるので、印を重ねると盤面が騒がしくなるため。
- 採らないもの: 正解配置とのマスごとの比較、ピースごとの正誤（§11 の「採用しない」は維持）。
- 完成: すべての外周ヒントが一致し手持ちを置き切ると、これまでどおり完成演出へ進む。
- 最終レビュー後の要検討（この対応では変えない）:
  - 難易度: 人間向け解法器（段05）は一致表示が無い前提（外周ヒントの目標だけから推論する）で推論レベルを測っている。一致表示があると、1個置くたびにどの外周ヒントが合ったかが分かり、試し置きで確かめる手間が下がる。推論レベルと体感の難しさの対応（`リフレクション難易度.md` §11）が変わりうるので、実プレイ照合は一致表示ありで行い、ずれたら定義を見直す。
  - スコア: 正確性は置き直し回数で測る（§16.3）。一致表示で試し置きの情報が増えるので、試し置き型のプレイの速さ・置き直し回数の分布（`リフレクション成績評価.md` §8 のシミュレーションの前提）が変わりうる。配点・減点幅・基準時間は変えずに、実プレイの記録で見直す。
  - 光路表示: 一致表示と合わせて、補助の扱い・回数を結果に出すかを見直す（§11.3）。

## 12. Undo・リセット・ヒント

- **Undo**: 配置・移動の直前状態へ戻す。推理自体を教えないため基本機能として許容候補。
- **盤面を戻す**: 同一セッションのまま開始配置へ戻す。
- **リセット / 再プレイ**: 同じproblemで新しいsessionを始める。
- **ヒント**: 初期実装では未採用。導入する場合、人間向け難易度分析で表現できる手筋から1ステップだけ示す方式を別途設計する。

### 12.1 補助操作の構成（AI判断（仮決定））

既存ゲーム（ナンプレ・パーキングジャム）と同じ構成にする（`SPEC-007`）。

| 操作 | 提供 | 振る舞い |
| --- | --- | --- |
| 待った | する | 直前の配置・移動・入れ替え・回収を1つ取り消す。何段でも戻せる。`undoCount` を数える |
| 盤面を戻す | する | 同じプレイのまま、盤面を空（全ピースがストック）へ戻す。経過時間は続く。`restartCount` を数え、待ったの履歴を消す |
| やり直す | する | 同じ問題を新しいプレイとして始める |
| 新しい問題 | する | 同じ難易度で別の問題を始める |
| 難易度変更・ホーム・検証情報 | する | 既存のプレイメニューと同じ |
| ヒント（次の一手の提示） | しない | 通常UIが確定手を提示しない（`GAME.md`） |
| 正解との照合 | しない | §11 |

- 待ったで取り消された配置・移動は、置き直し（§16）として数える。取り消しは「一度置いたものを動かし直した」ことと同じ事実のため。
- 比較した案: 待ったを提供しない（タクズと同じ）。タクズは巡回入力でマス単位に戻せるが、リフレクションでは移動・入れ替えの直前状態へ戻す手段が他に無く、誤タップの復旧コストが大きいため提供する。

## 13. クリア条件

問題生成時に「全ピース使用 + 一意解」を保証するため、プレイ時のクリア判定は次で成立する。

- 全ピースを使用している
- 全外周ヒントが目標と一致する

正解配置そのものとのセル比較は不要である。一意解保証により、この条件を満たす配置は正解配置と同値になる。

**AI判断（仮決定）**: クリア条件を満たした瞬間に入力を止め、全光路が揃う短い演出を返してから結果画面へ進む（既存ゲームの `clearing` → `result` と同じ進行）。失敗（ゲームオーバー）は無い。

## 14. 難易度

### 挑戦の仮説

難易度を盤面サイズやピース数そのものへ直結させない。

人間の解法として、少なくとも次の層を表現する必要がある。

1. **単一レーザーの局所推論**
   - 短い距離
   - 反射 / 吸収の位置候補
   - 入口付近で置けるピース種の削減
2. **入口・出口の対応**
   - 退出ヒント同士の対応
   - 1本の光路を両端から読む
3. **複数レーザーの交差制約**
   - 1セルの候補が複数ヒントで削られる
   - 1つの確定が離れたヒントへ伝播する
4. **ピース在庫制約**
   - ある種類を使い切ったことで他セルから除外する
   - 残数と残候補数が一致して配置を確定する
5. **仮定と矛盾**
   - 局所推論だけでは決まらず、候補を仮置きして複数ヒント先の矛盾まで追う

### 現在の検証状況

一意性検証用の完全解法器は成立したが、完全解法器の探索量をそのまま人間の難易度に使わない。

全光路列挙を毎回やり直す試作は7×7級で重かったため不採用とし、レーザー状態を有限状態制約として前向き・後ろ向きに伝播する分析器へ変更した。詳細は [リフレクション難易度PoC](リフレクション難易度PoC.md) を参照する。

5×5固定の200問でもL1〜L5がすべて現れ、ピース数と最高推論レベルのSpearman順位相関は約0.668だった。同じピース数の中でも複数レベルが混在するため、盤面規模やピース数をそのまま難易度にしていない。

供給についても、5×5 / 2ピース100問でL2が18%、5×5 / 10ピース30問でL5が20%現れた。事前生成問題集なら全5段階を棄却選別で継続供給できる見込みがある。

一方、難易度の完了条件には人間のプレイ体験との対応確認がある。固定したL1〜L5代表問題と境界問題をラベルを伏せて比較し、推理の深さが概ね段階的に増えること、L4/L5が単なるピース数の多さに見えないことを確認するまでは、**難易度ゲートを通過させない。**

### 14.1 挑戦の定義（AI判断（仮決定））

> 外周ヒントの観測結果から、見えないピースの位置と種類を1つずつ確定させ、1本の光路で決まらないときは複数の光路・手持ちの残数・仮定の帰結まで読んで確定させること。

挑戦にしないもの（`難易度.md`「挑戦ではない負担」）:

- 盤面サイズ・ピース数だけによる作業量の増加（単独ではレベルを決めない）
- 光路を頭の中で追い続ける作業記憶の負担（光路表示で軽減する。§11.3）
- ピースの見分けにくさ・セルの押しにくさ（UIで除く）
- タップ回数・所要時間そのもの

### 14.2 基準とするプレイ条件（AI判断（仮決定））

- ルール・6種のピース・外周ヒントの意味を理解している。
- 光路表示は、置いたピースの確認に使ってよい。ただし光路表示の結果を見ながら置き換えて解く使い方は基準にしない。
- 待った・盤面を戻すは解法上不要（一意解・推測なしで分析できる問題を出す）なので、難易度の基準では使わない。

### 14.3 5段階の組み合わせモデル（AI判断（仮決定））

**単一軸にしない。** 推論レベル（L1〜L5）を主軸に、盤面サイズとピース数をレベルごとの「許す範囲」として組み合わせる。

- パーキングジャムでは、依存構造の1系統だけで5段階を作る案がレビューで不採用になり（[パーキングジャム難易度5段階調査](../パーキングジャム/パーキングジャム難易度5段階調査.md) §14）、規模を「単独では段を決めないレバー」として組み合わせる第2版が採用された。この前例に揃える。
- 推論レベルは難易度PoCの L1〜L5（単一ヒントの直接確定 / 候補の直接整合性 / 制約伝播 / ピース在庫 / 仮定と矛盾）の最高レベルを使う。
- 盤面サイズとピース数は、人間が読む範囲（外周ヒント 4n 本、置く対象の数）を広げるレバーとして扱い、隣のレベルと重なる幅を持たせる。規模だけでレベルが上がる・下がることはない。

組み合わせ定義（段05で 5×5〜7×7 の3,300問の分布を見て確定した。値は `frontend/src/games/reflection/difficulty.ts` の `reflectionLevelCombinations` にデータとして持つ。計測と判断は [リフレクション難易度](リフレクション難易度.md) §7〜§9）:

| レベル | 最高推論レベル | 盤面サイズ | ピース数 | 利用者向けの挑戦の説明（案） |
| --- | --- | --- | --- | --- |
| 1 | L1 | 5×5 | 2〜4 | 1本のレーザーを見れば、置く場所と種類が決まる |
| 2 | L2 | 5×5〜6×6 | 2〜4 | 候補を他のレーザーと照らし合わせて絞る |
| 3 | L3 | 5×5〜6×6 | 4〜7 | 1つ決まると別のレーザーの候補が減り、連鎖して決まる |
| 4 | L4 | 6×6〜7×7 | 6〜10 | 手持ちの残り数も手がかりにして決める |
| 5 | L5 | 6×6〜7×7 | 10〜12 | 仮に置いた先の矛盾まで読まないと決まらない |

段05で段01の仮定義から変えたのは、レベル2 のピース数（3〜5 → 2〜4。L2 は2〜3ピースで最も出やすく、5ピースでは少ない）と、レベル5 のピース数（8〜12 → 10〜12。人間向け解法器の光路の扱いを直した後、L5 は 8〜9ピースで1〜4%しか出ない）の2点。

- 7×7を上限とする（§15）。8×8以上は提供しない。
- 6×6・7×7 でも L1〜L5 がすべて現れ、盤面サイズと最高推論レベルの順位相関は0.099、ピース数とは0.707だった。33条件のすべてで3種類以上の推論レベルが混ざる（事実（計測）。[リフレクション難易度](リフレクション難易度.md) §7）。L5 は少なく、最も多い 7×7・12ピースでも25%。提供範囲の問題の分析時間は中央値6ms・最大1.5秒で、問題集の生成に耐える。
- レベル1〜3に 5×5 を含め、レベル4〜5に 7×7 を含めるのは、規模を「上位ほど広い範囲まで読む」レバーとして使うため（推測）。PoC では 5×5 固定でも L1〜L5 が現れるため、規模は推論レベルの代わりではない（事実（計測））。
- ピース種の段階導入（例: レベル1は斜め鏡だけ）は採らない。斜め鏡だけの手持ちはかえって推論が深くなり、浅い推論の問題はブラックホールや反射体を多く含むため、段階の順序が推論の深さと逆になる（段05。[リフレクション難易度](リフレクション難易度.md) §8.6）。段08の入れ子のテストは、推論レベルと規模の範囲について行う。
- 評価可能範囲と提供範囲: 一意解だが分析器の L1〜L5 で完答できない問題は **評価不能** とし、レベル5へ押し込まない。分析できても上の組み合わせに入らない問題は **提供範囲外** とする（`難易度判定.md`）。

最終レビューで見てほしい点:

- レベル1→5で推理の深さが概ね増えると感じるか（ラベルを伏せた代表・境界問題の実プレイ。`難易度開発手順.md` 工程9）。
- レベル4/5が「ピースが多い・盤面が広い」だけに感じないか。
- 規模の範囲の重なり方が妥当か。ピース種の段階導入を採るか。

## 15. スマートフォン

外周ヒントが四辺にあるため、通常の盤面パズルより横幅制約が強い。

pa-zzleの実レイアウト上へ操作PoCを載せ、Repository Snapshotと同じOffline Dependenciesを使ってPlaywright / Chromiumで確認した。詳細は [リフレクション スマホ操作PoC](リフレクションスマホ操作PoC.md) を参照する。

| viewport | 7×7セル | 8×8セル | 横スクロール |
| --- | ---: | ---: | --- |
| 390px | 45.4px | 39.8px | なし |
| 375px | 43.3px | 37.9px | なし |
| 360px | 41.1px | 36.0px | なし |

全8条件で、44pxのストック選択、セル配置、外周ヒント選択、光路表示を実操作でき、`pageerror` / 意図しない `console.error` / failed request は0だった。

## 16. プレイ評価

BGAの順位点はマルチプレイヤーの速度競争用であり、pa-zzleへは採用しない。

pa-zzleで評価したい「上手さ」の第一候補は次の2軸である。

- **解決速度**: `elapsedMs`
- **配置の確かさ**: 一度置いたピースを後で動かし直した回数

記録候補:

- `elapsedMs`
- `relocationCount`
- `restartCount`
- `laserCheckCount`
- `inputCount`

このうち `laserCheckCount` は、光路表示を通常機能にする場合、少ないほど上手いと単純評価すると作業記憶能力を過剰に評価する可能性がある。そのため初期は記録だけに留め、スコアへ入れない。

最終的な100点の配点は代表問題を実際に遊び、時間と配置修正が独立した上手さを表すか確認してから決める。

### 16.1 良いプレイの定義（AI判断（仮決定））

> 外周ヒントから確定させてから置き、置いたピースを動かし直さずに、迷いなく配置を復元すること。

### 16.2 評価に使う事実（AI判断（仮決定））

| 事実 | 評価に使うか | 定義 |
| --- | --- | --- |
| `elapsedMs` | 使う（速さ） | プレイ開始からクリアまで。盤面を戻しても止めない |
| `relocationCount` | 使う（正確性） | 一度盤面に置いたピースを、別マスへ移す・入れ替える・ストックへ戻す・上書きで戻される・待ったで取り消される回数。入れ替えは動いた2個を1回と数える |
| `restartCount` | 使う（正確性） | 盤面を戻した回数。盤面を戻して回収されたピースは `relocationCount` に数えない |
| `undoCount` | 記録のみ | 待ったの回数。待ったで取り消した配置は `relocationCount` 側で数えるため、二重に減点しない |
| `laserCheckCount` | 記録のみ | 光路表示の回数（§11.3） |
| `inputCount` | 記録のみ | 盤面・ストックへの操作回数 |

### 16.3 評価規則（AI判断（仮決定）。配点は仮置き）

- 100点満点を **正確性 60点 + 速さ 40点** で配分する（仮置き）。
  - 正確性: `relocationCount` 0・`restartCount` 0 で満点。1回ごとに減点し、0点を下回らない。
  - 速さ: 問題ごとの基準時間以内で満点、超過に応じて減点。基準時間は盤面サイズ・ピース数・分析結果から問題ごとに決め、**レベルの高さそのものを加点しない**。
- 正確性を重くするのは、良いプレイの中心が「確定させてから置く」ことにあり、速さはその結果として付いてくると考えるため（推測）。スライドパズル（効率60 / 速さ40）と同じ比率を初期値にする。
- 係数・減点幅・基準時間は仮置きで、最終レビュー後の実プレイで校正する。評価は保存したプレイ事実から読み出し時に計算し直す（`SPEC-006`）ので、配点を変えても記録を移行しない。
- 比較した案: (a) 正確性60/速さ40（採用）、(b) 50/50（タクズ）、(c) 正確性・速さ・安定性（待った・盤面を戻す）の3観点（パーキングジャム）。(c) は待ったと置き直しが同じ事実を二重に数えるため採らない。

最終レビューで見てほしい点: 配点比率、減点幅、光路確認回数をスコアへ入れないことの妥当性。

段09で係数と基準時間を決めた（正確性60: 置き直し −5・盤面を戻す −15、速さ40: 基準時間 = 0.5秒 × 外周ヒント + 6秒 × ピース + 8秒 × 照らし直し + 15秒 × min(仮に置く回数, 10)、2倍で0点）。案の比較・問題集での分布・プレイ例・プレイヤー像のシミュレーションは [リフレクション成績評価](リフレクション成績評価.md) にまとめた。

## 17. 記録・再プレイ・診断

### プレイ記録

最低限保存候補:

- problem identity
- difficulty
- elapsedMs
- relocationCount
- restartCount
- 最終スコア

分析用の事実として必要なら `laserCheckCount`、`inputCount` も保持する。

**AI判断（仮決定）**: 既存ゲームに揃え、記録 payload にはスコアや段階を保存せず、生のプレイ事実（`elapsedMs`、`relocationCount`、`restartCount`、`undoCount`、`laserCheckCount`、`inputCount`）と、難易度、`ReflectionProblemIdentity`、スコアモデル版だけを保存する。スコアは読み出し時に再計算する。自己ベストの比較単位は難易度とする。

段09で次のように改めた（[リフレクション成績評価](リフレクション成績評価.md) §9）: スコアモデル版は保存せず（バイナリパズルと同じ。係数を変えたら過去の記録も新しい規則で評価し直す）、代わりに遊んだ問題の作業の量（`ReflectionSolveWorkload`）を保存する。問題集の版と番号は保存せず、identity から引く。内部診断で問題を指定したプレイは記録しない。

### 再プレイ

問題identityから同一problemを復元し、新しいsessionとして開始できること。

### 内部診断

開発時は次を確認できるようにする。

- generator version / problem pool version / seed
- 盤面サイズ
- ピース在庫
- 外周ヒント種別・距離分布
- 一意性検証結果
- 全ピース有効検証結果
- 対称正規化キー
- 難易度分析結果と使用手筋

**AI判断（仮決定）**: 上の項目を検証情報（既存ゲームのプレイメニュー「検証情報」）に出す。組み合わせ定義のどの条件でレベルが決まったか（最高推論レベル・盤面サイズ・ピース数）も表示し、最終レビューでの照合に使う。利用者のプレイ画面には出さない。

段10で次のように改めた（§19「検証情報」）: 検証情報に出すのは、難易度・seed・生成器の版・生成条件・ビルドに加え、問題集の版と番号・分析し直した分類・最高推論レベルとする。ピース在庫・外周ヒントの分布・一意性・全ピース有効・同型キーは、問題集の生成時の検証（`--verify`）とテストで保証しているので出さない。

## 21. 実装へ進むための残件

### 必須（全段実装後の最終レビューで行う）

1. 固定した難易度1〜5の代表・境界問題をラベルを伏せて実プレイ比較し、人間の挑戦と大きく矛盾しないことを確認する。
2. レーザー経路表示を補助のままにするか通常操作にするか試遊で判断する（仮決定は §11.3）。
3. プレイ評価の事実と100点化を代表問題で確認する（仮決定は §16.3）。

### 公開前

4. 正式表示名を決め、商標を最終確認する（§18）。

問題生成・一意解・多様性・スマートフォン操作については本実装へ進めるだけの成立性を確認できた。難易度も機械側の分析・5段階供給PoCは成立しており、現在の主要な未知は **難易度の人間対応**、**レーザー確認機能が推理を損なわないか**、**プレイ評価** である。
