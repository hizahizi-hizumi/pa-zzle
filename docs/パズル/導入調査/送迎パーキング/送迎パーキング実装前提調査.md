## 1. 根拠の書き分け

- **事実（リポジトリ）**: 今のリポジトリの文書・コード、別ブランチの資料、GitHub の Issue・PR で確かめたこと。
- **事実（計測）**: 上の調査コードで測った値。研究用 Python の実測で、製品コードの速さや人の手応えを表すものではない。スマホ操作の実測のうち Playwright で製品の枠を測った部分は一時スクリプトで行い、保存していない（測った値は `shuttle-parking_mobile.py` の定数に残した）。
- **推測**: 上から導いたが、人のプレイ・製品コード・測り直しで確かめていないこと。
- **AI判断（仮決定）**: 人間の判断を待たずに進めるため、合意と正本に沿って AI が決めたもの。§4 に理由・比べた案・覆したときに作り直す範囲を書く。

§4 の数値は、断りの無いかぎり §3 の表と同じ計測から引いた（出どころのスクリプトは §3 に書いた）。難易度の数値の詳細は難易度の資料にある。

人も AI も、まだこのパズルを遊んでいない。難易度・採点・件数の判断は、読み手と遊び方の模擬による仮説である。

## 2. 認識合わせの合意

導入調査 Issue #988 の合意節を正とする。出どころは #727 の方式比較で、プロダクトオーナー（PO）が試作を遊び「いちばん面白い。パズルっぽい。先読みがある」と評価した。認識合わせのページへの人間の返事は「go」。要点:

- 既存のパーキングジャムとは別のゲームとして足す。パーキングジャムは変えない。
- ルール: 駐車場の車（縦か横、2人乗りか3人乗り。長さ＝定員）をタップすると、向きに沿って、出口の辺まで進路が空なら外へ出て待機枠に入る。最初から全部見える乗客の列の先頭から順に、同じ色の待機車へ1人ずつ乗る（同じ色が複数あれば先に入った車）。満席で出発して枠が空く。待機枠が埋まると次の車を出せない。出せる手が無くなると詰み。全員を送り出せばクリア。
- 考えること: 乗客の列の先を読み、どの車をいつ待機枠へ入れるかを計画する。
- 解は複数あってよい。推測は要らない。「この手は負け」の表示は出さない。「1手戻す」「最初から」を付ける。
- 称えたい解き方の仮説: 戻さずに先を読んで解くこと（採点の項目は調査で別案と比べて決める）。
- 難しさは盤面の広さで作らない。罠の深さ（間違った車を出してから詰みが確定するまでに乗客が何人進むか）と重なりで5段階にする。見せた一言は Lv1「列の先頭に合う車を出していけば解ける」、Lv2「罠の結果が1〜4人先」、Lv3「5〜7人先」、Lv4「8人以上先」、Lv5「深い罠が重なる。5人先まで読んでも半分も勝てない」。
- 比較の試作は製品のコードとして引き継がず作り直す。難しさの測り方と問題の例は調査の材料に使う。

この文書の用語:

- **出口の辺**: 駐車場の4辺のうち、車が外へ出られる辺。問題ごとに1辺か、隣り合う2辺。調査コードと難易度の資料の「開口」「開いた辺」と同じもの。
- **1手戻す**（画面の名前）は GAME-005 の「待った」、**最初から**（画面の名前）は GAME-005 の「盤面を戻す」にあたる。どちらも同じプレイの続きで、「リセット」（新しいプレイ）とは別のもの。以下、画面の名前で書く。

合意から変えることが1つある。Lv3〜Lv5 の一言を、深さの言い方から罠の回数の言い方に変える（Lv5 は意味は同じで、言い方が変わる）（§4 の D-05）。面白さの核（先読み）は変えない。

### 4.2 採点の前提

D-15 の理由と比べた案。

- 採った方針: 主に「列の先を読み切り、罠の出庫を選ばずに全員を送り出すこと」、従に「その読みを速く行うこと」を称える。推測の要らない問題なので、罠に入る1回はどれも運ではなく読みの失敗と言える。罠に入ったかはプレイの事実から厳密に決まり、深さによらず1回と数えられる（§3）。罠1回を数え、その後の続きや戻した手数は追加で数えないのは、原因が何手か前にあり、詰んでから原因を探す試行錯誤を自然な遊び方として残すため（詰将棋の誤王手・マインスイーパーの地雷・一筆パズルの試し引きと同じ考え方で、このゲームの構造から説明できる）。
- 認識合わせの仮説「戻さずに先を読んで解く」との関係: 称えたいもの（先読み）は同じ。文字どおり「1手戻す・最初からを使わない」と読むと、押し間違いの取り消しや、詰む前に自分で誤りに気づいて戻すことまで同じに扱い、深い罠ほど同じ1回の失敗が重く出る。「戻さずに」を「罠に入らずに」と読み替えて採った。
- 退けた案:
  - 1手戻す・最初からの回数を数える: 上の理由。推測: 1手戻すには押し間違い・詰んでからの原因探し・詰む前の気づき・試し出しの4つの意味があり、回数では分けられない。
  - 戻した出庫の数を数える（氷の床迷路型）: 事実（計測、`shuttle-parking_scoring.py`、試作15問の勝ち筋上の罠 1,944件）: 結果が5人以上先に出る罠は、詰むまでに出せる出庫の最大の中央値が 2.5〜3、1〜4人先の罠は詰むまでの出庫の中央値が1。推測: 深い罠は上位に多いので、同じ失敗でも上位ほど点が下がる偏りになる。
  - 少ない手数（効率）: クリアの出庫数はルールで台数に固定され、差は戻した出庫としてしか現れない。
  - 出られないタップを主にする: パーキングジャムと同じ上手さになり、このゲームの挑戦（先読み）を表さない。副次の事実として扱いを score で決める。
  - 速さだけ（ブリッジパズル・リフレクション型）: 試して戻す遊び方と読み切る遊び方が時間でしか分かれず、PO が評価した先読みが点に表れにくい。
  - 詰みに達した回数を数える（次点）: 判定器が要らない利点があるが、詰む前に戻すと数えられず、読みの失敗を取り逃がす。

- 問題供給と図鑑の計測は案F の分類で測った。案G では、生成条件を巡回したときの費用、回転・反転・色の付け替えの重複（E3）、近い問題、図鑑の特徴の分布と難易度との相関を測り直していない。特に案G は待機枠を解ける最小だけにしたので、図鑑の待機枠の分布（案F では Lv1 の 86% が4枠、2枠はどのレベルでも 0.2〜6%）は変わる。
