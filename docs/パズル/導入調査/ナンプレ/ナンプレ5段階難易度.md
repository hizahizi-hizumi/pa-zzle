# ナンプレ5段階難易度

ナンプレの難易度を、3段階（かんたん・ふつう・むずかしい）から `レベル 1`〜`レベル 5` へ組み直すための検討記録。[難易度開発手順.md](../../難易度開発手順.md) の工程2〜11 に沿って、人間向け解法器の拡張、問題集合での分析、5段階の分類、問題集による供給までを記録する。

## 1. 目的と位置づけ

3段階の判定（`dependency-v1`。[ナンプレ難易度.md](ナンプレ難易度.md)）は、Naked Single / Hidden Single だけで解ける問題を「次の一手の見つけやすさ」で3つに分けていた。これを5つに割り直すのではなく、ナンプレ固有の挑戦が段階的に強くなる5段階として組み直す。

この文書は現在仕様の正本ではない。採用した契約（挑戦の定義、分析できる手筋の範囲、分類の考え方、評価不能・提供範囲外の扱い、問題集からの供給）は、画面・記録の移行と合わせて [SPEC-008 ナンプレ](../../../プロダクト/仕様/パズル/SPEC-008.md) の「問題」へ反映する（§13）。正確な手筋の実装・分類表・ヒント数の範囲はコードを正とする。試した案、採用しなかった案、比較結果はこの文書に残す。

根拠は次の見出し語で区別する。

- **事実（実測）**: §6 の問題集合・§14 の問題集と、コミット済みの分析・生成スクリプトで測った結果。
- **導出**: 定義から論理的に導けること。
- **既存知見**: 公開されている評価器・研究の知見。本書では測り直していない。
- **推測・仮説**: 実プレイで確かめていない判断。

まだ誰も実際に遊んで確かめていない。§10 の試遊が済むまで、各レベルの体験差は仮説として扱う。

## 2. 前提として引き継ぐ条件

| 条件 | 内容 |
| --- | --- |
| 盤面 | 全難易度で 9×9 に固定する。サイズを難易度にしない |
| ルール | 各行・各列・各 3×3 ブロックに 1〜9 が一度ずつ入る |
| 問題成立性 | 一意解であること。推測なしに解けることは別の条件として確かめる |
| 補助 | 候補数字のメモを手で付けられる。正しい数字を入れると、両立しない同じ行・列・ブロックのメモは消える。自動で全候補を書き込む機能・ヒントは無い（SPEC-008） |
| 誤りの扱い | 完成解と異なる入力はミスとして記録する（SPEC-008）。難易度の基準とするプレイ条件では、ミスの表示に頼らずに盤面を読んで数字を置く |
| 基準とするプレイ条件 | ルールと入力・メモの操作を理解している。仮置きと後戻り（推測）はしない。候補を消す手筋が要る段では、メモで候補を管理する |
| 供給 | 事前生成した問題集から seed で選ぶ（§14） |

## 3. ナンプレ固有の挑戦

### 3.1 挑戦の定義（仮説）

> 盤面から次に数字を置けるマスを見つけ出し、置けるマスが見つからないときは、行・列・ブロックの重なりや、いくつかのマス・数字の組を読んで候補を絞り、置けるマスを作り出すこと。

### 3.2 挑戦を強くするもの（仮説）

1. **必要な読みの種類**: 1つのブロックの中で数字の置き場所を探せば足りるか。行・列の中や、1マスに入り得る数字まで読むか。数字を置かずに候補を消す読み（重なり、組、複数の行・列やマスのつながり）が要るか。
2. **候補を消す読みが要る局面の数**: 1度消せば後は流れるのか。流れが止まるたびにまた要るのか。
3. **見つけにくさ**: その局面で置ける数字が盤面にいくつあるか（[ナンプレ難易度.md](ナンプレ難易度.md) の Pelánek の依存構造）。

### 3.3 挑戦にしないもの

- ヒント数、空きマスの数、ラウンド数（解き終わるまでの長さ）、入力回数、所要時間。作業量で、それだけでは難易度の根拠にしない。
- 解探索（バックトラック）の探索量。計算機の難しさで、人間の読みと対応しない（Pelánek、既存知見）。
- 盤面の見やすさ・入力のしにくさ（UI で除く）。

## 4. 分析モデル（人間向け解法器）

実装は `frontend/src/games/nanpure/problem/generation/human-solver.ts`。手筋の名前と深さの順は `problem/technique.ts` が持つ。問題成立性の確認は `generation/solver.ts`（完全探索）、特徴量の導出は `problem/difficulty-analysis.ts`、分類は `difficulty.ts` が持つ。

### 4.1 手筋

解法器は各空きマスの候補（入り得る数字）を持ち、数字を置くとその行・列・ブロックの候補からその数字を消す。人間がメモで候補を管理するのに当たる。

| 系統 | 手筋（コード上の名前） | 内容 | 既存の評価器での重さ（Sudoku Explainer のおおよその値、既存知見） |
| --- | --- | --- | --- |
| ブロックのシングル | 残り1マス（`full-house`） | 行・列・ブロックに空きが1マスだけ残り、入る数字が決まる | ― |
| | ブロックのシングル（`hidden-single-block`） | ブロックの中で、ある数字を置けるマスが1つしかない | 1.2 |
| 行・列・マスのシングル | 行・列のシングル（`hidden-single-line`） | 行・列の中で、ある数字を置けるマスが1つしかない | 1.5 |
| | マスのシングル（`naked-single`） | あるマスに入り得る数字が1つしかない | 2.3 |
| 重なり | ブロックと行・列の重なり（`locked-candidates`） | ブロックの中である数字の候補が1本の行・列に並ぶなら、その行・列の他のブロックから消す（ポインティング）。行・列の中で1つのブロックに収まるなら、そのブロックの他のマスから消す（クレーミング） | 2.6〜2.8 |
| 組 | 数字の組・場所の組（`naked-pair` / `hidden-pair` / `naked-triple` / `hidden-triple`） | 1つの単位で、2（3）マスの候補が合わせて2（3）数字なら他のマスからその数字を消す。2（3）数字の置き場所が合わせて2（3）マスならそのマスから他の候補を消す | 3.0〜4.0 |
| 複数の単位にまたがる形 | X-Wing・Swordfish（`x-wing` / `swordfish`） | ある数字の候補が2（3）本の行で同じ2（3）本の列に収まるなら、その列の他の行から消す（行と列を入れ替えても同じ） | 3.2・3.8 |
| | XY-Wing・XYZ-Wing（`xy-wing` / `xyz-wing`） | 候補2（3）つのマスを軸に、軸から見える候補2つの2マスが共通の数字 z を持ち、どの場合もどれかのマスが z になる。3マス（XY-Wing は両端の2マス）のすべてから見えるマスの z を消す | 4.2・4.4 |
| ― | それより深い手筋（連鎖、Unique Rectangle、4つ組など） | 扱わない | ― |

手筋の例（事実。`human-solver.test.ts` の入力）:

- ブロックのシングル: 行0・行1・列1・列2 に 1 があるとき、左上のブロックで 1 が入るのは r3c1（3行1列）だけ。
- 重なり: 左上のブロックで 7 の候補が1行目の3マスにしか無いとき、1行目の残り6マスから 7 を消す。
- XY-Wing: r1c1 の候補が {1,2}、r1c5 が {1,3}、r4c1 が {2,3} のとき、r1c1 が 1 なら r1c5 が 3、2 なら r4c1 が 3 になる。どちらでも r1c5 か r4c1 が 3 なので、両方から見える r4c5 から 3 を消す。

### 4.2 進め方

1. 局面ごとに §4.1 の表の上から順に、進められる最も浅い手筋を探す。
2. 数字を置く手筋なら、その手筋で置ける数字をまとめて置く。候補を消す手筋なら、見つけた最初の1か所の形だけで候補を消す。これを1**ラウンド**とする。
3. 全マスが埋まるまで繰り返す。どの手筋でも進めなくなれば止まる。

各ラウンドで記録する値:

- 使った手筋、置いた数字・消した候補。
- **置ける数字の数**: ラウンドの前に、数字を置く手筋のどれかで置けた異なる「マスと数字」の数（`dependency-v1` の次の一手候補数に当たる）。候補を消すラウンドでは 0。
- ラウンドの前の空きマスの数。

**導出**:

- どの手筋も健全である。解法器が解き切れたヒントは、推測なしに解けて、解も1つしかない。
- 手筋で進めることは、盤面の情報を減らさない（置いた数字と消した候補は残る）。ある手筋の集合で解き切れるかは、どの順で適用しても変わらない。局面ごとに最も浅い手筋を使う進め方で要った最も深い手筋は、「その手筋までの集合でなら解き切れる、最も浅い手筋」と一致する。したがって最も深い手筋は、同じ段の中の探す順（どのマス・どの単位から見るか）に左右されない。
- 最も深い手筋が要ったラウンド数や、候補を消すラウンド数は、どの形を先に使うかで変わりうる（§7.4）。

### 4.3 `dependency-v1` から変えた点

| 点 | `dependency-v1` | 本書 | 理由 |
| --- | --- | --- | --- |
| 手筋 | Naked Single / Hidden Single だけ | §4.1 の13手筋 | 「置けるマスが無いときに候補を絞る」読みはナンプレの中心的な挑戦で、それを分析できなければ上位の段を作れない。Naked / Hidden Single だけでは、一意解の問題の多くが評価不能になる（§4.4） |
| 盤面の持ち方 | 毎手、盤面から候補を計算し直す | 候補を持ち、消した候補を残す | 候補を消す手筋の結果を次の局面へ引き継ぐため |
| Hidden Single | 1つの手筋 | ブロックの中と行・列の中を分ける | ブロックの中だけを見る読みと、行・列の9マスを見る読みで重さが違う（既存の評価器も分けている） |
| 1手の単位 | 1マスずつ置く | ラウンド（同じ手筋で置ける数字をまとめて置く） | 最も深い手筋は単位に左右されない（§4.2 の導出）。長さの数え方を単純にするため |
| 分類の主軸 | 序盤25手の次の一手候補数の平均 | 最も深い手筋の系統 | §8.4 |

### 4.4 評価できる範囲

- §4.1 の表に無い手筋（連鎖、Unique Rectangle、4つ組、Jellyfish など）が要る問題は**評価不能**とし、提供しない。レベル5 へ押し込まない。
- **事実（実測）**: 一意解であることだけを保ってヒントを減らし切った問題の 36.8%（600問中221問）が評価不能だった（§7.1 の `uniqueness` の行）。製品の問題はすべて解法器で解き切れる範囲から作る。

### 4.5 問題成立性の確認

`classifyNanpureSolutions` が、候補の少ないマスから数字を試す完全探索で解を 0 / 1 / 2以上 まで数える。難易度分析は、解がちょうど1つのときだけ解法器を動かす。

## 6. 問題集合

### 6.1 生成方法

`problem/generator.ts` の生成器で作る。生成器は難易度を指定して問題を作る機能を持たない。問題集（§14）も同じ生成器で候補を作り、分類して振り分ける。

1. seed から完成盤を1つ作る（`findNanpureSolution` を seed の乱数で）。
2. 全マスをヒントとして始め、seed で決まる順にマスを1つずつ消す。消すと**手筋の上限**までの手筋で解き切れなくなるマスは残す。上限を `uniqueness` にしたときは、一意解であることだけを保つ。
3. できた問題を分析・分類する。手筋の上限で難易度を決めない。

旧来の生成器（ヒント数を 40 / 36 / 32 / 28 / 24 のどれかに決め、一意解を保って減らす）とは違い、ヒント数を指定しない。どの条件でも、上限までの手筋で解き切れる限り減らし切るので、ヒント数は 21〜30 に集まる（§7.3）。

### 6.2 条件

- 手筋の上限: `uniqueness` / `hidden-single-block` / `hidden-single-line` / `naked-single` / `locked-candidates` / `hidden-triple` / `xyz-wing` の7通り。
- 各条件 600 seed。計 4,200 問。

### 6.3 再現手順

```sh
bun run --cwd frontend analyze:nanpure -- --seeds 600 --jobs 4 --transforms 2 --output /tmp/nanpure-corpus/corpus
```

seed は `np-<手筋の上限>-<番号>`。1問は次で再現できる（例: `np-locked-candidates-740`）。

```ts
generateNanpureProblem(createNanpureProblemIdentity("locked-candidates", 740));
```

`uniqueness` の seed は `createNanpureProblemIdentity(null, …)` に対応する。同じ条件で並列数を変えて2回実行し、4,200問のヒント・分析・分類がすべて一致することを確かめた。

スクリプトの出力で再現できるのは、§7.1 の条件ごとの分類と最も深い手筋、§7.2 の特徴量の中央値、§7.3 の AUC（同条件内・同じヒント数）、§7.4 の同型変換での安定性、§7.5 の生成時間、§8.1 の案の比較である。次の値は、出力した `.jsonl` の問題を読み直して一度だけ数えたもので、スクリプトには含めていない。

- §7.3 のレベルごとのヒント数の分布。
- §7.4 の、別の系統の手筋でも解ける問題の割合（手筋の集合を変えて解き直した）。
- §8.4 の、3段階の判定（`legacy/`）との対応表。

- 1→2 と 2→3 は、同じヒント数でも次の一手の見つけにくさに大きな差がある（0.12・0.26、置ける数字が1つの局面は 0.88）。読みの種類が変わるとともに、探す負担も増えている。
- 3→4 と 4→5 は、長さ（ラウンド数）にも見つけにくさにも差がほとんど無い（0.45〜0.63）。4 と 5 は、新しい種類の読みが要ることだけで 3・4 と分かれる。上位レベルが長さで決まってはいない一方、隣との差は読みの種類の違いにだけかかっている（§12）。

### 7.4 探す順・同型変換への依存（事実（実測））

- 各問題を、行・列・帯・柱の入れ替え、転置、数字の付け替えを乱数で組み合わせた同型の問題2通りに変えて分析し直した（`--transforms 2`）。4,200問 × 2 の 8,400件すべてでレベルが一致し、分析できた 7,958件すべてで最も深い手筋が一致した（§4.2 の導出どおり）。最も深い手筋のラウンド数は 7,360件（92.5%）で一致し、残りは探す順で変わった。分類に使わないのはこのため。
- 手筋の段の順を入れ替えると分類は変わる（一度だけ数えた値）。
  - レベル3 の 71.9%（467問中336問）は、重なりを使わず組（ペア・トリプル）を使っても解ける。重なりを組より浅いとみなすので 3 になる。
  - レベル4 の 20.7%（174問中36問）は、組を使わず XY-Wing などを使っても解ける。組を XY-Wing より浅いとみなすので 4 になる。
  - 段の順は §4.1 の既存の評価器の重さの順に合わせた。この順が人間にとっても正しいかは §10 で確かめる。
- レベル2 の中では、行・列のシングルでもマスのシングルでも解ける問題が多い（行・列のシングル無しで解ける 37.5%、マスのシングル無しで解ける 64.9%）。2つを同じ段に置いたので、分類には影響しない。

## 8. 5段階の分類

### 8.1 案と比較

| 案 | 1 / 2 / 3 / 4 / 5 | 問題数（§6 の 4,200問） | 最も出やすい条件での割合 | 同じヒント数での隣接 AUC（ラウンド数 / 置ける数字の数） |
| --- | --- | --- | --- | --- |
| **P1（推奨）** | ブロックのシングル / 行・列・マスのシングル / 重なり / 組 / 複数の単位にまたがる形 | 690 / 2,570 / 467 / 174 / 78 | 100% / 97% / 26% / 14% / 8% | 0.78/0.12・0.80/0.26・0.63/0.53・0.51/0.45 |
| P2 | P1 の 4・5 を「組が2局面以上、または複数の単位にまたがる形」で 5 に分け直す | 690 / 2,570 / 467 / 103 / 149 | 100% / 97% / 26% / 9% / 13% | 0.78/0.12・0.80/0.26・0.58/0.53・0.58/0.49 |
| P3 | シングルを3段に分ける: ブロック / 行・列 / マス / 重なり / 組以上 | 690 / 1,669 / 901 / 467 / 252 | 100% / 96% / 49% / 26% / 18% | 0.74/0.15・0.65/0.29・0.74/0.38・0.64/0.51 |
| P0（不採用） | 置ける数字の数の平均を五分位で5つに切る（`dependency-v1` を5つに割る） | 各 20% | ― | §8.4 |

- **P1** は、隣り合うレベルの間で「新しい種類の読み」が1つずつ加わる。各段の意味を利用者に説明でき、既存の評価器の段とも並びが合う（§4.1）。上位ほど出る割合が低いが、事前生成で供給できる（§14）。
- **P2** は、4・5 の差に「候補を消す読みが何度も要る」という回数を足したもの。4→5 のラウンド数の AUC が 0.58 に上がり、長さの差が混ざる。組の回数は探す順でも変わる（§7.4）。
- **P3** は、行・列のシングルとマスのシングルを分ける。この2つはどちらでも解ける問題が多く（§7.4）、段の違いが「どちらを先に試したか」になりやすい。また重なり・組・複数の単位にまたがる形を 4・5 の2段へ詰めるので、候補を消す読みの種類の違いが失われる。
- **P0** は §8.4。

### 8.2 推奨案 P1

| レベル | 利用者向けの一文（案） | 分類条件（最も深い手筋） | 提供範囲内の割合（§6） |
| ---: | --- | --- | ---: |
| 1 | ブロックの中で、数字の置き場所を探せば進められる | 残り1マス・ブロックのシングルだけで解ける（ブロックのシングルが1つ以上要る） | 17.3% |
| 2 | 行や列の中の置き場所、1マスに入り得る数字まで読む場面がある | 行・列のシングルかマスのシングルが要る | 64.6% |
| 3 | 置ける数字が見つからないとき、ブロックと行・列の重なりで候補を絞る場面がある | ブロックと行・列の重なりが要る | 11.7% |
| 4 | いくつかのマス・数字の組を見つけて候補を絞る場面がある | ペア・トリプル（数字の組・場所の組）が要る | 4.4% |
| 5 | 複数の行・列やマスにまたがる候補のつながりを読んで候補を絞る場面がある | X-Wing・Swordfish・XY-Wing・XYZ-Wing が要る | 2.0% |

各レベルで強くなるもの:

- 1 → 2: ブロックの中だけでなく、行・列の9マスや、1マスから見える20マスを合わせて読む必要が出る。同じヒント数でも次の一手の場所が少ない（§7.3、AUC 0.12）。
- 2 → 3: 数字を置くだけでは進めない局面が現れ、数字を置かずに候補を消す読みが要る。メモで候補を管理する必要が出る。置ける数字が1つしかない局面も増える（0.88）。
- 3 → 4: 1つの数字の置き場所だけでなく、2〜3マスの候補や2〜3数字の置き場所を組として見る必要が出る。
- 4 → 5: 1つの単位の中だけでなく、2〜3本の行・列や、離れた3マスの候補のつながりを読む必要が出る。

実装は `difficulty.ts` の `classifyNanpureChallengeDifficulty` と `assessNanpureDifficulty`。

### 8.3 評価可能範囲と提供範囲

| 状態 | 条件 | 扱い |
| --- | --- | --- |
| 成立しない（`invalid`） | 解が無い、または2つ以上ある | 提供しない |
| 評価不能（`unsupported`） | 一意解だが、§4.1 の手筋で解き切れない | 提供しない。レベル5 へ押し込まない |
| 提供範囲外・軽すぎる（`out-of-range` / `too-light`） | 残り1マスを埋めるだけで解き終わる（最も深い手筋が `full-house`、またはヒントだけで埋まっている） | 提供しない |
| レベル1〜5（`classified`） | 上記以外 | §8.2 で分類する |

- **下限**: 行・列・ブロックの最後の1マスを埋めるだけの問題には、数字の置き場所を探す挑戦が無い。生成器の問題はヒントを減らし切るので、§6 では1問も現れなかった。ヒントの多い外部の問題などを分析するときのために状態として分けておく。
- **上限**: §4.1 の表に無い手筋は評価不能とし、提供範囲は §4.1 の手筋までとする。連鎖などは、ナンプレの挑戦としては成り立つが、現在の分析で評価できないので高難易度と推定しない（`難易度判定.md`）。

### 8.4 3段階を5つに割り直さない理由

3段階の判定（`dependency-v1`）は Naked / Hidden Single だけで解ける問題の中で、次の一手の見つけやすさを分けていた。5段階はこれを細かく割ったものではない。

**事実（実測、一度だけ数えた値）**: §6 の 4,200問を、3段階の判定（`legacy/` に残した `dependency-v1`）でも判定した。

| 3段階 | 1 | 2 | 3 | 4 | 5 | 評価不能 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| かんたん | 1 | 0 | 0 | 0 | 0 | 0 |
| ふつう | 144 | 64 | 0 | 0 | 0 | 0 |
| むずかしい | 545 | 2,506 | 0 | 0 | 0 | 0 |
| 評価不能 | 0 | 0 | 467 | 174 | 78 | 221 |

また、3段階の生成（`generateNanpureLegacyProblemForDifficulty`）で各段 200問を作って5段階で判定すると、かんたんは全問レベル1（ヒント数の中央値 40）、ふつうはレベル1 が 136・2 が 64（同 32）、むずかしいはレベル1 が 25・2 が 175（同 28）だった。

- 3段階はどの段も5段階のレベル1〜2 に収まる。3段階の差はヒント数（40 / 32 / 28）と見つけやすさの差で、ヒントを減らし切った問題はほぼすべて「むずかしい」になる。
- 5段階のレベル3〜5 は、3段階では評価不能として捨てていた問題である。これを分析できるようにしたことが、5段階を作れた理由である。
- 見つけやすさの五分位（P0）で5つに割ると、各段にレベル1〜5 が混ざる（§6 の問題で、最も見つけにくい五分位はレベル1 が 1問・2 が 450・3 が 222・4 が 75・5 が 43、最も見つけやすい五分位にもレベル3〜5 が 8問ある）。レベル2 はどの五分位にも 300問以上ある。置ける数字が多く見えていても、途中で候補を消す読みが要る問題を区別できない。
- 見つけやすさは、読みの種類が変わる 1→2・2→3 では段の差と同じ向きに大きく動く（§7.3）。分類の条件には入れず、裏付けとして使う。

## 9. 代表・境界・異常な問題

どの問題も問題集（§14）に含まれ、`generateNanpureProblem(createNanpureProblemIdentity(<手筋の上限>, <番号>))` で再現できる（`uniqueness` は `null`）。盤面は上の行から左→右の81文字で、`.` が空きマス。手筋は「名前×ラウンド数」。「消す」は候補を消すラウンド数、「連続」はその最長連続、「置ける」は置ける数字の数の平均、「1つ」はそれが1つの局面の数。

選び方: 代表は、そのレベルの問題集でラウンド数・候補を消すラウンド数・置ける数字の数が中央値に最も近い問題。境界・異常は、書いた条件で問題集から最初に見つかった問題。

一言の所感は、解法器の経過から読み取ったもので、実プレイではない。

## 11. ずれた場合の見直し方針

工程10。閾値だけを動かして合わせず、次の順で原因を疑う。

1. 挑戦の定義（§3）
2. 観測できていない挑戦
3. 特徴量の意味・計算（§5）
4. 判定方法（段の組み立て方）
5. 帯の境界

推奨案に即した例:

- **2 と 3 が逆転して感じられる場合（§10 の2）**
  1. 観測できていない挑戦: 見つけにくさ（置ける数字が1つの局面の数）が、読みの種類より効いていないか。
  2. 判定方法: レベル2 に見つけにくさの上限を設け、超える問題を 3 と同じ段にするのではなく、供給から外す（提供範囲外）か、2 の中の見つけやすさで供給を絞る。段の意味（新しい読みの種類）は保つ。
- **3 と 4、4 と 5 の差が薄い場合（§10 の4・5）**
  1. 挑戦の定義: 組・複数の単位にまたがる形が、人間にとっても重なりより深い読みだという前提（既存の評価器の順）を疑う。
  2. 特徴量: その手筋を見つける難しさ（盤面にその形が何か所あるか、形を作るマスが離れているか）を記録する。今の解法器は最初の1か所しか記録しない。
  3. 判定方法: 回数を条件に加える案（P2）や、段の順を入れ替える案と比べる。回数で段を作る場合は、長さの代理にならないかを §7.3 の AUC で確かめる。
- **レベル5 が重すぎる場合（§10 の6）**: 重すぎる手筋を提供範囲外にする。XY-Wing を外すとレベル5 はほぼ供給できなくなる（§7.1）ので、そのときは 5 の中身を「組を何度も要する」などに組み替える案と比べ、供給の見込みを測り直す。
- **同じレベルの中で長い問題が重く感じる場合**: 長さは挑戦ではない（§3.3）。判定は変えず、問題供給でヒント数・ラウンド数の範囲をそろえる。

## 12. 未解決の不確実性と限界

- **実プレイをしていない**。§9 の所感は解法器の経過から読み取ったもの。各レベルの体験差は §10 の試遊まで仮説である。
- **3→4 と 4→5 は読みの種類だけで分かれる**。長さにも見つけにくさにも差がほとんど無い（§7.3）。代表4・5 の違いは最後の1回の読みだけで、それが体験として段の差になるかが5段階の意味を左右しうる最大の不確実性。
- **段の順は既存の評価器に合わせた**。重なり→組→複数の単位にまたがる形の順を入れ替えると、レベル3 の 72%・レベル4 の 21% の分類が変わりうる（§7.4）。この順が人間の重さの順と合うかは確かめていない。
- **レベル5 の中身が偏る**。問題集のレベル5 の 86%（300問中259問）が XY-Wing、12% が XYZ-Wing で、X-Wing は 2%、Swordfish は 0。レベル5 の体験は実質的に「3マスの候補のつながり」の読みになる。
- **ラウンドの定義**: 数字を置く手筋は置ける数字をまとめて置き、候補を消す手筋は1か所ずつ使う。人間は1マスずつ置き、置いたマスから次が見えるので、実際の見つけやすさは局面ごとの数より高いことがある。
- **見つける難しさを見ていない**: 同じ手筋でも、形が盤面の離れた場所にまたがるか、候補の多いマスに埋もれているかで見つける難しさは変わる。解法器は形の有無だけを見る。
- **メモの負担**: レベル3 以上は候補の管理（メモ）を前提にする。メモを付ける手間は挑戦ではなく作業だが、レベル3 以上を遊ぶ体験の重さに含まれてしまう。
- **生成方法**: 無作為な順でヒントを減らし切る方法だけで作った。別の生成方法では各レベルの出やすさや特徴量の分布が変わりうる。
- **評価不能の問題**: 連鎖などが要る問題は扱わない。製品の問題は解法器で解き切れる範囲から作るので提供には影響しないが、その種の読みを楽しむ上級の挑戦は提供範囲に入らない。

## 14. 問題集（事実（実測））

問題供給として、各レベル 300問の問題集を作った。生成スクリプトは `frontend/scripts/generate-nanpure-problem-pool.ts`、生成物は `frontend/src/games/nanpure/problem/problem-pool.json`。

```sh
bun run --cwd frontend generate:nanpure-pool -- --jobs 4   # 生成
bun run --cwd frontend generate:nanpure-pool -- --verify   # 全問の検証
```

### 14.1 作り方

1. レベルごとに、そのレベルが現れやすい生成条件（§7.1）を決める。

   | レベル | 生成条件（手筋の上限） |
   | ---: | --- |
   | 1 | hidden-single-block |
   | 2 | hidden-single-line、naked-single |
   | 3 | locked-candidates |
   | 4 | hidden-triple、uniqueness |
   | 5 | xyz-wing、uniqueness |

   レベル4・5 に `uniqueness` を加えたのは、1問あたりの計算が軽く（§7.5）、出る割合を掛け合わせると上位レベル1問あたりの計算が少なくて済むため。

2. 各生成条件で、seed `np-<手筋の上限>-<番号>` の候補を番号順に作り、分析・分類する（§6.3 と同じ seed の系列）。
3. そのレベルに分類され、**ヒント数が 23〜27** の候補だけを採れる候補とする。範囲は全レベルで共通にした（§7.3）。
4. 生成条件を巡回し、各条件の採れる候補を番号順に1つずつ採る。同じ問題（解とヒントが同じ）は採らない。300問そろったら止める。

生成条件は候補を作る領域を決めるだけで、レベルは分類で決める（`難易度判定.md`「生成条件を難易度へ直結させない」）。採る問題は各条件の候補の番号順の並びだけで決まり、並列数（`--jobs`）や一度に調べる候補数（`--block`）に依存しない。`--jobs 4` と `--jobs 3 --block 150` で生成した JSON がバイト単位で一致することを確かめた。生成スクリプトの出力をそのままコミットし、他のゲームの問題集と同じく Biome の整形対象から外している。

回転・反転・数字の付け替えなどの同型の重複は除いていない。完成盤を seed の乱数で作るので、同型の問題が重なる見込みはごく小さい（推測）。

問題集の1問は `["locked-candidates", 740, "<102文字>"]` の形で持つ。先頭の2つ（手筋の上限・候補番号）から identity（生成器の版 `2`・seed・生成条件）を再構成し、102文字は解の81桁と、ヒントのマスを 1 とした位置の16進21桁を並べたもの。実行時は文字列を読んで問題を復元するだけで、生成器・解探索・難易度分析を呼ばない。記録に残した identity が問題集に無い（生成器の版が変わった後など）ときは `restoreNanpureProblem` が `null` を返す。

### 14.2 内訳

「候補」は、採る問題を決めるまでに調べた候補の数。「分類一致」はそのレベルに分類された割合、「採用率」はそのうえでヒント数の範囲に入った割合。計算時間は1スレッドあたりの生成と分析の合計（Linux コンテナ）で、レベル4 と 5 が共有する `uniqueness` の候補は両方に数える。

| レベル | 問題数 | 候補 | 分類一致 | 採用率 | 重複 | 計算時間 | 1問あたり |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 300 | 321 | 100.0% | 93.5% | 0 | 9.6 s | 32 ms |
| 2 | 300 | 323 | 96.0% | 92.9% | 0 | 14.7 s | 49 ms |
| 3 | 300 | 1,190 | 26.5% | 25.2% | 0 | 64.4 s | 215 ms |
| 4 | 300 | 3,684 | 8.6% | 8.1% | 0 | 141.0 s | 470 ms |
| 5 | 300 | 4,663 | 6.7% | 6.4% | 0 | 204.6 s | 682 ms |

- 生成は全体で 166 秒（4並列の経過時間）。`--verify` で 1,500問すべてを identity から生成し直し、次を確かめた（4並列で 20 秒）: 問題集の表記と一致する、一意解で手筋だけで解き切れる（分析の状態が `analyzed`）、分類がそのレベルと一致する、ヒント数が範囲内、重複が無い。
- 生成条件の内訳: 1 は hidden-single-block が 300。2 は各条件 150。3 は locked-candidates が 300。4・5 は各条件 150。
- 最も深い手筋の内訳: 2 は行・列のシングル 220・マスのシングル 80。4 は数字のペア 189・場所のペア 92・数字の3つ組 16・場所の3つ組 3。5 は XY-Wing 259・XYZ-Wing 36・X-Wing 5。
- 選択と復元（seed のハッシュで1問を選び、文字列から問題を戻す）は 10,000回で平均 0.05 ms、最大 7.7 ms。
- 大きさは JSON 200,630 バイト、gzip 79,892 バイト。
