# 開発進行の参考メモ

この文書は、別プロジェクト（AmuQuery）の振り返りから、pa-zzleにも適用できる一般的な知見だけを抽出した参考資料である。pa-zzleの現在仕様は定義しない。

## 成果物ではなく利用可能な一連の流れで区切る

実装を画面、API、データ、テストのような成果物単位だけで横に分けると、各部品が存在していても利用者の一連の体験が成立していない状態を作りやすい。

pa-zzle の PoC では、`docs/立ち上げ/PoC.md` にある次の流れを、小さくても最後まで成立する垂直スライスとして扱う。

```text
ゲーム選択
→ 難易度選択
→ 問題生成
→ プレイ
→ クリア判定
→ 成績表示
```

新しいパズルや大きな仕組みを追加するときは、必要な実装・契約・テスト・画面をこの流れが閉じる単位で揃えてから横展開する。

## 技術検証と利用体験の検証を分ける

「技術的に実現できること」と「アプリとして成立すること」は別に確認する。

技術検証では、問題生成、解法探索、一意解判定、難易度算出など、個別の成立性を確認する。
一方、利用体験の検証では、実際に問題を選び、遊び、終了し、成績を確認するところまでを通して、共通化の境界や不足要件を確認する。

個別技術の成功だけで PoC 全体を成立した扱いにしない。

## 静的な整合だけで実行時の成立を判断しない

設定や型、ファイルの存在が正しくても、実際の実行経路でしか見つからない不整合は残る。

重要な変更では、変更範囲に対応する静的検査に加えて、代表的な垂直スライスを実際に動かして確認する。

## 現在仕様と振り返りを混ぜない

現在の方針・要件・実装契約は、対象コード・設定と現行文書で管理する。
このメモのような振り返りは判断材料として利用してよいが、現在仕様の根拠として単独では扱わない。
