# AmuQuery 開発から得た知見

この文書は、AmuQueryを作る過程で発生した手戻りから得た開発上の知見を残すメモです。
製品の現在仕様そのものは `dev/docs/product/` を正とし、この文書は「なぜその進め方を採るのか」を説明します。

## 結論

目的設定そのものは大きくブレていなかった。

> 広告データ基盤で必要なSQL・データモデリング・品質・計測の能力を、実際に手を動かしながら身につける。

主な問題は、その目的を **要求 → 要件 → ユーザーストーリー → 受入条件** へ十分に落とさないまま、
「問題を作る」「fixtureを作る」「CLIを作る」「Webを作る」のような成果物単位へ分解したことにある。

その結果、各部品が存在していても、学習者の体験としては閉じていない状態が発生した。

## 実際に起きたこと

代表例:

- 問題文が要求する列とfixtureの実カラムが一致せず、SQLを書けない問題があった。
- fixture pathは存在するが、問題から必要なrelation・業務契約を判断できない問題があった。
- 練習問題は多数あったが、実際にSQLを書く問題が少なく、「AmuQuery」としての反復量が不足した。
- SQLを実行できても、練習問題をその場で自動採点する経路が不足していた。
- 回答artifactの配置規約が途中で揺れ、flat fileとproblem directoryが混在した。
- Web機能を簡易実装へ置き換えたことで、検索・fixture preview・実行等がデグレした。
- DuckDB runtimeの依存package不足が、静的validatorでは検知できず実行時に露呈した。
- 生のPython tracebackをWebへ出しており、学習者が修正行動へつなげにくかった。

これらは個別実装ミスでもあるが、共通して **end-to-endの受入条件が先に存在しなかった** ことの影響が大きい。

## 成果物単位の横割りが危険だった

避けたい分解:

```text
カリキュラムを作る
問題を作る
fixtureを作る
CLIを作る
Webを作る
採点器を作る
```

これでは、問題・fixture・runtime・採点がそれぞれ完成していても、
1問の学習体験が成立している保証にならない。

今後の完成単位:

```text
1問が完成している
=
学習目的が定義されている
+ 問題だけで要求を判断できる
+ 入力relation/columnが存在する
+ 回答artifactが最初から存在する
+ 指定runtimeで実行できる
+ 必要なら自動採点できる
+ 不正解/実行失敗時に修正可能なfeedbackがある
+ CLI/Webから同じ契約で扱える
+ 公開してはいけない評価情報が漏れない
```

## PoCとVertical Sliceを分ける

### 技術PoC

「技術的に成立するか」を確認する。

例:

- BigQuery Emulatorでnested/repeatedをロードできるか
- ARRAY / STRUCT / UNNESTを期待どおり実行できるか
- DuckDBで必要なSQL方言を扱えるか

### Vertical Slice / Pilot

「利用者体験として成立するか」を確認する。

例:

```text
問題を見る
→ 入力データを理解する
→ 回答を書く
→ 実行する
→ 採点する
→ エラー/不正解理由を見る
→ 修正する
→ 進捗へ反映される
```

今回不足していたのは後者。技術要素のPoCだけでは、教材としての完成度は保証できない。

## 今後の量産前パイロット

新しい問題型・採点方式・runtime・UIフローを追加する場合、最初に代表的な1問だけを縦に完成させる。

代表problem archetype:

1. DuckDB SQL-only + AUTO
2. DuckDB SQL + explanation
3. BigQuery Emulator SQL + AUTO
4. 説明/設計/レビュー問題
5. AUTO + rubricを要求する理解度チェック
6. 複数artifactを要求する総合課題

新しい型を大量展開する前に、その型の代表1問を次の順で通す。

```text
要求確認
→ 問題/fixture/answer artifact作成
→ runtime実行
→ 採点
→ Web/CLI
→ 敵対的ブラックボックスレビュー
→ validatorへ再発防止を追加
→ 横展開
```

## レビューの教訓

`./amu validate` が通ることは最低条件であり、GO判定そのものではない。

構造validatorが得意なこと:

- pathの実在
- ID整合
- manifest整合
- relation/columnの存在
- 公開境界
- UI routeや主要機能の回帰

構造validatorだけでは保証しにくいこと:

- 問題文だけで必要な判断ができるか
- 正常なN:Mと異常なJOIN増幅を回答者が区別できるか
- AUTO expectedを問題文から一意に導けるか
- 業務上の正とするデータ源が暗黙になっていないか
- 教材として十分な反復量があるか

そのため、最終レビューは **作者の意図を知らない回答者として、問題本文 + 公開fixture/資料だけを見る** ブラックボックス方式で行う。

## 実機テストの教訓

静的検査だけではruntimeの依存・version・エンジン固有挙動は閉じない。

リリース判定では、少なくとも代表vertical sliceを実runtimeで実行する。
SQL練習を大量変更した場合は、可能なら全AUTO referenceを実runtime上で走らせる。

「依存宣言に文字列が存在する」ことと、「実際に実行できる」ことを同一視しない。

## 回帰防止の教訓

変更前に既存機能inventoryを持つ。

特にWeb/CLIは「ファイルが存在する」ではなく、利用者が使っていた機能を受入条件として固定する。

例:

- 問題全文検索
- 種別/LU/実行環境/状態filter
- 問題詳細
- fixture profile/preview
- SQL実行
- SQL自動採点
- error feedback
- 進捗
- 次の必須ゲート

簡易化を目的に機能を消す場合は、意図した仕様変更として先に要求側で決める。

## 今後の原則

1. 目的から直接実装タスクへ飛ばない。
2. 要求・要件・ユーザーストーリー・受入条件を先に書く。
3. 新しい型は1本のVertical Sliceで検証してから量産する。
4. validatorは既知の失敗を再発させないために使う。
5. 最終GOは利用者視点のブラックボックスレビューで決める。
6. runtimeの成立は実runtimeで確認する。
7. 現在仕様と振り返りを混ぜない。現在仕様は `dev/docs/product/`、知見は `dev/docs/01memo/` に置く。


## 文書構造の知見

要求・要件・仕様・ユーザーストーリー・受入条件・画面設計を、それぞれ1つの巨大Markdownへ閉じ込めない。

1ファイルに集約すると、項目追加のたびに責務境界が曖昧になり、レビュー範囲も広がる。
今後は概念ごとにディレクトリを持ち、その中を関心事単位で分割する。

```text
dev/docs/product/
├── user-requirements/
├── system-requirements/
├── specification/
├── user-stories/
├── acceptance-criteria/
└── screen-design/
```

各ディレクトリの `README.md` は索引と責務だけを持つ。
本文は関心事ごとのファイルへ分け、ID (`RQ-*`, `FR-*`, `US-*`, `AC-*`, `SCR-*`) で横断参照する。
