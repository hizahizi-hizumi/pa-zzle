# pa-zzle 品質定義と品質保証の整備案（2026-11-07）

## 位置づけ

[アプリ全体の品質ギャップ調査](アプリ全体のプロ品質ギャップ調査-2026-11-07.md)と、その後の対話を踏まえ、**品質の正本をどこに定め、何によって担保するか**を整備するための設計案。現行の要求・要件・APP.md・GAME.md・難易度文書・Skill・CIを置き換える資料ではない。品質定義のうち今回確定したものは要求・要件・APP.mdを正本とし、機械検証と運用ルールは別の工程で整備する。

抽象的な製品方針は、ひとまず次の4つへ整理した。

- **広く遊べる**：多種類のパズルに出会い、気分に合わせて選べる。
- **深く遊べる**：良質で多様な問題を大量に解け、強い挑戦にも向き合える。
- **好きなだけ遊べる**：難易度・順番・量・テンポを自分で選び、気持ちよく繰り返せる。
- **成果を楽しめる**：スコアアタック、問題の収集、自己ベスト、統計を楽しめる。

これは新しい評価点数や一律の機能一覧ではない。個別ゲームには固有の面白さと、それに合う入力・評価・表現がある。途中再開は、十数分以上かけて解くような難問の供給に応じて必要性が高まる**条件付きの品質**であり、全ゲーム共通の最優先機能ではない。

## 1. 既存の正本に定義されているもの

| 品質の問い | 主な現行の正本 | 今回の議論との差分として確認したいこと |
| --- | --- | --- |
| 面白いゲームになっているか | RQ-001・003・004、NFR-001・002、APP.md、GAME.md | 面白さの評価を「機能成立」や「主観のOK」へ還元せず、解法・実操作の証拠で確認できるか |
| 違う種類の遊びを広く提供できるか | RQ-002、FR-001、NFR-016、APP.md | 種類数だけでなく、主要な判断・解き進め方の違いを確認できるか |
| 繰り返し新鮮に遊べるか | RQ-008、NFR-004・017、FR-003、難易度提供文書 | 問題量の基準をゲームごとに定め、解法の多様性と分けて検証できるか |
| 5段階の難易度に意味があり、強い挑戦もあるか | RQ-007、NFR-007〜009・018、難易度.md・難易度判定.md・難易度開発手順.md | レベルの相対的順序と、遊び込んだ人にも挑戦しがいがある上限を別々に検証できるか |
| 何問でも自分のペースで遊べるか | RQ-002・008・010、FR-003・025、NFR-005・006、SCR-002・004 | 次問移行・未クリア収集の手軽さを実プレイで評価できるか |
| スコア・収集・統計に価値があるか | RQ-005・006・009・010、FR-009・010・018・021〜025、NFR-010・011、SPEC-001・002・026 | 得点の妥当性・記録の比較条件・長期蓄積の保全をそれぞれ検証できるか |
| 操作・視認・反応が快適か | NFR-012〜015、DESIGN.md、各SCR、画面レビュー手順 | 実ブラウザ・実端末の操作、途中状態、完了遷移が変更時に確認されるか |

**結論**：品質の定義がまったく無いわけではない。RQ・FR・NFRに製品が保証すべきこと、APP/GAME等に判断原則、ゲーム仕様と難易度文書に固有の意味がある。新しい「品質基準.md」でこれを重複記述しない。**現行正本の不足を確認して必要箇所を改訂する**ことを第一段階とする。

### 今回の明文化と残る論点

1. **広く遊ぶ自由（反映）**：APP.md に「広く試す／深く遊び込む」を両立させる判断方針を追加。NFR-016 に、見た目の違いではなく主な判断や解き進め方が異なる種類を提供する保証を置いた。
2. **豊富な問題量（反映）**：RQ-008 に好きな種類を何問も遊びたい要求を、NFR-017 に各難易度での反復利用に耐える問題供給を明文化した。**ゲーム別の数量・連続利用の測定基準は未確定**であり、次の保証整備で具体化する。
3. **難問の奥行き（反映）**：RQ-007 に遊び込んだ後も手強い問題へ挑みたい要求を、NFR-018 に最上位の深い挑戦を追加した。NFR-007〜009の相対順位・5段階という保証と混同しない。熟練者にとっての挑戦の実態は未検証。
4. **継続して遊ぶ自由（既存の保証を維持）**：FR-003、NFR-005・006、図鑑の要件等を維持。未クリアを選んで連続プレイする機能や、強制的な自動進行を新設する決定ではない。
5. **成果の蓄積と保全（未決定）**：記録はブラウザ保存で、現行問題集から引けない旧問題は図鑑に反映されない。保存・移行・復旧の保証範囲は決まっておらず、新しい保証は設けなかった。
6. **面白さの担保（定義は既存）**：NFR-001・002の要件は重複させない。解法の観察や試遊の根拠をどのように残すかは、品質保証の工程で具体化する。

追加した保証は「既に全ゲームで検証・達成済み」という意味ではない。定義の正本化と、実際に成立しているという検証結果は別である。

## 2. 何をどの手段で担保するか

品質ごとに、**保証したい状態、証拠、検出できる欠陥、検出できないこと**を分ける。

| 品質 | 自動化できる主要な証拠 | 自動化だけでは不十分な証拠 |
| --- | --- | --- |
| **パズルの幅**（NFR-016） | ゲームごとの遊びの主要な判断・操作の比較 | 見た目と題材以外の違いが遊ぶ体験に現れるか |
| **問題成立性**（NFR-003） | 問題集の復元、ゲーム独立の検査器・ソルバーによる可解性・一意性等の確認、問題ID整合 | ゲーム固有の「公開ルールと問題としての自然さ」の妥当性 |
| **難易度**（NFR-007〜009・018） | 分類再現性、問題群の分布、境界・反例検査、問題供給の計測 | 人間の思考と特徴量の対応、最上位の問題の解き心地 |
| **多様性・量**（NFR-004・017） | 同形問題の除去、解法特徴・分布、レベル別件数、供給成功率・所要時間 | 異なる特徴量が実際に異なる面白さを生むか |
| **面白さ**（NFR-001・002） | 解法トレースの抽出、単調な反復や作業量の兆候の検出 | 代表問題の思考過程・発見・納得感、連続試遊時の新鮮さ |
| **操作・体験**（NFR-005・012〜015） | Vitest、Playwrightの状態遷移・入力・エラーの検査、実端末での再現可能な操作記録 | 見た目の階層、題材に合う操作感・音、長時間プレイの負担 |
| **スコア・記録**（NFR-010・011） | 評価の不変条件、記録の読み書き・再構成、比較単位の一貫性、旧版データの取り扱い | 何を良いプレイとするかの納得感、記録・統計を見返す価値 |
| **継続プレイ**（FR-003等） | 次の問題・再挑戦の導線、問題IDの選択規則、状態保存、処理遅延の実測 | 10〜20問続けたときのテンポ、重複の不満、達成表現とのバランス |

**機械的な正しさを保証できる項目**と、**証拠から品質の妥当性を判断する項目**を混同しない。人間が「OK」と言っただけでは後者の代用にならず、逆に機械検証がすべて通っても面白さは保証できない。

## 3. 現行の品質保証の仕組みと、接続すべき部分

**既にある仕組み**：

- `scripts/verify.sh` / Quality Gate：Biome、TypeScript、Vitest、ビルドを実行。現行リポジトリには360のテストファイルがある（テストケース数ではない）。そのうち269ファイルはゲーム配下。
- 新パズル候補評価チェックリスト：問題成立性・配布品質・難易度・操作・性能・製品価値を、根拠つきで独立判定する。
- `docs/パズル/難易度開発手順.md`：導入・変更の完了ゲートを持つ。5段階の意味・再現性・安定供給の3条件を採用する。
- `.claude/skills/add-puzzle/SKILL.md`：調査→実装→山場の検査→試遊と独立したレビュー→最終レビューの流れ。問題集 `--verify`、難易度の反例探し、iPhoneでの試遊、文書・体験・コードレビュー、未解決所見の記録を行う。
- `docs/開発/画面レビュー手順.md`：実ブラウザでの操作・途中状態・画面遷移・エラー確認を定める。

**主な接続不足の仮説**：

- 既存のRQ/FR/NFRから「今回はどの品質をどう検証したか」をPR上で確認する共通の読み方は明確でない。テストファイル中にNFR IDの直接参照はない。ただし、直接参照が無いことだけでテスト不足とは断定しない。
- `add-puzzle` は**新規パズルの追加**に強い。既存ゲームの問題集更新、採点変更、図鑑改修、UI改修で、どの検証を当てれば十分かを変更種類ごとに接続するとよい。
- 全問の厳密な成立性検査、解法の多様性、実プレイにおける面白さを、軽量なCIの成功と同義にしない。
- Quality Gateの単一ジョブは5分制限がある。全問題を毎回深く再解析する設計は、計測・費用・実効性の検討なしに採用しない。

## 4. 変更種類に応じた保証の実行案

新しい大掛かりな検査基盤を先に作らず、既存のSkill・テスト・レビューを変更の影響範囲へ結び付ける。

| 変更の種類 | 必ず検討する検証 | 既存の主な受け皿 |
| --- | --- | --- |
| 新ゲーム追加 | 採用判断、5段階、問題成立・供給、プレイ、採点、結果、図鑑、実端末 | `add-puzzle` Skill、候補チェックリスト、難易度開発手順 |
| 問題集・生成器の変更 | 同型・可解性・一意性、問題数・分布、既存記録との対応、代表問題の解法 | 問題集テスト、生成スクリプトの `--verify`、ゲーム固有分析 |
| 難易度モデルの変更 | 分類の再現性、帯の意味・境界、反例、供給、試遊 | 難易度開発手順、`design-game-difficulty` の検査 |
| 採点・プレイ記録の変更 | 採点の一貫性、意図せぬ攻略法の高評価、過去記録・自己ベストの再構成 | 既存Vitest、ゲーム別評価仕様、問題の比較試遊 |
| プレイ画面・演出の変更 | 実操作、連続操作、途中状態、スマホ幅、完了までの遷移・エラー | 画面レビュー手順、Playwright、ゲーム体験レビュー |
| 図鑑・問題選択の変更 | 収集数、絞り込み、再挑戦、未クリア出題、過去記録の扱い、操作回数 | SPEC-026、関連テスト、代表的な収集状態での操作確認 |
| 共通UI・アプリ導線の変更 | 影響する複数ゲームでの入口→解く→結果→次問、画面サイズ別の確認 | APP/GAME、各SCR、Playwright |

いずれも「表の項目全部を毎回実施」の意味ではない。対象変更が品質へどのように影響するかを特定し、既存の実行可能な検証を選び、実施しない項目には対象外の理由を残す。**測れないことは未確認と表示する**。

## 5. 品質の判定と証拠を残す方法

### 検証結果の区分と記録先（運用手順を整備済み）

判定語と必要な証拠は[変更時の品質検証手順](../開発/品質検証手順.md)に従う。既存の候補評価チェックリストと同じ**成立／不成立／要検証／対象外**を使い、未検証・環境制約・基準未確定を成立と呼ばない。

結果は原則として該当PRのValidation欄、既存のIssue・検証記録・CI Artifactでたどれるようにする。別の品質台帳や全要件・全テストIDの人手による追跡は設けない。

### 品質保証の完了条件（案）

1. **提供契約に反する確認済みの重大な問題**を未処理のまま「品質確認済み」としない。
2. **機械検証**は、その変更によって要求されるものが通っている。失敗は隠さず、対象と理由を明示する。
3. **体験に関わる変更**は、要求と一致する場面を実際に確認した根拠がある。主観だけを合格の理由にしない。
4. **未確認の重大項目**は合格に見せかけず、影響・検証不能の理由・いつ確認するかを明示して判断する。人間の承認だけで不確実性が消えたことにしない。
5. ゲームごとに正当性・難易度・供給・面白さ・操作の**必要な水準が異なる**ことを認め、全ゲームへ単一の閾値を押し付けない。特に難易度は既存の完了ゲートをそのまま使う。

これは全変更に人間の試遊を必須にする規則ではない。利用者体験に影響しない変更は既存の自動検証で十分な場合がある。機械試験と体験の検証のどちらが必要かは変更のリスクで決める。

## 6. 整備する成果物と作業の分割

**第1段階：品質定義の正本との照合（一部完了）**

- APP.md、RQ-007・008を改訂し、NFR-016〜018を追加した。既存の各要件へ面白さ・多様性・記録の保証を重複追加しない。
- 問題の豊富さと難問の深さを独立した保証にしたが、**実際の供給基準・熟練者に対する挑戦の確認は未完了**。第2・第3段階で検証できる条件へ接続する。
- 記録の長期保存・移行・復旧は範囲未決定のため定義の追加を保留する。要求の追加や仕様の変更を暗黙に決めない。

**第2段階：検証・レビューの運用を接続（手順の整備済み、適用実績の検証は継続）**

- [変更時の品質検証手順](../開発/品質検証手順.md)を作成し、変更種類から既存の難易度開発手順・add-puzzle・画面レビュー・テストへ到達する方法を整理した。
- `AGENTS.md` の検証節からこの手順を参照する。検証結果は既存のPR・Issue・CI Artifactに残し、独立した品質台帳は追加しない。
- 判定の語彙は既存の候補評価チェックリストと同じ「成立／不成立／要検証／対象外」を使う。環境制約と未設定の基準を合格扱いしない。
- 手順自体は問題集更新時の例に当てはめたが、既存ゲームの実改修PRでの適用と証拠の妥当性はまだ確認していない。Quality Gateの成功だけで製品体験の成立とはしない。

**第3段階：必要な自動化を追加**

- 変更範囲を選んで実行できる問題成立性・問題集検証、採点と記録の回帰テストを優先候補にする。
- 現行Quality Gateを基準とし、全量解析が5分制限へ収まるかを実測。高コスト検証は問題集更新時や別ジョブ・定期実行等、必要な条件に応じて分ける。
- 数字の閾値・専用の静的リント・独自検査フレームワークを先に作らない。既存テスト基盤・スクリプトを優先する。

**第4段階：既存ゲームへの適用と不足の改善**

- 全10ゲームの品質について、品質項目と確認根拠が存在するかを棚卸しする。未知を問題ありと同一視しない。
- 成立性・難易度・供給・多様性・面白さ・体験のうち、根拠の不足が製品価値に大きく影響するものから測定する。
- 結果を品質項目の合否と残余リスクとして報告し、実際に必要なゲーム固有の改善PRへつなぐ。

### この進め方を採る理由

- 既存の難易度と新ゲームの開発フローを破棄せず、重複しない。
- 「定義を明文化する」作業と「仕組みを作る」作業の完了を混同しない。
- CIで測れるものと実プレイでしか分からないものを区別できる。
- 全ゲームを総点数で序列化せず、各ゲームの持つ価値を検証できる。
- 議論を延々と続けず、まず正本の差分から実装可能な規模へ落とし込める。

**未決定**：NFR-017のゲーム別の供給量基準、NFR-018の実プレイとの対応を確認する方法、長期保存の具体的な保証範囲、検証頻度と費用、どの品質項目を自動でブロックするか。これらは次工程の検証・判断を経て対応する正本と実装に反映する。変更時の品質検証の選び方と報告方法は上記の手順で運用を開始する。
