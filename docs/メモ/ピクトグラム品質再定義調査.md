# ゲームピクトグラム品質の再定義に向けた調査

調査日: 2026-11-07  
対象: `main` の `add7b90d4d6889973f92ca8af84d2251c3366a17`

## 位置づけ

ゲームピクトグラムについて、リポジトリの現状、一般的な図記号・アイコン設計の知見、pa-zzle で目指す品質を照合した調査資料。**品質基準の改定案を示すものであり、現行の決まりを変更・確定する文書ではない。** 今の決まりは `DESIGN.md`、静的版・選択中の姿の制作方法は `.claude/skills/design-game-pictogram/` と `.claude/skills/design-game-pictogram-showcase/`、製品として保証することは要求・要件を正とする。

本稿では次の区分を用いる。

- **確認事実**: 対象のコード・資料・標準や研究から直接確かめられること。
- **観察・解釈**: 実際の図形・ルールを照合した所見。利用者調査の結果と混同しない。
- **提案**: pa-zzle の品質定義や検査工程に採用するか、今後決めること。
- **未検証**: 客観的なデータがなく、判断や実測を要すること。

## 1. 製品の目的とピクトグラムの役割

### 現行の目的（確認事実）

- `RQ-001` はアプリを通した面白さ・楽しさ・ワクワクを、`RQ-002` は遊びたいパズルを見つけ、これからのプレイへの期待を高めることを求める。
- `FR-001` は、複数のパズルについて「何を考え何をする遊びか」を区別して認識し、楽しく選べることを保証する。
- `APP.md` は「成り立つだけの案」を採らず、選ぶ・解く・結果を通した楽しさを優先する。
- `SCR-001` は、ゲーム名と実際に見る・触るものを縮約した表現を主役とし、ルール説明書にはしない。
- `DESIGN.md` は、一般の操作アイコンでゲームを代替せず、ゲーム固有の形と一覧での共通の描画言語を両立する。選択中は濃淡2色と同じ形を保ちながらゲーム固有色と動きを与える。
- `ADR-0016` と `ADR-0017` により、静止状態での形の同一性、ゲーム固有色、解けた瞬間を見せる再生形式等の既存決定がある。

したがって、ピクトグラムの品質は「どのゲームかを示せること」だけでは完結しない。一方、静的ピクトグラム単体にゲームルール全体の説明を求めるのも、現行の役割分担と異なる。**静的版はゲームの特徴を識別できる完成した姿、選択中の姿は色と動きでゲームの遊びと達成の魅力を補完する表現**という分担が妥当である（後段は提案として記述）。

| [ISO 9186-3:2014](https://www.iso.org/standard/59882.html) | 対象概念を知っている利用者が、その図記号と対象を結びつけられるかを評価する方法。 | 初めて見るパズルと既知のパズルを区別した評価を設計する。全パズルの名前を初見で当てられる必要はない。 |

| [Microsoft Fluent 2: Iconography](https://fluent2.microsoft.design/iconography/) | 操作のためのアイコンと製品を示すアイコンを区別し、小さくなるときは細部を省く。 | pa-zzle のゲームの姿を汎用操作アイコンに還元しない。小サイズでの情報の優先順位を検証する。 |

既存の `references/research.md` も意味的距離、視覚複雑性、具体性、光学重量、実表示条件の重要性を調査済みである。本調査の追加論点は、「それらを満たしているが、作品として弱い」状態を完成判定でどう扱うかにある。

外部知見からそのまま言い切れないこともある。ブランド固有の魅力、記憶に残りやすさ、遊ぶ意欲、選択中の動きが実際の利用行動を改善するかは、pa-zzle 固有の仮説であり、実測していない。

## 3. 現状の実装と品質担保

### 資産・契約（確認事実）

`frontend/src/games/*/assets/` には、以下の10ゲームそれぞれに静的版 `pictogram.svg` と選択中用 `pictogram-showcase.svg` がある。

- `hitofude-puzzle`、`ice-floor-maze`、`minesweeper`、`nanpure`、`parking-jam`
- `reflection`、`slide-puzzle`、`takuzu`、`tsume-shogi`、`water-sort`

静的版の制作 Skill は `viewBox="0 0 120 120"`、線幅 `4`・`2`、濃淡2色の描画契約を掲げる。`DESIGN.md` は共通描画言語と密度・重量を、`references/method.md` は意味的距離、要素の知覚、複雑性、具体性、弁別性、光学重量、実サイズでの成立を評価する。選択中用 Skill は、ゲームで何を考え何をするか、解けた瞬間の気持ちよさ、即時の選択手応え、画面の落ち着きの順で評価し、ブラウザ観察と別コンテキストのレビューまで含む。

静的版10点を以下のコマンドに相当する条件で検査した結果、**10/10がPASS**。また10点の `viewBox` は `0 0 120 120` だった。

```sh
for svg in frontend/src/games/*/assets/pictogram.svg; do
  python3 .claude/skills/design-game-pictogram/scripts/check_svg.py "$svg" \
    --max-colors 2 --forbid-gradients --forbid-filters \
    --forbid-external-images --forbid-text
done
```

このPASSが示すのは、XMLとして解析可能、viewBoxあり、指定した色数・禁止要素のチェックを通過したことである。**線幅の値・色トークンの名称・光学中心・意味の正しさ・造形美を保証しない**。`check_svg.py` の無引数実行が描画契約をすべて検査する、という解釈も誤りである。選択中用の10点については、存在の確認に限り、アニメーションの実行検査・全件の品質判定は今回行っていない。

### 現行フローの強みと不足（解釈）

**既にできていること**

- 着眼点を広く出し、異なる方向を残して、粗案をそのまま人間へ見せない。
- 112pxと48px等の実サイズ比較、光学補正、他ゲームとの並列確認を制作に組み込んでいる。
- 「候補の魅力」「一覧内で魅力的な表現」は既に評価対象として明記されている。魅力という概念が全くないわけではない。
- 選択中用は遊びの説明と達成の見せ方を区別し、技術検査・観察・第三者レビューを含めている。

**追加の検討が必要なこと**

1. **造形の完成度の判定が薄い。** 線・間隔・配置に「明らかな破綻がない」ことと、形状・比率・余白が洗練された完成品であることは異なる。後者を独立した判定として操作可能にする余地がある。
2. **魅力の評価は宣言されているが、合否判断につながりにくい。** 「魅力」には触れている一方、最終収束条件は意味・知覚・重量・契約適合や重大な問題の有無が中心で、凡庸な候補群から相対的に最良を選んだ場合の不合格判断が明確でない。
3. **ゲーム固有性とセット品質の衝突の扱いを深めたい。** 形状の統一がゲームの核を消したり、逆に個性の強調がセットを不揃いにしたりする場面で、どちらを優先するかの判断理由が必要。
4. **検査通過を視覚品質と混同しやすい。** 実際の `check_svg.py` は限定的な静的検査であり、制作契約の数値をすべて検査するものでもない。検査範囲と非対象を報告で分ける必要がある。
5. **利用者による妥当性の実測がない。** 「見分けやすい」「覚えやすい」「遊びたくなる」は、現状では人間レビュー上の判断であり、対象利用者の認識・記憶・行動の測定ではない。

## 4. pa-zzle で目指す品質の定義案

> ゲームピクトグラムは、各ゲームの本質的な視覚要素を凝縮し、実際の利用条件で識別でき、造形として完成され、ゲーム固有の魅力を伝える、pa-zzle の「選ぶ」体験を構成する視覚表現である。ゲームごとの姿を保ちながら一つのセットとして調和し、静的版だけでも成立する。選択中の姿は同一の形を土台に、ゲーム固有色と意味のある動きによって「何を考え、何をし、解けたとき何が起こるか」を補完する。

この文言は**調査上の定義案**である。`DESIGN.md`・Skill・要求の改定をこの文書で先取りしない。

### 評価する6つの性質（提案）

| 性質 | 判断したい問い | 失敗の例 |
|---|---|---|
| 1. 意味の適切さ | ゲーム自身の題材・盤・構造・操作と結びつくか。別のゲームを強く誤認させないか。 | どのゲームにも使える汎用記号に留まる。 |
| 2. 知覚・識別性 | 実サイズで主要な要素が読め、ほかのゲームから見分けられるか。 | 数字が潰れる、格子系のゲームが混同される。 |
| 3. 造形の完成度 | 構図、プロポーション、図形の接続、線、余白、重心、視覚階層が自然か。 | 部品は正しくても接続・比率が不自然、余白が片寄る。 |
| 4. 固有性・記憶性 | ゲーム固有の特徴があり、繰り返し見る中で認識の手がかりになるか。 | 別のゲームへ名前だけ差し替えられる。 |
| 5. 視覚的魅力 | 分かりやすさとは別に、ゲームを選ぶ楽しさに寄与する完成品か。 | 機械的に要素を配置しただけで印象に残らない。 |
| 6. セットとしての品質 | 他ゲームと並べたときに描画言語、密度、重心、視覚重量が調和するか。 | 単体ではよいが一覧で1点だけ大きく、細かく、濃い。 |

注意点:

- 6性質を単純に加点合計しない。「意味が誤っているが美しい」案や「伝わるが造形が破綻している」案を高得点で相殺しない。
- 単純性・具体性・意味的距離・光学重量は、6性質を診断するための**説明変数**として引き続き使う。従来の軸を捨てるものではない。
- 記憶性・選択意欲は、レビュー時の印象と実測値を明確に区別する。魅力を主張するだけで達成扱いにしない。
- 静的版のみに遊びの全手順を表現させない。選択中の動きも単なる飾りとして増やさない。

### 三段階の完成判定（提案）

1. **成立**: そのゲームの表現として意味が適切で、実サイズで知覚・識別できる。技術・SVG契約を守り、明白な破綻がない。
2. **造形の完成**: 主形状・補助要素の接続、比率、余白、視覚重心、線・面の階層を、局所と全体の両方から独立にレビューする。「特に問題が見当たらない」ではなく、形が成立している根拠を示す。
3. **製品体験への適合**: 単体の固有性・魅力と、全ゲームを並べた統一感を確認する。選択中は加えて遊びの核・達成の見せ場・静止状態からの連続性を確認する。

三段階は**全て必須**とする。全候補が不十分なら「採用候補なし・再探索」を許容する。既存Skillの人間による方向選択を置き換えず、選択の前後で候補を不適格と判定できるようにする。正確な運用ゲートや審査の責任分界は、別途規則への採用時に決める。

## 5. 検証方法の提案

品質定義だけを増やしても担保にはならないため、検証すべき対象・方法を分ける。

| 検証対象 | 方法案 | 言えること / 言えないこと |
|---|---|---|
| SVG契約 | 既存 `check_svg.py` 等の適切な引数で構文・禁止要素を検査。線幅・トークンなどの未検査範囲を明記。 | 決定論的な規約適合のみ。造形美や意味は判定できない。 |
| 知覚可能性 | 実際の表示枠と小サイズで、要素の読み取りを確認。ライト/ダークを含める。 | 要素の見え方。ゲームの意味理解とは別。 |
| 造形品質 | 表示条件を揃えた拡大・実寸・隣接比較で、形状・接続・余白・重心を独立レビュー。制作意図の説明を隠した評価も試す。 | 具体的な欠陥の発見。人の評価差があるため絶対的な数値保証ではない。 |
| ゲームの識別 | ゲームを知る人と初見の人を分け、名前なしで想起するもの・混同先を調べる。名前ありの一覧で選択させる評価も別に行う。 | 意味的距離と弁別性。初見で正式名称を答えられないだけで不合格にしない。 |
| 記憶性・魅力 | 一定期間後の再認、比較選好、ゲームを選びたくなる度合いを別々に確認する。 | 主観・行動傾向を測るが、実際の継続率やゲーム自体の面白さまで因果的に保証しない。 |
| 選択中の体験 | 現行の自己レビュー・実ブラウザ観察・別コンテキストの審査に加え、静止状態と動作後の双方でA/B/C/Dの目的を確かめる。 | 動きの成立、遊びと達成の伝達。実際の選択への効果は別途検証。 |

当面は10ゲームを同じ条件で棚卸し、強い例と弱い例を対で記録するのが有用である。最小サイズは実装で使われる値を確かめ、112px・48pxの比較は補助として維持する。複数の作り手・レビュー担当が違う結果を返す場合は、評価語彙と比較基準を改める。利用者テストの閾値は、対象者・課題・現状の基準値を確認してから設定し、根拠のない「正答率○%」を今は決めない。

## 6. 判断を保留する論点と次工程

### 現段階で決めないこと

- 各ゲームの既存SVGの採否・修正方針。上記の観察は探索対象であって不合格判定ではない。
- 6性質の点数や重み付け、利用者テストの合格率。
- 全ゲームの形状や角丸を強く統一すること。ゲーム固有の姿を損なう危険がある。
- `DESIGN.md` の規格変更、新たなSVG検査スクリプトの追加、静的版と選択中版の契約変更。

### 推奨する順序

1. 6性質が必要十分かを、既存10点の強み・問題例と照らして確かめる。
2. 造形品質・魅力の判断が揃うよう、良例／弱例と具体的な欠陥を使って評価基準を校正する。
3. 同一条件の比較、独立レビュー、必要に応じた利用者検証で、基準が実際に弱い成果物を落とせるか試す。
4. 成立した判断だけを `DESIGN.md` の全体原則と、制作Skillの評価・完成条件へ分担して反映する。過去の判断の根拠を失わないよう、`ADR-0016`・`ADR-0017` との整合を確認する。

この調査を作ったこと自体をもって、品質定義の合意や既存ピクトグラムの品質保証が完了したとは扱わない。
