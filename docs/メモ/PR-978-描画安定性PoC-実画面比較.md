# PR #978 盤面描画安定性PoC — 修正前後の実画面検証

## 対象と評価の前提

- 比較元: main `28515c34262df1647ed1ddff6878734bc32b570c`
- PoC: `22286ca176272c8edb2726572eb4bff5c5c17e3a`（検証時のコード）
- ブラウザ: Chromium 144.0.7559.96 / Debian 13、Playwright Python。
- 画面条件: 353×768 CSS px / DPR 1、390×844 CSS px / DPR 3（実際の `window.devicePixelRatio` と画像の物理寸法を確認）。2条件とも同じ「レベル1・No.0001」の固定問題を使用。
- 対象: バイナリパズル、マインスイーパー、リフレクション、詰将棋。
- 操作: バイナリパズルは空きマスに入力、マインスイーパーは未開示マスに旗、リフレクションは空きマスを選択、詰将棋は攻方の金を選択。**初期表示だけの検証ではない**。
- CSS入場フェードは実際のDOMに存在するアニメーションを再実行し、WAAPIで100ms地点に固定して取得。353×768では0 / 50 / 100 / 150 / 200msの5フレームも採取。これは**実際のiOS Safariで報告された不具合の再現動画ではない**。

|---|---:|---:|---:|
| バイナリパズル | 初期0 / 操作後0 | 初期0 / 操作後0 | 両版0 CSS px |
| マインスイーパー | 初期0 / 操作後0 | 初期0 / 操作後0 | 両版0 CSS px |
| リフレクション | 初期0 / 操作後0 | 初期0 / 操作後0 | 両版0 CSS px |
| 詰将棋 | 初期0 / 操作後0 | 初期0 / 操作後0 | 両版0 CSS px |

比較は盤面の同じDOM矩形を切り出し、RGB各チャンネルの差を調べたものです。操作で実際に変化した画素数（353 / 390-DPR3）は、順にバイナリパズル 3,386 / 37,382、マインスイーパー 135 / 1,293、リフレクション 2,450 / 26,244、詰将棋 1,348 / 14,777。各操作は画面に反映されています。実ブラウザの `pageerror` / `console.error` / `requestfailed` は対象8パターン両版とも0件です。

### 入場フェード100msにおける盤面画素の変化

「入場フェードを適用しない静止盤面」を基準に、各画素のRGB最大チャンネル差が2を超える画素を計数。

| ゲーム | 353×768・DPR1：main → PoC | 390×844・DPR3：main → PoC |
|---|---:|---:|
| バイナリパズル | 85,827 → **0** | 973,586 → **0** |
| マインスイーパー | 67,693 → **0** | 743,252 → **0** |
| リフレクション | 60,790 → **0** | 666,096 → **0** |
| 詰将棋 | 対象外（両版とも入場フェードなし） | 対象外（同左） |

353×768の5フレームでは、静止盤面と異なる画素数は次のとおりです（時点は0 / 50 / 100 / 150 / 200ms）。

- バイナリパズル: main = 90,300 / 90,244 / 85,827 / 5,713 / 0、PoC = **すべて0**。
- マインスイーパー: main = 106,816 / 84,377 / 67,693 / 3,075 / 0、PoC = **すべて0**。
- リフレクション: main = 62,750 / 62,750 / 60,790 / 1,984 / 0、PoC = **すべて0**。

この差は**ゲーム画面の盤面に入場フェードが掛からなくなったこと**を示します。mainの入場フェード自体が意図的な表現なので、「変化した全画素＝不具合画素」とみなしてはいけません。

### 実装上の検証と限界

- 共通 `animateBoardVisual(anchor, visual, ...)` はHTML/SVG双方に適用でき、配置要素そのものを対象にすると拒否することを既存テストで確認。
- 全ゲームがこのAPIを経由する仕組みには**未移行**。直接 `.animate()` やCSS変形を使う箇所は残っている。
- 完成演出を最後まで実操作で通した検証、複数状態でのラスタライズ飛びの再現、**実機iOS Safariでの修正前後比較**は未実施。今回の静止画・入場フェードの結果から、報告された1px前後のズレの解消を断定できない。
- サブピクセル丸め・隣接面の隙間・合成レイヤーの切り替えは独立した問題であり、現PoCのAPIがこれらすべてを解決したとは言えない。
- CIの[Quality Gate](https://github.com/hizahizi-hizumi/pa-zzle/actions/runs/44021812726)と[Workers Builds](https://github.com/hizahizi-hizumi/pa-zzle/pull/978/checks)は検証時コミットで成功。

## 判断

1. **技術的成立**: 配置を持つ要素と視覚効果要素を分けるAPIは既存の異なる描画方式へ導入できる。今回の4ゲーム・2端末条件では静止表示と通常操作の退行を検出しなかった。
2. **共通プレイ画面への効果**: 入場フェードから盤面を切り離すことは、CSSアニメーションのフレーム比較で確認できた。
3. **本来の目的に対する判定**: **未実証**。報告されている操作中・演出中の小数画素ズレを修正前で再現し、そのズレがPoCで消えることは確認できていない。現時点では「これで各パズルの個別修正を不要にできる」とは結論づけられない。**採用・全面移行の根拠として不十分**。

このPoCは設計実現性の検証としては完了ですが、問題解消を示すPoCとしては成立していません。判断に必要な残作業は、実際に報告されたズレの時点・描画画素をiOS Safari等で修正前後比較し、原因が単一の共通契約で吸収できるかを確かめることです。

## 再現手順

同一依存関係のmain・PoCのRepository Snapshotを2ディレクトリへ展開し、Viteを別ポート（例3101・3102）で起動。Playwrightの `ChatGPTBrowser` による応答中継で各ゲームのホームからレベル1・No.0001を開き、上記操作を行います。盤面の `getBoundingClientRect()` とPlaywrightスクリーンショットを採取し、RGB差を集計。DPR 3はChromiumのブラウザコンテキスト作成時に設定し、`devicePixelRatio` と1170×2532のフルスクリーン画像寸法を確認します。HTML/CSSの入場アニメーションは対象要素の `getAnimations()` を一時停止して時点を固定し、各フレームを比較します。

比較画像・5フレームGIF・全条件のPNGとJSON・再実行スクリプトは、実行会話へ添付した `pa-zzle-pr-978-visual-evidence.zip` に保存済みです。本GitHub資料は計測結果・判断を永続化するもので、画像本体はPRにアップロードしていません。


## 追試：PoC改訂版（詰将棋の詰み演出まで操作して検証）

前回のレポートは詰将棋を「駒の選択」までしか検証しておらず、詰み演出中の画素ズレを評価できなかった。その欠落を修正した。

### 比較条件と操作

- 比較元はPR #978の旧実装（`42434cbbf18f30a69c438c25dea2b0241cbf87e8`）、改訂版は本PRの最新コミット。
- Chromium、390×844 CSS px、レベル1・No.0001。
- `8一の金→9一`、玉方の応手`8三玉`、持駒の`金→8四`で詰みまで実操作。
- 完成演出を開始し、Web Animations APIの各アニメーションを停止して`currentTime=420ms`に固定、盤面の画像と`[data-piece]`のDOM矩形・computed transformを取得。

### 結果

| 指標 | 旧PoC | 改訂PoC |
|---|---:|---:|
| 駒自身を動かすWAAPIアニメーション | **4件** | **0件** |
| 盤面の光（`data-clear-glow`）へのWAAPIアニメーション | 81件 | 81件 |
| 7三の銀の見かけの位置 | 通常位置からY -1.01 CSS px | **通常位置** |
| 8四の金の見かけの位置 | 通常位置からY -1.01 CSS px | **通常位置** |
| 盤面の画素差（同じ演出時点、RGBチャネル差が2超） | \- | 旧版との比較で3,548/134,750画素 |

改訂版は`animateBoardPaint`を追加し、`transform`など形状を変えるキーフレームを拒否する。意図して動く着手演出は`animateBoardGeometry`で明示する。詰将棋の詰み演出は光だけをアニメーションし、駒の位置を動かさない。バイナリパズルの意図的な拡大演出は独立した幾何学的演出として維持する。

検証条件のChromiumでは、静止すべき駒の移動は解消した。ただし玉の詰み状態による**意図的な静的傾き**は維持しており、iOS Safariの実機描画や他の全ゲームのズレが解消したとは断定しない。現PoCのAPIは全ゲームへの適用を強制していないため、引き続き構造の完全適用と実機検証が必要。
