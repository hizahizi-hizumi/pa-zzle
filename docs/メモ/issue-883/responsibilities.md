# #883 責務構造の比較案（確定前）

## 一般的な基準と、採用しない形式

基本は機能別モジュール構成。何の意味や契約を決定するかを所有者の基準とし、同じ理由で変更されるコードを近づける。独立した機能や別ゲームの内部を必要以上に参照しない。参照先に必要なものが内部実装ではなく公開契約だけなら、契約の所有者を明確にする。

比較したのは技術種類別（全体にcomponents/hooks/services）、機能別（feature-first）、Feature-Sliced Design、DDD/クリーンアーキテクチャの形式的な層分け。形式的な層を全機能へ強制せず、11ゲームがある本アプリでは**機能別 + 画面合成・ゲーム統合 + 本当に共通の技術部品**を基準候補とする。

参考： [Redux Style Guide](https://redux.js.org/style-guide/) / [Thinking in React](https://react.dev/learn/thinking-in-react) / [Feature-Sliced Design](https://feature-sliced.design/docs/get-started/overview) / [Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)。設計上の参考であり、特定フレームワークやライブラリの採用を意味しない。

## 論理的な責務の候補

| 責務 | 主に決めること | 所有しないこと |
|---|---|---|
| ゲーム固有 | パズルの規則、問題、難易度、採点、プレイ操作、固有UI | 全アプリのルートや記録の保存方式 |
| ゲーム共通契約 | 同じ意味の問題識別、結果・session等の契約、共通ゲームUI | 特定ゲームの規則 |
| 記録 | プレイの事実、保存、履歴・自己ベストの共通導出 | 画面合成や固有採点 |
| 進捗・収集 | 図鑑、問題の収集状態、ゲーム横断の集計 | 記録の事実の正本 |
| 出題条件 | 候補の絞り込み、ランダム出題の条件と選択 | 問題生成・難易度判定 |
| 設定 | 利用者が変える値とその保存契約 | 設定される機能自体の計算規則 |
| ゲーム統合 | ゲーム登録とアプリへの能力の接続 | ゲーム内部ロジック |
| 画面・ナビゲーション | 画面の合成、ルーター値、遷移 | 独立機能のデータと評価規則 |
| アプリ起動 | 起動、初期化、実行時の全体接続 | パズルのルール |
| 汎用部品 | 再利用されるUIプリミティブと技術処理 | pa-zzleのドメイン判断 |

この10件は**思考の分類**であり、10ディレクトリを作る案ではない。進捗と図鑑を物理統合すること、記録UIを画面へすべて移すこと、`game-catalog/` を解体することは決定していない。

## 現行との差分に対する評価

- `games/` と `pages/`・`views/`：責務境界はかなり成立している。全面的に置き換える利益は未確認。
- `game-catalog/`：PR #424によるゲーム統合として意図的な存在。名称だけで廃止しない。個々の出題・画面・遷移の所有者を再判定する。
- `records/`：記録の機能固有UIを内部に持つこと自体は自然。`views/`への一律移動は初期提案から撤回し、機能の表示と画面の合成を個別判定する。
- `zukan/`：図鑑固有の規則とゲームホームのメニュー・成績が同居。ゲームホームのUIの所有者を再判定する。
- `collection/`：図鑑と概念上は近いが、物理的に統合した方がよい根拠はない。横断集計と画面表示の境界を確認する。
- `lib/`：汎用技術コードに機能固有の設定・出題条件が存在する。責務と依存方向の観点で個別確認する。
- `components/`：真の共通UIとアプリ専用UI・副作用接続の同居を評価する。

画面で使うUIは機能が所有してよい。「UIだからViewへ」「保存するからrecordsへ」「利用元が複数だからlibへ」という機械的な移動はしない。

## 判断の基準

1. その意味・契約・振る舞いの変更を最初に決める所有者はどこか。
2. 複数の利用者が必要としているのは、共通の意味か、実装形態の一致だけか。
3. アプリ・ゲーム・画面の分担（APP.md/GAME.md）と矛盾していないか。
4. 現行構造と比べて変更の局所性・発見可能性・循環防止・テスト容易性に**具体的な改善**があるか。
5. 既存のURL、保存、評価・出題条件、表示体験を意図せず変えないか。

次のM1で「何を維持するか」を確定し、M2で各ファイルを最終的な責務へ対応付ける。ここで挙げた責務分類・比較表を既定の規約として扱わない。
