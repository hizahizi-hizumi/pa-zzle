# パズル追加ワークフロー調査

> この文書は、パズル追加ワークフロー（`.claude/skills/add-puzzle/` と `.claude/agents/puzzle-*-reviewer.md`）の叩き台を作るために行った調査（2026-10-31）の記録であり、正本ではない。維持しない。
> 手順は Skill を、決まりは各正本（`AGENTS.md`、`docs/README.md`、`.claude/rules/`、`docs/プロダクト/`、`docs/パズル/`）を正とする。
>
> §1〜§6 は 2026-10-31 の1回目の調査と、それに基づく叩き台（当初の案）の記録である。その後 2026-11-01 に、作り方の領域別調査と2回の設計レビューを行い、プロダクトオーナーと前提を決め直して設計を v4 に改めた（§7〜§12）。当初の案と v4 が食い違うところは v4 を正とする。

## 結論

- 直近のパズル追加（スライドパズル以降）は、ほぼ同じ形で回っている。**導入成立性調査（4ゲート）→ `claude/<game>-NN-<topic>` の PR スタック（10〜13段）→ AI の全体・局所レビュー → 全段実装後の最終人間レビュー → 下の段から merge commit**。叩き台はこの形をそのまま型にした。
- 人間が判断しているのは、実際には「ルールの核」「本実装へ進むか」「最終レビュー（ピクトグラム・難易度プレビュー・難易度・ゲーム体験・フィードバック）」に限られる。それ以外を人間に聞くと不満が出ており、逆に設計上の重要判断を AI が黙って決めても不満が出ている。当初の叩き台の3関門（H0/H1/H2）はこの線引きによる（v4 では採らない。§10）。
- 人間レビューで最も多い指摘は**見た目の質**、最も手戻りが大きいのは**難易度**と**難易度プレビュー**。報告の分かりにくさへの指摘もほぼ全セッションで出ている。
- 仕組みとして欠けているのは、正式採用の記録、PR 段階の semantic lint、並行作業での採番、Claude Code 環境での画面確認手順、`game-structure.md` の追加手順の不足など。いくつかは叩き台の中で補い、規約を変える必要があるものは未決論点（§6）に残した。
- その後の調査と設計レビューで、大きな手戻りの原因は「AI に作り方が無い」ことより、人間の判断が要る前提が後から覆る順序・正本の書き方・共通基盤の並行変更にあると分かった（§8）。v4 では人間の関わりを「着手時の認識合わせ」と「作り切った後の最終レビュー」の2回にし、専用の作り方 Skill は必要になった順に1本ずつ作る（§10・§11）。

## 2. 最近のパズル追加の実際の進め方

### 2.1 全体の流れ

1. **候補の確認**: 人間が口語でアイデアを出す（「〜のアイデアあったっけ」）。AI が `docs/棚上げ/パズル候補.csv`・導入調査・コードを検索し、既存候補と近縁候補を返す。
2. **イメージ合わせ**: 遊べる紹介 HTML（Artifact）で「同じものを想像しているか」を確かめる。リポジトリには入れない（ハミルトン路、氷の床迷路）。
3. **導入成立性調査**: 4ゲート（問題供給・難易度運用・スマホプレイ・導入判断）。Opus サブエージェントを観点別に2〜4本並行し、メインが統合してコミットする。結論は直近3例とも `条件付き保留`。
4. **実装前提調査（段01）**: 仮決定一覧（理由・比べた案・最終レビューで判断してほしい点）とスタック計画。根拠を「事実／計測／外部知見／推測／AI判断（仮決定）」で書き分ける。
5. **本実装スタック**: 段ごとに Opus サブエージェントへ委譲。メインは共通ルールと段ごとの引継ぎを渡し、手本として直近パズルの同じ段の差分を指定する（ハミルトン路の段01は、リフレクション段01の差分を手本にした）。
6. **AI レビュー**: 段ごとの自己レビュー、スタック横断レビュー、人間レビュー前の全体・局所レビュー（詰将棋の段14・15が最新形）。
7. **最終人間レビュー**: Branch Preview URL を iPhone で触り、スクショ付きの短文で指摘する。Artifact のレビュー資料（論点ごとに「AI が決めたこと／判断してほしいこと／根拠／画像」、ラベルを伏せた遊び比べ）を併用する。
8. **マージ**: 最新 main へ rebase してから、人間が下の段から merge commit で数分のうちにまとめてマージする。
9. **後追い**: 共通化への追従 PR、本番で遊んでからの修正、難易度の再校正。

### 2.3 段の並び

スライドパズル以降、段の並びはほぼ一定で、`.claude/rules/game-structure.md` の標準配置とも対応する。

調査（仮決定一覧＋スタック計画）→ ルールと生成（UI なし）→ 固定問題で遊べる縦断 → プレイ UI → 難易度分析 → 問題集＋`--verify` → ピクトグラム＋ゲーム選択 → 難易度選択＋プレビュー → スコア・記録 → 結果・記録・再プレイの接続 → SPEC＋台帳

ばらつきは、ソルバーを独立段にするか（スライドパズル #397、詰将棋 #462・#463）、ピクトグラムを独立段にするか程度。リフレクションは11段、詰将棋は13段。

### 2.4 AI レビューの実態

- AI レビューは GitHub 上に残っていない。GitHub の review／review comment は #62 と #326 の2件だけで、どちらも初期に人のアカウントから貼った外部 AI レビュー。以後は PR 本文の `Validation`／`自己レビューでの修正`／`スタック横断レビューでの修正` 節に書かれている（#415、#416、#421）。
- サブエージェントはサブエージェントを起動できないため、レビュー役はメインが別に立てている（リフレクション段04）。
- 見つかったものの例: 難易度判定が深すぎる（リフレクション L5 が 753問→138問、#416）、数字キーや Esc が効かない、コントラスト不足、待ったの位置、問題集の再読込不可、大きすぎるコミット（#484）。
- チュートリアル作業では、経緯を知らない新しいレビュー役にチェックリストだけを渡して見直させ、拾えなかった問題はまず Skill 側のチェックリストを直していた（未マージの `origin/docs/game-tutorial-skill`）。
- 決定論的な検査は `./scripts/verify.sh` と CI `quality-gate`、問題集の `--verify`、Python 研究実装との照合（#413、400盤面）が担う。

### 2.5 人間レビューの実態

- 指摘は GitHub ではなくセッションのチャットで出る。人間が PR に書いたコメントは無い。AI が PR 本文の「人間レビュー対応（N回目）」に原文を引用して記録する形が最も詳しい（#421、#422）。
- 人間が見る領域は、スライドパズルのセッションで「ピクトグラム／プレビュー／難易度／パズル体験／フィードバック」の5つと定まり、それ以外は「ルールに書いてある通りに判断して」とされた（#362 の Validation にも記載）。詰将棋では4項目（ピクトグラム／難易度プレビュー／ゲーム体験／伏せ問題10問）に絞った。
- 材料は Branch Preview URL（最上段がスタック全体を反映）、Artifact のレビュー資料、記入式の最終レビュー資料（詰将棋）、問題ID の URL、人間自身のプレイ記録 JSON（リフレクション L5 の54件、#485）。

## 3. 人間レビューで出た指摘の傾向

### 3.1 分類と頻度

複数の調査結果を合わせた概数。

| 分類 | 頻度 | 例 |
|---|---|---|
| 見た目の質（はみ出し、がたつき、重なり順、角丸過多、窮屈さ） | 最多。リフレクションだけで約16件 | 光路が罫線の下に回る（#456）、プレイ中に盤面がガタつく（タクズ）、ボトルが潰れている（ウォーターソート）、「角丸多すぎるけど、design.md には沿ってるんかな」 |
| 難易度プレビュー | 7セッション中6で発生、1セッションで数回〜10回 | 盤面そのものをプレビューにしない・抽象化する（スライドパズル）、既存プレビューの意図（数字の密度）を捨てた（ナンプレ）、レベル2の盤面が埋まっている（タクズ） |
| 難易度の軸と水準 | 全パズル | レバーが1つだけになっている（ウォーターソート、パーキングジャム、マインスイーパー）、「レベル5でも簡単すぎる」（リフレクション）、レベル5内のばらつき（タクズ、#485）、L5 が4〜8秒（#457） |
| 状態の知らせ | 約5件 | 盤面の正誤が分からない（リフレクション。AI の仮決定「何も示さない」を覆した） |
| 補助操作・操作体系 | 約5件 | 待ったが無い→追加（タクズ）、待ったは要るか→削除（リフレクション）、iOS で隣のマスを押せない（#456） |
| ピクトグラム | 約5件、ただし1回で約10往復 | 3×3 を試す、角丸を控える、フォントをパスにする（スライドパズル）、レーザーがぶつ切り（リフレクション） |
| スコア・基準時間 | 約4件 | 置き直しのペナルティ→速さだけ、基準時間の再校正（リフレクション） |
| 既存ゲームとの一貫性 | 中 | 待ったをウォーターソートと変える意図、共通部品の流用、難易度選択はウォーターソートに合わせる（#382） |
| 名称・商標 | 少 | 正式名称・商用名を調べる（スライドパズル）、商標調査の未実施（パーキングジャム #407） |
| AI の報告・説明の質 | ほぼ全セッション | 案を記号だけで呼ぶ、推奨の利点が「一般的だから」しかない、スクショを見ずに推測で答える、何をレビューすればよいか分からない |
| 進め方・Git | 中 | PR を1本にまとめない、試行錯誤ごとに push しない、コードに試行錯誤のコメントを残さない、main 追従を merge commit でしない |

人間の指摘は短い口語で、1回に3〜10件ほど。強い不満が出たのは、プレビューの作り直しが繰り返されたときと、AI が画面を確かめずに報告したときだった。

### 3.2 手戻りの典型

1. **難易度が人間の試遊で作り直される**: 機械の分類は成立していても体感と合わない。試行ソルバーの追加→分類の作り直し→問題集の再生成→基準時間とプレビューの作り直しと連鎖し、規模が大きい（リフレクション L5 は段05、3回目レビュー、#485 の3回作り直し）。UI の変更で分類器の前提が崩れることもある（一致表示を足したら試し置きで解けるようになった）。
2. **プレビューの作り直し**: 画面仕様（旧 SCR-002）の過剰な適用、「実問題をそのままプレビューにする」方針の再発、既存プレビューの意図を読まない置き換えが原因。
3. **調査段階の前提の誤り**: パーキングジャムは PoC 条件を完成仕様として扱い全面撤回（#250、#287）。スライドパズルは「盤面サイズは難易度にしない」という AI の前提が覆り、10段を作り直した（#362〜#371 → #393〜#402）。
4. **AI の仮決定が覆る**: 正誤を示さない→一致表示、待ったの有無、配点 60/40→速さだけ。これを受けて、文書では「AI判断（仮決定）」と「人間判断」を見出し語で分けるようになった。
5. **AI が人間を通さず重要判断を前提にする**: マインスイーパーの「推測なし」、パーキングジャムの代表問題の選定基準。サブエージェントが正本の文書に確定事項として書いた例もある。
6. **main の共通化との衝突**: 長いスタックの作業中に共通化（#426〜#441、#464〜#490、#508〜#513）が進み、追従 PR（#455）や追従段（#497）が要った。
7. **人間レビュー前に止まる**: 詰将棋で全体・局所レビュー、`--verify`、PR 本文の更新を残したまま止まり、人間に止まっている理由を聞かれた。

## 4. うまくいっていない点

### 4.1 正式採用が記録されない

`docs/棚上げ/README.md` は導入判断に `正式採用` を持つが、提供中の7パズルのうち `正式採用` はナンプレとウォーターソートだけ。スライドパズル・タクズ・リフレクションは `条件付き保留`、マインスイーパーとパーキングジャムは `実装候補` のまま更新されていない。各 PR は「人間の実プレイ照合が済むまで台帳の段階は変えない」と書いてマージしている（#402、#422）が、その後に正式採用へ進めた記録は無い。AI が一括で `正式採用` にした変更は PR の範囲外として取り消された（`e6596500` → `b96fdc28`）。

v4 では、マージを本決定とし、別手続きの正式採用は持たない（§10）。

### 4.2 PR 段階で semantic lint が走らない

`.github/workflows/quality-gate.yml` は semantic lint の `check` を main への push と手動実行に限っている（課金抑制）。`scripts/verify.sh` も `--plan-only` までで provider を呼ばない。新しいパズルの責務混入（`game-structure/position-responsibility`、`game-ui/no-game-logic-in-ui` など）はマージ後に見つかり、ゲームごとの Issue（#446〜#453）になっている。cloud 環境には `TYPESAFE_API_KEY` が無い。

### 4.3 導入判断の区分と実態のずれ

区分は `未判断 / 実装候補 / 条件付き保留 / 見送り / 正式採用` だが、`実装候補` は 2026-09-15 の一括調査でしか付いておらず、`見送り` の例は無い。5段階難易度が採用条件になってからは、難易度運用が試遊待ちで `確認中` に留まるため、導入判断はほぼ必ず `条件付き保留` になり、そのまま本実装へ進んでいる。タクズのように採用条件の変化でゲートを `確認中` へ戻す例、ハミルトン路の `条件付き通過` のように README に無い値もある。

### 4.4 採番衝突

- SPEC 番号: スライドパズル SPEC-010→011、タクズ 011→012、詰将棋 014→015→019 と振り直した。ハミルトン路の実装前提調査も SPEC-019 を予約しており、詰将棋と衝突している。
- 候補 ID: 氷の床迷路は AI が PUZZLE-094 を採番した。並行作業との衝突を確かめる仕組みは無い。

### 4.5 壊れた参照

正本には壊れたパス参照は見つからなかった。資料の中には次がある。

- **`game-structure.md` の「ゲームを追加するとき」が4手順しかない**: `problem-pool.json` の `frontend/biome.json` `files.includes` からの除外、問題集生成・分析スクリプトと `package.json` の scripts、`PuzzleSelectionView.test.tsx` の一覧、全ゲームが持つ de facto 標準の UI ファイル群（`<Game>DifficultyPreview.tsx`、`<Game>HowToPlayDialog.tsx`、`<Game>Diagnostics.tsx` など）が書かれていない。

### 5.7 報告ルール

各項目は、セッションで繰り返し出た指摘から取った。

- 結論から短く、触る Preview URL と画像を添える。リポジトリ外のパスを渡さない（人間が開けない一時ファイルのパスを渡してレビューできないと言われた、スライドパズル）。
- 案を記号だけで呼ばず中身で説明し、推奨には具体的な利点を書く（マインスイーパー）。
- 推測と実測を分け、自分で画面を見てから報告する（タクズ、ウォーターソート、ナンプレ）。
- 人間に聞くのは本人が決めることだけ。ただし設計上の重要判断は H0 に含める（ナンプレの過剰な確認、マインスイーパーの推測あり/なし）。
- 確定した案を勝手に変えない（マインスイーパーのプレビュー）。PR 監視や定期確認を提案しない（スライドパズル、ウォーターソート、マインスイーパー）。
- 残作業を抱えたまま止まらない（詰将棋）。

## 6. 未決論点（当初の案の時点）

叩き台を作るときに決めきれなかった論点。叩き台では仮の扱いを決めてあるが、どれも人間の判断が要る。1〜3 と 6 は v4 で扱いを決めた（1・2: 関門を置かず着手時の認識合わせにする、3: 正式採用を持たずマージを本決定にする、6: 調査開始時に予約する。§10）。

1. **導入判断の区分**: 実態は「条件付き保留のまま本実装」（§4.3）。叩き台は H1 で明示的に判断する形にした。`実装候補` と `条件付き保留` の区分自体を見直すか。
2. **H0 を必須にするか**: 氷の床迷路の手戻りの少なさ（§5.1）からは必須が妥当に見えるが、人間が一度に判断する回数は増える。
3. **正式採用（H2）と台帳更新を必須工程にするか**: 必須にする場合、未更新の5パズル（スライドパズル、タクズ、リフレクション、マインスイーパー、パーキングジャム）の台帳をどうするか。台帳は資料で維持義務は無い。
4. **PR 段階の semantic lint**: cloud 環境に `TYPESAFE_API_KEY` を入れるか、CI の実行条件を変えるか、マージ後の Issue 化のままにするか。
5. **`game-structure.md` の不足**: §4.7 の不足を rule 側で直すか（`/add-rule` 系と `rule-reviewer` を通す）、Skill のチェックリストに留めるか。
6. **採番衝突の防止**: SPEC・PUZZLE ID の衝突（§4.4）を、最終段での採番と全ブランチ確認で防ぐか、予約の仕組みを作るか。
7. **チュートリアル Skill**: 未マージの `origin/docs/game-tutorial-skill` を段として組み込むか。組み込むなら、実装コードと rule 改訂を先に main へ入れる必要がある。
8. **壊れた参照**: 資料内の `docs/開発/*` などへの参照（§4.5）を直すか、資料なので放置するか。

この他に、叩き台では仮の扱いにしたが判断の余地があるもの:

- Claude Code 環境の画面確認を、環境準備手順を整えて AI 側で行うか、Branch Preview と実機に頼るか（§4.6）。
- 調査 Issue を必須にするか（Issue なしで進んだ例が3件ある）。
- 操作試作 HTML をコミットするか（§4.7）。

## 7. 作り方の調査で分かったこと

2026-11-01 に、4つの領域（面白さの核と問題の質／難易度／プレイ画面・難易度プレビュー・見た目／スコア・結果・記録）を Opus サブエージェントに分けて調べた。対象は main（#518 付近）、未マージのブランチ（詰将棋 `origin/claude/tsume-shogi-16-main-sync`、ハミルトン路 `origin/claude/hamiltonian-11-spec`、氷の床迷路、パーキングジャム難易度 v2 の #457）、各パズルの導入調査文書と PR 本文、§1 の会話記録。領域ごとに「初版 → 何がダメだったか → 決着」「方法」「評価軸」「失敗パターン」「機械検査にできるもの」「専用 Skill にする価値」をまとめた。画面は起動して見ていない。調査結果の全文は残していないので、要点をこの章に置く。

### 7.1 面白さの核と問題の質

- AI の初版は、どのパズルでも面白さか難易度の面で1回以上覆った。ほぼすべて人間の実プレイ（実機・試遊・記録 JSON）で見つかり、機械の分類が成り立っていることは手がかりにならなかった。
- 問題の質の失敗（自明・重複・偏り）は機械でほぼ見つかっている。例: ハミルトン路の全面盤は 96% 以上が重複、ウォーターソートは全レベル4色に張り付き、リフレクションの影響しないピース、氷の床迷路の無関係な岩。一方「簡単すぎ」「面白くない」は機械の検査を通り抜けた。
- 覆った原因は4つに分かれる: 規模の扱い、1レバー化、UI の知らせが挑戦の中身を変えたこと、核の天井が低いこと（パーキングジャムのレベル5 が4〜8秒、#457）。
- ルール変種の比較が効いた例: ハミルトン路（4変種と仕切り、#521）、氷の床迷路の床4構成、リフレクションの成立条件（全ピース使用、各ピースが少なくとも1本のヒントへ影響）。供給の制約がルールの核を変えることがある（ハミルトン路の仕切り）。
- 主な失敗パターン: PoC の条件を完成仕様に取り違える（パーキングジャム #250 → #287）、知らせの表示が挑戦を試行錯誤に変える、ルール変種を AI が無承認で前提にする（マインスイーパーの推測なし）、生成器が最初に合った候補を採って偏る、解き順・視点への依存、罰で難しくする（氷の床の穴）。
- 専用 Skill の判断: 価値は高いが、挑戦の定義・解法器・生成・品質・5段階は1本の連鎖なので難易度と束ねる案を推した。設計レビューでは、叩き台の `references/research.md` と大部分が重なり、着手時の材料として薄くてよいとされた（§8）。

### 7.2 難易度

- どのパズルでも `docs/パズル/難易度開発手順.md` の工程9（人間のプレイとの照合）はほぼ毎回未実施でマージされ、工程10 は人間の指摘をきっかけに後から走った。
- ずれは5つの型に収束する。
  1. 1レバー化（ウォーターソート、パーキングジャム第1版 D+）
  2. 規模の過剰排除。正本の「規模だけで帯を埋めない」を「規模を入れない」と読み、マインスイーパー・スライドパズル・パーキングジャムで人間が覆した（#372、#393、#406）
  3. 最上位が簡単すぎる。補助で「読む」が「試す」に置き換わる（リフレクション #421 4回目、パーキングジャム #457）
  4. 帯の中のばらつきとサイズの逆転（リフレクション #485、タクズのレベル5）
  5. 全レベルが同じ盤面に張り付く（ウォーターソートの全レベル4色）
- 作り直しは、分析 → 組み合わせ定義 → 問題集（数十分〜1時間超）→ 基準時間・プレビュー・SPEC・記録の互換へ波及する。
- 効いた方法: レバーを2〜3系統で出し、規模を入れないなら理由を書く。基準とするプレイ条件を UI の補助込みで決める。読むモデル（人間向け解法器）と試すモデル（リフレクション `trial-solver.ts`、ウォーターソートの自然詰み率）を両方持つ。解法器の緩さを別のサブエージェントに検査させる（リフレクションのレベル5 が 753問 → 138問、#416）。組み合わせ定義で、隣接レベルは規模を共有し、上位はどのレバーも下げず、見た目と難しさを逆転させない。候補領域を巡回して採る。レベルごとの一言説明を閾値より先に書く。
- 統計関数（Spearman、同条件 AUC、四分位）は `frontend/scripts/analyze-*.ts`・`generate-*-problem-pool.ts` の7ファイル以上に複製されている。
- ほかの失敗パターン: 静的な盤面特徴が実プレイで効かない（パーキングジャム v1）、解き順依存（タクズ）、分位点や等重み平均で切る、1人の実測への過適合、版の波及漏れ、人間判断の巻き戻し（§12 の #457）。
- 専用 Skill の判断: 4領域で最も価値が高い。手戻りが最大で型が繰り返し、新規追加以外（既存パズルの再設計、記録 JSON を受けた再校正）からも起動される。`難易度開発手順.md` は「何を満たせば完了か」の正本のまま残し、Skill は作り方・検査・波及を持つ。プレビューとスコアは束ねない。

### 7.3 プレイ画面・難易度プレビュー・見た目

- 指摘の件数は、見た目、難易度プレビュー、状態の知らせ、操作の順に多い。プレビューは最も手戻りが多い。
- プレビューの失敗は4型: 実問題の盤面をそのまま縮小する、難易度の軸でない違いで差を作る、描き込みすぎる、既存プレビューの意図を読まずに置き換える（ナンプレ、マインスイーパー #358）。決着した形は全ゲームで同じ構造に収束した（決まりは `DESIGN.md` §3 を正とする）。
- 見た目の指摘の多くは計測で再現できた（位置ずれ、がたつき、重なり順、はみ出し。#421、#456）。iOS Safari 固有のもの（ダブルタップ、描画順）は Chromium で再現できず、「未確認」と書くしかなかった。
- プレイ画面の説明文は毎回消すことになった（決まりは `GAME.md`）。補助操作と知らせは AI の仮決定が覆りやすい（待ったの追加と削除、一致表示の追加）。知らせを足すと難易度の前提が崩れるので、プレイ UI と難易度は一緒に見直す。
- 主な失敗パターン: 答えを描く、知らせが難易度を壊す、がたつき、座標系が2つある、重なり順を合成に任せる、角丸・枠・影の重ね、iOS のタップ、技術的に通ることを完成と取り違える、画面を見ずに報告する、指摘のつぎはぎ修正。
- 専用 Skill の判断: 価値は高い。プレイ UI とプレビューを別 Skill にする。見た目は単独で起動される場面が無いので独立 Skill にせず、計測は判断を含まないのでスクリプトにする。

### 7.4 スコア・結果・記録

- 人間が指摘したのは係数の大小より、(a) その操作を減点してよいか（待った、置き直し、総当たり）と、(b) 基準時間の水準だった。(a) は観点の定義まで戻り、(b) は人間の記録1件で直った（リフレクション #421 5回目）。
- 待ったの有無は評価と記録の形に直結する（タクズで追加、リフレクションで削除）。難易度の作り直しは採点に波及する（スライドパズルの盤面把握の時間、リフレクションの試し置きの項）。
- 基準時間は難易度ラベルではなく問題の作業量から求める（パーキングジャム v1 → v2、#404）。速さだけにすると総当たりが perfect になるゲームがある（詰将棋 #481）。AI の数値シミュレーションは仮定の上の導出で、校正は人間の実時間でしか進まなかった。
- 評価設計の横断工程（#279）は open のまま正本になっていない。
- 主な失敗パターン: 取れる値から観点を作る、遊び方の中心の操作を罰する、攻略法を称える、二重減点、解法器の回数をそのまま人間の時間にする、補助操作を既存ゲームと理由なく変える、結果を診断値の一覧にする、文書の数値とコードのずれ（§12）。
- 専用 Skill の判断: 独立 Skill にする価値はあるとした。ただし設計レビューでは、人間は単純化を求めており、記録での校正の部分は過大評価とされた。先に §12 の食い違いと #279 を片付ける。

### 7.5 4領域を通して

- 補助・知らせ → 基準とするプレイ条件 → 難易度の判定 → 問題集 → 基準時間 → プレビュー、という連鎖があり、逆向きもある（スライドパズルではプレビューの列数に合わせて難易度の割り当てを変えた）。
- 「人間の解き方のモデル」（基準とするプレイ条件、解法器、単純プレイヤー、作業量）は、難易度・プレイ UI・スコアが共有している。持ち主が分かれていたことが連鎖の一因だった。
- 単純プレイヤーは既にゲームごとにある（リフレクション `trial-solver.ts`、ウォーターソート `natural-play.ts`）。どれも人間に「簡単すぎる」と言われた後で足された。

## 8. 設計レビュー1回目の結論（専用 Skill 6本案）

### 8.1 対象と方法

叩き台の `add-puzzle` を薄い司令塔（関門 H0/H1/H2）にし、各段の作り方を専用 Skill 6本（難易度、難易度プレビュー、プレイ UI、面白さの核と問題の質、スコア、画面の撮影と計測）に分け、撮影と計測から順に作る案。経緯を渡さない4人のレビュー役（前提の診断、ワークフロー設計、パズル制作、反対の立場）が独立に読んだ。

### 8.2 診断が半分しか当たっていなかった

手戻りが起きる領域は実績と合っていた。しかし原因を「AI に作り方が無い」とした診断は、半分しか当たっていなかった。最も大きな手戻りの主な原因は次の3つである。

1. **人間が遊べる物に触れるのが最後の1回だけという順序**。リフレクションの連鎖（一致表示の追加 → 試し置きで解ける → 試行ソルバーの新設と問題集の版2〜4 → スコアと基準時間の作り直し）は、補助の決定が難易度より後に来たことによる（#421、#422、#485）。
2. **正本と人間の判断の食い違い**。AI は `docs/パズル/難易度.md`「挑戦ではない負担を難易度にしない」と `難易度開発手順.md` に従って規模を外し、3パズルで人間に覆された。
3. **共通基盤の並行変更への追従**（#382、#404、#455、#497）。#455 では、人間が決めた結果画面の形を共通部品の形に戻した。

ほかに分かったこと:

- 作り方の Skill が既にあった領域でも手戻りは減っていない。リフレクションのピクトグラムは `design-game-pictogram` に従って約30案から絞ったが、人間レビューで2回直しが出た（#418、#421）。
- リフレクションの人間指摘（約28件）は、機械的な欠陥7、書かれた決まりへの違反3〜4、書かれていない好み約9、遊んで決めるゲーム設計の判断約8に分かれる。Skill が効きうるのは主に前の2つで、後の2つは人間が遊ぶまで決まらない。決まりへの違反の分は 2026-10-04〜05 に正本へ入った（a190f37c）。
- 診断に無かった原因: 曖昧な指摘の読み違い（#421 の「枠線」を外枠と解釈したが罫線だった。#456 で判明）、iOS Safari 固有の不具合、ルール判定の不具合（偽の一致。性質テストで見つかる種類）、前例の機械的な流用（待った、配点 60/40）、人間レビューの滞留。

### 8.3 専用 Skill を先にまとめて作らない理由

- 方法論は既に正本にある（`難易度開発手順.md` の12工程）のに手戻りが出ている。手順を Skill に書き直すと正本と二重になる（`docs/README.md`）。Skill に固有に置く価値があるのは、検査スクリプト、実例、失敗パターン、人間に渡す資料の型に限られる。
- 6本で4,000〜5,000行の見込み。`.claude/rules/context-engineering.md` §5 は Skill を人間が書く前提にしており、まとめて作ると人間のレビュー量が大きい。既存の `design-game-pictogram` は作った後に更新されておらず、学びを Skill に戻す運用が回っていない。未マージのチュートリアル Skill（`origin/docs/game-tutorial-skill`）は1本で書き直しを重ねている。
- パズル追加は約1か月に1件で、少ない実行回数で6本を育てることになる。
- 撮影と計測は判断を含まないので、Skill ではなくスクリプト（`capture-screens.mjs` の拡張）にする。測定で見つかる不具合は人間指摘の1割強で、先頭に作る根拠は弱い。

結論として、次のパズルでその段に着いたときに、実際にうまくいった作業から1本ずつ作り、人間がレビューする。先に効くのは司令塔の段取りと正本の修正である。

### 8.4 v4 に引き継いだ指摘

- 司令塔の本文を短くし、制約を先頭に置く（コンパクション後に戻る本文は先頭の一部だけ。§9.5）。
- 段の実装担当を Agent 定義にし、`model: opus` を固定する。文章だけの指示はコンパクションで落ちる。
- 入れ子のサブエージェントは、この環境では起動できない。作り方の手順は1エージェントで完結させ、独立した検証はメインが別に立てる。
- 人間の選択を待つ `design-game-pictogram` と止まらない司令塔がぶつかるので、add-puzzle から呼ぶモードを足す。
- 決まりは正本に、作り方は Skill に、評価の観点はレビュー Agent に置き、互いに写さない。
- 最上位が簡単すぎることを、単純プレイヤーのシミュレーションで事前に検出する。
- 供給・性能・版の互換（生成時間、再生成時間、バンドル増分、記録の互換）を難所として扱う。

v4 で採らなかった提案: 段04 の後に人間が遊ぶ中間関門（H1.5）と、伏せ試遊のマージ前必須化。前者は §10.1 の前提2・5と合わない。後者は完了した例が無く、伏せる仕組みは #473 で main から消え、校正は公開後の記録 JSON（#459）で回っている（#485、#457）。

## 9. 設計レビュー2回目の結論（「作り切ってから見せる」案）

### 9.1 対象と方法

AI が一度作り切り、人間が判断しやすい形にしてから見せる案。人間の関わりは着手・最終レビュー・正式採用とマージ。前提が連鎖する判断は候補ごとのブランチで遊べる状態にし、条件ごとに難易度を測ってから並べる。反映は波及表に沿って原因の段へ畳み込む。3人のレビュー役（人間の判断負荷、実行可能性、反対の立場）が独立に読んだ。

### 9.2 往復の見込み

- 「1回で決まる」は実績から無理がある。リフレクションの5回は2〜3回に減る見込みにとどまる。指摘は層をなして出る（大きい問題が直ると細かい問題が見える）。基準時間の校正、実機でしか出ない不具合、見せてから決まる好みは、遊ばれる前には潰せない。
- 減る分の多くは、正本が育ったこと（2026-10-04〜05 の `GAME.md`・`DESIGN.md`）と、回帰が無くなることによる。設計の効果とは分けて見積もる。
- AI が論点と思っていない前提は選択肢にならない。規模を難易度のレバーにするかは3回とも AI の候補の外にあり、ハミルトン路の仕切りは最終レビューの論点に回った（#540）。
- 律速は往復回数ではなく、人間が遊んで判断する時間とその着手である。リフレクションの5回は約35時間に収まり、軽い往復は安かった。作り切ってから見せる形に最も近い詰将棋（#484、#492 で人間レビューを4項目に絞った）は約1か月未マージで、その間に main の共通化（#508〜#513）が入った。
- 往復回数だけを指標にすると、仮決定のままマージして後で直せば小さく見える。

### 9.3 選択肢づくりの負荷

- 好みで決まる単発の判断（ピクトグラム）では負荷を下げるが、前提が連鎖する判断では上げうる。判断の材料は遊ぶことなので、候補 × レベル × 数問を遊ぶ時間が増える。軸は互いに影響する（一致表示で、盤面の規模・試し置きの効き方・基準時間がすべて変わった）。
- 候補ごとに難易度を測るには解法器の作り直しが要ることがあり（#421 4回目は試行ソルバーの新設）、問題集の再生成だけでは済まない。今の分析は問題だけを受け取り、プレイ条件を引数に取らない。
- 好みは見せたものへの反応として決まり、AI が事前に並べた候補と推奨はたびたび外れた。人間の指摘の半分は選択ではなく方向づけ（もっと大きい盤面を試す、色を指定する）だった。
- 候補ごとのブランチは、記録が origin ごとの localStorage に分かれ、組み合わせとスタックの載せ直しが増える。
- 人間は PR にコメントを残さず、遊びながらの一言とスクショで指摘している。記入欄の多い資料は形が合わない。

### 9.4 積み直しの実地検証

ハミルトン路のスタックを使い捨てのクローンに取り、叩き台の反映手順（最上段で `--fixup` を作り、`rebase -i --autosquash --update-refs`）を試した（GitHub には書き込んでいない）。

- 後の段で触られていない箇所の修正は数秒で通り、全段のブランチが動いた。
- 段04 の `HamiltonianPathPlay.tsx` のうち段09・10 で書き換わった部分を最上段で直すと、fixup が段04 の版に当たらず衝突した。最上段の文脈で書いた修正は古い段に当たらない。ハミルトン路では同じ UI ファイルを4段が変更しており、人間の指摘が多い領域ほど当たる。叩き台は衝突したら止まるので、「止まらずに通す」と両立しない。過去のスタックが修正を上に段として積んでいたのも（スライドパズルの 11〜16、詰将棋の 14〜16）、この難しさの表れと読める。
- 問題集の入力（ルール、生成器、分析、組み合わせ定義）を問題集の段より後で変えると、問題集とその段のコードの食い違いが CI を素通りする。問題集のテストは ID の一意性と引けることしか見ず、`--verify` は CI で走らない。
- 叩き台は最上段の先端しか verify しないので、途中の段の失敗は push の後に見つかる。

### 9.5 実行面の制約

| 制約 | v4 での扱い |
|---|---|
| サブエージェントからサブエージェントを起動できない（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`。製品の既定ではない） | 実装・レビュー・修正の繰り返しはメインが回す。差分の全文や大量の画像をメインに入れない |
| コンパクション後に戻る Skill 本文は、Skill ごとに最近の起動1回分の先頭約 5k token（全体で 25k まで）。Read した reference は戻らない。叩き台の SKILL.md は約1万字で、制約節は 9,500 字目から | 本文を 4k token 未満にし、制約を先頭に置く。状態は PR 本文と実装前提調査に置く |
| Agent の `isolation: worktree` は既定ブランチから切る | メインが段の worktree を用意して渡す。実装担当はそこでコミットまで行い、push しない |
| `gh pr *` と GraphQL は 403。REST と GitHub MCP は使える | MCP を優先し、無ければ `gh api` の REST。`/pr` は使わない |
| Workers Builds は PR の無いブランチでもビルドし、check-run に版ごとの固定 URL が載る。CI は PR と main への push でしか走らない。クラウド環境からプレビュー URL に接続できない | 遊んで決める別案は PR なしの使い捨てブランチにし、手元で検証する |
| Playwright は Chromium だけで WebKit が無い | iOS 固有の点は最終レビュー資料に「実機で見てほしい未検証の点」として出す |
| 4コア、バックグラウンド実行は最長2時間。リフレクション級の問題集生成は数時間かかる | 候補の比較は小さな仮の問題集で行い、全部の再生成は採用案だけ、再開できる形にする |
| 叩き台は force-push の許可を H1 で得ていた。候補ブランチを同じ接頭辞で作ると、叩き台の「並行作業の形跡」判定に毎回当たる | 許可は着手時にまとめて得る。形跡は「同じ接頭辞のブランチで、自分たちの PR 本文の Stack 表に無いもの」とする |
| テキストの衝突が無くても、共通契約の変更への追従が要る（詰将棋の 16-main-sync） | main との使い捨てのマージで verify する |

v4 で採らなかった提案: 段04 直後の「返事を待たない5分の早期試遊」と、調査の終わりの「返事を待たない核の見本」は、§10.1 の前提2と合わない。前提変更の多くは着手時の認識合わせで聞く項目に移した。「マージと正式採用を分ける」は、前提3により正式採用そのものを持たない形にした。表示や補助の候補を1つのプレビュー内で切り替える内部フラグ案は、切り替えのコードと複数の問題集が成果物に入り、決まった後に外す作業がつぎはぎになるため、使い捨てブランチを採った。

## 10. プロダクトオーナーと決めた前提と v4 の判断

### 10.1 前提

1. AI の実装・作り直しは安い。限られているのは人間の時間と判断力で、最適化するのはマージまでに人間がかける時間・往復回数・着手からマージまでの日数。
2. 人間は指示してから10分程度は画面の前にいることが多いが、それ以降にできたものはすぐには見ない。返事を待たない途中報告は見ない。
3. 人間のマージ判断が本決定。マージ後の修正は新しい改善で、手戻りではない。台帳は資料で、マージに付随して更新する。
4. 着手時の認識合わせは、時間より中身の確かさを優先する。10分は目安で、締め切りではない。
5. 未完成のものを途中で人間に判断させない。

### 10.2 v4 の判断と根拠

| 判断 | 前提 | 根拠 |
|---|---|---|

### 10.3 効果の測り方

次に追加するパズルで、マージまでに人間がかけた時間（レビュー回数 × 所要時間の自己申告でよい）、往復回数、着手からマージまでの日数を記録する。指摘の分類（機械で見つけられたはず／書かれた決まりへの違反／好み／遊んで決めるもの／AI の前提の誤り／回帰／実機のみ）は、経緯を知らない別のサブエージェントが行う。2回目のレビューで、比較が1件対1件でパズルの新しさや正本の成長が混ざること、設計者が分類すると甘くなることが指摘されたためである。

## 11. 今後作る作り方 Skill の候補と順番

必要になった順に、実際にうまくいった作業から1本ずつ抜き出し、人間のレビューを付けて作る（§8.3）。決まりは正本に置き、Skill には写さない。各領域の調査の要点は §7 に置いた。

| 順 | 候補（名前は仮） | 範囲 | 先に要るもの・注意 |

## 12. 見つかった不整合・別件

この作業の範囲外として、直していないもの。

1. **自己ベストの時間の指標**: `docs/プロダクト/仕様/パズル/SPEC-008.md`（ナンプレ）と `SPEC-018.md`（パーキングジャム）は、自己ベストで経過時間を少ないほど良い値として比べると書く。コードは全ゲーム `time-delta-ms`（#510。`frontend/src/games/{nanpure,parking-jam}/play-record.ts`）。
2. **パーキングジャムの旧記録の再計算**: `docs/パズル/パーキングジャム採点.md`「保存と再計算」は、payloadVersion 2 の記録を `play-quality-v1` で再計算して表示し続けると書く。SPEC-001 と #510 は当時の規則で計算し直さない。#506 は open。
3. **#457（パーキングジャム難易度 v2、open）**: 人間が入れると決めた規模のレバー（#406）を分類から外している。人間判断との衝突として、マージ前に扱いを決める必要がある。
4. **タクズのレベル5 のばらつき**: 試遊でレベル5 内の差が指摘され、2,500問の実測で「素直に埋まるマス数」が 3〜37 だった。判定に入れる提案で止まり、`frontend/src/games/takuzu/difficulty.ts` は未反映。
5. **ナンプレの基準時間**: 全問共通の15分のまま、5段階化の後も未校正（#247 open、`docs/パズル/導入調査/ナンプレ/ナンプレ5段階難易度.md` §10）。新しいパズルの手本にしない。
6. **SPEC-019 の衝突**: 詰将棋（`origin/claude/tsume-shogi-13-spec`）とハミルトン路（`origin/claude/hamiltonian-11-spec`）が、どちらも `docs/プロダクト/仕様/パズル/SPEC-019.md` を作っている。後からマージする側が振り直す。v4 は調査開始時の予約で防ぐ。
7. **資料内の壊れた参照**: §4.5 のとおり（未マージの `docs/開発/*`、廃止した SCR-002、欠番の FR-004、改名前の `fifteen-puzzle`、移動前の `docs/立ち上げ/`）。資料は維持しない扱いで、直していない。
8. **正本の規模の書き方**: `docs/パズル/難易度.md`「挑戦ではない負担を難易度にしない」と `難易度開発手順.md` は、規模を難易度のレバーに入れてよいかを書いていない。AI が「入れない」と読み、3回覆された。直すかは人間の判断（§11 の難易度 Skill の前提）。
9. **問題集の整合を CI が見ていない**: 問題集のテストは ID の一意性と引けることしか確かめず、生成器や分類との一致を見る `--verify` は CI で走らない。

## 13. 実行役の単体検証（2026-11-01）

オーケストレーターを丸ごと試す前に、実行役を1つずつ、人間レビューの指摘が残っている過去の状態で検証した。正解は、その状態に当てはまる人間の指摘（リフレクション: PR #421 の人間レビュー対応から15件、ウォーターソート: Issue #67〜#69 から11件）。実行役には経緯も正解も渡さない。

### 13.1 結果

| 実行役 | リフレクション（`97e14512`） | ウォーターソート（`489bd6a1`） |
|---|---|---|
| 試遊役 `puzzle-playtester` | 再現率 27%（改良前）、適合率 88% | 再現率 59%（改良後）、事実として妥当な指摘の割合 95% |
| 体験レビュー役 `puzzle-experience-reviewer` | 再現率 23%（当時の正本だけで判断） | 再現率 77%（ただし今の正本で判断） |
| 両方を合わせた場合 | 43% | 86% |

- 試遊役は「遊んで困る・物足りない」指摘に強く、見た目・題材らしさ・熟練者の物足りなさは拾えない。困らなかったことを自分で打ち消す傾向があった（観点を直した）。
- 体験レビュー役は書かれた決まりの範囲でしか拾えない。リフレクションでは、書かれていない好み（色の量、待ったの要否、正誤の知らせ）について AI 自身の仮決定を「規約どおり」と追認した。ウォーターソートで高く出たのは、そのレビューの指摘がのちに `DESIGN.md`・`GAME.md` の決まりになっていたため（答えの漏れ）。
- 検証では、対象自身の今の仕様と今のコードが答えの経路になる。当時の版の正本だけで判断させる必要がある。

### 13.2 素朴なプレイヤーの検査

陽性（人間が「最上位が簡単すぎる」と言った状態: ウォーターソート `489bd6a1` の hard、リフレクション `72465e93` の L5、パーキングジャム main の L5）と陰性（ウォーターソート・リフレクションの今の main）で、素朴なプレイヤー（補助なしランダム、合法手ランダム、貪欲、試し置きして戻す）に各レベル30問を解かせた。

- 陽性3件はどの判定規則でも検出した。「解けた割合」で判定すると陰性1件を誤判定し、「貪欲の手数 ÷ 最短手数 ≦ 1.45」なら5件とも正しく分けた（閾値は5件を見てから置いたもので未検証）。
- 止める向きにだけ使える。素朴なプレイヤーが苦労しても、熟練者に難しいとは限らない（ウォーターソートの hard はランダムでは42%しか1回で解けないが、熟練者には簡単だった）。
- 合法手を選べば必ず解けるパズル（パーキングジャム）には原理的に効かず、「今出せる手の割合」のような構造量で代える。
- 今の main の問題集は、似た素朴なプレイヤー（ウォーターソートの `natural-play.ts`、リフレクションの `trial-solver.ts`）で選ばれていて、どちらも人間に指摘された後に作られた。共通の検査を先に回せば、指摘の前に見つけられた可能性が高い。
- 共通部分は `.claude/skills/add-puzzle/scripts/naive-play-core.ts`、ゲームごとのアダプタの手本は `examples/naive-play-*.ts`。

### 13.3 分かったこと

- 実際に効いていた仕組みは、人間の指摘を他のパズルにも効く決まりとして正本へ書き戻し、次のパズルで AI レビューが当てはめる流れだった。オーケストレーターの最終レビューの反映にこの書き戻しを入れた。
- 人間にしか判断できないもの（熟練者にとっての手応え、書かれていない好み、iOS 実機）は残る。AI 側でできるのは、それを最終レビュー資料の「見てほしい点」に絞って渡すこと。
