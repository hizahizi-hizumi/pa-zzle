# DESIGN.md をアプリ全体のデザインシステムに絞り、正式フォーマットの構成に従う

## 要約

- **決定**: `DESIGN.md` はアプリ全体のデザインシステムだけを書き、画面ごとの決まりを外す。外した決まりのうち意図のあるものは、画面ごとの目的と、優先すること・やらないことの意図（Why / Why not）だけを書く画面文書（`docs/プロダクト/画面/`）に移し、画面の What / How はコードとテストに任せる。構成は Google Labs DESIGN.md Format の8節に日本語見出しで従い、本文では決まりと、判断を広げるのに要る意図を伝える。YAML のトークンは置かず、正確な値は `@theme` の1か所を正本とする。
- **主な選択肢**: 画面ごとの優先順位を含む独自構成を保つ / 正式フォーマットに完全準拠し YAML トークンを正本にする / 節構成に従い、本文は決まりだけにする / 節構成に従い、本文で決まりと意図を伝える。
- **背景**: 画面文書の廃止（ADR-0003）で画面の決まりが `DESIGN.md` に移り、画面の判断が全体の決まりとして読まれる事故が起きた。同じ時に設計原則を決まりだけにしたため、決まりの無い場面へ判断を広げる手がかりも失われた。
- **要約**: DESIGN.md をアプリ全体のデザインシステムだけを書く文書にし、Google Labs DESIGN.md Format の8節（概要・色・タイポグラフィ・レイアウト・奥行き・形・コンポーネント・「すべきこと・避けること」）に日本語見出しで従い、本文で決まりと意図を伝える。外した画面ごとの決まりは、Why / Why not だけを書く画面文書に移す。独自構成の維持、YAML トークンを正本とする完全準拠、本文を決まりだけにする案と比べた。値の正本を @theme に保ち、画面の判断が全体の決まりに化けず、決まりの無い場面へ判断を広げられることを重視した。

## 背景と問題

`DESIGN.md` は 2026-09-17 に、デザイン上の意味・意図・判断原則の正本として独自の章立てで作った。正確なトークン値は最初から Tailwind CSS の `@theme` を正本とし、`DESIGN.md` を値の正本にすることと、文書から Tailwind 設定を生成することは対象外とした（Issue #73）。その時点で Google Labs の DESIGN.md Format（2026-04 公開）は既にあったが、検討した記録は無い。

画面種別ごとの判断は、`DESIGN.md` を全体の原則に保つために画面文書（SCR-001〜005）へ分けていた（PR #132）。ADR-0003 で画面文書を廃止した際（PR #499）、画面について決めたことを `DESIGN.md` の「画面ごとの優先順位」へ移した。その後も画面ごとの節が足され、`DESIGN.md` はデザインシステムと画面の決まりが混ざった文書になった。

混ざった結果、一つの画面の性質が根拠のないまま全ゲーム共通の決まりとして読まれ、後から外す必要が生じた（PR #545）。画面の決まりを写した記述は、画面の配置・構成・表示項目といった What / How を含み、実装と一緒に古くなる性質も持っていた。

同じ PR #499 で設計原則を決まりだけにした際、「表現の強さ」を何のために変えるかなど、決まりの意図を述べた文も外した。その後は継ぎ足しが続き、節の役割が曖昧なまま同じ決まりが複数の節に書かれた。

正式フォーマットは、トークンが正確な値を与え、本文がその値のある理由と使い方を伝えるものとしている。

## 判断基準

- エージェントが一貫した UI を作るための、アプリ全体の色・文字・形・状態・動き・音の使い分けが読めること。
- 決まりの無い場面でも、決まりの意図から同じ方向に判断できること。
- 画面の判断がアプリ全体の決まりとして読まれないこと。
- 正確な値の正本が1か所であること。
- 外した画面の決まりの意図を失わず、実装とずれる画面の写しを作らないこと。
- 広く使われている構成に揃い、エージェントが節の役割を迷わないこと。

## 検討した選択肢

1. **独自構成を保つ**: 今の章立てと「画面ごとの優先順位」を保つ。
2. **正式フォーマットに完全準拠する**: 英語見出しの8節に従い、YAML のトークンを値の正本にして `@theme` を生成する。
3. **節構成に従い、本文は決まりだけにする**: 8節に日本語見出しで従い、8節に収まらない全体の決まり（操作と状態・動き・音など）は独自節にする。YAML は置かず、画面ごとの決まりを外す。本文には決まりだけを書く。
4. **節構成に従い、本文で決まりと意図を伝える**: 3 と同じ構成で、決まりの無い場面へ判断を広げるのに要る決まりにだけ、一次資料に根拠のある意図を短く添える。

## 採用した選択肢と理由

採用: **節構成に従い、本文で決まりと意図を伝える**。理由: 正式フォーマットの節構成はデザインシステムの記述範囲そのものを表しており、そこに揃えると画面の決まりが入る余地が無くなる。値の正本を `@theme` に置く判断（Issue #73）は変える理由が無く、YAML を持つと値が二重になる。本文の役割は正式フォーマットに従い、値は `@theme` に任せて、決まりとその意図を伝える。決まりだけでは、決まりの無い場面でどちらへ判断するかが読めない。一方で、全項目に意図を求めると根拠の無い理由を書き足すことになるため、意図は要るところだけに、一次資料に根拠があるものだけを書く。書き方は ADR-0013 に揃える。

外した画面ごとの決まりは、画面ごとの文書（`docs/プロダクト/画面/`、`SCR-nnn`）に移す。画面文書には、遊ぶ人がその画面で何を得るか（目的）と、その画面で優先すること・やらないことを、その意図（Why / Why not）とともに書く。画面の配置・構成・大きさ・動きの手順・表示項目の並びといった What / How は書かず、コードとテストを正とする。ADR-0003 が廃止した旧画面文書（SCR-001〜005）は What / How を写していたため、実装とずれて古くなった。画面文書はコードより弱い正本で、食い違えば画面文書を直すことになるので、ずれうる What / How を持たせない。意図が一次資料に見つからない決まりと、要件・仕様や `APP.md`・`GAME.md`・`DESIGN.md` で言えている決まりは移さない。画面文書は、旧画面文書を戻すのではなく、この方針で作り直す。これにより、ADR-0003 のうち画面の文書を廃止した部分を置き換える。旧画面文書の番号は、番号に意味を持たせないまま使い直す。

画面ごとの節にあった決まりのうち、複数の画面で同じ意味を持つもの（評価段階の色、状態が変わっても周りの要素を動かさないこと、選ぶ場面で称賛や割合を付けないことなど）は、画面を名指さずに `DESIGN.md` の該当する節へ一般化して残す。ADR-0004・ADR-0011・ADR-0012 は、見せ方の正として `DESIGN.md` の「ゲームのホーム」「タイトル」「記録」を参照していた。これらの節は無くなるので、その参照先を、該当する画面文書と仕様・コードに置き換える。

### 帰結

- Good: `DESIGN.md` の各節の役割が決まり、画面の判断が全体の決まりとして読まれなくなる。
- Good: 値の正本が `@theme` の1か所に保たれる。
- Good: 決まりの意図が読め、決まりの無い場面でも同じ方向に判断できる。
- Good: 画面ごとの意図が画面文書に残り、画面を変えるときに、その画面で何を優先し何をやらないかを知らずに戻さない。
- Bad: YAML を持たないため、正式フォーマットの lint・export（`@google/design.md`）を使えない。
- Bad: 画面の配置・構成などの細部は文書から読めず、コードとテストを読む必要がある。
- Bad: この変更の直前の `DESIGN.md` の「画面ごとの優先順位」にあった決まりのうち、意図が見つからなかったものは、画面文書にも移さず、文書から読めなくなる。それらはコードと旧版にだけ残る。
- Bad: 根拠の見つからない決まりは意図を持たないまま残り、その決まりからは判断を広げにくい。

## 各選択肢の良し悪し

### 独自構成を保つ

- Good: 書き直しの手間が要らない。
- Bad: 画面の決まりとデザインシステムが混ざったままになり、画面の判断が全体の決まりとして読まれる事故が続く。

### 正式フォーマットに完全準拠する

- Good: 公式の lint・export・Tailwind 変換をそのまま使える。
- Bad: 値の正本が `DESIGN.md` に移り、Issue #73 の判断を覆す。生成の仕組みと、生成物と手で書いた CSS の境界の管理が新たに要る。

### 節構成に従い、本文は決まりだけにする

- Good: 節の役割が正式フォーマットと揃い、値の正本も変わらない。本文が短く保てる。
- Bad: 正式フォーマットが本文に求める役割を果たさず、決まりの無い場面への判断の手がかりが無い。

### 節構成に従い、本文で決まりと意図を伝える

- Good: 節の役割と本文の役割が正式フォーマットと揃い、値の正本も変わらない。
- Bad: 日本語見出しと独自節のため、正式フォーマットのツールでは検査できない。意図の根拠を一次資料から探す手間が要る。
