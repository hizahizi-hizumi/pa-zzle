# DESIGN.md をアプリ全体のデザインシステムに絞り、正式フォーマットの構成に従う

## 要約

- **決定**: `DESIGN.md` はアプリ全体のデザインシステムだけを定義し、画面ごとの決まりを持たない。構成は Google Labs DESIGN.md Format の8節に日本語見出しで従い、YAML のトークンは置かず、正確な値は `@theme` の1か所を正本とする。
- **主な選択肢**: 画面ごとの優先順位を含む独自構成を保つ / 正式フォーマットに完全準拠し YAML トークンを正本にする / 正式フォーマットの節構成に日本語見出しで従い、値は `@theme` に置く。
- **背景**: 画面文書の廃止（ADR-0003）で画面の決まりが `DESIGN.md` に移り、デザインシステムと画面の判断が混ざって、画面の判断が全体の決まりとして読まれる事故が起きた。
- **要約**: DESIGN.md をアプリ全体のデザインシステムだけを定義する文書に絞り、Google Labs DESIGN.md Format の8節（概要・色・タイポグラフィ・レイアウト・奥行き・形・コンポーネント・すべきこと・避けること）に日本語見出しで従う。画面ごとの優先順位を含む独自構成の維持、YAML トークンを正本とする完全準拠と比べた。値の正本を @theme の1か所に保つことと、画面の判断がアプリ全体の決まりに化けないことを重視した。

## 背景と問題

`DESIGN.md` は 2026-09-17 に、デザイン上の意味・意図・判断原則の正本として独自の章立てで作った。正確なトークン値は最初から Tailwind CSS の `@theme` を正本とし、`DESIGN.md` を値の正本にすることと、文書から Tailwind 設定を生成することは対象外とした（Issue #73）。その時点で Google Labs の DESIGN.md Format（2026-04 公開）は既にあったが、検討した記録は無い。

画面種別ごとの判断は、`DESIGN.md` を全体の原則に保つために画面文書（SCR-001〜005）へ分けていた（PR #132）。ADR-0003 で画面文書を廃止した際、画面について決めたことを `DESIGN.md` の「画面ごとの優先順位」へ移した。その後も画面ごとの節が足され、`DESIGN.md` はデザインシステムと画面の決まりが混ざった文書になった。

混ざった結果、一つの画面の性質が根拠のないまま全ゲーム共通の決まりとして読まれ、後から外す必要が生じた（PR #545）。画面の決まりを写した記述は、画面の配置・構成・表示項目といった What / How を含み、実装と一緒に古くなる性質も持っていた。

## 判断基準

- エージェントが一貫した UI を作るための、アプリ全体の色・文字・形・状態・動きの使い分けが読めること。
- 画面の判断がアプリ全体の決まりとして読まれないこと。
- 正確な値の正本が1か所であること。
- 広く使われている構成に揃い、エージェントが節の役割を迷わないこと。

## 検討した選択肢

1. **独自構成を保つ**: 今の章立てと「画面ごとの優先順位」を保つ。
2. **正式フォーマットに完全準拠する**: 英語見出しの8節に従い、YAML のトークンを値の正本にして `@theme` を生成する。
3. **節構成だけ従い、値は `@theme` に置く**: 8節に日本語見出しで従い、8節に収まらない全体の決まり（操作状態・動き・効果音など）は独自節にする。YAML は置かず、画面ごとの決まりを外す。

## 採用した選択肢と理由

採用: **節構成だけ従い、値は `@theme` に置く**。理由: 正式フォーマットの節構成はデザインシステムの記述範囲そのものを表しており、そこに揃えると画面の決まりが入る余地が無くなる。一方、値の正本を `@theme` に置く判断（Issue #73）は変える理由が無く、YAML を持つと値が二重になる。正式フォーマットも本文が最も重要でトークンは文脈だとしており、本文の構成だけ従っても趣旨は損なわない。

画面について残すべきなのは What / How ではなく、その画面の Why / Why not である。これは画面の作り直しの後に、Why / Why not だけを書く画面文書として作り直す。

### 帰結

- Good: `DESIGN.md` の各節の役割が決まり、画面の判断が全体の決まりとして読まれなくなる。
- Good: 値の正本が `@theme` の1か所に保たれる。
- Bad: YAML を持たないため、正式フォーマットの lint・export（`@google/design.md`）を使えない。
- Bad: 画面文書を作り直すまで、画面ごとの Why / Why not は文書から読めず、git 履歴（`DESIGN.md` の「画面ごとの優先順位」）を辿る必要がある。

## 各選択肢の良し悪し

### 独自構成を保つ

- Good: 書き直しの手間が要らない。
- Bad: 画面の決まりとデザインシステムが混ざったままになり、画面の判断が全体の決まりとして読まれる事故が続く。

### 正式フォーマットに完全準拠する

- Good: 公式の lint・export・Tailwind 変換をそのまま使える。
- Bad: 値の正本が `DESIGN.md` に移り、Issue #73 の判断を覆す。生成の仕組みと、生成物と手で書いた CSS の境界の管理が新たに要る。

### 節構成だけ従い、値は `@theme` に置く

- Good: 節の役割が正式フォーマットと揃い、値の正本も変わらない。
- Bad: 日本語見出しと独自節のため、正式フォーマットのツールでは検査できない。
