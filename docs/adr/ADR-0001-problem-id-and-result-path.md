# 問題IDと結果画面の専用パス

## 要約

- **決定**: 問題を生成情報全体から求めた不透明な問題IDで指してプレイ画面のURLに載せ、記録からの遊び直しを通常のプレイ導線へ統一し、結果画面に記録IDで開く専用パスを持たせる。
- **主な選択肢**: 問題の指し方（seed などの識別情報をそのままURLへ出す / 問題集の番号 / 生成情報全体のハッシュ）、遊び直しの入口（記録専用の再プレイパス / 問題ID付きのプレイ画面）、結果画面（プレイ画面の中の状態 / 記録IDの専用パス）。
- **背景**: 結果画面がURLを持たず再読み込みで次の問題が始まり、遊んでいる問題もURLから辿れず、記録からの遊び直しだけが専用パスで別扱いになっていた。
- **要約**: 問題を生成器の版・生成条件・seed・生成試行を含む識別情報全体のハッシュから求めた不透明な問題IDで指し、プレイ画面URLの problem クエリに載せる。seed の公開、問題集の番号、記録専用の再プレイパスと比べ、内部の意味を外へ出さず問題集の作り直しにも揺れないことを重視した。結果画面は記録IDの専用パスとし、再読み込みで結果を失わない。

## 背景と問題

各ゲームの問題は、生成器の版、生成条件、seed、生成試行などからなる識別情報（problem identity）で再現でき、記録にはこの識別情報を保存している。しかし次の問題があった。

- プレイ画面のURLは難易度だけを持ち、遊んでいる問題を指していなかった。プレイ中に再読み込みすると別の問題が始まった。
- 結果画面はプレイ画面の中の状態で、URLを持たなかった。結果を見たまま再読み込みすると、結果が消えて次の問題が始まった。
- 記録から同じ問題を遊び直す導線は `/records/replay/:recordId` という記録専用のパスで、記録を読んで問題を復元する専用の画面を持っていた。通常のプレイと別の入口・別の復元経路になっていた。
- 「新しい問題」や結果からの次の問題で、直前と同じ問題が続けて出ることを防いでいなかった。

seed は生成の入力の一部にすぎず、seed だけでは問題が決まらない。識別情報の各項目をURLへ出すと、URLが生成の内部構造（項目の意味や組み合わせ）に依存し、識別情報の形を変えるたびにURLの互換を考える必要が生じる。

## 判断基準

- 遊んでいる問題と見ている結果が、再読み込みで失われないこと。
- URLへ出す値に、難易度・生成条件・seed などの内部の意味を持たせないこと。
- 問題集を作り直して並び順が変わっても、同じ問題を同じ値で指せること。
- 記録の遊び直しと通常のプレイで、問題の始め方・記録の扱いを分けないこと。
- 遊び直せない記録（旧難易度区分、生成器の版違い、問題集から外れた問題など）を一律に扱えること。

## 検討した選択肢

1. **識別情報（seed など）をそのままURLのクエリへ出す**
2. **問題集の版と番号でURLに問題を指す**
3. **識別情報全体のハッシュから求めた不透明な問題IDでURLに問題を指す**

遊び直しの入口については、記録専用の再プレイパスを残す案と、問題ID付きの通常のプレイ画面へ遷移する案を比べた。結果画面については、プレイ画面の中の状態のままにする案と、記録IDで開く専用パス（`/puzzles/<game>/result/<記録ID>`）を持たせる案を比べた。

## 採用した選択肢と理由

採用: **識別情報全体のハッシュから求めた不透明な問題ID、問題ID付きのプレイ画面への遊び直しの統一、記録IDで開く結果画面の専用パス**。理由: 問題IDは識別情報の正規化した全体から一方向に求めるので、同じ問題からは常に同じ値になり、URLから内部の意味を読み取れず、問題集の並び順にも依存しない。問題IDから問題へは問題集の索引で引き、引けないIDは通知せず新しい問題を選ぶことで、遊び直せない記録や古いURLを一つの規則で扱える。遊び直しを通常のプレイ導線に寄せることで、問題の始め方と記録の保存が一つになり、専用の画面と復元経路が不要になる。結果画面は保存した記録から作り直せるので、記録IDを持つ専用パスにすれば再読み込みしても同じ結果を開き直せる。

プレイ画面のURLは `/puzzles/<game>/play/<難易度>?problem=<問題ID>` とし、遊んでいる問題の問題IDを履歴を増やさずに反映する。クリアして記録を保存できたら、結果画面へ履歴を置き換えて遷移する。

### 帰結

- Good: プレイ中や結果表示中に再読み込みしても、同じ問題・同じ結果のまま続けられる。
- Good: 記録の遊び直し、結果画面の「同じ問題」、URLでの問題指定が同じ入口になり、`/records/replay/:recordId` と専用 View を削除できた。
- Good: 問題IDを比べるだけで、「新しい問題」や結果からの次の問題で直前と同じ問題を避けられる。
- Bad: 問題IDは一方向のハッシュなので、問題IDから問題へは今の問題集を引くしかなく、問題集に無い問題は問題IDで遊べない。遊び直せない理由も利用者へ区別して示せない。
- Bad: 問題IDの算出方法（正規化とハッシュ）は記録やURLに残る値を決めるため、変えられない。
- Bad: 記録を保存しないプレイ（内部診断の遊び比べなど）と保存に失敗したプレイは結果画面の専用パスを持てず、その場で結果を出す経路が残る。
- Bad: 自己ベスト更新などの告知はクリア直後の遷移で渡す情報に依存し、記録から結果を開き直したときには出せない。

## 各選択肢の良し悪し

### 識別情報（seed など）をそのままURLのクエリへ出す

- Good: 問題集に無い問題も、URLから生成器で再現できる。
- Bad: URLが識別情報の項目と意味に依存し、生成器や識別情報の形を変えるたびにURLの互換を保つ必要がある。
- Bad: 難易度や生成条件がURLから読め、利用者向けの値として不要な意味を持つ。

### 問題集の版と番号でURLに問題を指す

- Good: 値が短く、問題集から直接引ける。
- Bad: 問題集を作り直すと番号が変わり、同じ問題を同じ値で指せない。記録との対応も崩れる。

### 識別情報全体のハッシュから求めた不透明な問題ID

- Good: 内部の意味を持たず、問題集の並び順に依存せず、記録の識別情報からも同じ値を求められる。
- Bad: 問題を引くのに問題集の索引が必要で、算出方法を固定する必要がある。
