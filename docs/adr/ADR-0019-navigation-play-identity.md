# 問題URLとプレイ継続を画面履歴から独立させる

## 要約

- **決定**: 問題IDを必須とするプレイURLを採用し、画面移動と挑戦の終了を分ける。
- **主な選択肢**: 難易度指定のランダム入口をプレイURLに残す / 問題IDをクエリに置く / 問題IDをパスの識別子にする。
- **背景**: 戻る・再読み込み・共有が異なる問題や新しい挑戦を生み、履歴をたどっても遊びの文脈を維持できなかった。
- **要約**: プレイURLをゲームと不透明な問題IDで識別し、難易度は問題から解決する。難易度だけのランダム入口やクエリで問題を後から補う方式と比較した。直接アクセス・再読み込み・共有で同じ問題を開き、画面移動とプレイ終了を分離して進行状態を引き継ぐことを優先した。

## 背景と問題

旧プレイURLは難易度を入口として問題を画面内で選び、問題IDを後からクエリに反映していた。問題が存在しないIDでも、別問題への自動変更によって同じ問題を指すという保証が崩れていた。ブラウザ履歴を画面移動に使っても、戻っただけで新しいプレイになると操作や推論が失われた。

ゲームの種類を問わず、開いた対象はURLで再現できる必要がある。一方、盤面の操作履歴や経過時間までURLへ載せると、長いURLと不正な状態の管理が必要になる。

## 判断基準

- URLが同じ問題を指し、無効なIDを黙って別問題へ置き換えないこと。
- ブラウザの戻る・進む・再読み込みで、プレイヤーが明示的にやり直さない限り挑戦を失わないこと。
- ゲーム固有の盤面や採点を、アプリのURL設計で均質化しないこと。
- ランダム選択による素早いプレイ開始の導線は保つこと。

## 検討した選択肢

1. **難易度指定のURLを維持し、プレイ画面内で問題IDを確定する**
2. **難易度と問題IDを併記したURLを使う**
3. **ゲームと問題IDを必須とするURLを使う**

## 採用した選択肢と理由

採用: **ゲームと問題IDを必須とするURLを使う**。理由: ランダム出題は遷移前に問題を決めればよく、難易度をURLに重複させる必要がないため。画面内の移動や一時的な中断はプレイの終了条件とせず、盤面・履歴・計数・開始時刻はプレイ側に保存する。結果は記録IDの独立URLで開き、保存失敗時も同じ画面へ遷移する。

### 帰結

- Good: プレイURLの意味は問題に固定され、戻る・再読み込みで別問題にすり替わらない。
- Good: ブラウザ履歴と待った・リセットなどのゲーム操作を独立して扱える。
- Bad: 同じタブ内の進行状態を保存・復元する処理が必要で、保存不可能な環境では途中状態の保証に限界がある。
- Bad: 問題集から消えたIDは直接開けないため、開けない理由を利用者へ知らせる必要がある。

## 各選択肢の良し悪し

### 難易度指定のURLを維持する

- Good: 現行のランダム開始経路を変更しなくて済む。
- Bad: URLを開いた時点では問題が確定せず、直接アクセスや共有の意味が曖昧になる。

### 難易度と問題IDを併記する

- Good: URLの見た目から難易度が分かる。
- Bad: 難易度を再分類した場合に同じ問題のURLの整合確認が必要になる。

### ゲームと問題IDのみを使う

- Good: 識別に必要な値だけで同じ問題を指せる。
- Bad: URLだけを読んでも難易度は分からない。難易度は画面で示す。

## 補足

- ADR-0001 のプレイURL構造と無効IDの自動置換を置き換える。問題IDの算出方式と記録からの遊び直しは維持する。
- ADR-0002 の保存失敗時の表示経路を置き換える。保存された記録を結果の正本とする判断は維持する。
