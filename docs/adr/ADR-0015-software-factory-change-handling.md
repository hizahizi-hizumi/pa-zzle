# 仕様どおりかは機械、楽しいかは PO が判断し、変更を自動・体験確認・承認に分ける

## 要約

- **決定**: エージェントが実装した変更を、差分と一方向ドア面の golden から CI が「自動」「体験確認」「承認」の3つの扱いに分ける。仕様どおりかは決定論的なゲート（静的検査、テスト、golden、プールの検証、Playwright の E2E）で閉じる。楽しいかと取り返しのつかない影響は PO が判断し、PO が merge することを承認とする。自動の扱いだけを CI が merge する。LLM の判定は助言に留め、合否に使わない。遊ぶ人の端末から情報を送る計測はしない。
- **主な選択肢**: 全 PR を PO が確かめる今の運用を続ける / 体験の判断も含めて完全に無人化する / 扱いを3つに分け、PO の判断を体験と一方向ドアに絞る。合否の付け方は、決定論的なゲート / LLM の判定。承認の表し方は、PO の merge / ラベル・承認コメント・Bot アカウント。
- **背景**: 実装の大半をエージェントが担い、約53日で約600 PR が作られた。PO は1人で、判断・確認・merge をすべて兼ねている。強制しているゲートは静的検査・単体テスト・ビルドだけで、PO の確認がほぼ唯一の統合検証になっている。
- **要約**: 差分と一方向ドア面の golden から CI が変更を自動・体験確認・承認に分け、仕様どおりかは静的検査・テスト・golden・E2E で閉じ、楽しいかと取り返しのつかない影響は PO が判断して merge する。全変更を PO が確かめる今の運用、完全無人化、LLM の判定をゲートにする案と比べた。PO の判断時間が最も希少であることと、面白さは人間にしか判定できないことを重視した。

## 背景と問題

- 実装の大半はエージェントが担っている。2026-09-12 から 2026-11-04 までに約600 PR が作られ、merge 以外のコミットの大半が Claude によるもの。
- PO は1人で、要求の判断、プレビューでの確認、merge をすべて兼ねている。

この開発の最も希少な資源は、PO の注意と判断の時間になっている。

### 品質の性質が二つに分かれる

- 機械で強く判定できる品質
  - パズルの成立性（一意解・可解性）、問題生成の決定性、問題ID、採点の性質、依存方向
  - ゲームごとのソルバーやプールの `--verify` など、判定器がすでにある
- 人間にしか判定できない品質
  - 面白さ、ワクワク、手触り（NFR-001・002、GAME.md、DESIGN.md）
  - 文書自身が、正しく動くだけでは成り立ったとみなさないと書いている

### 取り返しのつかない変更（一方向ドア）がある

- 記録は端末の localStorage にしか無い
- 生成器の版を上げると全問の問題ID が変わり、記録から遊び直せなくなる
- 評価は保存せず今の規則で導くので、評価規則を変えると過去の評価が遡って変わる
- 難易度の意味、URL も、一度出すと戻せない

### 今の運用の問題

- 強制しているゲートは Biome・tsc・Vitest・build だけ。統合の検証は PO がプレビューを見ることにほぼ頼っている
- 並列で作業するエージェントが、ADR・SPEC 番号の衝突、長いスタックと main の衝突、放置された PR を生んでいる
- LLM で規約を判定する semantic-lint は、調整に使っていない holdout で recall 54% だった。文脈の量で精度が 90% から 24% まで揺れたため、停止した

### 前提

- 未リリース。将来は一般公開する

## 判断基準

- PO の判断時間を、人間にしかできない判断（体験と一方向ドア）だけに使えること
- 仕様どおりかどうかを、再現できる決定論的な仕組みで保証できること
- 一方向ドアに触れた変更を、PO が知らずに受け入れないこと
- 合格基準を、実装と同じ変更の中で弱められないこと
- Claude Code と ChatGPT のどちらの実行環境で作った変更にも、同じ基準がかかること
- 遊ぶ人の情報を外へ送らず、プライバシーポリシーなどの義務を負わないこと

## 検討した選択肢

### 運用の形

1. **全 PR を PO が確かめる今の運用を続ける**
2. **体験の判断も含めて完全に無人化する**
3. **扱いを3つに分け、PO の判断を体験と一方向ドアに絞る**

### 合否の付け方

1. **決定論的なゲートで合否を付け、LLM の判定は助言にする**
2. **LLM の判定もゲートにする**

### 承認の表し方

1. **PO が merge することを承認とする**
2. **ラベル・承認コメント・Bot アカウントで承認を表す**

## 採用した選択肢と理由

採用: **扱いを3つに分け、PO の判断を体験と一方向ドアに絞る**。合否は決定論的なゲートで付け、LLM の判定は助言にする。承認は PO の merge で表す。

### 理由

- 面白さは人間にしか判定できないので、完全な無人化は品質を保証できない
- 一方で、仕様どおりかどうかは機械で判定でき、判定器もすでにある。そこまで PO が確かめるのは、最も希少な資源の使い方として誤っている
- LLM の判定は semantic-lint で精度も再現性も足りなかったので、合否には使わない
- PR は PO のアカウントで作られている
  - GitHub の仕様上、自分の PR は approve できない
  - エージェントは PO の権限で動くので、ラベルや承認コメントはエージェントにも付けられ、承認の証明にならない
  - そのため、承認を表すためだけの仕組みは作らない

### 3つの扱い

| 扱い | 対象 | merge する者 |
|---|---|---|
| 自動 | 遊ぶ人に見えるものが変わらず、一方向ドアにも合格基準にも触れない | CI |
| 体験確認 | 遊ぶ人に見えるものが変わる | PO がプレビューで遊んでから |
| 承認 | 一方向ドア、または合格基準（要求・要件、テストの削除、golden、E2E、CI、静的検査の設定、エージェント向けのルールなど）が変わる | PO が影響を確かめてから |

### 扱いの判定のしかた

- 扱いは、Producer の申告ではなく、差分の証拠から CI が決める
  - 変更されたパスで候補を出す
  - 一方向ドア面を golden として固定し、golden が変わった変更は承認にする
- 判定できないときは厳しい方に倒す
- PO の判断を助けるため、CI は体験レビュー票をジョブのサマリーに出す
  - 扱いとその理由
  - 変わった一方向ドア面
  - 関係する要件・仕様の ID
  - E2E のスクリーンショット

### 帰結

- Good
  - 一方向ドアに触れたかどうかが golden の差分で示されるので、PO はコードを読まずに影響を判断できる
  - 合格基準を変える変更は必ず承認になるので、実装と同じ変更の中で基準が黙って弱まることが無い
  - 正本が CI に置かれるので、どの実行環境で作った変更にも同じ判定がかかる
- Bad
  - パスで判定するので、見た目の変わらない UI のリファクタリングも体験確認になる
    - 画面ごとの見た目の差分（スクリーンショット比較）で格下げできるまでは、PO の確認が減りきらない
  - 「体験確認・承認の PR をエージェントが merge しない」ことは機械では強制できず、ルールで守らせる
  - golden や E2E の保守が増え、CI の時間が延びる
  - 自動 merge は、リポジトリ変数 `FACTORY_AUTO_MERGE` を有効にするまで動かない
    - 有効にするまでは、自動の扱いも PO が merge する

## 各選択肢の良し悪し

### 全 PR を PO が確かめる今の運用を続ける

- Good: 仕組みを足さずに済む
- Bad
  - PO の判断時間が、機械で確かめられる正しさの確認に使われる
  - 一方向ドアに触れたことを、PO が差分から読み取らなければならない

### 体験の判断も含めて完全に無人化する

- Good: PO の時間を最も減らせる
- Bad: 面白さという中核の品質を、誰も保証しない

### LLM の判定もゲートにする

- Good: 意味的な規約まで自動で止められる
- Bad: semantic-lint で精度も再現性も足りなかった。誤判定で止まる、または通ることが、決定論的なゲートへの信頼を下げる

### ラベル・承認コメント・Bot アカウントで承認を表す

- Good: merge と承認を分けて記録できる
- Bad
  - ラベルとコメントは、PO の権限で動くエージェントにも付けられ、承認の証明にならない
  - Bot アカウントは、権限とトークンの管理が増える

## 補足

- ADR-0003 は、実行されない受入条件の文書を廃止した。この ADR は受入条件を文書に戻さず、実行できる検査（テスト、golden、E2E）としてだけ持つ
- ADR-0001（問題ID）、ADR-0002（記録IDのパス）は、この ADR が golden で固定する一方向ドア面にあたる
