# 文書は意図・決定の理由・決まりに絞り、振る舞いはコードとテストを正とする

## 要約

- **決定**: 文書は「意図（要求・要件）」「決定の理由（ADR）」「決まり（仕様・設計原則・開発の手引き・エージェント向けルール）」に絞る。振る舞いの詳細はコードとテストを正とし、文書へ写さない。ユーザーストーリー・受入条件・画面の文書と、要件以外の upstream を廃止する。
- **主な選択肢**: 層を保って整合を取り続ける / 層を絞り、文書に残すものを決める / 文書をやめてコードだけにする。
- **背景**: 実装の大半をエージェントが行い、2週間で約500コミット進む。人手で振る舞いを写す層がずれ続け、決めたことと書き写しの区別もつかなくなった。

## 背景と問題

プロダクト文書は、要求 → 要件 → 仕様 → 画面、要求 → ユーザーストーリー → 受入条件の層と、各文書が上位のIDを指す upstream で構成していた。

- 仕様と画面は実装と一緒に更新される写しになり、実装より古い記述が残った。決めたことと、実装を書き写しただけのことが同じ文書に混ざり、どれを守るべきか区別できなかった。
- ユーザーストーリーと受入条件はどこからも使われず、受入条件は実行されなかった。
- upstream を使う仕組みは無く、ID の衝突や付け替えの手間だけが生じた。
- 決めたことの理由は PR や Issue に散り、後から辿るのが難しかった。

## 判断基準

- 古くなった文書がエージェントや人を誤らせないこと。
- 意図して決めたことが、知らずに戻されないこと。
- 文書の維持にかかる手間が、得られる価値を超えないこと。

## 検討した選択肢

1. **層を保って整合を取り続ける**
2. **層を絞り、文書に残すものを決める**
3. **文書をやめてコードだけにする**

## 採用した選択肢と理由

採用: **層を絞り、文書に残すものを決める**。理由: 失われると困るのは、何を目指し何を保証するか、なぜそう決めたか、毎回守るべき決まりの3つで、どれもコードからは読めない。振る舞いの詳細はコードとテストが持ち、文書に写すとずれる。

- 意図: 要求と要件。要件は要求を upstream で参照する。
- 決定の理由: ADR。理由を失うと戻されたり蒸し返されたりする決定だけを書く。
- 決まり: 仕様（アプリ・ゲーム共通の取り決めと、パズルごとの定義）、設計原則（DESIGN.md・GAME.md・APP.md）、開発の手引き（`docs/パズル/` の難易度文書）、エージェント向けルール（AGENTS.md・`.claude/rules`）。今の決定だけを言い切りで書き、理由や出典は書かない。
- 資料: 導入調査・メモ・立ち上げ・パズル候補の台帳。必要なときに読むもので、正本として維持しない。

レビューで決めたことは、同じ変更の中で、振る舞いはコードとテストに、守るべき決まりは決まりの文書に、理由が要るものは ADR に反映する。

### 帰結

- Good: 文書の量が減り、残る文書が正しいことを保ちやすくなる。
- Good: 決まりの文書が「今の決定」だけになり、守るべきものが読める。
- Bad: 要件から影響する文書を ID で辿れなくなる。
- Bad: 画面ごとの細部は文書から読めず、コードと DESIGN.md を見る必要がある。

## 各選択肢の良し悪し

### 層を保って整合を取り続ける

- Good: 要求から画面までを ID で辿れる。
- Bad: 実装の速さに整合が追いつかず、古い記述が残り続ける。

### 層を絞り、文書に残すものを決める

- Good: 守るべきものと書き写しを分けられる。
- Bad: 決めたことかどうかを見分けて書き直す手間が一度かかる。

### 文書をやめてコードだけにする

- Good: ずれが生じない。
- Bad: 意図と決定の理由が残らず、正しさを判定する基準が無くなる。

## 補足

- 文書の置き場所と書き方は `docs/README.md` と各ディレクトリの README を正とする。
