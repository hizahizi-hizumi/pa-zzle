# 棚上げ

現在のプロダクト定義とは別に、将来の検討対象として失いたくない要求・要件候補やパズル候補と、その補足メモを置く。

`docs/プロダクト/` の現在仕様の正本には含めない。棚上げした候補を置くこと自体は、調査・設計・実装へ着手することを意味しない。

## Issue との違い

- 棚上げは、候補そのものや検討状況を保持する。
- Issue は、調査・設計・実装・修正・正本化など、実行する作業の範囲と完了条件を管理する。
- 候補を棚上げするだけでは Issue を作らない。候補について具体的な作業へ着手するときに Issue を作る。

## 要件候補

`要件候補.csv` を一覧と索引にする。

- `ID`: 棚上げ内で候補を識別する。 `RQ-nnn` / `FR-nnn` / `NFR-nnn` など正本の識別子とは別物とする。
- `種別`: 候補の性質を示す。
- `概要`: 候補の内容を一覧で判断できる粒度で記す。
- `詳細`: 短い補足、または詳しいメモが必要な場合の `要件候補/<ID>.md` への相対参照を置く。不要なら空欄にする。

## パズル候補

`パズル候補.csv` は、パズル候補と採用フローの進み具合を見渡すための台帳にする。

- PoC初期の一次調査に挙がった候補を広く載せる。同名・同一系統として扱っているものはまとめてよい。
- `問題供給`、`難易度運用`、`スマホプレイ`、`導入判断` で、現在どこまで確認できているかを記す。
- 各ゲートの状態は厳密なワークフロー制御には使わず、`未確認`、`確認中`、`通過` など、その時点を判断できる短い表現を使う。
- `導入判断` は `未判断` / `実装候補` / `条件付き保留` / `見送り` / `正式採用` を使い、成立性調査での実装候補化と現在のプロダクトへの正式採用を区別する。
- `詳細` が必要な候補だけ `パズル候補/<ID>.md` を置き、各段階の調査・検証資料への索引にする。調査内容そのものは複製しない。
- 採用後の候補を必ず削除するなど、一覧から外す時期は固定しない。
- 実装順や着手予定は管理しない。具体的に着手するときは Issue で扱う。

候補から成立性調査・完成ゲーム化・正本化へ進める工程は [`../開発/パズル追加手順.md`](../開発/パズル追加手順.md) を参照する。
